作業デスクにはディスプレイが二台並んでいる。

左画面ではVS Codeを開いてブランチ競合の修正作業を進め、右画面のターミナルでは三つのローカルAgentが統合テストを並列で走らせている。

左側のターミナルで対話的な git rebase コマンドを叩こうとした瞬間、キー入力が突如として遮断された。カーソルが行の途中で完全に静止する。

見上げると、Playwrightが起動したChromiumウィンドウが画面の最前面に突然割り込んできていた。OSのキーボードフォーカスが完全に奪い去られてしまったのだ。バージョン管理用に叩いた一連のシェルコマンドは、そのままWebページの検索欄に流し込まれていた。

こんな目に遭って怒らないエンジニアがいるだろうか？

似たような自動化プロセスを走らせたことがある方なら、このカーソル強奪のストレスは痛いほど分かるはずだ。コードを書いている最中に、バックグラウンドのブラウザウィンドウが亡霊のように飛び出してきて思考の流れを断ち切る。

ブラウザの暴走を防ぐため、真っ先に思いつく対策は headless 無頭モードへの切り替えだ。しかし現実の開発現場では、ヘッドレス化によってさらに厄介なサイレント障害が引き起こされる。

第一にボット検知の遮断だ。保護機能を備えた多くの現代的Webシステムは、ヘッドレス環境を検知した途端に403エラーを返したり通信を遮断したりする。

第二にブラックボックス化によるフリーズだ。隠れたモーダルダイアログや捕捉されなかったJavaScriptエラーによって処理が停止し、ターミナルには120秒のネットワークタイムアウト待ちだけが残される。どこで止まっているのか？プロセスは動いているのにログは出ない。バックグラウンドのどの段階で死んだのか特定できず、デバッグのしようがない。

さらにリソース消費の問題もある。PlaywrightでChromeを動かすと、マルチエージェント並列環境で莫大な負荷がかかる。放置された五つのタブだけでメモリを1.6GB消費し、GPUプロセスがCPUコアを複数占有してファンが激しく回り続ける。

GitHubでPaul Nameless氏が公開しているオープンソース agweb は、まさにこうした開発現場の切実な不満を解消するために登場した。リポジトリは github.com/paul-nameless/agweb だ。重厚なChromiumフレームワークを完全に排除し、macOSネイティブのシステムWebKitエンジンを土台に据えている。

手元の開発環境に組み込んで二日間検証してみた。実測に基づく技術的な収支を整理してお伝えしたい。

## フォーカス強奪とメモリ消費：Playwright Chrome と ネイティブ WebKit の比較

PlaywrightはWebテストの自動化ツールとして成熟しており、極めて優秀だ。しかし自律型Agentにそのまま組み込むと歪みが生じる。従来の自動化フレームワークは「一回のセッションごとに独立したブラウザインスタンスを丸ごと立ち上げる」前提で設計されている。三つのAgentを並行稼働させると、アクティビティモニタには三組の巨大なGPUコンテキストと描画パイプラインが積み重なってしまう。

まずはメモリと待機時の消費電力という物理的な数値を見てみよう。数字は誤魔化せない。

M2 Maxチップを搭載したマシン上で、構造の複雑なドキュメントやテスト用Webページを五枚開き、三つの実行環境で比較した：

| 実行環境とアーキテクチャ構成 | 待機タブ5枚の物理メモリ消費 | 待機時のCPU負荷 | フォーカス強奪の挙動 |
| :--- | :--- | :--- | :--- |
| **Playwright ネイティブ Chrome** | 約 1.6 GB 物理メモリ | 5〜7コアが継続的に変動 | 頻繁にポップアップがフォーカスを強奪 |
| **Headless Chrome 無頭モード** | 約 730 MB 物理メモリ | 2〜3コアが軽度起動 | ポップアップなし、サイレント遮断の懸念 |
| **Agweb ネイティブ WebKit デーモン** | 約 590 MB 物理メモリ | ほぼ 0% に静止サスペンド | 単一ウィンドウ背面処理、フォーカス奪取ゼロ |

両者の最大の隔たりは、非アクティブな待機タブに対するサスペンド処理にある。

Chromeのバックグラウンド描画アーキテクチャは、非アクティブなタブに対してもタイマーやイベントループの定期ポーリングを維持し続ける。対するAgwebは、macOSネイティブWebKitが備える高度なサスペンド機構を直接呼び出している。

CPUの挙動を十分間観察してみた。Agentからの指示送信が止まると、二つのWebKit描画プロセスは三〜五秒のうちに負荷が6.8%から0.3%へと急速に落ち、そのまま完全に静止する。厳密なゼロではないものの、無視できる水準だ。

さらに大きな改善はキーボード操作の体験にある。

Agwebでは、ファイル選択、ダイアログ確認、ダウンロード承認といった全操作を、AgentがターミナルCLIを通じて直接応答する。画面上にOSネイティブのダイアログが飛び出すことはない。クリックやキー入力はmacOS底层のイベントストリームとしてシミュレートされ、滑らかなポインター移動軌跡を持つため、ホバーメニューやドラッグ操作も正常に認識される。

私は手元のコードを書き続け、Agentはバックグラウンドで処理を進める。私のカーソルは行末に留まり、一度として飛ばされることはない。

キーボードで Command+D を押すと、統合マルチタスク監視ダッシュボードが呼び出される：

<img src="https://img.freeaidog.com/images/blog/agweb-multi-agent-dashboard.webp" alt="Agweb マルチエージェントタブ統合監視ダッシュボード" />

各Agentの処理ストリームがサイドバーにタブとして整理される。UIはリアルタイムで部分更新され、左側でワークスペースの状態を確認し、右側で最新のDOM描画ビューを監視できるため、どのタスクが止まっているかが一目で把握できる。

## トークン収支：なぜ操作単位の差分Diffで数十万トークンを削減できるのか？

ブラウザ操作Agentを構築する際、多くの人は動作するかどうかだけに気を取られ、トークンの請求額を真剣に計算しない。

従来の自動化フローでは、シングルページアプリケーションに対してAgentが操作を一手進めるたびに、アクセシビリティツリー全体の完全なスナップショットを再取得することが多い。構造の複雑な現代のフロントエンドでは、整形後のスナップショットだけで8,000〜10,000トークン以上を消費してしまう。十数ステップに及ぶフォーム入力フローでは、DOM全体を繰り返し流し込むだけで数十分のうちに数十万トークンが消失する。テスト一回で大量のトークンを溶かすような請求に誰が耐えられるだろうか？

Agwebはこの課題に対し、操作単位の差分Diffメカニズムを採用した。

現在のページ上のインタラクティブ要素に対し、ref=e3 のようなセッション内で永続する参照識別番号を割り当てる。そのノードがDOM内に存在する限り、番号はセッション中ずっと固定される。Agentがクリックや入力指示を送ると、デーモンはその操作によって引き起こされたDOMの増分変化だけを返却し、ツリー全体の再取得を必要としない。

ターミナルでセレクターを送信する際は、外側をシングルクォートで囲む点に注意してほしい。私が最初に検証した際、習慣でダブルクォートを使ってしまい、zshが角括弧の内容をワイルドカード展開として処理した結果、原因不明の no such element エラーが発生して原因特定に二十分を浪費した：

```bash
# タスク専用ワークスペースを割り当てて対象ページを開く
agweb -w task open https://en.wikipedia.org/wiki/WebKit

# 現在のページの整理されたインタラクティブツリーを抽出
agweb -w task snapshot

# 外側をシングルクォートで囲みシェルの引用符剥離を防止
agweb -w task click 'role=button[name="Main menu"]'
```

コマンドラインは冗長なツリーを省き、増分レポートだけを即座に返す：

```text
### Changes
  - navigation "Site" [ref=e2]
-   - button "Main menu" [ref=e3]
+   - button "Main menu" [checked] [expanded] [ref=e3]
+   - list [ref=e1167]
+     - listitem [ref=e1168]
+       - link "Main page" [ref=e1169]
```

変化は明瞭だ。ボタンの状態が展開済みに更新され、その配下にリスト項目とホームページリンクが追加されたことが分かる。

Agentは次に操作可能な新しいref番号を即座に取得でき、高コストな全量snapshotコマンドを再度叩く必要が一切ない。社内の経費精算フォームのテストフローで実測してみたところ、従来の全量スナップショット方式では14ステップで11.8万トークンを消費していた処理が、差分増分方式に切り替えたことで3.6万トークンに抑えられ、コンテキスト全体で約70%の削減を達成した。浮いたトークン枠で、同じ日に二回以上の完全な回帰テストを追加実行できる計算だ。

## 認証情報とセキュリティ：パスワードをLLM対話ログから物理的に排除する

従来の自動ログインスクリプトには重大なプライバシー上の欠陥が存在していた。ブラウザにパスワードを入力させるため、多くのツールが平文のパスワードをそのままLLMのツール呼び出し引数に流し込んでいたのだ。

これは機密パスワードやワンタイム認証情報が、クラウドモデルの推論ログやローカルのチャット履歴ファイルに平文のまま記録されることを意味する。同僚と共有するためにログをエクスポートした際、パスワードが完全に露出してしまう危険性に誰が耐えられるだろうか？

Agwebは外部クレデンシャル注入パイプラインを採用してこの問題を解決している。

Agentが入力コマンドを実行する際、secret-cmd パラメータを使用して、pass や 1Password CLI、Bitwarden CLI といったローカルのセキュアな鍵管理ツールを指定できる：

```bash
# ローカルのpassツールがパスワードを復号しWebKitフォームに直接注入
agweb -w task fill "#password" --secret-cmd "pass show internal/staging-db"
```

実行チェーン全体がローカルシステムプロセス内部で完結する。Agentに返されるのは、フィールド入力が完了したことを示す真偽値の結果だけだ。パスワード自体はターミナルの標準出力にもLLMのコンテキストにも一切触れず、クラウドへの流出経路を物理的に遮断できる。

さらにマルチエージェント運用向けに、Agwebは名前付き永続プロファイルをサポートしている。コマンドに -p work を付与することで、複数のワークスペースが同一のログイン済みブラウザセッションを共有可能だ。メインAgentが一度ログインを完了すれば、補助Agent群は再認証なしでセッション状態を即座に再利用できる。

ただし運用上の注意点もある。あるタスクの操作によって誤ってログアウトされたりCookieが無効化されたりした場合、そのプロファイルに紐づく全Agentが一斉にオフラインとなる。並列Agentの障害調査時にはこの点を念頭に置いておく必要がある。

## ローカルビルド、CLIセットアップと頻出コマンド

本ソフトウェアは現在、macOS 26 以降の環境を必要とする。GitHub公式のReleasesページではビルド済みの Agweb.dmg パッケージが配布されている。ソースコードから自前でビルドする場合も手順はシンプルだ：

```bash
# ソースコードを取得し内部ビルドスクリプトを実行
git clone https://github.com/paul-nameless/agweb.git
cd agweb
./scripts/build.sh

# 生成されたバイナリをシステムパスにシンボリックリンク
build/Agweb.app/Contents/Helpers/agweb install-cli

# Claude Code および Codex 向けの自動スキルを登録
agweb install-skill
```

セットアップ完了後、日常的に多用する主要コマンドは以下の通りだ：

```bash
# 対象ページを開く【デーモン未起動時は自動起動】
agweb -w work-01 open https://news.ycombinator.com

# 現在のページから純粋なMarkdownテキストを抽出
agweb -w work-01 text

# フォーカスを奪わずにCAPTCHAや二要素認証を人間へ一時委譲
agweb -w work-01 ask "確認画面でSMS認証コードを入力してください"

# セッション全体の操作動画をMP4形式で録画
agweb -w work-01 video-start ./session-demo.mp4
agweb -w work-01 click 'text="Submit Order"'
agweb -w work-01 video-stop
```

## 制限事項と見送り基準：使ってはいけない場面とは？

メリットを多く述べてきたが、物理的な限界とトレードオフについても誠実に明記しておく必要がある。エンジニアリングの世界に無料の昼食は存在しない。

選定前に認識しておくべき明確な境界線は以下の三点だ：

第一に、macOS環境およびネイティブWebKitへの完全な依存だ。UbuntuやDebianサーバー、あるいはLinuxベースのDockerコンテナ内でヘッドレスCIを回す必要がある場合、Agwebは動作しない。その場合は迷わずPlaywrightを採用すべきであり、ここで時間を無駄にしてはならない。

第二に、Chrome専用のCDPプロトコル非対応である点だ。WebKitを基盤としているため、Chrome専用拡張機能やChrome DevToolsの独自デバッグプロトコルに依存するテストは一切互換性がない。

第三に、高度なアンチボット回避機能の限界だ。内蔵されたuBlock Originルールリストは四日ごとに更新されるものの、静的ドメインとCSS要素のフィルタリングに留まる。Cloudflare Turnstile等の強力な動的チャレンジを突破することはできない。そうしたサイトに対しては、無理にヘッドレスで突破しようとせず、通常の対話型ブラウザに切り替えるべきだ。

Macをメイン機として使い、日常的にPlaywrightのカーソル強奪に悩まされ、手元のターミナルでClaude CodeやCodexを走らせている開発者なら、Agwebは試す価値が十分にある。導入後に社内システムを一度動かし、カーソルが自分のコード行末に平穏に留まり続ける体験を確かめてみてほしい。
