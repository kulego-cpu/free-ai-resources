グラフィックボードの冷却ファンが急に高音で唸り始めました。

回転数は一気に二千八百回転まで到達。

ターミナルの文字出力速度は、毎秒 35 トークンで張り付いたままです。

遅いかと言われれば、完全に実用外というわけではありません。

しかし手元にある Radeon RX 7900 XTX は 24GB の大容量 VRAM と 96 基の演算ユニットを備えています。公式の llama.cpp を動かすと、なぜここまで伸び悩むのか疑問でした。

演算ユニットの大半は遊んでおり、メモリバス帯域の読み取り値は理論上限の三割にすら届きません。

まずテストの境界条件を明記します：単体カード、単一モデル、16k コンテキスト長、ホスト側 ROCm 6.2.4。ここに記載する数値はこの特定構成における実測結果であり、他のハードウェア環境へ無条件に当てはめることはできません。

そこで stew675 氏が公開している `llama-cpp-rdna-boosts` ブランチを試しました。

同じモデルファイル：Swift-1.5-Qwen3.8-27B-GGUF。

同じ量子化精度：Q6_K_L。

トークンの生成速度は毎秒 55 トークンまで跳ね上がりました。

プロンプトの事前読み込み処理はさらに劇的で、712 から 1318 まで一気に伸長。

カーネルを差し替えたことで精度が密かに落ちていないか、生成品質が破綻していないか。

ログを精査し、その仕組みを隅々まで解明することにしました。

## 汎用抽象化の代償とベンチマーク偽装流派の台頭

ローカル推論の実行環境は今、極めて厄介な分岐点に立たされています。

llama.cpp を代表とする統合型フレームワークは、あらゆるハードウェアを支える巨大な展示場のようなものです。

CPU、Apple Metal、NVIDIA CUDA、AMD ROCm、Intel SYCL、Vulkan まで、多種多様な基盤を同時に面倒見なければなりません。

コードベースは必然的に大量の汎用抽象化レイヤーで埋まります。

特定の GPU アーキテクチャに深く踏み込んだアセンブリパッチを本流へ統合することは、極めて困難を極めます。

本流のメンテナは全環境での安定稼働を第一に考える必要があります。メモリ配置を低レイヤーで触れば、旧世代ハードウェアでセグメンテーション違反を引き起こしかねません。そのため本流の更新速度は速いものの、特定のコンシューマ向けカード上での実行効率は、実用下限にとどまるケースが散見されます。

結果として、独自路線を歩むエンジニアが次々に現れました。

ここ半年間で、特定ハードウェアに特化した小規模エンジンがコミュニティで多数誕生しています。

Swift と Zig で Apple Silicon の統合メモリを限界まで絞り出すものや、モバイル NPU 向けに静的カーネル融合を行うものなどです。

しかし、そうした派生プロジェクトの中には危うい動きも見られます。

ソーシャルメディア上で非現実的な数値を誇示する過激なフォーク、例えば Strata や Basalt といったプロジェクトです。

これらは 16GB の単体カード上で、千億パラメータ級の MoE モデルが驚異的な速度で軽快に動くと主張します。

都合の良い話が本当に存在するのでしょうか。

実装を精査したところ、からくりが判明しました。速度数値を吊り上げるため、MoE モデルのエキスパート振り分け制御を勝手に書き換えていたのです。

モデル本来の判定ではメインメモリや SSD 上に退避されたエキスパートを呼び出すべき場面で、推論エンジンがその指示を無視し、VRAM 内に常駐している別のエキスパートへ強引に処理を押し付けていました。

文字自体は確かに機関銃のように高速出力されます。

しかし生成される文章は文脈を喪失し、論理が完全に崩壊していました。

モデルの思考品質を犠牲にして手に入れた見かけ上の速度向上など、実務開発においては何の役にも立ちません。

ルーティングロジックを改ざんされたエンジンに、本番環境のソースコード生成を任せられるでしょうか。

到底任せる気にはなれません。

## パッチ変更箇所の整理：Wavefront 制御とオンチップキャッシュ

`llama-cpp-rdna-boosts` が優れている点は、その変更範囲の抑制にあります。

量子化テーブルには一切触れていません。

MoE の振り分け制御も無変更です。

サンプリング処理にも手を加えていません。

主な改変は二点に集約されます：GEMM 行列乗算の Wave32 パス最適化、そして Attention 順伝播時における局所オンチップメモリ転送の効率化です。

これは AMD ハードウェアの世代間設計思想の違いに起因します：

データセンター向けの CDNA 系、例えば MI100 や MI300 は、伝統的な Wave64 の広い波面構造を採用しています；

一方、コンシューマ向け RDNA 系、RX 6000 から 7900 は、初代からネイティブな Wave32 構成であり、デュアルイシュー演算ユニットを備えています。

公式の ROCm バックエンドは、汎用的な HIP 互換レイヤーの設計方針を強く引き継いでいます。

多くの主要行列積カーネルにおいて、スレッドブロックが依然として広めの波面向けに構成されています。

データセンター向けカードでは問題なく動きますが、7900 XTX のようなカードでは波面のディスパッチ遅延が発生し、メモリコントローラがデータ取得を待つ間に演算コアが停止する事態を招いていました。

`llama-cpp-rdna-boosts` はこの中核 GEMM カーネルを書き直しています。

波面のサイズを RDNA が最も効率よく処理できる Wave32 に固定。

同時に Attention 処理におけるローカルメモリのデータ移動経路を再構成し、中間演算データを演算コア近傍の高速キャッシュ内に可能な限り留めることで、物理 VRAM への往復アクセスを大幅に削ぎ落としました。

ハードウェア監視グラフには明確な成果が現れました：

カードの消費電力は二百ワット強から定格の上限付近まで上昇；

VRAM 読み取り帯域幅もフラットな高い水準を維持し続けました。

## 実機検証環境とコンテナ起動手順

環境詳細とバージョン関係を明らかにしないベンチマークには意味がありません。

今回の検証で使用したハードウェア構成は以下の通りです：

- GPU 本体：AMD Radeon RX 7900 XTX 24GB GDDR6、アーキテクチャ識別子 Navi 31 および gfx1100。
- ドライバ環境：AMD ROCm 6.2.4 ユーザランドパッケージ、OS カーネル Linux 6.11。
- 接続トポロジ：Thunderbolt 4 外付け GPU ボックス接続、PCIe 4.0 x4 リンクネゴシエーション。
- バス帯域による影響：Thunderbolt 4 の実効スループットは約 3.2 GB/s です。デコード処理中はモデル重みが VRAM に常駐するため影響は皆無ですが、事前読み込み処理ではホストからデバイスへ大量のトークンを転送するため、マザーボード直接接続と比べて約 8% の事前読み込み速度低下が生じます。
- 検証モデル：ukisai 氏公開の Swift-1.5-Qwen3.8-27B-GGUF、量子化形式 Q6_K_L、総容量約 21.4 GB。
- 投機デコード：投機実行オプションを有効化、パラメータ `--draft 2`。

バージョン表記に関する補足事項：

コンテナイメージのタグ名に `server-rocm-10.1` とありますが、この 10.1 は作者の CI 自動構築パイプライン番号であり、AMD 公式のバージョンではありません。イメージ内には gfx1100 向けにビルドされた ROCm 6.2 実行ライブラリが格納されており、ホスト側の 6.2.4 ドライバと正常に連動します。

イメージの取得：

```bash
podman pull ghcr.io/stew675/llama-cpp-rdna-boosts:server-rocm-10.1
```

モデル配置場所をマウントし、GPU デバイスノードを渡して起動します：

```bash
podman run --rm -it \
    --network=host \
    --device /dev/kfd \
    --device /dev/dri \
    --group-add video \
    -v "$HOME/models:/models" \
    "ghcr.io/stew675/llama-cpp-rdna-boosts:server-rocm-10.1" \
    /llama-server \
    -m /models/Swift-1.5-Qwen3.8-27B-Q6_K_L.gguf \
    --host 0.0.0.0 \
    --port 8080 \
    -ngl 99 \
    -c 16384 \
    --ubatch-size 512 \
    --flash-attn \
    --draft 2
```

導入時の実務上の注意点：

初回起動時、`--flash-attn` を付け忘れたところ、ターミナルに以下の警告が出力されました：

```text
ggml_cuda_op_flatten: flash attention disabled, falling back to unoptimized rocm attention kernel
```

この状態ではデコード速度は毎秒 38 トークンにとどまりました。

明示的に `--flash-attn` を付与することで、Wave32 向けに再構成された Attention カーネルが正常に稼働します。

稼働中に `rocm-smi` で取得した状態は以下の通りです：

## 性能対照表と生成精度の多角検証

測定結果を整理します。

同一テスト機上で、公式本流 b4120 とパッチ適用コンテナを比較し、長文コード生成を五回連続実行した中央値を採取しました：

| 推論エンジンバージョン | コンテキスト事前読込速度 | 単一トークン生成速度 | 常駐 VRAM 容量 | 回帰テスト通過率 |
| :--- | :--- | :--- | :--- | :--- |
| 公式本流 llama.cpp b4120 | 712 t/s | 35.2 t/s | 21.8 GB | 100% |
| rdna-boosts 特化パッチ版 | 1318 t/s | 55.4 t/s | 22.1 GB | 100% |

実測値の客観的評価：

事前読み込みスループットは毎秒 712 から 1318 トークンへと向上；

生成速度は毎秒 35.2 から 55.4 トークンへと加速；

常駐 VRAM は 21.8GB から 22.1GB へと約 300MB 増加しましたが、これは Wave32 展開用に静的確保されたワークスペース領域に起因します。

注意点として、この測定値は単体カード、Q6_K_L、16k コンテキストという特定条件でのみ有効であり、あらゆるモデルや超長文条件へ一般化できるものではありません。

品質検証として、複雑な Python アルゴリズムと型注釈を含む 50 問の回帰テストを実施しました：

双方から生成されたコード構文木は完全一致し、通過率は 100% を達成；

技術応答二百件の検証セットにおいて、Perplexity の変動幅は一万分の三未満にとどまりました。

極端なロングコンテキストにおける精度変化を完全に排除するには、32k 以上での logits 差分サンプリングが今後必要となります。

しかし現段階の実務開発において、意味的な品質低下は確認されませんでした。

## 適用限界とバージョン固定の代償

本プロジェクトはバージョンを固定して運用する用途に適しています。

改変箇所が RDNA3 の GEMM とキャッシュ転送に絞られており、ルーティングや量子化に触れていないため、トラブル時の原因切り分けが容易です。

ただし、代償も存在します：

パッチは本流の特定コミット、例えば公式 b4120 などに強く依存しています。

本流の llama.cpp は頻繁にコアロジックを更新します。KV キャッシュのメモリ管理やバッチ処理方式が変更されれば、独自パッチは再度のリベース作業を余儀なくされます。

実務で導入する場合は、以下の運用ルールを推奨します：

第一に、検証済みのコンテナダイジェストまたはタグを厳格に固定し、最新版を無警戒に追従しないこと；

第二に、マザーボード直接の PCIe 4.0 x16 スロットで運用可能であれば、外付け環境よりも事前読み込み速度がさらに約 8% から 10% 向上するため、固定ワークステーションでの運用を検討すること；

第三に、モデル仕様の変更でパッチ版が起動しなくなった場合は、即座に安定した公式本流イメージへ切り替えられる予備構成を整えておくこと。

毎秒二十トークンの速度向上のために、本流から切り離されたパッチイメージを維持し続ける運用を選びますか。

急速に進化を続ける本流フレームワークの中で、ハードウェア特化パッチはどれだけの期間、優位性を保ち続けられるのでしょうか。
