開発用 Linux サーバーで `Claude Code` を使ってディスク IO の調査を進め、MacBook に戻って `Codex` へ引き継ごうとすると、たいてい同じ壁にぶつかる。両方のセッション履歴がマシンごとに分断されているのだ。

エラーログをもう一度貼り直すのか。30 分分の試行錯誤を新しいプロンプトに打ち直すのか。2 回もやればうんざりする。

昨日 Atuin が `18.24` で公開した `Threads` は、この手間を正面から潰しにきた。500 行で消えてしまう `.bash_history` を暗号化同期で救ったのと同じ発想で、`Claude Code` や `Codex`、`OpenCode` がホームディレクトリに残す追記型ログをそのまま同期基盤へ流す。

本稿の根拠は 3 つだけだ。`blog.atuin.sh/threads-agent-sessions/`、`github.com/atuinsh/atuin` の `v18.24.6` リリースノート、そして Hacker News スレッド `50453637` の議論である。手元に複数台のプライベート同期サーバーを組んで負荷計測できる環境はないため、同期遅延やスループットの実測値は書かない。

## Hook 不使用：ローカルのセッションファイルを直接解析する

最初は各エージェント CLI に専用プラグインを差し込む仕組みかと思ったが、コメント欄で開発者 `ellieh` が否定していた。現在の `Threads` は Hook を一切使っていない。各ツールがローカルに書き出すセッションファイルを直接パースし、会話ターン、実行コマンド、エラー出力をインデックス化している。

現時点の対応ツールは `Claude Code`、`Codex`、`Pi`、`Omp`、`OpenCode` の 5 つ。

導入と有効化は 3 コマンドで済む。

```bash
curl --proto '=https' --tlsv1.2 -LsSf https://setup.atuin.sh | sh
atuin resume
atuin mcp install claude
```

`atuin resume` を叩くと TUI が立ち上がる。過去の作業をキーワードで検索できるうえ、開発サーバー側で途中まで進めたスレッドを手元の MacBook にフォークして別ツールで続行できる。さらに `atuin mcp` を繋げば、新しいエージェント自身が過去の調査履歴を参照できるようになる。

ただ、便利さの裏に弱点もある。セッションログは厳密な DB スキーマではない。各ツールの仕様変更で形式が揺れやすく、現に `Claude Code` のシェル経由ファイル編集 diff だけで個別パッチが必要になっている。上流 CLI がフィールド名を 1 つ変えただけで、取り込みが静かに欠落しないだろうか。

## v18.24.6 の修正履歴に見える 4 つの実装上の地雷

公開直後から `atuinsh/atuin` は `18.24.6` まで細かく更新されている。宣伝文句よりリリースノートの修正項目の方がよほど正直だ。

- **シェル終了時の無限ハング**：コミット `4668` では、バックグラウンド起動前に継承ファイルディスクリプタを閉じ忘れて `pty-proxy` が終了時に固まる不具合を修正した。
- **macOS ソケット管理の競合**：コミット `4669` では `launchd` によるソケット管理を外している。Apple 環境の自動起動とソケット制御が衝突していたためだ。
- **Claude Code の diff 漏れと鍵書き込み**：`threads` 向けに 2 件の修正が入り、シェル経由編集の diff 取得補完と `atuin` 鍵名を含む書き込みパッチの保持が追加された。
- **MCP 依存ライブラリの更新遅延**：コミット `4690` で `rmcp` の脆弱性 3 件は更新されたが、SQLite 関連の修正は `sqlx` 側の互換性待ちで据え置きとなっている。

`4668` の記述を見て、思わず手元の端末プロセスを確認した。常駐デーモンを複数動かす環境では FD リークによるゾンビ化が一番厄介だ。まだ高頻度でパッチが飛ぶ段階なので、業務用の主力マシンへ無条件で常駐させるなら切り戻し手順を用意しておきたい。

ノイズ問題も現実的だ。Superlogical Rex を開発する `nzoschke` は、コーディングセッションの大半が使い捨ての実験であり、全部をグローバル履歴へ突っ込めば本当に必要な文脈が埋もれると指摘した。対照的に `justCallMeOmid` は、作業単位ごとにディレクトリを分けてログを置き、完了後は生ログを消して要約だけをベクトル DB へ残す運用に振り切っている。

## セキュリティ重視派が同期をためらう本当の理由

`Threads` の安全性を語るとき、多くの人は E2E 暗号化の強度ばかりを気にする。

暗号設計自体は筋が通っている。運用形態は大きく 3 パターンに分かれる。

**完全ローカル**——データは `~/.local/share/atuin` に留まり外部サーバーへ出ない。ただし同じホスト上でサンドボックス化されていない別プロセスや雑に動かしたスクリプトからは読める。単機での検索とバックアップ目的ならこれで十分だ。

**セルフホスト**——社内サーバーや自宅 NAS に同期先を置く構成。鍵配布を自前で管理する手間があり、さらにエージェントが `atuin mcp` 経由でアクセスした時点で中身は平文として読まれる。暗号化が効くのは通信経路上だけで、認可済み端末の内部では無防備になる。

**公式ホスト E2EE**——クライアント側で暗号化してから送信するため、運営側も中身を読めない。その代わり、登録済み端末の 1 台でも鍵を抜かれれば同期済み履歴全体が露出する。これはバグではなく共有履歴という設計そのものの代償だ。

Hacker News の `petesergeant` はここを理由に採用を見送っている。エージェントごとに独立サンドボックス、個別暗号化クレデンシャルストア、定期的なログスキャンまで組んで隔離を徹底してきたのに、全マシンの履歴を 1 つの検索プールへ集約すれば、苦労して築いた境界が崩れてしまう。

さらに厄介なのがツール側の権限仕様だ。

`ahmedketata` の指摘によれば、`Claude Code` でうっかり恒久許可を押すと、機密を含んだコマンドが平文のまま `.claude/settings.local.json` に残る。その断片がセッションログ経由で同期キューへ流れ込む。通信路が暗号化されていても、別の低信頼エージェントが `atuin mcp` で検索すればそのまま読めてしまう。この経路を眺めていて、根本的な自動防御は難しいと感じた。利用者が毎回 settings ファイルを監査する前提は現実的ではない。

折衷案もある。`dietr1ch` は中央同期サーバーを使わず、機密除去済みのバックアップだけを `Syncthing` で同期し、`grep` と `skim` で検索している。ツール横断の即時フォークは諦める代わりに、マシン間の権限境界をはっきり保てる。

## 導入してよい場面と、ローカルに留めるべき場面

もっとも、実用上の救済力も確かにある。スレッド内の `nklmilojevic` は、未コミットの `git worktree` を誤って消した際、`Atuin Threads` の履歴から変更内容を丸ごと復元できたと報告している。単なる `.bash_history` ではローカルの `grep` 止まりで、マシンを跨いだ変更や消えた worktree の文脈までは戻せない。

したがって当面の使い分けは次の 2 系統に絞るのが無難だ。

- 個人検証機や非機密リポジトリ：`Atuin 18.24.6+` で `atuin resume` を回し、Linux 開発機から MacBook へ `Claude Code` と `Codex` の調査文脈を引き継ぐ。
- 本番鍵、社内認証情報、顧客データを扱う端末：マシン間同期はオフのままにし、`atuin mcp` を自律エージェントへ常時接続しない。保存するならローカルで正規表現によるマスク処理を通す。

試す前に、最低限この 3 点だけは確認しておきたい。

1. `atuin --version` を実行し、`pty-proxy` の FD リーク修正が入った `18.24.6` 以上であることを確かめる。
2. `atuin mcp install` を打つ前に `.claude/settings.local.json` と `.env` の履歴を確認し、実トークンがログに混ざっていないか洗う。
3. 私用ノート PC と会社の踏み台サーバーで同じ同期アカウントを使う場合、踏み台側の操作履歴まで自宅環境へ引き戻して本当に問題ないか。
