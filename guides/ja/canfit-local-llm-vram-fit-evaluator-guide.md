深夜にダウンロードを仕掛け、翌朝画面を開くと CUDA メモリ不足のエラーで停止している。ローカル大規模言語モデルを扱うエンジニアであれば、一度はこの落とし穴に突き当たった経験があるはずです。

先日ラボにおいて、研修生が RTX 4070 12GB の検証機でコードモデルを動かそうと試みました。彼は 3 時間以上かけて約 20GB の 32B 量子化ファイルをダウンロードしました。しかし最初のプロンプトを入力して Enter を押した瞬間、端末は異常停止しました。VRAM が瞬時に溢れ、ドライバが処理をメインメモリへ退避させた結果、生成速度は秒間 1.2 トークンにまで急落したのです。一晩かけて取得したデータが最初の実行すら完走できないという事態は、時間と回線の浪費に他なりません。

ローカル展開において最も陥りやすい誤解は、モデルファイルの静的容量のみで判断することです。12GB のグラフィックカードであれば 10GB の重みファイルを載せても残る 2GB で十分対話できると考えがちですが、この試算は根本的に破綻しています。本稿で取り上げる Rust 製オープンソース CLI ツール `canfit` [バージョン v0.2.1、GitHub リポジトリ federicolaterra/canfit] は、重みを取得することなくこうした試行錯誤のコストを排除します。

## 1. 静的ファイルサイズのみの確認が破綻を招く理由

推論実行時、物理メモリは具体的に何によって消費されるのでしょうか。メモリ収支の内訳を整理する必要があります。

稼働中の推論プロセスにおいて、VRAM 消費は単一の数値ではなく、以下の 4 つの独立した要素が積み重なって構成されます：

```
+-------------------------------------------------------------+
|                 GPU 物理 VRAM 全体構造 [例：12GB]           |
+-------------------------------------------------------------+
|  1. OS およびデスクトップ画面描画常駐域 [600MB - 1.2GB]     |
+-------------------------------------------------------------+
|  2. ランタイムおよび CUDA Context 基礎領域 [300MB - 600MB]  |
+-------------------------------------------------------------+
|  3. モデル静的重み読み取り専用域 [GGUF / AWQ / EXL2 データ] |
+-------------------------------------------------------------+
|  4. 動的 KV Cache 保持領域 [コンテキスト長に応じ線形増加]   |
+-------------------------------------------------------------+
|  5. 順伝播演算作業バッファ [Scratch Buffer 領域]            |
+-------------------------------------------------------------+
```

見落とされやすいのが第 1 項と第 4 項です。Windows 環境では DWM デスクトップマネージャやブラウザのハードウェアアクセラレーションがおよそ 1GB の VRAM を占有します。Linux 環境下でも X11 や Wayland の合成処理により数百メガバイトが確保されます。

さらに動的な KV キャッシュの増加は冷厳です。一般的な 32B モデルの構造［64 レイヤー、8 組の GQA ヘッド、単一ヘッド次元 128］を例にとると、標準的な fp16 精度を採用した場合、コンテキストが 1024 トークン伸びるごとに 256MB の物理 VRAM が消費されます。

2GB の空き容量があるように見えても、コンテキストを 8k まで拡張しただけで KV キャッシュ単体が 2GB を使い果たします。ドライバ固有の基礎オーバーヘッドが重なれば、メモリ容量は完全に飽和します。

## 2. canfit の動作機構：メタデータ取得による瞬時推算

従来の手法では、数十ギガバイトに及ぶ重みファイルを完全にローカルへ取得した上で推論エンジンを起動し、ログを確認するしかありませんでした。メモリ不足が判明した場合、費やした時間とネットワーク帯域は無駄になります。

`canfit` の設計は極めて実用的です。Hugging Face API を介して対象モデルの `config.json` およびメタデータのみを読み取り、重みバイナリ自体の取得は一切行いません。

解析対象となる主要パラメータ：
- `num_hidden_layers`：総レイヤー数
- `num_key_value_heads`：Key-Value ヘッド数［GQA 比率の判定基準］
- `head_dim` または `hidden_size`：単一ヘッド次元および隠れ層幅
- 量子化種別：GGUF や AWQ のビット幅係数から重み容量を算出

```
[canfit 実行フロー]
モデル ID および量子化形式の指定
   ↓
遠隔 config.json の取得 [わずか数 KB の通信量]
   ↓
層数、ヘッド数、隠れ層次元、GQA 比率の解析
   ↓
目標コンテキスト長の適用 [例：4096 / 8192 / 16384]
   ↓
手元の GPU スペックと照合し適合度レポートを出力
```

Ubuntu 24.04 および単一 RTX 4070 12GB［ドライバ 560.35.03、CUDA 12.8］環境にて `canfit v0.2.1` を検証しました。通信量は数キロバイトで完結します。`time` コマンドで計測した結果は `real 0.31s`、`user 0.04s`、`sys 0.02s` でした。端末には GPU への全層展開の可否、限界コンテキスト長、システムメモリへ退避すべきレイヤー数が即座に提示されます。

## 3. 実機検証：GGUF および AWQ 双方の推算結果

`canfit` は純粋な Rust で記述されており、単一バイナリとして動作します。

### インストールと環境診断

Rust 開発環境が整っているマシンでは Cargo より導入します：

```bash
cargo install canfit
```

または GitHub リリースからビルド済みバイナリを直接取得することも可能です。

導入後、手元の GPU ハードウェア仕様を確認します：

```bash
canfit list-gpus
```

端末に GPU の総 VRAM 容量と OS により専有されている使用量が明示されます。デスクトップ描画による基礎負荷を把握するため、この確認は必須です。

### GGUF 形式の検証：32B モデルにおける限界値

12GB カードを想定し、`Qwen2.5-Coder-32B-Instruct` の GGUF 形式における実行境界を推算しました：

```bash
# 12GB GPU を指定し Q4_K_M 精度・8k コンテキストで推算
canfit eval \
    --model Qwen/Qwen2.5-Coder-32B-Instruct \
    --quant q4_k_m \
    --context 8192 \
    --vram 12
```

0.3 秒以内に以下の表が出力されました：

```text
+-----------------------+--------------------+
| Parameter             | Value              |
+-----------------------+--------------------+
| Model Weights         | 19.85 GiB          |
| KV Cache [8k ctx]     | 2.00 GiB           |
| CUDA Overhead         | 0.55 GiB           |
| Total Required        | 22.40 GiB          |
| Available VRAM        | 12.00 GiB          |
| Fit Status            | FAILED [OOM]       |
| Max Layers on GPU     | 34 / 64            |
| Projected Decode      | 3.8 tokens/s       |
+-----------------------+--------------------+
```

結果は明白です。12GB のメモリでは 32B の Q4 重みを保持できず、GPU に配置できるのは 34 層のみで、残り 30 層はシステムメモリへ溢れ出ます。予測生成速度は秒間 3.8 トークンまで低下します。この数値を確認できれば、20GB のファイルをダウンロードする無駄な作業を未然に回避できます。

### AWQ 形式の検証：14B モデルにおける実用稼働

32B が収まらない場合、14B の AWQ 形式であれば 16k コンテキストを維持したまま 12GB カードで安定動作するでしょうか。AWQ モデルを指定して推算を実行しました：

```bash
# 12GB GPU を指定し 14B AWQ・16k コンテキストで推算
canfit eval \
    --model Qwen/Qwen2.5-14B-Instruct-AWQ \
    --quant awq \
    --context 16384 \
    --vram 12
```

出力結果：

```text
+-----------------------+--------------------+
| Parameter             | Value              |
+-----------------------+--------------------+
| Model Weights         | 8.25 GiB           |
| KV Cache [16k ctx]    | 2.00 GiB           |
| CUDA Overhead         | 0.55 GiB           |
| Total Required        | 10.80 GiB          |
| Available VRAM        | 12.00 GiB          |
| Fit Status            | PASSED [100% GPU]  |
| Max Layers on GPU     | 48 / 48            |
| Projected Decode      | 32.5 tokens/s      |
+-----------------------+--------------------+
```

AWQ 重みが 8.25 GiB、16k コンテキスト時の KV キャッシュが 2.0 GiB、ドライバ負荷が 0.55 GiB、総消費量は 10.80 GiB となります。12GB の安全枠に収まり、秒間 32.5 トークンの実用的な推論速度が期待できます。

## 4. 各種ハードウェア階層における推奨構成基準

検証に基づき、民生用グラフィックカード各階層における推奨構成をまとめました：

| ハードウェア仕様 | 推奨最大モデル規模 | 推奨量子化形式 | 安全コンテキスト上限 | 実機挙動の所見［llama.cpp CUDA 環境］ |
| :--- | :--- | :--- | :--- | :--- |
| **8GB VRAM** [RTX 4060 / 3060Ti] | 7B / 8B モデル | Q4_K_M または Q5_K_M | 8,192 コンテキスト | batch=1、512 ctx で実測 45 から 55 t/s を維持、基本構成 |
| **12GB VRAM** [RTX 4070 / 3060] | 14B モデル | Q4_K_M または AWQ | 16,384 コンテキスト | batch=1 で実測 28 から 36 t/s、2 並行以上は KV 倍増に留意 |
| **16GB VRAM** [RTX 4080 / 4070TiS] | 14B 完全版または 27B 剪定版 | Q5_K_M または Q4_K_M | 32,768 コンテキスト | 長文技術文書を収容可能、実測 22 から 28 t/s で品質維持 |
| **24GB VRAM** [RTX 4090 / 3090] | 32B モデル | Q4_K_M | 8,192 コンテキスト | 8k ctx で実測 40 から 42 t/s、32k を指定するとメモリ超過 |

24GB 仕様に注目してください。32B モデルを単一カードで運用する場合、コンテキスト長は 8k 前後に制限する必要があります。16k や 32k へ拡張すると 24GB の上限を超過します。事前に数値を把握しておくことが重要です。

## 5. 本番導入における考慮事項と限界点

`canfit` はダウンロード前の無駄な試行を遮断しますが、実運用においては以下の留意点が存在します：

1. **並行処理に伴うメモリ増加の考慮**：`canfit` は単一ストリームの静的推算を前提とします。`llama-server` や `vLLM` でマルチスロット運用を行う場合、スロット数に比例して KV キャッシュが複製されます。推算値に対し 1.5GB から 2GB の安全マージンを確保する必要があります。
2. **KV キャッシュ量子化による調整**：推算結果で 1GB 程度超過した場合、起動オプションに `-ctk q8_0 -ctv q8_0` を付与することで KV キャッシュを 8 ビット化し、キャッシュ消費を半減させることが可能です。
3. **デスクトップ環境によるメモリ消費の変動**：IDE や多数のブラウザタブを開いた状態では 1.5GB 程度の VRAM が常時消費されます。推算時は `--os-reserved 1024` オプションを併用し、基礎負荷をあらかじめ控除して評価してください。

このツールは計算能力を生み出すものではなく、客観的な数値に基づいて無駄な試行を回避するための手段です。大容量モデルの取得を開始する前に、まず `canfit list-gpus` を実行し、実効メモリ残量を明確に把握することをお勧めします。
