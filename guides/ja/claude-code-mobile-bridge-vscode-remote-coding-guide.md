Claude Code に大規模な単体テスト群を実行させると、完了までに数分間の待ち時間が発生します。

この隙間時間は居心地が悪いものです。画面の前でじっと待つのは退屈であり、ソファに移動したり飲み物を取りに行った隙にテストが落ちた際、エラー内容を一行確認するためだけにデスクへ戻ってキーボードを叩き直すのは非効率です。

これまでリモートデスクトップも試しました。しかし 6 インチの画面でピンチズームを繰り返し、仮想ポインタで小さなターミナルを探す作業は数分で限界を迎えます。スマホのブラウザで独立した Claude を開く方法も不便でした。別のチャット画面には現在の作業コンテキストが一切共有されておらず、エラー原因を尋ねても直前の実行コマンドやプロジェクト構成を聞き返されるため、端末のログを延々とコピーして渡す羽目になります。

先日 V2EX の共有創造ノードにおいて、VS Code 拡張機能 liliangshan.claude-code-config-helper が公開されました。VS Code v1.95 以上および Node.js v20.18 環境に対応し、軽量な中継サービスを待機させます。デスクの PC は Claude CLI v0.2.14 でタスクを動かし続け、スマホのブラウザから同一セッションへ直接接続して会話を継続できます。

キーボードから離れた状態で同じ文脈を引き継げるのか。実際の業務コード改修においてスマホ操作がどこまで実用になるのか。サブスクリプション期間計算の改修プロジェクトで丸一日検証しました。

## スマホを指示出し端末に限定する運用の境界線

スマホはこのフローにおいてエディタではなく、単なるリモコンです。六インチのタッチ画面でファイルパスを打ち込むのは現実的ではありません。

担える役割は三つです。単体テストの合否を確認し、修正の方向性を指示し、モデルが迷走した際に停止させることです。デスクに戻ってから差分を確認し、納得した上でコミットします。

実務での日付計算を例に挙げます。会員特典の付与期限を月末付与で計算する際、packages/billing/src/services/subscription.ts における 2027 年 1 月 31 日の境界値テストで不合格が出たとします。

デスク前にいると、開発者は直感的にエラーを直してと大まかな指示を出しがちです。モデルはテストを通すためだけに、テスト側の期待値を書き換えて合格させてしまう危険があります。

スマホ中継を挟む運用では、作業のリズムが明確に分かれます：

```text
デスクでの制約指示
"npm test -- test/unit/expiry.spec.ts -t subscription-expiry
期限計算テストのみ実行、最初の失敗入力と実際値を報告、ファイル編集は禁止"
    │
    ▼
ソファでスマホブラウザから確認
入力 2027-01-31T23:59:59Z に対し、2 月の 31 日不在による境界エラーを確認
    │
    ▼
スマホから業務ルールを裁定
"実装とテストの双方が想定する計算ルールをまず報告せよ、
単に合格させるためにテストの期待値を改変することは禁止"
    │
    ▼
デスクへ戻り差分を確認
他の課金プランへ影響がないかを精査し、Git コミットを実施
```

ソファにいながら送信した一行の制約指示は、デスク側で実行中の Claude Code セッションへ直接流し込まれます。スマホでログを貼り直す手間がなく、モデルが勝手にテストコードを改ざんする事態も防げます。指示出しと大画面での検証を分担する運用は快適です。

## ネットワーク構成とローカル中継を確立する 3 手順

スマホから接続する際、最初に確認すべきはネットワーク構成です。バインド先のアドレス設定を誤ると接続できません。

中継サービスを 127.0.0.1 のまま待機させるとどうなるか。同一の Wi-Fi 環境にあってもスマホからは接続できません。ループバックアドレスは自端末からの通信しか受け付けないためです。

接続方法は二通りあります。0.0.0.0 にバインドして authKey 認証トークンを設定しローカル IP 経由でアクセスするか、拡張機能が提供する暗号化 WebSocket 中継ルートを利用するかです。

ソースコードは GitHub の `liliangshan/claude-code-config-helper` にて公開されています。設定は以下の 3 ステップです：

### ステップ 1：デスクトップ側の基本設定

VS Code の拡張機能マーケットプレイスで拡張 ID liliangshan.claude-code-config-helper を検索し、公開者が liliangshan であることを確認して導入します。端末側には Node.js と Claude CLI が導入済みである必要があります。

サイドバーの LLS CCAI アイコンを開き、ローカルの Claude CLI 実行パスを選択し、モデルの API 認証情報を設定します。

パネルからテスト指示を送信し、応答がストリーミングされることを確認します。

### ステップ 2：対象ワークスペースの認証と紐付け

VS Code で作業対象のプロジェクトフォルダを開きます。

チャット入力欄の下にあるリモート接続ボタンをクリックします。デバイス識別用のアカウントを作成してログインし、現在開いているワークスペースを紐付けます：

```json
// 局域網直結を行う場合は 0.0.0.0 にバインドし認証トークンを設定
{
  "remoteBridge.bindHost": "0.0.0.0",
  "remoteBridge.port": 9120,
  "remoteBridge.authKey": "CUSTOM_LOCAL_TOKEN_HEX",
  "remoteBridge.workspace": "current-project-root"
}
```

初回はテスト用リポジトリを使い、スマホからの送信がどのターミナルに反映されるかを目視確認することを推奨します。

### ステップ 3：スマホブラウザからのアクセス

スマホのブラウザで中継アドレスまたは 192.168.1.120:9120 などのローカル IP を開き、アカウント認証またはトークン入力を行います。

画面にはオンライン状態の PC 名、プロジェクト名、稼働セッションが一覧表示されます。メインワークスペースを選択し、読み取り専用の指示を送信してみます：

```text
プロジェクトの計算仕様を把握したい、最初に確認すべきファイルを提示せよ、コード編集は不要
```

デスクのモニターに目をやると、全く同じ文言が VS Code のターミナルに反映され、続いてモデルの思考プロセスと推奨ファイル名がスマホ画面へリアルタイムに中継されます。

## セッション運用の勘所：主セッションと並行調査の使い分け

操作画面には、主ワークスペースと並行タスクという二つの入口が用意されています。

この二つをどう使い分けるべきか。選択を誤るとコンテキストが分断されます。

原則は単純です。直前の、続けて、二つ目のエラーといった指示代名詞を含む追問は、必ず同一の主セッションに送信しなければなりません。

テストで複数のエラーが出た際、二番目のエラーも同じ原因かと尋ねたい場合、この追問は主セッションでのみ成立します。主セッションだけが直前のテスト終了コードとスタックトレースを保持しているためです。誤って新規の並行タスクに送信すると、モデルは何のことか理解できません。

並行タスクは、完全に独立した読み取り専用の調査に適しています。

主セッションがコードを改修している間、並行タスクは読み取り専用に徹します。両者に subscription.ts を同時に触らせてはいけません。差分が上書きされ、どこが基準線か分からなくなります。並行タスクにはファイル名と行番号の列挙のみを命じます：

```text
コード全体で一ヶ月を一律三十日と仮定している箇所を抽出せよ、ファイル名と行番号のみ列挙し、変更は加えるな
```

両タスクは同一のソースコードを参照しますが、コンテキストウィンドウは完全に分離されています。片方が修正を進め、もう片方が調査を担います。

## 運用現場での注意点：遵守すべき 4 つの安全基準

便利なツールですが、スマホから遠隔で作業を進める上では注意すべき落とし穴があります。

### 注意 1：PC のスリープによる通信切断

スマホは単なる操作画面であり、実処理を行う本体はデスクの PC です。

指示を出した後に席を離れたところ、スマホ側の表示がオフラインになった事例がありました。操作のない状態が数分続いたことで、MacBook がディスプレイ消灯に伴いネットワーク接続を切断してしまったのが原因でした。

離席して作業を継続する場合、PC 側がスリープに入らない設定にする必要があります。ターミナルで caffeinate -dimsu -t 7200 を実行して一時的にスリープを防止する運用が有効です。

### 注意 2：画面の停止ボタンは変更の取り消しではない

スマホの操作画面には赤色の停止ボタンが配置されています。

停止ボタンを押しても、すでに行われたファイル変更は元に戻りません。

このボタンはターミナルで SIGINT シグナルを送信する処理と同等です。後続のトークン生成やツール実行を打ち切るだけであり、直前のステップでディスクに書き込まれたコードはそのまま残ります。PC に戻った際は git status および git diff --stat HEAD~1 を実行して変更箇所を点検する手順を省いてはなりません。

### 注意 3：スマホ画面からの安易なコミット許可は厳禁

テストが全件合格した通知をスマホで確認しても、即座にコミットやデプロイを命じてはなりません。

テスト合格は既存のテストケースでエラーが出なかったことを証明するだけであり、不要なコード変更が含まれていないかを保証するものではありません。

モデルは関係のないコード整形を行ったり、重要なコメントを誤って削除することがあります。次の一手を指示する判断はスマホで行えますが、複数ファイルの一括修正や Git のコミットとプッシュは、デスクの大画面で差分を完全に確認してから行うべきです。

### 注意 4：中継アカウントとモデル API キーの混同

初期設定時に端末が見つからないという問い合わせが散見されます。

中継サービスのアカウントと、~/.claude/config.json に設定されたモデル用 API キーを混同しているケースが目立ちます。中継用アカウントは 9120 ポートを介したデバイスの接続管理を担うだけであり、モデルの利用枠は含まれません。推論処理にはローカルの settings.json に設定された正規の認証情報が消費されます。

## 実践的なまとめと技術的境界

スマホを開発フローに組み込む試みは実用的な選択と言えるでしょうか。

巨大なアーキテクチャ設計をスマホ画面だけで完結させようとするなら、それは無謀な試みです。タッチパネルは大画面モニターと打鍵環境に敵いません。

デスクに戻ったら diff を精査する。スマホからコミットやマイグレーションを実行しない。テストが通ってもモデルが勝手に不要な整形やコメント削除を行っていないか自分の目で確認する。スマホは、単にテストを通すためだけに期待値を改変するな、といった要所の方針指示にとどめるのが健全です。

大掛かりなテストの合間に席を立ち、ソファで失敗箇所を確認して適切な指示を投げる。この分担を守ることで、開発作業の無駄な待機時間を大きく削ることができます。
