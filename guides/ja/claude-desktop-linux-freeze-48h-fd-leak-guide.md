水曜の午後、作業用の Linux ワークステーションが突然激しくカクつき始めた。

マウスカーソルは秒間2フレーム程度しか動かない。キーボードを叩いても文字が出るまでに3〜4秒かかる。

端末を開いて uptime コマンドを叩いた。結果が返ってくるまでに20秒待たされた。システムのロードアベレージは 46.34 に達していた。16コアのマシンなので、各コアのキューに3つ近くのタスクが積まれている計算だ。一体どんな処理が暴走すればこうなるのか？ビルドスクリプトの暴走を疑って ps aux を確認したが、異常なプロセスは見当たらない。

カーネルの I/O 圧力指標を確認してみる：

```bash
# カーネルの I/O 圧力指標を確認
cat /proc/pressure/io
```

出力された full の10秒平均値は 85.3 を記録していた。高速な NVMe SSD が絶え間ない書き込みで完全に飽和している。

右画面の Claude デスクトップ版に目をやると、画面は真っ白になり、骨架プレースホルダーだけが残されていた：

<img src="https://img.freeaidog.com/images/blog/claude-desktop-frozen-skeleton.webp" alt="Claude デスクトップ版のフリーズ画面" />

マウスでクリックしても一切反応しない。

プロセスリストを洗い出すと、ディスクを猛烈に叩いていたのは systemd-coredump だった。Claude の描画プロセスが SIGILL 信号でクラッシュし、OSがプロセス全体のメモリイメージをディスクに書き出そうとしていたのだ。5分間で 92.4GB ものデータを書き散らかした末、タイムアウトで強制終了され、利用可能なダンプファイルすら残らなかった。これではデバッグのしようがない。

Linux 上でこのアプリを使っていると、2〜3日おきに決まって死ぬ。真っ白になるか、完全に固まるかのどちらかだ。ログには「メインWebviewが無応答のため再読み込みする」という決まり文句が繰り返されるだけで、一度として正常に復帰した試しがない。

デバッガを繋ぎ2週間かけて調査した結果、27バイトの小さな未読レスポンスが引き起こすファイルディスクリプタの雪崩に辿り着いた。

## なぜクラッシュダンプが 1.5TB に膨張するのか？

チャット画面の描画プロセスがなぜ 1.5TB ものダンプを吐き出すのか？これは Chromium 特有の仮想アドレス空間確保の仕様によるものだ。

本アプリは Electron 44 で動作しており、内部コアは Chrome 152 に該当する。起動時に V8 エンジンはサンドボックス用に 1TB の仮想アドレス空間を確保し、その前後に 64GB と 288GB の保護領域を配置する。メモリ管理機構や GC ヒープと合わせると、予約される仮想空間だけで 1.3TB を超える。

通常の Linux 環境であれば、madvise システムコール経由で DONTDUMP フラグを渡し、ダンプ対象から除外するようカーネルに指示できる。

しかし描画プロセスの seccomp サンドボックス設定 baseline_policy.cc は、madvise のパラメータを厳しく制限している。許可されているのは DONTNEED、WILLNEED、RANDOM、REMOVE、NORMAL、FREE の6種類のみだ。MADV_DONTDUMP はリストに含まれておらず、カーネルから EPERM エラーで拒絶される。

クラッシュ発生時、カーネルはパイプを通じてデータを転送する。パイプはスパースファイルの空洞をスキップできないため、ゼロで埋まった巨大な仮想空間がそのまま物理ディスクへの連続書き込みに化けてしまう。

原作者の Vladimir Petrzhikovskii 氏が blog.dfb.sh/blog/claude-desktop-freeze で報告している通り、彼は lseek のデータ探索機能を用いた Rust ツールを自作し、1.5TB のスパースファイル検索を0.7秒に短縮して調査を進めた。

## 942個の共有メモリと27バイトの心拍通信

メモリダンプを解析すると、描画プロセスが保持するファイル記述子が1,000個近くまで積み上がっていた：

```bash
# 描画プロセスが保持するファイル記述子数を確認
ls -l /proc/$RENDERER_PID/fd | wc -l
```

そのうち942個が 2MB の POSIX 共有メモリ領域を指していた。strings で中身をスキャンすると、938個の領域に全く同じ27バイトの JSON が書き込まれていた：

```json
{
  "refresh_after_seconds": 0
}
```

このわずか27バイトのために、プロセスは900個以上の 2MB 共有メモリ領域を開き続けていた。退席通知のレスポンスに、なぜ更新間隔の指示が含まれているのか？

内部の関数テーブルと V8 ヒープを逆引きすると、これらのリクエストは内蔵の Code タブから送信されていた。

このタブには在席確認機能が備わっている。ウィンドウが最小化されたり放置されたりすると、フロントエンドは退席通知を送信する：

```http
POST /v1/code/channels/session-id/client/presence HTTP/1.1
Host: api.anthropic.com
Content-Type: application/json

{"client_id": "client-token", "clear": true}
```

リクエストには keepalive フラグが付与されている。サーバーへ退席を伝え、バックエンドは27バイトのレスポンスを返す。

通知を投げっぱなしにする設計のため、フロントエンドは戻り値を一切読み取らない。空の catch を添えて放置する。バックグラウンドで動かしている間、この通信が1時間に数十回のペースで静かに積み上がっていく。

35時間以上が経過すると、開かれたディスクリプタは1,000個の大台に迫る。

## 根本原因：no-store ヘッダーから IPC デッドロックへ

サーバーは Cache-Control: no-store を返し、フロントエンドはストリームを読まない。

Chromium は読み取られるかキャンセルされるまで、未読データをパイプ内に保持し続ける仕様になっている。本来はディスクキャッシュを防ぐための no-store が、ここではパイプの破棄を阻む壁となった。最小再現環境で手動 GC を走らせると、JS側のレスポンスオブジェクトは回収されたが、/proc/$PID/fd の記述子数は1つも減らなかった。GC で破棄されたならディスクリプタも閉じるべきではないのか？

Chromium の fetch_manager.cc において、通常は BufferingBytesConsumer がパイプからデータをメモリへ吸い出し、速やかにディスクリプタを閉じる。

しかしコード内には「レスポンスヘッダーに Cache-Control: no-store が含まれる場合、自動バッファリングをスキップする」という分岐が存在する。

キャッシュ無効のデータがメモリを圧迫しないよう配慮した設計だが、その代償としてデータは明示的に読み取られるか body.cancel されるまで Mojo パイプ内に拘束される。

サーバーは no-store を付与し、フロントエンドは読まない。もしフロントエンドが永久に読まなければどうなるか？ディスクリプタは開きっぱなしになる。

Chromium は仕様を遵守し、V8 の GC は C++ 側の Mojo パイプを解放できない。無視された27バイトごとに、2MB の共有メモリと1つのファイル記述子が居座り続ける。

Linux における描画プロセスのソフトリミット ulimit -Sn は通常 1024 に設定されている：

```bash
# ファイル記述子の制限値を確認
ulimit -Sn
```

リークしたパイプが1,000個前後に達すると、利用可能な記述子は底をつく。

この状態でメインスレッドが IndexedDB の読み書きを行おうとすると、ブラウザプロセス側から新しい記述子を渡そうとする。

しかしカーネル側で枯渇が発生し、ソケットに MSG_CTRUNC フラグが立つ。

Chrome 152 の Mojo はこの切断エラーを正しくリカバリできず、メッセージ待ちのまま無期限に停止する。

後続の全 IPC 通信が詰まり、メインスレッドは完全に凍結。画面は応答不能のまま固まる。

## アップストリームの対応：仕様通りの回答と Bot による即時クローズ

原因を突き止めた Vladimir 氏は、関係する2つのアップストリームへバグ報告を提出した。

まず Chromium の課題管理システムへ、ディスクリプタ枯渇時にはデッドロックではなく TypeError を投げるべきだと報告した【Issue 582417463】。

しかし担当者は過去の Issue 378822137 の重複として即日クローズした。これが仕様通りの挙動と言えるだろうか？

担当者の回答は明快だった。レスポンスを読む権利があるのに読まない選択をした以上、それは想定された動作である。将来読む可能性をブラウザ側で否定できないため、パイプは開いたまま保持せざるを得ない、という見解だ。

次に Anthropic 公式リポジトリ anthropics/claude-code へ報告した。

クライアント側の修正は極めて簡単で、未読ストリームに対して cancel を1行追加するだけで済む。

Issue 107887 が作成された。

しかし人間の開発者が現れることはなく、数分後に自動管理 Bot が invalid ラベルを貼り、「Claude Code に関係ない内容と見なされる」として非情にクローズした。

ブラウザ側は仕様準拠と主張し、モデル側の Bot は調査を門前払いする。

結果として、ユーザーだけが数日おきのクラッシュに付き合わされることになる。

## ローカルでの回避策：Caddy による3分間ヘッダー書換

公式側の修正を待つよりも、ローカルで回避策を講じる方が圧倒的に早い。

対策は2つある。フロントエンドの fetch をフックしてストリームを破棄するか、ネットワーク層で Cache-Control: no-store を剥がすかだ。

Claude デスクトップ版は起動時に Web アセットを動的取得するため、バイナリ改変よりもネットワーク層での対応が安全だ。

ローカルで Caddy を動かしている場合、以下の設定を追加するだけで解決する：

```caddyfile
api.anthropic.com {
    reverse_proxy https://api.anthropic.com {
        header_up Host {upstream_hostport}
        @presence path /v1/code/channels/*/client/presence
        handle_response @presence {
            header -Cache-Control
        }
    }
}
```

ヘッダーを取り除けば、Chromium の BufferingBytesConsumer が250ミリ秒以内にパイプを自動排出し、記述子を閉じてくれる。

またリモートデバッグポートを有効にして起動する方法もある：

```bash
# リモートデバッグポートを付与して起動
claude-desktop --remote-debugging-port=9222
```

このパッチを適用して7日間連続稼働させたところ、記述子数は36〜41の間で完全に安定し、RSS メモリも横ばいを維持、負荷も0.1以下に収まった。

2つのアップストリーム Issue は今も閉じられたままだ。公式の修正が入るまで、あと何回の48時間周期を見送ることになるのだろうか？
