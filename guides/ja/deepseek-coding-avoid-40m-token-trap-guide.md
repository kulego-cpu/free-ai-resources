# DeepSeekで4000万トークンの請求爆発を回避する5つの実践鉄則

DeepSeekは単価が安いからと、何でも叶う願望機のようにコードを書かせていませんか？

技術コミュニティV2EXの投稿スレッド t/1255533 にて、手痛い現実に直面した開発者の事例が話題を集めました。

手持ちのCodex枠を使い切った投稿主は、プロジェクトの国際化辞書を9言語へ一括翻訳しようとDeepSeek APIに切り替えました。しかしバッチ処理を数周走らせたところで、管理画面の請求額が跳ね上がりました。気がつけば4200万トークン以上が消費されていたのです。

フォーラムで投稿主は嘆きました。単価が安いと聞いていたのに、辞書翻訳だけで数千万トークンも飛ぶのはなぜなのか？どこが節約になっているのか？

安さは相対的なものです。前提条件やアーキテクチャ設計を丸投げしてプロンプトを投げていれば、終わりのない再試行とコンテキスト膨張によって残高は一瞬で消え去ります。

以下にまとめる5つの原則は、私自身が現場で踏み抜いた失敗と、該当スレッドのエンジニアたちが一致して挙げた教訓です。重要度順ではなく、開発者が実際に遭遇する順番で解説します。

## 鉄則1：プロンプト先頭は絶対に変えない —— キャッシュを外せば速さも徒労に終わる

多くの人は、9言語に翻訳する消費トークンを単純に原文の9倍だと考えがちです。

計算上は平穏に見えても、請求書は冷徹です。

大惨事はこうして起きました。投稿主はリクエストのたびに、長大な元辞書JSONと翻訳済みの数千行に及ぶ文脈をプロンプトに丸ごと流し込んでいました。ターンを重ねるごとに、1回のリクエストコンテキストは2万から3万トークンへ急激に肥大化していきました。

さらに致命的だったのが、Prompt Cacheの完全破壊です。

DeepSeek公式のPrompt Cache機構は、文字列の先頭並び順に極めてシビアです。システムプロンプト冒頭の記号を1つ変えたり、対象言語の順番を入れ替えたりするだけで、プレフィックスハッシュの照合は即座に無効化されます。

本来なら9割引が適用されるはずのキャッシュヒットがゼロになり、毎回全額課金されます。APIループを数百回回せば、4000万トークンなど一瞬で蒸発します。

キャッシュを確実に効かせるには、固定されたプレフィックス構造を厳格に保ちます：

```json
{
  "model": "deepseek-coder",
  "messages": [
    {
      "role": "system",
      "content": "あなたは熟練したバックエンド開発者です。指定仕様に従い、ステートレスな純粋関数を出力してください。"
    },
    {
      "role": "user",
      "content": "【固定規約】入力構造: dict_a, 期待出力: dict_b\n---\n【動的タスク】ファイル: services/worker.py, 対象関数: process_task"
    }
  ],
  "temperature": 0.0,
  "max_tokens": 2048
}
```

ターミナルからの呼び出し例：

```bash
curl https://api.deepseek.com/chat/completions \
  -H "Content-Type: application/json" \
  -H "Authorization: Bearer $DEEPSEEK_API_KEY" \
  -d @payload.json
```

固定のシステムルールとサンプル契約は最上部に固定配置し、動的に変化するテキストは必ず末尾に付加します。

## 鉄則2：関数は書けても設計は書けない —— タスク仕様表で丸投げを排除する

DeepSeekは関数は書けても、全体のアーキテクチャ設計は書けません。この1点に尽きます。

関数の引数型、戻り値、想定テストケースをきちんと揃えて渡せば、1発でパスします。しかし「権限管理付きのマルチテナント基盤を作って」と大雑把に投げると、1回目はデコレータ、2回目はミドルウェア、3回目はカラム名をuser_id_v2に変更するなど迷走を始めます。3ターン消費した頃にはトークンが枯渇し、コードは崩壊して最初から書き直す羽目になります。

私はまずClaudeなどを使い、4列構成のタスク仕様書を作成します：ファイルパス / 変更対象関数 / 依存関係 / ユニットテスト受入条件。仕様書にはコードを書かず、改修箇所だけを明確にします。

40件のタスク仕様書なら、入出力合わせても8kトークン足らずで作成できます。DeepSeekにアーキテクチャを当て推量させれば、手戻りだけで20万トークンが消し飛びます。

| ファイルパス | 変更対象関数 | 上流下流の依存 | ユニットテスト受入条件 |
| :--- | :--- | :--- | :--- |
| services/auth.py | verify_token | redis_pool, jwt | 期限切れでExpiredTokenErrorを送出、正常時にuser_idを返却 |
| services/order.py | calc_discount | models.Promotion | 段階割引計算の精度を小数第2位まで保持 |
| tasks/sync.py | drain_queue | aiomysql.Pool | タイムアウト時の自動再試行と状態重複排除 |

この表をもとに、DeepSeekへ1タスクずつ順番に渡します。明確な入出力を与えれば、生成されたコードをそのまま本番リポジトリへ反映できます。

## 鉄則3：スタックトレースによる障害調査こそ最大の強み

私自身が最も恩恵を実感したのは、tracebackログを貼り付けて原因追究させる作業でした。

先週水曜、本番環境のasyncio.TaskGroup配下でKeyErrorが発生し、スタック深度は47層、aiomysqlのプール待機が2箇所挟まっていました。スタックログと該当する約60行の関数をそのままDeepSeekに投入しました。推論レベルをhighに指定して40秒ほど待つと、finallyブロック内でconn.cursorが2回再利用されている箇所を一発で指摘しました。

1時間近く睨み合って見落としていた原因を、即座に見抜いてみせたのです。

```text
Traceback - most recent call last:
  File "/srv/app/services/worker.py", line 142, in process_batch
  File "/srv/app/services/worker.py", line 88, in sync_channel
KeyError: 'cursor_reuse_conflict'
```

具体的な文法エラー、ヌル安全の抜け漏れ、並行処理のデッドロック検出において圧倒的な実力を発揮します。大規模なリファクタリングを丸投げするのではなく、ピンポイントのエラーログと関連コードを渡すのが最も効率的です。

## 鉄則4：推論レベルはhighを選びmaxは避ける —— タイムアウトと無駄な再計算を防ぐ

思考深度の設定項目を見ると、最大値のmaxを選びたくなるのが人情です。しかし本当に必要でしょうか？

max設定を盲信してはいけません。

DeepSeekの推論ロジックにおいて、maxは内部で膨大な思考ツリー探索を展開します。具体的な関数実装や文法チェックにおいて、max指定は数分におよぶ待機時間を引き起こします。通信が途中で切断されれば、全コンテキストが最初から再計算され、さらに1万トークンが水泡に帰します。

日常の開発やバグ調査には、high設定で十分です。応答時間は30秒から50秒前後に収まり、要点へ一直線に向かうため、タイムアウトによる通信遮断も回避できます。

## 鉄則5：バッチ処理は独立スライスと冪等性で雪だるま化を防ぐ

4200万トークン消費の根本原因は、文脈を雪だるま式に抱え込み続けたことにあります。

投稿主は翻訳済みのフランス語、ドイツ語、日本語の履歴をすべて1つのセッションに積み重ね、新たな言語を追記していました。7言語目に達する頃にはコンテキスト窓が限界近くまで埋まり、短文の翻訳でも毎回数万トークンの過去ログが送受信されていたのです。

バッチタスクでは、完全に分離されたパイプラインを組む必要があります：

個々のサブタスクには、そのタスクに必要な入力と辞書ルールだけを持たせます。結果が出力されたら即座にディスクへ保存し、セッションコンテキストを破棄します。次のタスクは完全にクリーンなセッションで開始します。

過去の履歴との依存を断ち切り、各リクエストに冪等キーを付与します。途中でネットワークが切れても、再実行が必要なのは数百トークンの小タスク1件だけであり、全体への被害を防げます。

## まとめ：スイカはナイフで切る、重機で繊細な作業はしない

これら5つの鉄則を押さえれば、DeepSeekを使った開発が高額な試行錯誤に化けることはありません：

1. 先頭プレフィックスを固定し、Prompt Cacheで9割引きを確実に享受する。

2. 関数は書けても設計は書けないと認識し、4列のタスク仕様書で主導権を握る。

3. 障害調査にはスタックトレースを投入し、並行処理のバグを瞬時に特定させる。

4. 推論レベルはhighを選択し、maxによるタイムアウト再試行を回避する。

5. バッチ処理は独立スライスで実行し、コンテキストの雪だるま化を断つ。

大局的なアーキテクチャ設計は上位モデルで行い、具体的な関数実装やエラー調査は高コストパフォーマンスなモデルに任せる。文脈とキャッシュを管理できれば、利用料金は常に安全圏に収まります。
