# DeepSeekがOpenRouterトラフィックの53%を独占：複数ターンAgentでアグリゲーター中継を避けるべき理由

監視サイト dirac.run が集計した OpenRouter の最新統計は、オープンモデル陣営にとって極めてインパクトのある数字を提示しました。

1日あたり27兆トークンという巨大な流通量のうち、DeepSeek 単独で53%のシェアを占拠。Qwen や他社モデルを合わせると、オープンモデル陣営の合計比率はすでに75%の壁を大きく突破しています。

8ヶ月前の状況を振り返ると、上位はほぼすべて商用閉鎖型モデルが独占していました。わずか200日余りで、潮流は完全に逆転したと言えます。

開発者コミュニティで共有される請求額の比較も劇的です。終日バックグラウンドで自動リファクタリング Agent を走らせ、数十万トークンを消費しても、DeepSeek の利用料はわずか4ドル強。同等の処理を商用最上位モデルで実行した場合、400ドルを超える請求書が届くことも珍しくありません。

100倍もの価格差が存在する以上、自動化パイプラインをオープンモデルに移行するのは自然な流れです。超高度なアーキテクチャ設計やマルチモーダル整合において商用閉鎖型モデルが優位を保つ場面もありますが、単調なリファクタリングやテストコード作成では、無駄な開発費を抑えたいのが現場の本音でしょう。

しかし、安易に中継アグリゲーターの接続先を書き換えるだけで4ドルの低コストを享受できると考えると、深夜の請求書によって手痛い教訓を得ることになります。

## 1. 突如跳ね上がった38ドルの請求額

先週の水曜日深夜、私は2年間運用してきた古いユーティリティコード群の全面リファクタリングに着手しました。

2万行を超えるレガシーコードには、型定義のない関数が無数に散らばっています。手作業で目を通せば、丸二日は潰れてしまう規模です。

そこで私は、単一セッションで連続対話を行う自律スクリプトを作成しました。設定の手間を省くため、接続先エンドポイントには OpenRouter 経由の DeepSeek インターフェースを迷わず指定。100万トークンあたり十数セントという単価なら、どれだけ回しても予算内に収まると考えていました。

最初の15ターンは極めて快適に推移しました。

Agent はファイルを順次読み込み、依存関係を解析し、単体テストを生成してアサーションを実行。

コンテキストは開始時の8Kから、徐々に28Kトークン前後まで膨らんでいきました。管理画面で確認した1回ごとの課金額は2セント未満。極めて順調です。

ここで夜食の時間が訪れました。私はノートPCを閉じ、近所の店でラーメンを食べ、シャワーを浴びて戻りました。所要時間はおよそ40分です。

書斎に戻り、画面を開いてスクリプトに第16ターン以降の作業を再開させました。

2時間後、全テストが通過してタスクは完了。

伸びをしてログアウトする前に利用額ダッシュボードを更新した瞬間、私は目を疑いました。

最大でも4ドルから5ドル程度と見込んでいた作業に、38.60ドルの請求が記録されていたのです。

一体何が起きたのでしょうか。

深夜に料金改定が行われたのでしょうか、それともスクリプトがループしたのでしょうか。コミット履歴は正常そのものです。上乗せされた数十ドルは、どこに消えたのでしょうか。

## 2. 10分間のキャッシュ断崖とノード跨ぎルーティングの破綻

端末のログとHTTP応答ヘッダーを30分以上調査して、ようやく不審な挙動を突き止めました。

証拠は応答ヘッダー内のバックエンドプロバイダー項目に記録されていました。

最初の15ターンでは、担当プロバイダーはある特定のホスティング業者に固定されていました。しかし食事から戻った第16ターン目、プロバイダーは別の業者へと密かに切り替わっていたのです。

これこそが、長大なコンテキストを扱う Agent において中継アグリゲーターが抱える構造的リスクです。

OpenRouter のようなアグリゲーターは、本質的にトラフィック分散を行うルーティング層です。自社で巨大データセンターを保有するのではなく、Together、Fireworks、DeepInfra、Novita、Lepton といった外部ホスティング業者へリクエストを振り分けています。

利用者の計算コストを抑えるため、プラットフォーム側もキャッシュ対応ルーティングを実装しています。

しかしこの仕組みには致命的な弱点があります。セッション親和性の保持期間がわずか10分間に設定されている点です。

10分以内に連続してリクエストを送り続けていれば、スケジューラーは同一ホスティング業者の同一GPUノードへ優先的に割り振ります。

しかし人間の思考や休憩が10分を超えた場合や、割り当て先ノードのキューが一時的に混雑した場合はどうなるでしょうか。

スケジューラーは即座にフォールバックを実行し、次のリクエストをまったく無関係な別のマシンへ転送してしまいます。

ここで悲劇が起こります。

以前の業者のGPUメモリ上には、直前15ターンで蓄積された28Kトークンの KV Cache が温まった状態で残っています。しかし新しく割り当てられたサーバーには、過去の対話履歴など一切存在しません。VRAMは完全に冷え切っています。

前触れなく送りつけられた2万8000トークンの長文に対し、新しいノードに選択肢はありません。

届いた28Kトークン全量を、ゼロから高負荷な Prefill 行列演算で再計算せざるを得ないのです。

課金レートは一瞬で跳ね上がります。

キャッシュがヒットしていれば、100万トークンあたり0.014ドルで済みます。キャッシュが完全に消失した場合、通常単価である0.14ドルが全量に適用されます。

単価が瞬時に10倍へ高騰した計算です。

作業が進むにつれてコンテキストは30Kから50Kへと肥大化します。

対話の合間に10分以上の空白ができるたび、キャッシュの連鎖は断ち切られ、それまでに蓄積したコスト優位性はすべて消滅します。

さらに深刻なのがレスポンス遅延です。

キャッシュが効いていた序盤は、送信から1秒台でテキストが出力されていました。キャッシュ蒸発後は2万8000トークンを再計算するため、端末のカーソルが17秒間も完全にフリーズしました。

スクリプトがこの17秒の停止を通信タイムアウトと誤認しないと言い切れるでしょうか。

タイムアウト判定による再試行が走れば、さらに全量再計算が重複します。本来数ドルで済むはずだった作業が、複数ノードの冷え切ったキャッシュ再構築によって38ドルまで膨れ上がってしまいました。

## 3. 公式APIが提供する永続プレフィックスキャッシュの強み

中継ルーティングに10分間の断崖が存在するのに対し、なぜ DeepSeek 公式APIへの直結ではこの現象が起きないのでしょうか。

根本的な違いは、サーバー側のVRAMスケジューリング設計にあります。

公式クラスターは、当初からグローバルなプレフィックスキャッシュ構造を前提として設計されています。リクエストの前半部分が過去の対話と一致している限り、分散スケジューラーは計算済みの注意機構テンソルを再利用します。

公式ノードのキャッシュ保持時間はどれほどでしょうか。決して5分や10分といった短時間ではありません。

混雑状況にもよりますが、公式のコンテキストキャッシュは数時間から翌日まで維持されるケースが一般的です。夜間にPCを閉じ、翌朝に作業を再開しても、数万トークンの過去文脈が高い確率でVRAM上にそのまま残存します。

この数値の開きは明白です。

40ターンの往復において、キャッシュが効いていれば入力費は30セント未満です。毎回消失した場合は3ドルを超過します。

データガバナンスの安全性も無視できません。

中継アグリゲーターの利用は、複数の独立した第三者ノードを経由することを意味します。自社のソースコードがどのサーバーのメモリを通過したのか、法的に確実な証明を得るのは困難です。

公式APIはゼロデータ保持ポリシーを明言しており、ユーザー入力が将来のモデル学習に使用されることはありません。業務コードを扱う上で、この方針は極めて重要です。

## 4. プレフィックスキャッシュを最大限に活かす実装作法

公式エンドポイントへ切り替えさえすれば、すべて解決するのでしょうか。

そう単純ではありません。コード側のプロンプト構築に配慮がなければ、自分自身の手でキャッシュを破壊してしまいます。

多くの開発者は、システムプロンプトの先頭に現在日時を埋め込む実装を行いがちです。

あるいは、ループごとにランダムなUUIDを生成して文頭に挿入するケースも見られます。

これらの実装はプレフィックスキャッシュの最大の天敵です。

プレフィックスキャッシュは、左から右へ完全一致でトークンハッシュを照合します。冒頭10トークン目に秒単位で変化する文字列が存在すれば、その後に5万行の同一コードが続いていても、10トークン目の位置でキャッシュチェーンは破断します。

それ以降の文脈はすべて未ヒット扱いとなります。

キャッシュヒット率を90%以上に保つには、以下のようにリクエストを組み立てます。

```python
import os
import requests

DEEPSEEK_API_KEY = os.environ.get("DEEPSEEK_API_KEY")
API_ENDPOINT = "https://api.deepseek.com/v1/chat/completions"

# 静的システムプロンプト：動的タイムスタンプや乱数を混入させない
STATIC_SYSTEM_PROMPT = (
    "You are a senior code refactoring engineer. "
    "Follow PEP 8 rules and emit only structured diffs."
)

def build_stable_payload(session_history, new_user_msg, current_time_str):
    messages = [
        {"role": "system", "content": STATIC_SYSTEM_PROMPT}
    ]
    # 対話履歴は時系列順に追記し、過去メッセージを途中で書き換えない
    for item in session_history:
        messages.append(item)
    
    # 動的メタデータは最新ユーザー入力の末尾にのみ付与する
    decorated_user_msg = f"{new_user_msg}
[Meta: {current_time_str}]"
    messages.append({"role": "user", "content": decorated_user_msg})
    
    return {
        "model": "deepseek-chat",
        "messages": messages,
        "temperature": 0.0,
        "stream": False
    }

def call_deepseek(payload):
    headers = {
        "Authorization": f"Bearer {DEEPSEEK_API_KEY}",
        "Content-Type": "application/json"
    }
    resp = requests.post(API_ENDPOINT, json=payload, headers=headers, timeout=60)
    data = resp.json()
    
    usage = data.get("usage", {})
    cache_hit_tokens = usage.get("prompt_cache_hit_tokens", 0)
    cache_miss_tokens = usage.get("prompt_cache_miss_tokens", 0)
    
    return data, cache_hit_tokens, cache_miss_tokens
```

基本原則は明快です。

第一に、固定の役割指示を先頭に固定すること。

第二に、過去の対話履歴を変更せず末尾へ追加すること。

第三に、日時や動的変数は最新メッセージの末尾にのみ付加すること。

先頭のバイト列を不変に保つことで、スケジューラーはミリ秒単位で既存キャッシュを再利用し、ヒット率を9割以上に維持できます。

## 5. Googleの100兆トークン報道に見る計測基準の乖離

市場規模の議論に戻りましょう。

OpenRouter の27兆トークンという記録に対し、Google の1日100兆トークンを引き合いに出して冷淡な見方をする声も存在します。

しかし、計測基準の違いを無視した直接比較は実態を見誤らせます。

Google の100兆トークンという数値の95%以上は、静的なキャッシュ読み取り処理です。

現代の検索エンジンにおいて、頻出クエリのインデックスやプロンプトテンプレートは TPU メモリ上に常駐しています。

ユーザーの検索時に行われる大半の処理は超高速なキャッシュ読み出しであり、ゼロから新規トークンを生成する前方向計算はごく一部に過ぎません。

さらに、Google の計算リソースを最も多く消費しているのは自社の検索サービスや推薦アルゴリズム、社内プロダクトです。

自社完結で高度にキャッシュ化された読み取りトラフィックと、OpenRouter 上で世界中の開発者が費用を投じて未知のコードを検証する実計算トラフィックは、本質的に異なる負荷です。

キャッシュ構造を無視して総トークン数だけを比較しても、実質的な計算能力の評価にはつながりません。

## 6. 実務における選定基準とセルフチェック

一連の検証を経て、私の実務選定基準は明確に定まりました。

単発の対話テストや新しいオープンモデルの手軽な比較検証であれば、OpenRouter は極めて有用なツールです。複数業者への個別支払いを一本化でき、単発リクエストならキャッシュ消失の弊害もありません。

しかし、長時間の自律コーディング Agent や、多数のファイルを解析する多段階ワークフローにおいては、サードパーティ中継ルーティングの利用を即座に停止すべきです。

APIキー設定の数分間を惜しんだ結果、想定の十数倍に達する請求と深刻なタイムアウト待ちに直面することになります。

公式原廠エンドポイントへ直結し、固定プレフィックスを先頭に固定することこそが、DeepSeek の真価を引き出す確実な方法です。

今夜スクリプトを放置して就寝する前に、コードの外周ループに日次利用額のリミッターを正しく組み込んであるでしょうか。
