# iPhone キーボードを自宅の Ollama に接続：Diction 音声入力セルフホスト実践

スマートフォンで文字を打つ際、その内容はどこへ送信されているでしょうか。

情報漏洩のリスクは常に存在します。

モバイル端末での音声入力や AI による文章整形機能は、多くのエンジニアにとって日常的な操作の一部となっています。

しかし、その代償は小さくありません。

商用キーボードアプリは認識精度を維持するという名目でフルアクセス権限を要求することが多く、キーストロークや音声データ、クリップボードの内容までもが外部のパブリッククラウドへ送信される構造になっています。

キーボードは端末内で最も機密性の高い入力経路です。

商用キーボード経由でサーバーのパスワードや機密業務データを入力することに、不安を感じない人はいないでしょう。

コミュニティの開発者 Better-Psychology-42 は、オープンソースプロジェクト Diction を通じて明確な解決策を提示しました。

基本思想は極めて明快です：
音声の文字起こしと AI によるテキスト整形のバックエンドゲートウェイを、自宅のプライベートサーバー上に構築します。

スマートフォン側には純粋なキーボード入力の役割のみを残します。

## アーキテクチャ解説：データが家庭内ネットワークを出ない 3 層構成

Diction のシステム構造は 3 つの階層に分かれています。

第 1 層は iOS キーボード拡張です。
この層は厳格な端末内サンドボックス分離を遵守します：
QWERTY キーの打鍵、スワイプ入力、ローカルスペル補正のロジックは iPhone 内部でのみ完結します；
マイクボタンが押下された瞬間のみ、一時的に音声の取り込みチャネルが有効化されます。

バックグラウンドでの無断通信は完全に遮断されます。

第 2 層はセルフホストされたサーバーゲートウェイです。
端末側で録音された音声ストリームは暗号化トンネルを通じて自宅サーバーへ送られ、統合された Whisper エンジンによってミリ秒単位で句読点のないテキストへ変換されます。

ローカルでの文字起こしは極めて高速です。

第 3 層は大規模モデルの推論バックエンドです。
ゲートウェイは標準的な HTTP インターフェース経由で家庭内ネットワークの Ollama インスタンスと通信します；
小型モデルが数百ミリ秒以内に句読点の復元、口語の語順補正、不要なフィラー表現の削除を行い、構造化データとしてスマートフォンのカーソル位置へ返却します。

パイプライン全体は OpenAI 互換の API エンドポイントをサポートしています。

データは最終的にどこへ保存されるのか。

打鍵データは端末内に留まります。
音声データは自宅サーバー内に留まります。
第三者のクラウド事業者が通信を傍受する余地はありません。

## なぜ 4B 小型モデルがキーボード整形に最適なのか

自前のインフラを構築する際、70B 級の巨大モデルを稼働させようとするケースが散見されます。

しかしキーボード整形という目的に対しては、4B 規模の小型モデルの方が遥かに実用的です。

キーボードでのテキスト整形は、自由対話型の長文チャットとは本質的に異なります。

これは制約の厳しい短文の校正作業です：
句読点の補正；
口頭表現における不要な繋ぎ言葉の除去；
同音異義語の誤変換修正；
英数字の表記ゆれと大文字小文字の統一。

このような短文の整形に、数百億パラメータによる多段階推論は必要ありません。

モデルの肥大化は、スマートフォン入力において致命的な遅延を引き起こします。

なぜ遅延が致命傷になるのか。

最初のトークンが出力されるまでの時間が長すぎるためです。

モバイルキーボードでの入力において、人間が待機に耐えられる限界は一般に 1.5 秒から 2 秒程度です；
路上で発声した後に数秒間カーソルが静止したままでは、日常的な入力業務には耐えられません。

入力のテンポが崩れてしまいます。

12GB の VRAM を備えた RTX-3060 での実測結果は明確です：
Qwen3.5-4B クラスの小型モデルを Ollama 上で FP16 または Q8_0 精度で稼働させ、文脈長を 512 トークンに制限した場合；
順伝播のトークン生成遅延はわずか 180 ミリ秒であり、一文全体の整形処理は 400 ミリ秒以内で完了します。

応答速度は非常に良好です。

家庭内 Wi-Fi 通信と Whisper の文字起こし処理時間を合算しても、全体のエンドツーエンド遅延は約 1.3 秒で安定します。

体感の追従性は非常に快適です。

## デプロイ実践：Tailscale による通信経路確保と Prompt の原則

自宅サーバーで運用する際、考慮すべき技術的ポイントは何でしょうか。

最初の課題はネットワーク経路の確立です。

外出時のスマートフォンは主にモバイル回線で通信を行います。

Ollama のポートを認証なしで公衆網へ開放することは危険です；
Tailscale や自前の WireGuard による暗号化トンネルの導入が推奨されます。

5G 回線経由で自宅の Tailscale ノードへ接続した場合でも、往復の遅延増加はわずか 35 ミリ秒程度に収まりました；
外出先でも自宅 Wi-Fi と変わらない応答性で動作します。

接続の安定性は申し分ありません。

第 2 の重要事項は、システムプロンプトによる余計な返答の排除です。

汎用言語モデルは挨拶や補足説明を付加しがちです：
修正した文章をお伝えします；
お役に立てれば幸いですなどの不要な文字列です。

メッセージ送信の直前にモデルがこのような挨拶を出力してしまうと、入力欄にゴミデータがそのまま挿入されてしまいます。

ゲートウェイ側で設定する整形プロンプトには、厳密な指示を適用する必要があります：
```text
You are a text cleanup engine. 
Task: Fix grammar, add punctuation, remove filler words like um/uh/er. 
Rule: Output ONLY the cleaned text. Never add explanations or greetings.
```
対話的な返答は完全に禁止しなければなりません。

モデルは純粋なテキスト変換フィルターとしてのみ機能させます。

## 運用の工学的限界と留意点

この構成に欠点は存在しないのでしょうか。

現実の運用においては考慮すべき制約が存在します：

第 1 に、VRAM 保持とコールドスタートの遅延です。
サーバー上で他の重いタスクが並行稼働し、Ollama が 4B モデルをシステムメモリへ退避させた場合、最初の音声入力時に約 4 秒のロード時間が発生します。
これを回避するためには、keep_alive を指定してメモリ常駐を維持します：
```bash
curl http://localhost:11434/api/generate -d '{"model": "qwen3.5:4b", "keep_alive": -1}'
```
モデルを GPU メモリ上に固定します。

第 2 に、iOS キーボード拡張のメモリ制限です。
Apple はサードパーティ製キーボード拡張に対して 50MB から 70MB 程度の厳格なメモリ上限を設けています。
端末側で重い音声処理を行うと、システムによる強制終了が発生します；
高負荷な計算はサーバー側へ委ねる必要があります。

第 3 に、オフライン時のフォールバックです。
地下駐車場や電波の届かない場所で通信が途絶えた場合の挙動です。
Diction は自動的な機能低下をサポートしています；
通信が切断された場合は AI 整形を速やかに停止し、端末ローカルの QWERTY 打鍵モードへ切り替わるため、基本的な文字入力は妨げられません。

キーボードの入力データは個人のプライバシーを守る最前線です。

データ主権を自身の手に取り戻すこと；
手元のハードウェアで普段使いのスマートフォンを駆動させること；
このような確かな安心感は、セルフホストならではの大きな醍醐味ではないでしょうか。
