# Agent の推論待ちに熱血トレンドを流し見：DSH Desktop 用サイドバー拡張 DS-NewsTop の構造と導入実測

ローカルで長時間の自動開発タスクを実行する。
例えば Agent にモジュール全体のリファクタリングを任せる場面。
モデルの推論には二分から三分程度の待ち時間が生じます。
ブラウザを開いてニュースを眺めるか？
タブを巡回しているうちに集中が切れてしまいます。
元の画面に戻った頃には、確認すべきコードの差分を忘れてしまうこともしばしばです。
AI クライアントの内部に軽量なサイドバーがあればどうでしょうか。
ターミナルの出力を監視しつつ、コミュニティの技術トレンドを斜め読みする。
読み終わればワンクリックで折りたたむ。
メインエディタの領域を圧迫しません。

オープンソース拡張 DS-NewsTop はこの課題に対応します。
DSH Desktop 専用に設計されており、Cordis モジュール機構を通じてサイドバーに各プラットフォームのトレンドを統合します。

## 1. アーキテクチャ解説：同一生成元プロキシとポーリング排除の設計思想

DSH にこの拡張を導入する前、まず内部にタイマー処理が存在するか確認しました。

理由は実体験に基づきます。
昨年、90 秒おきに数十の外部 API へ一斉フェッチを放つ類似拡張を入れたことがあります。
当時ローカルで 7B モデルの推論を回していたところ、冷却ファンが急激に回転し始めました。
それ以来、リアルタイムを謳う拡張機能を見たら、まずソースコードの setInterval を探すのが習慣になりました。

DS-NewsTop には自動ポーリング用のタイマーが存在しません。
パネルを展開した時のみリクエストを送信し、閉じている間は通信を完全に停止します。
この設計が、本拡張を常駐させるかどうかの決定打となりました。

リクエスト経路も整理されています。フロントエンドはホストのローカルエンドポイントのみを呼び出します。
`/dsh-hot-list/items?id=sourceID`
フロントエンドはこのローカルポートからデータを受け取ります。
ホスト側があらかじめ固定された上流リストを参照してデータを取得します。
上流の URL はホストコード内で定数として固定されており、フロントエンドから任意のパラメータを渡しても反映されません。
当初は意識していませんでしたが、SSRF の攻撃面を考えると理にかなっています。
もし任意のアドレスを許容していれば、社内イントラネットのスキャンに悪用されるオープンプロキシになりかねません。

60 秒のインメモリキャッシュも実用的です。
サイドバーを頻繁に開閉しても外部ネットワークへ無駄な通信を飛ばさず、即座に画面が表示されます。

データ取得ルートは二系統に整理されています。
GitHub、Hacker News、V2EX、知乎など 18 サイトはオープンソースの NewsNow サービスを経由します。
小衆ソフトウェア発見チャンネルの Markdown ページは個別パーサーで処理し、固定ルール投稿を除外して上位の共有情報を抽出します。

仮に上流サービスが 502 エラーを返した場合でも、直前に取得したデータが保持され、再試行ボタンが表示されます。
NewsNow が一時的に不安定になった際も、古い一覧が残っていたため作業が中断されることはありませんでした。

## 2. 互換性の境界条件とリソース負荷の実測

三時間連続で稼働させ、メモリリークの有無と CPU 負荷を観察しました。
計測には macOS のアクティビティモニタを使用しており、専用プロファイラによる厳密な値ではないため、目安としての記録です。

### テスト環境のスペック
- ホスト環境：DSH Desktop 2.0.18、コア互換バージョン 0.2.1-rc.2 および 0.2.1-rc.3
- ハードウェア：M2 Max 搭載 MacBook Pro、32GB 統合メモリ
- プラグインバージョン：dsh-hot-list 1.3.2 安定版

### 実機動作におけるリソース比較

メモリ面では、コールドスタート後に 40MB から 50MB 程度の増加で安定しました。
三時間の連続運用中、明確なメモリ増加傾向は見られませんでした。
比較として Chrome 128 でニュースサイトを七つのタブで開いた際、アクティビティモニタは約 1.1GB から 1.3GB のメモリ消費を示しました。
ただしタブ数やスリープ機能の有無で差が出るため、大まかな規模の対比に過ぎません。

CPU 面では、サンプリング窓内でプロセス表示が 0.0 に張り付いていました。
0.0 は絶対的なゼロを意味するわけではなく、アクティビティモニタの測定精度を下回っている状態を指します。
確認できたのは、ファンを回転させるような高負荷なバックグラウンド動作が発生しなかった点です。

| 評価指標と状況 | 通常ブラウザで複数タブ閲覧 | DS-NewsTop サイドバー常駐 | 実測状況と技術境界 |
| :--- | :--- | :--- | :--- |
| 常駐メモリ増分 | 約 1.1GB から 1.3GB 消費 | ホストプロセスで約 45MB 増加 | 重厚なレンダリングエンジンと広告スクリプトを排除 |
| アイドル時 CPU 負荷 | ページスクリプトで偶発的に 1% | アクティビティモニタで 0.0 推移 | 監視精度以下、目立った負荷スパイクなし |
| 外部通信の発生契機 | タイマーにより常時定期通信 | パネル表示または更新クリック時のみ | モデル推論の通信帯域を阻害しない |
| テーマ配色の追従 | 外部拡張機能による強制変換 | DSH ホストの背景変数と枠線色を継承 | 明色、暗色、ホスト自動追従に対応 |
| プラットフォーム境界 | 一般的なウェブブラウザ全般 | DSH Desktop の Cordis 体系に特化 | 通常の VS Code や Cursor に直接導入不可 |

導入前の注意点です。
本ツールは DSH Desktop の Cordis 拡張機能として構築されています。
VS Code マーケットプレイスの通常拡張ではないため、素の VS Code に直接読み込ませることはできません。
非 DSH 環境で類似の構成を作りたい場合は、UI カード設計と NewsNow API を参考に独自移植する必要があります。
無理な直接インストールは避けてください。

## 3. 実践導入：三段階のサイドバー組み込み手順

DSH Desktop 2.0.18 への導入手順は以下の通りです。

### 1. ターミナルからのパッケージ追加
DSH Desktop を起動します。
メニューから内蔵ターミナルを立ち上げ、標準デスクトップ Profile フォルダへ移動します。

```bash
cd ~/.dsh/profiles/desktop
pnpm add dsh-hot-list@1.3.2
```

GitHub Releases から直接 tgz アーカイブを取得し、絶対パス指定で導入することも可能です。

### 2. 設定ファイルへのバンドル登録
同ディレクトリ内の package.json を開きます。
dsh.profile.bundles 配列の末尾にプラグイン名 dsh-hot-list を追加します。公式の基盤パッケージはそのまま保持してください。

```json
{
  "dsh": {
    "profile": {
      "bundles": [
        "@deepseek-ai/dsh-base",
        "@deepseek-ai/dsh-web-app",
        "dsh-hot-list"
      ]
    }
  }
}
```

JSON の構文に誤りがないか確認します。
波括弧の閉じ忘れや末尾の余計なカンマがあると、プロファイル全体の読み込みに失敗するため注意が必要です。

### 3. 再起動と動作確認
DSH Desktop を完全に終了して再起動します。
クライアント左端のアクティビティバーにアイコンが表示されます。
クリックしてサイドバーを開きます。
右上の設定アイコンから 19 の情報源を取捨選択できます。初期設定では 14 プラットフォームが有効です。
設定値は DSH のローカルストレージへ保存されます。

## 4. 完了点検チェックリスト

以下の四点を確認して作業を完了します。
- プロセスメモリの確認：ホストのメモリ増加幅が 50MB 前後で推移していること。
- オフライン耐性の検証：ネットワーク切断時にカードをクリックし、白画面にならず直前のキャッシュと再試行案内が残ること。
- ダークテーマ連携の点検：DSH をダークモードへ切り替え、枠線と背景色が正しく連動すること。
- アイドル時通信の監視：パケットキャプチャを行い、サイドバー非表示時に外部通信が発生しないこと。
