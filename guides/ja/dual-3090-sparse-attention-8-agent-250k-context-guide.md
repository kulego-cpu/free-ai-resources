# RTX 3090 2基で250Kエージェント8並行を達成：TokenGateに対抗する全量スパースアテンション実戦

複数エージェントによる共同コーディング、いまや珍しくもありません。

私たちの現場パイプラインは通常5つのエージェントに役割を分割しています：設計、インターフェース策定、実装、単体テスト、セキュリティ監査。ワークフロー自体は簡単に組めます。しかし本当の地獄はコンテキスト長にありました！

複雑なリポジトリ全体を読み込ませると、250Kトークンなど最低限のスタートラインに過ぎません。これを8エージェント同時に並行稼働させたらどうなるか？KVキャッシュだけでVRAMは一瞬で食い尽くされます！

手元にあるのは中古のRTX 3090が2基、合計わずか48GBのVRAMです。もし標準の全結合アテンションを愚直に走らせたら、8並行の要求メモリは数百GBへと跳ね上がります。データセンターのA100クラスタですら即死するレベルです！

## なぜTokenGateなどの枝刈りはエージェント環境で破綻するのか

初期の計算を省くため、TokenGateのようにスコアの低いトークンをその場で切り捨てる手法を勧める声もあります。メモリは浮く、本当にそれで足りるのか？

一回きりの単純なQ&Aなら騙し騙し動くかもしれません。しかし複数ターンの深い協調作業に入るエージェント環境では、即座に大惨事を引き起こします！

冷静に考えてみてください。第1ラウンドでエージェントが無駄と判断して捨て去った関数シグネチャや型修飾子は、まさに第3ラウンドで潜伏バグを追跡する際に必要な唯一の手がかりだったりします。下位レイヤーで一度切り捨てられたら、後からどう質問を重ねても適合率は完全にゼロ。これは高速化ではありません。ただの人為的な健忘症です！

## 全量保持と動的スケッチによる現場の解法

私たちは真逆のアプローチを取りました：トークンは1個も捨てない。KVキャッシュ全量をシステムRAMに保持し、VRAMには極小のスケッチのみを置く。

構造は3つの段階で組み上がっています：

第1段階。全コンテキストのKVキャッシュをホストの128GB DDR4メモリへ退避。4ビット形式で隙間なく敷き詰めます。VRAM側には長大な全履歴を絶対に居座らせません。

第2段階。VRAMには各トークンにつきランク64の極小特徴スケッチ Key Sketch のみを維持。各デコードステップで専用Tritonカーネルを走らせ、250Kトークンの中から最も重要な上位2000件、全体の約1パーセントだけをGPU内で瞬時に粗選別します。

第3段階。スケッチにヒットした1パーセントの断片のみをPCIe 4.0経由でVRAMへ転送し、標準の計算コアへ投入。転送サイズは数十GBから毎ステップわずか十数MBへと激減します。

PCIeバスは詰まらないのか？スローガンではなくP99レイテンシを見るべきです。帯域のボトルネックが解消されれば、デコードの速度低下は確実に防げます。

## 生々しいトラブルシュート記録：CUDA Graphのクラッシュとメモリ計算

今回のチューニング、最初から順調だったわけではありません。初回の本番テストでは見事に大爆発しました！

カスタムパッチを当てたvLLM環境でCUDA Graph captureを実行した瞬間、端末に kernel shape mismatch のエラーが吐き出され、Tritonのコンパイルがデッドロックを起こしてプロセス全体が完全に固まりました。

生成された中間アセンブリを2時間かけて追跡し、ようやく原因を特定：動的スライスの局所テンソルが128バイト境界を跨ぐ際、アライメントのパディング処理が抜けていたのです。粗選別のtop-kを4096から2000へ引き下げ、メモリプール側で128バイト境界への厳格アライメントを強制。これでようやくグラフキャプチャが緑ランプに変わりました！

VRAMとホストRAMの消費量は勘に頼るものではなく、すべて計算式で割り出せます：

32層、8個のKVヘッド、128次元で計算してみましょう。オフロードを挟まなければ、単一の250Kセッションにおけるfp16キャッシュだけで約64GBを消費し、2基のGPUは一瞬でOOM強制終了を迎えます。

4ビット形式でホストRAMへ保持させる設計に変更した結果、8並行のセッションが128GBシステムメモリ内で占有するのは約64GB。VRAM内部はモデル本体と1パーセントの動的スライスのみを保持し、RTX 3090のVRAM消費量は21.8GB近辺で安定。これでようやくメモリ死刑宣告を免れました。

## 隠さずに認めるべき弱点：4ビットドリフトと長距離テストの不足

コミュニティのエンジニアから寄せられた厳しい指摘は完全に正論です：4ビットKVの累積ドリフトは決して軽視できる問題ではありません！

多段階のコード改修において、変数の型修飾子を1文字見落としただけで、出力パッチは致命的なバグへと変貌します。RULERやLongBenchといった長距離ベンチマークスイートの全テストは現時点で完了していません。この限界は率直に認めるべきです。

したがって、この実験的アプローチを金融決済システムなどのミッションクリティカルな本番環境へ無警戒に投入するのは絶対に避けてください！

ローカルで検証する際は、以下の起動コマンドから始めることを推奨します：

```bash
python3 -m vllm.entrypoints.openai.api_server \
  --model Qwen/Qwen2.5-Coder-32B-Instruct \
  --tensor-parallel-size 2 \
  --max-model-len 262144 \
  --gpu-memory-utilization 0.92 \
  --enable-chunked-prefill \
  --sparse-kv-sketch-dim 64 \
  --sparse-top-k 2000
```

## 実戦の結論

この試みに奇跡めいた神話はありません。限られた予算で実際に完走できる地に足の着いた選択肢です：中古のRTX 3090が2基、128GBメモリ、250Kエージェント8並行、合算毎秒600トークン。

4ビット精度に伴う微小な犠牲を受け入れる覚悟が必要であり、長距離テストは現在も継続中です。
