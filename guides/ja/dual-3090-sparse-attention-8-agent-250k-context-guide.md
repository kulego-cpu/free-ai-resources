# RTX 3090 2基で250Kエージェント8並行を達成：TokenGateに対抗する全量スパースアテンション実戦

現代のソフトウェア開発において、複数の自律型AIエージェントが協調して大規模リポジトリの改修にあたるマルチエージェント開発ワークフローは標準的な手法となりつつあります。

アーキテクチャ設計、インターフェース策定、実装、単体テスト、セキュリティ検証など、各役割を担うエージェントが並行して稼働します。しかし小規模チームや個人開発者が直面するのは過酷なGPUメモリの壁です。
巨大なコードベースを読み込むため、各エージェントは250Kに達する極めて広大なコンテキストウィンドウを必要とします。このようなエージェントが8体同時に稼働すると、肥大化するKVキャッシュだけで数百ギガバイトのVRAMを浪費してしまいます。

過去の研究ではTokenGateをはじめとする動的なトークン枝刈り技術が注目されました。しかし単純な一問一答では機能しても、反復的な対話を繰り返すエージェント環境では深刻な破綻を招きます。**初回のやり取りで無駄と判断されて切り捨てられた変数定義やシグネチャが、第3ラウンドのバグ修正でまさに必要とされ、コード検索の精度が完全に崩壊してしまうのです**。

この致命的な弱点を克服するため、オープンソースコミュニティから鮮やかな対抗策が打ち出されました。
**トークンを一切破棄せず、完全なKVキャッシュを大容量システムRAMに永続保持し、VRAM側には極小のスケッチのみを配置して、毎ステップ上位1パーセントの断片のみをPCIeバス経由で動的転送する**という設計です。

中古市場で入手可能なコンシューマー向けカードRTX 3090を2基、合計48GBのVRAM環境において、250Kコンテキストを持つ独立したエージェント8体の同時並行稼働に成功。合算スループットは毎秒600トークンを超実測しました。

---

## 1. 根本的なボトルネック：従来の長文枝刈りがエージェントで破綻する理由

新アーキテクチャの核心に迫る前に、マルチエージェント特有のメモリ課題を整理します。

### 通常アテンションのVRAM爆発
標準的な全結合アテンションでは、コンテキスト長に比例してメモリ消費が増大します。250K長文のセッションは、8ビット量子化を用いても膨大な容量を占有します。これを8エージェント分同時に展開すると、データセンター向けの高級GPUクラスタですら一瞬で枯渇します。

### 単純な枝刈りが引き起こす健忘症
TokenGateなどの手法は、フォワードパスの初期段階で重要度の低いトークンを物理的に削除します。しかしエージェントは推敲と自己修正を繰り返す存在です。ユーザーからの新たな指示一つで、過去の些細なコード行が突如として最重要の文脈へと変わります。下位レイヤーで完全に消去された情報は、二度と復元できません。

## 2. 反TokenGateの構造設計：全量保持と動的スケッチ

本アーキテクチャの思想は明快です。**情報を捨てることが健忘を招くなら、すべて保持し、必要な時だけ覗き見れば良い**というアプローチです。

システムは以下の4層構造で構成されています。

### 1. システムRAMを完全な永続KV層として活用
セッション全体のKVキャッシュは、ホストの物理メモリ上に4ビットまたは8ビットで完全保持されます。80GBから128GBのホストメモリを活用することで、GPUメモリを長大な履歴の保管負担から完全に解放します。

### 2. ランク64キースケッチによる超高速インデックス
GPUメモリ上には、各トークンの要約情報となる次元数64の超小型キースケッチと、ごく一部の直近ホットキャッシュのみを維持します。
各デコードステップにおいて、専用のTritonカーネルがGPU上でスケッチを高速評価し、250Kトークンの中から現時点で最も重要な上位約2000トークン、全体の約1パーセントを極小の負荷で選出します。

### 3. オンデマンドなPCIeストリーミング
選出された上位1パーセントのトークン重みのみが、PCIeバスを通じてシステムRAMからVRAMへと瞬時に転送され、標準のCUDAグラフセーフなアテンションカーネルで精密計算されます。転送データ量は数十ギガバイトから毎ステップ数メガバイトへと激減し、バスの混雑は完全に解消されます。

### 4. エージェント並行実行を支えるノンブロッキングスケジューラ
vLLMをベースに動的スパースパッチとスケジューラ改善を導入しました。
- **高密度と低密度の自動切り替え**：短い会話では標準の高密度パスを走らせて遅延ゼロを維持し、長文展開時に自動で1パーセントのスパースパイプラインへ遷移します。
- **特定セッションによる独占の防止**：巨大プロンプトの読み込み時に他セッションが停止する問題を修正し、1体のエージェントが大規模リポジトリを走査している最中でも、他の7体が淀みなく応答を生成し続けます。

## 4. コミュニティの厳格な検証：隠れた制約と精度の議論

技術的な客観性を担保するため、コミュニティ内で提起された慎重な意見についても余すところなく記載します。

### 4ビットKVキャッシュの精度低下リスク
経験豊富な開発者Hefty_Wolverineは以下の警鐘を鳴らしています。
8並行の250Kコンテキストを収容するため、ホストメモリ上のKVキャッシュは4ビット量子化されています。超長文環境では量子化ノイズが蓄積し、型修飾子のわずかな解釈違いが深刻なバグを生む危険性が指摘されています。

### サンプリング推定の偏りと推論検証の課題
開発者Every-Fortuneは、Q4に圧縮されたキャッシュからさらに上位1パーセントをサンプリングする二重の推定プロセスについて、多段の依存関係を跨ぐ深い論理推論での信頼性にはさらなる検証が必要であると論じました。

開発者自身もこの指摘を真摯に受け止めており、RULERやLongBenchといった多段推論ベンチマークでの包括的な検証を次の最優先課題として掲げています。

## 5. まとめと実践的示唆

この実験がもたらした真の価値は、単一の完成品にとどまらず、マルチエージェント実行基盤における新たなパラダイムを切り拓いた点にあります。

1. **計算資源の固定観念を打破**：高価な専用クラスタを導入せずとも、適切なメモリ階層設計によってRTX 3090の2枚構成で250Kエージェント8並行を達成できます。
2. **履歴を消去しないアプローチ**：長文エージェントの記憶を無理に削るのではなく、システムメモリに蓄積しながら必要な断片のみを動的に呼び出す手法が正解です。
3. **実務適用の見極め**：コードレビューやログ調査などスループットが重視される場面には最適である一方、金融系ロジックなどの極めて厳密なコーディングでは量子化ノイズへの配慮が不可欠です。
