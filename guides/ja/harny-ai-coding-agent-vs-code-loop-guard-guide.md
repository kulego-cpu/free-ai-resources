まず現場の悩みから入りましょう。ローカルの小型モデルで自律コーディング Agent を動かすと、十中八九失敗します。

多くの開発者が Mac や 16GB VRAM を積んだマシン上で、Ollama や llama.cpp を使い Qwen2.5-Coder-7B の Q4_K_M や Llama-3.1-8B-Instruct を動かしています。1 往復の補完や日常的なチャットであれば快適に動きます。しかし VS Code 内でツール呼び出し権限を与えてコード修正を自律実行させると、途端に収集がつかなくなります。

典型的な失敗パターンは二つあります：

一つ目は無限ループです。小型モデルは同じエラーの周りを堂々巡りし、同一のツールを繰り返し呼び出し、文脈限界を食いつぶすまで止まりません。

二つ目はディスクへの不意打ち上書きです。モデルの理解が少しずれただけで、元のソースコード全体を壊れた骨組みに書き換えてしまい、取り返しがつかなくなります。

オープンソース拡張機能 Harny はこの二大課題を解決するために作られました。GitHub 上の spltek/harny にて MIT ライセンスで公開され、現在の実測バージョンは v0.3.2 です。VS Code および VSCodium のサイドバーに常駐するこのツールは、モデルの賢さを過剰に宣伝することなく、Loop Guard と Analyze モードという二つの確実なブレーキを備えています。

ローカルモデルは日々のリファクタリングに耐えうるのか。この防御機構は本当に破綻を防げるのか。

## 小型モデルが Agent 処理で抱える先天的な弱点

クラウド上の超巨大モデルは、自己修正能力と長期的な計画性に優れています。ツールの実行に失敗しても、通常は 2 往復以内に別のアプローチへ切り替えます。

しかし 7B から 14B 規模のローカル小型モデルはどうでしょうか。

小型モデルが Agent 処理で失敗する理由は、致命的な三つの構造的要因にあります：

最も軽い問題は注意力の散漫です。やり取りが増えるにつれてコマンド出力やファイル内容が文脈に蓄積されます。数千トークンが積み重なると、最初の指示を忘れてしまいます。仕様上の 32K 文脈窓はベンチマーク上の数値であり、実戦での保証ではありません。

さらに深刻なのは同じ過ちの反復です。ツールの呼び出しに失敗してエラーを目にした際、小型モデルは推論のバックトラックを行えません。無意識にまったく同じ引数で再実行し、同じ釈明を出力し続けます。貪欲サンプリングの局所解がブラックホールのようにモデルを縛り付けます。

最も被害が大きいのは確認なしの上書きです。多くの統合型 Agent はワークスペースのファイルを直接変更します。論理構造が崩れた小型モデルは正常な業務コードを誤って消し去り、ファイルを破壊します。

Harny の設計思想は明快です。モデルが自律的に判断できないのであれば、外側の実行フレームワークが確実な安全帯を設けるべきだというアプローチです。

## 核心設計一：Loop Guard による無限ループの強制切断

Agent の実機検証において最もトークンを浪費しストレスとなるのが無限ループです。

Harny は実行レイヤー内部にリアルタイムの Loop Guard を組み込んでいます。モデルが自発的に気づくのを待つのではなく、実行履歴のスライディング指紋テーブルを監視します。

```text
モデルがツール呼び出しを発行
       │
       ▼
┌──────────────────┐
│ 特徴ハッシュ計算   │  関数名 + 引数ハッシュ + 出力類似度
└────────┬─────────┘
       │
       ▼
       / 重複パターン合致？ \
     <                      > ── いいえ ──▶ 通常通り実行
       \       はい         /
       │
       ▼
┌──────────────────┐
│ Loop Guard 介入  │
└────────┬─────────┘
       │  段階的な制御
       ├─▶ 第 1 段階：反復を警告しアプローチ変更を促す指示を注入
       ├─▶ 第 2 段階：該当ツールの呼び出しを遮断しスタックを巻き戻す
       └─▶ 第 3 段階：セッションを停止し手動操作へ切り替える
```

実際の検証環境で、Ollama 上の Qwen2.5-Coder-7B に TypeScript の型エラー解消を指示しました。ターミナルには以下のエラーが出力されました：

```text
src/index.ts:14:7 - error TS2322: Type 'string' is not assignable to type 'number'.
npm run build exited with code 2
```

モデルは誤った引数修正を行いました。2 回目のビルドも失敗しました。反省することなく、3 回目も同一のコマンド呼び出しを試みました。

普段であればターミナルの空転を見守るしかありません。しかし 3 回目の実行直前、Harny の画面上に遮断の警告が表示されました：

```text
[Loop Guard] Detected repeated tool execution: npm run build
Action blocked. Injecting steering prompt to switch investigation approach.
```

ツール実行権限が即座に奪われ、tsconfig.json とソースの型定義を read_file で確認するよう促す指示が強制注入されました。

この処理により無限リトライが断ち切られ、貴重な文脈容量が保護されました。

## 核心設計二：Analyze モードによる Dry-run 防壁

コードの改修で最も警戒すべきは誤削除です。

Harny は作業モードを **Analyze 分析モード** と **Build 構築モード** の二つに厳密に分けています。

セッションはデフォルトで Analyze モードとして動作します。このモード下では、ファイルの作成、修正、削除を伴うすべてのツールが Dry-run 模擬状態で動きます。

これが意味することは何か。

推論と実ファイルへの書き込みの間に、物理的な壁が築かれます。Analyze モード中、モデルはファイルを修正した気になっていますが、ディスク上の実ファイルはまったく変わりません。モデルが暴走しても、一文字たりとも消される心配はありません。

Harny はサイドバー上に正確な Unified Diff 差分画面を生成します。Git コミット前のコードレビューと同じように、どの変数や関数が変更されたかを 1 行ずつ確認できます。

差分の妥当性を人間が目視確認した上で、手動で Build モードへ切り替えて初めてディスクへの書き込みが実行されます。

書き込み権限を人間の手元に残す設計が、安心感をもたらします。

## 核心設計三：観察マスクとコンテキスト便箋機能

無限ループに加えて、ローカル環境で頻発するのがメモリと文脈の枯渇です。Apple Silicon M2 Pro 16GB で 8K 文脈を動かす際、膨大なログが流入するとメモリ圧迫が生じます。

観察マスク Observation Masking は実証済みの技術です。Anthropic の文脈管理手法や JetBrains の調査報告でも示されている通り、古いコマンド出力を要約へ置き換え、直近の応答のみを保持することで長時間の作業性能を維持できます。

Harny の実装は合理的です：

一つ目は古い観察出力の自動マスキングです。複数ターンの会話の中で、直近 1 から 2 回のコマンド出力のみをそのまま保持します。それ以前の長い出力は状態要約へ自動変換され、事実のみを残して冗長な文字列を削ぎ落とします。

二つ目は構造化された Scratchpad 任務メモの保持です。修正したファイル一覧や現在の検証段階のみを専用メモに記録し、過去 20 回分の不要なやり取りは文脈から破棄します。

8K 文脈の小型モデルでテストしたところ、過去の指示を忘れることなく 10 ターン以上の複数ファイル改修を完了できました。

## 実践手順：Ollama から Harny への接続

ローカルで安全な Harny 環境を立ち上げる手順は簡単です：

### 1. ローカルモデルのエンドポイント起動

Ollama や llama.cpp を起動します。Ollama の場合、デフォルトで 11434 番ポートが開きます：

```bash
ollama run qwen2.5-coder:7b
```

### 2. Harny 拡張機能の設定

VS Code の拡張機能メニューから Harny を導入し、サイドバーの設定を開きます：

- **API Protocol**: OpenAI Compatible を選択
- **Base URL**: `http://localhost:11434/v1`
- **API Key**: `ollama` などの任意の文字を入力
- **Model Name**: `qwen2.5-coder:7b`

### 3. トラブルシューティングの推奨手順

ローカルモデルを使用する際は以下の手順を推奨します：

必ず Analyze モードから開始します。課題を提示し、モデルにファイルの読み取りと Unified Diff の提案を行わせます。この事前確認を省いてはいけません。

差分の境界を目視します。関係のないファイルが巻き込まれていないか、既存のコメントが消えていないかを確認します。

確認後に Build モードへ切り替えて適用します。ワンクリックで反映させた後、ローカルターミナルでテストを回して修正を完了させます。

## まとめ

超巨大クラウドモデルが普及する現在、あえてローカルで動かす意義はどこにあるのでしょうか。

理由は明快です。機密コードを外に出さないこと、オフラインでも作業できること、毎月の API 請求書に怯えずに済むこと。派手さはありませんが、どれも現場で外せない利点です。

Harny が示す教訓は実践的です。モデルが汎用知能に達するまでの過渡期において、堅牢な実行フレームワークと防御設計がパラメータ規模の不足を補います。

手元に余っているローカル VRAM があるなら、確実な安全枠をはめて試してみてはいかがでしょうか。

確実なブレーキと境界線を設ければ、ローカルモデルも安全に役立ってくれます。
