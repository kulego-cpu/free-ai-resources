ローカル環境で大規模言語モデルを動かす際、量子化バージョンの選定で迷った経験は誰にでもあるはずです。

重みファイルをダウンロードする前、誰もが躊躇します。

Q8_0を選ぶと、ファイルサイズは十数ギガバイトに膨らみます。グラフィックボードのVRAMには収まりきらず、システムメモリへ溢れ出た瞬間に生成速度は秒間2〜3トークンへと失速し、画面は紙芝居状態に陥ります。

一方でQ2_KやQ3_Kを選べば、ファイルサイズは手頃でVRAMにも余裕で収まります。しかし極限まで圧縮された2ビットや3ビットで、推論能力がどれほど削ぎ落とされたのか不安が残ります。学術論文には整然としたパープレキシティ統計表が並びますが、日々のコード作成や論理推論においてその数値が何を意味するのか、指標だけでは見えてきません。

誰にも実態は分からないのです。

モデルの劣化は均一なペースで進むわけではありません。長文推論の特定の転換点において、確率分布が平坦化した結果、文法的には通じるものの事実関係が破綻した候補単語を一度選んでしまうと、その1トークンを境に出力全体が幻覚へと崩壊します。

なぜ突然脱線してしまうのか？

これまで2つの量子化モデルによる判断のズレを観察するには、Pythonスクリプトを書いてフックを仕込み、ロジットを地道に回収するしかありませんでした。コードの作成は煩雑で、原因究明の効率も極めて低い状態でした。

そんな中、GitHubに登場したオープンソースプロジェクトinside-llmが、この面倒な調査を単一バイナリで動く対話型ツールに変えてくれました。

開発者はManuel García氏で、リポジトリは `https://github.com/manuelgscom/inside-llm`、ライセンスはMITです。内部に完全なllama.cppコアを内蔵しており、ブラウザ上で2つのGGUFモデルを並行動作させ、トークン単位で分岐境界線を可視化してくれます。

内部はどのような仕組みで動いているのか？本当に実用的なのか？

ローカルのマシンに導入し、徹底的に検証してみました。

## 1. ハードウェア環境と単一バイナリ設計：どのように動作するのか

検証データに客観的な基準を持たせるため、実行環境を明記しておきます：
- OS：Ubuntu 24.04 LTS、Linux 6.8カーネル
- GPUおよびドライバ：GeForce RTX 3060 12GB GDDR6、NVIDIAドライバ 550.54.14、CUDA 12.4
- CPUおよびメモリ：AMD Ryzen 5 5600 6コア、32GB DDR4物理メモリ
- 導入バージョン：inside-llm release v0.2.1、Gitコミット a9f4c21、llama.cpp b3800コア内蔵

多くの可視化ツールは初期設定が極めて煩雑です。Python仮想環境を作成し、PyTorchを入れ、ビルド依存関係を整え、CUDAドライバの不整合が起きれば半日が環境構築だけで消えてしまいます。

inside-llmのアーキテクチャ設計には、生粋のC++エンジニアらしい実直さが表れています。バックエンドエンジンはC++17で書かれ、llama.cppおよびggmlライブラリと静的リンクしています。WebフロントエンドはSvelte 5を採用し、3D確率地形の描画にはthree.jsを使用しています。ビルド時にすべてのWeb静的リソースが単一バイナリの内部へ直接埋め込まれます。

`chmod +x` で実行権限を与えてターミナルから直接実行すると、コンソールには `listening on :8642` と1行だけ表示され、静かに待機します。

ブラウザで `http://localhost:8642` を開くと、UIが瞬時に立ち上がります。pip installも、npm run devも、商用APIキーの登録手続きも一切不要です。初めて動かした際、習慣でREADMEをめくって環境変数の設定欄を探してしまいましたが、設定項目など最初から存在しませんでした。

```bash
# 実行ファイルに権限を付与
chmod +x ./inside-llm

# ローカルエンジンを起動し8642ポートで待機
./inside-llm --port 8642
```

データ通信には軽量なバイナリフレームが採用され、ブラウザとC++エンジンの間をWebSocket経由で高速に行き来します。

公式リリースページでは、LinuxとWindows向けにCUDA版とVulkan版のコンパイル済みバイナリが配布されています。CUDA開発環境が入っていない事務用PCであっても、GPUドライバさえ正常に動いていれば、解凍してすぐに起動できます。

## 2. デュアルストリーム並行比較：Q2_KとQ8_0が分岐する瞬間を捉える

Web画面に入ったら、まずはModel AとModel Bを選択します。

ここで1つ物理的な制約があります。両モデルは同一のトークナイザー語彙を共有していなければなりません。今回は同一モデルファミリーから2つの重みを用意しました：
- Model A：`Qwen2.5-7B-Instruct-Q2_K.gguf`、ファイルサイズ 2.78 GiB
- Model B：`Qwen2.5-7B-Instruct-Q8_0.gguf`、ファイルサイズ 7.70 GiB

読み込み時間について、mmap経由でVRAMにマッピングされ、Model Aは1.2秒、Model Bは4.1秒でロードが完了しました。最初のトークン出力レイテンシは310ミリ秒で、ロックステップ時のスループットは28.4トークン毎秒を安定して記録しました。

動作モードは2種類用意されています：
- ロックステップモード Lockstep：同一の入力プロンプト文脈を両モデルに強制入力し、現在の候補単語の確率分布を左右並べて比較します。
- フリーモード Free：各モデルが自身でサンプリングしたトークンに基づき推論を進め、両者の出力テキストが完全に分岐するまで観察します。

複雑な並行カウンタのコード推論タスクでテストを行いました。最初の30文字までは両者の出力が完全に一致していましたが、31番目のトークンに達した瞬間、決定的な分岐が発生しました。

どこでズレが生じたのか？

確率グラフを確認すると原因は一目瞭然でした。

Q8_0側では候補単語 `eight` が0.87という圧倒的な確率を占め、競合候補を完全に平伏させていました。

一方でQ2_Kに切り替えると、`eight` は0.31まで急落し、`six` が0.29まで迫っていました。本来なら0.01以下に沈んでいるはずのノイズ候補が、一様に0.05付近まで浮上していたのです。

確率が消えたわけではありません。量子化ノイズによって山が均され、平坦化してしまったのです。分布が平坦になれば、サンプラーのわずかな揺らぎで誤った単語が選ばれてしまいます。

UIのStreamパネルでは、分岐が発生した箇所に鮮やかなマゼンタ色のマークが付きます。候補パネルを開くと左右対称の棒グラフが表示され、右側にはシャノンエントロピーと双方向カルバック・ライブラー情報量 KLダイバージェンスが算出されます。Q8_0を基準分布P、圧縮されたQ2_Kを近似分布Qと置いたとき、31番目の直前までKL値は0.04付近で安定していましたが、分岐点において一気に1.82へと跳ね上がりました。精度の劣化が定性的な印象論ではなく、時系列上の座標として明確に特定できるのです。

## 3. サンプラー段階追跡：Top-k、Top-p、Min-pは何を削ぎ落としているのか

普段ollamaやllama-serverでサンプリングパラメータを調整する際、多くのエンジニアが勘に頼っています。温度は0.7か0.8か？Top-pを0.9にすると有効な表現まで切り捨てていないか？最近注目を集めるMin-pは、従来の切り捨て手法と何が違うのか？

普段のパラメータ調整はブラックボックス相手の暗中模索になりがちですが、inside-llmはその箱に透明な窓を開けてくれます。Gatesパネルはllama.cpp内部のサンプラーパイプラインを忠実に再現しており、生のロジットベクトルが出力された後、ペナルティ項、Top-k、Top-p、Min-p、温度スケーリング、GBNF文法制約を順に通過します。各段階の上部には、生き残った候補単語の数が明示されます。

```bash
# 特定のモデルペアとコンテキスト長を指定して起動
./inside-llm \
  --model-a ./models/Qwen2.5-7B-Instruct-Q2_K.gguf \
  --model-b ./models/Qwen2.5-7B-Instruct-Q8_0.gguf \
  --ctx 4096
```

各フィルタ段階をクリックすると、切り捨て前後の分布変化がグラフで表示されます。実際の挙動を観察すると驚きの連続でした。

Top-p 0.9は緩やかな設定に思えますが、トップ候補の確率が92%を占める高確信度の場面では、Top-pは最初の段階で残りの数千個の候補を一網打尽に切り捨ててしまいます。逆に分布が平坦な場面では、意味の曖昧な境界単語を数十個も通過させてしまいます。

一方でMin-pを0.05に設定すると、切り捨て閾値がトップ候補の確信度に応じて自動連動します。トップが0.92であれば閾値は自動的に0.046まで引き上げられ、Q2_Kで異常浮上した0.01〜0.03の末尾ノイズが綺麗にカットされます。この直感的な挙動の把握は、ドキュメントを読み込むよりも遥かに深い納得感を与えてくれます。

## 4. Logit Lens隠れ層投影：モデルはどの層で決断を下しているのか

最終出力の比較だけであれば、単なる綺麗なデバッグツールに過ぎません。`--lens` オプションを付けて起動すると、Logit Lensに基づく全層の隠れ状態投影機構が作動します。

Qwen2.5-7Bは28層のTransformerブロックで構成されています。モデルは最終層で急に答えをひらめくのか、それとも中間層の時点で既に正解候補を絞り込んでいるのか？

Logit Lensを有効にすると、画面下部に2次元の層別タイムステップ投影図が展開され、3Dの立体確率地形としても表示可能です。横軸はトークン生成の進行度、縦軸はネットワークの物理的な層の深さを表します。

アルゴリズムの計算量証明問題を解かせてみました。プロンプトを入力した直後、最初の5層までは高エントロピーなノイズ候補が並びます。

正解はどの層で固まるのか？

14層付近に達すると、鍵となるアルゴリズム名の確率が徐々に凝縮し始めます。21層目に到達した時点では、前方にまだ7層も残っているにもかかわらず、正解の確率はすでに82%を超えており、残りの層は文末の接続詞や表現の微調整を行っているに過ぎませんでした。

一方で量子化による劣化が激しいQ2_Kモデルでは、この確率の凝縮が25層目まで遅れ、途中でアテンションのわずかな揺らぎによって別候補へと引っ張られやすくなります。

さらに、タイムライン上の任意の分岐点を直接クリックすることも可能です。インメモリのスナップショット機能により、分岐直前の状態へと瞬時に巻き戻し、別の候補単語から再推論を分岐させることができます。突発的な幻覚の原因を突き止める上で、極めて心強い実験環境となります。

## 5. 実運用における技術的制約と注意点

非常に有用なツールですが、実機で扱う上ではいくつか物理的な制約を把握しておく必要があります。

まずVRAM容量の壁です。8GBのグラフィックボードで7Bモデルを2つ同時に並行動作させようとしてはいけません。初回テスト時に調整を行わずに起動したところ、2つの合計サイズが10GBを超え、`CUDA error: out of memory` が発生して `ggml_cuda_compute_forward` のメモリ確保で停止しました。

8GBカードでデュアルモデルは動くのか？

`-ngl 18` でGPUオフロード層を削れば動作自体は可能ですが、計算層の一部がメインメモリへ追いやられ、生成速度は秒間28トークンから3.8トークンへと急降下しました。コード比較が1回終わるまでに40分近く待たされることになります。

対話型の調査でこの待機時間に耐えられるエンジニアはいません。8GB環境であれば、3Bクラスのモデルを2つ並べて比較する運用をお勧めします。

次に語彙の一致という大前提です。2つのモデルは同一ファミリーでなければなりません。Llama-3とQwen2.5を並べて比較しても、トークナイザーのエンコード規則が根本から異なるため、トークンIDの対応が取れず、統計的な情報量を計算しても意味がありません。

最後に、現時点ではテキスト単一モーダルのみの対応となっています。マルチモーダルモデルの重みファイルを読み込むことは可能ですが、UI上での可視化はテキスト生成パスに限定されており、視覚アテンションの投影機能はまだ実装されていません。

現在、新しい量子化ファイルを試す際は、まずinside-llmに通す習慣がつきました。同一プロンプトを入力し、両者が何トークン目で分岐するかを確かめます。早い段階で分岐するならそのタスクは精度に敏感なのでQ5_K_MやQ8_0を使い、数百トークン後まで分岐しないならQ2_Kで妥協し、浮いたVRAMでコンテキスト長を2倍に広げるといった現実的な判断が下せます。

何でも解決する魔法の杖ではありません。語彙が合わなければ動きませんし、マルチモーダルもまだ見られません。作者のissueによると視覚投影も開発中とのことです。現時点でのテキスト検証ツールとしては、十分実用に耐えうる仕上がりです。

デスクトップの描画負荷を差し引いた後、手元のグラフィックボードには実際にどれだけのVRAM空き容量が残っていますか？闇雲にダウンロードする前に、nvidia-smiで計算してみることをお勧めします。
