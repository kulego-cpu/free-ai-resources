# Claude Code 端末プロキシ実践：LiteLLM による PKCE 更新処理、Gemini 2.5 と DeepSeek の 0 円ルーティング

先週の金曜日、手元の検証環境で TypeScript プロジェクトを対象に Claude Code による自動移行を走らせました。

対象は複数の AST パーサーを抱える 12000 行規模のオープンソースリポジトリです。

開始からわずか 30 分でモジュール横断の型推論と非同期関数のリファクタリングが 3 周完了しました。

その時点で Anthropic 公式ダッシュボードには 4.2 ドルの請求が記録されていました。

痛い出費です。

財布に直撃します。

ターミナル内での対話操作そのものは極めて軽快でした。

本当に速い。

しかしこの消費ペースでは毎月のトークン代を維持できません。

多くのエンジニアがローカルのリバースプロキシを経由してサードパーティのエンドポイントに転送しようと試みています。

しかし環境変数を書き換えただけでは大抵 2 時間も持ちません。

なぜか。

セッションの実行中に突然 OAuth トークン失効エラーを吐いてターミナルがクラッシュするからです。

ローカル回線の瞬断による TLS タイムアウトでしょうか。

当初は完全に原因を見誤っていました。

的外れな推測でした。

パケットをキャプチャして認証ハンドシェイクを確認したところ、構造上の障壁が判明しました。

昨日、オープンソースのゲートウェイである LiteLLM にコミット dc378de207f8 がマージされました。

このコミットは Claude Code をローカルプロキシ経由で動かした際に発生する PKCE 認証更新の断絶をピンポイントで修復するものです。

まさに欲しかった修正でした。

コミットの diff を確認すると、proxy_server.py の変更は十数行にとどまります。

anthropic.py に _refresh_oauth_token というモック処理の分岐が追加され、残りはテストケースでした。

仕組みの本質は /v1/oauth/refresh に飛んでくるリクエストを横取りすることです。

プロキシ側でローカル生成したダミートークンを返し、expires_at を次の周期へ先送りします。

要するにクライアントに対して期限切れではないと偽装する処理です。

トークンの更新リクエストは Anthropic の推論用 API ではなく、独立した OAuth 専用エンドポイントに向けて送信されていました。

見落としやすい設計です。

そのため ANTHROPIC_BASE_URL だけを書き換えても更新パケットはすり抜けてしまっていたのです。

Google AI Studio は Gemini 2.5 Flash の無料枠を提供しています。

DeepSeek V3 公式 API は安価なフォールバック先として機能します。

このパイプラインをローカルで確立すれば、日々の開発におけるトークン課金をゼロに近づけることができます。

## 一、 認証インターセプトはどこで破綻していたのか

Claude Code はオープン規格準拠の汎用 CLI エージェントとは設計思想が異なります。

Cline や Aider などのツールは標準的な HTTP クライアントとして実装されています。

設定ファイルに任意の baseURL と API キーを指定すれば、リクエストは忠実に送信されます。

しかし Claude Code は Anthropic の自社環境に強く最適化されたプロプライエタリなツールです。

初期接続からセッション維持にかけて 2 系統の認証ルートを使い分けています：
- 環境変数 ANTHROPIC_API_KEY を直接読み込み、公式の従量課金枠を消費するルート；
- claude login コマンドを実行し、ブラウザ経由の PKCE フローで一時トークンを取得するルート。

多くの開発者がシェル上でローカル向けのリダイレクトを試みました：

```bash
export ANTHROPIC_BASE_URL=http://127.0.0.1:4000
export ANTHROPIC_API_KEY=sk-dummy-mock-token
```

単発の質疑応答であれば問題なく動作します。

非常に軽快です。

順調に見えます。

しかし時間のかかる本格的なリファクタリングを任せると、セッション継続時間が 2 時間を超えた段階で強制的に更新パケットが送出されます。

一般的なプロキシはこの独自ハンドシェイクに対応していません。

ゲートウェイは即座に 401 エラーを返します：

その場で停止。

```text
Error: Failed to refresh PKCE authentication session
OAuth token expired, server returned 401 Unauthorized
```

20 分間かけて構築された数万トークン分のコードコンテキストが一瞬で消し飛びます。

前触れのないクラッシュとコンテキスト消失に耐えられるエンジニアはいません。

LiteLLM のコミット dc378de207f8 はこの断絶を解消しました。

ゲートウェイがローカルループバック内で更新パケットをキャプチャし、インクリメントされた認証情報を自動発行します。

横取り成功。

実によく機能します。

更新処理はすべてローカルメモリ内で完結します。

クライアントは公式クラスタが正常応答したと認識し、長時間のセッションが維持されます。

## 二、 上流モデルの組み合わせロジック

通信経路が開通した後は、バックエンドに配置するモデルの選定が重要になります。

Google AI Studio は Gemini 2.5 Flash 向けに手厚いデイリー無料枠を提供しています。

1 回のリクエストでネイティブに 100 万トークンのコンテキストを扱えます。

巨大なコードベースの AST 構文木を分割せずに一括で読み込めるため、開発効率が劇的に向上します。

無料枠は魅力的ですが、厳格な制約が存在します。

無料枠の制限値は 1 分あたり最大 15 リクエストです。

エージェントが複数ファイルを並行走査して編集を繰り返すと、数秒でレートリミットに達し 429 エラーを食らいます。

その際に代替となるバックアップ手段がなければ処理は即座に停止してしまいます。

フォールバック先に求められる要件は明確です：
- DeepSeek V3 アーキテクチャを採用した公式 deepseek-chat エンドポイントを利用すること；
- キャッシュヒット時は 100 万トークンあたり 0.014 ドル、ミス時でも 0.14 ドルと破格であること；
- コード生成能力と構造化 JSON 出力精度が高いこと。

この 2 系統を LiteLLM で束ねる構成をとります。通常時は無料枠を使い、バースト時は超低価格 API に逃がす二重構造です。

## 三、 ローカル config.yaml の作成と設定の注意点

ローカルマシンに独立した Python 仮想環境を作成し、修正パッチを含む LiteLLM を導入します：

```bash
python3 -m venv .venv-litellm
source .venv-litellm/bin/activate
pip install --upgrade "litellm[proxy]>=1.61.0"
```

続いて作業ディレクトリ内に config.yaml を作成します：

```yaml
model_list:
  - model_name: claude-3-5-sonnet-20241022
    litellm_params:
      model: gemini/gemini-2.5-flash
      api_key: os.environ/GEMINI_API_KEY
      rpm: 15
    model_info:
      supports_function_calling: true

  - model_name: claude-3-7-sonnet
    litellm_params:
      model: deepseek/deepseek-chat
      api_key: os.environ/DEEPSEEK_API_KEY
      api_base: https://api.deepseek.com/v1
    model_info:
      supports_function_calling: true

router_settings:
  routing_strategy: latency-based-routing
  fallbacks:
    - claude-3-5-sonnet-20241022: ["claude-3-7-sonnet"]
  num_retries: 2
  timeout: 45

litellm_settings:
  drop_params: true
  set_verbose: false
```

この設定において絶対に外せない急所が 2 点存在します。

第 1 に drop_params を true に設定することです。

もし drop_params を無効のままにするとどうなるか。

Claude Code は thinking 深度やベータ版固有の独自パラメータをリクエストボディに付与します。

未対応のモデルは未知のプロパティを検知した瞬間に HTTP 400 バリデーションエラーを返します。

drop_params を有効にすることで、転送前に不要な独自パラメータをゲートウェイ側で自動除去できます。

第 2 に supports_function_calling を明示的に true にすることです。

必須設定です。

ここを忘れると完全に機能不全に陥ります。

ファイル書き換えや正規表現検索はすべて Function Calling プロトコル経由で実行されます。

このフラグが抜けているとツール実行結果が単なるテキストとして扱われ、エージェントが一切動作しなくなります。

ツール呼び出しが動かないエージェントなど役に立つでしょうか。

## 四、 起動手順と実機での疎通検証

設定完了後、メインのターミナルで各社の API キーをエクスポートしてプロキシを起動します：

```bash
export GEMINI_API_KEY="あなたのGoogleAPIキー"
export DEEPSEEK_API_KEY="あなたのDeepSeekAPIキー"

litellm --config config.yaml --host 127.0.0.1 --port 4000
```

コンソールに起動ログが表示されます：

```text
INFO:     Started server process 84210
INFO:     Waiting for application startup.
INFO:     Application startup complete.
INFO:     Uvicorn running on http://127.0.0.1:4000
```

別のターミナルタブを開き、対象プロジェクトのルートディレクトリに移動して環境変数を流し込みます：

```bash
export ANTHROPIC_BASE_URL="http://127.0.0.1:4000"
export ANTHROPIC_API_KEY="sk-mock-litellm-local-auth"

claude
```

ターミナルに Claude Code 特有の対話プロンプトが立ち上がります。

起動成功。

具体的なタスクを与えてみました：未処理の Promise を検出して try catch で保護し、対応するユニットテストを更新せよ。

LiteLLM のコンソールに標準的なアクセスログが流れ始めます：

```text
INFO:     127.0.0.1:54320 - "POST /v1/messages HTTP/1.1" 200 OK
INFO:     127.0.0.1:54322 - "POST /v1/messages HTTP/1.1" 200 OK
```

カーソルが目まぐるしく点滅し、初回のリファクタリングとテスト実行が走り切りました。

一見すると完璧に見えます。

しかし別系統のモデルにすげ替えた状態で、実際のツール呼び出し引数は常に正確に維持されるのでしょうか。

実情はそれほど甘くありません。

## 五、 ツール呼び出しの不具合トラブルシューティングと縮退実測

多くのチュートリアル記事では異種モデルのプロキシ化があたかも無欠であるかのように語られます。

しかし高負荷な実務コーディングにおいて、ツール呼び出し周りは決して無風ではありませんでした。

16 回に及ぶ連続テストの中で、3 つの典型的な不具合に直面しました。

第 1 のトラブルは階層の深いディレクトリを走査する edit_file で発生しました。

不気味な挙動でした。

Gemini がスキーマ定義の old_string を old_text という名前で出力したのです。

Claude Code クライアントは必須フィールドが欠落したと判定し、Invalid tool input エラーで停止しました。

これは単なるモデルの幻覚でしょうか。

5 分ほど追跡して判明したのはレスポンス側のスキーマドリフトでした。

drop_params はモデルへ向かう入力引数を削るだけで、モデルから返却される tool schema の正規化までは担当しません。

解決策として設定ファイルに軽量な post_call_hook を組み込み、クライアントへ返す前に old_text を old_string へ強制書き換えしました。

解決です。

第 2 のトラブルは DeepSeek への縮退時に起きました。

run_shell_command の引数に含まれる timeout をモデルが文字列の "30" として出力しました。

ローカルの実行プロセスが int 型への直接変換を試み、型エラーで例外を発生させました。

第 3 のトラブルは Gemini の 15 RPM 制限に激突した瞬間のフェイルオーバーで発生しました。

LiteLLM はおよそ 65 ミリ秒で deepseek-chat へトラフィックを迂回させました。

しかし DeepSeek は初回の試行で tool_use ブロックを欠落させ、単なる解説文のみを返してきました。

リトライ設定がなければその場でセッションは中断していたはずです。

router_settings に num_retries: 2 を明記していたおかげで、2 回目の試行で無事にツール呼び出しブロックを回収できました。

実戦環境においてツール呼び出しの成功率が 9 割を超えれば上出来と評価すべきです。

設定しただけで完璧に動く環境など幻想に過ぎません。

検証環境：M2 MacBook Air メモリ 16GB、光回線 500Mbps。
- Gemini 2.5 Flash の初回応答時間は 320 から 480 ミリ秒、生成速度は 75 から 90 トークン毎秒。
- DeepSeek V3 の初回応答時間は 650 から 850 ミリ秒、生成速度は 40 から 55 トークン毎秒。

数十ミリ秒の切り替え遅延は作業時の快適性に影響を与えるでしょうか。

画面上のカーソルを見守る限り、切り替えに伴う体感上の引っ掛かりは皆無でした。

極めてスムーズです。

ただし背後のリトライ戦略を漏れなく記述しておくことが絶対条件です。

## 六、 運用の現実的境界線と妥協点

一連の検証を終えた今、実務での線引きを率直に明言しておく必要があります。

勤務先の機密プロジェクトでローカル LiteLLM を常用することは推奨しません。

127.0.0.1 へのバインドが技術的に危険だからではありません。

外部ネットワークからスキャンされる心配は皆無です。

問題は組織のコンプライアンス規約にあります。

絶対に抵触してはいけません。

大半の企業において開発ソースコードを外部 API へ送信する行為は情報セキュリティ部門の承認を要します。細切れに分割して送信しても規約違反に変わりはありません。

そうした環境では躊躇せず公式のエンタープライズ契約を申請すべきです。

一方で個人のオープンソース開発、趣味のリポジトリ、自作ツールの開発であれば、本構成は圧倒的な威力を発揮します。

Gemini 2.5 Flash の無料枠で日常のリファクタリングを賄い、溢れた分を DeepSeek に逃がしても 1 日の出費は数円から数十円程度に収まります。

唯一この構成をおすすめできないユースケースは、CI パイプラインでの大規模な完全無人実行です。

15 RPM の壁は高頻度な並列処理に耐えられず、連続する 429 エラーによってビルド完了が大幅に遅延します。

そうした自動化で月額料金をケチるのは本末転倒です。

数十ミリ秒のフェイルオーバーのために手元で設定を作り込む価値はあるでしょうか。

毎月数千円から数万円のサブスクリプション費用を節約しつつ自由な開発環境を手に入れられるなら、数行のフック処理を書く労力など微々たるものです。

大幅なコスト削減。

極めて有意義です。

このプロキシ構成は私の作業マシン上で 1 週間以上安定して稼働し続けています。

折を見て old_text のフィールド名ドリフトを解消する正規化パッチを LiteLLM 本家にプルリクエストとして送るつもりです。

アップストリームに取り込まれるのが理想的です。

ローカルで pip upgrade を実行するたびにフックパッチを手動で当て直すのは地味に骨が折れます。

実に面倒です。
