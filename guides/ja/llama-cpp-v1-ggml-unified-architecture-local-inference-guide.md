2年前の春、端末に表示された粗削りな純 C 言語による推論ループを見て、単一ファイル構成の実験的コードが将来 v1.0.0 という正式なタグを刻むと誰が予想できたでしょうか。

2026 年 11 月 18 日、Georgi Gerganov 氏は llama.cpp および基盤テンソルライブラリ GGML の v1.0.0 正式リリースを発表しました。Linux ワークステーションや Apple Silicon で日々ローカル推論を追求するエンジニアにとって、この改訂は何を意味するのでしょうか。それは、機種固有のマクロが散乱し、ビルドフラグの変更で破綻し、長文推論時のメモリ断片化で突然プロセスがクラッシュした過渡期の完全な終焉を指します。

過去半年間、実運用環境でマルチスロットの並行処理サーバを運用する中で、最も警戒すべきは不意に投下される長文リクエストでした。モニタリング上は空き VRAM が 2 から 3GB 程度見えていても、並行スロットの拡張時にアロケータが失敗し、デーモンが突然落ちる事態が多発していました。深夜の障害対応に追われる現場の苦悩は耐え難いものです。今回 v1.0.0 の公開を受け、我々は即座にソースコードから再ビルドを実施し、Linux および macOS 双方の検証機でアーキテクチャの変更点とスループットの物理的限界を洗い出しました。

## 1. 単一プロトタイプからモジュール化テンソル計算エンジンへ

2023 年 3 月の草創期、llama.cpp は main.cpp と少数のヘッダーのみで構築されていました。モデルの重みをメモリマッピングし、MacBook 上で AVX2 命令を用いた行列乗算を手書き実行することで、Python や PyTorch に依存しない純粋な推論環境を切り拓いたのです。

しかし、その簡潔さは多種多様なハードウェアへの対応という壁に突き当たりました。NVIDIA CUDA への対応ではカーネル内部に条件分岐マクロが詰め込まれ、Apple Metal では Objective-C++ による糊付けレイヤーが重なり、続いて Vulkan、SYCL、OpenCL、ROCm、各社 NPU の要求が殺到しました。2025 年半ばの段階で内部コードを開くと、各ハードウェアの専用ロジックが錯綜し、基本演算をわずかに修正しただけで特定バックエンドのビルドが破損する深刻な連鎖リスクを抱えていました。

v1.0.0 の本質的な前進は、こうした複雑な依存関係を明快なモジュール階層へ再編した点にあります：

```
+-------------------------------------------------------------+
|                 アプリケーションとサービス層                 |
|    llama-cli  |  llama-server  |  llama-bench  | 各言語結合 |
+-------------------------------------------------------------+
                              |
+-------------------------------------------------------------+
|                 Llama コアエンジン [llama.cpp]              |
|    モデル構造定義 | KV キャッシュ管理 | 分割 | 連続バッチ   |
+-------------------------------------------------------------+
                              |
+-------------------------------------------------------------+
|                 GGML 計算グラフ制御層 [ggml-sched]           |
|    静的グラフ解析 | メモリ設計 [ggml-alloc] | 異種分散実行  |
+-------------------------------------------------------------+
                              |
+-------------------------------------------------------------+
|                 GGML 統合バックエンド層 [ggml-backend]      |
|    ggml-cpu  |  ggml-cuda  |  ggml-metal  |  ggml-vulkan    |
+-------------------------------------------------------------+
```

最下層の `ggml-backend` 仕様が確立されたことで、各ハードウェアのドライバは機器検出・メモリ確保・グラフ実行インターフェースの実装に専念できるようになりました。演算子の修正が他機種を巻き込んで自壊する危険性は、ハードウェア抽象化の境界によって封じ込められました。

## 2. GGML 静的グラフ設計と VRAM 断片化の抑止

ローカル推論をダウンさせる真の要因は何でしょうか。計算力の不足は単に処理速度を落とすだけです。実運用ログにおいて致命傷となるのは、ヒープメモリの断片化に伴う予期せぬ強制終了です。

初期の GGML にも内部メモリプールは存在していましたが、可変長コンテキストに対する大域的な事前設計が欠如していました。数万文字の技術ドキュメントが入力され前方向計算グラフが展開されるたび、一時テンソル領域が頻繁に確保・解放を繰り返します。数時間の連続稼働を経て物理 VRAM は細切れの領域へと寸断され、わずか数百メガバイトの要求であっても CUDA アウトオブメモリエラーを招いてプロセスが停止していました。

v1.0.0 は成熟した `ggml-alloc` メモリ設計器とスロットスケジューラの連動により、この課題を根本から抑制します：

1. **トポロジ事前コンパイル**：推論実行に先立ち、全計算グラフを静的走査して全出力テンソルの寿命を厳密に算出します。
2. **物理メモリ領域の再利用**：テンソル A の寿命がテンソル B の終了前に尽きる場合、テンソル C はテンソル A が占有していた同一バッファを直ちに流用し、OS や GPU ドライバへの再要求を回避します。
3. **完全固定された作業領域**：読み取り専用のモデル重み領域と静的 KV キャッシュ領域を除き、全一時メモリは事前確保された固定長の Scratch Buffer 内に収束します。

この設計がもたらす効果は劇的です。モデルロード完了の瞬間に使用メモリの上限が確定し、長時間の連続会話を経てもメモリ消費グラフは完全な水平線を維持します。

## 3. 実機性能比較：RTX 4090 対 M3 Max

設計の美しさは、現場の実測スループットによって評価されなければなりません。我々は二種類の代表的ハイエンド機材を用意し、v1.0.0 の実力値を計測しました。

### 検証環境と機材構成

テスト対象には、オープンソース界隈で注目を集める `Qwen2.5-Coder-32B-Instruct` の `Q4_K_M` 量子化モデルを採用しました。GGUF ファイルサイズは約 19.85 GB です。

機材仕様：
- **検証機 A**：Linux ワークステーション、AMD Ryzen 9 7950X、NVIDIA GeForce RTX 4090 24GB、ドライバ 560.35.03、CUDA 12.8、Ubuntu 24.04 LTS。
- **検証機 B**：Apple MacBook Pro、M3 Max [16コア CPU / 40コア GPU]、128GB ユニファイドメモリ、帯域公称 400 GB/s、macOS Sequoia 15.1。

### KV キャッシュ消費の物理計算式

ベンチマークに先立ち、メモリ消費の数学的基礎を確認する必要があります。19.85 GB の重みファイルを 24GB のグラフィックカードに載せれば、残る 4.15 GB で余裕を持って長文を処理できるという推測は成立しません。

KV キャッシュの必要容量を算出する数式は以下の通りです：

$$VRAM_{\text{KV}} = 2 \times L \times N_{\text{kv}} \times D_{\text{head}} \times B_{\text{dtype}} \times S_{\text{ctx}}$$

Qwen 2.5 32B のアーキテクチャ定数は次の通りです：
- レイヤー数 $L = 64$
- Key-Value ヘッド数 $N_{\text{kv}} = 8$ [Grouped-Query Attention GQA 採用]
- 単一ヘッド次元 $D_{\text{head}} = 128$
- 半精度浮動小数点のバイト幅 $B_{\text{dtype}} = 2$ [fp16]

代入により、1トークンあたりに必要なキャッシュ容量が求まります：

$$2 \times 64 \times 8 \times 128 \times 2 = 262,144 \text{ バイト} = 0.25 \text{ MB / トークン}$$

実用コンテキスト長における消費量：
- $8,192$ トークン：$2.0\text{ GB}$。安定動作の許容範囲に収まります。
- $16,384$ トークン：$4.0\text{ GB}$。空き容量が逼迫します。
- $32,768$ トークン：$8.0\text{ GB}$。単一カードのメモリ限界を超過します。

計算結果は厳格です。RTX 4090 では重み 19.85 GB に 32k コンテキストの 8.0 GB が加わると計 27.85 GB となり、24GB 境界を突破してクラッシュします。8k コンテキストに制限した場合のみ、重みとキャッシュの合計が 21.85 GB となり、作業バッファを含めて 24GB の枠内に収まります。一方、128GB ユニファイドメモリを積む M3 Max では容量面の制約は生じません。

### 実測デコードおよびプリフィル速度

各環境において `llama-bench` を用いて 3 回の反復測定を行い、測定誤差 2.5% 以内の中央値を抽出しました：

| 検証プラットフォーム | 構成および実行モード | プロンプト処理速度 [Prefill] | 自帰帰デコード速度 [Generation] | 実際の VRAM 占有量 |
| :--- | :--- | :--- | :--- | :--- |
| **RTX 4090 24GB** [全層 GPU オフロード 64/64] | 8k 長、Flash Attention 有効 | 682.4 tokens/s | 42.1 tokens/s | 22.45 GB |
| **RTX 4090 24GB** [全層 GPU オフロード 64/64] | 8k 長、Flash Attention 無効 | 412.0 tokens/s | 40.8 tokens/s | 22.88 GB |
| **M3 Max 128GB** [Metal ユニファイドメモリ] | 8k 長、Flash Attention 有効 | 296.5 tokens/s | 18.5 tokens/s | 22.20 GB |
| **M3 Max 128GB** [Metal ユニファイドメモリ] | 32k 満杯、Flash Attention 有効 | 288.0 tokens/s | 17.8 tokens/s | 28.30 GB |

なぜ RTX 4090 は秒間 42 トークンに達し、M3 Max は秒間 18 トークンに留まるのでしょうか。ここにはメモリ帯域という物理の壁が存在します。

自帰帰デコード段階では、新しいトークンを 1 個生成するたびに 19.85 GB の全重みパラメータをメモリから順次読み出す必要があります。したがって、生成速度の上限値はバスの物理帯域幅に拘束されます：

$$\text{理論デコード上限} \approx \frac{\text{物理メモリ帯域 [GB/s]}}{\text{モデルパラメータサイズ [GB]}}$$

- RTX 4090 の GDDR6X 帯域は 1008 GB/s であり、理論上限は $1008 / 19.85 \approx 50.78\text{ tokens/s}$ です。実測 42.1 tokens/s は理論限界の 82.9% に達し、CUDA コアの密度の高い駆動を示しています。
- M3 Max の帯域は 400 GB/s であり、理論上限は $400 / 19.85 \approx 20.15\text{ tokens/s}$ です。実測 18.5 tokens/s は理論限界の 91.8% を達成しており、Metal の効率性は極めて高い水準です。

デコード処理中、GPU コアの大半はメモリ転送の完了待ち状態となります。投機的サンプリングを使用しない前提において、民生用単一カードで 32B モデルを秒間 100 トークン以上で回すという主張は物理法則に反します。

## 4. ビルド設定の罠と継続的バッチ処理の本番展開

v1.0.0 のビルドに際し、過去の習慣に起因する設定トラブルに直面しました。

### CMake オプション廃止の落とし穴

過去の多くの技術資料では、`-DLLAMA_CUBLAS=ON` または `-DLLAMA_CUDA=ON` を付与してビルドするのが通例でした。しかし v1.0.0 では全バックエンドが GGML 配下に統合されたため、従来の `LLAMA_` プレフィックス付きオプションは一掃されています。

旧来のコマンドを実行した場合：

```bash
# 誤った指定：廃止パラメータはエラーを出さず静かに無視されます
cmake -B build -DLLAMA_CUDA=ON
cmake --build build --config Release -j 16
```

バイナリのビルド自体は正常終了しますが、実行時に GPU ファンは回転せず、CPU 負荷が 1600% まで跳ね上がり、生成速度は秒間 1.6 トークンへ急落します。`CMakeCache.txt` を調査した結果、旧フラグが無効なカスタム変数として破棄され、純粋な CPU ビルドへ縮退していたことが判明しました。

正式な現行ビルド指定では、新しいバックエンド接頭辞を使用する必要があります：

```bash
# 正しい指定：CUDA 12 および Ada Lovelace アーキテクチャを明示
cmake -B build \
    -DGGML_CUDA=ON \
    -DCMAKE_CUDA_ARCHITECTURES=89 \
    -DGGML_CUDA_F16=ON

cmake --build build --config Release -j 16
```

macOS 環境では CMake が Metal を自動検知します：

```bash
# macOS での Metal アクセラレーション有効化
cmake -B build -DGGML_METAL=ON
cmake --build build --config Release -j $(sysctl -n hw.logicalcpu)
```

### llama-server 継続的バッチ処理の実戦投入

同梱の HTTP サーバ `llama-server` は、軽量な本番用途において十分な実用性を備えています。Slot 単位のスケジューリングに基づく継続的バッチ処理をネイティブ実装しており、先行リクエストの完了を待たずに複数接続を動的に処理可能です。

推奨される本番起動スクリプト：

```bash
./build/bin/llama-server \
    -m ./models/qwen2.5-coder-32b-instruct-q4_k_m.gguf \
    --host 0.0.0.0 \
    --port 8080 \
    -ngl 64 \
    -c 16384 \
    -np 4 \
    --flash-attn \
    --cont-batching \
    -ctk q8_0 \
    -ctv q8_0
```

主要オプション解説：
- `-ngl 64`：全 64 層を完全に GPU VRAM へ転送。
- `-c 16384`：全体で 16k トークン分のコンテキストプールを確保。
- `-np 4`：4 個の独立スロットを展開し、4 並行の非同期リクエストを待機なしで処理。
- `--flash-attn`：Flash Attention 演算を強制し、計算中の一時メモリを圧縮。
- `-ctk q8_0 -ctv q8_0`：KV キャッシュを 8 ビット量子化して保持し、メモリ消費を半減させて並行展開時の安全マージンを確保。

## 5. 現場導入における物理的制約と選定基準

v1.0.0 の登場により、あらゆる環境で 30B 級のモデルが快適に動くかのような過度の期待も見られます。しかし実務における機材選定の基準は明白です：

1. **単一 24GB VRAM は 32B モデルの実用下限**：コード記述の論理精度を維持するには `Q4_K_M` が最低限の防衛ラインです。VRAM が不足してメインメモリへ逃がした場合、秒間 3 から 5 トークンまで失速し、対話的補完ツールとしては破綻します。
2. **MacBook のメモリ容量と帯域幅の兼ね合い**：64GB や 128GB を備えた Mac は 32k コンテキストや 70B モデルを悠々とロードできますが、秒間 18 トークンの速度上限から、チーム共用ゲートウェイではなく個人用のアナリスト端末としての運用が適しています。
3. **KV キャッシュ量子化は並行運用の必須要件**：2 並行を超えるマルチスロット運用では、`-ctk q8_0 -ctv q8_0` の適用がメモリ枯渇を防ぐ必須手腕です。我々のストレステストにおいて、コード検証セットにおける Perplexity 低下は 0.8% 未満に留まり、実用許容範囲内でした。

モデルファイル容量だけで判断せず、まず帯域幅を算出してください。トークン 1 個の生成ごとに 19.85 GB の重みを走査する以上、RTX 4090 の 1008 GB/s、M3 Max の 400 GB/s という数値が理論上限を確定させています。投機的デコードを用いない限り、その速度を超えることは物理的に不可能です。ローカル環境が安定稼働に耐えうるかどうかは、精神論ではなくこの除算の結果が物語っています。
