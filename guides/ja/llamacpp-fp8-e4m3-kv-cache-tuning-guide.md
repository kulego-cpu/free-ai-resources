# 8GB VRAMで32k文脈をOOMなしで完走させる：llama.cpp ネイティブ FP8 KV キャッシュ実践チューニング

深夜2時17分、ターミナルが突然落ちました。

通常のエラー表示ではなく、ウィンドウ全体が暗転し、カーソルが消える間もありませんでした。

2秒ほど呆然とした後、慌てて `nvidia-smi` を確認しました。

プロセスは既に消失しており、VRAM使用率のグラフは垂直にゼロへと急降下していました。

当時動かしていたのは Qwen2.5-7B-Instruct、Q4_K_M 量子化、モデルサイズ 4.65GB です。

搭載GPUはデスクトップ用の RTX 4060、VRAMはちょうど 8GB。

2万トークン程度のアーキテクチャ設計書なら余裕で収まると思い込んでいました。

その見通しはあまりにも甘かったのです。

ローカルLLMを動かす際、多くの人はモデルの重みが 4-bit か 8-bit かにばかり注目します。

モデルがVRAMに収まりさえすれば、すべて問題ないと思われがちです。

しかし、長文ドキュメントの精読やマルチターン検索を実行した瞬間、重み以上のメモリを貪り食う真の刺客が姿を現します。

それがキー・バリュー・キャッシュ――KV Cache です。

幸いなことに、llama.cpp のメインブランチにネイティブ FP8 E4M3 キャッシュ機能がマージされました。

これは本当に 8GB GPU を長文クラッシュの淵から救い出せるのでしょうか。

コンパイルから起動引数、サンプリング温度の調整まで、丸一日かけて数十回のベンチマークを実施しました。

物理VRAMの計算根拠、実際のクラッシュログ、そしてトラブルシューティングの手順をすべて記録します。

## 1. 物理VRAMの算出：なぜ2万トークンで8GBメモリが吹き飛ぶのか

長文処理で OOM に直面した際、多くの人が疑問に感じます。

数万文字のテキストを入力しただけで、なぜ数ギガバイトものVRAMが突如として消滅するのか。

これには厳密な手計算が必要です。

モデルが自己回帰推論を行う際、過去の全トークンに対応するキーベクトルとバリューベクトルをVRAM上に保持し続ける必要があります。

もし破棄してしまうとどうなるか。

新しいトークンを1つ生成するたびに、過去の全テキストに対してアテンションを最初から再計算しなければならなくなります。

この重複計算を防ぐためにメモリへ常駐させる行列こそが KV Cache です。

Qwen2.5-7B の設計構成を確認してみましょう。

総レイヤー数：28 層；

アテンション構造：GQA 採用、KV ヘッド数は 4 個；

各ヘッドの隠れ層次元：128。

デフォルト状態の llama.cpp は、キャッシュを標準的な FP16 精度で保持するため、1数値あたり 2 バイトを消費します。

1トークンが全28層を通過する際に確保されるメモリ量を計算します：

$$2 \times 28 \text{ 層} \times 4 \text{ ヘッド} \times 128 \text{ 次元} \times 2 \text{ バイト} = 57,344 \text{ バイト}$$

つまり、わずか 1 トークンが投入されただけで、約 56 KB のVRAMが固定確保されます。

数千トークンの会話では問題になりません。

しかし、コンテキスト長が 32,768 トークンに達した場合はどうなるでしょうか：

$$32,768 \times 57,344 \text{ バイト} = 1,879,048,192 \text{ バイト} \approx 1,792 \text{ MiB} \approx 1.88 \text{ GB}$$

モデル重みが 4.65GB、キャッシュが 1.88GB、合計で 6.53GB です。

RTX 4060 の物理VRAMは 8,192 MB 存在します。

理論上は 1.6GB の空きがあるはずなのに、なぜ2万トークン強で落ちたのでしょうか。

実際のランタイム消費は、机上の計算よりもはるかに過酷です。

第1の要因、ドライバ基本占有――CUDA コンテキストを初期化するだけで 500MB から 700MB が消費されます。

第2の要因、スクラッチバッファ――行列乗算の中間テンソルを一時展開するためのメモリ領域が不可欠です。

第3の要因、ブロック事前確保――断片化を防ぎ高速な連続処理を維持するため、アロケータが物理ページを前もって大きく確保します。

これらの運用メモリが 1.88GB の純キャッシュに上乗せされた結果、ピーク消費量は 8.4GB を突破します。

8GB という物理上限に直面したドライバには、プロセスを OOM で強制終了させる以外の選択肢が残りません。

<img src="https://img.freeaidog.com/images/blog/llamacpp-fp8-e4m3-kv-cache-tuning-guide.webp" alt="RTX 4060 8GB VRAM 配分比較：32k 文脈におけるネイティブ FP8 E4M3 と標準 FP16 の動作比較" />

ここに FP8 E4M3 フォーマットの決定的な価値があります。

FP8 は1数値あたりわずか 1 バイトしか消費しません。

FP16 と比較して、純粋なデータ保持容量を半分に圧縮します。

本来 1,792 MiB を要していた 32k キャッシュは、約 896 MiB へと削減されます。

節約された約 900 MiB こそが、ドライバ負荷や計算バッファを吸収するための防波堤となります。

## 2. トラブル検証：引数変更のみでカーネルを有効化しなかった場合の4倍速度低下

まず、ビルド環境とバージョンを明示します：

```text
llama.cpp b4821 [git rev-parse HEAD で確認]
CUDA 12.6 / ドライバ 560.35.03 / Ubuntu 24.04 LTS
```

Linux 上での CMake ビルドにおける注意点です。

デフォルトの生成器は Makefile または Ninja であり、単一構成モードで動作します。`cmake --build build --config Release` と実行しても `--config` は完全に無視されます。

設定段階でビルドタイプを渡すのが確実です：

```bash
# 正しい CMake ビルド手順
cmake -B build -DGGML_CUDA=ON -DCMAKE_BUILD_TYPE=Release
cmake --build build -j$(nproc)
```

ビルドは問題なく完了しました。

フォーラムの記述に従い、キャッシュ型を指定してサーバを起動しました：

```bash
# 初回に試した誤った起動コマンド
./build/bin/llama-server \
  -m models/qwen2.5-7b-instruct-q4_k_m.gguf \
  -c 32768 \
  -ctk f8_e4m3 \
  -ctv f8_e4m3 \
  -ngl 99 \
  --port 8080
```

サーバは起動し、初期VRAM消費も下がっていました。

起動ログの以下の行を必ず確認してください：

```text
llama_kv_cache_init:      CUDA0 KV buffer size =   960.00 MiB (f8_e4m3)
```

**もし 1836 MiB 以上の数字が表示されている場合、引数が反映されず FP16 で動いています。** ここを確認せずに進めると、その後の計測値はすべて意味を失います。

2万トークンの文書を投入しました。

しかし、プログレスバーがほとんど進みません。

普段なら20秒程度で終わるプロンプト処理が、1分経っても2割程度しか進みません。

なぜこれほど遅いのか。

別ターミナルで `nvidia-smi dmon` を確認しました。

GPU コア使用率が 20% から 95% の間で激しく乱高下し、メモリバス帯域が全く使われていませんでした。

実測の処理速度は 58 token/s まで急落していました。

速度が4分の1に落ちてしまっては、いくらメモリが浮いても実用になりません。

詳細ログを有効にして再実行しました：

```text
ggml_cuda_flash_attn: flash attention disabled or unsupported for current tensor types, falling back to legacy batched gemm...
ggml_cuda_op_mul_mat: non-aligned memory striding detected, dequantizing fp8 on the fly to fp16 registers
```

原因は一目瞭然でした。

FlashAttention を明示的に有効にしていないため、専用の融合カーネルが起動していなかったのです。

GPU は計算の直前に、VRAM上の FP8 データをその場で FP16 レジスタへと逆量子化し、レガシーな行列演算を実行していました。

Tensor Core のハードウェア恩恵を得るどころか、頻繁な型変換と非アライメントメモリアクセスによって演算器が窒息していました。

FlashAttention の併用は必須です。

修正した起動引数がこちらです：

```bash
# 検証済みの正しい起動コマンド
./build/bin/llama-server \
  -m models/qwen2.5-7b-instruct-q4_k_m.gguf \
  -c 32768 \
  -ctk f8_e4m3 \
  -ctv f8_e4m3 \
  --flash-attn \
  -ngl 99 \
  --parallel 1 \
  --port 8080
```

起動ログが期待通りの出力を返しました：

```text
llama_new_context_with_model: n_ctx = 32768, n_batch = 2048, n_ubatch = 512, flash_attn = 1
llama_kv_cache_init:      CUDA0 KV buffer size =   960.00 MiB (f8_e4m3)
```

再度テストを実施しました。

2万トークンのプロンプト処理は約82秒で完了し、処理速度は 243.9 token/s で安定しました。

ピークVRAM消費は 7.11GB で停止しました。

8GB の物理上限に対して、約 900MB の安全マージンが確保されました。

## 3. 精度検証：JSONキーのクォート欠落と真の原因

メモリが安定し、速度も回復しました。これで万全でしょうか。

そう単純ではありませんでした。

その日の午後、法務契約書から構造化データを抽出するタスクを検証しました。

数千トークンの短い文書では完璧な JSON を出力していました。

しかし、会話が15往復を超え、文脈長が 28,000 トークンを超えたところで出力が乱れ始めました：

```json
{
  "service_level_agreement": {
    "uptime_guarantee": 99.9,
    latency_threshold_ms: 250,
    "penalty_clause: "applicable within 30 days"
  }
}
```

`latency_threshold_ms` の開始クォートが欠落し、`penalty_clause` では終了クォートが消滅しています。

後続のバリデータが即座にエラーを出して停止しました。

FP8 量子化によって精度が破壊されたのでしょうか。

厳密な比較実験を行いました。

同一の 28k 文脈に対し、キャッシュを `-ctk f16` に戻し、温度 0.8 で10回実行しました。結果、3回クォート落ちが発生しました。

続いて `f8_e4m3` で同様に温度 0.8 で10回実行したところ、2回から3回クォート落ちが発生しました。

両者の失敗頻度はほぼ同等でした。

これは何を意味しているのか。

**真の変数はサンプリング温度でした。**

28,000 トークン規模の末尾文脈は、確率分布の乱れが生じやすい領域です。温度 0.8 のままでは確率の低い記号の欠落を許容してしまいます。

FP8 E4M3 は指数部4ビット、仮数部3ビットで構成され、表現できる最大値は 448 に制限されています。

長距離計算での微小な丸め誤差は、不安定な確率分布をわずかに揺らす増幅器に過ぎず、根本原因ではありませんでした。

API パラメータを修正しました：

```bash
# 温度を抑えた高精度抽出リクエスト例
curl http://127.0.0.1:8080/v1/chat/completions \
  -H "Content-Type: application/json" \
  -d '{
    "model": "qwen2.5-7b-instruct",
    "messages": [
      {"role": "system", "content": "あなたは厳密なデータ抽出エンジンです。規格に準拠した有効なJSONのみを出力してください。"},
      {"role": "user", "content": "以下の文書から技術仕様一覧を抽出してください：\n\n[本文省略...]"}
    ],
    "temperature": 0.15,
    "top_p": 0.95
  }'
```

温度を 0.15、`top_p` を 0.95 に固定しました。

その後、28k 規模の抽出を20回連続で実行しましたが、クォート落ちは0回でした。

構文の崩れは完全に解消されました。

## 4. 実機ベンチマーク比較：FP16、Q8_0、FP8 E4M3 の実測値一覧

同様の環境を持つ方々の参考として、実測結果をまとめました。

テスト環境：

OS：Ubuntu 24.04 LTS、Linux 6.8 カーネル；

ハードウェア：Intel Core i5-13400F、32GB DDR5 5600MHz；

GPU：デスクトップ版 NVIDIA GeForce RTX 4060 8GB、ドライバ 560.35.03；

対象モデル：Qwen2.5-7B-Instruct-Q4_K_M.gguf。

| KV キャッシュ戦略 | 32k ピークVRAM | プロンプト処理速度 | 生成速度 | 32k テスト状態 | 動作特性と挙動 |
| :--- | :--- | :--- | :--- | :--- | :--- |
| **標準 FP16 ［デフォルト］** | 8.42 GB 超過 | -- | -- | ❌ **OOM クラッシュ** | 24,500トークン付近でメモリ枯渇、強制終了 |
| **量子化 Q8_0** | 7.65 GB | 186.2 token/s | 36.8 token/s | ⚠️ **ギリギリ通過** | 同等容量だがFA融合がないため中間バッファが大きい |
| **ネイティブ FP8 E4M3 + FA** | 7.11 GB | 243.9 token/s | 40.3 token/s | ✅ **極めて安定** | 空き約900MB、Tensor Core ハードウェア加速 |

Q8_0 と FP8 が共に1バイトデータであるにもかかわらず、VRAMピークに 0.54GB の差が生じる理由は何でしょうか。

その差は FlashAttention の有無に起因します。

ネイティブ FP8 と FlashAttention の組み合わせは中間アテンション行列の展開領域を削減しますが、Q8_0 は依然として大きな作業バッファを要求します。

結論は明快です。

8GB GPU において、従来の FP16 で 32k 文脈を扱うのは不可能です。

Q8_0 は通過こそしますがメモリの余裕がなく、バックグラウンドの別プロセスでクラッシュするリスクを抱えます。

FP8 E4M3 と FlashAttention の組み合わせのみが、エントリーカードにおける実用性を確保します。

## 5. 実践的な推奨事項とハードウェア境界

丸一日の検証を経て得られた実用的な指針は以下の3点です：

**旧世代GPUでは無理に有効化しないこと。**

FP8 E4M3 の真価は Ada Lovelace SM 8.9 以降のアーキテクチャでのみ発揮されます。

RTX 3060 や 3070 などの Ampere 世代は、ハードウェアレベルで FP8 テンソル命令を持っていません。

旧世代で無理に指定すると逆量子化オーバーヘッドでかえって低速化します。その場合は Q8_0 を使用してください。

**FlashAttention は必ずセットで起動すること。**

`-ctk f8_e4m3` を指定しながら `--flash-attn` を忘れると、速度は 58 token/s まで落ち込みます。これらは必ずペアで記述してください。

**長文抽出では温度を 0.2 以下に抑えること。**

長大コンテキストの末尾における丸め誤差は、確定的なサンプリングで抑え込む必要があります。精度が最優先される場面では温度を下げてください。

最後に一つ補足します。

本稿の計測値はデスクトップ版 RTX 4060 によるものです。

ノートPC版や外付けGPUボックスでは熱設計や電力制限が異なるため、数値の差異が生じるのは正常です。絶対的なスコアではなく、設計上の参考値としてお役立てください。

お使いの 8GB GPU は、32k 文テキストを受け入れる準備が整いましたか？
