去年の冬、私は 2 ノード 8 基の RTX 4090 を搭載した推論クラスタの運用を引き継ぎました。

Grafana の監視ダッシュボードには見事なグラフが並んでいました：VRAM 使用率は 7 割、GPU 使用率は常時 90% 前後を維持。

当時の私は、8 枚の GPU を限界まで絞り尽くせていると鼻高々でした。

フロントエンドの開発チームからチャットでメンションが殺到するまでは。

カーソルが 3 行目で完全に止まって動かない。これが最初の報告でした。

私はてっきり WebSocket の切断だと思い、HAR ログを取得させました。

しかしパケットを解析しても、コネクションは正常に維持されており、パケットロスもゼロ。単に最初のトークンがいつまで経っても返ってこない状態でした。

あるエンジニアがストップウォッチで計ったところ、Enter キーを押してから最初の文字が出るまでの待ち時間で、給湯室に行ってインスタントコーヒーを淹れることができたといいます。

ネットワーク機器の故障でしょうか？私は 2 日間かけて社内回線を疑いました。

パケットキャプチャ、NIC の設定見直し、光モジュールの交換……すべて徒労に終わりました。

3 日目の深夜、ようやく本当のボトルネックの正体に辿り着きました。

## ダッシュボードの錯覚：平均 480ms の裏で p99 が 2 秒に激突

ハードウェアの真の限界を見極めるため、私は Locust を使って負荷試験を組みました。

虚飾のない実戦構成です。

64 個の非同期コルーチンを立ち上げ、HumanEval のコード断片を並行して流し込み、出力上限を 512 トークンに固定して 10 分間の定常状態を計測しました。

起動パラメータでは、並行上限を最大まで引き上げました：

```bash
# 最大並行バッチで vLLM を起動
vllm serve Qwen/Qwen2.5-Coder-32B-Instruct \
  --tensor-parallel-size 4 \
  --max-num-seqs 128 \
  --max-model-len 16384 \
  --gpu-memory-utilization 0.92
```

表面的な数値は極めて魅力的でした：`max_num_seqs` を 4 から 128 に引き上げたことで、クラスタ全体のスループットは 320 tok/s から一気に 1280 tok/s 超へと跳ね上がりました。

実に 4 倍のトークン生成量です。これを見て最適化成功と思わない人がいるでしょうか？

全体のメトリクスを眺める限り、どこにも問題は見当たりません。

しかし私は致命的な事実を見落としていました：画面に描画されていたのは、初回トークン生成時間 [TTFT] の平均値だったのです。

平均値は 480ms で、一見まったく問題ありません。

ところが Prometheus からパーセンタイル値を取り出した瞬間、背筋が凍りつきました：p90 は 1.2 秒、p99 に至っては 1.95 秒まで跳ね上がっていたのです。

コンテナの標準出力ログを開くと、同じ警告が画面を埋め尽くしていました：

```text
WARNING [vllm.core.scheduler] Sequence group 1422 is preempted by PreemptionMode.RECOMPUTE.
```

警告ログが滝のように流れていました。

24GB 搭載の RTX 4090 が 4 基、ノード全体の物理 VRAM は 96GB です。

32B クラスの bfloat16 ネイティブモデルをロードするだけで、重みだけで約 64GB が占有されます。

KV キャッシュに割り当て可能な残存容量はせいぜい 24GB 程度であり、文脈にして 8 万から 9 万トークン分しか収まりません。

並行数が 128 に達すると、各セッションの平均履歴が 600 から 700 トークンを超えた途端にキャッシュが枯渇します。

メモリプールが完全に空になりました。

CUDA OOM によるプロセス強制終了を防ぐため、vLLM のスケジューラはやむなく再計算プリエンプションを発動します。

後続セッションのキャッシュを強制破棄し、先行リクエストが完了した後に最初から Prefill をやり直すのです。

2 秒間待たされていたフロントエンドのエンジニアは、まさにセッションがメモリから蹴り出された瞬間に当たっていたわけです。

こんな激しいカクつきに耐えられる人がいるでしょうか？

その夜、私はローリングアップデートで `max_num_seqs` を 24 に戻し、負荷試験をやり直しました。p99 は 340ms に落ち着きました。

チャットでの苦情はピタリと止まりました。

128 並行でキャッシュ破棄を起こさずスループットを維持する設定値は、現在の構成では未だに見出せていません。備忘録としてここに残しておきます。

## 4090 に NVLink はない：PCIe 接続下における All-Reduce 通信の壁

並列化戦略を調整する際にも、私は浅はかな思い込みをしていました。

1 枚で遅いなら、複数枚に計算を分散させれば単純に速くなるはずではないか？

テンソル並列 [TP] が遅延を極限まで縮めるという解説はネット上に溢れており、数百ギガバイトの帯域を持つ NVLink 接続を前提にした記述も散見されます。

しかしコンシューマ向け GPU にその前提は通用しません。

Ada Lovelace 世代以降、Nvidia は 40 シリーズのゲーミングカードから物理的な NVLink 端子を完全に撤廃しました。

この世代のカードに金手指はありません。

検証機でトポロジ確認コマンドを叩きます：

```bash
nvidia-smi topo -m
```

表示されたマトリクスはすべて `SYS` で埋め尽くされていました。

カード間の通信は直接接続できず、CPU ルートコンプレックス、マザーボードの PCIe 4.0 x16 スロット、そしてメインメモリを経由して迂回します。

双方向の理論帯域はわずか 64GB/s です。

さらに Linux の標準ドライバ環境下では、ハードウェア P2P が無効化されているため、通信はいったんホストメモリへと退避します。

当時、私は 32B モデルの応答性を高めようと、単一ノード 4 枚のカードで無理やり TP=4 を適用しました。

その結果、1 トークンあたりの生成時間 [ITL] は、元の 22ms から 58ms へと悪化しました。

演算コアは 4 倍になったのに、文字の出力が 2 倍以上遅くなったのです。私は頭を抱えました。

Nsight Systems でカーネルの実行プロファイルを追跡したところ、原因は一目瞭然でした。

Transformer の各アテンション層とフィードフォワード層の計算が終わるたび、4 つの GPU プロセス間で `all_reduce` の集合通信同期が発生します。

計算自体は 1.2ms で終わっているのに、PCIe バス上でのデータ同期待ちに 3.8ms も浪費していたのです。

GPU コアはバスの完了をただ虚しく待つだけでした。細いバスに過密通信を流し込めば、詰まるのは自明です。

高速ファブリックを持たないコンシューマ環境で高い並列度を組むのは、貧弱な道路に巨大な交通量を押し込むようなものです。

その後、私はアーキテクチャを改め、2 基ずつのペアで TP=2 を組み、ペア間は HTTP のリクエスト単位データ並列で振り分けました。1 文字あたりの生成時間は即座に 26ms へと回復しました。

4090 を扱うエンジニアは、スーパーコンピュータ向けのチューニング数値を真に受けてはいけません。マザーボードのスロット帯域を冷徹に計算するべきです。

## 量子化の断崖絶壁：インデント崩壊による HumanEval 28 ポイント急落

VRAM が逼迫した際、最初に試される手段は量子化です。

多くの記事は量子化を無傷の魔法のように語ります：VRAM が半減し、速度が倍増し、ベンチマークスコアの低下はごくわずかだと。

そんな甘い話を鵜呑みにしてよいのでしょうか？

厳格なコーディング現場では、まったく異なる現実が待っています。

同一の検証環境下において、Qwen2.5-Coder-32B を 3 種類の量子化フォーマットで HumanEval pass@1 ベンチマークにかけました：

```text
HumanEval 50 題自動コード生成ベンチマーク [commit: 4e7b8a1]
- FP16 ネイティブ基準値：82.0%
- FP8 動的量子化：80.4% [わずか 1.6% の微減]
- 従来型 INT4 形式：54.2% [27.8% の壊滅的急落]
```

FP16 から FP8 への移行は、静的重みであれ `--kv-cache-dtype fp8` によるキャッシュ圧縮であれ、驚くほど安定していました。

VRAM 消費は半分に削減されました。

KV キャッシュの収容枠は 2 倍に拡大しました。

メモリ帯域の負荷が軽減されたことで、トークン出力速度は約 8 割向上しました。

しかし FP8 の一線を越えて汎用の INT4 重みに踏み込んだ瞬間、コード生成ロジックは断崖絶壁を転がり落ちます。

通過率 54.2% ということは、2 問に 1 問が確実に落ちる計算です。

節約できた 6GB のメモリに、それほどの価値があったでしょうか？

私は失敗した 20 件のケースをすべて洗い出しました。

実に 17 件が深いネストのインデントずれで死亡していました。

ループや条件分岐が 3 階層を超えると、INT4 モデルはスペース 4 個を 6 個に誤認したり、多重 try-except ブロックのスコープを勝手に早期クローズしたりするのです。

残る 3 件はクォートを含む複雑な f-string 内で発生し、モデルは同一コード行の無限リピートに陥りました。

このようなコードは、CI の flake8 静的解析すらパスできません。単体テストにかける以前の問題です。

わずか 6GB の VRAM を削った代償は、アシスタント機能自体の完全な破綻でした。

社内文書の要約や検索リランキングが目的なら、INT4 によるコスト削減は十分に合理的です。

しかしプログラマ向けのリアルタイム支援において、FP8 は死守すべき絶対防衛ラインです。

NVFP4 や MXFP4 のようなブロック単位独立スケーリングを備えた新世代形式で蒸留再学習されていない限り、生の INT4 で複雑な長文コードを扱うのは危険極まりありません。

## Prefill と Decode の物理分離：長大プロンプトと高頻度生成の同居が破綻する理由

単一ノード内のパラメータ調整がもぐら叩きになるなら、近年業界で叫ばれている P/D 分離は何を解決するのでしょうか？

その物理的本質は明快です：特性のまったく異なる計算フェーズを、物理的に別々のマシンへと隔離することです。

Prefill フェーズは行列積の演算密度に依存する計算律速であり、要求されるのは GPU の Tensor Core 演算能力 TFLOPS です。数千字の文脈が一括投入され、コアを限界まで占有します。

Decode フェーズは高頻度なメモリアクセスに依存する帯域律速であり、要求されるのは毎秒何 GB のデータを転送できるかです。1 文字吐き出すごとに、全パラメータと累積された KV キャッシュをメモリから総浚いします。

この 2 つのタスクを同一の GPU に同居させることが、カーソル停止の真因です。

あるユーザ向けに毎秒 50 トークンで順調に関数を生成している最中、別のユーザから 2 万行の OpenAPI 定義が投げ込まれたとします。

スケジューラは膨大なアテンション計算を行うため、ストリーミング用のコアを即座に明け渡さなければなりません。

進行中のデコード処理は強制的にサスペンドされます。

エンジニアの画面上では、カーソルが唐突に 1 秒半フリーズする現象として現れます。

文字が止まった画面を見せられて、平気でいられるエンジニアがいるでしょうか？

P/D 分離は、クラスタを 2 系統の専用ノード群に物理分割します：

```text
クライアント要求
    │
    ▼
[API 負荷分散ゲートウェイ]
    │
    ├─► [Prefill 専用クラスタ]：高密度演算カード群で長大プロンプトを一気に消化
    │         │
    │         ▼ [RDMA / 高速社内網経由で KV キャッシュ状態を直送]
    └─► [Decode 専用クラスタ]：H100 等の超広帯域メモリマシン [3.35TB/s] で出力に専念
```

Prefill が完了すると、KV キャッシュのパケットが高速ネットワーク経由で Decode クラスタに直接引き渡され、Decode 側は中断されることなく文字を吐き出し続けます。

マルチターンを繰り返すエージェント環境において、この分離設計は p99 の遅延ジッターを 6 割以上削ぎ落とします。

ただし導入コストも相応です：ノード間 KV 転送を司るミドルウェアを自前で運用する必要があり、トラフィックの偏りに備えて機材枠を 2 割以上多めに確保しなければなりません。

メガクラウドが好む手法ですが、相応の規模を前提とします。

数台規模のチームであれば、分散 KV 転送の罠に飛び込むよりも、chunked prefill で突発遅延を抑え込むほうが遥かに現実的です。

## 投機的デコードの実態：コード生成における採択率と温度減衰

最後に、推論効率の天井を真に外側へ押し広げる技術について触れます：投機的デコードです。

日常会話タスクで投機的デコードを試した結果、落胆して機能を切ったエンジニアは少なくありません。

自由入力は発散しやすく、小型の下書きモデルによる予測採択率は 30% 前後で頭打ちになります。

予測を外すたびに主力モデルによる検証とロールバックが走り、時間を節約できないどころか無駄な計算リソースを浪費します。

これでは本末転倒ではないでしょうか？

しかし厳格に規律づけられたコード補全環境では、データの規則性が一変します。

コードには確固たる構文パターンが存在します：クラス宣言、標準ライブラリのインポート、括弧の対応、規則正しいインデント。

同系統の軽量モデル Qwen2.5-Coder-0.5B を下書きヘッドとして 32B 主力モデルと組み合わせた実測値です：

語彙トークナイザの厳密な物理アライメントが不可欠であり、わずかでも不一致があれば予測は全滅します。

サンプリング温度を 0.2 に絞り込んだ低ランダム性環境下では、平均採択長は 3.8 から 4.1 トークンに達しました。

主力モデルが 4 回逐次実行すべきだった前向計算を、検証フェーズの 1 回のバッチ前向処理で一括パスできる計算になります。

3 回分のメモリデータ転送を丸ごとスキップできる恩恵は、本物のハードウェア余力となって還元されます。

しかし油断は禁物です。

投機的デコードには、温度上昇に伴う極めて急峻な減衰曲線が存在します：

温度が 0.2 のときは採択率が 7 割前後に保たれ、体感速度は 2 倍近くに加速します；

しかし開発者がプラグイン側で温度を 0.7 に引き上げて柔軟なコードを書かせようとした瞬間、採択長は 1.6 トークンへと急落します。

さらに厄介なのが、検証時の一時的なメモリ急膨張です。

検証フェーズにおいて、主力モデルは下書きが提示した K 個の候補分岐を並行処理するため、検証バッチサイズが瞬間的に K 倍に膨れ上がります。

この突入負荷は、逼迫した VRAM プールを一瞬で限界まで追い込みます。

基礎的な KV キャッシュ使用率がすでに 90% に迫っている場合、投機的デコードの有効化は高速化をもたらさず、むしろ早期のプリエンプションや OOM クラッシュを誘発します。

高温度の環境下では、下書きヘッドを切ったほうが賢明ではないでしょうか？

現在、私たちのクラスタでは 2 つのノードが稼働しています。

`max_num_seqs` は 24 に固定；重みの FP8 量子化を適用；動的 FP8 KV キャッシュも維持；しかし投機的デコードは一時停止しています。新規エンドポイントの温度がフロント側で 0.75 に設定されており、有効にしてもメモリを無駄食いするだけだからです。

リクエストのサンプリング温度に応じて下書きヘッドを動的に切り替えるプロキシをどう設計するか、最適な構成はまだ模索中です。

社内でコード補全クラスタを運用している方は、先週の p99 モニタリングを一度引き出してみてください。画面の前のエンジニアたちが、本当は何を待たされているのかが見えてくるはずです。
