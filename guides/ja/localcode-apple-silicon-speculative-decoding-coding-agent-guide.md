先月の利用請求書が届き、金額は 460 ドルに達していました。上長は何も言いませんでしたが、自分ですぐに利用内訳を確認しました。

開発者をローカル環境へ向かわせる真の要因は、技術的なこだわりではありません。過去に二度、顧客から届いたリポジトリに厳格な国外持ち出し禁止条項が付いており、数名でセキュリティ規程を調べた結果、最終的に社内ネットワークの極めて遅い旧型サーバーで凌ぐしかありませんでした。正規表現を三箇所直すだけで半日を費やした苦い経験があります。

そのため LocalCode が GitHub に公開された際、すぐにクローンして試しました。確かめたかったのは一点だけです。手元の 16GB 統合メモリを積んだ M3 MacBook で、通信が遮断され、顧客の規程で外部接続が禁じられ、テザリングも使えない状況下において、日常的な開発業務をどこまで完結できるのかという点です。

ローカル環境で自律型コーディングエージェントを動かすには、常に二つの高い障壁がありました。一つ目は推論速度です。通常の量子化モデルは秒間十数トークン程度しか出ず、カーソルが進むのを待つだけで集中力が削がれます。二つ目は長いコンテキストによるメモリ逼迫です。複数モジュールのソースコードを読み込ませると、利用可能メモリは即座に赤色警告を示します。

LocalCode は Apple Silicon の統合メモリに焦点を当てて最適化を行っています。事前コンパイルされた Metal GPU カーネルを組み込み、公式の軽量 Drafter モデルによる推測サンプリングを実行し、既存コードの改修を高速化する Copy Drafting 機能を備えています。

コマンド一つで本当に立ち上がり、外部通信ゼロでどこまで実用に耐えるのか。この 16GB マシンで丸一日テストを行いました。

## ハードウェア構成とメモリ占有の実態

検証環境は 16GB 統合メモリを搭載した M3 MacBook Pro 標準モデル、OS は macOS 15 です。

Astral が開発する uv パッケージマネージャーを利用すれば、導入はコマンド一行で完了します：

```bash
uv pip install localcode
```

導入は手軽ですが、作業を始める前にメモリ配分を把握しておくことが不可欠です。

起動前に `vm_stat` でベースラインを計測したところ、空きページから換算した実質的な利用可能容量は約 4.2 GB でした。つまりモデルや推論バッファに割り当て可能な物理的マージンは 12 GB 未満です。

検証では Qwen2.5-Coder-14B-Instruct-Q4_K_M をメインモデルに採用し、推測層には公式の 1.5B Drafter を組み合わせました。パラメータは攻めた構成を取り、`-ngl 99` で全層を GPU にオフロード、コンテキスト長 `--ctx-size` は 8192 に設定、KV Cache は統合メモリ保護のため標準の fp16 から q8 に落としました。

起動後にアクティビティモニタを確認したところ、有線メモリ領域は一気に 11.2 GB まで跳ね上がりました：

```text
Qwen2.5-Coder 14B メインモデル重み：約 7.1 GB
付属 1.5B 公式 Drafter モデル：約 1.3 GB
8-bit KV Cache 確保領域：約 2.2 GB
エージェント作業領域とコンテキストバッファ：約 0.6 GB
─────────────────────────────────────────────
実行時ピークメモリ合計：約 11.2 GB
```

残り約六百メガバイトという数字は、実質的に何を意味するでしょうか。

構文を確認しようとブラウザのタブを一つ開いた瞬間、メモリプレッシャーは緑色から黄色へと切り替わりました。OS は即座に SSD へのスワップ退避を開始し、`swapouts` は毎秒数百ページの勢いで増加しました。秒間 38 トークンあった生成速度は 19 トークンへ、さらに 11 トークンへと急落しました。

これは余裕がある状態ではなく、メモリ破綻の瀬戸際です。バックグラウンドで動くあらゆる処理が、推論スループットを直接圧迫します。

## 二段階の高速化：Drafter 推測と Copy Drafting

このツールの特徴は、新規コードの生成と既存コードの修正で推測ロジックを切り替えている点にあります。

### 1. 公式 Drafter による前方向推測サンプリング

大規模言語モデルの一般的な生成手法は厳格な自己回帰であり、一文字出力するたびに数百億回の行列乗算を伴うため負荷がかかります。

推測デコードの構造は明快です。軽量な 1.5B モデルが先行して 3 から 5 トークンを盲目的に予測し、後段の 14B メインモデルが一度の順伝播計算で候補群の正誤を一括判定します。的中したトークンは即座に確定され、外れた箇所のみ再計算されます。

新規 API ルーティング作成時の実測値は以下の通りです：

- 14B 単体モデル実行時：平均生成速度 約 21.4 tok/s
- 1.5B Drafter 併用推測時：平均生成速度 約 38.6 tok/s
- 提案トークンの採択率：概ね 58% から 64% で推移

生成速度は約 8 割向上しました。統合メモリアーキテクチャにより PCIe 経由の転送オーバーヘッドが生じないため、モデル間のやり取りに遅延が発生しません。

### 2. コード改修に威力を発揮する Copy Drafting

新規コードの生成が速くなること以上に実用的なのが、既存コードの修正作業です。

実際の現場でゼロからファイルを新規作成する機会は多くありません。日常業務の大半は既存の 500 行のスクリプトに対してメソッドを二つ修正したり、例外処理を追加する作業です。従来のエージェントでは、変更のない数百行のコードも一文字ずつ再出力されるのを待つ必要がありました。

LocalCode の Copy Drafting はブラックボックスではありません。実装フローを確認すると、草稿生成時にローカルディスク上の既存ファイルを末尾コンテキストとして注入し、メモリ上のトークンキャッシュと照合して高速検証を行っています：

```text
既存ファイルキャッシュ
    │
    ▼
[並列候補トークン注入] ───> 変更のない既存コードと合致
    │                               │
    ▼                               ▼
メインモデルの一括検証 ───> 70+ tok/s で高速スキップ
    │
    ▼
ロジック変更箇所に到達 ───> 通常の Drafter 推測に切り替え
```

480 行の Python スクリプト修正テストでは、変更のない宣言文が秒間 70 から 85 トークンという速度で画面上を流れていきました。修正全体の所要時間は従来の 24 秒から 7 秒未満に短縮され、思考を中断させない快適さが得られます。

## 開発現場での課題：三つの実トラブル

正常に動作したからといってトラブルがないわけではありません。実際の現場リポジトリで検証したところ、具体的な三つの問題に直面しました。

### 課題 1：初回起動時の Metal Shader コンパイル停止

導入後に起動コマンドを実行すると、loading metal kernels と表示された直後にターミナルのカーソルが停止しました。

進捗表示はなく、ファンも回転しません。プロセスのデッドロックかインストールミスを疑いました。

数秒待っても反応がなく、Ctrl+C を二度押して強制終了しました。再実行しても同じ場所で止まります。別ターミナルで `top` を実行して確認したところ、`localcode-metal-cc` というプロセスが CPU 単一コアを 98% 占有し、着色器コードの機械語コンパイルを処理中でした。

```bash
# 初回導入後は事前にウォームアップを実行することを推奨
$ time localcode --warmup-only
real    0m23.418s
```

約 23 秒間、ターミナル出力は完全に途絶えていました。事前の知識がないとハングアップと判断しやすい挙動です。コンパイル済みの Metal キャッシュは `~/Library/Caches/localcode/metal/` に保存されるため、二回目の起動は 1.2 秒で完了します。

### 課題 2：深いディレクトリ構造における相対パスの喪失

階層が平坦な単一ディレクトリでは正確でした。しかし複数パッケージで構成されるモノレポに投入した途端、挙動が乱れました。

指示内容：`packages/backend/src/utils/formatter.ts` に対する単体テストの追加。

14B モデルは正確なテストコードを作成しましたが、ファイル書き込みツールを実行する段階で長い相対パスの解釈を誤りました。指定された `tests` ディレクトリではなく、プロジェクトのルート直下に平坦なファイル `src_utils_formatter.test.ts` を作成してしまったのです。

小型オープンモデルは商用最上位モデルに比べて、ツール呼び出し引数の追従性で劣る場面があります。ロジックに問題がなくても保存先が狂う場合があるため、画面の片隅に `git status` を常に表示しておく運用が欠かせません。

### 課題 3：32B モデルにおけるメモリスワップの崩壊

興味本位で Qwen2.5-Coder-32B の 4 ビット版を試してみました。

展開された重みだけで約 19 GB に達し、KV Cache を含めると 16GB の物理メモリは瞬時に飽和しました。macOS はメモリ不足警告を表示し、SSD へのスワップ処理で本体が熱を帯びました。

生成自体は完了したものの、速度は 38 トークンから 2.8 tok/s へと急落しました。キーボード入力の表示すら遅延し、対話的な開発は不可能です。16GB 搭載機において 14B クラスは物理的な限界線です。

## 3 つの課題に対するベンチマーク比較

同一マシンにおいて、同一プロジェクトの 3 つの課題に対する測定結果をまとめました：
- 課題 1：FastAPI ルーティング骨格の生成
- 課題 2：480 行のデータ処理スクリプト改修と例外処理追加
- 課題 3：計算モジュールに対する境界値単体テスト 12 件の追加

測定結果の比較表は以下の通りです：

| 検証構成 | 平均スループット | 初回応答遅延 | 改修処理所要時間 | 16G メモリ消費ピーク |
| :--- | :--- | :--- | :--- | :--- |
| 基準 1：通常 Ollama による 14B 単体実行 | 21.4 tok/s | 1.8 秒 | 24.2 秒 | 8.3 GB |
| 基準 2：LocalCode と 1.5B Drafter 併用 | 38.6 tok/s | 2.1 秒 | 14.5 秒 | 11.2 GB |
| 基準 3：LocalCode と Copy Drafting 併用 | 74.2 tok/s | 1.4 秒 | 6.8 秒 | 11.4 GB |

推測サンプリングにより入力時のもたつきが解消され、Copy Drafting により既存コードの修正時間は大幅に削減されました。

## 実践的な推奨事項と適用境界

日常の主力モデルを完全に代替することは現時点では現実的ではありません。

しかし現在の運用方針は明確です。新幹線や飛行機での移動中、あるいはネットワーク接続が許されない顧客先において威力を発揮します。単体テストの作成、例外処理の補強、独立関数の手直しといった作業には十分対応でき、秒間 70 トークン以上の速度により待ち時間もほとんど生じません。

複数サービスに跨る大規模リファクタリングを任せるのは避けるべきであり、16GB 環境で 32B を走らせるのも無理があります。主力を置き換える存在ではなく、過酷なオフライン環境下でもコーディングを完遂できる安全弁として捉えるのが賢明です。普段は意識しなくても、合規上の制約に直面した際、手元に動く道具がある安心感は大きな価値を持ちます。
