ローカル動作をうたう個人知識ベースの多くは、LAN ケーブルを抜いた瞬間にメッキが剥がれます。

文書チャンクを勝手に外部へ送出したり、バックグラウンドで絶え間なくテレメトリを送信したり。パケット解析ツールを開けば、暗号化されていない通信が飛び交っていることも珍しくありません。

真の完全オフラインか、それとも見せかけか。

職場のデスクで会計データ、機密ソースコード、未公開の仕様書を扱う際、守るべき防衛線はただひとつ：ファイルは端末から出さず、通信は一切外へ流さないこと。

開発者 nwaoga 氏が GitHub で公開した Loft は、極めてストイックな完全スタンドアロン路線を貫いています。リポジトリは github.com/nwaoga/loft にて公開されています。

フロントエンドは Tauri 2 と Svelte 5 を採用。画面上部のノッチ領域に格納される UI を備え、バックエンドは Rust の std::process::Command 経由で llama.cpp を直接制御します。Python 依存や外付けベクトルデータベースは一切不要。すべてのデータ処理が手元の端末内で完結します：

今回は統合 GPU 搭載、ユニファイドメモリ 16GB の薄型ノート PC で丸一週間実証実験を実施しました。

チャットモデルには Qwen 2.5 3B Instruct の Q4_K_M GGUF [約 2.2GB] を採用。ベクトル埋め込みには 24MB の bge-small-zh-v1.5 Q8_0 を選定しました。入念に検証を重ねた結果、注目に値する設計思想が見えてきました。

## アーキテクチャ解析：なぜ独立した 2 つの llama-server プロセスに分けるのか

ローカル RAG 環境を構築する際、ひとつのサーバープロセスを立ち上げてチャットと埋め込みを同居させる構成が真っ先に検討されがちです。

しかし、その構成で本当に安定稼働するのでしょうか。

実運用においては深刻なキューの詰まりに直面します。

埋め込みモデルのプーリング層と、チャットモデルによる逐次トークン生成では計算リソースの要求特性が大きく異なります。単一プロセスで埋め込み抽出と文章生成を同時に実行すると、内部キューで激しいリソース競合が発生します。さらにメモリ管理も厄介です。生成には膨大な KV キャッシュが必要ですが、埋め込みはバッチスループットを重視します。両者が同じプロセス内で競合すれば、双方の処理能力が頭打ちになります。身動きが取れなくなります。

Loft はここで極めて明確な境界線を引きました。

Rust メインプロセスは、バックグラウンドで 2 つの独立した子プロセスを常駐させます：

- プロセス 1：対話生成専用、2.2GB の Qwen 2.5 3B Instruct Q4_K_M を常駐。
- プロセス 2：特徴抽出専用、24MB の bge-small-zh-v1.5 Q8_0 を常駐。

画像インデックス時には、第 3 の視覚プロセスとして SmolVLM-500M-Instruct Q4_K_M を一時的に起動。画像解析が完了すると即座に終了し、メモリをシステムへ返却します。実に無駄のない設計です。

ふたつの独立プロセスを動かすと、メモリ消費量が倍増するのではないか。

htop で 2 時間監視を続けたところ、合計常駐メモリはわずか 3.8GB に収まりました。単一プロセス混在運用時よりもむしろ低い値です。アイドル時の埋め込みプロセスは KV キャッシュを保持しないため、RSS は約 600MB まで低下しました。当初の懸念は杞憂でした。

ただし初期設定時には思わぬ落とし穴もありました。

llama-server の -np パラメータがデフォルトの 4 に設定され、埋め込み側の -b と -ub が未調整だったため、200 チャンクの分割処理で即座に OOM が発生。コンソールに failed to allocate compute buffer のエラーが大量に出力されました。

対話プロセスのコンテキスト長 -c を 8192 から 4096 へ縮小し、埋め込み側のバッチサイズを 512 に抑えることで安定動作を確保しました。公式マニュアルには明記されていない実戦的な知見です。

## ベクトルストレージの選定：重厚な外部 DB を排除し sqlite-vec 単一ファイルで完結

ローカル知識ベース導入の最大の障壁は、往々にして外部ベクトルデータベースの構築手順です。

数百件の文書を検索するためだけに、数百メガバイトのメモリを消費する独立デーモンを立ち上げるのは本末転倒です。ポート監視や通信設定が加われば、潜在的な障害箇所は跳ね上がります。データベースのポート設定で休日を潰したいエンジニアなどいません。

Loft は SQLite のベクトル拡張である sqlite-vec を採用しました。

ディレクトリメタデータ、ファイルハッシュ値、分割チャンク、高次元ベクトルがすべて単一の loft.db ファイル内に集約されます。たったひとつのファイルですべてが完結します。

さらに文書分割には物理的な上限を設定。1 ファイルあたりの最大分割数を 2000 チャンク [テキスト換算で約 3MB] に制限しています。

検証のため 8000 チャンク相当のログファイルで無制限分割をテストしました。埋め込み処理に 14 分を要し、筐体は素手で触れないほど発熱。検索結果の上位 6 件中 5 件が同一の重複ログヘッダーで占められ、回答の精度は著しく低下しました。上限を 2000 チャンクに絞ると処理は 3 分で完了し、上位 6 件中 4 件が目的の規約条項を正確にヒットしました。

2000 という数値は当てずっぽうではありません。一般的なノート PC が耐えうる実用的な境界値であり、これ以上増やしても得られるのは有益な検索結果ではなくノイズに過ぎません：

| 分割戦略と規模 | 初回ベクトル化所要時間 | 最近傍 6 件の検索遅延 | 実際の回答適合精度 |
| :--- | :--- | :--- | :--- |
| **無制限分割 8000 チャンク** | 約 14 分 | 420 ミリ秒前後 | 希薄なノイズが混入し回答が破綻 |
| **Loft 制限 2000 チャンク** | 約 3 分 | 28 ミリ秒 | 文脈が引き締まり該当条項に的中 |

巨大なログや長大な表形式データに対して無制限に分割を走らせると、推論処理が長時間膠着するだけでなく、検索空間が類似のゴミデータで汚染されます。2000 チャンクの上限設定は、バッテリー寿命を守りつつプロンプト内の情報密度を維持するための合理的な防壁です。

## 幻覚防止と追問リライト：接地プロンプトと厳格な拒否ロジック

パラメータ数の小さいローカルモデルで RAG を動かす際、最大の課題となるのが根拠不足による幻覚生成です。

安易なオープンソース実装では、検索結果のチャンクをそのままプロンプトへ流し込みがちです。確実な根拠が見つからない場合、小規模モデルは容易に事実無根の作り話を始めます。虚偽の回答を真に受けて契約書を精査するわけにはいきません。

どう防ぐべきか。一筋縄ではいきません。

Loft は 3 段階の防御パイプラインを実装しています。

第 1 層は類似度スコアの下限フィルタリング。

質問をベクトル化した後、sqlite-vec から上位 6 件のチャンクを抽出。最高類似度スコアから著しく乖離した候補は強制除外され、文脈に入る有効テキスト量は最大 6KB に制限されます。

第 2 層は拒否プロンプトの厳格な適用。

チャンク内に回答根拠が存在しない場合、モデルは推測による出力を固く禁じられます。インデックスされた文書内に関連情報が見つかりません、指定された文書に基づいてのみ回答可能です、という定型文で回答を安全に停止します。

第 3 層は会話文脈を踏まえた質問の再構成。

経費精算の手順を尋ねた直後に領収書はどこへ提出すればいいですかと追問した場合、その短いフレーズでそのままベクトル検索をかけても適切な断片はヒットしません。

主語が省略された問いかけにどう対処すべきか。

Loft はチャットモデルを呼び出して短い意味補完を行い、代名詞を具体的な検索クエリへ書き換えた上で sqlite-vec へ問い合わせます。

この処理により、追問ごとに 1 回の追加推論が発生します。3B モデルによるリライトは約 400 ミリ秒を要しますが、経費精算の規約を確実に引き当てる価値があります。最新環境であれば妥当なコストですが、古い CPU で 7B モデルを動かして 2 秒かかるような構成では熟慮が必要です。

回答下部には参照元ドロワーが配置され、クリックで該当ファイルや段落へ瞬時にジャンプできます。ファイル閲覧時は OS 標準のエディタを呼び出しますが、実行ファイルやスクリプトはファイルマネージャー上でハイライト表示されるのみで、バックグラウンドでの無断実行は防がれています。

## ハードウェア負荷の実測：薄型ノートとバッテリー駆動時の挙動

一般的な民生機で実用に耐えるのか。客観的なリソース消費量を整理します。

検証環境は独立 GPU を持たない一般的な 16GB ユニファイドメモリ搭載ノート PC。モデルは Qwen 2.5 3B と軽量埋め込みモデルの組み合わせです。

コールドスタートおよび連続問答時の実測値は以下の通りです：

- 常駐物理メモリ：対話プロセスと埋め込みプロセスの合計で約 3.8GB を消費。
- ベクトル埋め込み速度：CPU 演算のみで毎秒約 45 チャンクを処理。
- ストリーミング生成速度：初速レイテンシは約 1.2 秒、以降は毎秒 22 から 28 トークンの速度を維持。

興味深いのは電源状態に応じた適応制御です。

AC アダプタが抜かれバッテリー駆動に切り替わったことを検知すると、内蔵ステートマシンが自動的にデバウンス遅延を延長し、並行スレッドの割り当てを自律的に抑制します。冷却スタンドを使用しない状態でも、キーボード表面温度は約 39 度前後で推移。ファンの異常回転や熱によるサーマルスロットリングは発生しませんでした。

## 物理的な制約と妥協点：どのような用途に適さないか

優れた側面を評価する一方で、割り切るべき制約も存在します。

OCR 機能は OS 環境に強く依存します。スキャン PDF や画像内の文字認識について、Loft は Windows 標準のシステム OCR エンジンを呼び出す仕様となっています。macOS や Linux で実行した場合、画像レイヤーからテキストを抽出することはできません。クロスプラットフォーム利用者はこの差分に注意が必要です。

また軽量マルチモーダルモデルの認識精度にも限界があります。

SmolVLM-500M-Instruct を組み込むことで画像概要の生成は可能ですが、判別できるのは風景や簡易な棒グラフといった大まかな輪郭に留まります。複雑な折れ線グラフや微細な数値データを読み取らせようとすると、小規模モデル特有の幻覚が頻発します。高精度な帳票読み取りツールとしての過信は禁物です。

加えて複数端末間でのネットワーク共有機能は備わっていません。全ポートは 127.0.0.1 に厳密にバインドされ、認証基盤やアカウント分離の仕組みもありません。リバースプロキシを介してチーム共有知識ベースとして流用する設計にはなっていません。

手元のオフィス端末内で機密文書を安全に管理し、煩雑な環境構築に煩わされたくないユーザーにとって、Loft の二重プロセス設計は軽快さと強固な隔離性を高い次元で両立しています。

数百メガバイトの開発フォルダを読み込ませ、Wi-Fi を切断して一度質問を投げてみてください。完全オフラインのローカル環境が日常業務に耐えうるか、手元で確かな手応えが得られるはずです。
