先日、Thinking Machines LabがInkling-2-Miniのオープンソース重みを静かに公開しました。

元OpenAIの技術陣が手掛けたこのモデルは、非常に珍しいアーキテクチャを採用しています。循環型混合エキスパートと呼ばれるLooped MoE構造を備え、物理パラメータ総数は26.4Bに達する一方、トークンあたりのアクティブパラメータは3.4Bに抑えられています。中間層が1回の推論パスの中で3回連続して繰り返し呼び出される設計となっており、物理メモリを増やさずに深い論理推論を行う仕組みです。

発想は極めて秀逸です。しかし、手元でFP16の元重みを計量してみると、実に18.89GBありました。

8GBのVRAMを搭載したグラフィックボードや、8GB統一メモリのMacBook Airでは、ベース重みを読み込むことすらできず、門前払いを食らいます。

諦めて電源を切ろうとしていたところ、Hacker Newsの首位に関連スレッドが浮上しました。開発者ShinMegamiBosonがLookAtMyQuantコンパイラを公開し、Inkling-2-Miniをわずか5.4GBのメモリに収めて動作させる検証例を提示したのです。平均ビット幅は1.63 bpwまで切り詰められていました。

1.63 bpwとは何を意味するのか。通常のGGUF形式でIQ2やIQ1まで圧縮した場合、出力は支離滅裂な文章になりがちです。5.4GBで本当に意味のある回答が出力できるのか、それとも机上の数値遊びに過ぎないのか。

私はリポジトリをローカルへ引き込み、2台の実機環境で徹底的な検証を行いました。

## 1. 極限圧縮のメカニズム：なぜ通常の手法は1.63ビットで崩壊するのか

多くの技術者が疑問に思うはずです。普段使用しているAWQやGPTQは4-bit前後なら実用に耐えるのに、なぜ2-bitを下回ると途端に意味不明な文字列を吐き出すのか。

理由は行列内の各重みの重要度が極端に不均一だからです。

従来の均一な量子化は、テンソル全体を固定の格子で丸め込みます。高ビット幅であれば冗長性があるため劣化は目立ちません。しかし2-bitを下回ると、アテンションの方向性を支えるごく少数の決定的な重みまで強制的に平滑化され、モデルの推論ロジックは即座に崩壊します。

LookAtMyQuant 2はコンパイラ駆動型のアプローチを採っています。コードを精査すると、中核はFisher情報量による動的ビット配分とトレリス状態グラフの最適化という2点に集約されます。

### 1.1 Fisher情報量による感度プロファイリング

LAMQはすべての層が等価であるという前提を排しています。

コンパイラはまず、C4テキストやコード断片からなる少量のキャリブレーションデータを流し込み、各重みブロックに対する損失関数の2階微分、すなわちFisher情報量を算出します。

曲率が高い領域は、重みがわずかに変動しただけでも出力の意味が激変することを意味します。逆に曲率が平坦な領域は、大胆に切り落としても出力への影響は軽微です。

この曲率マップに基づき、LAMQは精度予算を動的に分配します。

埋め込み層、出力射影層、および初期のアテンション行列には3-bitまたは4-bitを割り当てて重点保護します。

ループ内部で呼び出し頻度が低い微小エキスパートFFN層は、1-bitまたは1.5-bitまで容赦なく切り詰めます。

モデル全体で加重平均すると、平均ビット幅はちょうど1.63 bpwに収まります。

### 1.2 トレリス符号化と層ごとの蒸留修復

ビット幅を確定した後、単純な近傍丸めではなくトレリス状態グラフ探索を実行します。

アルゴリズムは動的計画法により、大域的に丸め誤差を相殺できる量子化パスを選択します。エンコード完了後、元の高精度出力との差分を埋めるため、層ごとに蒸留ファインチューニングを施します。

紙の上で計算している分には美しく見えます。しかし実機で動かしてみると、真っ先に直面したのはメモリ帯域の壁でした。ビット演算による解包処理が走るたび、遅延が1層ずつ積み上がっていきます。残る作業は泥臭い力仕事の連続でした。

## 2. 実機稼働環境とMetalカーネルの不具合修正ログ

今回の検証には2種類の物理環境を用いました。

1台目は単体のNVIDIA GeForce RTX 4060 8GB構成。ドライバ550.127.05、CUDA 12.4環境です。

2台目はApple Silicon M3チップ搭載、16GB統一メモリのMacBook。macOS 15.1で動作しています。

### 2.1 ビルド時のヘッダ未検出エラー

LookAtMyQuantはApple Silicon向けに専用のMetal展開カーネルを提供しています。コマンドを実行してCLIを導入します。

```bash
pip install git+https://github.com/ShinMegamiBoson/lookatmyquant.git
```

ビルド済みの重みをローカルに配置し、推論コマンドを走らせました。

```bash
lamq generate shinmegamiboson/Inkling-2-Mini-LookAtMyQuant-5.4GB \
  --prompt "Write a quicksort in Python."
```

テンソルシャードを数個ロードしたところで、ターミナルが突然エラーを吐いて停止しました。

```text
MetalCompilerError: Compilation failed: unknown type name 'half4x4'
  Device::newLibraryWithSource failed to compile custom kernel: lamq_trellis_unpack.metal
```

解包シェーダーのJITコンパイル段階で処理が中断されていました。

macOS 15の更新ログを確認したところ、Sequoia環境下でXcode Command Line ToolsのMetal標準ライブラリのパス構成が変更されていました。明示的なパス指定がない場合、一部の組み込み行列型が認識されなくなっていたのです。

対応は単純でした。シェル環境にツールチェーンのパス変数を渡します。

```bash
export METAL_XCODE_TOOLCHAIN_PATH="/Applications/Xcode.app/Contents/Developer/Toolchains/XcodeDefault.xctoolchain"
```

再度起動コマンドを実行しました。

ターミナルにシェーダーキャッシュの書き込みログが流れ、正常に推論生成フェーズへ遷移しました。

### 2.2 稼働時の実メモリ消費量

推論実行時の物理リソース占有状況は以下の通りでした。

- ベース重みの静的専有量は5.38GB。
- 4,096トークンのコンテキスト設定下で、KVキャッシュはおよそ1.15GB。
- ランタイムおよびフレームワークのオーバーヘッドは約0.35GB。
- システム全体のピーク専有量は6.88GBで推移。

8GBのRTX 4060環境においてメモリ不足によるプロセス停止は起きず、16GBのMac環境でもディスクスワップの発生は皆無でした。

公称通りの5.4GB枠に収まっていることは実証されました。

## 3. 実測スループット：循環構造が要求する時間的代償

メモリには収まりました。では処理速度はどうなのか。

5.4GBのモデルなら軽快に動くはずだと錯覚しがちです。計測を終えて私は口を閉ざしました。5.4GBには収まりましたが、速度は決して甘くありませんでした。

プロンプト長を変えながら5回の測定を行い、中央値を記録しました。

| 入力コンテキスト長 | Prefill スループット | Decode 生成スループット | ピークVRAM消費 |
| :--- | :--- | :--- | :--- |
| 512 トークン | 74.2 tokens/s | 23.8 tokens/s | 6.42GB |
| 2,048 トークン | 68.5 tokens/s | 22.4 tokens/s | 6.68GB |
| 4,096 トークン | 59.1 tokens/s | 20.6 tokens/s | 6.88GB |
| 8,192 トークン | 46.3 tokens/s | 18.2 tokens/s | 7.35GB |

なぜ生成速度が毎秒20から23トークン付近で頭打ちになるのか。

これこそが循環MoE構造が宿命として背負う物理的なコストです。

重み容量は5.4GBですが、トークンを1つ生成するたびに、中間層が3回連続して計算を実行します。これはハードウェアから見れば、70層を超える巨大なモデルを走らせているのと等価な計算量を要求されます。

さらに、トレリス符号の解包処理がシェーダー側でビット演算を頻繁に実行するため、逆量子化のオーバーヘッドが無視できません。

確実に動きますが、決して高速ではありません。文書の推敲やコードの下書き程度なら実用範囲ですが、低遅延が必須となる音声アシスタント用途には適しません。

## 4. 精度劣化の境界テスト

数値目標がどれほど立派でも、出力されるテキストの品質が伴わなければ意味を成しません。

1.63 bpwの実用性を確かめるため、3つの異なる難易度のタスクで出力を検証しました。

### 4.1 基本的なコード生成とロジック解説

型ヒントを明示した非同期リクエスト制限クラスの実装を指示しました。

出力されたコードは構造的で整然としていました。asyncio.Semaphoreが正しく利用され、例外処理や基本テストケースまで整っており、構文エラーは見当たりませんでした。一般的なソフトウェア開発タスクにおいて、推論基盤は堅固に維持されています。

### 4.2 厳密な数値計算と記号推論

タスクを4段階の連続行列演算に切り替え、厳格な出力形式を指定しました。

この段階で1.63 bpwの限界が露呈しました。

3ステップ目の数値計算において、符号の取り違えが発生しました。3回繰り返したところ、4-bit版では96パーセントだった形式適合率が、88パーセントまで低下しました。

はっきり言えば、厳密な数値推論において1.63 bpwは力不足です。計算深度が増すにつれ、記号がブレ始めます。安定した構造化出力を期待しても、数回回せば破綻します。

## 5. ハードウェアの境界線と導入指針

検証を終えて、この構成は誰に向いているのか。

第1に、8GBのGPUや8GBメモリのMacしか持っておらず、それでも26Bクラスの論理展開をローカルで体感したい技術者にとって、LAMQ 2は数少ない現実的な選択肢となります。

本当に収まるのかと問われれば、間違いなく収まります。

第2に、16GBや24GBのVRAMがあるなら、迷わず通常の4-bit版を動かすべきです。メモリに余裕がある状況で、あえて1.63 bpwの妥協を受け入れる理由はありません。

第3に、ベンチマークの派手な数字に惑わされてはなりません。ストレージは削減されました。しかしその代償として、トークンを生成するたびに中間層の計算を3回余分に回す必要があります。削減した容量の分、時間を余計に支払うことになります。

今後、より高効率なアセンブリ展開カーネルが合流するかどうかは未知数です。実機の物理挙動とメモリ計算を冷静に見つめることこそが、技術選定における最大の近道です。
