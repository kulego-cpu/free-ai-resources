# Claude CodeとCodexの記憶とSkillを一括管理：MemDockデスクトップワークベンチ実践ガイド

Claude CodeやCodexを使ってコードを書く中で、記憶の汚染に悩まされたことはありませんか。

多くのプロジェクトのルートディレクトリには、ルールファイルが長期間放置されています：`CLAUDE.md` や `AGENTS.md` です。

最初は快適に機能します。コーディング規約やテストコマンド、ビルド手順を細かく記述しておけば、アシスタントは指示通りに動いてくれます。しかし半月も開発を続ければ、テストフレームワークはJestからVitestへと移行し、ビルドスクリプトも刷新されます。それにもかかわらず、新しいセッションを立ち上げると、モデルは賢くなるどころか過去の陳腐化したルールに従って廃止済みのコマンドを叩き始めます。

テキストでテストコマンドを修正しても、モデルは頑なに古い手順を繰り返します。

過去のセッションで生成された不正確な経験が自動記憶に残骸として残り、新規セッションの判断を狂わせ続けます。この不毛な堂々巡りに辟易した経験は誰にでもあるはずです。

さらに深刻なのが、二大ツールの分断です。

ターミナルで動作するClaude Codeは軽快で俊敏です。一方で複数ファイルの大規模な差分確認やアーキテクチャの把握には、Codexのグラフィカルな画面構成が向いています。しかし両者の拡張機能や記憶は完全に分断されています。Claude Code向けに多数の自動化Skillをセットアップしても、Codexに切り替えると手動でディレクトリを探し直して再設定しなければなりません。ノートPCを持ち出すたびに両環境がリセットされる手間は大きなストレスです。

コミュニティ開発者のcturing氏がオープンソースワークベンチMemDockを公開しました。リポジトリはGitHubでホストされています：`LingyiChen-AI/MemDock`。

まず、このツールがやらないことを明確にしておきます。

コードを自動生成することはなく、プロンプトを代筆することも、サードパーティモデルへ勝手に中継することもありません。導入後も手元のClaude Codeは以前と同じままであり、ターミナルで叩くコマンドも `claude` のままです。ただプロジェクトルートに `.memdock/` というフォルダが追加され、ルールの履歴バージョンが保管されるだけです。設定変更で破綻した際に過去の状態へロールバックできる、本質的にはそれだけのツールです。

担う役割は以下の三点に絞られています：

どのルールを残すべきか。セッションをどちらのツールで走らせるか。マシン間での設定移行をどう行うか。

この三点のみであり、それ以外の領域には一切踏み込みません。

## 記憶の腐敗防止：なぜ【審査待ち】バッファが不可欠なのか

巷の自動記憶機能における最大の設計ミスは、大規模言語モデルに対してルールファイルへの直接書き込み権限を無制限に与えてしまう点にあります。

深夜のコーディング作業中、一時的なエラーをやり過ごすために急ごしらえの汚いワークアラウンドを書いたとします。モデルはその場しのぎの記述を絶対的な原則と誤認し、プロジェクトのルールベースに書き加えてしまいます。その結果、後続のコード生成がすべてその毒された記憶に引きずられ、同じ落とし穴に何度も嵌ることになります。

MemDockの設計思想は極めて慎重です：審査待ちバッファの設置です。

グローバルおよびプロジェクト単位で、`CLAUDE.md`、`AGENTS.md`、Claude Codeのローカル自動記憶を横断検索できます。古いルールが見つかれば、画面上で差分を比較しながら手動編集でき、いつでも過去のリビジョンへ復元できます。

とりわけ実用的なのが、週次の経験抽出ワークフローです。

システムは直近の会話ログを自動走査し、将来にわたって保持すべき技術的知見や修正が必要な旧ルールを抽出します。

しかし、抽出された提案がファイルへ即座に自動保存されることはありません。

提案はすべて審査待ち領域にプールされます。開発者は画面を開き、左側に旧ルール、中央に新規提案、右側に当時の会話原文を並べて比較検討します。

承認ボタンを押して初めてファイルへ永続化され、却下すれば不適切な記憶はその場で破棄されます。

初期導入時に経験した失敗として、ビルド成果物である `dist/` フォルダのエラーログが誤ってルール候補として抽出されてしまったケースがありました。MemDockの除外対象リストに `dist/` と `coverage/` を即座に追加したことで、提案プールを清潔に保てるようになりました。

記憶の依存関係グラフ機能を併用すれば、現在有効な各ルールがどの会話セッションから生まれたのかを視点追跡できます。ルール改定を手探りで行う必要はもうありません。

## ツール間の架橋：Claude CodeとCodexの双方向セッション変換

二つのツールのどちらに一本化すべきかという議論は無意味です。

現場のエンジニアは用途に応じて両者を日常的に往復しています。

ターミナル環境はレスポンスが極めて速く、明確な目標を定めてテストを実行したり、単一ファイルを改修したり、一括リファクタリングを行う場面に適しています。一方で複数モジュールにまたがる設計検討では、Codexのマルチペイン差分ビューアのほうが認知負荷を大幅に抑えられます。

MemDockの中核的な機能は、双方向セッション変換です。

Claude Codeのターミナルで対話を進める中で、複数ファイルにまたがる複雑な改修が必要になった場合、ワンクリックでCodexのセッションへ引き継ぎ、GUI上で作業を継続できます。

逆方向の移行も同様にスムーズです。Codex上で仕様とアーキテクチャを固めた後、ワンタッチでネイティブターミナルへ戻し、重いバッチ処理をコマンドラインで走らせることができます。

拡張機能Skillの管理も一元化されます。

両ツールに導入済みのグローバルおよびプロジェクト固有のSkillが一覧表示され、Superpowersプラグイン群もパッケージ単位で整理されます。GitHubリポジトリURL、ローカルパス、ZIPアーカイブからの直接導入に対応しています。

Claude Code側で動作確認を済ませたデバッグ用Skillは、コピーボタン一つでCodex側へ設定ファイルを意識することなく複製展開できます。

## 並列開発の分離：Git Worktreeとマシン間同期の現実的コスト

単一の作業ツリーでAIエージェントを走らせると、ファイルの編集ロックによる競合が発生しがちです。

あるセッションでアシスタントにバックエンドのデータ構造を大改修させている最中に、別のセッションでフロントエンドの入力フォームを修正させようとすると、単一のGitワークスペース内で未コミットの変更が衝突し、作業が完全に立ち往生します。

MemDockはGit Worktreeの並列メカニズムをUIへ統合しています。

機能開発ごとに独立したディレクトリを切り出し、`git worktree add ../feat-schema feat/schema` を実行して並行作業を進められます。ターミナルでステータスを確認すると以下の構成が得られます：

```text
$ git worktree list
/Users/cool/work/project-core       b39a1c2 [main]
/Users/cool/work/feat-schema        d7e4120 [feat/schema]
/Users/cool/work/feat-ui-auth       a199f03 [feat/ui-auth]
```

ただし、コンフリクトを完全に消滅させられると過信してはいけません。

Worktreeが提供するのはコード作成時の分離であり、ブランチ合流時のマージ競合を魔法のように解消するわけではありません。先週ブランチを合流させた際も、ファイル2件で衝突が発生しました。幸いにも変更箇所が三十行のスキーマ定義部分に集中していたため、解消作業は短時間で完了しました。

真のメリットは作業コンテキストの完全な隔離にあります。片方のブランチでテストを実行し、もう片方で画面を実装していても、それぞれの `node_modules` 依存関係が混ざり合う心配はありません。

一方でトレードオフも存在します。Worktreeを3面展開すれば、ディスク消費量は倍増します。各ディレクトリで依存パッケージをそれぞれ保持する必要があるため、ストレージ残量には十分注意してください。

開発マシンの移行も容易です。記憶ルールとSkill構成をJSONへパッケージングし、GitHubのプライベートリポジトリ経由で一括同期できます。

ただしセキュリティ面での注意点があります：

`CLAUDE.md` をGitHubへプッシュする際は、事前に内容を必ず目視点検してください。社内検証サーバのIPアドレスやステージング用APIキーの接頭辞をルールファイルにハードコードする開発者は少なくありません。プライベートリポジトリは社内ネットワークと同等の安全境界ではないため、秘密情報の混入は情報漏洩事故に直結します。

また、MemDockのライセンスはsource-available形式です。個人用途での利用は無償で開放されていますが、二次配布や商用パッケージとしての無断再販は禁止されています。

## 日常の運用ルーチンと所感

現在の私の運用スタイルは以下の通りです：Claude Codeでテストと単一ファイルの修正を行い、Codexで差分をレビューし、ルール変更はすべて審査待ちプールへ蓄積して週1回まとめて整理します。金曜の退勤前にプライベートリポジトリへ同期しておけば、帰宅後にMacBook側で即座に開発を再開できます。

完全に洗練されているとは言えません。マシンを切り替えるたびにアクセストークンを手動再入力する手間が残っており、作者が告知しているOSキーチェーン統合はまだ実装されていません。

皆さんは普段、AI開発ツールの記憶とルールをどのように管理していますか。より良い運用ノウハウがあれば、ぜひコメント欄で共有してください。
