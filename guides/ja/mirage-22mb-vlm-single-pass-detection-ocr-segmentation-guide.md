# 22MB 未満の単一パス視覚モデルによる検出と OCR：Mirage のアーキテクチャ検証

エッジデバイスや軽量な仮想マシンでマルチモーダルモデルを運用する際、メモリと帯域幅の不足は常に最大の障壁となります。

主流のモデルは単一 GPU であっても 8GB の VRAM を容易に消費します。標準的な 1080p 解像度のスクリーンショットを入力するだけでも、パッチ分割によって数千個の視覚トークンが消費されます。これら長大なシーケンスを自己回帰デコーダに投入すると、ファンが全速力で回転し、カーソルは数秒間にわたり静止します。端末の応答が止まります。実際の運用現場では、画像内の電源スイッチの座標とドアプレートに書かれた短い文字列だけを取得したい場面が少なくありません。

数個のバウンディングボックスと短い文字列を得るためだけに数十 GB の巨大モデルを常駐させると、インフラ費用が膨らみ、端末のバッテリーも急激に減少します。

専用グラフィックカードを持たないエッジノードにおいて、真に求められているのはモデル重みを数十メガバイト以下に圧縮し、物体位置特定、OCR 文字抽出、空間トポロジー関係のみを切り出すことです。従来の自己回帰構造でこれを実現できるでしょうか。

長い間、その答えは否定的でした。

最近、オープンソースコミュニティに極限の軽量構成を持つモデルが登場しました。Cactus Compute チームが公開した Mirage は、Apache 2.0 ライセンスに基づくオープンウェイトのエッジ向けマルチモーダルモデルです。

コミュニティでの一次議論と開発者のフィードバックは以下の技術スレッドで確認できます：
https://www.reddit.com/r/LocalLLaMA/comments/1xpm8mw/

モデル全体の配布サイズはわずか 22MB です。総パラメータ数は 51.3M 前後に収まっています。さらに重要な点として、単一パスの前方推論でシーン説明、物体検出枠、文字認識、セグメンテーションマスク、空間トポロジー関係を同時に出力します。

これほど小さなモデルが、どうやって多数の視覚タスクを単一パスに統合しているのでしょうか。本当にそれほど軽量なのでしょうか。

私自身、実際に検証するまでは疑念を抱いていました。

## ハードウェア予算と 51.3M パラメータの配分

従来のマルチモーダルモデルが巨大化する理由は、汎用デコーダにすべての処理を負担させようとする設計にあります。

デコーダが画像の説明文を生成するだけでなく、連続したテキストストリームの中で浮動小数点座標を出力する必要があります。この手法は、小規模モデルの貴重な容量を低効率な座標文字の生成で浪費させてしまいます。

Mirage の設計方針は大きく異なります。デコーダに過剰な自己注意層を積み上げる代わりに、51.3M の全体パラメータを明確に役割分担させています：

- 画像エンコーダ。パラメータ数約 7.8M。HConvGLU モジュールを採用し、固定アダマール変換により多チャンネル特徴量を混合し、軽量な学習可能畳み込み層で補正；
- 言語デコーダ。パラメータ数約 40.8M。Simple Attention とアダマール多層パーセプトロンを組み合わせたコンパクト構造で、Needle および Whistle アーキテクチャを継承；
- 専用出力ヘッド。パラメータ数約 2.6M。軽量な文字認識ヘッドと空間幾何ヘッドで構成。

パラメータの配分を計算すると構造の意図が明確になります。

空間座標とマスク生成はテキストデコーダによる推測に委ねられません。2.6M の並列専用ヘッドが直接構造化データを出力します。言語デコーダは物体の意味ラベル、基本属性、空間的な因果関係の出力に集中します。

文字認識も同様の仕組みを採用しています。モデル内部に専用のテキスト走査経路を備え、文字特徴を抽出した上で意味アライメントを実行します。

この明確な役割分担により、40.8M の言語デコーダは無駄な負荷を負わずに済みます。

シーン説明の出力言語として、英語、ドイツ語、フランス語、スペイン語、イタリア語、オランダ語、ポーランド語の 7 言語に対応しています。出力テキストは簡潔で無駄がありません。

## モバイル NPU での 74ms と通常 CPU での 5.8 秒という実測落差

超小型モデルの性能を評価する際は、実行環境のハードウェア仕様を明示する必要があります。

原著者が提示した指標は、Samsung Galaxy S26 スマートフォンを基準としています：

- 内蔵された神経回路網処理装置 NPU で実行した場合、全タスクの単一推論時間は約 74 ミリ秒；
- スマートフォンの CPU で実行した場合、単一推論時間は約 107 ミリ秒。

100 ミリ秒未満の応答速度であれば、端末内でのアルバム自動分類や撮影時の補助フォーカスとして実用的な速度です。

しかし、アクセラレータを持たないクラウド VM やオフィスの旧式 PC で動かした場合、同じような性能が得られるでしょうか。性能の妥協点は存在しないのでしょうか。

コミュニティ開発者の MagoViejo 氏は、加速装置を持たない一般的な x86 パソコンにこの重みを読み込ませて検証しました。デュアルコア CPU の浮動小数点演算のみに依存した環境では、画像 1 枚の完全解析に 5.8 秒を要しました。

モバイル NPU の 74 ミリ秒から一般 PC の 5.8 秒へ、処理時間は約 80 倍に急増します。この原因は計算ユニットの違いにあります。Galaxy S26 は定点テンソル演算専用の NPU を備えているのに対し、旧型 x86 パソコンはハードウェアベクトル加速のない CPU コアで浮動小数点行列を直接計算するため、計算能力の限界が直ちに露呈します。

この実測値からハードウェアの境界線が見えてきます。ハードウェアの挙動は誠実です。

使用端末に最新の NPU が搭載されていれば、数十ミリ秒の応答速度は実用的な価値を持ちます。

一方で、安価なシングルコア仮想マシン上でリアルタイム映像監視を行おうとすれば、毎秒 0.2 フレームという処理速度では監視パイプラインが即座に破綻します。約 6 秒の待機時間を前にして、リアルタイム映像処理に組み込める現場があるでしょうか。どのような本番システムがこれほどの遅延を許容できるでしょうか。

手元の余剰低スペック Linux マシンで試行しました。ファンが即座に唸りを上げました。

バックグラウンドでの画像オフライン分類、起動時の前処理、専用 GPU を持たない軽量エージェントの低負荷な視覚機能として配置することこそ、現実的なエンジニアリング判断です。オフラインのバッチ処理であれば、クラウド費用を大幅に削減できます。

## コミュニティの議論とコンテナ環境でのエラー対応

いかなるオープンソース基盤であっても、本番環境に導入される前にはコミュニティによる厳密な検証を受けます。

Mirage の公開後、議論の中で 2 つの主な論点が浮上しました。

第 1 の論点は、コミュニティの自動監視ツールによる判定です。アカウント stylome-ai-detection が公開スレッドに対して AI 生成テキストの可能性があるとの警告を付与しました。作者が直ちに技術的詳細を回答したものの、告知文の表現に対して慎重な開発者の間で懸念が生じました。

これは真の技術成果なのか、それとも宣伝上の誇張なのか。

第 2 の論点は、従来の物体検出アルゴリズム YOLO との比較です。

産業用 PC の CPU 上での検出フレームレート単体で見れば、軽量化された YOLO nano の方が依然として高速です。Mirage の真の価値は純粋な FPS の競争ではなく、22MB という極小サイズの中に文字認識と複数物体間の空間関係解析を統合した点にあります。

ローカル環境での導入手順は単純です。Python 3.10 以上の環境で公式パッケージを導入します：

```bash
pip install cactus-compute
```

Python インターフェースを通じて標準パイプラインを呼び出します：

```python
import cactus_compute

pipeline = cactus_compute.MiragePipeline.from_pretrained("cactus-compute/mirage-v1")
outputs = pipeline.analyze_image("test_sample.jpg")

print("Detected Boxes:", outputs.boxes)
print("OCR Text:", outputs.text_segments)
print("Spatial Topology:", outputs.relationships)
```

初期状態の Ubuntu 22.04 コンテナで初回実行した際、ターミナルに直ちにエラーが出力されました：ImportError: libGL.so.1: cannot open shared object file: No such file or directory。

処理が停止しました。

環境ログを確認したところ、基底部分でグラフィック描画ライブラリに依存していました。コンテナ内で apt-get update && apt-get install -y libgl1 を実行して不足パッケージを補完することで、正常に推論が完了しました。

不足ライブラリを追加するだけで解決します。

この初期設定を通過すれば、推論処理は安定して動作します。

## 技術的境界と選定基準

今回の検証を通じて、Mirage のような 22MB 級マルチタスクモデルの選定基準が明確になりました。

適した運用用途：
- モバイルおよびウェアラブル機器。低消費電力 NPU を搭載し、看板文字や物体輪郭をオフラインで解析する機器；
- エッジエージェントの負荷分散。Raspberry Pi や産業機器に前置フィルタとして配置し、無意味なフレームを除外して異常時のみクラウドへ転送；
- プライベート写真のオフライン索引作成。画像を外部送信せず、バックグラウンドで時間をかけて検索タグを付与。

適さない運用用途：
- 高フレームレートの産業検査。毎秒数十フレームの連続映像で欠陥を検出する場合、YOLO や専用検出ヘッドを採用すべきです；
- 複雑なオープンエンド図面解析。複雑なチャート論理や複数ページの会計資料を解析する場合、クラウドの大規模モデル API を利用すべきです。

タスク構造を問題定義に組み込み、専用の空間ヘッドで言語デコーダの負荷を分散させる設計思想は極めて合理的です。

ただし、22MB の物理的制約が存在する以上、万能の知能を期待すべきではありません。軽量で用途の明確なエッジ向け万能ナイフとして扱うことで、アクセス集中時にも破綻しない堅牢なシステムを構築できます。

エッジハードウェアで安定運用するために、通常 CPU 環境における約 6 秒の待機時間を許容できるでしょうか。それとも、あなたの機器にはすでに専用 NPU が搭載されているでしょうか。
