中古の RTX 3090 が 2 枚、合計 48GB の VRAM。

数十億のアクティブパラメータを持つ MoE モデルをすべて VRAM に載せようとすれば、即座に CUDA out of memory で停止します。

骨幹ネットワークを GPU に残し、使用頻度の低いエキスパートをメインメモリに逃がす。起動できるか。起動はできます。

しかし実際に推論を始めると、生成速度は毎秒 2 から 3 トークンに急落。CPU 使用率は 100% に張り付き、肝心の GPU 使用率はわずか 3% で遊んでいます。

まずは nvidia-smi を見直し、PCIe 帯域を確認すべきです。問題の多くは計算カーネルではなく、バス経由の重み転送にあります。

検証データは GitHub の公開リポジトリ https://github.com/alesha-pro/inference-optimization-playbook によるものです。

テスト環境は Ubuntu 22.04 LTS、300W 制限の RTX 3090 を 4 枚、PCIe 3.0 x16、8 チャンネル DDR4-2133 メモリ、ドライバ 580.12 と CUDA 12.8。ランタイムには独自パッチを当てた llama.cpp コミット 1cd7102 および自作エンジン maya-ik2 r5 を使用。DeepSeek、Qwen、混元などのモデルに対して 115 の仮説を試し、97 系統の比較実測値を記録しています。

この記録で最も価値があるのは、速度向上グラフではなく詳細に記載された失敗リストです。ネット上で推奨される多くの調整手法が、実環境では全く効果がないか、逆に性能を破壊することが証明されています。

## 重み転送が直面する物理的限界

なぜ MoE のハイブリッドオフロードは極端に遅くなるのか。物理的な計算式を確認します。

MoE モデルは 1 トークン出力するごとに、ルーターが数十のエキスパートからごく一部を選択します。数千枚の GPU を備えるクラウドなら全エキスパートが VRAM に常駐しますが、民生用マザーボードでは PCIe レーンの帯域が著しく不足します。

選ばれたエキスパートが VRAM にない場合、PCIe 経由でメインメモリから運ばなければなりません。数値を整理します：

- 量子化後のエキスパート 1 つの重みは約 150MB から 300MB
- 1 トークンあたり通常 4 から 8 のエキスパートが起動
- すべて未ロードのエキスパートに当たれば、1 ステップで 1.2GB のデータ転送が発生
- 一般的な PCIe 3.0 x16 の実効転送速度は毎秒約 12GB から 14GB

これが何を意味するか。

純粋なデータ移動だけで、理論上の生成速度は毎秒十数トークン以下に制限されます。複数 GPU がメモリチャンネルを奪い合えば、遅延はさらに倍増します。

どこに本質的な手を入れるべきか。

## 明確に成果を出した 4 つの低レイヤ改善

97 組の比較検証の中で、桁違いの性能向上を記録した手法は 4 つに限られます。

### 1. 仮想メモリページを破棄し、Pinned RAM で DMA 転送を直結

一般的なプログラムはページング可能な仮想メモリを使います。ドライバが GPU にデータを送る際、まず OS 内部のロック領域へ一時コピーし、そこから DMA を実行します。この二重コピーがメモリ帯域を浪費します。

対策はシンプルです。初期化時にメモリ固定用システムコールを発行し、メモリ内のエキスパート重みを物理 RAM 上に直接固定します。

実測の成果はどうだったか。

4 枚の GPU で DeepSeek V4.1 Flash をオフロード実行した際、プロンプトのチャンク分割と組み合わせて 32K コンテキストの事前計算速度が毎秒 430 から 2,199 トークンへ跳ね上がりました。CPU 側での無駄なコピーを排除したことによる 5 倍の高速化です。

### 2. パイプライン分割を廃止し、テンソル並列へ完全移行

カードごとに層を割り振るレイヤー分割は直感的ですが、オフロード環境では重大なパイプラインバブルを招きます。

前段のエキスパートがメモリ転送を待つ間、後段の GPU は完全にアイドル状態となります。カード間の同期が崩れ、40% 以上の時間で処理が停止します。

チームは GLM-5.3-Flash の 2.05bpw 評価において層分割を破棄し、完全なテンソル並列を採用しました。各 GPU が全エキスパートの重み行列の 4 分の 1 を保持し、DMA 転送と行列計算を同時に走らせ、最後に All-Reduce で結果を集約します。

4 枚構成において、生成速度は毎秒 48.3 から 67 トークン前後へ安定して向上。GPU 間の処理待ちが解消されました。

### 3. 未常駐エキスパートは CPU で即座に計算し、常駐分のみ GPU で処理

未常駐エキスパートを PCIe 経由で運ぶ帯域が足りないなら、多コア CPU を使ってメインメモリ上で直接計算すればよいのではないか。

混元 Hy4 Flash の 2 枚構成において、チームはスケジューラを再構築しました：

```text
               ┌───────────────────────────────┐
               │    Router トークン判定         │
               └───────┬───────────────┬───────┘
                       │               │
             [VRAM 常駐エキスパート] [未常駐エキスパート]
                       │               │
                       ▼               ▼
               ┌───────────────┐┌───────────────┐
               │ GPU コア計算   ││ CPU マルチスレッド│
               │ 並列 GEMM     ││ メモリ上直接計算 │
               └───────┬───────┘└───────┬───────┘
                       │               │
                       ▼               ▼
               ┌───────────────────────────────┐
               │    中間層合流バリア           │
               └───────────────────────────────┘
```

選択された 8 つのエキスパートのうち 6 つが VRAM にあり 2 つがメモリにある場合、重みの転送を中止。VRAM 側の 6 つは GPU で計算し、メモリ側の 2 つは CPU スレッドで並列処理します。完了後に転送されるのは軽量なアクティベーション値のみです。

コード生成テストにおいて、混元の生成速度は毎秒 24.6 から 70.4 トークンへと急伸しました。

### 4. 単一グラフ化：数千回のカーネル発行を 1 つの CUDA Graph に集約

モデル全体が 24GB の単一 GPU に収まる場合、ボトルネックはバス帯域からカーネル発行オーバーヘッドへ遷移します。

Inkling 2 Mini の例では、24 層の MoE に 3,072 のエキスパートが存在します。標準の llama.cpp ではトークン生成ごとにドライバ層を 1,404 回往復します。カーネル自体は数マイクロ秒で終わるにもかかわらず、発行待ちの滞留によって速度が毎秒 57 トークンで頭打ちになります。

解決策は明確です。maya-ik2 r5 エンジンにて全エキスパート計算と残差結合を 1 つの CUDA Graph に統合し、発行回数を 781 回へ削減しました。

量子化精度を落とすことなく、生成速度は毎秒 57 から 112 トークンへ倍増しました。

## データを前に崩れ去った最適化の俗説

成功例の裏には、全く効果がなかった失敗例が多数存在します。

### 1. 静的なエキスパート使用頻度ファイルは流用できるか？

一般的なテスト文章を流して出現頻度を記録し、上位 20% を VRAM に固定すれば 80% ヒットするという説があります。

現実は甘くありません。MiniMax によるテストでは、単一の質問から作成したプロファイルは元質問に対して 90% の的中率を示したものの、同分野の別質問では 64% に急落。プロファイルを使わずランダムに配置した場合でも 61% であり、有意な差は見られませんでした。

### 2. 自作の小型モデルによる投機的デコードは万能か？

小型モデルで素早く候補を出し、親モデルで一括検証する手法は論理的です。しかし 3 種類のオープンソースモデルで検証した結果、独自ファインチューニングした小型モデルによる速度向上はほぼゼロでした。

ドラフト側の受容率が少しでも落ちると再計算のロールバックが発生し、一括検証の利益を完全に相殺してしまいます。

### 3. 短文ベンチマークの数値は長文でも再現するか？

128 トークンの短いベンチマークで 27% の向上を示したアテンション設定が、8K の長いコンテキストに投入した途端に 4 往復目でオーバーフローを起こし、実効スループットが 2% 低下した事例が記録されています。短文の結果を過信してはなりません。

## 実践的なトラブルシューティング手順

民生用カードで大型 MoE を動かす際は、まず以下のコマンドでボトルネックを特定してください：

```bash
# GPU 負荷と PCIe バス使用率をリアルタイム監視
nvidia-smi dmon -s et -d 1
# マザーボードのスロットが実際に 16x リンクで認識されているか確認
sudo lspci -vv -s $(lspci | grep -i nvidia | head -n 1 | awk '{print $1}') | grep LnkSta:
# NUMA ノード構成とメモリ競合を確認
numactl --hardware
# 巨大ページメモリを有効化し物理メモリを確保
sudo sysctl -w vm.nr_hugepages=1024
```

第一にバス監視。PCIe 負荷が 90% を超えているなら問題はデータ転送です。巨大ページメモリの有効化と Pinned 転送の適用を優先してください。

第二にルーティング分布の分析。選択エキスパートが分散しているなら静的プロファイルに拘泥せず、テンソル並列か CPU 並列計算を選択すべきです。

第三に本番規模での耐久テスト。実務で使用する数万文字のログを流し、長文セッションで破綻なく完走できる構成こそが実用に耐える環境です。
