## 1. なぜ従来の議事録ツールは企業情報漏洩の温床になるのか？

業務効率のために機密情報を犠牲にする必要があるのか？
答えはクラウド型ツールの安易な設計にあります。

市販の商用議事録製品の大半は、単なるクラウド転送中継器に過ぎません。
第1に、ブラウザ拡張でマイクとスピーカーの音声を録音；
第2に、高音質な音声ストリームを業者のパブリッククラウドへ無加工で送信；
第3に、クラウド側でモデルを回し、要約テキストを画面へ返送します。

一見すると便利。
実態は危険極まりない構成です！
社内の密談、激しい議論、口頭で伝えたテスト用パスワードまで、すべて他社のストレージに保管されます。
業者の設定ミスや不正アクセス、内部不正が起きれば、機密は一瞬で白日の下に晒されます。
これはアシスタントではありません。
いつ爆発するかわからない時限爆弾です！

Natively 3.0の設計思想は極めて明快です。
外部への通信経路を完全に遮断せよ！
文字起こし、モデル推論、過去ログ検索の全工程をローカル環境に封じ込めます。

## 2. 構造解剖：完全オフライン議事録を支える3本の柱

ネットワークを切断したノートPCで、どうやって長時間の会議を処理するのか？
システムは3つの低レイヤモジュールで構成されています。

### 1. Rustによるゼロコピー音声分離パイプライン
WebAudio経由のキャプチャは遅延と音割れの原因になります。
NativelyはRustで記述されたネイティブ音声パイプラインを実装。
OSの低レイヤAPIを通じて相手の音声を直接取得；
それと同時に自分のマイク入力を独立して録音します。
2系統の音声は物理的に分離。
相手の音声が部屋の雑音として回り込む不具合を排除します。

### 2. 端末内完結のWhisperおよびParakeet文字起こし
パイプラインに入った音声は、最適化されたONNXエンジンへ直接送られます。
Mac環境ではMetalおよびCoreMLハードウェアアクセラレーションを活用；
Windows環境ではDirectMLインターフェースを使用します。
応答遅延は0.5秒未満に収まります！
文字起こし枠を購入する必要もありません。
音声が外へ漏れる心配もゼロです。

### 3. Ollama連携とローカルMCPサーバー
文字起こしされたテキストは、ローカルで稼働するOllamaプロセスへ直結。
Qwen2.5 7BやLlama3.2 3Bなど、好みのオープンモデルを頭脳として選択可能です。
最新の3.0では、ローカルのループバックネットワーク上にMCPサーバーを起動する機能まで追加されました！
ターミナル上で動く別の自律型エージェントから、先週の会議で決定したAPI仕様を直接問い合わせることができます。

## 3. 実機ベンチマーク：誇張なしの負荷データ

この全ローカル環境は実用に耐えうるのか？
実機のMacBook Pro上で負荷テストを実施しました。

### 検証ハードウェア構成
- 測定環境：MacBook Pro M2 Maxチップ、32GB統合メモリ
- ローカルLLM：Ollama上で稼働するQwen2.5 7B Instruct
- 音声認識モデル：Whisper large-v3-turbo CoreML量子化版
- 比較対象：一般的な商用クラウド議事録SaaSクライアント

### 45分間の技術会議における実測比較データ

5回の実測会議データから中央値を算出。

| 評価項目と測定シナリオ | 従来の商用クラウドツール | Natively 3.0 完全ローカル | 測定結果と動作ステータス |
| :--- | :--- | :--- | :--- |
| 音声データの外部送信量 | 1時間あたり数百メガバイト | 完全にゼロバイト外部送信なし | 機密保持要件を物理的にクリア |
| 音声認識の端到端遅延 | 800ミリ秒から1.5秒程度 | 450ミリ秒から600ミリ秒安定 | Rust製パイプラインが高速 |
| 議事録要約とタスク抽出時間 | クラウド側で約4秒程度 | ローカル7Bモデルで約8秒 | ローカル演算のため速度は劣る |

無料ソフトウェアだからといって、計算資源まで無料なわけではありません。
動画会議自体がカメラと画面共有でリソースを消費します。
そこへWhisperの音声処理が加わり；
バックグラウンドでOllamaが推論を走らせます。
統合メモリ消費量は一気に22GBへ跳ね上がります！
ファンが回転し始めます。

もし手元のPCが8GBや16GBメモリなら、即座に諦めてください。
低スペック機で無理に同時起動すれば、会議アプリごとフリーズするのがオチです！

## 4. トラブルシューティングとコミュニティでの議論

2日間の連続テストで遭遇した注意点と、コミュニティで浮上している懸念をまとめました。

### 1. マイク排他制御による音声脱落
インストール直後、相手の声は文字起こしされるのに、自分の声が一切記録されませんでした。
原因究明の結果、Web会議ソフトがマイク入力を排他ロックしていたことが判明。
対処法は単純です。
設定画面を開き、マイク直結モードからシステム音声ミキサー共有モードへ切り替えます。
解決しました。

### 2. コンテキスト過大による推論遅延
Ollamaのコンテキスト枠を広く取りすぎると、会議開始から30分経過したあたりで7Bモデルの生成速度が急落します。
相手が早口になると、メモリキューに音声切片が溜まり始めます。
スライドコンテキスト窓は8192以下に固定してください。
定期的に区切って要約させるのが安定稼働の秘訣です。

### 3. コミュニティの議論：ローカルMCPサーバーの権限管理
Redditの技術者kantorcodes1が重要な問題を提起しました。
Natively 3.0のローカルMCPサーバーには、厳格な読み取り専用保護があるのか？
現状の実装は簡素です。
ローカルポートが特定されれば、他のツールからMCP経由でアクセスできてしまいます。
未検証の自律型スクリプトをローカルで動かした場合、会議記録を盗し見されるだけでなく、過去ログを改ざんされるリスクすらあります！
公式が強固なアクセス制御を実装するまで、このMCPポートを無防備な外部エージェントへ接続するのは避けるべきです。

### 4. スポンサー広告への留意点
GitHubのREADME上部には、商用デスクトップ録音APIのPRリンクが掲載されています。
個人利用は無料ですが、将来的にクラウド課金版を展開する意図が窺えます。
利用時はローカル設定を厳守してください。
ローカルOllamaのみを指定し、クラウド連携を避けることが肝要です。

## 5. セットアップ手順：ローカル導入の3ステップ

データプライバシーを最優先する技術者は、以下の手順で構築可能です。

### 1. ローカルOllamaの準備
Ollamaを起動し、適切なモデルをプルします。

```bash
ollama run qwen2.5:7b
```

### 2. クライアントのインストール
Mac環境ではHomebrewでインストールします。

```bash
brew install --cask Natively-AI-assistant/tap/natively
```

### 3. 完全オフライン設定
アプリの設定パネルを開きます。
- モデル提供元にOllamaを指定し、ポート11434を設定。
- 音声認識にローカルWhisperエンジンを選択。
- クラウド同期や共有のトグルをすべてオフにし、ローカル表示を確認。

Wi-Fiを切断し、機内モードで録音を試してみてください。
画面上にリアルタイムで流れる字幕とアクションアイテム。
データが完全に自分の手元にある安心感は、月額課金のクラウドツールでは決して味わえません！
