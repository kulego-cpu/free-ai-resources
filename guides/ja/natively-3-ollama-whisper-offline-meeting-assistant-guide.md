# Natively 3.0 と Ollama による完全ローカル議事録レビュー：オフライン文字起こし、実測ハード負荷と MCP ポート検証

先週金曜日の午後三時、技術選定レビュー会議。
競合三社の調達原価見積もりが画面に投映されていました。
同僚が何気なくクラウド型 AI 議事録ツールを立ち上げようとした瞬間、法務担当が制止しました。昨年発生した大手会議記録 SaaS の情報漏洩事件では、8 万 3000 人分の録音や画面キャプチャが外部流出したと報じられています。原価見積もりや内部コード設計を外部クラウドへ送るわけにはいきません。
二時間に及ぶ会議は手作業でメモを取りましたが、二箇所の決定事項が漏れました。
会議後、私は Natively 3.0 の検証に着手しました。議事録の自動化は必要ですが、音声データは一歩も社外の端末から出さない前提です。

## 1. クラウド型ツールの脅威モデルとローカル隔離の設計思想

市販のクラウド型議事録ツールは、どのようにデータを処理しているのでしょうか。
パケットを解析すると、主に三段階のパイプラインで動いています。
ブラウザ拡張機能や仮想オーディオデバイスがマイクとスピーカーの音声をキャプチャします。
切り出された音声ファイルがパブリッククラウドのオブジェクトストレージへアップロードされます。
クラウド上の音声認識と大規模言語モデルが要約テキストを生成し、画面へ返送します。

設計上の懸念点は明確です。
生の音声データが第三者のサーバストレージに残ります。
バケット権限の設定ミスや認証情報の漏洩が発生した場合、調達価格や未公開のシステム設計、社内の議論がそのまま平文で晒されるリスクがあります。
機密を守るための確実な解は、外部通信権限を最初から遮断することです。

Natively 3.0 の設計方針は単純明快です。
音声キャプチャ、文字起こし、モデル要約、履歴検索のすべてを単一マシン内で完結させます。
すべての通信をループバックアドレス 127.0.0.1 に固定し、外部への音声送信をゼロにします。

## 2. アーキテクチャ解説：完全オフライン駆動を支える三要素

ネットワークを遮断したノート PC で二時間の会議を処理し続けるため、以下の三要素が協調して動作します。

### 1. Rust による二系統ネイティブ音声分離
ブラウザの WebAudio は高負荷時に音飛びや遅延が生じやすい特性があります。
Natively は音声取得パイプラインを Rust で実装しています。
一方は OS のコアオーディオ出力を監視して相手の発言を記録します。
もう一方は物理マイクの入力を独立して取得し、自身の発言を記録します。
二つの音軌を物理的に分離することで、スピーカーからの音声がマイクへ逆流して話者分離を混乱させる事態を防ぎます。

### 2. エッジ版 Whisper と Parakeet 音声認識エンジン
切り出された音声データは外部 API を経由せず、ローカル推論エンジンへ直接渡されます。
Apple Silicon では CoreML と Metal パイプラインでハードウェア加速を行います。
Windows では DirectML を利用します。
音声認識の遅延は 450 ミリ秒から 600 ミリ秒の範囲に収まり、従量課金 API も不要です。

### 3. Ollama バックエンドとローカル MCP サーバ
文字起こしされたテキストストリームは、ローカルで稼働する Ollama プロセスへ順次送られます。
利用モデルは Qwen2.5 7B や軽量な Llama3.2 3B などを選択できます。
バージョン 3.0 では、ローカルのループバックネットワーク上に Model Context Protocol すなわち MCP サーバが実装されました。
開発用エージェントから過去の議事録データを検索できるかという点についても、標準 MCP 経由で即座に参照可能です。

## 3. 実機検証：45 分間の会議における負荷と限界

完全ローカルでの稼働にハードウェアが耐えうるか検証しました。
まずリソース消費の記録です。検証機は M2 Max 搭載 MacBook Pro、メモリ 32GB。音声認識に Whisper large-v3-turbo 量子化モデル、推論に Ollama Qwen2.5 7B 指令調整版を使用しました。
参加者五名、45 分間の二系統音声会議において、ピークメモリ消費は 22GB に達し、ファンの回転数が上がり、SoC 温度は 85 度近くを推移しました。
16GB 以下のマシンで文字起こしと 7B 推論を同時に回す運用は推奨しません。8GB では実行自体を避けるべきです。
以下の表は五回の会議中央値であり、合成ベンチマークではありません。

| 評価指標と項目 | 従来のクラウド型 SaaS | Natively 3.0 ローカル構成 | 実測状況と境界条件 |
| :--- | :--- | :--- | :--- |
| 音声外部送信トラフィック | 毎時数百メガバイトをクラウド送信 | 外部送信ゼロ、内部通信のみ | クラウド側データ漏洩リスクを排除 |
| 音声認識レスポンス遅延 | 800 ミリ秒から 1500 ミリ秒で変動 | 450 ミリ秒から 600 ミリ秒 | Rust ローカル配管でネットワーク往復なし |
| 要約生成の所要時間 | クラウド側で約 4 秒で完了 | ローカル 7B モデルで約 8 秒 | 計算資源の差によりクラウドが高速 |
| ホストシステム最大メモリ消費 | クライアント単体で約 450MB | ホスト全体で 22GB に到達 | Whisper と推論モデルの常駐コスト |
| 連続稼働時の発熱とファン | 発熱僅少、ファンはほぼ静音 | 発熱が顕著、SoC は約 85 度 | 継続的な高負荷演算による発熱 |

完全ローカル運用には強固な秘匿性がある反面、確実な物理的負荷が発生します。
ビデオ会議ソフト自体がグラフィック描画と映像デコードを消費します。
さらにローカル Whisper が音声切片を連続処理し、Ollama が推論コンテキストを保持します。
これらが重なることで合計 22GB のメモリを消費します。
16GB マシンでこの構成を走らせた場合、仮想メモリのスワップが発生して描画コマ落ちを招く可能性が高いです。

## 4. トラブルシューティングとセキュリティ境界

複数回の検証を通じて確認された留意事項は以下の通りです。

### 1. マイク排他制御による録音欠落
導入初期、相手の発言は文字起こしされるものの自身の発言が抜ける事象が発生しました。
調査の結果、会議ソフトが物理マイクデバイスを排他的にロックしていたことが原因でした。
設定画面から音声取得元を直接マイク監視からシステムミキサー入力へ切り替えることで解決しました。

### 2. 長時間会議における推論速度の低下
会議時間が 30 分を超えてテキスト量が蓄積すると、モデルの推論速度が低下する挙動が見られました。
コンテキストを無制限に拡張すると、7B モデルの生成速度が秒間 40 文字から 10 文字前後まで落ち込みます。
スライドコンテキスト幅を 8192 トークン以内に固定し、定期的な区切りで部分要約を行う構成が適しています。

### 3. ローカル MCP サーバのセキュリティ境界
MCP の実装について検証しました。バージョン 3.0 はループバック上に軽量な MCP サーバを起動します。現行バージョンには詳細なアクセス制御や読み取り専用の隔離機能は見当たりません。ポート番号を把握しているローカルプロセスであれば議事録をクエリ可能です。万一信頼できないエージェントスクリプトが同居している場合、議事録の改変や削除が行われるリスクが存在します。公式による権限制御が追加されるまでは、外部パイプラインへ接続せず、リッスンアドレスを 0.0.0.0 へ変更しないよう注意が必要です。

### 4. ドキュメント内のスポンサーリンク確認
プロジェクトの README 先頭には商用録音 API のスポンサーリンクが記載されています。
ツール本体はオープンソースですが、設定時は外部の有料クラウドを選ばず、ローカルの 127.0.0.1 接続を維持するよう確認してください。

## 5. 構築手順と動作検証チェックリスト

完全ローカル環境を立ち上げる際の手順は以下の通りです。

### 1. ローカル Ollama の準備
Ollama を導入し、検証済みモデルを取得します。

```bash
ollama run qwen2.5:7b
```

### 2. クライアントの導入
macOS 環境では Homebrew 経由でインストールします。

```bash
brew install --cask Natively-AI-assistant/tap/natively
```

### 3. オフライン設定の適用
設定画面を開き、各項目を調整します。
- モデルプロバイダに Ollama を指定し、ポート番号 11434 を設定。
- 音声認識にローカル Whisper を選択し、初回にエッジ重みファイルを保存。
- クラウド同期関連のスイッチを解除し、オフライン表示を確認。

### 4. オフライン検証とポートの確認
Wi-Fi を切断し、機内モードでテスト音声を記録します。字幕がリアルタイムで流れ、ToDo リストが生成され、ファイルはローカルに保存されます。代償は 22GB のメモリとファン音です。ターミナルで `lsof -i :11434` を実行して Ollama が 127.0.0.1 のみでリッスンしていることを確認し、MCP ポートが LAN へ公開されていないこと、議事録がローカル SQLite へ保存されていることを点検して作業完了です。
