## 1. キャパシティ設計の破綻：12人の利用に8枚のH100が必要だったか

まず私たち自身の愚行から振り返らなければならない。

先月初旬、社内ドキュメント検索と検証のPoC案件を受託した。

事前の要件定義会議で、発注元の技術責任者が本格展開時には百人規模の同時アクセスがあり得ると口頭で触れた。

安全策を取りたい心理と、技術報告会で堂々たる構成を見せたい虚栄心が重なり、私たちは段階的な負荷検証を怠った。

大手パブリッククラウド上で8枚のNvidia H100 80GB SXM5インスタンスをいきなりオンデマンドで契約した。

当時の時間単位の課金明細は以下の通りだった：
- 1基あたりの1時間料金：3.85米ドル；
- 8基合計の1時間料金：30.80米ドル；
- 30日間連続稼働の総費用：30.80 × 24 × 30 = 22,176米ドル；
- 人民元換算の支出総額：約159,600元、日本円にして300万円超に達する。

16万元近い大金を溶かした結果、実際の現場はどうだったか。

検証が始まって実際にアクセスした社内スタッフは、わずか12人だった。

日中の平均同時リクエスト数は3件から5件にとどまった。

12人の利用に8基のH100が必要だったか。

まったく不要だった。

完全なる予算の無駄遣いだった。

毎晩22時を過ぎると、インスタンスのGPU稼働率はゼロに張り付いた。

データセンターの冷却ファンだけが、空虚な640GBのVRAMに向けて夜通し回転していた。

これは算力不足の問題ではない。典型的なキャパシティ設計の事故である。

社内オフィス向けの小規模用途であれば、妥当な代替案はいくらでもあった。

単一のL4やA10Gインスタンスを借りれば、1時間あたり1ドルから1.5ドル程度で済む。

そちらのほうが遥かに賢明だったのではないか。

当然そうである。

あるいは商用APIを呼び出し、消費したトークン分だけ支払えば、月額数百ドルで十分収まったはずだ。

8基のH100を稼働させるのは、蚊を叩くために超大型大砲を持ち出すような愚挙だった。

クラウド事業者が親切にダウングレードを促してくれるだろうか。

促してくれるはずがない。

手痛い授業料を支払った私は、クラウド環境を即座に破棄し、自席の足元に検証用ハードウェアを引き入れた。

## 2. 電気代だけの比較を拒否する：ローカル作業環境の完全なTCO帳簿

ローカル推論が語られる際、世間では不誠実な比較が横行している。家庭用電気代だけを取り出して高額なクラウド請求書とぶつけるやり方だ。

本物のエンジニアリングにおいて、ハードウェア自作のコストは電気代にとどまらない。

資産の減価償却、ネットワーク回線、バックアップ体制、そして日常の保守工数すべてが総保有コストTCOに含まれる。

電気代だけを比べるのは自己欺瞞ではないか。

まったくその通りである。

デスク下のテスト環境を引き出し、実ハードウェアの資産価格を精査する：
- 主力アクセラレータ：MSI RTX 4060 Ti 16GB、購入費2,850元。標準の4060は8GBしかなく、16GBを確保するには4060 Tiが必須である；
- ホスト母体：中古B650ベアボーン筐体と32GBメモリ、購入費1,300元；
- 補助ノード：Mac mini M4 24GBユニファイドメモリ、政府補助適用後で4,100元；
- 固定資産の初期投資総額：2850 + 1300 + 4100 = 8,250元整。

このハードウェア固定資産を一般的な36ヶ月で均等減価償却する：
`8250 ÷ 36 ≒ 月額229.17元`。

動かせない確定支出である。

次に実際の消費電力を計測する。

コンセントに高精度の電力ロガーを接続した。

RTX 4060 TiホストがQwen 2.5 7Bのフル推論を実行中の瞬間消費電力は約162Wで安定し、待機時は42Wだった。

日中8時間をフル推論、残り16時間を待機と仮定する：
1日の総消費電力量は：`0.162 × 8 + 0.042 × 16 ≒ 1.968 kWh`。

民生電力単価を1kWhあたり0.65元として計算すると、1日あたりの電気代は1.28元、30日換算で約38.4元となる。

補助のMac miniの待機消費電力約8元を加えると、電力コストは月額47元未満に収まる。

最後に運用周辺設備と保守予備費を加算する：
- 600Wの家庭用無停電電源装置UPS、月額減価償却15元；
- ギガビットLANポートと毎日の自動差分バックアップ体制、月額20元。バックアップを削る人間がいるだろうか。障害時に責任を取れない；
- 週30分のログ確認に要するエンジニア保守工数の按分、月額50元。

これらを合算する：
`ハードウェア償却229元 + 電気代47元 + 周辺設備35元 + 保守予備50元 = 月間総TCO 約361元`。

公有クラウドの単一インスタンス契約で数千元、クラスタで数万元が飛ぶことと対照的である。

外部向けの突発的な百万規模アクセスを捌く必要がない社内用途であれば、この帳簿は極めて説得力がある。

## 3. モデル選定の真実：なぜ9割の業務に70Bの巨体は不要なのか

多くのチームがクラウド利用料に縛られる原因は、70Bや数千億のMoEを採用しなければ業務に耐えないと思い込む固定観念にある。

日常のオフィス業務で毎日難解な数学オリンピックを解く必要があるだろうか。

必要ない。

私たちはコード生成、契約書条項の抽出、複数往復の顧客対応に関して社内でブラインド比較テストを実施した。

実測データは以下の通りである：

| モデル規格と量子化設定 | ファイル容量 | 最低VRAM要件 | 実測生成スループット | 指令遵守精度 |
| :--- | :--- | :--- | :--- | :--- |
| **Qwen 2.5 7B Instruct Q4_K_M** | 4.68 GB | 6.5 GB VRAM | 38.5 tokens/s | 94.2% |
| **Qwen 2.5 14B Instruct Q4_K_M** | 9.24 GB | 12.0 GB VRAM | 24.2 tokens/s | 96.8% |
| **Qwen 2.5 32B Instruct Q4_K_M** | 19.8 GB | 24.0 GB VRAM または統合メモリ | 12.8 tokens/s | 97.5% |
| **Llama 3.3 70B Instruct Q4_K_M** | 42.5 GB | 48.0 GB デュアルGPU構成 | 6.4 tokens/s | 98.1% |

第1行と第4行の比較に着目してほしい：
適切なQ4量子化を施した7Bモデルは、容量5GB未満で安価なグラフィックカードに丸ごと収まり、秒間40トークン近くで出力し、指令遵守率は94.2%に達する。

70Bに引き上げたところで、遵守率の向上は4ポイント未満にすぎない。

それに対して機材費は10倍に跳ね上がり、生成速度は秒間数文字にまで落ち込む。

画面の前で点滅するカーソルを眺めながら利用者が苛立つだけだ。

めったに発生しない特殊な例外処理のためだけに巨大な虚栄の維持費を払い続けるのは、エンジニアリングとして割に合わない。

## 4. ローカル展開の実践：RTX 4060 Tiとllama.cppによる高速起動

Ubuntu 24.04環境において、軽量な推論基盤としてllama.cppを構築する。

まず対象GPUのCUDAアーキテクチャに最適化してソースからビルドする：

```bash
# GPUドライバとCUDAランタイムの状態確認
nvidia-smi

# ソースコードを取得しCUDAバックエンドを有効化してコンパイル
git clone https://github.com/ggml-org/llama.cpp.git
cd llama.cpp
cmake -B build -DGGML_CUDA=ON
cmake --build build --config Release -j8
```

続いて公式に量子化されたGGUF形式ウェイトを取得する：

```bash
# huggingface-cliを用いてmodelsディレクトリに保存
huggingface-cli download Qwen/Qwen2.5-7B-Instruct-GGUF qwen2.5-7b-instruct-q4_k_m.gguf --local-dir ./models
```

ローカル推論サーバデーモンを立ち上げる：

```bash
# Flash Attentionと複数スロットを指定して起動
./build/bin/llama-server \
  -m ./models/qwen2.5-7b-instruct-q4_k_m.gguf \
  --port 8080 \
  --host 0.0.0.0 \
  -ngl 99 \
  -c 32768 \
  -fa \
  --cache-type-k q4_0 \
  --cache-type-v q4_0 \
  -np 4
```

指定した各起動フラグの意図は以下の通りである：
- `-ngl 99` 全28レイヤーをRTX 4060 Tiの16GB VRAMに完全オフロードする；
- `-c 32768` 単一セッションの最大コンテキスト長を32kトークンまで拡張する；
- `-fa` Flash Attentionを強制有効化し中間テンソルの過剰確保を防ぐ；
- `--cache-type-k q4_0` および `--cache-type-v q4_0` KVキャッシュを4bitに圧縮する；
- `-np 4` 社内複数クライアントからの並行処理を受け付けるため4スロットを確保する。

ターミナルから疎通とスループットを検証する：

```bash
curl http://localhost:8080/v1/chat/completions \
  -H "Content-Type: application/json" \
  -d '{
    "model": "qwen2.5-7b-instruct",
    "messages": [
      {"role": "system", "content": "あなたはLinux性能トラブルシューティングの専門家です。"},
      {"role": "user", "content": "ページフォルトとSwapスラッシングの回避手順を解説してください。"}
    ],
    "temperature": 0.2
  }'
```

単一接続における最初のトークン到達時間は約170ミリ秒、その後の生成流速は秒間38.6トークンで安定した。

自席のローカル環境でこのレスポンスが得られれば、日常業務に不足はない。

## 5. トラブルシューティングの教訓：GQAキャッシュ計算の落とし穴とOOM分析

メモリ調整の過程で、私も典型的な理論計算の失敗に直面した。

### 5.1 クエリヘッド数でキャッシュを計算した誤算

検証初日、同僚が持ち込んだ長大な契約書を流し込んだ途端、画面にVRAM枯渇のエラーが出現した：

```text
CUDA error: out of memory
  current allocated: 15.38 GB, max allocated: 15.82 GB
  failed to allocate 256.00 MB for KV Cache tensor
Aborted - core dumped
```

私は当初、Qwen 2.5 7Bの28個のアテンションヘッドすべてがキャッシュを保持すると勘違いし、トークンあたり392KB、32kで12GBに達すると誤認した。

しかしリポジトリ内の `config.json` を再確認して設計を理解した。

Qwen 2.5 7BはGQA【Grouped Query Attention】を採用している：
- `num_attention_heads = 28` クエリヘッド数；
- `num_key_value_heads = 4` 実際のKVキャッシュヘッド数；
- `head_dim = 128` 単一ヘッドの次元数；
- `num_hidden_layers = 28` 総レイヤー数。

半精度FP16における単一トークンの物理KVキャッシュサイズは以下の通りである：
`2 × 28 × 4 × 128 × 2 バイト = 57,344 バイト ≒ 56 KB`。

1セッションあたり32kコンテキストを満載しても、理論値はわずか：
`32000 × 56 KB ≒ 1.75 GB`。

単一セッションが1.75GBで済むのに、なぜ16GBのVRAMが吹き飛んだのか。

チューニングなしで4スロットの同時並行をGPUが受け止めきれるだろうか。

答えは起動引数の `-np 4` にあった。

Flash AttentionもKV量子化も適用しない状態では、4スロット分のFP16プールが事前に確保され：
`4 × 1.75 GB = 7.0 GB`。

7GBのKVキャッシュにモデルウェイト4.68GB、CUDAランタイム、そして非連続なメモリ断片化が重なり、総要求量は瞬時に15.5GBを超えた。

解決策は起動コマンドに記した2つの指定である：
第1に `-fa` を付与してFlash Attentionを有効化すること；
第2に `--cache-type-k q4_0 --cache-type-v q4_0` を指定すること。

KeyとValueを4bit化することでトークンあたり約14KBまで圧縮され、4スロットが32kをフル消費しても合計1.75GB前後に収まる。

常駐メモリ使用量は8.2GB近辺に落ち着いた。

複数セッションの並行時もメモリ不足は二度と起きていない。

安堵した。

### 5.2 Swap過熱によるNVMeサーマルスロットリングの断崖

もう一つの手痛い失敗は、薄型ノートPCでの検証だった。

16GBメモリのノートPC上でSwapを利用して32Bモデルを無理に動かした際、最初の数分間は秒間8トークンで推移した。

しかし4分が経過した頃、生成速度は突如秒間0.5文字へと暴落し、画面の操作が完全に固まった。

ストレージのセンサ情報を確認した：

```bash
# NVMeコントローラの稼働温度を確認
smartctl -a /dev/nvme0n1 | grep Temperature
```

表示されたコントローラ温度は76度に達していた。

76度の高温でSSDを焼き続けたい人間などいるだろうか。

金属ヒートシンクもファン冷却もない薄型筐体では、過剰なページングによって75度の限界温度に即座に衝突する。

ドライブのファームウェアが素子の破損を防ぐため強制スロットリングを発動し、IOPS性能が8割以上削減されたのだ。

放熱設計のない軽量端末で仮想メモリを使って巨大モデルを動かすのは、ハードウェアを痛めるだけで実用性がない。

## 6. 現実的な選定基準と意思決定チェックリスト

一連のパラメータとコストの検証を経て、私たちは3つの明確な技術的境界線に辿り着いた：

- **第1の基準：8GBメモリの薄型ノートや旧式PC**
  3Bまたは7BのQ4モデルに徹すること。コンテキスト長は4096トークン以内に制限する。SSDのSwapで32Bモデルを動かすというネットの宣伝を信じてはならない。過熱による速度低下で実用性が損なわれる。

- **第2の基準：12GBから16GBのVRAMを備えたデスクトップ**
  RTX 4060 Ti 16GBがコストパフォーマンスの最適解である。7Bまたは14Bモデルに量子化キャッシュとFlash Attentionを組み合わせることで、5人から15人規模のチームの日常需要を月額TCO 400元【約8,000円】未満で賄える。

- **第3の基準：公有クラウドと商用APIを迷わず選ぶべき条件**
  顧客契約で99.99%のSLA稼働率を保証する場合、千件単位の突発的なアクセス集中が予測される場合、あるいは厳格なデータコンプライアンスと複数拠点の冗長化が必須な場合は、迷わず大手の公有クラウドや公式エンタープライズAPIを採用すべきである。エッジの自作は予測可能な社内コストを抑制し、クラウドは弾力性とリスクヘッジを担う。

GPU算力の逼迫は巨額のマネーが動くマクロの構造劇であり、銀行口座から引き落とされる毎月の請求書こそが個々の現実である。

同時アクセス数、実際のコンテキスト長、機材の減価償却、そして消費電力を正確に算出できれば、焦燥感に振り回されない冷静な構成が見えてくるはずだ。
