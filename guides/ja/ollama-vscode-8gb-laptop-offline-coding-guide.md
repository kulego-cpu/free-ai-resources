# 8GBノートPCで快適に動かすローカルAIコーディング：OllamaとVS Codeの4つの実践チューニング

多くの開発者が、長年愛用してきた旧型ノートPCやメモリ8GBのモバイルPCを手元に残しています。クラウドAIサービスが普及した現代においても、飛行機内や移動中などのオフライン環境で即座に動作し、機密コードやプライベート設定を外部に一切送信しないローカル開発アシスタントの需要は高まる一方です。

しかし、ContinueやTwinnyといったVS Code拡張機能を導入したものの、期待通りに動作せず挫折するケースが後を絶ちません。

一般的なチュートリアルの指示に従って7B以上のモデルを導入すると、8GB環境では数秒から数十秒にわたる激しいシステムフリーズが発生します。ファンが激しく回転し、マウスカーソルが飛び、エディタ全体が無応答状態に陥ります。

その理由は極めて明快です。8GBの物理メモリを搭載した環境では、最新のOSとVS Code本体および言語サーバの起動だけで3GBから4GBが消費されます。そこに4.5GB以上のメモリを要する7Bモデルを無理に読み込ませると、物理メモリの上限を一瞬で突破し、ディスクスワップの嵐が発生します。開発を効率化するためのツールが、システム全体を停止させる原因になってしまうのです。

Redditのr/ollamaコミュニティにおいて、開発者volkin115をはじめとする検証グループが、8GBノートPCをターゲットとした実戦的なチューニング検証を公開しました。適切な4つの調整方針を適用することで、高価なハードウェアを用意せずとも、8GBマシン上で滑らかなローカルコード補完を実現できることが実証されています。

---

## 一、 根本原因：なぜ8GB環境でローカルAIがフリーズするのか

調整を始める前に、ハードウェアのメモリ収支を整理します。

| 稼働コンポーネント | 通常メモリ消費量 | 空き物理メモリ | 動作状態 |
| :--- | :--- | :--- | :--- |
| OSおよび基本バックグラウンド処理 | 約2.2GBから2.8GB | 約5.5GB | 軽快に動作 |
| VS Code本体および各種言語サーバ | 約1.2GBから1.8GB | 約3.7GBから4.2GB | エディタ準備完了 |
| 7B 4-bit量子化モデルとコンテキスト | 約4.8GBが必要 | 大幅なマイナス超過 | 激しいスワップと数十秒の停止 |
| 3B 4-bit量子化モデルとコンテキスト | 約1.9GBから2.2GB | 約1.5GBから2.0GBの余裕 | スワップ皆無で極めて安定 |

7Bモデルの強制読み込みは、メモリ不足によるディスク読み書き待ちを誘発します。CPUがディスクI/O待ちで占有されることこそが、エディタ停止の直接の引き金です。

---

## 二、 対策1：7Bへの執着を捨て、3Bの俊敏性を活かす

パラメータ数が7B未満の小型モデルは実用に耐えないという先入観が存在しますが、実際の検証結果はその思い込みを覆しました。

単一関数の補完、リファクタリング、正規表現の作成、型注釈の付与、ドキュメント生成といった日常業務において、コーディング特化型のqwen2.5-coder:3bは極めて高い構文精度と高速な生成能力を発揮します。

```bash
ollama run qwen2.5-coder:3b
```

### 3Bモデルが8GBマシンに最適な理由

* **極めてコンパクトなメモリ消費**：4-bit量子化された3Bモデルはメモリ上で約1.9GBしか消費せず、OSやエディタの領域を圧迫しません。
* **低遅延な初期トークン出力**：低消費電力な旧型CPU環境でも、補完キー入力後ほぼミリ秒単位でストリーミング生成が始まります。
* **十分な構文理解力**：Python、TypeScript、JavaScript、Goなどの主要言語において、基本アルゴリズムや標準ライブラリの利用に関する補完精度は実務水準に達しています。

極端な省電力環境では1.5Bモデルという選択肢もありますが、構文の論理的一貫性と精度のバランスにおいて、3Bは現時点で8GB環境の最良の選択肢です。

## 三、 対策2：コンテキストの制限と2048トークン上限の徹底

Ollamaの/api/chatエンドポイントと連携する際、過去の会話履歴をすべて送信する構成は低スペック機において致命的な遅延をもたらします。

### KVキャッシュ膨張が引き起こす遅延の連鎖

コンテキストが肥大化すると、モデル内部のキー・バリューキャッシュのメモリ消費が急増します。さらに重要な点として、非力なCPUでは長文プロンプトの初期評価計算にかかる時間が急激に跳ね上がります。

コミュニティの検証担当UpbeatMad氏らの比較テストによると、コンテキスト長を無制限のまま放置して8Kなどに達した場合、1回の補完にかかる初期待ち時間は12秒から15秒以上に跳ね上がります。一方でコンテキスト上限を2048トークンに固定すると、1回のリクエストあたり約10秒の待ち時間が短縮され、軽快な操作感が復活します。

### スライディングウィンドウの実装原則

* **上限の厳格設定**：推論パラメータのnum_ctxを2048に明示的に固定します。
* **履歴の絞り込み**：対話型インターフェースではシステム設定と直近3から4往復の会話のみを保持し、古い履歴は破棄します。
* **インライン補完の最適化**：行補完ではカーソル周辺の上方50行および下方20行程度を切り出して渡し、不要な文脈を遮断します。

## 四、 対策3：対象を単一のアクティブファイルに限定する

昨今のAI開発ツールでは、ワークスペース全体を走査して依存関係を読み解く巨大な自律型エージェント構成が注目を集めています。しかし、このような重厚なアーキテクチャを8GBノートPCに持ち込むと深刻な処理遅延を招きます。

### 単一ファイル集中がもたらす効果

小型のローカルモデルに無関係なファイル内容を大量に与えると、アテンションが分散し、存在しない変数や別ファイルの仕様を誤認する幻覚現象が発生しやすくなります。

さらに、ローカルマシン上でファイル全走査やベクトルインデックス作成を並行動作させると、エディタ本来の構文解析処理に悪影響を及ぼします。

### 明確な作業境界の維持

軽量な拡張機能においては、単一ファイル志向を徹底することが推奨されます。

* 編集中のアクティブファイルのみをコンテキストとして参照します。
* 差分の生成は現在選択されている関数や特定ブロックに限定します。
* 境界を明確に保つことで、小型モデルであっても高い的確性で補完結果を返せます。

## 五、 対策4：柔軟なタグ前方一致による接続エラー防止

独自拡張の開発やクライアント設定において、モデル名を厳密な文字列として固定記述してしまうミスが散見されます。

### 固定文字列が招く脆さ

量子化レベルの変更やOllamaによるタグ定義の微細な更新があった場合、/api/tagsによる厳密一致の確認に失敗し、モデルが見つからないという警告が出て動作が停止します。

### 柔軟な正規表現および部分一致

クライアント側の照合ロジックでは、qwen2.5-coderという名称と3bというモデル規模が含まれていれば接続を許可するような柔軟な判定を導入します。

この設計により、環境移行やアップデート時のメンテナンス負担を大幅に削減できます。

## 六、 8GB環境向け推奨パラメータ一覧

スムーズな運用のための標準推奨設定は以下の通りです。

| 設定項目 | 推奨値 | 調整の目的 |
| :--- | :--- | :--- |
| model | qwen2.5-coder:3b | 優れた文法精度と2GB程度の省メモリを両立 |
| num_ctx | 2048 | プロンプト評価の遅延を防ぎ待ち時間を大幅短縮 |
| num_predict | 256から512 | 短いコード補完に集中させ暴走を防止 |
| num_thread | 4または物理コア数 | スレッド競合による過熱とクロック低下を抑制 |
| temperature | 0.2 | 出力のブレを抑え決定論的で堅牢なコードを生成 |

## 七、 なぜ無料クラウド全盛期にローカル3Bを使うのか

無料枠を提供するクラウド型コード補完サービスが多数存在する中で、あえて手元の8GBノートPCでローカル3Bモデルを稼働させる意義はどこにあるのでしょうか。

その理由は明確です。

* **完全なコードの主権と機密保護**：企業の機密プロジェクトやプライベートな設定ファイルの内容が外部に流出する懸念は皆無です。
* **ネットワークからの完全な独立**：オフライン環境、新幹線や機内、電波の届かない場所でも、エディタを開けば常にAIが伴走します。
* **利用制限や中断の排除**：利用回数制限、予期せぬ課金発生、APIゲートウェイの障害や規約改定によるサービス停止のリスクから完全に解放されます。

限られたハードウェア資源と真摯に向き合い、適切なチューニングによって実用的な価値を引き出すことこそ、エンジニアリング本来の醍醐味と言えます。
