私たちの開発チームは昨年、Devin を実務検証しました。

使い心地は率直に言って素晴らしかったです。Slack でタスクを投げれば、自律的に環境を立ち上げ、テストを実行し、Pull Request を自動で提出してくれました。

もう元には戻れないとすら感じました。

しかし更新の時期が来て、財務担当者が私のデスクにやって来ました。

1アカウントあたり月額 500 ドル。

10 人のチームなら年間 6 万ドルです。この予算があれば RTX 4090 搭載のハイエンドワークステーションを 2 台買ってもお釣りが来ます。

私は自問しました。その法外な費用の正体はどこにあるのか。

使い捨てサンドボックス仮想マシンの計算コストなのか、それとも単にプロプライエタリな囲い込みによる席料なのか。

納得がいきませんでした。結局、私たちは自作環境の構築に舵を切りました。

費用だけでなく、セキュリティとガバナンスの懸念はさらに深刻でした。

機密のビジネスロジックを含むコードがすべて閉じたクラウドへ吸い込まれていきます。どの物理サーバーで動いているのか、依存パッケージのインストールスクリプトが特権昇格していないか、実行ログはいつまで保存されるのか。

誰一人として明確に答えられません。

オープンソース界隈でも代替の試みはありました。初期の OpenDevin や各種のローカルシェルスクリプトを試しましたが、実用段階で致命的な欠陥を露呈しました。

ホスト環境の設定を破壊してしまうか、ダイヤルアップ接続並みに応答が重いかのどちらかでした。

昨日 GitHub で公開された OpenComputer は、極めて地に足のついた解法を提示しています。

リポジトリは `https://github.com/diggerhq/opencomputer`、ライセンスは Apache 2.0 です。

セルフホストの仮想マシン上で、Devin 比 3.3 倍の速度で PR を作成できると謳っています。

このアーキテクチャはどのような構造なのか、単なる宣伝文句なのか。ゲートウェイのソースコードを精査し、ローカル仮想マシン上で実際に動作検証を行いました。

## 1. 従来のクラウド型 Agent はなぜ耐えがたいほど遅かったのか？

エージェントの最適化に取り組むエンジニアは、よくある心理的罠に陥りがちです。

AI が遅いのは、LLM のトークン生成速度が足りないからだと錯覚してしまうのです。

私もかつてこの落とし穴にはまりました。

応答を速くしようと、あえて最も軽量なモデルを繋ぎました。しかし簡単なテストコマンドを投げても、ターミナルのカーソルは相変わらず 30 秒以上停止したままでした。

真のボトルネックはモデルの推論時間だったのでしょうか。

全く違いました。

実際のコーディング作業フローにおいて、最も時間を浪費しているのは環境のコールドスタートとネットワークを介した I/O 往復です。

従来のクラウド型エージェントの標準フローは極めて重厚でした。

まずタスクを受信します。

次にリモートのオブジェクトストレージからスナップショットを引き出します。

新しいマイクロ仮想マシンをコールドブートします。

公開ネットワーク越しにリポジトリを再クローンします。

依存関係のインストールスクリプトを走らせます。

コードを修正し、最後に環境状態を固めてクラウドへ再アップロードします。

この一連の儀式だけで、2 分から 3 分が消え去ります。

10 秒以上待たされる環境で、エンジニアの集中力は保てるでしょうか。

無理です。

人間のコンテキストは容易に霧散します。ブラウザの別タブを見たりチャットに返信したりした瞬間、脳内の設計図は消滅します。

我に返ったときには、エージェントは間違った前提のもとで突っ走り、7 つも 8 つものファイルを破壊しています。

その散らかった部屋を誰が片付けるのでしょうか。

結局すべてを捨ててやり直すしかありません。

OpenComputer チームはこの本質的欠陥を指摘しました。即時性を失ったエージェントは、放置型のバッチジョブに成り下がるしかありません。

ラップトップ上の Claude Code に匹敵する軽快な追従性を得るには、実行環境をディスクの最も近くへ引き戻す必要があります。

## 2. 逆方向ゲートウェイ Calvin：インバウンドポートを完全に封鎖できる理由

セルフホスト型エージェントを社内プライベートクラウドやオンプレミスサーバーに配備する際、最大の壁となるのはセキュリティ部門の承認です。

外部への攻撃対象領域をどう抑え込むのか。

多くのオープンソースツールは、外部からの Webhook 通知を受けるために、ファイアウォールに受信ポートの穴を開けるか、トンネリングツールを要求します。

インターネットに向けてポートを開放すれば、不正スキャンや権限昇格のリスクを避けられません。

パブリック IP が必須だという思い込みに、私も長年囚われていました。

アウトバウンドの常時接続アプローチを試して初めて気づきました。コラボレーションの本質はメッセージを受信できることであり、外部から直接探索可能であることではありません。

この二つは過去 10 年間混同されてきました。

OpenComputer の中核ゲートウェイは Calvin と呼ばれます。

設計思想は明快です。ホスト仮想マシンはインバウンドの受信ポートを一切開放しません。

システムは逆方向 WebSocket によるアウトバウンド常時接続を採用しています。

オーケストレーション層は Cloudflare Workers と Durable Objects 上に構築され、軽量なメッセージ中継とルーティングのみを担当します。

内部ネットワークにある仮想マシンは、起動時に自発的に Cloudflare エッジノードへアウトバウンド接続を張ります。

開発者が Slack チャンネルで `@Computer` をメンションすると、Slack の Webhook は Cloudflare Workers へ到達します。

Workers は事前確立された逆方向 WebSocket パイプを通じて、社内仮想マシン上の Calvin ゲートウェイへ指示を滑り込ませます。

ファイアウォール側で必要なのは、外向きの 443 ポート通信を許可することだけです。

VPC のプライベートサブネット、NAT 配下の社内 LAN、固定パブリック IP を持たない古いマシンであっても、ミリ秒単位で外部タスクに応答できます。

外部の攻撃者は、インターネット上をいくらスキャンしてもリッスン中のポートを一切発見できません。

## 3. rootless Podman 隔離：単機ローカル NVMe の極限スループット

指示が仮想マシンの内部に届いた後、次の難題が生じます。コード実行環境をどう安全に隔離するか。

ベアメタルホスト上で直接コードを走らせるわけにはいきません。

自律エージェントが誤って破壊的なシェルコマンドを実行すれば、OS 全体が機能停止に追い込まれます。

しかし重厚なハイパーバイザー仮想化では遅すぎます。

OpenComputer が選択したのは rootless Podman コンテナでした。

Slack のスレッドごとに、非特権コンテナインスタンスが 1 対 1 で立ち上がります。

注目すべき設計上の工夫が三点あります。

一点目は非特権ユーザー空間での実行です。コンテナ内のプロセスがエスケープを起こしたとしても、ホスト上では権限のない一般ユーザーに過ぎず、カーネルの変更や別セッションのデータへの干渉は不可能です。

二点目は状態書き込みを物理ディスク優先にした点です。コード解析やビルドの中間ファイルは、仮想マシンのローカル高速 NVMe SSD へ直接読み書きされ、低速なネットワーク共有ファイルシステムをバイパスします。

三点目は Git 増量スナップショットによる二重の安全弁です。作業区切りごとにローカル Git へ自動コミットされ、非同期でリモート同期されます。

Ubuntu 24.04 マシンで実測したところ、タスク受領からコンテナのマウント完了までにかかった時間はわずか 380 ミリ秒前後でした。

ベースイメージ層が事前キャッシュされているため、起動に数十秒を要する従来のクラウド仮想マシンとは比較にならない俊敏さを見せます。

```bash
# Podman rootless ランタイムを指定して Calvin ゲートウェイを起動
calvin-gateway --runtime podman --isolation rootless --max-concurrent 4
```

## 4. 実戦シナリオ検証：最小再現プロジェクトでのバグ修正フロー

アーキテクチャ図を眺めるだけでは不十分です。

Node の典型的な非同期メモリリーク調査シナリオを用いて実測を行いました。

外部ネットワークのブレを排除するため、イベントリスナーとキャッシュ破棄ルーチンを含む最小再現プロジェクトを準備しました。

ベースイメージを事前キャッシュしたコンテナ環境に対象リポジトリを認可し、Slack のテストチャンネルに指示を投稿しました。

```text
@Computer 継続的な負荷テスト中にメモリが解放されず増加し続けます。leak_detector.js を調査して修正し、npm test をパスさせて PR を作成してください。
```

送信をクリックしました。

約 4 秒後、Slack チャンネルに `@Computer` から応答カードが届きました。

なぜこれほど速いのか。

ベースとなる Node ランタイムと依存パッケージ群が Podman のボリューム内にすでに温められていたからです。外部からの再ダウンロードをスキップし、即座にブランチをチェックアウトして静的解析に着手しました。

約 15 秒後、スレッド内に調査スタックトレースが共有されました。

`leak_detector.js` 内のグローバルイベントリスナーがコネクション切断時に解除されず、クロージャ参照がヒープメモリに残留している事実を正確に突き止めました。

提示された差分は的確で、`cleanup` フックに関数解除の処理が追記されていました。

さらに十数秒後、自動実行された `npm test` が全てグリーンとなり、GitHub 上に整った Pull Request のリンクが自動生成されました。

タスク発注から完了まで、所要時間は約 35 秒でした。

## 5. 3.3 倍高速化の測定条件と真実の比較

公式発表では Devin 比 3.3 倍の高速化を主張しています。

測定条件を明らかにしない数字には何の意味もありません。

私の検証環境は、8 コア 16GB メモリの ThinkCentre デスクトップに 1TB の NVMe SSD を換装し、社内の 500Mbps 光回線に接続した構成です。`expressjs/express` や `node-fetch/node-fetch` などテストスイートの整った成熟プロジェクトから 4 つの修正課題を選び、それぞれ 3 回測定して中央値を算出しました。

OpenComputer 側は、Slack へのタスク投入から PR 生成までの中央値が 56 秒、最初のプッシュ応答は 24 秒でした。

Devin 側は、全工程の完了に 185 秒を要しました。

ただし、この 3.3 倍という倍率に対して私は一定の留保を抱いています。

Devin はクローズドソース製品であり、背後でどのモデル階層が動いていたのか、起動前のイメージ事前ウォームアップが存在したのかを外部から固定して検証することはできません。

テスト当日、私たちの回線でも一度だけ偶発的なジッターが発生し、その異常回は無効として再測定しました。

厳密に言えば、3.3 倍という差は私の特定のハードウェアと良好なネットワーク条件下で観測された数値であり、上限寄りに出ている可能性が高いです。

実務上の真の性能差は 2 倍前後とみるのが妥当でしょう。ローカル NVMe によるビルド時間の短縮効果は、ネットワーク品質が劣る環境ほど際立ち、超高速な専用線環境では差が縮小するはずです。

## 6. 直面した三つの障壁と導入の見極め基準

セルフホストの運用は決して平坦な道ではありません。公式ドキュメントに明記されていない落とし穴に、私は一通り足を取られました。

第一の壁は、現時点で Slack に強く依存している点です。

Calvin ゲートウェイは Slack を前提に作られています。チームの主たるコミュニケーションツールが Discord、Teams、LINE WORKS などの場合、現時点で公式の変換アダプターは存在しません。自前でイベント中継層を書く必要があります。

第二の壁は、rootless Podman のホスト権限設定の複雑さです。

Ubuntu などの環境で rootless Podman を安定動作させるには、`subuid` と `subgid` のマッピング範囲を適切に割り振り、cgroups v2 を有効化しておく必要があります。

初動テスト時、AppArmor のセキュリティポリシーに引っかかり、ボリュームマウント時にデバイスノードが見つからないエラーを吐いて停止しました。設定を整理するのに 30 分以上を費やしました。

```bash
# 実行ユーザーに十分な従属UID範囲を割り当てる設定
sudo usermod --add-subuids 100000-165535 --add-subgids 100000-165535 devin-agent
# ログアウト後もエージェントの常駐プロセスを維持する設定
sudo loginctl enable-linger devin-agent
```

第三の壁は、モデル推論のトークン費用は依然として自己負担である点です。

OpenComputer が解決するのはエージェントの実行サンドボックス、協調通知、自動化パイプラインです。モデルの推論枠が無償で提供されるわけではありません。

設定ファイルには Anthropic や OpenAI の API キー、あるいは互換性のある推論エンドポイントを登録する必要があります。

エージェントがテスト失敗と自己修復のループを際限なく繰り返せば、トークン消費の請求書は確実に膨らみます。

浮くのは高額なソフトウェア席料であって、物理的な推論コストではありません。

モデル選定の失敗は私も身をもって経験しました。以前、安価な小型モデルでバグ修正を試みた際、生成されたコードの差分を 3 回見直しても怪しさが抜けず、結局ロールバックしました。

推論能力が Claude 3.5 Sonnet、GPT-4o、DeepSeek V3 といった上位層に達していない場合、コードを触らせるほど混迷を深める結果になります。

ブラックボックスを解体し、コードと実行環境を手元のインフラへ引き戻すことは、確かなコスト削減と主権奪還をもたらします。

しかし、コンテナ権限、回線品質、モデルの費用管理に至るまで、すべての技術的ディテールを引き受ける覚悟が開発チームに求められます。
