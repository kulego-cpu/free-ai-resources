# 断片化した記憶からの脱却：Project Moah と Syro で構築する完全ローカル複数 Agent 協調ワークステーション

16GB メモリのノートパソコンで 2 つから 3 つのコマンドライン型コーディングエージェントを同時に動かすと、過酷な現実に直面します。

ファンが高速回転を始めます。熱による抑制が発生します。ターミナルのカーソル移動にも目に見える遅延が生じます。手軽さを求めて重い統合開発環境のウィンドウを複数開き、それぞれのターミナルでエージェントを走らせる開発者は少なくありません。このやり方はマシンの応答性を急速に損ないます。

推論が深まるにつれて、背後の Chromium レンダリングプロセスや各種拡張機能が 3.8GB を超える物理メモリを消費します。スワップ領域の書き込みが激増し、ストレージの負荷が赤信号に達します。複数エージェントの並行処理には、高価な業務機が不可欠なのでしょうか。

ハードウェアの制約以上に深刻なのが、エージェント同士の完全な認知的分断です。

左側の Claude Code は認証モジュールを再構築し、トークン検証をセッション方式からステートレス署名へと変更しました。一方、右側の Codex は注文処理のテストを書いており、直前の設計変更を知らないため、廃止予定の古いセッション mock を大量に生成します。双方がブラックボックスの中で作業を進めた結果、Git マージ時に 47 箇所の構文衝突が発生します。

従来は共有 Markdown をリポジトリに配置する手法が一般的でした。しかし平文ファイルは単なる静的な文字列です。数千行に及ぶ長大な文書を毎回読み直せば、コンテキスト消費が激増します。

進退両難。断片的な記憶と高額なリソース消費の板挟みから、どう脱出すべきでしょうか。

本質的な解法は 2 つあります。デスクトップ側は重い外枠を完全に削ぎ落とし、知識共有側は重み付きグラフ構造で因果関係を循環させる必要があります。

## 脱 Electron の執念：Syro による Worktree ネイティブ編成

エージェントごとのターミナル管理を効率化するため、高機能な GUI ツールを求める声は多くあります。既存の管理ツールはどのような構造でしょうか。

大半は Webview のラッパーアプリです。常駐するだけで数百メガバイトを消費し、複数動かせばフリーズします。より軽量な選択肢は存在します。

オープンソースコミュニティにおいて、開発者 osdodo は極限の無駄削ぎを追求した Syro を公開しました。

GitHub リポジトリ：
https://github.com/osdodo/syro

このツールは Electron、Chromium、Node の実行基盤を完全に排除しています。Rust 言語と GPUI 描画ライブラリで直接構築されています。高速エディタでおなじみの GPUI は、OS の描画機能と直接通信します。起動時間はどれくらいでしょうか。わずか 0.2 秒未満です。待機時のメモリ消費量は約 48MB に収まります。

なぜ Syro は複数エージェントの協調作業に適しているのでしょうか。

その理由は、Git Worktree との完全な結合にあります。従来、複数ブランチの並行作業では checkout による切り替えや複数リポジトリの複製が行われていました。未コミットの変更が衝突し、ディスク容量が無駄になります。そのような苦労を続ける必要があるでしょうか。

Syro の手法は簡潔です。1 つのベースリポジトリを保ちながら、機能ごとに Worktree ディレクトリを並列展開します。Syro の単一ウィンドウ内で、各 Worktree が独立したコンテキストを持つワークスペースとして機能します。

画面上には専用ターミナル、ファイルツリー、差分表示、履歴ログが横並びで表示されます。状態を示す 3 つの表示灯が用意されています：

- 実行中：エージェントが推論、ファイル変更、テストを実行している状態；
- 待機中：現在のタスクが完了し、CPU とメモリが休止している状態；
- 入力待ち：機微な変更操作の前に開発者の承認を求めている状態。

3 つの表示灯が一列に並びます。一目見れば、どの工位が動いていて、どの工位がキーボード入力を待っているか分かります。

ただし、現実の制約も冷静に把握すべきです。GitHub のスター数は現在 1 つにとどまる個人開発ツールです。macOS 15.1 以上に最適化されており、Windows 用の事前ビルド済みバイナリは未提供です。外部高解像度ディスプレイ接続時に描画不整合で落ちる事例や、数千行のログ出力で画面が 1.5 秒止まる現象が確認されています。設定変更時は再起動が必要です。macOS 以外の環境では、tmux と Git Worktree スクリプトの併用が確実な代替案となります。

## 知識グラフの循環：Project Moah が解決する散乱メモ問題

物理的な分離が整った後、複数エージェント間でどのように同一の知識基盤を共有するのでしょうか。

平文メモの致命的な弱点は、因果関係の欠落です。例えばテーブルのあるカラムが非推奨になった場合、直接の理由は 1 週間前のシャーディング決定であり、間接の影響は複数エンドポイントでの削除義務です。通常の文字列検索でこの連鎖を追跡するのは困難です。

開発者 Namache が公開した Project Moah は、この課題を解決するローカル脳です：
https://github.com/Namache/project-moah

MIT ライセンスで配布され、ローカル環境で動作し、標準 MCP 経由で各エージェントと接続します。データはローカルの SQLite に保存され、Windows、Debian、Ubuntu、Fedora に対応します。

ヘブライ語で Moah は脳を意味します。平文フォルダを廃止し、ネットワーク構造のトポロジーに再編成します：

```text
Project Moah グラフ伝播の計算ルール：

1. 棚階層の活性化：
   Knowledge > Architecture > Authentication
   現在のタスクに関連する棚のみが目覚め、無関係なノードは休眠します。

2. 多段ホップ減衰：
   1 ホップの関連度 = 基準リンク重み × 確信度
   n ホップの関連度 = 基準リンク重み × 確信度 × 0.85 の n-1 乗

3. 独立経路の確率加算：
   異なる 2 つの経路が同一ルールを指し、確率が各 0.5 の場合：
   統合関連度 = 1 - (1 - 0.5) × (1 - 0.5) = 0.75
   理論値は 1.0 に無限に近づきますが、完全な 100% は付与されません。

4. 動的リンク重みの加減：
   テスト通過に寄与した採用：重み +0.08
   構文エラーの原因となった採用：重み -0.08
   30 日間未参照の接続：自動的に減衰し除外されます。
```

知識は木構造の棚に配置されます。支払い処理を書く際、音声ドライバの規則は読み込まれません。無関係な棚が休眠しているため、コンテキストを無駄に消費しません。

多段減衰アルゴリズムは整然と機能します。直接の隣接ノードは重みを維持しますが、段数を重ねるごとに 0.85 の乗数で関連度が下がります。

複数の推論経路が同一ルールに行き着いた場合、独立確率モデルで統合されます。2 系統が 0.5 を示した際の統合値は 0.75 です。なぜ 1.0 満点にしないのでしょうか。確率グラフに絶対的な真理は存在しないため、余裕を持たせることで過度の確信による暴走を防ぎます。

総合関連度が 0.20 を下回ったノードは、コンテキストから自動排除されます。

トンプソン抽出も実用性に優れます。探索を有効にすると、過去の強リンクだけでなく、低確率で周辺ノードも探索します。

実機検証で具体的な重み変動を確認しました。Claude Code が非互換の署名検証アルゴリズムを導入し、テストで 14 件の AssertionError が発生しました。Moah は失敗を検知し、該当ノードの重みを 0.08 減点して 0.50 から 0.42 に下げました。その後 Codex が旧版互換の記述を採用してテストを通したため、重みが 0.08 加点され 0.58 に上昇しました。この仕組みは、固定的な文書よりも開発現場の実態に即しています。

## 暴走の阻止：ルール固定化とチェックポイント

共有脳があっても、エージェントが問題を起こす可能性はあるでしょうか。

権限外の変更は起こり得ます。エージェントの厄介な問題は、コードが書けないことではなく、基盤ルールを勝手に書き換えてしまう点です。

例外処理は共通インターセプターを通す原則を定めていても、型エラーに直面したエージェントが勝手に基底例外クラスを書き換えてエラーを握りつぶすことがあります。

Project Moah は人間に最終決定権を残しています。それがルールの固定化です。

重要な設計方針は、登録時に固定指定が可能です。固定されたノードに対して、接続エージェントは読み取り権限しか持ちません。勝手な変更はできません。

変更を望む場合、MCP 経由で人間の受信箱へ改定案を提出する義務があります。

責任区分は明瞭です。理由、利点、影響範囲を提出し、人間が画面で承認して初めてノードが更新されます。

チェックポイント機能も作業の引き継ぎを円滑にします。

商用モデルの枠が枯渇した際、新しいターミナルで最初から前提を説明し直す作業は無駄です。

Moah では各段階をチェックポイントとして保存できます。未完了タスク、決定事項、知識グラフがまとめて保管されます。

主力モデルが基盤を作った後、軽量オープンモデルが同一チェックポイントから再開し、前工程の説明なしでテスト作成を継続できます。

## 実装手順：MCP 接続から Worktree 2 面運用まで

構築作業は単純で、15 分ほどで完了します。16GB メモリの標準的な PC を前提にします。

第 1 手順：Project Moah デーモンを起動します。バックグラウンドで常駐し、ローカルで MCP を公開します。エージェントの設定ファイルに追記します：

```json
{
  "mcpServers": {
    "project-moah": {
      "command": "moah",
      "args": ["serve", "--local-db", "/Users/cool/data/moah-brain.db"]
    }
  }
}
```

設定後、起動時にグラフ DB が検出され、照会や提案の機能が有効になります。

第 2 手順：Git コマンドで独立ディレクトリを切ります：

```bash
git worktree add ../freeai-cache-layer feature/cache-opt
git worktree add ../freeai-e2e-suite feature/e2e-test
```

基盤リポジトリは共通です。親階層に 2 つのフォルダが作成され、コミット履歴を共有しながらブランチが分離されます。

第 3 手順：Syro の画面を開き、左右の画面に上記 2 つの Worktree を割り当てます。左に Claude Code、右に Codex を配置します。

2 エージェント並行時の負荷はどうでしょうか。

計測結果は明快です。Syro 本体の常駐メモリは 48MB 未満です。重いレンダリング層を排したため、両者でビルドを走らせてもマシン全体のメモリ使用量は 9.2GB 以内に収まります。

左のエージェントがキャッシュ仕様を変更すると、Moah に決定事項が記録されます。右のエージェントは 0.85 の減衰計算を通じて新仕様を検知し、テストを自動調整します。人間による書類移動は不要です。

## 限界と実態：思考停止のための魔法ではない

この構成は万能でしょうか。

そうではありません。無料の近道は存在しません。現実的な注意点を確認しておく必要があります。

第 1 に、初期データの導入負荷です。空のデータベースでは、減衰計算も棚の選別も機能しません。開始時に人間が 15 件以上の設計原則を登録する必要があります。

第 2 に、グラフ保守の規律です。関数の細かな修正まで無差別に登録させると、データベースは短期間で乱雑化します。信頼度が下がったノードの整理作業は不可欠です。

ツールの進化は生産性を高めるためのものであり、人間が設計判断を放棄するためのものではありません。Syro はハードウェア資源を守り、Project Moah は複数ブランチ間の整合性を守ります。

この 2 つを守ることで、自律エージェントの編隊は真価を発揮します。多角的な並行開発において、手元の環境は本番負荷に耐えられる状態にあるでしょうか。
