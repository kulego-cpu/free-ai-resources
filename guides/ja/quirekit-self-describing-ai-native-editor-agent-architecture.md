# 50個のTiptap拡張をFunction Callingに詰め込んで成功率48%に終わった理由：QuireKitのlist/explain/call移行記録

AI搭載型のリッチテキストエディタを開発する現場では、多くのチームが同じ壁に突き当たります。

エディタにAI copilotを組み込み、自動で文字装飾や表の追加、見出しの階層調整を行わせたいと考えたとき、真っ先に思い浮かぶのは既存プラグインをそのままFunction CallingのToolとして公開することです。

太字設定に関数を1つ。

表の挿入に関数を1つ。

見出しレベルの変更に関数をもう1つ。

エディタに数十種類の拡張機能があれば、システムプロンプトの中に律儀に数十個のTool Schemaを並べていくことになります。

私たちも最初はまったく同じ方法を採用しました。

しかし、実際の文書編集操作を模した100件のテストセットを実行したところ、その完了率は予想をはるかに下回るものでした。

100件中、正常に処理を完了できたのはわずか48件にとどまり、総合通過率は48%でした。

モデルはエラーとパラメータ再試行のループに囚われ、1タスクあたり平均4.2往復もの通信を消費しました。

さらに致命的だったのは、27件ものタスクにおいて、API側が正常終了を返しているにもかかわらずエディタ上のDOMが一切更新されないサイレント障害が発生したことです。

オープンソースプロジェクトQuireKitの作者がV2EXの投稿t/1253992で指摘していたのは、まさにこの構造的欠陥でした。

彼らはプロンプトを肥大化させる代わりに、極めて規律ある自己記述型メタケーパビリティアーキテクチャを提案していました。

私たちはその設計思想に基づき、ローカルテスト環境の通信層を再設計しました。

同一の100件の複合タスクを実行した結果、タスク通過数は48件から98件へと跳ね上がり、平均往復回数は1.1回に収束しました。

## 1. ツール平置型アーキテクチャが抱える3大欠陥：エラーログと根本原因の分析

通信層の刷新がなぜ劇的な効果を生むのかを理解するには、従来の平置型アプローチがリッチテキストエンジン内部のどこで破綻していたのかを整理する必要があります。

最新のリッチテキストエディタの基盤は、厳格な抽象構文木状態マシンです。

ProseMirrorもそうです。

Tiptapもそうです。

Lexicalも同様です。

単なるHTML文字列の結合でも、Markdownテキストの流し込みでもありません。

数十個の操作インターフェースを無防備に大規模言語モデルへ渡すと、通信経路は3つの壁に激突します。

### 欠陥1：プロンプトコンテキストの肥大化とツールの誤選択

機能が充実したエディタでは、ノードとマークの拡張機能は容易に50種類を超えます：

- ブロック要素：段落、レベル1から6までの見出し、箇条書きリスト、番号付きリスト、タスクリスト、引用ブロック、コードブロック
- インラインマーク：太字、斜体、取り消し線、下線、インラインコード、文字色、ハイライト色、外部リンク
- 複合コンポーネント：データ表、行の結合、列の分割、画像埋め込み、グラフカード、折りたたみパネル、数式ブロック

これらをすべてOpenAI形式のTools定義に落とし込むと、リクエストごとに2,400トークン以上が消費されます。

50個もの関数Schemaが並ぶと、モデルの注意力は平坦なパラメータ群に分散してしまいます。

50個の選択肢の中からモデルが常に正しい関数を選び出せるでしょうか？

極めて困難です。私たちの検証ログでも、DeepSeek Flashにおいて頻繁な選択ブレが確認されました：

第3節の末尾にある表へ新規行を追加するよう指示したにもかかわらず、モデルは行挿入ではなく`table.splitCell`を呼び出したり、文字のハイライト指定に対してセルの背景塗りつぶしを選択してしまいました。

### 欠陥2：二重シリアライズによるメタデータの欠落

50個のSchemaを維持する負担から逃れるため、一部のチームは妥協案を選びます：

モデルにMarkdown形式で出力させ、フロントエンド側でHTMLへ変換してエディタに流し込む方式です。

この方法は一見手軽に見えますが、本番運用においては重大な不整合を招きます。

Markdownの表現力は極めて限定的です。

複数行にまたがるセルの結合は表現できません。

ブロックノードに紐づく業務IDや権限ロックも表現できません。

共同編集時のカーソル位置も維持できません。

データフローは二重の変換工程を経由することになります：

```text
ドキュメントAST状態マシン -> 簡易Markdownへ書き出し -> モデルがテキスト書き換え -> 正規表現でHTMLへ変換 -> ProseMirrorへ流し込みAST再構築
```

この二重の変換工程を通ることで、原稿が持っていたメタデータはすべて失われます。

段落の一節を太字にするだけの操作が、結果としてドキュメント全体の再パースを引き起こし、下部にあった複雑な入れ子表がバラバラのプレーンテキストに成り下がるケースが頻発します。

### 欠陥3：1次元座標の推測失敗とサイレント障害

テストセットで確認された27件のサイレント障害の原因は、まさに座標の扱い方にありました。

ProseMirror内部のドキュメント位置指定は、ノードタグの開閉に基づく1次元の整数値で厳密に計算されます。

段落の開始位置が12で、終了位置が48といった具合です。

大規模言語モデルがDOMツリー内部の正確な1次元整数オフセットを自力で算出できるでしょうか？

まず不可能です。モデルはDOMのバイト位置を空間的に把握しているわけではなく、確率に基づいて位置数値を推測しているに過ぎません。

モデルが表の挿入位置として120を指定したものの、実際の表ノードが84で終了していた場合、ProseMirrorの内部エンジンは即座に例外を送出します：

```text
RangeError: Position 184 out of range 0..126
    at Object.replaceRange [node_modules/prosemirror-transform/dist/index.js:1042:15]
    at handleLegacyToolCall [src/editor/legacy-bridge.ts:68:12]
```

さらに厄介なのはフロントエンド側のラッパー実装です。

画面のクラッシュを防ぐため、多くの開発者は外側に包括的なtry-catchを配置し、結果として正常終了レスポンスを返してしまいます：

```text
POST /api/editor/dispatch 200 OK
Response: {"status": 200, "message": "command executed successfully"}
```

APIは200を返し、チャット画面ではモデルが完了を告げているにもかかわらず、エディタ上のキャンバスには何の変化も起きていません。

このような仮死状態をユーザーが許容できるでしょうか？私たちの検証では、これが実に27回も発生していました。

## 2. QuireKitの自己記述プロトコル：50個のツールを3つのメタ指令に集約

QuireKitのアプローチはモデル自体のファインチューニングではなく、ツール層の通信プロトコルそのものの再定義です。

システムプロンプトに常駐していた50個以上の静的Schemaをすべて取り払い、モデルへ公開する窓口を3つのメタ指令のみに絞り込みます：

- `list`：現在のエディタキャンバスで有効化されている機能一覧を動的に探索
- `explain`：対象のアクションに必要なパラメータ構造と制約境界をオンデマンドで取得
- `call`：基盤の状態マシンへアトミックトランザクションを発行し、構造化ログを受信

```text
呼び出しのライフサイクル：
1. 編集意図の受信 -> listを発行して有効な機能を低トークンで探索
2. 対象アクションの特定 -> explainを発行してパラメータ契約をオンデマンド取得
3. ペイロードの組み立て -> callを発行してProseMirrorトランザクションを直結
```

### ステップ1：listによる機能一覧の動的探索

システムプロンプト内には個別プラグインの定義を一切記載せず、統一された通信プロトコルの書式のみを保持します。

編集操作が必要になった際、モデルはまずエディタ環境に対して探索リクエストを送信します：

```bash
cli api list --target editor --json
```

エディタ環境は現在マウントされている拡張機能のサマリ一覧を返します：

```json
{
  "capabilities": [
    {"id": "doc.structure", "desc": "ドキュメントのアウトラインおよびASTブロック構造を照会"},
    {"id": "heading.set", "desc": "指定ブロックまたは選択範囲の見出しレベルを設定"},
    {"id": "table.insertRow", "desc": "指定テーブルインデックスまたは現在の末尾に空行を追加"},
    {"id": "callout.create", "desc": "指定位置に警告またはメモ用のコールアウトカードを挿入"}
  ]
}
```

この軽量インデックスには機能IDと短い説明文のみが含まれます。

60個以上のプラグインが存在する場合でも、リスト全体のトークン消費量は180トークン未満に収まります。

プロンプトの静的フットプリントは90%以上削減され、モデルは整理されたディレクトリと対面するため選択ミスが大幅に抑制されます。

### ステップ2：explainによるパラメータ契約のオンデマンド取得

カタログの中から`table.insertRow`が適していると判断したモデルは、次にそのアクション専用の仕様を取得します：

```bash
cli api explain table.insertRow --target editor --json
```

エディタ側はその機能に対応するSchemaのみを返します：

```json
{
  "capability": "table.insertRow",
  "parameters": {
    "type": "object",
    "properties": {
      "tableIndex": {
        "type": "integer",
        "description": "ドキュメント内におけるテーブルの0始まりの出現順インデックス"
      },
      "position": {
        "type": "string",
        "enum": ["before", "after"],
        "default": "after"
      },
      "targetRow": {
        "type": "integer",
        "description": "基準となる行番号、未指定時は末尾に追加"
      }
    },
    "required": ["tableIndex"]
  },
  "constraints": {
    "requiresFocus": false,
    "transactionType": "atomic"
  }
}
```

1回の通信で必要となる1つのSchemaのみを読み込むため、モデルのコンテキストは高度に集中します。

私たちの検証ログにおいて、このステップで不正なフィールドが生成された事例は確認されませんでした。

### ステップ3：callによるネイティブトランザクションの直接発行

仕様を取得したモデルは、パラメータを構築して直接実行を指示します：

```bash
cli api call table.insertRow --target editor --input '{"tableIndex": 0, "position": "after", "targetRow": 2}' --json
```

エディタ内部では、QuireKitがこの入力をProseMirrorのネイティブトランザクションへマッピングします：

```ts
// 実装イメージ：import、ヘルパー関数、型定義は省略
export function handleInsertRowCommand(
  editor: Editor,
  input: InsertRowInput
): CommandResult {
  const { tableIndex, position, targetRow } = input;
  const state = editor.state;

  const tableNode = findTableNodeByIndex(state.doc, tableIndex);
  if (!tableNode) {
    return {
      success: false,
      errorCode: "ERR_TABLE_NOT_FOUND",
      errorMsg: `インデックス ${tableIndex} のテーブルノードが見つかりません`,
    };
  }

  let tr = state.tr;
  try {
    tr = addRowAtPosition(tr, tableNode.pos, targetRow, position);
    editor.view.dispatch(tr);

    return {
      success: true,
      affectedRange: [tableNode.pos, tableNode.pos + tableNode.node.nodeSize],
      docVersion: editor.state.version,
    };
  } catch (err: unknown) {
    const message = err instanceof Error ? err.message : String(err);
    return {
      success: false,
      errorCode: "ERR_TRANSACTION_FAILED",
      errorMsg: `トランザクション実行エラー：${message}`,
    };
  }
}
```

テーブルの指定インデックスが存在しない場合、コードは即座に中断し、`ERR_TABLE_NOT_FOUND`を返します。

エラーレスポンスにはドキュメント内に存在するテーブル総数と有効なインデックス範囲が明示されます。

明確な診断情報を受け取ったモデルは、偽りの成功をユーザーへ報告することなく、その場でパラメータを自己修正して再試行できます。

## 3. ベンチマークテストセットの設計と実測データ

両アプローチの差異を公平に評価するため、私たちは100件の複合編集タスクからなるテストセットを構築しました。

この100件のテストケースはどのように設計されたのでしょうか？

実際のプロダクト開発で多発する難所を網羅するため、5つのカテゴリに各20件ずつ均等配分しました：

- カテゴリA：複数階層のネストリストのインデント調整とタスク完了状態の一括切り替え——20件
- カテゴリB：複数セクションにまたがる要約抽出と警告コールアウトカードの自動生成——20件
- カテゴリC：3行4列テーブルのデータ補完、動的計算式の修正、ヘッダー行の固定——20件
- カテゴリD：インラインマークの付与と外部業務エンティティIDのメタデータバインド——20件
- カテゴリE：長大な技術文書におけるクロスリファレンスリンクの自動更新とアンカー修復——20件

評価モデルにはDeepSeek Flashを採用し、temperatureを0.2に固定、タスクごとに最大5回までのリトライを許容しました。

合否判定にはヘッドレスブラウザによる検証を導入し、ProseMirrorのASTノード構造が期待通りに変異していることを確認しました。

検証結果の比較データは以下の通りです：

```text
========================================================================================
ベンチマーク指標          ツール平置方式 (50+ Schemas)     QuireKit自己記述型プロトコル
========================================================================================
テスト総ケース数          100 件                          100 件
タスク成功数              48 件                           98 件
総合タスク通過率          48.0%                           98.0%
平均対話往復回数          4.2 往復 / タスク               1.1 往復 / タスク
タスク平均消費トークン    3,840 トークン                  620 トークン
平均エンドツーエンド応答  6.8 秒 (P95)                    1.4 秒 (P95)
サイレント障害発生数      27 件                           0 件 (本検証では未観測)
新規拡張の追加メンテナンス 手動でPromptとSchemaを保守     完全ゼロ (リフレクションにより自動公開)
========================================================================================
```

平置方式で通過した48件のうち、31件は複数回のエラー再試行を余儀なくされ、P95応答時間は6.8秒まで悪化しました。

一方、自己記述型プロトコルは平均消費トークンを3,840から620へと大幅に削減しました。

モデルが初回の試行で正確なアクションとパラメータを選択できるため、通過した98件の大多数がわずか1往復で処理を完結させています。

## 4. 現場のエンジニアリング収支：実測レイテンシと移行コスト

自己記述型アーキテクチャの導入にはトレードオフが存在します。

### 収支1：複数往復に伴うネットワーク遅延とクライアントキャッシュの効果

explainによる追加の往復通信によってレイテンシは悪化しないでしょうか？

未キャッシュのマイナーな操作を呼び出す際、事前のスキーマ照会によるオーバーヘッドは避けられません。

ローカルネットワーク環境でDeepSeekのAPIを計測したところ、HTTPの1往復にかかる物理時間は平均約120ミリ秒でした。

事前のexplainを挟むと、タスク完了までに約240ミリ秒の追加待機が発生します。

この遅延を抑えるため、フロントエンドのAgent層にインメモリキャッシュを導入しました。

初期化時に、段落、太字、レベル2見出し、箇条書きリスト、表の行追加という5つの高頻度アクションのSchemaをメモリに常駐させます。

100件のテスト実行において、これら5つの高頻度操作のキャッシュヒット率は76%に達しました。

キャッシュにヒットした場合はexplainをスキップして即座にcallを実行するため、P95応答時間は1.4秒から1.1秒へとさらに短縮されました。

### 収支2：基盤状態マシンの規律とレガシーコードの移行工数

innerHTMLによる直接書き換えを行っている既存システムから容易に移行できるでしょうか？

できません。このアーキテクチャは、エディタ基盤がアトミックなトランザクション処理とリフレクション機能を備えていることを前提としています。

既存システムにおける改修コストの試算は以下の通りです：

- アウトライン探索用の読み取り専用APIの実装：約1人日
- 主要5操作に対するProseMirrorトランザクションの境界保護実装：約2人日
- テーブルおよび複合入れ子コンポーネントのエラー捕捉とロールバック機構：約3から5人日

DOMを直接書き換える古い実装が残っている場合、そのまま自己記述型アーキテクチャを適用することは不可能です。

DOM操作を厳格に管理されたトランザクションへ置き換えて初めて、安定した運用が可能になります。

## 5. 移行ロードマップと実践的な推奨手順

プロンプトの肥大化やツールの選択ブレに悩むチームに向けて、3段階の段階的移行を提案します：

第1段階：プロンプトの削減。

プロンプトから長大なTool定義を一括で削除し、読み取り専用の`doc.structure`のみを残します。モデルにまず文書全体の構造を把握させます。

第2段階：探索ゲートウェイの構築。

`list`と`explain`のルートを実装し、見出しやリスト、太字などの基本操作のJSON Schemaを独立した定義ファイルへと切り出します。

第3段階：トランザクションのエラー処理の徹底。

バックエンドで例外をもみ消すのをやめ、範囲外の指定やノードの欠損に対して明確なエラーコードを返すように設計します。

モデルが自律的にAPI仕様を参照し、エラー発生時に正確なスタックトレースを受け取れるようになって初めて、AI copilotは不安定なプロトタイプから頼れる本番ツールへと進化します。

数十個のツールをプロンプトに詰め込んで運を天に任せるよりも、自己記述型の明確なAPIゲートウェイを提供する方が、はるかに健全なAgent開発と言えるのではないでしょうか。
