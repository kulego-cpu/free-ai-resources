# Qwen 4.0と5.0もオープンソースを継続：云栖大会で公式がデマを一蹴

先週金曜日の午後、私たちのインフラチームはサーバルームで急遽フェイルオーバー対策会議を開きました。

発端は技術コミュニティで出回った1枚のスクリーンショットです。Qwen4がアリババ最後のオープンソースモデルとなり、今後は商用クラウドAPIへ全面移行するという内容でした。

公式の一次ソースはありません。フォーラムの投稿とチャットの画像だけです。

それでも最悪の事態を想定して検証を進めざるを得ませんでした。

私たちの社内クラスタではRTX 4090デュアル搭載ノードが3台、64GBユニファイドメモリのMac Studioが2台稼働しています。稼働しているのはQwen2.5 72Bの微調整派生モデルです。コードのセマンティック検索、社内ナレッジベース検索、単体テスト自動生成パイプラインのすべてがこの基盤に依存しています。

上流のモデル供給が止まれば、単にモデル名を変更するだけでなく、推論スケジューリングの根本的な再構築が必要になります。

当時、私たちは代替候補であるLlama 3.3 70Bの量子化ブランチを手元に落とし、長文コンテキストでのコード補完テストの準備を進めていました。

そして本日午前、云栖大会のメインステージから最新情報が届きました。

通義千問チームの公式スライドにはっきり示されたコミットメントは明白でした：今後もQwen 4.0およびQwen 5.0のオープンソース公開を堅持する。

移行計画の緊急度はひとまず下げられます。しかし、実機での検証作業はここからが本番です。

---

## 1. なぜ事前にデュアル4090での負荷検証が必要だったのか

運用エンジニアが最も恐れるのは、予告なしの上流サプライチェーンの遮断です。

ソフトウェア開発は基盤ライブラリに依存します。ローカルでの大規模モデル運用は、オープンウェイトの継続的な提供に完全に依存しています。

近年のAI業界の変遷を振り返れば、初期に完全オープンを謳いながら成熟後に重みを閉ざした組織や、最高峰のフラッグシップモデルを有料APIの背後に囲い込んだ前例は珍しくありません。

オンプレミスで運用するチームにとって、口頭での噂話だけで安心できるはずがありません。

先週、私たちはRTX 4090デュアル構成のマシンでQwen2.5 72BのAWQ 4-bit版を負荷テストしました。

起動コマンドは以下の通りです：

```bash
python3 -m vllm.entrypoints.openai.api_server \
  --model Qwen/Qwen2.5-72B-Instruct-AWQ \
  --quantization awq \
  --tensor-parallel-size 2 \
  --max-model-len 32768 \
  --gpu-memory-utilization 0.95
```

24GBメモリのグラフィックボード2枚で合計48GBの容量です。静的AWQ重みを展開した時点で約38.2GBが消費されます。動的KVキャッシュに残された領域はわずか9.8GBです。

同時リクエストを8セッションまで引き上げ、各コンテキストが8Kトークンに達した瞬間、VRAM使用量は46.8GBへ急上昇しました。

この時、p99デコード遅延は単一セッション時の24ミリ秒から176ミリ秒へ跳ね上がり、GPU間のPCIe 4.0バス通信に明らかな待ち行列が発生しました。

もしQwen4がオープンソースで提供されず、商用クラウドAPIへの移行を余儀なくされれば、月額トークン費用の高騰だけに留まりません。社内のコミットログが外部ネットワークを流れるため、セキュリティコンプライアンス審査で即座に却下されます。

オープンソースの継続は、私たちにとって単なる理念の話ではありません。実務ラインを動かし続けられるかどうかの死活問題です。

## 2. 公開されたエコシステム規模と検証すべき実務項目

カンファレンス会場では最新の運用指標も共有されました：

- 全世界累計モデルダウンロード数：30億回突破
- 公式自主開発オープンソースモデル：460種類以上
- コミュニティ派生モデル総数：30万件以上

規模の大きさは疑いようがありません。しかし、現場のインフラ担当にとって、数字の羅列だけで手放しに喜ぶわけにはいきません。

私たちが注目している実務上の検証ポイントは3点です：

第1に、7Bおよび14Bモデルを24GBの単一GPU上でAWQ量子化した後、32Kコンテキストを保持できるKVキャッシュ領域が確保できるか。

第2に、32Bモデルを2枚のカードでテンソル並列分割した際、PCIe 4.0バスを経由することでどれだけのスループット低下が生じるか。

第3に、高負荷な多セッション並列環境下で、72Bモデルが長文コンテキスト処理中にメモリ溢れを起こさないか。

壇上でオープンソース方針が示された以上、次に確認すべきはHuggingFaceやGitHubに実際のファイルとライセンス文書が届く時期です。

## 3. コミュニティの冷静な視点：物理的支配と残された疑問

スライド発表の後、コミュニティの反応は分かれました。

セルフホスト派は安堵しました。最大の利点は物理的な主権です。

重みファイルは手元のNVMe SSDに保管され、推論データが社内ネットワークの外に出ることはありません。トークンごとの従量課金も発生せず、サービス提供者が深夜にフィルタリング設定を変更して正当なコードが遮断される心配も無用です。

しかし、現場経験の豊富なエンジニアたちからは本質的な疑問が提示されています：

第1に、モデルサイズの切り分けです。全寸法のフラッグシップモデルが公開されるのか、それとも軽量な蒸留版のみにとどまるのか。

もし超巨大なMoEモデルが商用クラウド専用として囲い込まれるのであれば、オープンソースの価値は大きく低下します。

第2に、提供スケジュールのタイムラグです。商用APIの提供開始とオープンウェイトの一般公開との間に、数週間から数ヶ月の保護期間が設定されるのかどうか。

これらの疑問に対して、現時点で公式な回答文書は出ていません。基調講演の発表だけで納得するのではなく、リポジトリの配備完了まで見届ける必要があります。

## 4. 主観評価を排した5つの客観的検証基準

私たちは曖昧な主観的スコアリングを行わず、Qwen4の提供状況を以下の5つの明確な基準で評価します：

1. **ライセンスの完全性**：商用利用可能なApache 2.0が継続されるか、あるいは利用制限条項が追加されるか。
2. **全パラメータの網羅性**：主力サイズやMoEアーキテクチャが全量公開されるか、軽量モデルに限定されるか。
3. **同日リリースの有無**：クラウドAPIの提供開始と同時にオープンリポジトリへ重みが配置されるか。
4. **チェックサムの整合性**：公式にsha256ハッシュリストが提供され、分割ファイルが欠損なく検証できるか。
5. **推論エンジンの対応速度**：vLLM、SGLang、llama.cppの公式メインブランチが48時間以内に互換PRを取り込めるか。

## 5. 今後の追跡計画

云栖大会で公式方針が明言されたため、Llama 3.3への緊急移行作業は一時保留とします。

今後の実務工程は明確です：

1. GitHubの公式リポジトリにおけるリリース動向とプルリクエストを継続監視する。
2. 重み公開後、直ちにRTX 4090デュアル環境で上記のvLLM負荷テストを実施し、メモリ推移、初回応答時間、スループットを計測する。
3. llama.cppにおけるGGUFフォーマットの量子化損失を検証し、一般のワークステーションで再現可能な設定手順をまとめる。

すべては実際の重みファイルの到着をもって判断します。詳細な検証ログと設定スクリプトは準備が整い次第速やかに公開します。
