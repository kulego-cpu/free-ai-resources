パラメータを真似る前に、まず手元のハードウェアの実情をご覧ください。

検証環境は単体RTX 4090、ドライババージョン550.54.14、CUDA 12.4です。

ローカルで27Bクラスの高密度モデルを公式の標準16ビット浮動小数点で動かそうとすると、最初のステップで即座にクラッシュします。

静的ウェイトだけで54GBを消費します。

民生用GPUではモデルのロードすら完了せず、ターミナルが異常終了します。

標準的なQ4_K_Mの4ビット整数量子化を選んだ場合はどうでしょうか。

ファイルサイズは約16.8GBまで縮小し、一見24GBの物理VRAMに収まるように見えます。

しかし、コンテキスト長を32k以上に広げたり長文ドキュメントを入力したりした途端、確保メモリが急激に跳ね上がります。

画面が2秒ほど固まり、見慣れたエラーログが表示されます：

```text
CUDA error: out of memory
current device: 0, total: 24564 MB, allocated: 23890 MB, free: 674 MB
cudaMalloc failed: out of memory
```

プロセスは即座に強制終了します。

なぜ27Bモデルの長文脈推論はコンシューマー向けカードにとってこれほど厳しいのでしょうか。

多くの人が静的ウェイトばかりを気にして、動的なKey-Value [KV] キャッシュの急激なメモリ消費を軽視しているためです。

128k [131,072トークン] という高負荷環境では、非量子化のFP16 KVキャッシュ単体だけで18GB前後の専用VRAMを消費します。

静的ウェイト16.8GBにキャッシュ18GBを加えると、必要なメモリは34GBを超えます。24GBの単一カードで耐えられるはずがありません。

今回の実機テストでは、容量14.9GBの `Qwen3.8-27B-UD-Q4_K_XL.gguf` を使用しました。ランタイムにはcommit `b3842` でビルドした `llama.cpp` を用いています。

単一の24GBグラフィックボードで131,072コンテキストは本当に走るのでしょうか。

結論から言えば、動作は可能ですが、無条件に快適に動くわけではありません。

検証中にOOMクラッシュを2度経験し、マイクロバッチ設定を3回変更してようやく安定稼働に漕ぎ着けました。

以下に、計算リソースの収支、実際のログ、そして必要となった性能面での妥協点を詳細に記録します。

---

## メモリ収支の計算：なぜ以前は24GBで128kがクラッシュしたのか

トラブルシューティングには、VRAMが実際にどこで消費されているかを把握する必要があります。

ローカル環境での推論時、物理VRAMは主に3つのブロックに分かれます：

第1ブロックは、ファイルサイズに直結するモデルの静的ウェイトです。

第2ブロックは、文脈長に応じて線形に増加する動的KV Cacheプールです。

第3ブロックは、CUDAランタイム、Flash Attentionの計算ワークスペース、そしてメモリの断片化領域です。

多くのエンジニアが第3ブロックの存在を見落としています。

長大な文脈を処理する際、アテンション演算用の作業領域として、128k環境下では1.5GB〜2.5GB程度のバッファがあらかじめ必要となります。

Qwen3.8-27Bは64層のアテンション層、隠れ層次元5120のGQAアーキテクチャを採用しています。

キャッシュを量子化せず、標準の16ビット浮動小数点でKVキャッシュを保持した場合：

トークンが1つ進むごとに固定バイトの文脈メモリが消費されます。

大まかな計算では、1,000トークンごとに約145MBのVRAMが消費されます。

131,072トークンをフルに埋めると、過去の対話履歴を記憶するだけで18.5GBものVRAMを占有します。

計算の内訳を振り返ると：

標準Q4_K_Mの静的ウェイトが16.8GB。

動的キャッシュ18.5GBを加えると合計35.3GB。

ここには計算ワークスペースの容量が含まれていません。

単一の24GBカードにこの処理を投げると、コンテキストが40kを超えた段階で確実にメモリ不足に陥ります。

24GBの枠内に収めるには、静的ウェイトと動的キャッシュの両方を削る必要があります。

## 第1ステップ：UD-Q4_K_XLによるウェイトの軽量化

全層を一律に量子化すると、モデルの品質に不必要な劣化が生じます。

大規模言語モデルの内部ネットワーク層は、層ごとに重要度が大きく異なります。

入力埋め込み層やアテンション機構のクエリ射影行列のビットを削ると、論理的推論力や指示追従性が急激に低下します。

一方で中間層から深層にかけての前饋ネットワークは、強めに量子化しても出力への影響が比較的小さく抑えられます。

UD-Q4_K_XLは非一様な重要度スライシングを採用しています：

アテンションの中核重みは5ビット〜6ビットの混合精度を維持し、重要度の低い前饋ネットワーク層は勾配スコアに基づいてQ3やQ4レベルまで選択的に圧縮します。

RTX 4090での実測フットプリント：

| 量子化形式 | ファイル容量 | ロード後の純占有量 | 稼働ステータスと文脈上限 |
| :--- | :--- | :--- | :--- |
| 原生 FP16 | 54.2 GB | ロード不可 | 起動時に即時OOMクラッシュ |
| 従来型 Q4_K_M | 16.8 GB | 約 17.5 GB | 35k付近でメモリ警告 |
| 動的 UD-Q4_K_XL | 14.9 GB | 約 15.6 GB | キャッシュ用に約8GBを確保 |
| 極限量化 UD-IQ3_XXS | 11.2 GB | 約 11.9 GB | 16GB環境向け最低限の回避策 |

UD-Q4_K_XLにより、ベースVRAM占有量を17.5GBから15.6GBへ引き下げることができました。

削り出せた約2GBの余裕が、長文コンテキスト処理を成立させるための命綱となります。

---

## 第2ステップ：KVキャッシュを16ビットから8ビットへ圧縮

静的ウェイトを15.6GBまで落としても、18.5GBのFP16キャッシュをそのまま搭載することはできません。

ここでllama.cppの量子化フラグ `--cache-type-k` と `--cache-type-v` を変更します。

デフォルト値はどちらも `f16` です。

起動時に `q8_0` を指定し、KeyとValueを対称8ビット整数へ変換します。

`q8_0` は万能の魔法ではありません。

1要素あたりの消費を2バイトから1バイトへ圧縮する計算になりますが、実際にはスケール係数、アライメント、アテンション用ワークスペースの追加メモリが必要です。

131,072トークンの実測において、`q8_0` 有効時のKVキャッシュ占有量は18.5GBから約9.4GBへと減少しました。完全に50%減となるわけではありません。

それでも9.4GBであれば、全体のメモリ枠内で計算が成立する範囲に入ってきます。

なぜさらに極端な `q4_0` キャッシュを選ばないのでしょうか。

比較検証を行った結果、4ビットキャッシュではコンテキストが64kを超えたあたりから、特定の変数名や数値列に対する検索再現率が明確に落ち始めました。

一方 `q8_0` では長文検索の精度が安定しており、FP16との記憶性能差はほとんど体感されませんでした。

したがって、実用的な主力構成としては `q8_0` が推奨されます。

## 実機クラッシュ記録：なぜ計算上収まるはずなのにOOMが起きたのか

15.6GBのウェイトに9.4GBのキャッシュを加えると約25GBとなり、依然として24GBを超過します。

ここに多くの人が陥る落とし穴があります。

超長文コンテキストを読み込む際、通常の大きなバッチサイズで処理を実行すると、瞬間的なメモリスパイクが発生します。

最初に実行したコマンドは以下の通りです：

```bash
./build/bin/llama-server \
  --model ./models/qwen3.8-27b-UD-Q4_K_XL.gguf \
  --n-gpu-layers 99 \
  --ctx-size 131072 \
  --cache-type-k q8_0 \
  --cache-type-v q8_0 \
  --flash-attn on \
  --batch-size 2048 \
  --ubatch-size 512
```

長文を入力したところ、プロンプトのプリフィル処理中にファンが高速回転し、ターミナルに `CUDA error: out of memory` が出力されて強制終了しました。

原因は `--ubatch-size 512` にありました。

128kの高負荷環境下では、Flash Attentionが大きなテンポラリバッファを要求します。512のマイクロバッチが瞬間的にメモリを確保したことで、残りの空きVRAMを突き破ってしまったのです。

対策として、`--ubatch-size` を512から256へ半減させました。

`nvidia-smi` で監視した結果：

総確保メモリは24,564 MBの物理上限に対し、23,210 MBで安定し、約1.3GBの安全マージンが確保されました。

ただし明確なトレードオフとして、マイクロバッチを半減させたことで、プロンプトのプリフィル処理速度は3〜4割ほど低下します。

この速度低下は受け入れるべき現実的な妥協点です。

## 速度測定：MTP投機的デコードの実効性能

メモリが安定した後、生成速度の検証に移ります。

単一の4090で27Bモデルを動かす場合、GDDR6Xのメモリ帯域幅の限界により、通常の自己回帰出力速度は毎秒13〜15トークン程度に制限されます。

Qwen3.8はネイティブなMulti-Token Prediction [MTP] 構造を備えています。

1トークンずつ順番に計算するのではなく、メインネットワークの出力と並行して、補助予測ヘッドが後続の第2・第3トークンを同時に推測します。

予測が的中すれば、そのまま確定出力として採用されます。

約3,000行のTypeScriptコード解析タスクにおける実測値：

純粋な自己回帰モード：

出力速度は約14.1トークン/秒。

MTPとFlash Attentionを併用した場合：

コードやJSONなど構文規則が明確なテキストでは、予測的中率が約6割に達し、出力速度は毎秒21.8〜24.3トークンへと向上しました。

一方で自由記述の文章生成では的中率が4割以下に低下し、毎秒17トークン程度まで減速します。

実効速度はプロンプトの決定論的性質に大きく依存します。

## 実機再現用起動構成

単体RTX 4090、Ubuntu 22.04 LTS、CUDA 12.4環境で検証したパラメータ構成です。

まず32kでテストし、`nvidia-smi` の推移を確認した上で64k、131,072へと段階的に引き上げることを推奨します。

```bash
./build/bin/llama-server \
  --model ./models/qwen3.8-27b-UD-Q4_K_XL.gguf \
  --n-gpu-layers 99 \
  --ctx-size 131072 \
  --cache-type-k q8_0 \
  --cache-type-v q8_0 \
  --flash-attn on \
  --batch-size 2048 \
  --ubatch-size 256 \
  --threads 8 \
  --host 0.0.0.0 \
  --port 8080
```

主要パラメータの意図：

`--n-gpu-layers 99`：全層をGPU VRAMへオフロードします。

`--ctx-size 131072`：128kコンテキスト領域を確保します。

`--cache-type-k q8_0` および `--cache-type-v q8_0`：8ビットKVキャッシュ圧縮を有効化します。

`--flash-attn on`：計算バッファの多重確保を防ぐための必須指定です。

`--ubatch-size 256`：メモリスパイクを防ぐ安全マージンです。

## 16GB GPU環境での運用について

RTX 4080や16GB VRAM搭載ノートPCをお使いの場合、設定のダウングレードが必要です。

モデルを容量11.2GBの `UD-IQ3_XXS` に変更します。

コンテキスト長を65,536 [64k] に制限し、KVキャッシュを `q4_0` に設定します：

```bash
./build/bin/llama-server \
  --model ./models/qwen3.8-27b-UD-IQ3_XXS.gguf \
  --n-gpu-layers 99 \
  --ctx-size 65536 \
  --cache-type-k q4_0 \
  --cache-type-v q4_0 \
  --flash-attn on \
  --ubatch-size 256 \
  --port 8080
```

総VRAM消費量は約15.1GBに収まります。長文の概要把握やドキュメント検索には十分実用的ですが、深い論理推論においては4ビット量子化よりも精度が低下します。

## まとめ

チューニング作業に魔法のような奇跡はありません。

すべては計算リソースのトレードオフです：

非重要層の精度を削ってウェイト容量を捻出する。

仮数部の微小な精度を削ってキャッシュ容量を確保する。

プリフィルの待ち時間を受け入れてOOMクラッシュを回避する。

各オプションの裏には明確な妥協が存在します。ハードウェアの空き容量を正しく把握し、実機のログを観察しながら、ご自身の環境に適したパラメータを見極めてください。
