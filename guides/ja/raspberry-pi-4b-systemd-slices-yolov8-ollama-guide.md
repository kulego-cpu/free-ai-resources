# 8GB ラズベリーパイで視覚モデルと LLM を両立：systemd slices でリアルタイム通信の揺らぎを防ぐ

省電力なエッジ機器で限界まで計算性能を引き出す際、最も警戒すべき事態は重要なリアルタイム処理に対する計算資源の枯渇です。

オープンソース海洋監視システムに組み込まれた 8GB メモリの Raspberry Pi 4B が手元にあります。このヘッドレス Debian 環境は、3 系統の主要処理を同時に稼働させています。第 1 は船舶計器から針路、水深、風速、エンジン回転数を高頻度で取得する Signal K 遠隔測定サービス。第 2 は ONNX 経由で船首カメラ映像を毎秒 5 フレームで走査する YOLOv8 nano モデル。第 3 は海事運用マニュアルをローカル検索するために Llama 3.2 1B を読み込んだ Ollama です。

このマルチタスク構成は、小型基板の計算能力を恒常的な過負荷の限界へと追い込み、負荷集中時の処理遅延を招きます。

視覚モデルのみが動作している平時は、4 コアの CPU 使用率は 50% 前後で推移し、アルミ筐体の温度は 68 度付近で踏みとどまり、熱暴走による周波数低下を辛うじて回避しています。

しかし現場作業員がブラウザから Ollama に手引書の質問を送信した瞬間、大規模モデルが多重スレッドで推論を開始し、4 つの CPU コアは即座に 100% へ張り付きます。

深刻な障害が直ちに発生します。制御画面の応答が停止します。

平滑に流れていた計器データが大幅にパケット破棄を起こし始めます。データ更新遅延は数十ミリ秒から数秒へと一気に跳ね上がり、計器パネルには通信切断のアラートが多発します。

航海中や工場内巡視において、言語モデルの応答待ちのために基礎的な計測データが途絶することは、安全管理上決して許容できない事故です。計器が停止する状況を誰が許容できるでしょうか。

8GB のラズベリーパイで画像認識とローカル言語モデルを共存させることは本当に不可能なのか。

最近、オープンソースエンジニアコミュニティから極めて実用的なシステム設計が提示されました。Linux の systemd slices 機構を利用してこの 3 重負荷の衝突を制御する手順が記録されました。

議論と検証の記録は以下の公開スレッドで確認できます：
https://www.reddit.com/r/ollama/comments/1xpeb8t/

原因を掘り下げると、従来よく用いられる CPU コア固定の手法は、計算資源全体が飽和した環境では機能しないことが判明しました。

最新の Linux カーネルが備える cgroups v2 機構を用い、厳密な資源分割を行う必要があります。

## なぜ CPUAffinity によるコア固定は完全に破綻するのか

複数の処理が CPU を奪い合う状況に直面した際、経験豊富なエンジニアほどコア固定を選択しがちです。

本プロジェクトの原著者も最初にその手法を試みました。

サービス定義ファイルに CPUAffinity を指定し、重要な Signal K 遠隔測定サービスをコア 0 へ強制的に割り当て、推論処理を残り 3 コアへ追いやろうとしました。

同時に、8GB メモリが推論処理で枯渇することを防ぐため、2GB のスワップファイルを確保し、swappiness を 10 に設定して物理メモリを実処理へ優先配分しました。

この標準的な対策によって、計器データの破棄問題は解決したでしょうか。

結果は完全な失敗でした。遅延はまったく改善しませんでした。

Ollama と YOLOv8 が全開で推論を行う際、主スレッドはコア 0 を避けますが、基底のデバイス割り込み、ディスク書き込み、タイマー、ネットワーク軟割り込みは依然として全コアを跨いで頻繁に割り込みを発生させます。

残り 3 つのコアが 100% まで使い尽くされると、OS のコンテキストスイッチ負荷が急激に跳ね上がります。

コア 0 上の遠隔測定プロセスがシステムコールを発行したり共有ロックを要求するたびに、スケジューラは他コアの資源解放を待機させられます。

キャッシュ破棄が頻発します。コンテキストスイッチ数が急増します。

コア固定はリアルタイム処理に独立した環境を提供するどころか、コア間の偏りを人為的に助長させただけでした。

4 コア全体が飽和している状態では、単一スレッドのコア固定だけでミリ秒以下の応答性を保証することは不可能です。現場の遅延は解消されませんでした。

供給される総計算量の上限に対して根本から制限をかける必要があります。計算負荷を確実に抑え込む手段はあるでしょうか。最初は誰もが確信を持てずにいました。

---

## 核心的解決策：systemd slices で築く 2 重の防壁

コミュニティ開発者の Geekomcomputer 氏が提示した解決策は、現代の Linux 資源制御の要点を突いたものでした。

Raspberry Pi 4B が搭載する Broadcom 4 コア CPU の総演算力は有限です。個別のプロセスに空きコアを割り振るのではなく、推論タスクが同時に全速力で暴走することを防ぐ点にあります。

具体的には systemd のカスタムスライスを定義し、2 重の防壁を構築します：

- 第 1 の防壁：CPUWeight による絶対的な優先度設定；
- 第 2 の防壁：CPUQuota による推論タスクの上限規制。

設定手順は明快です。systemd の設定ディレクトリに 2 つのスライス定義ファイルを新規作成します。

1 つ目はテレメトリ用の telemetry.slice です：

```ini
[Unit]
Description=Telemetry and Critical Realtime Slice

[Slice]
CPUWeight=1000
```

2 つ目は推論処理を収容する inference.slice です：

```ini
[Unit]
Description=AI Inference Background Slice

[Slice]
CPUWeight=50
CPUQuota=200%
```

この 2 つの防壁がもたらす効果を検証します。

標準設定において、Linux の通常サービスが継承する CPU 重みは 100 です。テレメトリ用スライスの重みを 1000 へ引き上げ、推論用スライスを 50 へ引き下げます。

資源競合が発生した際、遠隔測定プロセスにデータが届くたびに、カーネルスケジューラは迷わず最優先で CPU 実行時間を割り当てます。

さらに決定的な設定が CPUQuota=200% という上限規制です。

4 コアのラズベリーパイは全コア合計で 400% の時間枠を持っています。推論スライスの配額を 200% に制限することは、どれほど推論要求が集中しても、YOLOv8 と Ollama の合計が最大 2 コア分の能力しか占有できないことを意味します。

これにより、OS 基盤、ネットワーク通信、ログ書き込み、リアルタイム遠隔測定のために、2 コア分の余力が恒常的に確保されます。

## 実装検証と温度低下の副次効果

スライスファイルを配置した後、設定を再読み込みして対象サービスを各スライス配下へ登録します。

systemd デーモンを再読み込みします：

```bash
sudo systemctl daemon-reload
```

ユニットファイル内で所属スライスを指定するか、コマンドから直接プロセスを起動します：

```bash
sudo systemd-run --slice=inference.slice ollama serve
```

同一の Raspberry Pi 上で負荷テストを再実行しました。

ブラウザから長文の推論要求を発行した際、監視画面の挙動は一変しました：

推論プロセスが動作しても、htop 上の全体 CPU 使用率は 250% 前後で確実に抑制されました。

コア 0 とコア 1 の負荷は極めて軽快に保たれています。

計器盤の遠隔測定データを確認すると、針路と水深グラフは滑らかに更新を続け、通信遅延は 15 ミリ秒以下に安定し、タイムアウト警告は完全に消失しました。

処理は正常に完了しました。計測データは平穏を取り戻しました。

さらに歓迎すべき成果として、動作温度の大幅な改善が確認されました。

以前は推論が並行動作すると全コア高負荷が続き、アルミ筐体の温度は熱暴走の危険域である 70 度に迫っていました。

200% の配額制限を適用した結果、10 分間の連続問答テスト後も外殻温度は 61 度前後に安定し、周波数低下のリスクを完全に回避できました。

推論速度のわずかな低下を受け入れ、組み込み機器全体の堅牢性を獲得する。この選択は極めて妥当です。計器が停止する事態に誰が冷静でいられるでしょうか。速度を削って安定性を取る価値は十分にあります。

## エッジ共存環境における技術境界と選定基準

今回の実測検証を通じ、低電力基板でリアルタイム処理と大規模モデルを混在運用する際の基準が明確になりました。

Raspberry Pi 4B などの小型基板を運用する際は、以下の 3 点を確認してください：
- ハードウェアの物理的限界を認識すること。複数モデルを同時に制限なしで全開稼働させようとしてはならず、計算量に天井を設ける必要があります；
- 単純なコア固定への盲信を捨てること。割り込みが多発する環境では、cgroups による重み付けと配額制限を優先します；
- 動作温度を監視すること。65 度を超える状態は周波数低下の前兆であり、適切な流量制限はファンの増設よりも効果的な対策となります。

ハードウェア性能が限定的であっても、適切なシステム管理を施すことで小型基板は高い信頼性を発揮します。

推論負荷に圧迫される小型マシンを運用する際、次回の環境構築ではバックグラウンド推論にどの程度の CPUQuota を設定しますか。
