結論から言えば、動作はしますが真似してはいけません。

クラウド技術者の間には根強い直感があります。サーバーレス構成が動画の分割エンコードなどで何百もの並列処理を効率よくこなせるなら、大規模言語モデルも同じように動かせるはずではないかという考えです。

専用 GPU インスタンスを常時起動しておけば、待機中も毎秒コストが発生し続けます。マイクロサービスのように必要なときだけモデルを立ち上げ、実行ミリ秒単位で支払うことができれば、インフラ費用は劇的に抑えられるのではないか。

エンジニアの Noah Lindner 氏はこの仮説を検証すべく、Qwen アーキテクチャに基づく決定モデルを実際に分解し、AWS Lambda 上にパイプラインを構築しました。

結果は厳しいものでした。1 件のドキュメント処理に 17 秒を要し、処理コストは 3.4 セントに達しました。マネージド GPU エンドポイントで実行した場合の約 0.04 セントと比較して、処理速度は極めて遅く、推論コストは 80 倍に急増しました。

これはサーバーレスの柔軟性の問題ではありません。層間のテンソル状態をオブジェクトストレージに渡してはいけないという根本的な物理制約の問題です。

## なぜ Lambda でモデルを組み立てようとしたのか

サーバーレスの魅力は使った分だけ支払う従量課金にあります。

動画の分割変換やサムネイル生成、イベント駆動型のデータクレンジングにおいて、Lambda はコストを大幅に削減できます。

一方で大規模言語モデルの推論には従来の構成において二つの大きな課題がありました：

一つ目はコールドスタートと常時起動費用の板挟みです。A10G や A100 を積んだインスタンスは、夜間にアクセスが数件しかなくても時間単位の固定費用が引かれ続けます。

二つ目は急激なアクセス集中に対する弾力性の問題です。突発的に数千件のリクエストが押し寄せた場合、通常インスタンスの自動拡張ではイメージ取得と重みロードに 2 から 3 分を要し、起動を待つ間にタイムアウトしてしまいます。

モデルを完全にサーバーレス化できれば、アイドルコストゼロと瞬間的な並列拡張を両立できるという青写真が描かれました。

しかし関数の実行環境が持つ物理的制約が立ちはだかりました。

## 9.3GB の重みを 34 個の関数に分割するトポロジ

最初の障壁はデプロイパッケージの容量制限でした。AWS Lambda には展開後の容量制限があり、直接アップロードで 250MB、コンテナイメージでも数 GB 程度に制限されます。

実験で使われた Qwen ベースのモデルは重みサイズが約 9.3GB でした。9.3GB のモデル全体を単一の Lambda に押し込むことは、メモリや初期化の制限から不可能です。

そこで筆者は Transformer の層構造に着目して分割を試みました：

Transformer は層が直列に積み重なる構造を持っています。このモデルは 32 層の Transformer 層で構成され、1 層あたり約 225MB です。前後の Embedding 層と LM Head を含めて合計 34 個の独立した Lambda 関数に分割しました。225MB であれば各 Lambda の実行環境に容易に収まります。

トポロジは以下の直列リレーパイプラインとして設計されました：

```text
プロンプト入力
     │
     ▼
┌─────────────┐
│ Lambda 0    │  Embeddings 読み込み
└──────┬──────┘
       │  活性化テンソルを S3 に書き込み
       ▼
┌─────────────┐
│ Lambda 1    │  Transformer Layer 0 を処理、約 225MB 重み
└──────┬──────┘
       │  活性化テンソルを S3 に書き込み
       ▼
      ... 中間 30 層の関数が直列にリレー
       │  活性化テンソルを S3 に書き込み
       ▼
┌─────────────┐
│ Lambda 32   │  Transformer Layer 31 を処理
└──────┬──────┘
       │  活性化テンソルを S3 に書き込み
       ▼
┌─────────────┐
│ Lambda 33   │  LM Head 読み込み、出力トークンと確率を生成
└─────────────┘
```

パイプラインが通った段階で、筆者はまず出力を検証しました。

同じプロンプトを入力したところ、ローカルの PyTorch と Lambda パイプラインの top-1 トークンは一致しました。順伝播の計算自体は正常に成立したわけです。

しかし複数回の試行やコンテキストのやり取りを重ねる中で、累計で 5600 回もの Lambda 呼び出しが発生しました。

そして請求画面を開いたとき、1 ドキュメントあたり 17 秒と 3.4 セントという数字が判明しました。計算が合うことと実用に耐えることはまったく別の問題です。

## 17 秒と 3.4 セント：80 倍の逆ザヤ請求書の内訳

動作するからといって本番環境で使えるわけではありません。

管理画面の記録は冷酷でした。

ドキュメント 1 件の推論に 17 秒かかり、計算時間とストレージ呼び出しで 3.4 セントが計上されました。

同等クラスの Qwen をクラウドのマネージド GPU インスタンスで実行した場合、推論遅延は数十から数百ミリ秒にとどまり、1 リクエストあたり約 0.04 セントです。

3.4 セントと 0.04 セントの比較では、コストは 80 倍に膨らみました。

費用削減を狙ったサーバーレス実験が、予算を食いつぶす結果となった原因はどこにあったのでしょうか。

### 原因一：S3 を中継するテンソル転送の遅延沼

GPU 内部では、層間のテンソルは SRAM や HBM を通じて毎秒テラバイト級の広帯域で転送されます。

しかし 34 個の独立した Lambda 関数の間ではメモリ空間が共有されません。前層の計算結果を次層に渡すには、シリアライズしてネットワーク越しに送る必要があります。

実験では中間テンソルの受け渡しに Amazon S3 を利用しました。32 層の直列パイプラインでは、各層ごとにテンソルを変換して S3 に書き込み、次層がそれを読み出して展開します。

トークンごと、層ごとに PUT 1 回と GET 1 回を行うと、32 層で 64 回のオブジェクトリクエストが発生します。175 トークンを出力すれば 11000 回以上の S3 アクセスが生じます。

これは指数関数的ではなく線形的な増加ですが、17 秒の大半を消費するには十分な負荷です。大半の時間は行列計算ではなく、S3 と Lambda 間のデータ往復の待機に消えていました。

### 原因二：CPU で密行列計算を行うことによる時間加算

AWS Lambda は基本的に汎用 CPU で動作します。最大メモリを割り当てて CPU コア性能を引き上げたとしても、汎用 x86 や ARM の命令セットでは専用テンソルコアに太刀打ちできません。

GPU なら数ミリ秒で終わる行列乗算に、CPU では数百ミリ秒を要します。

Lambda の料金は実行時間とメモリ容量の積で計算されます。実行時間が数十倍に延びれば、数千回の呼び出しを通じて請求額は跳ね上がります。

### 原因三：コールドスタートと直列スケジューリングの遅延累積

5600 回の呼び出しは均一には進みません。コンテナ割り当て、225MB の重み取得、初期化処理においてコールドスタートのブレが発生します。

厳密な直列依存チェーンでは、全体の所要時間は最も遅いノードの合計で決まります。途中の数層で起動遅延が生じるだけで、後続のすべての関数が待機状態に追い込まれます。

## この実験が示す LLM 推理の物理的境界

商業的には破綻した試みでしたが、システム設計における重要な境界線を浮き彫りにしました。

### 計算集約型と IO 集約型の本質的な違い

サーバーレス構成が動画変換やログ処理で大きな成果を上げられるのは、それらが無状態のデータパイプラインであり、ノード間の依存がなく通信よりも計算処理が勝っているためです。

対して大規模言語モデルは、メモリ帯域幅と極小の通信遅延に依存する計算処理です。Transformer の自己回帰生成ではトークンを 1 個出力するたびに重み全体を参照し、直前の隠れ状態を必要とします。密結合した状態を切り離してネットワーク越しに渡す設計は、ハードウェアの特性に逆行しています。

### 見せかけの柔軟性と実際のコスト

ゼロアイドルにこだわり、待機リソースを悪と見なして複雑な分散中継を組む傾向が見られます。

しかし低頻度の利用であっても、小型の GPU インスタンスを 80 パーセント遊休させておくほうが、数千回のサーバーレス起動を繰り返すより月額費用はずっと安く済みます。待機費用は目に見えますが、分散アーキテクチャの通信負荷や複雑さは見えないところで積み重なります。

### サーバーレス推論の現実的な構成

大規模モデル時代においてサーバーレスが無意味というわけではありません。

適切なサーバーレス構成とは、単一モデルを 32 分割することではなく、プラットフォーム基盤側でインスタンスをウォームプール化することです：

一つ目は GPU コンテナインスタンスの秒単位課金です。重みは物理ホストの共有キャッシュに事前展開されており、ルーティング層だけがリクエストを振り分ける構造をとります。

二つ目はプロンプト成形や認可、JSON パースなどの軽量な補助処理をサーバーレスに任せ、重い行列計算は高帯域接続された専用チップに常駐させる設計です。

## まとめ

この実験から得られる教訓は明確です：

第一に、Transformer の層を動画ファイルのように分割してはいけません。層間の状態は強結合であり、S3 を中継に使うと遅延と API 課金が同時に膨らみます。

第二に、低頻度の推論には素直に小型 GPU インスタンスを利用すべきです。80 パーセント遊休していても、5600 回のコールドスタートを繰り返すより安価です。

第三に、柔軟性を求めるならプラットフォームの GPU ウォームプールを活用し、関数計算でモデルを自作分割するのは避けるべきです。

低頻度推論のために純粋なサーバーレスにこだわる必要があるでしょうか。

節約すべきは稼働率の数値ではなく、月末の請求書の実額です。
