# VRAM不足で極遅になったローカルLLMを救う：spilltuneでllama-serverのメモリ溢れ最適値を自動探索する

RTX 3060 12GBやRTX 4060を購入し、自宅のマシンで30Bクラスの中規模モデルを動かそうとして、多くの人が冷や水を浴びせられます。

17.1GBの重みを持つ31B Q4_K_Mモデルを例に挙げましょう。GPUのVRAMは12GBしかありません。どうやりくりしても、約7GB分の重みがシステムRAMへ溢れ出します。

メインメモリへの溢れが発生した瞬間、llama-serverの出力速度はGPU直結の広帯域からシステムメモリの帯域幅の限界へと急転直下します。

ターミナルのカーソルは1秒に3.4トークンしか進みません。

コーヒーを淹れて戻ってきても、短いコード解説文の出力すら終わっていません。

最初はディスプレイドライバの不具合を疑いました。旧バージョンに戻しても改善しませんでした。WindowsのデスクトップウィンドウマネージャがVRAMを消費しているのかとも疑いましたが、nvidia-smiで監視しても不審なプロセスはありませんでした。

最終的にコミュニティの議論から原因に辿り着きました。llama.cppのデフォルト設定であるfitフラグは、VRAMに安全マージンを確保します。12GBのGPUにおいて無駄に確保された1GBの余白は、GPUにあと二層の重みを載せられるかどうかの決定的な境界線上に位置していたのです。

なぜわずか2GBの不足で速度が半減するのでしょうか？

これは気分の問題ではなく、360GB/sのGDDR6帯域幅から20GB/sのDDR4メインメモリ帯域幅への物理的な落差です。トークンを1つ生成するたびに、CPUはPCIeバス越しに7GBもの重みを往復輸送しなければなりません。物理の制約は誤魔化せません。

llama.cppに多くのチューニングパラメータが用意されていることは知られています。fit-targetを詰めてGPU載せ替え層を増やす、MTPやDFlash補助モデルで投機的サンプリングを組む、推測ステップ数を伸ばす、信頼度閾値を調整するなどです。

しかし、パラメータの組み合わせ数が多すぎます。

VRAMは何メガバイト残すべきでしょうか？補助モデルは4回推測すべきでしょうか、それとも16回でしょうか？信頼度の足切りは0.5が良いのか0.7が良いのか？

先週、私は手動で二十回以上テストを回しましたが、前半の七、八回は完全に無駄骨でした。最も酷い時はVRAMが枯渇してllama-serverがOSによって強制終了されました。補助モデルを組み込んだ結果、逆に3.4から2.2トークン毎秒へ減速する始末でした。

そんな折、GitHub上にこの課題を解決するオープンソースツールが登場しました。作者0xydendrumによるspilltuneです。リポジトリはgithub.com/0xydendrum/spilltuneで公開されています。

空理空論は語りません。手動で丸一日かかる泥臭い試行錯誤を、全自動の山登り最適化タスクへと凝縮してくれます。

## 1. 根本的なボトルネック：メモリ溢れ時のバス転送コスト

spilltuneの価値を理解するために、VRAMとメインメモリの物理スペックを比較してみましょう。

RTX 3060 12GBのメモリ帯域幅は約360GB/sです。デュアルチャネルのDDR4-3200は理論値でも25.6GB/s、実働OS上では20GB/s前後が関の山です。

実に十八倍もの性能差があります。

モデル全体がVRAMに収まっていれば、GPUのテンソルコアは最高速度で重みを読み出せます。

しかし全体の三分の一の層がメインメモリに溢れ出ると、自己回帰デコードを行うたびに、CPUはボトルネックであるバスを経由して7GBの重みを読み出さなければなりません。

バケツの最短の板がシステムメモリ帯域幅になります。一番遅い伝送路が全体の生成ペースを支配してしまうのです。

デフォルトのllama-serverは極めて安全寄りの配分を行います。長いコンテキストで即座にOOMが発生するのを避けるため、fit-onを有効にし、1024MBものVRAMを空けたまま保持します。

12GBのカードにとって、1GBを空けたままにするということは、本来ならGPUに載せられた二、三層の重みをメインメモリへ追い出していることと同義です。

貴重な1GBのVRAMを遊ばせておく余裕などあるでしょうか？二層落ちるだけで、生成速度は二、三割削られます。

投機的サンプリングにも落とし穴があります。DFlashやMTPの補助モデルを読み込めば無条件に速くなると信じられがちです。

しかし実際には速度が落ちることが多々あります。

なぜでしょうか？信頼度の足切り設定が欠けているからです。軽量な補助モデルはコードや数学には強いものの、一般的な創作文や雑談では当てずっぽうな推測を連発します。親モデルが毎回答えを破棄するため、メモリ転送の負荷だけが無駄に増えてしまうのです。

個別のハードウェア構成とモデルの組み合わせに応じて実機測定を行わない限り、机上の推測はすべて的外れになります。

## 2. spilltuneの測定手法：四つの評価題材と自動山登り探索

spilltuneの構造は明快です。

外部の重いフレームワークに依存せず、純粋なPythonスクリプトからローカルのllama-serverバイナリを直接呼び出します。

探索は三つの明確な段階に分かれています：

```text
第1段階：VRAM限界境界の探査
デフォルトの1024MB確保から512MB、256MBへと段階的に縮小し、落ちない最大GPU層数を特定

第2段階：投機的サンプリング補助パラメータの山登り
補助モデル形式の検知、初期推測数の試行、信頼度閾値のスイープによる最適受容率の探索

第3段階：複合ジャンルでの実測検証
数学、コード生成、概念説明、創作文の四題材で出力を検証し、実運用コマンドを出力
```

注目すべきは評価設計です。一般的なベンチマークは手抜きとしてHello Worldのような定型文を流しがちです。短い挨拶文の測定だけで、実用的なコーディング時の速度を測れるでしょうか？簡単な質問では推測の的中率が見かけ上跳ね上がり、数字が水増しされてしまいます。

spilltuneは数学的推論、コード生成、概念説明、物語創作という性質の異なる四つの内蔵プロンプトを備えています。

各試行で生成されるトークン数は192トークンに固定されています。

なぜ四つの題材を測る必要があるのでしょうか？

実測経験上、投機的サンプリング補助モデルはコードや数学では70%以上の受容率を叩き出しますが、発散的な物語創作では30%以下に急落することが珍しくないからです。

特定の題材で補助モデルが足を引っ張る場合、spilltuneは二系統の推奨コマンドを提示します。コードを書く時は補助パラメータを付け、創作時には補助を外すという現実的な使い分けです。

## 3. 実機検証：RTX 3060 12GBで31Bモデルを限界駆動する

spilltuneの効果を確かめるため、Windows 11の検証機で全プロセスを実行しました。

ハードウェア構成：

- プロセッサ：Intel Core i5-14600KF
- グラフィックス：NVIDIA GeForce RTX 3060 12GB
- メモリ：32GB DDR4-3200 デュアルチャネル
- llama.cppビルド：b11798
- 対象モデル：Gemma 4 31B Instruct Q4_K_M、ファイルサイズ17.1GB、60層
- 補助モデル：Gemma 4 31B DFlash Q4_K_M、ファイルサイズ0.85GB

実行前の必須作業として、VRAMを消費するバックグラウンドアプリを完全に終了させておきます。ブラウザのハードウェアアクセラレーションや描画ツールを閉じ、GPUを初期空き状態にします。

導入と実行コマンド：

```bash
# GitHubの最新コミットから直接インストール
pip install git+https://github.com/0xydendrum/spilltune

# 主モデルと補助モデルを指定して自動チューニングを開始
spilltune gemma-4-31B-it-Q4_K_M.gguf --draft gemma4-31b-it-dflash-Q4_K_M.gguf
```

起動すると、ハードウェア認識状況が出力されます：

```text
Hardware: NVIDIA GeForce RTX 3060 12 GB (0.4 GB in use); RAM 32 GB (25 GB free)
Model:    gemma-4-31B-it-Q4_K_M.gguf: 17.1 GB, 60 layers, dense
Helper:   gemma4-31b-it-dflash-Q4_K_M.gguf: 0.85 GB, --spec-type draft-dflash
          6.9 GB of it has to live in system RAM.
```

前提が明示されます。6.9GBの重みはメインメモリへの常駐を余儀なくされます。

自動試行が始まります。

第1試行はllama-serverのデフォルト設定によるベースライン測定です：

```text
Stage 1/3: where the model's layers go (GPU vs RAM)
  trial  1  baseline: llama-server defaults ...
            3.4 tokens/sec, 31/61 layers on GPU
```

デフォルトではGPUに31層しか載らず、生成速度は毎秒3.4トークンでした。

続いて、VRAMの保留容量を1024MBから512MB、384MBへと段階的に削っていきます。

GPU側の層数は31層から38層へと着実に増加しました。

第2段階で補助モデルが介入し、推測ステップ数と信頼度足切り閾値の組み合わせが試行されます。

第15試行において、山登りアルゴリズムがピーク速度を捉えました：

```text
  trial 15  dflash helper, 6 guesses, confidence cut-off 0.7, 384 MiB less VRAM held back ...
            6.5 tokens/sec, 66% of guesses accepted, 21/61 layers on GPU

BEST for one chat: 6.5 tokens/sec (1.92x the defaults' 3.4)
```

推測6回、信頼度閾値0.7、VRAM確保384MB。

生成速度は毎秒3.4トークンから毎秒6.5トークンへ跳ね上がりました。

実に1.92倍の向上です。

VRAMの余白を384MBまで削って動作は本当に安定するのでしょうか？

途中で突然クラッシュしたりしないのでしょうか？

全テストを走らせましたが、一度も落ちることなく安定動作しました。出力の品質も懸念ありません。全VRAM環境での出力結果とコードや数学の解答を突き合わせましたが、サンプリング揺らぎによる些細な表現差を除けば有意な精度の欠落は見られませんでした。

補助モデルをMTP形式に差し替えたところ、第13試行で毎秒8.9トークンに達し、デフォルト比で2.61倍の高速化を達成しました。

全行程は無人放置で32分で終了し、そのまま利用できる起動コマンドが出力されました：

```bash
# spilltuneが出力した本番向けワンライナー起動コマンド
llama-server.exe -m gemma-4-31B-it-Q4_K_M.gguf -c 4096 -np 1 \
  --fit on --fit-target 2098 \
  -md gemma4-31b-it-dflash-Q4_K_M.gguf -ngld 99 \
  --spec-type draft-dflash --spec-draft-n-max 6 --spec-draft-p-min 0.7
```

ローカルディレクトリにはreport.htmlも出力され、各層の配置割合や推測受容率の推移が記録されます。

## 4. MoE特有の挙動：なぜ多く推測すると逆に遅くなるのか

Gemma 4 26B-A4BのようなMoEアーキテクチャをテストした際、直感に反する挙動に遭遇しました。

一般的には、推測が当たる限り、先々のトークンを多く予測したほうが速くなるはずです。そうではないのでしょうか？

しかしMoEモデルでは、この法則が崩れます。

実測データを見てみましょう：

| 設定 | 数学題材 | コーディング | 概念説明 | 創作文 |
| :--- | :--- | :--- | :--- | :--- |
| MoE デフォルト補助なし | 39.8 t/s | 40.4 t/s | 40.1 t/s | 39.7 t/s |
| DFlash補助あり 8ステップ推測 | 37.4 t/s | 45.7 t/s | 23.4 t/s | 20.5 t/s |
| DFlash補助あり 2ステップ推測 | 50.8 t/s | 51.8 t/s | 37.7 t/s | 31.8 t/s |

右端の列に注目してください。

推測ステップ数を8に設定すると、創作文の出力速度は通常時の40前後から20.5トークン毎秒へと半減してしまいました。

なぜ推測を増やすと失速するのでしょうか？メインメモリ上でのエキスパート重みの入れ替えに時間を費やすのは本末転倒ではないでしょうか？

理由は、MoEのエキスパート重みが巨大でシステムメモリ上に残らざるを得ない点にあります。推測した8トークンが異なるエキスパートに分岐すると、CPUはメモリから次々と異なるエキスパート重みを呼び出さなければなりません。

メモリバスの激しい競合が、投機的サンプリングの利得を帳消しにしてしまいます。

推測を2ステップに抑えるとエキスパートの切り替え頻度が落ち着き、コードや数学の生成速度は毎秒50トークンを突破しました。

レポートは明確に結論づけています。MoEでは投機ステップ数を極力控えめにし、創作用途で減速するなら補助モデルを切るのが賢明です。自分で実機を回して確認するほうが、分厚いマニュアルを読むより遥かに早い実感を掴めます。

## 5. 制約事項と実践的な注意事項

便利なツールですが、物理的な限界も明確です。

以下の四点に注意してください：

第一に、コンテキスト長の前提です。spilltuneはデフォルトで4096トークンのコンテキストを基準に显存余量を計算します。日常的に32Kの長文を扱う場合は、コマンドに明示的に`--ctx 32768`を渡す必要があります。指定を怠ると、長文を入れた瞬間にOOMで即死します。実務に即したコンテキスト長を指定していますか？

第二に、補助モデルの適合性です。補助モデルは主モデルと同じアーキテクチャかつ同一のトークナイザでなければなりません。異なる系統の補助モデルを読み込ませると初期ロード時にエラー終了します。

第三に、単一GPUへの特化です。現行のspilltuneは単一カードの最適化のみを対象としており、マルチGPUの分散配置探索は未実装です。

第四に、プラットフォームの対象範囲です。検証はWindows 11とCUDA環境で実施しました。Apple Siliconのマシンは手元にありませんが、ユニファイドメモリ構造であるためPCIeバスのボトルネックが存在せず、この最適化を適用する意味合いは薄いと考えられます。

ハードウェアは固定ですが、パラメータの追い込みは手元で完結します。

30分スクリプトを走らせて保守的な初期設定によるメモリ帯域幅の無駄遣いを回収することは、毎秒3.4トークンの遅さに甘んじるより遥かに実利的です。VRAMの壁にぶつかる前に、物理的な限界値を一度測ってみてはいかがでしょうか？
