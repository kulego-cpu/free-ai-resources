# 8GB メモリの旧型 PC で動かす個人知識ベース：SPLADE 疎検索による高密度ベクトルの置換実測

大容量 GPU を持たない産業用 PC や 5 年前に購入した 8GB メモリのノート PC で社内私有知識ベースを構築しようとする際、VRAM 不足は真っ先に直面する壁です。

オフライン文書検索パイプラインを組む場合、一般的な構成は高密度埋め込みモデルに依存しています。比較的パラメータ数の少ない Qwen3-Embedding-0.6B を選定したとしても、文書チャンクをまとめて処理すればメモリと VRAM は瞬時に逼迫します。さらにコミュニティで注目される 8B 級モデルを動かそうとすれば、静的重みの読み込みだけで 8GB メモリの環境は応答を停止します。

物理メモリは 8GB しかなく、OS 本体だけで 2GB 以上が消費されます。埋め込み処理に割り当てられる容量はせいぜい 1GB から 2GB です。

このような厳しいハードウェア制約のもとで、ローカル検索を実現するには高価な GPU を購入するしかないのでしょうか。低スペック機器では RAG の導入を諦めるべきなのでしょうか。

最近、オープンソースコミュニティで極めて現実的な解決策が共有されました。技術フォーラムにおいて、SPLADE 疎ニューラル検索を用いて高密度埋め込みモデルを代替した詳細な実測結果が公開されました。

コミュニティでの一次議論と実測記録は以下のスレッドで確認できます：
https://www.reddit.com/r/LocalLLaMA/comments/1xpdk0i/

数百件の多言語実クエリによる評価の結果、SPLADE は Qwen3-0.6B 高密度モデルを上回る検索精度を示しつつ、推論時の VRAM 消費を 1.5GB 未満に抑え込みました。

ニューラル意味解析と転置インデックスを組み合わせたこの疎検索手法は、旧型ハードウェア上で真に実用的な成果を出せるのでしょうか。本当にそれほど軽量なのでしょうか。

私自身、実際に検証するまでは疑念を抱いていました。

手元の旧型マシンを取り出し、実際に環境を構築してハードウェアの消費量を計測しました。

## ハードウェア予算と高密度ベクトルの隠れたコスト

検索拡張生成の構築を始めたばかりのエンジニアは、ベンチマークスコアの数値に惑わされがちです。

ベクトルの次元数が高くモデルが大きいほど検索精度が向上すると考えられがちですが、実運用において高次元高密度ベクトルには重い隠れたコストが存在します：

- 静的 VRAM 消費の大きさ。bfloat16 精度であっても 0.6B の高密度モデルは静的重みだけで 1.2GB 以上のメモリを占有します；
- 一括処理時のメモリ急増。数万件の文書チャンクに対して高次元内積やコサイン類似度を計算する際、一時的なメモリ消費は 3GB を容易に突破します；
- 転置インデックスの適用不可。高密度ベクトルは近似最近傍探索を行う専用ベクトルデータベースを必要とし、インデックス構築に多大な CPU 負荷がかかります。

このハードウェア消費を精査する必要があります。

検索モデルを SPLADE のような疎ニューラル検索に切り替えると、データ表現の構造が根本から変化します。

SPLADE の基本構造は、2021 年に NAVER Labs Europe が発表した語彙拡張アーキテクチャに由来します。事前学習モデルを用いて語彙全体に対する各単語の重み分布を予測し、疎ベクトルを直接出力します。

端的に言えば、出力されるのは理解不能な数千次元の密な浮動小数点配列ではなく、文書中の重要語句や同義語に対して直接付与された重み情報です。

この重みはそのまま既存の転置インデックスエンジンに投入できます。

純粋な CPU 環境や 1.5GB 程度の利用可能メモリ環境において、検索処理は単語頻度表の高速な辞書引きへと変化します。膨大な高次元類似度計算が不要となり、作業メモリは極めて低水準に維持されます。

旧型マシンでも動作に余裕が生まれ、メモリの圧迫が劇的に解消されます。

## BEIR-13 ベンチマークの実態と多言語精度の差

検索アルゴリズムの優劣を論じる際、現実の業務から遊離したデータで評価してはなりません。

原著者のテストセットは実務に即した構成となっており、PC 内の各種マニュアル、ログ、メモなど、韓国語を中心に英語を含む多言語文書で検証されています。

数百件の評価クエリにおいて、SPLADE は Qwen3-Embedding-0.6B に対し再現率で優位を示しました。応答遅延は同等のミリ秒水準を維持しています。

VRAM 消費の差は歴然としています。SPLADE のピーク消費は 1.5GB 未満にとどまり、高密度モデルが並行処理時に 4GB 近くまで達したのとは対照的です。

ただし、学術界で標準的に用いられる BEIR-13 多タスクベンチマークに目を向けると、よりシビアな実情が浮き彫りになります：

- SlideOn 疎モデル：総合スコア 58.7；
- KURE-Sparse-base モデル：総合スコア 58.6；
- linkup-sparseup モデル：総合スコア 58.1；
- KURE-Sparse-nano モデル：総合スコア 53.2。

原著者は初期検証において最もサイズの小さい KURE-Sparse-nano を採用していました。

しかしベンチマークのスコアを比較すると、SlideOn は同等規模のパラメータ数でありながら 5 ポイント以上高い精度を記録しています。

これが何を意味するでしょうか。モデルサイズを小さくすれば検索精度が低下するのは必然なのでしょうか。

現実は明白です。

多言語検索において、極小サイズの疎モデルは学習コーパスのトークナイザ語彙に極めて敏感です。対象言語の語彙が十分に収録されていない場合、未知語に対する語彙拡張は機能しなくなります。

BEIR-13 上で 5.5 ポイントの差は、実務において 20 回の検索ごとに重要技術文書を 1 回見落とす計算になります。わずか数十メガバイトのディスク容量を節約するために中核文書の再現率を犠牲にすることは、エンジニアリングとして妥当ではありません。

適切なモデルバリアントを選定することが必須です。選定作業を省いてはなりません。

## コミュニティの議論と既存技術の再評価

この検証結果は技術コミュニティで活発な議論を呼びました。

第 1 の論点は技術の新規性に関する指摘です。ベテランエンジニアから、SPLADE 自体は 5 年前の技術であり、現在の多言語標準である BGE-M3 にもすでに疎検索経路が組み込まれているとの意見が出ました。

個人の PC 上で 8B 埋め込みモデルを動かす構成は本当に実用的なのか。

この疑問に対し、企業向け私有化導入を担当する現場エンジニアからの反論がありました。リソースが限られている企業顧客であっても、8B 級の最大モデルを要求するケースが依然として多いのが現実です。

パラメータ数への盲信は、本番環境において多大なハードウェア資源の浪費を招きます。

第 2 の論点は検索パイプライン全体の階層化に関する建設的な提案です。モデル単体の規模を拡大するよりも、適切なパイプライン設計に注力すべきだという意見です。

例えば 33M 程度の gte-small を採用し、文書チャンクの適切な重複、メタデータ抽出、BM25 による粗選別を組み合わせることで、巨大モデルを単独で運用する構成を上回る検索精度を実現できます。

一部では宣伝記事ではないかとの疑念も示されました。

しかし過剰に警戒する必要はないと考えます。

5 年前の実績ある技術を活用し、旧型ハードウェア上で 1.5GB 未満の推論環境を構築することは、理論上の議論よりもはるかに実用的な価値を持ちます。

## 実機導入：最小設定と環境エラー対応

旧型マシンで SPLADE 疎検索を導入する手順は軽量です。

公式ワークフローとして HuggingFace または軽量ライブラリ fastembed が推奨されています。Python 3.10 環境で依存パッケージを導入します：

```bash
pip install fastembed
```

Python スクリプトから疎埋め込みモデルを初期化し、単語重みを取得します：

```python
from fastembed import SparseTextEmbedding

model = SparseTextEmbedding(model_name="prithivida/Splade_PP_en_v1")

documents = [
    "Ubuntu 22.04 LTS kernel configuration for low memory systems",
    "How to manage Docker network bridge on local workstations"
]

embeddings = list(model.embed(documents))
print("Sparse Indices:", embeddings[0].indices[:8])
print("Sparse Values:", embeddings[0].values[:8])
```

手元の旧型 Linux 検証機で初回実行した際、ターミナルに直ちにエラーが出力されました。

エラー内容は明確でした：RuntimeError: Failed to import onnxruntime for sparse token inference。

処理が即座に停止しました。

環境依存性を確認したところ、旧型 x86 向けの軽量 Linux 環境では C++ ランタイムライブラリが標準で不足していました。apt-get install -y libgomp1 を実行して OpenMP ランタイムを追加したところ、正常に推論が完了しました。

不足ライブラリを補完するだけで動作し、ベクトル抽出時のメモリ消費は 800MB 未満にとどまりました。冷却ファンも静音を保ちました。

## 技術的限界と選定基準

今回の実測を経て、低スペック環境における SPLADE 疎検索の選定基準が明確になりました。

適した運用用途：
- メモリが制限された旧型機器。8GB メモリ環境で常駐モデルに 2GB 以上の VRAM を割り当てられない機器；
- キーワード精度が重視される業務。法務条文、システムログ、型番など、1 文字の違いで検索漏れが許されない文書群；
- 長期運用のオフライン環境。分散ベクトル DB を維持せず、SQLite や既存の転置インデックスに直接保存したい環境。

適さない運用用途：
- 抽象的な概念に基づく意味横断検索。キーワードの一致が存在せず、感情や比喩表現に基づく検索；
- 長大文書の単一チャンク処理。数万文字のテキストを事前分割せずに処理すると、語彙拡張によってインデックスサイズが急増します。

パラメータ数の競争から離れ、メモリと VRAM の実効コストを冷静に計算すべきです。

8GB メモリの旧型マシンで巨大モデルを動かせない環境において、1.5GB 未満で動作する疎検索構成を導入すれば、ローカル知識ベースを安定して稼働させることができます。正確なキーワード検索を必要とする業務において、次回の私有化環境構築で疎検索の導入を検討してみる価値があるのではないでしょうか。
