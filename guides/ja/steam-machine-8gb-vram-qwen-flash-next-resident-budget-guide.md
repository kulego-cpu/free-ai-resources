# 8GB VRAM ゲーム機で MoE 大規模モデルを動かす：なぜ 1 つの設定だけが真に有効なのか

手頃なハードウェアで大規模モデルを動かそうとする時、最も陥りやすい罠は、他人の設定値をそのまま鵜呑みにすることです。

ネット上で神設定ともてはやされる数値も、自分のマザーボードに適用すると効果が出ないばかりか、逆に処理速度を落とすことが少なくありません。

今回の検証機はリビングから引き揚げてきた古い Valve Steam Machine のカスタム構成です。
OS は純正の SteamOS 3.9.5。
GPU は 8GB の独立 VRAM を備えた AMD Navi 33 構成。
マザーボードには DDR4 メモリが 2 枚挿さり、合計 32GB を搭載。
ストレージには一般的な NVMe ソリッドステートドライブを使用しています。

通常の感覚からすれば、8GB の VRAM で巨大な混合エキスパートモデルを動かすなど無謀に思えます。

しかし、超低ビットの三値量子化の進展は目覚ましいものがあります。

新たに公開された Qwen3.8 Flash-Next Gyro S は TQ1_0 水準の三値圧縮を採用。
モデル全体のファイル容量は十数ギガバイトにまで切り詰められました。
8GB の VRAM とシステムメモリを組み合わせることで、ついに現実的な稼働ラインに入ったのです。

LocalLLaMA フォーラムの先行者が、この構成に関する詳細な実測データを公開しました：
https://www.reddit.com/r/LocalLLaMA/comments/1xq8s2n/

投稿者は各チューニング項目のオンオフによる実際の生成速度の変化を克明に記録しています。

その結果は示唆に富むものでした。多くの定番設定が効果を示さない中、たった一つのパラメータだけが劇的な速度向上を叩き出しました。その設定には一体どんな仕組みが隠されていたのでしょうか。

---

## 1. 基準検証環境とデフォルト動作の挙動

検証環境には Strata ターミナル 0.2.9 を使用し、バックエンドには AMD 向けにビルドされた HIP 推論エンジン 0.1.55 ブランチを呼び出しています。

限界性能を確かめるため、文脈長は一気に 128K まで拡大。
マルチモーダル視覚モジュールは停止。
投機的マルチトークン予測もオフ。
KV キャッシュはメモリ節約のため q4_0 精度で量子化しました。

初回の基準測定は、いかなる手動調整も加えない純粋なデフォルト状態で実施します。

入力プロンプトの長さは約 8,000 トークンで統一。
測定は連続 3 回行い、初回のウォームアップを除外した中央値を記録しました。

未調整の標準状態における Navi 33 の測定結果は次の通りです：

プロンプトの前処理速度は毎秒 219 から 240 トークンで安定。

続く自己回帰デコード速度は毎秒 15.1 から 15.9 トークンを推移しました。

8GB VRAM の古い据え置きゲーム機において、128K の長大文脈を維持しながら秒間 15 文字前後の速度を保てるなら、小規模なスクリプト生成やオフラインの手順書検索には十分実用的と言えます。

それでも、コミュニティで語られる高速化の技を見聞きすれば、さらに上を目指したくなるのが自然です。試さずにはいられません。

---

## 2. 定番パラメータの検証：効果の見られなかった 3 つの調整

最初に試したのは、推論エンジン付属の自動クイックチューナーでした。

調整コマンドを実行すると、数行の検出ログが表示された後、現在の構成がすでに最速であるという通知が返り、微細な調整ステップはそのままスキップされました。

実測データもそれを裏付けました。
前処理速度は毎秒 237 から 239 トークン。
デコード速度は毎秒 14.5 から 17.2 トークンの間で揺れ動き、デフォルト状態よりも分散が広がっただけで、実質的な向上は見られませんでした。

2 番目に試したのは、多くのユーザーが推奨する PCIe バスの帯域比率設定です：

```bash
strata-server --model qwen3.8-flash-next-gyro-s-tq1_0.gguf --set pcie-frac=0.35
```

携帯ゲーム機ユーザーの間では、この数値によってメインメモリと VRAM 間の転送詰まりが解消されると話題になっていました。

しかし実測結果はどうだったでしょうか。
3 回の計測中央値において、前処理は毎秒 239 トークン、デコード速度は毎秒 14.8 から 16.0 トークンでした。

速度グラフはデフォルト状態と完全に重なり合いました。

何の変化も起きません。

投稿者の 0.35 という数値は、彼自身のマザーボード配線とコントローラの遅延に合わせた固有の産物でした。異なるマシンで他人の数値を真似しても、気休め以上の効果は得られません。

3 番目の試みは、直感的に陥りやすい VRAM の確保枠拡大です。

VRAM が足りないなら、重要ウェイトをより強固に固定し、さらに 900MB の安全マージンを設ければスワップ揺らぎを抑制できるのではないかと考えがちです。

```bash
strata-server --set kv-resident=20480 --set vram-reserve=900
```

結果は予想を裏切るものでした。
前処理速度は毎秒 227 から 229 に低下。
デコード速度も毎秒 14.8 から 15.5 トークンにとどまりました。

速くなるどころか、わずかに数値を落とす結果となりました。

無駄骨でした。

VRAM 予約領域をむやみに広げると、かえって計算用ワークスペースが圧迫されます。アテンション行列積の計算時にシェーダーコアの作業領域が狭まり、逆効果となったのです。

期待された 3 つの設定がすべて不発に終わり、このゲーム機の性能は秒間 15 トークンで頭打ちなのでしょうか。

## 3. 真の突破口：エキスパート層をエンジン固有メモリに囲い込む

検証が手詰まりになった段階で、フォーラムに記載されていた 4 番目のパラメータを投入しました：

```bash
strata-server --model qwen3.8-flash-next-gyro-s-tq1_0.gguf --set resident-budget-gib=64
```

約 8,000 トークンのプロンプトで再計測を行ったところ、目を見張る数値が表示されました：

前処理速度は毎秒 232 から 242 トークンを維持。

デコード速度は一気に毎秒 17.3 から 19.8 トークンまで急伸。
平均値は秒間 18 トークンの大台に定着し、約 20% という明確な性能向上が実証されました。

なぜ PCIe 比率や VRAM 確保では歯が立たなかったのに、この設定値を 64 に指定しただけで天井を突破できたのでしょうか。

原因は、OS のメモリ管理と混合エキスパートモデルの動作特性との衝突にありました。

この設定を適用する前、システムモニタでメモリの内訳を観察しました：

```bash
free -m
cat /proc/meminfo | grep -E "Active|Inactive|Cached"
```

不可解な状態が見て取れました。
搭載メモリは 32GB あるにもかかわらず、使用中メモリの使用量は 5GB 未満にとどまっていました。

その一方で、Cached の項目には 28GB 近くのデータが居座っていたのです。

これは何を意味しているのでしょうか。

明示的な常駐予算が与えられていない場合、Linux カーネルは VRAM から溢れたエキスパート層のウェイトを通常ファイルと同じ扱いにして、OS のページキャッシュへと送ってしまいます。

あるトークンが特定のエキスパートを呼び出すと、エンジンがメモリにデータを要求します。カーネルはページキャッシュからそのデータを探し出してアクティブメモリへ転送し、計算が終わると再び非アクティブとして扱います。

OS は常にページ切り替え、ステータス追跡、ユーザー空間とカーネル空間のデータ往復に忙殺されていました。

このオーバーヘッドは単発なら数十マイクロ秒に過ぎません。しかし MoE モデルは 1 トークン生成ごとに幾つものエキスパートを切り替えます。何万回ものメモリ往復が積み重なり、演算能力の 2 割を奪い去っていたのです。

この設定を追加することは、ランタイムのアロケータに対してエキスパート層をユーザー空間の専用プール内に常駐させ、OS によるページキャッシュへの追放を禁じる命令を下すことを意味します。

カーネル空間での無駄なデータ往復が消え去ったことで、秒間 3 トークンの純粋な速度向上が実現しました。

## 4. 128K 極限文脈でのストレステストと性能の代償

短い検証で効果が出たとしても、実際の 128K 極限文脈でメモリ不足エラーを起こさずに耐えきれるでしょうか。

安定性を確認するため、58,000 トークンと 61,000 トークンという極めて長大な 2 組のテストテキストを投入しました。

これらは演算力だけでなく、物理メモリの限界を直接試すテストです。

約 6 万トークンの入力に対し、両テストとも約 4 分間の前処理を経て、それぞれ毎秒 234 および 236 トークンを記録。

その後デコード段階へ移行しました。
生成速度は毎秒 17.6 から 17.9 トークンの間で極めて安定して推移しました。

強制終了は発生せず、スワップ使用量は 0.2GB から 0.3GB への微増にとどまり、空き物理メモリも 3.4GB 以上を維持しました。128K の長大ウィンドウを見事に処理しきったのです。

その後、コミュニティの別のユーザーが 16GB メモリ版 Steam Deck で同様の検証を行いました。
デコード速度は毎秒 21 トークンにまで達しました。

ただし、代償もはっきりしています。総メモリが 16GB しかない携帯機では、メモリ逼迫により KV キャッシュが約 4GB まで制限され、長文の収容力は大きく低下します。限られたリソースの中で速度と文脈長のどちらを優先するかは、ユーザー自身の選択にかかっています。

また、1 ビット三値量子化の精度について、まともな文章が書けるのかという懸念もありました。

実測の結果、日常会話の長文ではやや単調さが残るものの、コード解析や Python スクリプト作成、JSON 構造化変換といった用途では驚くほど堅実な挙動を示しました。ローカルのアシスタントとしては実用的な仕上がりです。

## 5. 旧世代ゲーム機活用のまとめと実務上の留意点

今回の検証を踏まえ、AMD 製 GPU や旧型ゲーム機で大規模モデルを動かそうとする技術者に向け、重要な留意点を整理します：

第 1 に、他人のバス比率や微細な VRAM 確保設定を真似して時間を浪費しないこと。マザーボードやドライバ環境が異なれば、微小な数値はほとんど効果を持ちません。

第 2 に、MoE モデルの推論時にはモデルメモリが OS のファイルキャッシュに吸い込まれていないか確認すること。物理メモリに余裕があるなら、常駐枠を明示してエキスパート層をユーザー空間に固定することが最優先です。

第 3 に、極小ビット量子化は省 VRAM 環境への入場券に過ぎないこと。コード生成や定型作業には有用ですが、クラウドの最高峰モデルと同等の思索能力を期待すべきではありません。

夜更けのリビングの片隅で、コントローラを脇に置いたゲーム機からターミナルの文字が滑らかに流れ出します。引き出しに眠る旧世代機を引っ張り出して、真に役立つパラメータを試してみませんか。
