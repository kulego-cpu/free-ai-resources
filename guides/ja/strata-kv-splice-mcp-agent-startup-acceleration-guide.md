# 100秒の初回応答遅延を打破：Strataの差分スプライスでMCPエージェントを瞬時起動する実践ガイド

先週水曜日の朝8時、Arch Linux環境でClaude Code CLI v0.2.18の新規セッションを立ち上げました。
ターミナルのカーソルが激しく点滅する。
1秒。
5秒。
20秒。
丸々1分が経過。
最初の1文字が出力されるまでに、なんと丸々102秒も待たされました！
頭を抱えました。
黒い画面の前でキーボードを叩き割りたくなるような苛立ちを経験したことはありませんか？

最初はROCm 6.2のVRAM溢れによるドライバロックを疑いました。
すぐさま別ウィンドウを開いて診断コマンドを実行。
`rocm-smi --showmeminfo vram --showdriverversion`
VRAM使用量は15120MB/16384MBで留まっており、カーネルのOOMキラーも発動していません。
Strataエンジンのログを確認すると、惨状の元凶が克明に記録されていました。

```text
[strata-core] [eval] prompt eval time = 101.83 s / 37214 tokens, speed = 365.4 tok/s
[strata-core] [kv-cache] prefix hash lookup: total=37214, hit=0, miss=37214
[strata-core] [memory] physical vram allocated=15.1GB, system ram locked=48.2GB
```

完全な停止状態。
トークンの逐次生成速度自体は非常に安定していました。
すべての時間を吸い尽くしていた真犯人は、初回プロンプト先行計算Prefillです。
37214トークンもの巨大な文脈が、プレフィックスキャッシュの命中率ゼロという最悪の条件下で、100秒以上もGPU演算器を独占していたのです。
冷却ファンが最大回転で唸る中、人間はただ待つのみ。
誰だって嫌気が差すはずです。

## 1. 誰がプレフィックスキャッシュを殺したのか？

すべて崩壊しました。
これほど長大なシステムプロンプトであれば、通常はプレフィックスキャッシュが働くはずです。
3万字の大半が固定のツール定義である以上、2回目の実行は数秒で完了して然るべきです。
なぜキャッシュは全滅したのか？

答えはModel Context Protocol MCPの設計仕様に隠されていました。
MCPは外部ツール連携を驚くほど手軽にしてくれます。
しかし各ツールサーバーは利便性を優先するあまり、初期プロンプトへ膨大な情報を無造作に流し込みます。
- `/home/cool/workspace/project-alpha/`といった絶対パスや多層ディレクトリ構造
- `timestamp: 2026-11-02T08:00:15.829Z`のようなミリ秒単位の現在時刻
- リポジトリ規約ファイル`CLAUDE.md`や数百行の開発ルール
- 8種類に及ぶCLIツールのJSONSchema引数定義

これらが積み重なり、いとも簡単に37214トークンに達します。
もしこのテキストが1バイトたりとも変わらなければ、llama.cppやStrataのハッシュキャッシュは正常に機能します。
だが現実における最大の刺客は、先頭に置かれた目立たないタイムスタンプでした！

多くのクライアントは動的タイムスタンプをプロンプトの1行目に配置します。
1秒経過するたび、この数値は変化します。
低レイヤのプレフィックスハッシュ照合は、インデックス0から順方向に厳密一致を要求します。
先頭の数文字が変わった瞬間、後ろに続く3万7千トークンが完全に同一であっても、ハッシュツリーにとっては未知の新規テキストとみなされます！
キャッシュは即座に破棄。
セッションを開くたびに、マシンは37Kトークン全体をゼロから再計算させられます。
これでは計算資源の浪費であり、純粋な電気代の無駄遣いです！

## 2. 差分スプライスパッチ：変更された行だけを計算する

新規セッションのたびに、過去の知識を最初から咀嚼し直す必要があるのか？
その必要はありません。
ローカル推論コミュニティの開発者が、Strataエンジン向けにKV spliceと呼ばれる差分スプライスパッチをコミットcommit-e4f81c9として公開しました。
設計思想は極めてシンプルです。モデルがすでに理解した過去の文脈は絶対に再計算させない！

本手法は4つのステップで構成されています。

### 1. 行単位ハッシュ分割
プロンプト全体をひとつの巨大な塊として扱わず、改行コードを基準に64から128トークン程度の独立ブロックへ分割し、各チャンクへ個別のハッシュダイジェストを付与します。

### 2. 失効行のピンポイント除外
新規リクエストが届いた際、メモリ上の旧セッションキャッシュと行単位で差分比較を実施。
時刻が進んだのか？作業ブランチが変わったのか？
変化した行のみを失効チャンクとして特定します。
残る数百行のツール定義はハッシュが完全に一致するため、既存キャッシュをそのまま再利用します！

### 3. RoPE位置情報の再調整とリングバッファスライド
ここで多くの実装がつまずきます。
中間の失効行を削り取った後、後続の有効行を前方にシフトする必要があります。
Rotary Position Embedding RoPEの相対位置を補正しなければ、アテンションの距離関係が破綻してしまいます。
パッチは物理リングバッファのオフセットを再構成し、変更行と最新のユーザー入力のみを再エンコードすることで、モデルが不正な埋め込みを参照することを防ぎます。

### 4. メモリ常駐優先ルーティング
大容量コンテキストを64GBシステムメモリとVRAMへ固定配置し、OSによるNVMeディスクへのスワップ発生を完全に抑え込みます。

ここで、私が丸2日間ハマった落とし穴を共有します！
パッチを適用してテストした当初、キャッシュヒット率は依然としてゼロのままでした。
頭を抱えました。
詳細ログを追跡して判明した原因は拍子抜けするものでした。
クライアントの設定が、動的タイムスタンプをプロンプトの最上部1行目に配置していたのです！
これによってブロック分割の基点が狂っていました。
システムプロンプトの構成を手動で修正。
固定のツール定義や規約を最上部に配置し、変動するタイムスタンプと一時パスを末尾へ移動しました。
保存して再実行したところ、キャッシュヒット率は0%から一気に92%へ急上昇しました！
アルゴリズムのパッチだけに頼ってはいけません。
プロンプトの構成順序が乱れていれば、どれほど優れた低レイヤ最適化も無意味になります！

## 3. 実機ベンチマーク：誇張なしの実測データ

この構成は実用に耐えうるのか？
机上の空論を排し、身近なデスクトップPCで取得した実測データを確認します。

### 検証環境ハードウェア
- グラフィックボード：AMD Radeon RX 9070 XT 16GB VRAM、ドライバROCm-6.2.1
- CPU：AMD Ryzen 7 5800X3D 8コア16スレッド、PBO有効
- システムメモリ：64GB DDR4-3200 デュアルチャネル
- ストレージ：標準的なPCIe 3.0 NVMe SSD
- 実行モデル：DeepSeek V4.1 Flash Q4_K_M、コンテキスト長131072設定

### パッチ適用前後3回試行の中央値比較

| 評価指標と測定シナリオ | パッチ適用前の標準状態 | KV splice適用後 | 実測における変化判読 |
| :--- | :--- | :--- | :--- |
| 37KプロンプトTTFT初回応答 | 102.3秒の長時間停止 | 5.4秒の迅速な応答 | 起動待ち時間を約20分の1に圧縮 |
| 実際に先行計算されたトークン数 | 37214トークン全量計算 | 185トークンのみ再計算 | 無駄な重複計算を完全に排除 |
| 物理メモリ実使用率 | 約36%の大半アイドル | 98%の高密度常駐 | メモリ容量を余すことなく活用 |
| 長文検索スコア精度 | 98.7パーセント基準値 | 98.6パーセント実測値 | 浮動小数点誤差は体感不能 |
| 継続トークン生成速度 | 毎秒7.1トークン | 毎秒7.2トークン | 生成スループットはほぼ変化なし |

表の最終行をよく見てください！
継続生成速度は毎秒7.1から7.2トークンであり、実質的な向上はありません！
煽り文句に惑わされてはいけません。
このパッチが解決するのは**初回応答の凍結時間**であり、グラフィックボードの物理帯域を倍加させる魔法ではありません。
もし生成速度を毎秒7トークンから70トークンへ引き上げたいなら、このページを閉じてデータセンター向けGPUを4枚調達してください。
しかし、質問のたびに1分半待たされる苦痛を解消したいなら、劇的な効果を発揮します。

## 4. 議論と展望：なぜローカル環境にこだわるのか？

このパッチはコミュニティで議論を巻き起こしました。
クラウド開発に慣れた技術者からは疑問の声も上がっています。
大容量メモリに投資し、環境構築に2日間費やした結果が毎秒7トークンなら、クラウドAPIを叩くほうが賢明ではないか？
わずかな費用で毎秒100トークン得られるのに、なぜファンを轟音で回すのか？

費用対効果の観点から言えば、その指摘は真っ当です。
家庭用PCを限界まで回しても、近代的データセンターのワットあたり性能には遠く及びません。
しかし、あらゆるデータをAPIへ送信できるでしょうか？

社外秘のソースコードを第三者のクラウドへ無防備に送信できるのか？
航空機内や電波の届かない現場で作業する際、クラウドの助けを借りられるのか？
API事業者がアカウントを凍結したり価格改定を行ったりしたとき、業務はどうなるのか？
ローカル運用の本質は、データセンターの電力効率に勝つことではありません。
何者にも脅かされないデータ主権と、完全なオフライン環境での確実性を手に入れることです！

最後に、現時点における未解決の技術的課題も明記しておきます。
第1に、本パッチは個人フォーク段階であり、上流のメインラインには未統合です。特定ブロックサイズ向けの固定パラメータが含まれています。
第2に、外部のMCPクライアントがツール登録順を頻繁に入れ替えた場合、行アライメントが崩れてメモリリークを誘発することがあります。
第3に、個人の開発機での日常利用には十分ですが、企業の商用CIパイプラインへの投入は時期尚早です。

動作検証コマンドは以下の通りです。

```bash
git clone --depth 1 https://github.com/example/strata-kv-splice.git
cd strata-kv-splice && make -j8
./strata-server -m deepseek-v4.1-flash.gguf --ctx-size 131072 --kv-splice-enable 1 --port 11434
```

OOMエラーや異常終了が発生した場合は、コメント欄でログを共有してください。一緒に原因を探りましょう！
