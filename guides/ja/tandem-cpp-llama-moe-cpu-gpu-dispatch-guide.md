# 独自形式の呪縛を打破：tandem.cppで汎用MoEモデルの生成速度を3.3倍化する実践導入ガイド

ローカル環境で自前のAI実行環境を構築するエンジニアにとって、混合エキスパート構造 Mixture of Experts は常に魅力と葛藤が隣り合わせの存在でした。

その恩恵は絶大です。総パラメータ数は数百億規模に達し、巨大モデルに匹敵する卓越した知識を備えながら、各トークンのデコード時にはそのごく一部のエキスパートのみをアクティブにするため、理論上の計算負荷は極めて低く抑えられます。しかし現実の運用環境では、量子化後でも40GBから80GBに及ぶモデルサイズが、24GBのVRAMしか持たない単一のグラフィックボードを容易に圧倒してしまいます。

これまでエンジニアには二つの不満の残る選択肢しかありませんでした。
従来のllama.cppによるCPUオフロードに甘んじ、PCIeバス経由の転送遅延により1秒あたり20から30トークンという低速に耐えるか、
あるいは特定形式への変換を強制し、裏でエキスパートの間引きを行う閉鎖的な専用エンジンに頼るかです。

本日公開された独立プロジェクトtandem.cppは、この二者択一の妥協に終止符を打ちました。

llama.cppに直接組み込む軽量なパッチセットとして設計され、独自形式への変換を一切必要とせず、コミュニティに存在するあらゆる標準GGUF形式のMoEモデルをそのまま高速化します。さらに数式上の近似処理を完全に排除し、単一GPUにおけるデコード性能を原生比3.3倍へと一気に押し上げます。

## 1. 従来の手法が抱えていた物理的および構造的な課題

tandem.cppがもたらした突破口を深く理解するために、従来のMoE推論における代表的な制約を整理します。

### バス転送の物理的ボトルネック
従来のオフロード手法は、システムメモリを受動的な記憶領域として扱います。VRAMに入り切らないエキスパート層はメインメモリへ配置され、ルーティング処理で必要とされるたびにPCIeバスを通じてGPUへと転送されます。しかし最新の規格であっても帯域には上限があり、毎ステップ大量のテンソルを読み込むことで、GPUの高い計算能力の大部分がデータ待ちで空転してしまいます。

### 独自フォーマットによる囲い込みと精度の低下
この問題を回避すべく登場した一部の専用エンジンは、特殊な並び替えを施した非標準フォーマットへの変換を要求しました。さらに深刻な問題として、ベンチマークで見栄えの良い数値を演出するため、寄与度の低いエキスパートを独断で切り捨てる処理が密かに仕込まれているケースが多発していました。昨日検証した通り、こうした姑息な間引きはモデルの思考力に決定的な損傷を与えます。

## 2. tandem.cppのアプローチ：CPUとGPUによる真の協調推論

tandem.cppの基本哲学は極めて明快です。**近似を行わず、独自形式を強要せず、各ハードウェアの特性を最大限に活かすこと**です。

単一ユーザーの自己回帰生成は、メモリ帯域とレイテンシに強く依存します。メモリ上の重みをGPUへ転送してバスを詰まらせるくらいなら、待機しているマルチコアCPU側で直接そのエキスパートの計算を実行させれば良いという発想です。

本アーキテクチャは以下の二つの要素で成り立っています。

- **高頻度エキスパートのVRAM常駐**：ルーティングで最も頻繁に呼び出される中核エキスパートをGPUの高速VRAMに固定し、テラバイト級のメモリ帯域でフル稼働させます。
- **マルチコアCPUによる並列協調計算**：メモリ上に退避された低頻度エキスパートが選択された場合、PCIeバス経由の重み転送は行わず、ホストCPUに直接行列計算を委託します。GPUとCPUがそれぞれの領域で計算を完了させ、ホスト側で即座に出力を合流させることで、バス帯域の制約を完全に回避します。

開発チームはさらに、以下の厳格な開発指針を遵守しています。
**tandem.cppは末尾エキスパートの間引きを一切行わず、キャッシュ優遇の歪んだルーティングを導入せず、貪欲サンプリングの強制も行いません。すべてのトークン生成は原生のllama.cppと数学的に完全に同一です。**

## 3. 実機ベンチマーク検証：厳格な実測データ

標準的な実機環境において、この協調アーキテクチャがどれほどの性能向上を示すか、コミュニティによる厳密な検証が行われました。

### 検証ハードウェア環境
- **プロセッサ**：Intel Core i5-12400F 6コア12スレッド
- **システムメモリ**：64GB DDR4 デュアルチャネル
- **グラフィックボード**：NVIDIA GeForce RTX 4090 VRAM 24GB
- **テスト指標**：GSM8K 数学推論タスクにおける実効生成速度

### 実測デコードスループット比較表

| モデルおよび量子化設定 | 原生 llama.cpp | tandem.cpp 協調 | Strata 正確モード | 原生比の高速化倍率 |
| :--- | :--- | :--- | :--- | :--- |
| **Qwen 3.8 Flash Next IQ3_S 貪欲** | 29.8 t/s | **97.3 t/s** | 103.6 t/s | **3.27倍** |
| **Qwen 3.8 Flash Next 標準サンプリング** | 29.4 t/s | **96.1 t/s** | 98.1 t/s | **3.27倍** |
| **gpt-oss-120b 巨大モデル 貪欲** | 27.8 t/s | **51.5 t/s** | 汎用GGUF非対応 | **1.85倍** |
| **gpt-oss-120b 巨大モデル 推奨設定** | 27.7 t/s | **48.0 t/s** | 汎用GGUF非対応 | **1.73倍** |
| **長文プロンプト 64k Prefill 処理** | 基準速度 | **1.4倍から1.8倍高速** | — | **初回応答の大幅短縮** |

その他にもGLM-4.5-AirやQwen 3.6 35B A3B、DeepSeek V4.1など、多種多様なスパースMoEモデルにおいて1.4倍から2.1倍の安定した速度向上が実証されました。

この結果が示す意義は明白です。
原生llama.cppに対して3倍以上の劇的な進化を遂げつつ、独自形式を要求するStrataの正確モードに肉薄する性能を汎用GGUFのまま達成した点に、極めて高い実用価値が存在します。

## 4. コミュニティの議論と技術的境界線

プロジェクトの公開に伴い、技術コミュニティでは活発な議論が交わされ、以下の知見が共有されました。

### 原生キャッシュ機能との根本的な相違点
llama.cpp本体にもキャッシュ関連のプルリクエストが存在しますが、根本的な違いは**能動的な異種協調と受動的な待機の差**にあります。本体のキャッシュ実装は依然としてGPU主導であり、キャッシュミス時にはストールが発生します。対照的にtandem.cppはCPUスレッドを能動的な計算リソースとして常時活用します。

### メモリ帯域の影響度
ハードウェア構成による影響も実測されています。
- 16GBメモリで帯域が制限された低予算マシンであっても、56.9 t/sの実用的な速度を記録しました。
- 広帯域なDDR5デュアルチャネルやワークステーション向けクアッドチャネル構成では、CPU側の処理速度がさらに加速し、より高いスループットを引き出すことが可能です。

### 速度と精度の境界
一部のエンジンが提示する127 t/s超の数値は、エキスパートの間引きによる近似演算が前提となっています。コード生成や論理的思考タスクにおいて誤回答やハルシネーションを絶対に許容できない業務用途では、完全な精度を維持するtandem.cppの97.3 t/sこそが最も誠実な選択肢となります。

## 5. 実践導入手順：ソースビルドと実行

tandem.cppはGitHubのリポジトリ github.com/ewhacc/tandem.cpp にてパッチ集として公開されています。標準的な環境であれば数分で導入可能です。

### リポジトリの取得とパッチ適用
公式llama.cppをクローンし、パッチを適用します。

```bash
git clone https://github.com/ggml-org/llama.cpp
cd llama.cpp
git clone https://github.com/ewhacc/tandem.cpp /tmp/tandem
git apply /tmp/tandem/patches/*.patch
```

### CMakeによるビルド実行
CUDAアクセラレーションを有効化し、ホスト環境に最適化してコンパイルします。

```bash
cmake -B build -DGGML_CUDA=ON -DCMAKE_BUILD_TYPE=Release
cmake --build build --config Release -j
```

### 汎用MoEモデルの実行
ダウンロード済みの標準GGUFモデルをそのまま指定して推論を実行します。

```bash
./build/bin/llama-cli -m ./models/qwen3.8-flash-next-iq3_s.gguf -p "Pythonで並行処理スクレイパーを記述してください" -n 512
```

## 6. アーキテクトの視点：オープンな規格と計算の誠実さ

推論速度の向上を追求する際、ユーザーを独自規格に縛り付けたり、裏で精度を間引いて数値を飾るような近道は常に魅力的に見えます。しかしオープンソースが真に前進する力は、オープンな標準への敬意と、数学的な正確性の追求から生まれます。

tandem.cppはハードウェア構造への深い洞察と巧みな協調スケジューリングにより、**モデルの知性を一切犠牲にせず、汎用フォーマットの利便性を保ったまま飛躍的な性能向上を達成できること**を証明しました。

手元のGPUで最先端のMoEモデルをストレスなく動かしたいと願うすべてのエンジニアにとって、見逃せない確かな前進です。
