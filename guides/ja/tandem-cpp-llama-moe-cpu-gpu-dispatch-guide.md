# llama.cppにパッチを当てる：単一4090で汎用MoEの生成速度を秒速29から97トークンへ引き上げた実機検証ログ

ローカル環境で混合エキスパートMoEモデルを動かす際。
最大の頭痛の種は総パラメータ数ではありません。
エキスパート重みの大半がメインメモリで眠ったままになることです！
ルーティングがメモリ上のエキスパートを指名するたび、実行基盤は何百メガバイトもの重みテンソルをPCIeバス越しに必死でGPUへ転送します。
PCIe 4.0 x16の理論片道帯域は31.5 GB/sに過ぎません。
GPUの行列演算ユニットはデータが届くまでただ空転するのみ。
カーソルは1秒間に20文字程度しか進みません。
ファンの風切り音だけが響く。
画面の前でただ待たされる。
遅すぎます！

tandem.cppというオープンソースパッチの設計思想は極めて無骨です。
バス経由の転送で詰まるなら、最初から転送しなければいい！
メインメモリ上のエキスパートは、マルチコアCPUがその場で直接行列計算を行えばいいのです。
公式リポジトリの指示に従ってllama.cppにパッチを適用し、手元のマシンで丸2日間連続負荷テストを実施しました。
実機で得られた具体的な測定数値と、事前に把握しておくべき技術的落とし穴を報告します。

## 1. なぜ従来のVRAMオフロードはGPUを飢餓状態にするのか？

屈指の性能を誇るRTX 4090が、なぜMoEモデルの推論で牛歩のような遅さになるのか？
答えはバス転送ペナルティにあります。
過酷な物理的現実です。

量子化後で約40GBある標準的なMoEモデルを例にとります。
単一の24GB VRAMでは全重みを格納できません。
従来のllama.cppによるオフロード手法は極めて単純です。
収まる層だけをVRAMに詰め込み、溢れた層はシステムメモリに置きます。
ゲーティング機構がメモリ上のエキスパートを選択した瞬間、厄介な事態が発生します。
実行基盤はPCIeバスを経由して重みをVRAMへ緊急転送しなければなりません。
トークンを1つ生成するごとに、バス上を何百メガバイトものデータが往復します。
GPUが誇る強力な計算能力の8割以上が、データ転送待ちで無駄に消費されているのです！
計算力は余っているのに、通信経路が完全に詰まっています。

以前、秒速100トークン以上を謳う専用エンジンが話題になりました。
しかしソースコードを精査すると疑問符が付きました。
ベンチマークの数値を盛るために末尾のエキスパートを勝手にスキップしていたり；
コミュニティに流通する標準GGUFを排除して独自フォーマットへの変換を強制していたり；
貪欲法サンプリングに固定してスコアを偽装していたりしました。
モデルの思考力を削って得た見かけの速度など、本番環境では無用です！

## 2. tandem.cppの構造：CPUとGPUの真の異種並列計算

READMEに記された核心ロジックは実質2点のみです。
メモリ上のエキスパートをバス転送しないこと；
CPUとGPUで明確に計算負荷を分担すること。
効果はあるのか？
抜群に効きます。

パッチの実行フローは2つの要素から成り立っています。

### 1. ホットエキスパートのVRAM常駐
利用頻度の最も高い中核エキスパートを4090のVRAMへ常駐させます。
テラバイト級の超広帯域グラフィックメモリを活かし、全速で行列乗算を実行します。

### 2. メモリ内直接計算とホスト側での出力合流
ルーティングがメモリ上のコールドエキスパートを選択した場合、バス転送は一切行いません。
そのエキスパートの計算タスクをマルチコアCPUへ直接投入します。
GPUが中核エキスパートを計算。
CPUが補助エキスパートをその場で処理。
双方が計算を終えた段階で、ホストメモリ上で活性化テンソルの加算合成を行います。
バス経由の転送オーバーヘッドはゼロになります！

作者はプロジェクト文書で明確に表明しています。本パッチはエキスパートのスキップを行わず、ルーターの重み付けも改変しない。
出力されるテキスト品質は原生llama.cppと基本的に同等です。

ただし、ここでひとつ事実誤認を正しておく必要があります。
数式上完全に一致するという主張は、異種並列カーネルを書いたことがない者の机上の空論です！
同一シードを用いて200回のサンプリング比較を実施しました。
最初の100トークンは完全に一致します。
しかし、その先で微小なビットレベルの差異が時折発生します。
なぜか？
CPUとGPUでは浮動小数点の積算順序が物理的に異なるからです！
ハードウェアの浮動小数点加算は厳密な結合法則を満たしません。
並列タイルの積算順序が変われば、末尾の切り捨て結果に必ず差異が生じます。
とはいえ、この微小な揺らぎは産業的な許容範囲内に収まっており、GSM8K数学テストのスコア偏差は0.3%未満でした。

## 3. 実機ベンチマーク：5回測定の中央値とハードウェア負荷

実測値はどうだったのか？
推測を排し、手元のデスクトップ実機で取得した負荷データを確認します。

### 検証ハードウェア構成
- CPU：i5-12400F 全6コア4.4GHz固定
- GPU：RTX 4090 24GB VRAM
- システムメモリ：64GB DDR4-3200 デュアルチャネル
- OS：Ubuntu 24.04 LTS
- 評価モデル：Qwen2-57B-A14B 標準GGUF IQ3_S量子化版

### 5回測定の中央値比較データ

測定条件は統一：n_predictは512、バッチサイズは2048、温度パラメータは推奨既定値を使用。

| モデル構造と実行条件 | 原生llama.cppオフロード | tandem.cpp並列パッチ | 測定速度向上比 | 実機負荷と動作ステータス |
| :--- | :--- | :--- | :--- | :--- |
| Qwen2-57B-A14B 貪欲デコード | 毎秒29.8トークン | 毎秒97.3トークン | 3.26倍 | GPU電力210WかつCPU6コア使用率96% |
| Qwen2-57B-A14B ランダム抽出 | 毎秒29.4トークン | 毎秒96.1トークン | 3.27倍 | サンプリング追加遅延は2ミリ秒未満 |
| Mixtral-8x7B-Instruct Q4_K_M | 毎秒33.5トークン | 毎秒68.2トークン | 2.03倍 | 活性エキスパート増加でCPU負荷増 |
| 64k長文コンテキストPrefill | 基準遅延時間 | 約1.4倍の高速化 | 1.42倍 | 前処理段階の律速はアテンション計算 |

毎秒29.8から97.3トークンへ、3倍強の向上を達成しました。
正直に言って、事前の予想を上回る結果でした。
手頃な6コアi5で出せる速度はせいぜい60前後だろうと見積もっていたからです。
バックグラウンドで`htop`と`perf stat`を監視して納得しました。
CPUの物理6コアすべてが上限近くまで使い倒されていたのです！
メモリバス帯域の使用率も75%を超えていました。
このパッチの正体は、何もない空間から計算力を生み出す魔法ではありません。
マルチコアCPUの余剰計算力とメモリ帯域を総動員して、完全に詰まっていたPCIeバスを迂回する泥臭い力業なのです！

## 4. 導入を避けるべき環境と未解決の課題

過度な期待は禁物です。
以下の環境に当てはまる場合は、導入を見送ることを強く推奨します。

第1に、ノートPCや16GBメモリ搭載機で同様の結果を期待してはいけません！
40GBのMoE重みが物理メモリに入り切らない場合、OSはmmap経由で仮想メモリスワップに頼ることになります。
ストレージへの激しいページフォルトが発生した瞬間、スループットは一桁まで急落し、システム全体がフリーズします。
物理メモリが足りない環境では手を出さないでください！

第2に、VRAMに余裕がない場合は依然としてOOMクラッシュが発生します。
VRAM割り当て設定`--moe-cache-mib`は手動で調整し、コンテキスト展開用に最低3GB以上の安全マージンを確保する必要があります。

第3に、より巨大なモデルを動かす場合、6コアCPUでは明らかに力不足となります。
さらに大型のMoEを狙うなら、CPUは最低8コア以上、メモリはDDR5やクアッドチャネル構成を用意すべきです。

第4に、長文の先行計算Prefill段階における改善は限定的で、約1.4倍程度に留まります。
トークン生成速度が3倍になったからといって、初回応答速度まで同等に跳ね上がるわけではありません。

## 5. ビルド手順と実行コマンド

パッチのソースコードはGitHubのgithub.com/ewhacc/tandem.cppで公開されています。
変更箇所は3つの低レイヤソースファイルのみです。
パッチの適用とビルド手順は以下の通りです。

```bash
git clone https://github.com/ggml-org/llama.cpp
cd llama.cpp && git checkout b3920
git clone --depth 1 https://github.com/ewhacc/tandem.cpp /tmp/tandem
git apply /tmp/tandem/patches/*.patch
cmake -B build -DGGML_CUDA=ON -DCMAKE_BUILD_TYPE=Release
cmake --build build --config Release -j8
./build/bin/llama-cli -m ./models/qwen2-57b-a14b.gguf --n-gpu-layers 33 --moe-cache-mib 6144 -p "Pythonで並行クローラーを書いてください" -n 512
```

興味のある方は自身の実機でビルドしてみてください。
万が一セグメンテーション違反が発生した場合は、issue欄にログを投稿して一緒に原因を究明しましょう！
