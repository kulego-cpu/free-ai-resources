8GB の VRAM で 27B パラメータのコーディングエージェントが本当に動くのでしょうか。

私自身、最初は疑っていました。53.8GB の FP16 モデルを 5.93GB まで圧縮すれば、1 パラメータあたり約 1.76 bit しか残りません。まともな推論が崩壊しても不思議ではないはずです。

11 月 24 日、PrismML が `Ternary Bonsai 2.5 27B` を公開し、Hacker News トップページで一気に 400 近い支持を集めました。

公式ホワイトペーパーと Hugging Face リポジトリ `prism-ml/Ternary-Bonsai-2.5-27B-GGUF` を突き合わせて検証しました。

結論から言います。実用になります。ただし手元の古い `llama.cpp` でそのまま読み込むと、高確率で罠に嵌まります。

## なぜ今回の三値量子化は崩壊しなかったのか

従来の極低ビット量子化は、複数ターンのツール呼び出しに入った瞬間に破綻しがちでした。

前世代の Bonsai 2 27B は DeepSWE で 0 点、AppWorld の複数ステップ課題でも 51.2 点止まりでした。ツールがエラーを返した途端に無限ループへ陥り、捏造した完了報告を返すケースが目立ちました。

Bonsai 2.5 のベースは引き続き `Qwen3.8-27B` です。言語バックボーン 24.35B、視覚タワー 0.47B、埋め込み 2.54B という構成で、線形アテンション約 75% とフルアテンション 25% を組み合わせています。

格納形式も据え置きです。g128 単位で FP16 スケーリングを行う 1.58-bit 三値重みであり、値は `-1`、`0`、`+1` の 3 種類のみを取ります。ブロック単位の直交 Hadamard 回転をオフラインで重みに折り込んでいるため、推論時は活性化値側を回転させるだけで済み、余分なメモリ帯域を消費しません。

精度はどこまで維持されたのでしょうか。統一された `xhigh` 思考モードでの比較表を確認します：

| 評価ベンチマーク | 容量比較 | Qwen3.8 FP16 | GSQ-RCO IQ2_XS | Bonsai 2 27B | Bonsai 2.5 27B |
| :--- | :--- | :--- | :--- | :--- | :--- |
| モデルサイズ | GB | 53.8 | 8.4 | 5.93 | 5.93 |
| 重みあたりビット数 | bpw | 16.0 | 2.50 | 1.76 | 1.76 |
| SWE-bench Verified | コーディング | 80.6 | 74.4 | 60.8 | 75.6 |
| DeepSWE v1.1 | コーディング | 30.1 | 17.7 | 0.0 | 27.0 |
| Terminal-Bench 2.1 | 端末操作 | 70.8 | 53.4 | 52.8 | 60.1 |
| AppWorld | ツール連携 | 93.2 | 46.5 | 51.2 | 90.5 |
| τ³-Bench | 多ターン対話 | 72.8 | 67.5 | 69.1 | 73.9 |

`GSQ-RCO IQ2_XS` の列に注目してください。Bonsai 2.5 より 4 割もサイズが大きいのに、AppWorld では 46.5 点まで急落しています。一方の Bonsai 2.5 はツール呼び出し 5 課題平均で 77.2 点を記録し、FP16 の 77.7 点に 0.5 点差まで迫りました。

これで元の FP16 を完全に超えたと言えるでしょうか。

そうではありません。Terminal-Bench 2.1 では FP16 より 10.7 点低く、BFCL v4 でも 3.6 点劣ります。HN のコメント欄でも過去の無限ループに懲りた開発者から、ベンチマーク最適化への疑念が寄せられていました。

1/9 の VRAM で約 9 割のコーディング性能を引き出せるなら、ローカル補完の選択肢として十分に割に合う取引です。

## 実際の速度はどの程度か：MTP と通常版を混同しない

転載記事の多くが 204 tok/s という数字だけを強調していますが、計測条件が抜け落ちています。

リポジトリにはドラフトヘッドを持たない基本 GGUF と、マルチトークン予測用のドラフト層を備えた `-mtp.gguf` の 2 系統が置かれています。

MTP 投機的デコードを使わない素の `PTQ1_0` および `PQ2_0` の速度は以下の通りです：

- RTX 4090：`PTQ1_0` デコード 112 tok/s、プロンプト処理 3,452 tok/s
- RTX 5090：`PTQ1_0` デコード 163 tok/s。プロンプト処理 4,198 tok/s
- Apple M5 Pro：Metal は `PQ2_0` のみ計測、デコード 30.2 tok/s

`-mtp.gguf` と公式 `presets/llama.cpp/mtp-cuda.json` を併用して初めて、RTX 4090 で 204 tok/s 付近まで伸びます。視覚タワーの `mmproj-Q8_0.gguf` は別ファイル化されているため、テキスト専用のコード作業なら読み込まず 630MB の VRAM を節約できます。

## 実機で動かす前に押さえるべき四つの落とし穴

ベンチマーク表を眺めるより、実際に手元で動かす際の 4 つの罠を先に把握しておく必要があります。

### 5.99GB の PTQ1_0 を落としたのに純正 llama.cpp が拒否する？

リポジトリには 3 種類のパッキング形式があり、対応ランタイムが異なります：

- `PTQ1_0`：5.99 GB、1.76 bpw 密パッキング、NVIDIA 環境で最速だが `PrismML-Eng/llama.cpp` フォークが必須
- `PQ2_0`：7.25 GB、Apple Metal 向け 2-bit スロット形式、こちらもフォーク版が必要
- `Q2_0`：7.67 GB、標準 `llama.cpp` 互換形式

フォーク版のビルドを避けて純正バイナリで `Q2_0` を動かしたい場合はどうでしょうか。

動作しますが、バージョンの境界線があります：**ビルド `b11556` 以降**が必須です。このビルドで Hadamard 活性化処理が統合されました。

厄介なことに、古い純正 `llama.cpp` で `Q2_0` を開くと**エラーを一切出さずに読み込みを終え、文字化けしたゴミを出力し続けます**。実行前に `llama-cli --version` を必ず確認してください。

### デフォルト 4 スロットが 10GB VRAM を食い潰す

約 6GB のモデルなのに、10GB の RTX 3080 でサーバーを起動すると画面描画ごと固まりかける現象が報告されています。

原因は並列スロット数です。`llama-server` は無指定だと共有 KV キャッシュを持つ 4 スロットを自動確保します。Hugging Face の議論では、これにより VRAM 使用量が 9.5 GB まで跳ね上がり、`-np 1` で単一スロットに制限したことで 7.8 GB まで下がった実測値が共有されています。

### --min-p 0 の指定漏れでサンプリングが偏る

標準の `llama.cpp` は `min_p=0.05` を初期値として適用します。Bonsai 2.5 は Qwen3.8 推奨の思考パラメータを前提としており、`min_p` の無効化が求められます。この指定を忘れると、長いコード生成で同じ表現を繰り返す症状が出やすくなります。

### -n 256 指定では思考の途中で打ち切られる

本モデルはデフォルトで `xhigh` 思考モードに入り、`low` モードには非対応です。`low` を渡しても内部的には `xhigh` に近い長さの思考を展開します。

コマンド例でうっかり `-n 256` を指定すると、`<think>` ブロック内の分析だけで上限を使い切り、肝心のコードが 1 行も出力されません。

## そのまま使えるローカル起動スクリプト

PrismML フォークまたは `b11556` 以降の純正 `llama.cpp` を用意できたら、以下の引数で起動します：

```bash
# 案 A：PrismML フォークで最小 5.99GB の PTQ1_0 を動かす
git clone https://github.com/PrismML-Eng/llama.cpp && cd llama.cpp
cmake -B build -DGGML_CUDA=ON && cmake --build build -j

hf download prism-ml/Ternary-Bonsai-2.5-27B-GGUF Ternary-Bonsai-2.5-27B-PTQ1_0.gguf --local-dir .

./build/bin/llama-server -m Ternary-Bonsai-2.5-27B-PTQ1_0.gguf \
  -ngl 99 -fa on -np 1 -c 32768 -n 16384 \
  --temp 1.0 --top-p 0.95 --top-k 20 --min-p 0 \
  --host 127.0.0.1 --port 8080
```

16GB メモリの Mac なら `Ternary-Bonsai-2.5-27B-PQ2_0.gguf` を選び、ビルド時の `-DGGML_CUDA=ON` を外せば Metal 加速が効きます。ビルド自体を省きたい場合は 7.67GB の `Q2_0` を `b11556+` の純正 `llama-server` へ渡してください。

## 日常の開発ツールチェーンに組み込む価値はあるか

8GB GPU や 16GB ノート PC ではこれまで Qwen3.8-27B の起動すら現実的ではありませんでした。6GB 程度の容量で SWE-bench 75.6 相当の推論を持ち歩けるようになった点は、オフライン補完の切り札になります。

一方で 1.76 bpw が完全精度の代替にならない現実も残ります。Terminal-Bench で 10 点落ちている重みは軽くありません。複雑な複数ファイルのリファクタリングを何十ターンも回した際にどこまで安定性を保てるか、手元のプライベートリポジトリで引き続き負荷検証を進めています。
