ステーブルコイン発行元の Tether がエッジ向け小型モデルをオープンソース公開した。名前は `BotPsy-0.8B`。`Qwen3.5-0.8B` をベースに調整し、スマートフォンや低スペック PC 上でのローカル関数呼び出しを主戦場にしている。

どれだけ小さいかというと、`Q4_K_M` 量子化版が `0.53 GB`——正確には `504.8 MiB` しかない。`Q8_0` でも `0.81 GB` だ。

`BFCL v4` で `44.0` 点、`ToolSandbox` で `64.6` 点を叩き出し、パラメータ数 `2.5` 倍の `Qwen3.5-2B-Think` を抑えている。数字だけ見れば魅力的だ。しかし今すぐ `gguf` をスマホへ放り込んでも、まともな JSON が返らない可能性が高い。本体モデルカードと `GGUFs` リポジトリの注記を読み込むと、先に押さえるべきポイントが 3 つ見えてくる。

参照元は `huggingface.co/qvac/BotPsy-0.8B`、`huggingface.co/qvac/BotPsy-0.8B-GGUFs` のモデルカード、そして公式ブログ `huggingface.co/blog/qvac/botpsy` の 3 箇所だ。Android 実機で `32768` コンテキスト時のメモリピークやサーマルスロットリングまでは測れていないため、実機の消費電力や生成速度の数値は書かない。

## なぜ 0.8B が 2B を上回るのか——そしてどこで失速するか

`BotPsy-0.8B` の土台は `Qwen3.5-0.8B` だ。`Gated DeltaNet` とゲート付きアテンションのハイブリッド構成で、テキスト専用、Apache 2.0 ライセンスで提供されている。

同一ハーネスでのベースモデル `Qwen3.5-0.8B-Think` との比較を見ると、`BFCL v4` は `23.4` から `44.0`、`ACEBench` は `30.1` から `58.7`、`τ-bench` の小売・通信・銀行平均は `23.2` から `51.5` へとほぼ倍増している。汎用知能が底上げされたのではなく、ツール呼び出し経路に絞って鍛え上げた結果だ。適切なツールがないときに呼び出しを拒否できるかを測る BFCL v4 のハルシネーション耐性も `86.1` 点と高い。

ところが知識系ベンチマークへ目を落とすと、一気に足元が抜ける。

`GPQA Diamond` は `38.1` 点で `Qwen3.5-2B-Think` の `59.9` 点に 20 点以上離され、`MMLU-Pro` も `48.9` 点対 `65.5` 点に留まる。さらに目立つのが `BrowseComp-Plus` で、最高でも `4.5` 点しか出ていない。オープンな多段 Web リサーチは無理だ。戦える領域は「意図が明確で、ツール集合が固定された」短鎖の呼び出しに限られる。

## 起動時の最初の罠：思考モードがデフォルトでオフ

初見のテストでゴミ出力を引きやすい一番の原因がここにある。

`BotPsy-0.8B` は思考モード前提で学習・評価されている。それなのに `GGUFs` のモデルカードには、内蔵チャットテンプレートがデフォルトで非思考モードになっていると明記されている。フラグを上書きせずそのまま `llama-cli` へ読ませると、思考プロセスを飛ばしていきなり JSON を吐き出し、呼び出し精度が落ちる。

公式の `llama.cpp` サーバー起動コマンドはかなり厳しいサンプリング指定を置いている。

```bash
hf download qvac/BotPsy-0.8B-GGUFs botpsy-0.8b-q8_0.gguf --local-dir .

llama-server -m botpsy-0.8b-q8_0.gguf --jinja -c 32768 \
    --temp 0.3 --top-p 0.95 --top-k 20 --presence-penalty 1.5 \
    --chat-template-kwargs '{"enable_thinking": true}' --port 8080
```

見落としやすい引数が 2 つある。1 つ目は `--chat-template-kwargs '{"enable_thinking": true}'` で、これが抜けるとベンチマーク表のモデルとは別物になる。2 つ目は `--presence-penalty 1.5` だ。通常の小型モデル運用でここまで強いペナルティを掛ける例は少ないが、クライアント既定値の `0` や `1.0` のままだと、思考ブロック内で反復ループに陥りやすい。

加えて、GGUF 版ではベースモデルのマルチトークン予測 `MTP` レイヤーが削られており、推奨言語は英語とされている。日本語や中国語の長文入力でどこまで精度が落ちるかは公式文書に一切記載がない。

## 量子化の収支：Q8_0 で容量半減、ただし推論エンジン差の方が大きい

リポジトリには 3 種類の GGUF ファイルが置かれているが、選び方ははっきりしている。

`botpsy-0.8b-bf16.gguf` は `1446.5 MiB`、約 `1.52 GB` もあり、10 項目平均 `50.4` 点と `Q8_0` より `0.3` 点低い。評価の基準線以外で落とす理由がない。実用は二択になる。PC や 8GB RAM のスマホなら `botpsy-0.8b-q8_0.gguf` 一択で、`774.2 MiB`、KL ダイバージェンス `0.001`、平均 `50.7` 点とサイズ半減で劣化がない。メモリがぎりぎりなら `botpsy-0.8b-q4_k_m-imat.gguf` の `504.8 MiB` へ落とす手もある。imatrix 較正で KL は通常 `Q4_K_M` の `0.048` から `0.036` まで抑えられているが、10 項目平均は `48.9` 点へ下がり、`GPQA Diamond` と `MMLU-Pro` が 3〜4 点削れる。約 270 MiB を浮かせるために知識系スコアを捨てるのはメモリ制約が厳しいときだけにしたい。

ここで面白い逆転現象がある。同じ無劣化の BF16 重みを使っても、`vLLM` と `llama.cpp` CUDA `b12169` の間では `τ-bench` が `4.0` 点、`Claw-Eval` が `3.1` 点、`IFBench` が逆方向に `2.8` 点も動く。`0.8B` 規模では推論エンジンとサンプリング揺らぎの差が、BF16 から Q8_0 への量子化誤差を上回っている。コンマ 1 点の量子化ランキングを細かく追う意味はあまりない。

## 向いている用途と、触らない方がよい用途

棲み分けは明確で、デスクトップの `7B` や `14B` 汎用モデルを置き換えるものではない。

オフライン音声アシスタント、予定登録トリガー、ローカルファイル整理など、ツール一覧が固定でスキーマが整っており、数ターンで完結する処理なら、`800MB` 前後のメモリで Apache 2.0 のローカル関数呼び出しエンジンが回る価値は十分にある。

逆に複数ファイルのコード改修、長い非英語ドキュメント解析、Web 横断検索を `0.8B` に任せるのは無理がある。`BrowseComp-Plus` の `4.5` 点がそのまま上限を示している。

重みを落とす前に次の 3 点を確認しておきたい。

1. 利用するクライアントが `llama-server` へ `enable_thinking: true` を渡せるか。既定テンプレートのままでは本来の挙動にならない。
2. メモリに `1GB` の余裕があるなら `botpsy-0.8b-q8_0.gguf` を選び、`Q4_K_M` で知識劣化のリスクを取らない。
3. 起動例に `-c 32768` とあっても、エッジ端末で 32K フルコンテキストに長い思考出力を乗せて遅延とメモリが耐えられるかは別問題だ。まずは短いコンテキストから負荷を確かめたい。
