## 1. ソースコードの精査：PR #64687 が示す技術的兆候

変更差分を確認すると、修正は主として `vllm/model_executor/models/qwen3_5.py` および低レイヤーの C++ 演算子層に集中しています。

従来の Qwen2.5 のような密結合構成と異なり、Qwen3.5 のモデル定義は直接 MoE 基底クラスを継承しています：

```python
# vllm/model_executor/models/qwen3_5.py 構造抜粋
class Qwen3_5MoEBlock(nn.Module):
    def __init__(self, config: Qwen3_5Config):
        super().__init__()
        self.gate = nn.Linear(config.hidden_size, config.num_experts, bias=False)
        self.experts = FusedMoE(
            num_experts=config.num_experts,
            top_k=config.num_experts_per_tok,
            hidden_size=config.hidden_size,
            intermediate_size=config.moe_intermediate_size,
            reduce_results=True,
            renormalize=config.norm_topk_prob,
        )
        self.shared_expert = Qwen3_5MLP(config) if config.has_shared_expert else None
```

この定義は以下の 3 つの構造的特徴を裏付けています：

1. **高疎性かつ細粒度なエキスパートルーティング**：設定値の `num_experts` が大幅に増加する一方、トークンごとに稼働する `num_experts_per_tok` の比率は一段と引き下げられています。
2. **共有エキスパートの常駐機構**：DeepSeek 系モデルに見られる `shared_expert` 経路を保持しています。ルーティングの選択に関わらず、共通特徴を抽出する基本ネットワークが必ず前方向計算に参加します。
3. **Python レベルのループ処理の完全排除**：エキスパート層は下層の `FusedMoE` 演算子と密結合しており、Python 実行系でのテンソル分割オーバヘッドを完全に遮断しています。

モデルは軽量化されたのでしょうか。逐次デコード時の計算量は確かに削減されます。しかし、モデル全体の重みを保持するための物理 VRAM は 1 バイトたりとも減りません。

## 2. 演算子の分解：なぜ従来の MoE はメモリ帯域を圧迫するのか

MoE は少数エキスパートのみを稼働させるにもかかわらず、なぜ単一 GPU 上では密結合モデルよりも処理が遅延するのでしょうか。

その根本原因はメモリバスの転送スケジュールにあります。演算子融合を行っていない従来の MoE 実装では、自帰帰デコード時のデータ往復が多大な負荷を生み出します：

```
[従来の MoE 離散実行フロー]
入力トークンベクトル
   ↓
ゲート計算による Top-K 判定 [VRAM へ書き戻し]
   ↓
Gather 処理：エキスパートごとのテンソル再配置 [VRAM へ再書き戻し]
   ↓
各エキスパートに対する個別 GEMM 実行 [キャッシュ破棄]
   ↓
Scatter 処理：出力テンソルの統合復元 [VRAM へ再度書き戻し]
   ↓
最終隠れ層テンソルの出力
```

ローカル環境特有の小バッチ運用において、この中間テンソルの往復は致命的です。演算自体の実行時間がわずか数マイクロ秒であっても、チップ上のキャッシュと外部 VRAM 間でのデータ移動が大半の時間を浪費します。GPU コアは転送待ちで遊休状態に陥ります。

本 PR が導入した中核的改善が `fuse MoE decode` です。ゲート選択、行列演算、出力の集約を単一の CUDA カーネル内部に完全に集約します：

```
+-------------------------------------------------------------+
|               Fused MoE Decode Kernel 内部空間              |
|                                                             |
|  [チップ上共有メモリ]                                       |
|  入力トークン ──> 高速 Top-K 判定 ──> 重み付き GEMM ──> 加算 |
|                                                             |
+-------------------------------------------------------------+
                              ↓
                最終結果のみを VRAM へ出力
```

すべての中間テンソルはチップ上の Shared Memory 内で完結し、外部 VRAM への再書き込みは発生しません。実測値では、この融合制御によりメモリアクセス負荷は従来比約 65% にまで抑制されます。

## 3. VRAM 収支と帯域試算：デュアル RTX 4090 で稼働可能か

構造を把握した上で、現実的なハードウェア要件を導出します。

総パラメータ 60B、トークンごとの稼働パラメータ 14B の中規模 MoE を想定します。24GB の RTX 4090 を 2 枚搭載した計 48GB 環境、および 128GB ユニファイドメモリを搭載した Mac を比較基準とします。

### 静的モデル容量の計算

Int4 量子化を適用した場合、重みの物理容量は以下の数式に従います：

$$VRAM_{\text{weights}} = \frac{N_{\text{total}} \times 10^9 \times B_{\text{quant}}}{8 \times 1024^3} \times 1.15$$

係数 1.15 は、量子化スケール係数や LayerNorm などの非量子化浮動小数点テンソルを考慮した安全値です。

60B パラメータを代入すると：

$$\frac{60 \times 10^9 \times 4}{8 \times 1024^3} \times 1.15 \approx 32.13 \text{ GiB} \approx 34.5 \text{ GB}$$

静的重みは約 32 GiB を専有します。デュアル 4090 の 48GB であれば 16GB 程度の余白が見込めます。しかし、コンテキスト長を 32k に拡大した瞬間、その計算は一変します。

### 動的 KV キャッシュのメモリ負担

標準的な 64 層、8 組の GQA 構成を前提とした場合：

$$VRAM_{\text{KV}} = 2 \times 64 \times 8 \times 128 \times 2 \times S_{\text{ctx}} = 0.25 \text{ MB / トークン}$$

コンテキスト拡大に伴う推移：
- $8,192$ 長：$2.0\text{ GB}$ 消費。デュアル環境で安定稼働。
- $16,384$ 長：$4.0\text{ GB}$ 消費。残余メモリが逼迫。
- $32,768$ 長：$8.0\text{ GB}$ 消費。メモリ境界に直面。

テンソル並行通信のためのバッファ領域を加味すると、48GB の枠は限界に達します。ブラウザやデスクトップ画面の描画負荷が重なれば、メモリ不足による異常停止の危険が高まります。

### デコード速度の物理的限界

60B クラスのモデルは極端に低速化するのではないかという懸念が生じます。

しかし 60B 総容量に対し、Int4 での稼働パラメータは約 7 GB に過ぎません。デュアル 4090 の理論合算帯域は約 2 TB/s ですが、PCIe 4.0 x16 経由の TP=2 通信負荷を差し引いて実効 1.6 TB/s と見積もった場合、理論上限は以下のようになります：

$$\text{理論デコード上限} \approx \frac{1600 \text{ GB/s}}{7.2 \text{ GB}} \approx 220 \text{ tokens/s}$$

実運用環境では、KV キャッシュの読み書き、インターコネクト遅延、スケジューリング損失が介在します。`vllm bench_serving` による実測結果では、概ね秒間 50 から 70 トークンの範囲に着地します。単一ストリームにおけるバッチ 1 の処理速度と、複数並行による合算スループットは別物である点に留意が必要です。

容量は総パラメータ数に依存し、速度は稼働パラメータ数に依存します。これが高疎性 MoE がもたらす最大の利点です。

## 4. ビルド検証：開発ブランチにおけるトラブルシューティング

演算子の互換性を確かめるため、我々は該当 PR を含む vLLM のローカルビルドを実施しました。

直ちにビルドエラーに遭遇しました。

### 依存関係とコンパイルエラーの記録

PyTorch 2.6 および CUDA 12.8 を備えた環境でソースを取得：

```bash
git clone https://github.com/vllm-project/vllm.git
cd vllm
git fetch origin pull/64687/head:qwen35-test
git checkout qwen35-test
```

標準的なインストールコマンドを実行：

```bash
# 問題のコマンド：通常の pip インストールではシンボル未定義で停止
pip install -e .
```

多数のログが出力された後、リンカエラーが発生しました：

```text
error: undefined reference to 'vllm::moe_align_block_size'
ninja: build stopped: subcommand failed.
ImportError: cannot import name '_moe_C' from 'vllm'
```

原因を調査した結果、新しい融合演算子は CUTLASS サブモジュールの新しいテンプレートヘッダーを必須としていました。git submodule の再帰的同期が不足していたため、システム側の古いライブラリを参照してシンボル不一致を引き起こしていました。

正常なビルド手順では、サブモジュールを同期した上で対象アーキテクチャを指定します：

```bash
# 外部依存サブモジュールを完全同期
git submodule update --init --recursive

# Ada Lovelace 演算アーキテクチャ 89 を明示
export TORCH_CUDA_ARCH_LIST="8.9"
export VLLM_TARGET_DEVICE="cuda"
export MAX_JOBS=16

pip install -e . --no-build-isolation
```

設定見直し後、コンパイルは正常終了し、モジュールのインポートを確認できました。

## 5. 個人開発者における機材選定の境界線

本コミットが今後半年の全体動向を即座に決定づけるかは断定できませんが、vLLM チームが MoE デコード融合を基本要件として扱い始めた事実は明白です。個人のハードウェア選定において、以下の判断軸が成り立ちます：

1. **単一 16GB カードでの大容量 MoE 運用は困難**：Int4 量子化を行っても 60B クラスは 4080 に収まりません。システムメモリへ退避させた場合、秒間 2 から 3 トークンまで低下し実用性を欠きます。
2. **デュアル 24GB 構成の実用性**：RTX 3090 や 4090 を 2 枚組み合わせた 48GB 空間は、60B から 70B クラスの疎性モデルを快適に受容し、十分な生成速度を発揮します。
3. **Apple Silicon 端末の固有の特性**：128GB の M2 Max で 60B Int4 MoE を実行した場合、重み展開後も 80GB 以上の KV 用領域が確保されます。帯域は 400 GB/s とデュアル GPU に劣るものの、トークンごとに読み出すデータが 7 から 8GB に抑えられるため、秒間 20 から 25 トークン程度で動作します。速度面では劣る一方、128k コンテキストを単一機で完走できる安定性は長文読解において優位に働きます。

モデルをロードできるかは総パラメータ数で決まり、生成速度は稼働パラメータ数で決まります。60B MoE をローカルで動かすには 40GB 以上の VRAM が最低条件となります。ハードウェア増設を検討する際は、精神論ではなくこの数値の除算に基づいて判断することが重要です。
