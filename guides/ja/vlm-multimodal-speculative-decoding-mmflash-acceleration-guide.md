# VLM推論高速化の実践：22%採択率の崩壊からMMFlashによる3.58倍可逆高速化まで

一昨日の午後、ローカルワークステーションで動画スライスのバッチ解析を実行していました。

検証ベースモデルにはQwen2-VL-7B-Instructを選定しました。

パイプラインは1080P車載カメラ映像から車線逸脱、障害物接近、異常挙動を連続検出するタスクです。

単カードの出力スループットを高めるため、サービス設定で投機的サンプリングのドラフトヘッドを追加しました。

純テキストLLM環境において、投機的サンプリングは標準技術として定着しています。

小型ドラフトモデルが候補トークンを予測します。

大型ターゲットモデルが一括で検証します。

一般的なテキストタスクであれば、2倍から3倍の高速化は容易に達成できます。

しかしマルチモーダル処理を開始して2分後、監視パネルの数値を見て言葉を失いました。

毎秒のデコードスループットは向上するどころか、通常の自己回帰生成より12.4%も低下していました。

GPUファンは激しく回転します。

処理遅延は目に見えて延伸しました。

VRAMの枯渇を疑いました。

nvtop画面を確認したところ、24GB中4.2GBの空きがあり、CUDAコア稼働率は98%と35%の間を激しく変動していました。

ハードウェア的なデッドロックではありません。

推論パイプラインは一体どこで詰まっていたのでしょうか？

バックエンドからトークン検証ログを抽出して原因を突き止めました。

## 1. 現場検証：マルチモーダルでドラフト受容率が22%へ崩落した理由

棄却サンプリングログに真因が記録されていました。

純テキスト生成時、ドラフトモデルの受容率は安定していました。

構文構造やインデント、there、is、the、returnなどの一般的な接続表現では、受容率は46%から52%を維持していました。

しかし出力が密集した画像描写に入ると、ドラフトモデルの予測精度は一気に崩壊しました。

画像内容を描写し始めた瞬間、ドラフトモデルは完全に破綻します。

前走車のボディカラーを予測させても外れます。

遠方の制限速度標識を読ませると、5トークン中4トークンが棄却されます。

歩行者バウンディングボックスの座標を出力させると、先頭の数値から外れます。

実際の検証ログは次の通りでした：

```text
[VLM-Speculative] Step 142: draft proposed 16 tokens
[VLM-Speculative] Target verification result:
  Pos 0: "The" (acc=1, p_target=0.88, p_draft=0.85) -> ACCEPT
  Pos 1: " vehicle" (acc=1, p_target=0.74, p_draft=0.71) -> ACCEPT
  Pos 2: " in" (acc=1, p_target=0.69, p_draft=0.65) -> ACCEPT
  Pos 3: " the" (acc=1, p_target=0.91, p_draft=0.89) -> ACCEPT
  Pos 4: " front" (acc=1, p_target=0.82, p_draft=0.78) -> ACCEPT
  Pos 5: " is" (acc=1, p_target=0.95, p_draft=0.92) -> ACCEPT
  Pos 6: " a" (acc=1, p_target=0.89, p_draft=0.86) -> ACCEPT
  Pos 7: " silver" (acc=0, p_target=0.64 [silver], p_draft=0.03 [black]) -> REJECT
[VLM-Speculative] Sequence rolled back from pos 7. Accepted tokens: 7/16.
[VLM-Speculative] Sub-cohort aggregate acceptance rate:
  Language prior tokens: 46.8%
  Visual dependent tokens: 22.3%
```

棄却ログをトークン属性別に分類しました。

視覚エンティティの受容率は22.3%でした。

同時期の純テキストトークンは46%以上を維持していました。

両者の差は2倍以上に達していました。

受容率の崩壊は何を意味するのでしょうか？

小型ドラフトモデルが5トークン提案するたび、主モデルが4トークンを棄却することを意味します。

主モデルは候補トークン列を切り捨ててロールバックし、棄却位置の真の分布を再計算しなければなりません。

ドラフト生成に要した計算資源は無駄になります。

主モデルの再計算負担が増加します。

結果としてマルチモーダル全体の処理スループットが通常時を下回ってしまいます。

なぜ小型ドラフトモデルは視覚タスクでこれほど脆弱なのでしょうか？

原因はパラメータ規模の格差にあります。

一般的な投機ドラフトモデルは1B前後の規模しかありません。

高解像度画像を処理する視覚エンコーダの多重空間特徴を保持できず、数千トークンの画像情報を横断的に理解する能力も備えていません。

主モデルが深い自己注意で把握する画像細部を、小型ドラフトは文脈確率だけで盲目的に推測するしかありません。

純テキスト向けの投機的サンプリング手法は、マルチモーダルモデルにそのまま適用できるでしょうか？

実測では明確なマイナス効果を示しました。

シンガポール国立大学NUS-HPC-AI-Labが公開したMMFlashは、まさにこの視覚的乖離を解決するために設計されました。

論文およびソースコードのリポジトリは以下の通りです：

論文URL：https://arxiv.org/abs/2603.09062

リポジトリURL：https://github.com/NUS-HPC-AI-Lab/MMFlash

この設計はマルチモーダルドラフトの根本課題を解決します。

## 2. 均等仮説の打破：視覚依存度メトリクスと加重訓練

ドラフトモデルのパラメータを増やす手法は採算が合いません。

軽量化が目的のドラフトを7Bまで拡大するなら、主モデルを直接実行した方が効率的です。

NUSチームは問題を定量化しました：現在の生成位置において、画像入力を除去した状態で主モデルを走らせ、次トークンの確率分布のずれを測定します。

ずれが激しければ画像画素に強く依存する単語であり、ずれが小さければ言語確率だけで予測可能な単語です。

このKLダイバージェンスが視覚依存度D_visとなります。

この基準により、損失関数を均等に扱う必要がなくなります。

視覚依存度が高い単語に対して損失の重みを引き上げます。

ドラフトモデルの限られた表現容量を、視覚情報が必須となるトークンへ優先配分します。

ブロック拡散手法と組み合わせた推論フローは以下の通りです：

```text
主干視覚モデル [Target VLM: Qwen2-VL / LLaVA-OneVision]
├─ 画像特徴抽出とクロスモーダル射影層
└─ 第1層の融合隠れ状態を出力 [Fused Hidden States]
      │
      ▼
MMFlash ブロック拡散ドラフト器 [Block Diffusion Drafter]
├─ 主モデルの隠れ状態を直接受領 [独立画像エンコーダ不要]
├─ スパース注意マスクパターン [Sparse Attention Patterns]
└─ 1回の拡散ステップで16候補トークンを並列予測
      │
      ▼
主モデルによるツリー検証 [Tree-based Verification]
├─ 合致系列を採択し不一致分岐を即座に破棄
└─ 棄却サンプリング定理により元の自己回帰分布と完全等価
```

加重学習に加え、逐次的な自己回帰ループから脱却した点も重要です。

EAGLEなどの従来手法はドラフト段階でも1トークンずつ順番に出力していました。

MMFlashはDFlashのブロック拡散思想を継承し、1回の軽量前向伝播で条件付き拡散ヘッドを用いて最大16トークンを一括予測します。

ドラフト生成遅延は単一の前向処理時間内に抑えられます。

実測データでは、視覚依存トークンの受容率は22.3%から実用的な64.7%へと回復しました。

## 3. 長尺動画コンテキストと2万トークンの注意機構トラップ

2万トークンを全体自己注意で処理する構成は、現場で直面しやすい罠です。

4K解像度の文書画像を分割処理すると、視覚トークンは数千規模に達します。

60秒のフルHD動画であれば、入力コンテキストは容易に24000トークンを超過します。

ドラフトモデルが2万以上の過去トークンに対して毎回全量2次自己注意を計算した場合、どうなるでしょうか？

ドラフト処理の計算量が主モデルの検証コストを上回ってしまいます。

ドラフトモデルが小型だからといって、注意機構の計算量が小さくなるでしょうか？

そのようなことはありません。

MMFlashは実用的な設計を採用しています：独立した重い画像エンコーダを持たず、主モデル第1層の融合隠れ状態を直接再利用します。

その上で長尺動画履歴に対して間引きを実施します：
1. 開始部のアテンションシンクで重要な初期トークンを維持；
2. 変化の少ない背景フレームに対するストライド間引きサンプリング；
3. 直近の生成ステップ周辺をフル解像度で保持する局所スライディングウィンドウ。

この構成により、アテンション計算量は2次関数から線形近傍まで圧縮されます。

長尺動画が円滑に動作する理由はハードウェア性能だけではありません。

スパース注意機構によって計算量を大幅に削減した成果です。

## 4. ハードウェア台帳：RTX 4090とA100の実測検証

机上の理論値だけでなく、実機での検証が不可欠です。

Qwen2-VL-7BおよびLLaVA-OneVisionを用いて2種類の環境で実測しました：
- ノードA：NVIDIA GeForce RTX 4090 [24GB GDDR6X、ドライバ 550.54.14、CUDA 12.4]；
- ノードB：NVIDIA A100-SXM4-80GB [HBM2eメモリ]。

4090環境ではQwen2-VL-7Bをbfloat16で稼働させると14.8GBを占有し、ドラフトヘッドとKVキャッシュが1.34GBを消費し、残り7.8GBとなります。

この残容量で2並列ストリームを処理でき、それ以上の多重度ではスループットが低下します。

A100環境ではVRAMの制約を受けませんが、検証完了後に返却するクラウドインスタンスです。

VRAM内訳は明確に区別して計測しました：
1.34GBの内訳はドラフトモデル本体の0.58GBと、2万トークン分のKVキャッシュ0.76GBの合算値です。

サービスは統一CLIから起動します：

```bash
python3 -m mmflash.serve   --model-path Qwen/Qwen2-VL-7B-Instruct   --draft-path NUS-HPC-AI-Lab/Qwen2-VL-7B-MMFlash-Drafter   --num-speculative-tokens 16   --sparse-video-window 2048   --dtype bfloat16   --device cuda:0
```

3つのシナリオで取得したベンチマークデータは以下の通りです：

標準テキストQAタスク：
ベースラインの自己回帰平均速度は28.6 Tokens/s；
MMFlash適用時の生成速度は74.2 Tokens/s；
実測加速比は2.59倍でした。

高解像度工業図面および密集OCRタスク：
視覚トークン負荷によりベースライン速度は18.4 Tokens/sへ低下；
EAGLE-3は受容率が22.3%にとどまり実効速度21.1 Tokens/s、加速比は1.15倍に停滞；
MMFlashは適応的加重により受容率を64.7%へ引き上げ、生成速度65.8 Tokens/sを記録；
エンドツーエンドの加速比は3.58倍に達しました。

数学的な完全性も維持されます。

棄却サンプリングにより、検証を通過したトークン分布は元モデルの独立生成結果と完全一致します。

## 5. 導入時の境界条件と自己診断

MMFlashを本番パイプラインへ導入する際は、2つの境界条件に留意する必要があります。

第1に、プロンプトPrefill段階のボトルネックです。投機的サンプリングはPrefillを高速化できません。

数万トークンの超長文OCRで出力が1文字の分類結果である場合、Prefill段階が処理時間全体の85%以上を占めます。

投機的サンプリングは後続の逐次生成を短縮する技術であり、初回の前向伝播時間は変わりません。

第2に、モデル量子化の整合性です。

Qwen2-VLをAWQやGPTQの4ビットへ量子化し、ドラフトモデルを非対応のFP16のまま運用した場合、隠れ層表現の乖離により受容率が急落し、コンテキストエラーが発生します。

自社のマルチモーダル業務において、レイテンシの要因はPrefill段階でしょうか、それとも逐次生成段階でしょうか？

モデル蒸留と端側量子化を組み合わせることで、ドラフトヘッドの消費メモリを500MB未満まで抑えられるでしょうか？

本番クラスタへの展開前に、対象データセットを用いて単カード環境で受容率を実測検証することをお勧めします。
