# 音声AIはなぜ「もう一度言っていただけますか」と聞き返すのか：WebRTCのTarget Delayと意味論的期限の齟齬をMoQで解消する

地下駐車場やエレベーター前で音声AIを使っていて、誰もが一度はこの苛立ちを味わったことがあるはずです。

マイクを押して、真剣に長文の指示を話しかけます。二つの契約書の違約金条項を比較し、納期遅延時の賠償上限を整理してください。

携帯電話の電波がアンテナ五本から三本に落ちます。車載Bluetoothやモバイル回線が一瞬揺らぎます。

音声モデルは二秒ほど沈黙します。

そして、丁寧かつ絶望的な返答を返してきます。申し訳ありません、通信が途切れたようです。もう一度言っていただけますか？

助手席にスマートフォンを投げ出したくなる瞬間です。周囲が騒がしい場所で、誰が同じ長い指示を三回も繰り返したいでしょうか？

背後では数千億パラメータの最新モデルが稼働しています。数十枚のH100アクセラレータがミリ秒単位でトークンを出力しています。推論自体の遅延は450ms以内に収まっているのです。

いったい何が起きているのでしょうか？莫大なコストを投じたシステムが、なぜ三十年前のトランシーバーに劣る挙動を示すのでしょうか？

多くの人は基地局の電波を疑います。Whisperの音声認識耐性が低いせいにする人もいます。端末側のノイズキャンセリングを疑う声もあります。

本当にAIモデルが脆いのでしょうか？

先週、私たちはUbuntu 22.04 LTSの検証サーバー上でパケットキャプチャを実施しました。

テスト構成は単純です。仮想イーサネットペアで二台のサーバーを直結しました。Linuxのtcコマンドを使い、netemで10%のパケットロス、40msの基礎遅延、10msのジッターを注入しました。音声形式には64kbps、フレーム長20msのOpusを採用しました。

Wiresharkのフィルタにrtpとrtcpを設定します。赤と白の再送マーカーと順序逆転パケットが画面を埋め尽くしました。

三回の検証ログを突き合わせました。

問題は基地局でもモデルの知能でもありませんでした。原因はトランスポート層にありました。Web会議用のtarget delay設計と、LLMが必要とする意味論的期限が根本から衝突していたのです。

## 1. 人間同士の会話重視設計：WebRTCのTarget Delayは誰を守るのか

音声データの脱落原因を理解するには、WebRTCの設計思想に立ち返る必要があります。

<img src="https://img.freeaidog.com/images/blog/webrtc-moq-context-loss-architecture.webp" alt="文脈欠損と遅延バジェットにおけるWebRTCとMoQのアーキテクチャ比較" />

起源は2011年に遡ります。GoogleがGlobal IP Solutionsを買収し、メディアエンジンをChromium向けにオープンソース化しました。これが現在のlibwebrtcです。

想定利用者は一貫して生身の人間でした。

二人の人間が画面越しにGoogle MeetやZoomで会話します。人間の対話許容度は極めて厳格です。音声遅延が200msを超えると、お互いに発言が被り始め、気まずい衝突が起きます。数百ミリ秒も遅れて届く音声で、誰がまともに会話できるでしょうか？

低遅延を最優先するため、WebRTCは厳格なtarget delay戦略を採用しました。

その中核がNetEQジッターバッファです。NetEQはジッター吸収、タイムストレッチ、パケットロス隠蔽、再送管理を統合したモジュールです。

人間同士の会議では、リアルタイム性が完全性に勝ります。ジッターによって20msのOpus音声パケットが35ms遅延し、予定された再生ウィンドウを過ぎると、NetEQは待機しません。直ちに波形補間処理を行い、失われた音声を埋めるか、無音を挿入します。

WebRTCはSDP経由でa=rtcp-fb:* nackを設定し、再送を要求できます。ただし、この再送は主に映像フレーム向けです。音声ストリームにおいて、NetEQの再生スケジューラが遅延パケットを数百ミリ秒も待つことはありません。音声が急に途切れ、その後に倍速再生されたら、人間の耳は耐えられないからです。

人間の日常会話であれば、数十ミリ秒の子音が欠落しても、脳が前後の文脈から自動的に推測します。どうしても聞き取れなければ、聞き返せば済みます。

WebRTCの設計は、欠落の復元責任をそのまま人間の脳に委ねていました。

しかし、受け手がAIモデルになった瞬間、この前提は崩壊します。

## 2. 文脈ブロッキングの矛盾：シリコン脳は意味の完了を待っている

大規模言語モデルは人間の耳とは異なります。20msごとの細切れ音声に付き合う必要はありません。

音声AIには明確な物理的特性が存在します。それが文脈ブロッキングです。

日常的な質問の発話タイムラインを見てみましょう：

```text
0.0s : フランスの
1.0s : フランスの首都は
2.0s : フランスの首都はどこに
3.2s : フランスの首都はどこにありますか？
```

この3.2秒の流れに注目してください。人間が質問を終えるまで、モデルはパリという答えの計算を始めることができません。全文の文脈が揃うことが、推論開始の絶対条件だからです。

ユーザーが話している数秒間、ネットワークには極めて大きな遅延許容空間が存在します。

もし1.0秒の時点でパケットロスが発生し、首都という単語のOpusパケットが落ちたら何が起きるでしょうか？

1. 重要な名詞を含むRTPパケットが失われます。
2. NetEQはパケットが再生期限に間に合わなかったと判断し、破棄します。
3. 後からNACKパケットが届いても、再生スケジューラは既にそのタイムスロットを通過しています。
4. Whisper音声認識には欠落した波形が届き、フランスのどこにありますかと認識されます。
5. 主語を失った言語モデルは困惑し、もう一度言っていただけますかと聞き返すしかありません。

主語を奪われたモデルに何ができるでしょうか？推測するか聞き返す以外に道はありません。

通信量の観点からも不条理です。標準的な64kbpsのOpus音声は、1秒あたりわずか8KBです。20msのパケットなら160バイト程度に過ぎません。

人間が文末を言い終えるまで、まだ2秒以上あります。その間、ネットワークは空いています。パケットロスが10%あっても、往復遅延40msの環境で160バイトを三回再送するのに120msもかかりません。

ユーザーが息を吸い終える前に、失われたパケットは余裕で回収できます。

ユーザーが話し終えた後、サーバー側のエンコーダは回収された音声を5msで処理できます。ユーザーは遅延を一切感じません。

パケットロス自体が罪なのではありません。150msの再生枠を守るために、モデルが数秒後にしか使わない文脈をゴミ箱に捨ててしまうことこそが問題なのです。

これは遅延の勝利ではなく、意味論的期限の致命的な見落としです。

## 3. 下り再生のジレンマ：なぜサーバー側でtime.sleepを呼ぶのか

下りの音声生成ラインも同じ構造的制約を抱えています。

近年のCartesia SonicやElevenLabs Turboなどの音声合成は極めて高速です。10秒分の返答音声なら、GPU上で200ms以内に合成が完了します。

端末のRAMは安価です。2分間の非圧縮音声でも1MB程度しかメモリを使いません。なぜ手元に先読みバッファを作らないのでしょうか？

自然な設計であれば、生成された音声を一気に端末へ転送し、端末側のローカルプレイヤーがタイムスタンプに沿って再生するはずです。

そうすれば、車がトンネルに入って三秒間通信が途絶えても、手元のバッファで滑らかに再生が続きます。

しかし、標準的なWebRTCは到着した時刻の物理クロックに縛られています。

WebRTCのAudioTrackはアプリ主導の突発的な先読みバッファを前提としていません。サーバーが10秒分の音声を200msで流し込むと、受信側のジッターバッファが即座に溢れ、音割れや倍速再生を引き起こします。

この制約を回避するため、一部の開発現場では奇妙なコードが書かれています：

```python
# 人間の発話速度を模倣して少しずつパケットを送る妥協コード
# クライアント側のジッターバッファ溢れを防ぐために不可欠
while not audio_queue.empty():
    chunk = audio_queue.get()
    webrtc_track.send_frame(chunk)
    time.sleep(0.0195)  # 強制的に休眠させて速度を落とす
```

サーバーは人工的に休眠させられ、音声パケットはモバイル回線を遅々と進むことになります。

移動中に電波が途切れた瞬間、進んでいたパケットが失われます。ユーザーには途切れた返答が届き、沈黙が訪れます。

計算資源を消費し、トークン料金を支払いながら、トランスポート層の硬直さゆえに体験が台無しになるのです。

## 4. Media over QUICによる解決：決定権を意味論的期限に取り戻す

このアーキテクチャの矛盾を打破するため、オープンソースコミュニティが注視しているのがMedia over QUIC、通称MoQです。

IETF RFC 9000に基づくQUIC上で動作し、単一の接続内に独立したオブジェクトとトラックを多重化します。音声パケットごとに明示的な生存期限と優先度を付与できます。

```text
WebRTC パイプライン：
PCM音声 -> UDPパケット -> 30ms超過で即破棄 -> 文脈破壊 -> ユーザーへ聞き返し

MoQ パイプライン：
PCM音声 -> QUIC優先ストリーム -> 発話完了まで静かに再送 -> 文脈保持 -> 的確な推論
```

このモデルは二つの根本課題を解決します。

### 1. 意味論的期限に基づく上り再送

ユーザーが発話している間、MoQはcontext_deadlineを設定します。発話が完了する絶対時刻を過ぎない限り、失われた音声パケットは最高優先度で再送されます。

私たちは検証クラスタで厳密な比較実験を行いました：

- テストデータ：Common Voice中国語テストセットから抽出した100本の音声、長さは3.5秒から6.2秒。
- ネットワーク環境：Linux tc netemで10%パケットロス、40ms基礎遅延、10msジッターを付与。
- 音声認識：Whisper-large-v3を使用、温度パラメータは0固定。
- 比較対象：Pion WebRTC v4.0.0とQUICベースのMoQプロトタイプゲートウェイ。

実験結果は明確でした：

WebRTC環境では、100回中21回で重要な音声が欠落し、AIによる聞き返しが発生しました。JiWERで計測した平均単語誤り率は16.8%、分散は1.4%でした。

一方、意味論的期限再送を有効にしたMoQ環境では、失われたパケットは発話終了の120ms前にすべて回収されました。平均再送往復時間は58msでした。単語誤り率はロスなし環境の3.1%に近い3.4%に留まりました。100回の試行で聞き返しは0回でした。不安定な回線において、この安定性は決定的な違いを生みます。

### 2. 軽量制御プレーンによる瞬間的な割り込み

音声を先読みバッファに溜め込んでいる際、ユーザーが急に口を挟んでAIの発話を遮ったらどうなるでしょうか？古い音声が再生され続けるのでしょうか？回線ごと切断しなければならないのでしょうか？

MoQは軽量な制御プレーンによって瞬時に割り込みを処理します：

MoQ仕様において、トラックの生成と破棄は極めて低コストです。サーバーがユーザーの割り込み音声を検知すると、制御ストリーム上でUNSUBSCRIBEコマンドを送り、古いトラックを停止して新しいTrack IDを発行します。

受信側プレイヤーは制御フレームを受け取ったミリ秒単位でローカルのFIFOバッファを破棄し、新しいトラックの受信に切り替えます。ソケットセッションを切断する必要はありません。

```python
# 非同期QUICセッションでの動的トラック破棄処理の例
import asyncio

class MoQAudioSession:
    def __init__(self, quic_connection, context_deadline_ms=4500):
        self.conn = quic_connection
        self.deadline_ms = context_deadline_ms
        self.current_track_id = 0

    async def handle_user_interruption(self):
        # 接続を切断することなく古いトラックを破棄
        self.current_track_id += 1
        control_packet = {
            "type": "TRACK_ABORT",
            "old_track_id": self.current_track_id - 1,
            "new_track_id": self.current_track_id
        }
        await self.conn.send_control_frame(control_packet)
        # 受信側は即座に古い再生バッファを破棄する
```

## 5. 実運用に向けた境界条件と技術的制約

明日から本番環境のWebRTCを完全に置き換えることはできるでしょうか？

答えは否です。

新しいプロトコルを導入するには、三つの障壁を直視する必要があります：

第一に、企業ネットワークによるUDP 443ポートの遮断です。厳格な社内LANでは未検査のUDPトラフィックが遮断されることが珍しくありません。QUICハンドシェイクが通らなければ、WebSocketやTCPへフォールバックする必要があり、ヘッドオブラインブロッキング回避の利点が削られます。閉塞環境への備えは万全でしょうか？

第二に、ブラウザ環境の成熟度です。WebRTCは十五年間の実装蓄積があります。WebTransportやブラウザ側MoQライブラリは、古いAndroid WebViewや一部の組み込み環境においてポリフィルを必要とします。

第三に、クラウド側の音声認識や音声合成サービスとの接続性です。外部ベンダーが未加工のRTPストリームしか受け付けない場合、エッジゲートウェイでパケットの再パッケージ化や時間軸補正を行うメモリコピー負荷が発生します。

実測データに基づく選定指針は以下の通りです：

車載インフォテインメント、産業用ハンディ端末、社内専用ハードウェアなど、ネットワーク構成を完全に管理できる環境であれば、QUICベースの音声トランスポートを導入することで通信途絶を大幅に防ぐことができます。

一方、不特定多数のブラウザからアクセスされる一般Webサービスでは、WebRTCをフォールバックとして残しつつ、ネイティブiOSおよびAndroidアプリから段階的にQUIC音声トランスポートを展開するのが堅実です。

モデルパラメータを8Bから70Bに引き上げても、Web会議時代の固定観念でパケットを捨てていては、AIはいつまでも聞き返しを繰り返します。通信の配管を見直す準備はできていますか？
