プライベートなナレッジベースを構築する技術者の多くが、GitHub で約 2 万スターを集めるシングルバイナリ Rust 製検索エンジン XERJ に注目しています。単一実行ファイルで完結し、標準的な Elasticsearch プロトコルに対応、メモリ消費はわずか数十メガバイトで、コマンド一つですぐに起動します。英語のドキュメントや API リファレンスを引く分には、ミリ秒単位の俊敏な応答が実に快適です。

しかし、実際の中国語ビジネス文書や財務報告書を投入した瞬間、この標準構成は手痛い洗礼を受けることになりました。

私たちは 208 件の実環境コンプライアンス文書を 33,575 件のチャンクに分割し、60 問の厳格なエンドツーエンド評価を実施しました。ターミナルに出力された測定結果は厳しいものでした。ネイティブ XERJ の BM25 語彙検索において、証拠パッセージの Top 3 再現率はわずか 22.22% にとどまり、タスク判定の達成率は 5.3% まで急落しました。

一体どこで破綻したのか。約 2 万スターの Rust エンジンが基本的な転置インデックス作成でつまずいたのか。

生ログとチャンクの突合作業を一日かけて進めた結果、Rust コア自体の検索ロジックには何の問題もないことが判明しました。精度低下の真因は、中国語文書に特有の三つの泥臭い前処理の落とし穴にありました。数字表記の断絶、PDF 由来のフォント文字化け、そして単漢字マッチングが引き起こす過剰適合ノイズです。

私たちは XERJ の Rust ソースコードに一切手を加えず、Python 標準ライブラリのみで構成された軽量なクエリアダプターを構築しました。同一の 33,575 チャンクで再テストを実行したところ、Top 3 証拠再現率は 91.11% へと跳ね上がり、判定達成率は 97.4% まで回復しました。

検証レポートは PR #3371、コーパス収録は PR #3372 として xerj-org/xerj 本家にマージ済みです。カーネル側での CJK ネイティブ対応は公式 Issue #3377 で進行しています。本稿では私たちが直面した三つの障害と、クライアント側アダプターの実装詳細を解説します。

## 評価環境とコーパス仕様

トイデータによる過学習を防ぐため、今回の評価で使用した 33,575 チャンクはすべて実際のコンプライアンス文書から取得し、単一ネームスペースでインデックス化しました：

- 測定環境：Apple Silicon チップ、ユニファイドメモリ、macOS 環境
- エンジン構成：XERJ v1.0.0-rc.101、ポート 9200 で待機、XERJ_DISABLE_QUERY_CACHE=1 によりキャッシュを完全無効化
- コーパス構成：
  1. 法規コーパス：中国現行の民商法と会社法など 29 法規、合計 3,204 条文を条文単位で保持
  2. 臨床試験テーブル：NIH および Europe PMC の臨床研究 55 本から抽出した 271 点の三線表
  3. 上場企業開示資料：テンセント 0700.HK の各四半期報告書、米国 10-K 開示、科創板の目論見書
- 検証フロー：抽出された Top 3 証拠パッセージを検証用ローカルモデルに直接渡し、根拠不十分な場合は回答拒否を義務付け

33,575 チャンクのインデックス作成は全体で約 9.2 秒と極めて高速でした。しかし法条文や財務数値を問うクエリを流した途端、精度は壊滅しました。

## ネイティブ検索が直面した三つの障害

ログを調査した当初、BM25 の語頻度調整に原因があるのではないかと疑いました。しかしテキストを突き合わせるうちに、入力層と前処理層の根本的なズレが浮かび上がってきました。

### 1. アラビア数字と漢数字表記の食い違い

中国語の法律条文本文は、通常「第一百四十七条」のように漢数字で厳格に記述されます。

しかし実際の利用者が検索する際、誰が正式な漢数字を一字ずつ入力するでしょうか。実環境での入力はほぼ例外なく「会社法第 147 条の取締役責任」のようにアラビア数字になります。

XERJ のデフォルトトークナイザーは「第 147 条」を「第」「147」「条」に分割します。ところがインデックス側には「百」「四十」「七」として登録されています。辞書内で 147 が一致せず、最も重要な限定詞の重みがゼロに落ちてしまいます。結果として「会社法」「取締役」などの一般語を含む無関係な条文ばかりが抽出され、本命の第 147 条は 30 位圏外へ追いやられました。

この不一致により、法規検索のピンポイント正答率はゼロになりました。

### 2. 香港取引所 PDF の CMap 文字化けと表の改行崩れ

財務担当者が頻繁に扱う香港取引所の繁体字 PDF 開示資料は、非構造化 RAG における最大の難所です。

テンセントの決算短信を解析した際、特定の月に関する段落がすべて検索漏れする怪現象に遭遇しました。抽出テキストを出力して原因がわかりました：

```text
截至二零二六年九月三十日止三箇月 -> 抽出結果 -> 截至二零二六年九尸三十日止三箇月
```

一部の古い PDF フォント内で、「月」の Unicode CMap エンコーディングがずれ、機械的に無関係な文字「尸」に誤認識されていました。文書内に 341 箇所もこの文字化けが存在し、正規の「月」は一つもありませんでした。これでは「第 3 四半期 3 ヶ月実績」で検索してもヒットするはずがありません。

文字そのものが化けていては、エンジンの性能がどれほど高くても手も足も出ません。

さらに深刻なのがテーブル数値の改行分割です。貸借対照表などの数値で改行が挟まると：

```text
売上高合計 39.\n9 億ドル
会計上のマイナス表記 (\n1,234.5) 百万円
```

小数点が数値から切り離され、インデックスには「39.」と「9」が別々に格納されます。「39.9 億」で検索しても完全に一致しません。

### 3. 単漢字フォールバックによる過剰適合と幻覚

耐障害性を測るため、基准テストには回答不能な引っかけ問題を 4 問混入させていました。海外子会社の個別売上を開示していない資料に対して、その売上額を問うようなクエリです。

本来の理想的な挙動は、証拠なしとして明確に回答を拒絶することです。

しかしネイティブ BM25 は単漢字マッチングにフォールバックしました。クエリに含まれる個々の漢字が数千件の無関係な段落に部分一致し、毎回 15 から 3,319 件もの不要なチャンクを引っ張ってきました。コンテキストウィンドウがゴミ情報で埋め尽くされ、モデルは無理な推論から幻覚を出力しました。引っかけ問題は全滅しました。

## 標準ライブラリのみで動くクライアント修復アダプター

多くの現場では、こうした課題に対して Rust カーネルの改修や、GPU を大量消費するリランカーモデルの導入を検討しがちです。しかしエッジ環境や小規模環境において、文字化け対策のためだけに GPU を増設するのは現実的ではありません。

私たちはクライアント側に query_cn と名付けた軽量アダプターを配置しました。外部 pip パッケージを一切追加せず、Python 標準ライブラリの re と unicodedata のみで完結させました。

処理は三段階で進みます：

```text
ユーザーの検索クエリ
    │
    ▼
[工程 1：アラビア数字と漢数字の双方向展開]
"第147条" を "第一百四十七条" と "147" の両方へ展開
    │
    ▼
[工程 2：CMap 文字化けと数値改行の自動修復]
日付前後の文字化けを治し、分割された小数を連結
    │
    ▼
[工程 3：高信頼度フレーズ制約と過剰召喚の遮断]
短すぎる単字適合を破棄し、証拠不足時は空集合を返却
    │
    ▼
XERJ 検索エンドポイントへ投入
```

### 実装の肝：法規番号の双方向マッピング

正規表現で条文パターンを捉え、アラビア数字と漢数字の両方を multi_match 候補へ同時投入します：

```python
import re

CN_NUM_MAP = {
    '0': '零', '1': '一', '2': '二', '3': '三', '4': '四',
    '5': '五', '6': '六', '7': '七', '8': '八', '9': '九'
}

def expand_legal_query(query: str) -> str:
    def replacer(match):
        raw_num = match.group(1)
        # アラビア数字を漢数字条文へ展開して併記
        return f'第{raw_num}条 第{raw_num}条'

    return re.sub(r'第\s*(\d+)\s*条', replacer, query)
```

この処理を挟むことで、「会社法第 147 条」と検索した場合でも両方の表記がインデックスを直撃し、目的の条文が確実に最上位へ浮上します。

### 実装の肝：文脈を限定した安全な CMap 修復

文字化けした文字を全文一括で置換するのは危険です。医療用語や法医学用語に含まれる正常な語彙まで巻き添えにしてしまうからです。

私たちは日付および前後の文脈に厳密に限定して置換を適用しました：

```python
def repair_hkex_cmap_safe(text: str) -> str:
    # 日付文脈に合致する場合のみ置換を実行
    pattern = r'([0-9]{1,4})\s*化けた文字\s*([0-9]{1,2})\s*日'
    
    def repl_date(m):
        return f'{m.group(1)}月{m.group(2)}日'

    res = re.sub(pattern, repl_date, text)
    # 改行で泣き別れになった小数を連結
    res = re.sub(r'(\d+)\.\s*\n\s*(\d+)', r'\1.\2', res)
    return res
```

この実装により、テンセント決算書の 341 箇所の文字化けを正確に修復し、他の専門用語に対する誤爆はゼロでした。

## 改造前後の比較：60 問の実測データ

同一の Apple Silicon 環境で、XERJ のインデックスには一切手を加えず、クライアント側の処理のみを切り替えて比較しました。

問題構成：
- SEC 財務および XBRL 関連：20 問
- 未上場ハイテク企業の目論見書：10 問
- 中国現行法規およびコンプライアンス：15 問
- 回答不可能な引っかけ問題：15 問

測定結果一覧：

| 評価ブランチ | 正解数 | 不正解数 | 拒否成功数 | 正味スコア | 証拠 R@1 | 証拠 R@3 | 検索 p50 遅延 |
| :--- | :--- | :--- | :--- | :--- | :--- | :--- | :--- |
| 正解パッセージ直接供給 | 52 | 7 | 1 | 38 | 100.0% | 100.0% | 0.0 ms |
| ネイティブ XERJ BM25 | 24 | 11 | 25 | 2 | 17.78% | 22.22% | 113.67 ms |
| query_cn アダプター適用 | 49 | 6 | 5 | 37 | 77.78% | 91.11% | 102.50 ms |

証拠パッセージの Top 3 再現率は 22.22% から 91.11% へと劇的に改善し、回答拒否に起因する判定エラーは 25 件から 5 件へと激減しました。正解パッセージ直供時を 100% と置いた達成率換算では、ネイティブ BM25 の 5.3% から、実用に耐えうる 97.4% まで回復しました。

検索遅延も悪化していません。事前コンパイルされた正規表現による処理は 1 ミリ秒未満で終わり、無駄な過剰召喚が消えたことで、検索 p50 遅延は 113.67 ms から 102.50 ms へとわずかに短縮されました。引っかけ問題 4 問もすべて正しく回答拒否が作動しました。

## 実務における導入指針

今回の検証から得られた最大の教訓は、検索精度が振るわないからといって短絡的に埋め込みモデルの大型化に走るな、ということです。

実際のプロダクション環境において、ベクトルモデルは万能薬ではありません。文書抽出時の文字化けや数字表記の食い違いは、モデル側では修復不能です。モデルを取り替える前に、まず次の三点を確認してください：

- PDF 抽出パイプラインがフォントの CMap 異常を検知・修復できているか
- 条文や章節の番号が漢数字とアラビア数字の間で相互変換されているか
- 低信頼度の単文字検索に対して過剰適合を抑止し、空集合を返せているか

XERJ コアにおける多言語および CJK サポートの議論は公式 Issue #3377 で進行中です。しかしエンジン内部の更新を待つまでもなく、クライアント前処理の適正化こそが最小限のコストで確実な精度をもたらす近道です。
