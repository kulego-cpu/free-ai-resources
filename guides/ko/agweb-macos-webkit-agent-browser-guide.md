작업 데스크에는 모니터 두 대가 놓여 있다.

왼쪽 모니터에는 VS Code를 띄워 두고 복잡한 브랜치 충돌을 수정하고 있었고, 오른쪽 터미널에서는 세 개의 로컬 Agent가 엔드투엔드 통합 테스트를 병렬로 실행하고 있었다.

왼쪽 터미널에서 대화형 git rebase 명령어를 입력하려던 순간, 키보드 입력이 갑자기 끊겼다. 커서가 행 중간에 멈춰 섰다.

고개를 들어보니, 오른쪽 화면에 Playwright가 실행한 Chromium 창이 예고도 없이 최상단으로 튀어나와 있었다. 운영체제의 전역 키보드 포커스가 순식간에 빼앗겨 버렸다. 버전 관리 도구에 입력하려던 터미널 명령어들이 고스란히 웹 페이지 검색창 안으로 쏟아져 들어갔다.

이런 상황을 겪고 화가 나지 않을 엔지니어가 있을까?

비슷한 자동화 프로세스를 실행해 본 개발자라면 커서를 도둑맞는 이 짜증스러운 상황이 낯설지 않을 것이다. 한창 코드를 작성하고 있을 때 백그라운드 브라우저 팝업이 유령처럼 튀어나와 작업 몰입을 산산조각 낸다.

브라우저가 제멋대로 튀어나오는 것을 막기 위해 가장 먼저 떠올리는 방법은 headless 무두 모드로의 전환이다. 그러나 실제 엔지니어링 환경에서 헤드리스 모드는 더 골치 아픈 침묵의 재앙을 몰고 온다.

첫 번째는 봇 탐지 차단이다. 보호 메커니즘을 갖춘 최신 웹 시스템들은 헤드리스 환경을 감지하자마자 403 차단 오류를 뱉거나 연결을 끊어버린다.

두 번째는 블랙박스 동결 현상이다. 페이지가 보이지 않는 모달 대화상자나 포착되지 않은 자바스크립트 오류에 걸려 멈추면, 터미널에는 120초 동안의 무의미한 네트워크 타임아웃 대기만 남는다. 어디서 멈춘 것인가? 프로세스는 살아있는데 로그는 비어있다. 백그라운드 어느 단계에서 뻗었는지 알 수 없어 디버깅 자체가 불가능해진다.

리소스 소모 문제도 빼놓을 수 없다. Playwright로 Chrome 인스턴스를 띄우면 멀티 에이전트 동시 실행 시 부하가 극심하다. 유휴 상태의 탭 다섯 개만 띄워 두어도 메모리를 1.6GB나 잡아먹고, GPU 프로세스가 CPU 코어를 여러 개 점유하여 팬이 맹렬하게 돌아간다.

GitHub에서 개발자 Paul Nameless가 공개한 오픈소스 agweb 은 바로 이러한 현장의 구체적인 고통을 해결하기 위해 개발되었다. 저장소 주소는 github.com/paul-nameless/agweb 이다. 무거운 Chromium 프레임워크를 완전히 버리고, macOS 네이티브 시스템 WebKit 엔진을 밑바닥에 직접 결합했다.

로컬 워크플로우에 연동하여 이틀 동안 검증해 보았다. 기존의 고생담과 비교하여 가장 실질적인 기술적 지표들을 정리해 본다.

## 포커스 탈취와 상주 메모리: Playwright Chrome vs 네이티브 WebKit 비교

Playwright는 웹 자동화 테스트 도구로서 성숙하고 우수하다. 그러나 자율형 Agent 환경에 그대로 얹으면 삐걱거리기 시작한다. 전통적인 프레임워크들은 독립 세션마다 브라우저 인스턴스를 통째로 띄우는 구조로 설계되어 있다. 세 개의 Agent가 병렬로 작동하면 활성 상태 보기에는 세 벌의 거대한 GPU 컨텍스트와 렌더링 파이프라인이 겹겹이 쌓인다.

먼저 메모리와 대기 전력 소모라는 물리적 수치부터 살펴보자. 숫자는 거짓말을 하지 않는다.

M2 Max 칩이 탑재된 테스트 기기에서 복잡한 문서와 테스트 웹 페이지 다섯 개를 띄우고 세 가지 런타임 환경을 비교했다:

| 런타임 아키텍처 환경 | 유휴 탭 5개 물리 메모리 소모 | 유휴 상태 CPU 부하 | 포커스 탈취 동작 |
| :--- | :--- | :--- | :--- |
| **Playwright 네이티브 Chrome** | 약 1.6 GB 물리 메모리 | 5~7개 코어 지속 변동 | 빈번한 팝업으로 포커스 탈취 |
| **Headless Chrome 무두 모드** | 약 730 MB 물리 메모리 | 2~3개 코어 가벼운 기상 | 팝업 없음, 잠재적 침묵 차단 |
| **Agweb 네이티브 WebKit 데몬** | 약 590 MB 물리 메모리 | 거의 0% 수준 정적 서스펜드 | 단일 창 백그라운드, 탈취 제로 |

가장 큰 격차는 비활성 유휴 탭의 서스펜드 정책에서 나타난다.

Chrome의 백그라운드 렌더링 아키텍처는 비활성 페이지에 대해서도 타이머와 이벤트 루프 폴링을 계속 유지한다. 반면 Agweb은 macOS 시스템 WebKit이 제공하는 심층 일시 중단 메커니즘을 호출한다.

CPU 사용률을 10분 동안 지켜보았다. Agent의 작업 지시가 멈추자 두 개의 WebKit 렌더링 프로세스는 3초에서 5초 사이에 부하가 6.8%에서 0.3%로 급격히 떨어지더니 그대로 얌전히 멈추어 섰다. 완전한 제로는 아니지만 무시해도 좋은 수준이다.

더 중요한 개선은 키보드 입력 경험이다.

Agweb의 파일 선택, 대화상자 확인, 파일 다운로드 승인은 모두 터미널 CLI를 통해 Agent가 직접 응답한다. 화면상에 네이티브 팝업 대화상자가 튀어나올 일이 없다. 클릭과 키 입력 이벤트는 macOS 시스템 저수준 이벤트 체인으로 모의 생성되며, 포인터 이동에 부드러운 궤적이 반영되어 호버 메뉴와 드래그 요소도 정상 인식된다.

나는 내 코드를 작성하고, Agent는 백그라운드에서 제 갈 길을 간다. 내 커서는 코드 줄 끝에 얌전히 머물며 단 한 번도 튀지 않는다.

키보드 단축키 Command+D 를 누르면 통합 멀티태스킹 모니터링 대시보드가 열린다:

<img src="https://img.freeaidog.com/images/blog/agweb-multi-agent-dashboard.webp" alt="Agweb 멀티 에이전트 탭 통합 모니터링 대시보드" />

각 Agent의 작업 스트림이 사이드바에 탭별로 정리되어 표시된다. 전체 페이지는 실시간으로 부분 갱신되며, 왼쪽에서 워크스페이스 상태를 확인하고 오른쪽에서 최신 DOM 렌더링 뷰를 실시간 모니터링할 수 있어 어느 작업이 멈췄는지 한눈에 파악할 수 있다.

## 토큰 회계: 작업 단위 차분 Diff는 왜 수십만 토큰을 아껴주는가?

브라우저 조작 Agent를 만들 때 많은 사람들이 동작 성공 여부에만 집중하고 토큰 청구액은 제대로 계산하지 않는다.

전통적인 자동화 흐름에서는 단일 페이지 애플리케이션에서 Agent가 동작을 한 단계 수행할 때마다 접근성 트리 전체의 스냅샷을 다시 가져온다. 노드가 복잡한 현대 웹 프론트엔드 환경에서 정형화된 스냅샷 하나가 8,000에서 10,000개 이상의 토큰을 손쉽게 집어삼킨다. 10여 단계가 넘어가는 긴 폼 입력 프로세스에서는 전체 DOM을 반복해서 쏟아붓는 것만으로 30분 만에 수십만 토큰이 증발한다. 테스트 한 번에 대량의 토큰을 날리는 비용을 누가 감당할 수 있겠는가?

Agweb은 이 지점에서 작업 단위 차분 Diff 메커니즘을 도입했다.

현재 페이지의 상호작용 노드마다 ref=e3 형태의 지속적인 참조 식별 번호를 부여한다. 해당 노드가 DOM 안에 남아있는 한 세션 내내 이 번호는 바뀌지 않는다. Agent가 클릭이나 입력 명령을 보내면, 데몬은 이번 조작으로 인해 발생한 DOM 변경 증분만을 반환하며 트리 전체를 다시 가져오지 않는다.

터미널에서 선택자를 전달할 때는 바깥쪽을 작은따옴표로 감싸야 한다는 점을 주의해야 한다. 처음에 무심코 큰따옴표를 썼다가 zsh가 대괄호 내용을 와일드카드 확장으로 처리해 버려서 no such element 오류가 발생했고, 셸 변수 해석 문제임을 알아채는 데 20분을 허비했다:

```bash
# 전용 워크스페이스를 할당하고 대상 웹 페이지 열기
agweb -w task open https://en.wikipedia.org/wiki/WebKit

# 현재 페이지의 정제된 상호작용 노드 트리 추출
agweb -w task snapshot

# 셸의 따옴표 제거를 방지하기 위해 바깥쪽에 작은따옴표 사용
agweb -w task click 'role=button[name="Main menu"]'
```

커맨드라인은 불필요한 전체 트리를 쏟아내지 않고 변경 증분 보고만을 즉시 반환한다:

```text
### Changes
  - navigation "Site" [ref=e2]
-   - button "Main menu" [ref=e3]
+   - button "Main menu" [checked] [expanded] [ref=e3]
+   - list [ref=e1167]
+     - listitem [ref=e1168]
+       - link "Main page" [ref=e1169]
```

변화는 매우 명확하다. 버튼 노드 상태가 펼침으로 갱신되었고, 그 아래에 리스트 항목과 메인 페이지 링크가 추가된 것을 볼 수 있다.

Agent는 다음에 조작할 새로운 ref 번호를 즉시 획득하므로 비용이 많이 드는 전체 snapshot 명령을 다시 호출할 필요가 전혀 없다. 사내 경비 정산 폼 테스트 흐름으로 직접 실측해 보았다. 기존 전체 스냅샷 방식에서는 14단계 상호작용에 118,000 토큰이 소모되었으나, 차분 증분 방식으로 전환하자 36,000 토큰으로 감소하여 전체 컨텍스트 부피를 약 70% 압축했다. 절약된 토큰 덕분에 같은 날 완전한 회귀 테스트를 두 차례 더 돌릴 수 있었다.

## 인증 정보와 보안: LLM 대화 기록에서 비밀번호를 물리적으로 격리하기

기존의 자동 로그인 스크립트에는 치명적인 개인정보 보호 결함이 존재했다. 브라우저에 비밀번호를 채워 넣기 위해 많은 도구들이 평문 비밀번호를 대형 모델의 툴 호출 인자로 그대로 넘겨주었던 것이다.

이는 비밀번호나 일회용 인증 토큰이 클라우드 모델의 추론 로그와 로컬 채팅 덤프 파일에 그대로 기록됨을 의미한다. 동료와 공유하기 위해 로그를 내보낼 때 비밀번호가 고스란히 노출되는 보안 위험을 누가 감수하겠는가?

Agweb은 외장 인증 정보 주입 파이프라인 방식을 채택했다.

Agent가 입력 명령을 보낼 때 secret-cmd 매개변수를 사용하여 pass, 1Password CLI, Bitwarden CLI 같은 로컬의 안전한 키 관리 도구를 지정할 수 있다:

```bash
# 로컬 pass 도구가 비밀번호를 직접 복호화하여 WebKit 폼에 주입
agweb -w task fill "#password" --secret-cmd "pass show internal/staging-db"
```

전체 실행 체인이 로컬 시스템 프로세스 내부에서 완결된다. Agent가 전달받는 것은 필드 입력이 성공했다는 단순 불리언 결과뿐이다. 비밀번호 자체는 터미널 표준 출력에도 LLM 컨텍스트에도 절대 노출되지 않으며, 클라우드로 유출되는 통로를 물리적으로 차단한다.

또한 멀티 에이전트 협업을 위해 Agweb은 이름이 지정된 영구 프로파일을 지원한다. 명령어에 -p work 옵션을 추가하면 여러 워크스페이스가 동일한 로그인 세션 환경을 공유할 수 있다. 메인 Agent가 로그인을 마치면 보조 Agent들은 재인증 없이 세션 상태를 즉시 재사용한다.

다만 엔지니어링 주의사항도 있다. 특정 작업에서 조작 실수로 로그아웃되거나 쿠키가 무효화되면 해당 프로파일에 묶인 모든 Agent가 일제히 오프라인으로 튕겨 나간다. 동시 실행 장애를 디버깅할 때 이 지점을 염두에 두어야 한다.

## 로컬 빌드, CLI 설정 및 주요 명령어 모음

현재 이 소프트웨어는 macOS 26 이상 버전을 필요로 한다. 공식 GitHub Releases 페이지에서 사전 빌드된 Agweb.dmg 디스크 이미지를 제공한다. 소스코드에서 직접 빌드하는 과정도 깔끔하다:

```bash
# 소스코드를 내려받고 내부 빌드 스크립트 실행
git clone https://github.com/paul-nameless/agweb.git
cd agweb
./scripts/build.sh

# 빌드된 바이너리를 시스템 경로에 심볼릭 링크로 연결
build/Agweb.app/Contents/Helpers/agweb install-cli

# Claude Code 및 Codex용 자동 스킬 등록
agweb install-skill
```

설정이 완료된 후 일상적으로 자주 사용하는 핵심 명령어는 다음과 같다:

```bash
# 대상 웹 페이지 열기, 데몬이 미실행 상태이면 자동 구동
agweb -w work-01 open https://news.ycombinator.com

# 현재 페이지의 정제된 Markdown 본문 추출
agweb -w work-01 text

# 포커스를 뺏지 않고 CAPTCHA나 2차 인증을 사람에게 임시 위임
agweb -w work-01 ask "팝업 창에서 SMS 인증번호 입력을 완료해 주세요"

# 세션의 전체 조작 영상을 MP4 포맷으로 녹화
agweb -w work-01 video-start ./session-demo.mp4
agweb -w work-01 click 'text="Submit Order"'
agweb -w work-01 video-stop
```

## 제약 사항과 포기 기준: 어떤 환경에서 쓰면 안 되는가?

장점을 많이 이야기했지만 물리적인 한계와 절충점도 솔직하게 밝혀 두어야 한다. 엔지니어링에 공짜 점심은 없다.

도입 전 반드시 따져보아야 할 세 가지 기준선은 다음과 같다:

첫째, macOS 및 네이티브 WebKit에 엄격히 종속된다. Ubuntu나 Debian 서버, 혹은 Linux 기반 Docker 컨테이너에서 헤드리스 CI 파이프라인을 돌려야 한다면 Agweb은 실행조차 되지 않는다. 그런 환경에서는 주저 없이 Playwright를 사용해야 하며 여기서 시간을 낭비해서는 안 된다.

둘째, Chrome 전용 CDP 프로토콜 생태계를 지원하지 않는다. WebKit 기반이므로 Chrome 전용 확장 프로그램이나 Chrome DevTools 전용 디버깅 프로토콜에 의존하는 테스트는 전혀 호환되지 않는다.

셋째, 고도화된 안티 봇 우회 능력의 한계다. 내장된 uBlock Origin 규칙 목록이 4일마다 자동 갱신되지만, 정적 도메인 및 CSS 요소 필터링 수준에 머문다. Cloudflare Turnstile 같은 강력한 동적 지문 챌린지를 돌파할 수는 없다. 이러한 하드코어 사이트를 상대할 때는 헤드리스 스크립트로 억지 돌파하려 하지 말고 일반 대화형 브라우저로 전환해야 한다.

Mac을 주력 머신으로 사용하고, 일상적으로 Playwright의 커서 강탈에 시달리며, 터미널에서 Claude Code나 Codex를 주로 실행하는 개발자라면 Agweb은 시도해 볼 가치가 충분하다. 빌드를 마친 후 사내 시스템을 한 번 돌려보고, 커서가 자신의 코드 줄 끝에 온전히 머물러 있는지 직접 확인해 보길 바란다.
