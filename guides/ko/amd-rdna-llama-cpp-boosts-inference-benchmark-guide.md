그래픽카드 냉각 팬이 갑자기 고음으로 회전하기 시작했습니다.

분당 회전수는 순식간에 2800 RPM까지 치솟았습니다.

터미널의 텍스트 생성 속도는 초당 35 토큰에 머물러 있었습니다.

느리다고 볼 수는 없지만, 24GB VRAM과 96개 컴퓨트 유닛을 갖춘 Radeon RX 7900 XTX에서 공식 llama.cpp가 이 정도 성능에 머무는 것은 아쉬운 일이었습니다.

스트림 프로세서 상당수가 유휴 상태였고, 메모리 버스 대역폭 판독값은 이론 한계치의 30%에도 미치지 못했습니다.

먼저 테스트 경계 조건을 명확히 밝힙니다: 단일 카드, 단일 모델, 16k 컨텍스트 윈도우, 호스트 환경 ROCm 6.2.4. 본문에 제시된 수치는 해당 특정 환경의 실측값이며 모든 하드웨어로 무조건 일반화할 수 없습니다.

동일한 모델 가중치: Swift-1.5-Qwen3.8-27B-GGUF.

동일한 양자화 정밀도: Q6_K_L.

토큰 생성 속도는 즉시 초당 55 토큰으로 뛰어올랐습니다.

프롬프트 사전 처리 속도는 712에서 1318까지 더욱 가파르게 상승했습니다.

커널을 교체하면서 모델 정밀도가 훼손되지는 않았을까, 생성 품질이 무너지지는 않았을까.

터미널 로그를 확인하며 세부 사항을 면밀히 분석했습니다.

## 범용 추론의 추상화 비용과 벤치마크 조작 갈래의 등장

로컬 추론 환경은 현재 까다로운 갈림길에 마주해 있습니다.

llama.cpp로 대표되는 통합 프로젝트는 모든 하드웨어를 아우르는 거대한 거점 역할을 수행합니다.

CPU, Apple Metal, NVIDIA CUDA, AMD ROCm, Intel SYCL, Vulkan 등 다양한 플랫폼을 폭넓게 지원해야 합니다.

코드베이스에는 자연스럽게 다수의 범용 추상화 레이어가 자리 잡게 됩니다.

특정 GPU 아키텍처에 깊이 의존하는 어셈블리 패치를 메인 브랜치에 통합하기란 매우 어렵습니다.

메인테이너는 플랫폼 간 안정성을 최우선으로 고려해야 하며, 저수준 메모리 구조를 건드리면 구형 하드웨어에서 오류가 발생할 위험이 있습니다. 이 때문에 메인 브랜치의 업데이트는 빠르지만, 특정 소비자용 그래픽카드에서의 실행 효율은 기초적인 수준에 머무르기 쉽습니다.

그 결과 엔지니어들이 각자의 독자적인 브랜치를 개발하기 시작했습니다.

최근 반년 동안 특정 하드웨어에 특화된 소규모 엔진이 다수 등장했습니다.

Swift와 Zig로 애플 실리콘 통합 메모리를 최대로 활용하는 프로젝트나 모바일 NPU에 맞춰 정적 커널을 융합하는 시도가 대표적입니다.

그러나 이러한 파생 프로젝트 중에는 왜곡된 흐름도 존재합니다.

소셜 미디어에서 비현실적인 속도 수치를 앞세우는 과격한 포크, 예컨대 Strata나 Basalt 같은 프로젝트들입니다.

이들은 16GB VRAM 단일 카드에서 수천억 개 파라미터의 MoE 모델이 놀라운 속도로 동작한다고 주장합니다.

하지만 하드웨어 성능을 뛰어넘는 손쉬운 마법이 존재할 리 없습니다.

코드 구현을 살펴보면 한계가 드러납니다. 처리 속도 수치를 부풀리기 위해 MoE 모델의 라우팅 판단 로직을 임의로 변경했던 것입니다.

모델이 시스템 RAM이나 SSD에 위치한 전문가 가중치를 호출해야 할 시점에 추론 엔진이 이를 무시하고 VRAM에 상주하는 다른 전문가에게 강제로 처리를 떠넘깁니다.

토큰 생성은 매우 빠르게 진행되지만, 출력된 결과물은 문맥을 완전히 잃고 논리가 무너집니다.

추론 품질을 포기하고 얻은 겉포장 속도는 실제 엔지니어링 환경에서 아무런 가치가 없습니다.

라우팅 로직이 조작된 엔진에 실서비스용 코드 생성을 맡길 수 있겠습니까.

저는 결코 맡길 수 없습니다.

## 패치 수정 범위 분석: 웨이브프론트 스케줄링과 온칩 캐시

`llama-cpp-rdna-boosts`의 장점은 수정 범위를 엄격하게 제한한 데 있습니다.

양자화 테이블을 건드리지 않았습니다.

MoE 전문가 선택 로직도 변경하지 않았습니다.

샘플링 알고리즘 역시 원형 그대로 유지했습니다.

주요 수정 사항은 두 가지에 집중됩니다: GEMM 행렬 곱셈의 Wave32 경로 최적화, 그리고 Attention 연산 시 로컬 온칩 메모리 전송 구조 개선입니다.

이는 AMD 하드웨어 세대별 설계 차이에서 기인합니다:

데이터센터용 CDNA 계열, 예를 들어 MI100 및 MI300은 전통적인 Wave64 광폭 웨이브프론트 구조를 취합니다;

반면 소비자용 RDNA 계열, 즉 RX 6000부터 7900 시리즈는 초기부터 네이티브 Wave32 구조와 듀얼 이슈 연산 장치를 갖추고 있습니다.

공식 ROCm 백엔드는 범용 HIP 호환 레이어의 설계를 폭넓게 따릅니다.

상당수 행렬 연산 커널이 여전히 광폭 웨이브프론트 단위로 스레드 블록을 묶습니다.

전문가용 연산 카드에서는 안정적이지만 7900 XTX 같은 게임용 카드에서는 웨이브프론트 대기 지연이 발생하여 메모리 컨트롤러가 데이터를 가져오는 동안 연산 코어가 유휴 상태에 머뭅니다.

`llama-cpp-rdna-boosts`는 이 핵심 GEMM 커널을 재작성했습니다.

웨이브프론트 폭을 RDNA에 가장 적합한 Wave32 크기로 고정했습니다.

동시에 Attention 연산 시 로컬 메모리 전송 경로를 재정비하여 중간 연산 결과가 글로벌 VRAM으로 불필요하게 왕복하지 않고 코어 근처 고속 온칩 캐시에 머물도록 유도했습니다.

하드웨어 모니터링 그래프에 즉각적인 변화가 나타났습니다:

소비전력은 200W 초반에서 정격 한계치 부근까지 정직하게 상승했습니다;

VRAM 읽기 대역폭 또한 고르고 평탄한 고원 형태의 곡선을 기록했습니다.

## 실제 테스트 환경과 컨테이너 배포 절차

세부 환경과 버전 체계를 명시하지 않은 벤치마크는 신뢰하기 어렵습니다.

이번 실측에 투입된 외장 그래픽 독 환경의 하드웨어 구성은 다음과 같습니다:

- GPU 핵심: AMD Radeon RX 7900 XTX 24GB GDDR6, 아키텍처 코드명 Navi 31 및 gfx1100.
- 드라이버 환경: AMD ROCm 6.2.4 유저랜드 패키지, 리눅스 커널 6.11.
- 연결 토폴로지: 썬더볼트 4 외장 그래픽 독 연결, PCIe 4.0 x4 링크 협상, 독립 GPU 렌더링 노드로 인식.
- 토폴로지 손실: 썬더볼트 4의 실효 대역폭은 약 3.2 GB/s입니다. 토큰 생성 중에는 모델 가중치가 VRAM에 상주하므로 대역폭 영향이 거의 없지만, 사전 처리 시에는 대량의 프롬프트를 전송해야 하므로 메인보드 직결 대비 약 8%의 사전 처리 속도 손실이 발생합니다.
- 평가 모델: ukisai 배포 Swift-1.5-Qwen3.8-27B-GGUF, 양자화 규격 Q6_K_L, 가중치 크기 약 21.4 GB.
- 추측 디코딩: 투기 실행 옵션 활성화, 매개변수 `--draft 2`.

버전 표기에 관한 설명:

컨테이너 이미지 태그의 `server-rocm-10.1`에서 10.1은 제작자의 CI 자동 빌드 파이프라인 번호이며 AMD 공식 버전이 아닙니다. 이미지 내부에는 gfx1100 전용으로 컴파일된 ROCm 6.2 런타임이 포함되어 호스트의 6.2.4 드라이버와 정상 호환됩니다.

이미지 내려받기:

```bash
podman pull ghcr.io/stew675/llama-cpp-rdna-boosts:server-rocm-10.1
```

모델 경로를 마운트하고 그래픽 디바이스 노드를 전달하여 구동합니다:

```bash
podman run --rm -it \
    --network=host \
    --device /dev/kfd \
    --device /dev/dri \
    --group-add video \
    -v "$HOME/models:/models" \
    "ghcr.io/stew675/llama-cpp-rdna-boosts:server-rocm-10.1" \
    /llama-server \
    -m /models/Swift-1.5-Qwen3.8-27B-Q6_K_L.gguf \
    --host 0.0.0.0 \
    --port 8080 \
    -ngl 99 \
    -c 16384 \
    --ubatch-size 512 \
    --flash-attn \
    --draft 2
```

도입 과정에서 마주했던 문제:

최초 실행 시 `--flash-attn` 플래그를 누락하자 터미널에 다음 경고가 출력되었습니다:

```text
ggml_cuda_op_flatten: flash attention disabled, falling back to unoptimized rocm attention kernel
```

이 상태에서는 토큰 생성 속도가 초당 38 토큰 수준에 그쳤습니다.

`--flash-attn`을 명시해야만 Wave32 구조에 맞춰 재구성된 Attention 커널이 활성화됩니다.

## 성능 비교와 출력 정밀도 교차 검증

측정 결과를 정리합니다.

동일한 테스트 장비에서 공식 메인 b4120 버전과 패치 적용 버전을 비교하며 긴 코드 생성을 5회 반복 실행한 중앙값을 측정했습니다:

| 런타임 엔진 버전 | 프롬프트 사전 처리 속도 | 토큰 생성 속도 | 상주 VRAM 용량 | 회귀 테스트 통과율 |
| :--- | :--- | :--- | :--- | :--- |
| 공식 메인 llama.cpp b4120 | 712 t/s | 35.2 t/s | 21.8 GB | 100% |
| rdna-boosts 전용 패치 버전 | 1318 t/s | 55.4 t/s | 22.1 GB | 100% |

실측 수치의 객관적 사실:

사전 처리 처리량은 초당 712에서 1318 토큰으로 향상되었습니다;

토큰 생성 속도는 초당 35.2에서 55.4 토큰으로 가속되었습니다;

상주 VRAM 사용량은 21.8GB에서 22.1GB로 약 300MB 소폭 증가했는데, 이는 Wave32 연산을 위해 사전에 정적으로 할당된 워크스페이스에 따른 것입니다.

주의할 점은 이 수치가 단일 카드, Q6_K_L 양자화, 16k 컨텍스트라는 특정 조건에서의 결과이며 모든 모델과 초장문 환경으로 무작정 확대 해석해서는 안 된다는 사실입니다.

품질 검증을 위해 복잡한 파이썬 알고리즘과 타입 힌트를 포함한 50개 과제를 대상으로 회귀 테스트를 수행했습니다:

양측에서 생성된 코드 구문 트리는 바이트 단위로 일치하며 통과율 100%를 달성했습니다;

200개 기술 질의응답 검증 세트에서 Perplexity 변동 폭은 1만 분의 3 미만이었습니다.

초장문 컨텍스트에서의 미세한 품질 변화를 완전히 배제하려면 32k 이상 환경에서 logits 차분 샘플링 검증이 지속되어야 할 것입니다.

하지만 현재 일상 개발 환경에서는 의미적인 품질 저하가 관측되지 않았습니다.

## 적용 한계와 버전 고정 운영의 대가

이 브랜치는 특정 버전을 고정하여 운영하는 용도에 알맞습니다.

수정 범위가 RDNA3의 GEMM과 캐시 전송에 집중되어 있고 라우팅이나 양자화를 건드리지 않아 문제 발생 시 원인 분석이 명확합니다.

그러나 감수해야 할 한계도 뚜렷합니다:

패치가 공식 메인 b4120과 같은 특정 커밋에 종속되어 있습니다.

공식 llama.cpp는 핵심 로직을 수시로 개편합니다. KV 캐시 풀 관리 방식이나 배치 스케줄링 구조가 바뀌면 독자 패치는 번거로운 리베이스 작업을 거쳐야 합니다.

실무 개발 환경에서 이 방식을 사용할 경우 다음 지침을 권장합니다:

첫째, 검증된 컨테이너 다이제스트 또는 태그를 엄격히 고정하고 최신 빌드를 맹목적으로 따라가지 말 것;
