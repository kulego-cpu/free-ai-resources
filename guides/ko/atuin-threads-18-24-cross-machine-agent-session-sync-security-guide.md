원격 리눅스 개발 서버에서 `Claude Code`로 디스크 IO 병목을 파고들다가 노트북을 덮고, MacBook으로 돌아와 `Codex`로 작업을 이어가려 하면 늘 같은 벽에 막힌다. 두 장비의 세션 기록이 서로 완전히 단절되어 있기 때문이다.

에러 로그를 다시 복사해 붙일 것인가. 방금 전까지 30분 동안 밟았던 시행착오를 새 창에 처음부터 다시 설명할 것인가. 두 번만 겪어도 금방 질린다.

어제 Atuin이 `18.24` 버전에 `Threads`를 정식으로 올렸다. 발상은 단순하다. 500줄만 넘어가면 잘리는 `.bash_history`를 암호화 동기화로 해결했던 것처럼, `Claude Code`나 `Codex`, `OpenCode`가 홈 디렉터리에 남기는 추가 전용 로그 역시 같은 동기화 엔진에 태우겠다는 것이다.

이 글의 근거는 세 곳뿐이다. `blog.atuin.sh/threads-agent-sessions/`, `github.com/atuinsh/atuin` 저장소의 `v18.24.6` 릴리스 노트, 그리고 Hacker News 스레드 `50453637`의 댓글 80여 개다. 여러 대의 사설 동기화 서버를 띄워 부하 테스트를 돌릴 여건은 없었으므로 지연 시간이나 처리량 수치는 적지 않는다.

## Hook 없이 로컬 세션 파일을 직접 파싱하는 방식

처음 교차 도구 이어받기라는 설명을 봤을 때는 Atuin이 각 에이전트 CLI마다 전용 플러그인을 심는 줄 알았다.

댓글에서 메인테이너 `ellieh`가 직접 밝힌 내용을 보니 그게 아니었다. 현재 `Threads`는 Hook을 전혀 쓰지 않는다. 각 코딩 도구가 이미 로컬에 저장하고 있는 세션 파일을 직접 파싱해 대화 턴, 실행 명령, 오류 출력을 인덱싱한다.

현재 지원하는 도구는 `Claude Code`, `Codex`, `Pi`, `Omp`, `OpenCode` 다섯 가지다.

설치와 활성화는 명령어 세 줄로 끝난다.

```bash
curl --proto '=https' --tlsv1.2 -LsSf https://setup.atuin.sh | sh
atuin resume
atuin mcp install claude
```

`atuin resume`을 실행하면 터미널 TUI가 열린다. 키워드로 예전 세션을 검색할 수 있고, 원격 개발 서버에서 하던 스레드를 로컬로 포크해 다른 하네스로 이어갈 수도 있다. `atuin mcp`까지 연결하면 새로 연 에이전트가 과거 트러블슈팅 기록을 스스로 조회한다.

물론 구조적인 약점도 바로 보인다. 세션 로그는 엄격한 DB 스키마가 아니다. 도구마다 포맷이 수시로 바뀌고, 당장 `Claude Code`의 셸 편집 diff만 해도 별도 패치를 얹어야 했다. 업스트림 CLI가 필드 이름 하나만 바꿔도 수집기가 조용히 데이터를 놓치지 않을까.

## v18.24.6 패치 노트에서 드러난 구현상의 거친 모서리

출시 직후부터 `atuinsh/atuin`은 벌써 `18.24.6`까지 패치가 이어졌다. 홍보 문구보다 릴리스 노트의 수정 내역이 현재 완성도를 훨씬 솔직하게 보여준다.

- **셸 종료 시 무한 행**: 커밋 `4668`은 백그라운드 데몬 자동 실행 전에 상속된 파일 디스크립터를 닫지 않아 셸 종료 시 `pty-proxy`가 무한 대기하던 결함을 고쳤다.
- **macOS 소켓 관리 충돌**: 커밋 `4669`는 `launchd`를 통한 소켓 관리를 제거했다. 애플 환경의 서비스 감독 체계와 데몬 기동 경로가 충돌했기 때문이다.
- **Claude Code diff 누락과 키 기록**: `threads` 쪽에도 두 가지 패치가 들어갔다. 셸 편집에서 나온 diff 수집을 보강했고, `atuin` 키 이름이 포함된 쓰기 패치를 보존하도록 수정했다.
- **MCP 의존성 보안 패치 지연**: 커밋 `4690`으로 `rmcp` 보안 권고 세 건은 반영됐지만, SQLite 관련 수정은 `sqlx` 호환성 문제로 아직 묶여 있다.

`4668` 항목을 보고 나도 내 로컬 터미널 프로세스를 다시 확인했다. 백그라운드 데몬을 여러 개 띄워 쓰는 환경에서는 FD 누수로 셸이 좀비처럼 걸리는 문제만큼 피곤한 게 없다. 아직 패치가 빠르게 쏟아지는 시기인 만큼 주력 업무 장비에 바로 상시 구동을 걸 때는 롤백 경로를 먼저 챙겨두는 편이 안전하다.

신호 대 잡음비 문제도 만만치 않다. Superlogical Rex를 만드는 `nzoschke`는 코딩 세션의 상당수가 일회성 실험인데 이를 전부 전역 기록에 쌓으면 정작 중요한 맥락이 묻힐 수 있다고 지적했다. 반대로 `justCallMeOmid`는 작업 항목별 디렉터리에만 로그를 두고, 일이 끝나면 원본 대화는 지운 뒤 짧은 결정 요약만 벡터 DB에 남기는 방식을 택했다.

## 보안에 민감한 개발자들이 선을 긋는 진짜 이유

`Threads` 보안을 이야기할 때 많은 사람이 종단간 암호화 여부만 따진다.

암호학적인 설계 자체는 깔끔하다. 배포 방식은 크게 세 갈래로 나뉜다.

**완전 로컬 모드** — 데이터는 `~/.local/share/atuin`에만 머물고 외부 서버로 나가지 않는다. 다만 같은 호스트 안에서 샌드박스 격리가 되지 않은 다른 프로세스나 무심코 돌린 서드파티 스크립트는 접근할 수 있다. 단일 장비 검색과 백업 용도라면 이걸로 충분하다.

**자체 서버 구축** — 사내 서버나 집 NAS에 동기화 서버를 두는 형태다. 키 배포를 직접 관리해야 하고, 일단 에이전트가 `atuin mcp`로 접근 권한을 얻으면 내부에서는 평문으로 읽힌다. 암호화는 전송 구간만 지킬 뿐 인가된 단말 안에서는 열려 있다.

**공식 호스팅 E2EE** — 클라이언트에서 암호화한 뒤 업로드하므로 운영 측도 원문을 읽지 못한다. 대신 등록된 단말 중 한 곳만 키가 탈취돼도 전체 동기화 이력이 노출된다는 전제를 받아들여야 한다. 버그가 아니라 공유 이력 구조가 갖는 필연적 대가다.

Hacker News의 `petesergeant`는 바로 이 지점 때문에 도입을 거절했다. 몇 달 동안 에이전트별 샌드박스 격리, 분리된 암호화 자격 증명 저장소, 정기 로그 스캔까지 구축해 놓았는데, 모든 장비의 세션을 하나의 교차 검색 풀로 합치면 어렵게 만든 격리 경계가 한꺼번에 무너지기 때문이다.

도구 권한 설정은 이 경로를 더 취약하게 만든다.

`ahmedketata`가 짚었듯이 `Claude Code`에서 실수로 영구 허용을 한 번 누르면 민감한 명령이 평문으로 `.claude/settings.local.json`에 남는다. 이 조각이 세션 로그를 타고 동기화 큐로 들어간다. 전송 구간이 암호화돼 있어도 신뢰도가 낮은 다른 에이전트가 `atuin mcp`로 조회하면 그대로 노출된다. 이 흐름을 한참 들여다봤지만 뾰족한 해법이 떠오르지 않았다. 모든 사용자가 매번 settings 파일을 감사하리라 기대할 수는 없다.

절충안도 있다. `dietr1ch`는 중앙 동기화 서버 대신 민감 정보를 걸러낸 백업본만 `Syncthing`으로 묶고 로컬에서 `grep`과 `skim`으로 검색한다. 하네스 간 즉각적인 포크는 포기하는 대신 장비별 권한 경계를 분명히 지킬 수 있다.

## 써도 되는 상황과 로컬에 묶어둬야 할 상황

물론 실전에서의 효용도 분명하다. 댓글에서 `nklmilojevic`은 커밋하지 않은 `git worktree`를 실수로 날렸을 때 `Atuin Threads` 기록 덕분에 수정 내역을 복구했다고 전했다. 단순 `.bash_history`로는 단일 호스트 `grep` 이상을 기대하기 어렵고, 장비가 바뀐 작업이나 지워진 worktree 맥락까지는 되살리지 못한다.

그래서 내 기준에서는 도입 범위를 둘로 쪼개서 가져간다.

- 개인 실험 장비와 비기밀 저장소: `Atuin 18.24.6+`에서 `atuin resume`을 켜고 리눅스 개발기와 MacBook 사이에서 `Claude Code`와 `Codex` 조사 맥락을 이어간다.
- 운영 키, 사내 인증 정보, 고객 데이터가 있는 장비: 크로스 머신 동기화를 끄고 자율 에이전트에 `atuin mcp`를 전역 마운트하지 않으며, 보관이 필요할 때도 로컬 정규식 마스킹을 먼저 거친다.

직접 켜보기 전에 아래 세 가지는 먼저 확인하는 편이 좋다.

1. `atuin --version`을 확인해 `pty-proxy` FD 누수 행이 수정된 `18.24.6` 이상인지 점검한다.
2. `atuin mcp install`을 실행하기 전에 `.claude/settings.local.json`과 `.env` 이력을 훑어 실제 토큰이 세션 로그에 섞이지 않았는지 본다.
3. 개인 노트북과 회사 배스천 서버에 같은 동기화 계정을 물린다면, 배스천 작업 기록까지 집 PC로 내려받아도 정말 괜찮은지 따져볼 일이다.
