당신의 데스크톱 환경에 도대체 몇 개의 Chromium 브라우저 엔진이 상주해야 하는가?

이 생각은 오랫동안 제 머릿속을 떠나지 않았습니다.

일상적인 업무 시작. 터미널에는 컴파일 작업이 돌고 있습니다.

시중의 흔한 AI 데스크톱 클라이언트를 가볍게 실행합니다. 프롬프트를 한 자도 타이핑하기 전에 작업 관리자에는 4개의 보조 프로세스가 일제히 등장합니다.

메모리 점유율은 순식간에 800MB를 넘어섭니다. 잠시 방심하면 금세 1.2GB로 치솟습니다.

노트북 팬이 시끄럽게 돕니다. 참으로 거슬립니다. 이런 낭비를 누가 견딜 수 있을까요?

솔직히 말해 우리는 그저 글자를 입력하고 SSE 스트림을 받으며 옆에 파일 결과물을 띄워둘 가벼운 도구가 필요할 뿐입니다. 어째서 수십 메가바이트짜리 웹 브라우저 렌더링 엔진을 백그라운드에 늘 띄워두어야 하는 걸까요?

며칠 전 오픈소스 커뮤니티에서 GitHub의 `Scronkfinkle/byob` 프로젝트를 접했습니다.

전체 이름은 Bring Your Own Brain.

최신 commit 8f2a1b9 체크아웃. 코드베이스는 Rust 2024 edition 기반으로 빌드되며, 의존성은 egui 0.29 및 wgpu 0.20에 고정되어 있습니다.

핵심 셀링 포인트는 명쾌합니다: 100% 순수 Rust 작성, Electron 의존성 제로, GPU 하드웨어 가속 직결 렌더링, 자체 결과물 보드 및 안전 샌드박스 탑재.

크기는 극도로 작습니다.

`cargo build --release`로 빌드한 경량 바이너리는 약 13MB에 불과합니다. 보조 도구와 확장 의존성을 전부 패키징해도 배포 디렉터리 전체가 58MB 안팎에 머뭅니다.

실제 상주 메모리는 과연 얼마나 될까요?

메모리 측정은 기준과 도구를 투명하게 밝히지 않으면 무의미합니다.

Linux 테스트 머신에서 `ps_mem` 도구로 PSS 물리 상주 메모리를 측정한 결과, 콜드 스타트 유휴 상태에서 약 41MB를 기록했습니다.

macOS 14 Apple Silicon 머신에서는 활성 상태 보기의 상주 메모리가 약 38MB로 집계되었습니다. 이 3MB 차이는 macOS가 시스템 동적 공유 라이브러리의 일부를 프로세스 상주 공간에 포함하기 때문입니다.

우측 결과물 패널에 200KB Markdown 파싱 문서를 띄우고 대화 히스토리를 30회 누적한 상태에서도 피크 메모리는 85MB 이내로 철저히 억제되었습니다. 수백 턴의 초장문 컨텍스트나 대용량 고해상도 이미지를 쏟아부었을 때 100MB를 넘길지는 아직 제 환경에서 거기까지 극한 부하를 걸어보지 않았습니다.

창 드래그 조작감은 극도로 매끄럽습니다.

120Hz 고주사율 디스플레이 환경에서 화면이 하드웨어 수직 동기화 신호에 직접 맞물려 커서 움직임에 일말의 버벅임도 없습니다.

화면 하얗게 멈추는 현상도 없고, 웹 런타임의 수화 지연으로 인한 답답함도 전혀 없습니다.

이 놀라운 경량성은 어떤 엔지니어링 절충을 거쳐 탄생한 것일까요? 과연 성숙한 상용 클라이언트를 완전히 대체할 수 있을까요?

## 아키텍처 해부: 데스크톱에서 Electron과 비동기 Tokio를 걷어낼 수 있었던 이유

byob의 Cargo 워크스페이스를 열어보면 역할이 아주 깔끔하게 분리되어 있습니다.

프로젝트는 크게 세 가지 핵심 크레이트로 나뉩니다:

- `byob-agent`: 상태 머신 스케줄링, 컨텍스트 축소, 툴 호출 루프 및 승인 흐름을 담당하는 헤드리스 엔진;
- `byob-protocol`: 프로세스 간 및 네트워크 통신 이벤트 페이로드를 규정하는 프로토콜 정의;
- `byob-ui-egui`: 즉시 모드 GUI 프레임워크 egui와 wgpu를 기반으로 구축된 네이티브 그래픽 인터페이스.

가장 놀라웠던 점은 `byob-agent` 내부의 I/O 모델 선택이었습니다.

현대 Rust 네트워크 생태계는 tokio가 사실상 독점하고 있습니다. 통신 코드를 작성한다면 으레 async/await 패키지를 떠올립니다.

하지만 이 에이전트 엔진은 정반대 설계를 택했습니다: 경량 동기 블로킹 스레드와 스레드 간 채널의 조합입니다.

개발자가 게으름을 피운 것일까요?

`byob-agent/src/runtime.rs`를 들여다보고 바로 납득했습니다——작성자는 애초에 수만 개 동시 접속 같은 고병렬 환경을 고려할 생각이 없었습니다. 스레드 풀 상한선은 8개로 엄격히 고정되어 있으며, 초과 작업은 큐에서 차례를 기다립니다.

단일 사용자가 쓰는 데스크톱 프로그램에서 동시에 수십 개 추론 스트림을 뿜어낼 일이 과연 있을까요?

한 스레드가 수신 스트림을 블로킹 방식으로 읽고, 다른 스레드가 도구 실행을 처리하며, 고정 길이 채널로 이벤트를 주고받습니다. 구조는 이게 전부입니다.

이 미니멀한 I/O 모델에도 현실적인 대가는 따릅니다. 긴 컨텍스트 히스토리를 재생할 때 고정 길이 채널이 막히는 현상이 발생하여 버퍼 크기를 수동으로 넓혀주어야 했습니다. 초기 테스트에서 이 문제로 잠시 헤맸습니다.

유휴 상태에서 CPU 사용률은 0%에서 0.8% 사이를 미세하게 오갈 뿐입니다. `top` 프로세스 목록에서도 거의 눈에 띄지 않습니다.

단축키를 누르면 창이 즉각 튀어나옵니다. 이 물리적인 즉각 반응은 무거운 Webview 껍데기로는 결코 맛볼 수 없는 쾌감입니다.

## 로컬 두뇌 핫스왑: Ollama 및 표준 규격 API 연동 실전

흔한 로컬용 데스크톱 도구들이 가장 눈살을 찌푸리게 만드는 부분은, 설치 프로그램 안에 독자 변조된 llama.cpp나 특정 양자화 모델을 억지로 끼워 파는 행태입니다.

다운로드는 한 세월이고 수 기가바이트의 디스크 용량이 증발합니다.

byob는 철저한 순수 클라이언트 노선을 걷습니다: 가중치 파일을 일절 포함하지 않고 모델 선택권을 온전히 사용자에게 넘깁니다.

로컬 머신이나 사내 네트워크에 구동 중인 추론 서비스만 있다면 URL 하나로 즉시 연동됩니다.

가장 대표적인 짝꿍은 로컬의 Ollama입니다.

터미널에서 명령어 한 줄로 모델을 기동합니다:

```bash
ollama run qwen2.5:14b
```

기본적으로 Ollama는 로컬 포트에서 OpenAI 호환 규격의 REST 인터페이스를 엽니다.

byob 설정 창으로 들어가 프로토콜을 OpenAI 규격으로 맞춥니다. 엔드포인트에 `http://localhost:11434/v1`을 입력하고 API 키 항목은 비워두거나 임의의 문자를 채웁니다.

이것으로 끝일까요? 무슨 함정이 있을까요?

테스트 도중 미묘한 호환성 걸림돌을 만났습니다: 도구 호출 스키마 파싱 문제입니다.

7B나 8B 규모의 소형 오픈소스 모델들은 엄격한 JSON Schema 형식의 도구 정의를 해석하다가 자주 오류를 뿜습니다.

닫는 괄호를 빼먹거나 호출 인자 페이로드를 엉망진창 문자열로 뭉개버리곤 합니다.

클라이언트가 표준 tool_calls 규격만을 고집하면 대화 전체가 에러와 함께 멈춰섭니다.

byob는 여기에 노련한 대비책을 마련해두었습니다: 구조화 프롬프트 폴백 메커니즘입니다.

대상 엔드포인트가 함수 호출을 네이티브로 지원하지 못하거나 소형 모델이 스키마 검증에 계속 실패할 경우, 시스템 프롬프트에 미리 정의된 XML 태그를 자동으로 주입합니다.

모델이 텍스트 블록 형태로 도구 실행 의도를 방출하도록 유도합니다:

```xml
<tool_call>
<name>read_file</name>
<arguments>
{"path": "src/main.rs"}
</arguments>
</tool_call>
```

클라이언트가 이 XML 블록을 중간에서 가로채 즉석에서 파싱하여 로컬 도구를 실행합니다.

이 폴백 설계가 큰 힘을 발휘했습니다.

사양이 넉넉지 않은 노트북에서 Qwen2.5-7B를 구동하더라도, 네이티브 툴 호출 기능에 의존하지 않고 로컬 파일 탐색 작업을 매끄럽게 수행할 수 있습니다.

## 분할 결과물 패널과 안전 샌드박스: Bubblewrap 격리 기술

Claude 웹 버전을 써보신 분들이라면 누구나 Artifacts 결과물 창의 편리함을 기억하실 것입니다.

왼쪽에서 대화를 나누는 동안 오른쪽 분할 패널에서 표, 차트, 상호작용 가능한 가벼운 웹 애플리케이션이 실시간으로 렌더링됩니다.

byob는 이 인터랙션을 순수 Rust 데스크톱 환경으로 그대로 가져왔습니다.

채팅창 옆에는 독립된 결과물 워크벤치가 상주합니다:

- Markdown 및 코드 강조 문서: 리비전 이력을 보존하며 자유로운 전후 비교 지원;
- 벡터 그래픽 및 동적 차트: GPU 프래그먼트 셰이더로 직접 래스터화하여 부드러운 확대 축소 지원;
- 구조화 테이블: 뷰포트 행 가상화 기법을 적용하여 화면에 보이는 영역만 렌더링하므로 수십만 행 CSV를 불러와도 UI가 멈추지 않습니다.

더욱 중요한 것은 보안에 대한 확신입니다.

파일 수정과 셸 실행 권한을 자율 에이전트에게 통째로 넘기는 것은 누구에게나 불안한 일입니다.

많은 개발자가 에이전트 도구를 꺼리는 이유는, 모델이 오작동하여 작업 공간에 위험한 일괄 삭제 명령을 실행할까 두렵기 때문입니다.

byob는 실행 파이프라인에 2중 방어선을 구축했습니다.

첫 번째 방어선은 명시적 승인 카드입니다.

모델이 로컬 파일을 변경하려 할 때 클라이언트는 디스크에 곧장 쓰지 않고, 녹색과 붉은색으로 표기된 통합 diff 카드를 화면에 띄웁니다.

추가된 줄과 삭제된 줄이 투명하게 드러납니다. 에이전트가 단독으로 처리할 수 있는가? 불가능합니다.

사람이 마우스로 승인 버튼을 누르지 않는 한 실제 변경 사항은 디스크에 반영되지 않습니다.

실수로 잘못 승인했다 하더라도 턴 단위 언두 기능을 통해 작업 디렉터리를 원클릭으로 되돌릴 수 있습니다.

두 번째 방어선은 Linux 환경의 로우레벨 컨테이너 격리입니다.

무거운 Docker 데몬을 띄우는 대신 경량 유틸리티인 `bwrap`을 직접 통합했습니다.

Linux 사용자 네임스페이스를 활용하여 하위 프로세스를 안전한 보호망 안에 가둡니다:

```bash
bwrap \
  --ro-bind /usr /usr \
  --ro-bind /lib /lib \
  --tmpfs /tmp \
  --proc /proc \
  --dev /dev \
  --bind ./scratch ./scratch \
  --unshare-all \
  --die-with-parent \
  python3 script.py
```

이 스크립트를 참고할 때는 다음 세부 사항을 반드시 주의 깊게 확인해야 합니다:

흔히 보이는 `--ro-bind /lib64 /lib64` 옵션을 의도적으로 제외했습니다. Arch Linux나 일부 경량 Fedora 환경에는 독립된 `/lib64` 디렉터리가 존재하지 않으며, 이를 포함하면 bwrap이 No such file or directory 치명적 에러를 뱉으며 샌드박스가 즉시 꺼집니다.

`--proc /proc`과 `--dev /dev`는 절대 생략할 수 없습니다. `/dev/urandom` 디바이스가 없으면 Python 인터프리터가 초기화 과정에서 에러도 없이 멈춰버립니다. 이 원인을 추적하느라 30분 넘게 진땀을 뺐습니다.

`--unshare-all` 플래그는 네트워크 연결까지 차단하여 외부 유출을 원천 방어합니다. 통신이 필요한 스크립트라면 명시적으로 `--share-net`을 전달해야 합니다.

모든 파괴적 영향력은 임시 샌드박스 디렉터리 내부에 완벽히 봉인됩니다. 대단히 든든합니다.

## 현장의 솔직한 한계와 미해결 과제: 메인 업무 머신으로 적합한가?

가벼움과 저전력 특성을 높이 평가했지만, 현장의 거친 현실도 직시해야 합니다.

이 도구를 일상 업무의 주력 도구로 삼으려 한다면 몇 가지 복병을 미리 알아두어야 합니다.

첫째는 그래픽 파이프라인 업데이트로 인한 불안정성입니다.

`wgpu 0.20`으로 올린 후, Arch Linux Wayland 환경에서 창 크기를 조절할 때 화면 전체가 검게 깜빡이며 프레임 드롭이 발생했습니다. 문제를 피하고자 임시로 의존성을 `wgpu 0.19`로 고정해두었습니다.

둘째는 CJK 폰트 렌더링의 불편함입니다.

egui 내장 폰트 라이브러리에는 완전한 한중일 한자 글리프가 들어있지 않습니다.

소스를 내려받아 그대로 빌드하면 한글 입력 시 화면 전체가 하얀 두부 모양의 깨진 사각형으로 뒤덮입니다.

한글을 정상 출력하려면 설정 파일에 시스템 폰트 경로를 직접 명시해야 합니다:

```toml
[ui.font]
family = "Noto Sans CJK SC"
size = 14.0
```

코드 레벨에서 동적 폰트 검색 로직을 추가하는 작업도 가능하지만, 일반 사용자에게는 진입 장벽이 꽤 높습니다.

셋째는 복잡한 웹 결과물 렌더링의 한계입니다.

순수 Rust 환경에서 현대 웹 프론트엔드를 완전무결하게 렌더링하는 것은 업계 공통의 난제입니다.

실험적인 Servo 모듈을 도입하고 있지만, 클라이언트 사이드 수화 로직이 복잡한 웹 앱을 띄우면 스타일 왜곡이나 스크립트 타임아웃이 간헐적으로 발생합니다.

이 영역에서만큼은 Electron이 오랜 세월 쌓아 올린 웹 호환성의 벽이 여전히 높습니다.

저는 이 38MB짜리 경량 도구를 메인 머신에서 2주간 실사용해왔으며, 무거운 클라이언트로 되돌아갈 생각은 없습니다.

하지만 일반 사용자에게 무작정 추천할 만큼 다듬어진 상태는 아닙니다——폰트 설정 수작업, 웹 결과물 렌더링 제약, Windows 환경에서의 장기 검증 부족 등이 남아있습니다.

이런 빈틈들은 향후 오픈소스 커뮤니티의 기여를 지켜보아야 할 것입니다. 일정이 밀려 있어 당장 제가 Wayland 화면 프레임 드롭 수정 PR을 보낼 여력은 없습니다.

웹 브라우저의 무거운 껍데기를 완전히 벗어던진 이 순수 네이티브 노선이 긱을 위한 미래의 작업 환경이 될 수 있을까요?
