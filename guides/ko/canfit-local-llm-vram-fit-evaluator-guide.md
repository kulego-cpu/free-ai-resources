밤새 다운로드를 걸어두고 다음 날 아침 터미널을 열었을 때 메모리 부족 오류로 멈춰 있는 상황. 로컬 거대 언어 모델을 다뤄본 엔지니어라면 누구나 한 번쯤 겪어보았을 난관입니다.

얼마 전 연구실에서 한 실습생이 RTX 4070 12GB 장비에서 코딩 모델을 구동하려 시도했습니다. 그는 3시간 넘게 걸려 약 20GB 크기의 32B 양자화 가중치를 받았습니다. 하지만 첫 프롬프트를 입력하고 엔터를 누르자마자 프로세스가 튕겼습니다. VRAM이 한계에 달해 드라이버가 연산을 시스템 메모리로 넘겼고, 토큰 생성 속도는 초당 1.2개로 곤두박질쳤습니다. 밤새 받은 파일이 첫 대화조차 제대로 수행하지 못하는 헛수고가 된 셈입니다.

로컬 배포에서 가장 흔한 실수는 모델 파일의 디스크 용량만 보고 판단하는 것입니다. 12GB 그래픽카드에 10GB 가중치가 들어가니 남은 2GB로 충분히 대화할 수 있다고 믿기 쉽지만, 이 계산은 완전히 빗나간 것입니다. 오늘 다룰 Rust 기반 오픈소스 CLI 도구 `canfit` [v0.2.1 버전, GitHub 저장소 federicolaterra/canfit]은 가중치를 내려받지 않고도 이러한 시행착오 비용을 사전에 차단합니다.

## 1. 정적 파일 크기만으로 판단하면 실패하는 이유

추론 실행 시 물리 메모리는 구체적으로 어디에 소모될까요? 실제 VRAM 장부의 구성을 명확히 파악해야 합니다.

실행 중인 추론 환경에서 메모리 소모는 단일 항목이 아니라 네 가지 고정 비용이 중첩되어 발생합니다:

```
+-------------------------------------------------------------+
|                 GPU 물리 VRAM 전체 구조 [예: 12GB]          |
+-------------------------------------------------------------+
|  1. 운영체제 및 데스크톱 화면 렌더링 상주 [600MB - 1.2GB]   |
+-------------------------------------------------------------+
|  2. 런타임 및 CUDA Context 기본 점유 [300MB - 600MB]        |
+-------------------------------------------------------------+
|  3. 모델 정적 읽기 전용 가중치 [GGUF / AWQ / EXL2 데이터]  |
+-------------------------------------------------------------+
|  4. 동적 KV Cache 풀 [컨텍스트 길이에 비례해 선형 증가]    |
+-------------------------------------------------------------+
|  5. 순방향 연산 스크래치 버퍼 [임시 활성화 텐서 재사용]     |
+-------------------------------------------------------------+
```

많은 이들이 1번과 4번 항목을 간과합니다. Windows 환경에서는 DWM 윈도우 관리자와 브라우저 하드웨어 가속이 약 1GB의 VRAM을 상시 점유합니다. Linux 환경에서도 X11이나 Wayland 컴포지터가 수백 메가바이트를 소모합니다.

더 위험한 요소는 동적 KV 캐시의 증가입니다. 64개 레이어, 8개 GQA 헤드, 단일 헤드 차원 128로 설계된 32B 모델의 경우, 표준 fp16 정밀도 적용 시 1024개 컨텍스트 토큰마다 정확히 256MB의 물리 VRAM이 추가 소모됩니다.

2GB 여유가 남아 있는 것처럼 보여도 컨텍스트를 8k까지만 늘리면 KV 캐시 단독으로 2GB를 전부 삼켜버립니다. 드라이버 기본 오버헤드가 더해지는 순간 메모리는 즉시 한계를 초과하여 강제 종료됩니다.

## 2. canfit의 동작 메커니즘: 메타데이터 기반 초고속 산출

기존 방식은 수십 기가바이트에 달하는 가중치를 전부 다운로드한 뒤 엔진을 띄워 로그를 확인하는 수밖에 없었습니다. 메모리가 부족할 경우 몇 시간에 걸친 네트워크 대역폭과 대기 시간이 허공으로 사라집니다.

`canfit`의 접근 방식은 매우 효율적입니다. Hugging Face API를 통해 대상 모델의 `config.json`과 메타데이터만 조회하며, 대용량 가중치 파일은 일절 내려받지 않습니다.

도구가 추출하는 핵심 파라미터는 명확합니다:
- `num_hidden_layers`: 전체 레이어 수
- `num_key_value_heads`: GQA 비율을 판별하는 Key-Value 헤드 수
- `head_dim` 또는 `hidden_size`: 단일 헤드 차원 및 은닉층 너비
- 양자화 규격: GGUF 또는 AWQ 비트 폭 계수를 통한 가중치 용량 환산

```
[canfit 실행 흐름]
모델 식별자 및 양자화 규격 지정
   ↓
원격 config.json 수신 [수 킬로바이트 수준]
   ↓
레이어 수, 헤드 수, 은닉 차원, GQA 비율 분석
   ↓
목표 컨텍스트 길이 대입 [예: 4096 / 8192 / 16384]
   ↓
보유한 GPU 스펙과 대조하여 적합도 리포트 출력
```

Ubuntu 24.04 및 단일 RTX 4070 12GB [드라이버 560.35.03, CUDA 12.8] 환경에서 `canfit v0.2.1`을 검증했습니다. 네트워크 통신량은 수 KB에 불과합니다. `time` 명령어로 측정한 소요 시간은 `real 0.31s`, `user 0.04s`, `sys 0.02s`였습니다. 터미널에는 전체 GPU 오프로드 가능 여부, 최대 안전 컨텍스트 길이, 시스템 메모리로 넘겨야 하는 레이어 수가 즉시 표시됩니다.

## 3. 실전 테스트: GGUF 및 AWQ 듀얼 규격 측정

`canfit`은 순수 Rust로 작성되어 단일 바이너리로 구동됩니다.

### 설치 및 로컬 하드웨어 진단

Rust 툴체인이 준비된 환경에서는 Cargo로 즉시 설치할 수 있습니다:

```bash
cargo install canfit
```

또는 GitHub 릴리스 페이지에서 사전 빌드된 바이너리를 직접 내려받아 사용할 수도 있습니다.

설치 후 먼저 로컬 그래픽카드 하드웨어 제원을 확인합니다:

```bash
canfit list-gpus
```

터미널에 물리 VRAM 총량과 현재 데스크톱 환경이 점유 중인 잔여 용량이 출력됩니다. 실제 가용 공간을 파악하기 위해 이 단계를 반드시 선행해야 합니다.

### GGUF 규격 측정: 32B 모델의 한계 확인

12GB 그래픽카드를 기준으로 `Qwen2.5-Coder-32B-Instruct`의 GGUF 실행 한계를 산출했습니다:

```bash
# 12GB 그래픽카드를 지정하고 Q4_K_M 양자화와 8k 컨텍스트로 계산
canfit eval \
    --model Qwen/Qwen2.5-Coder-32B-Instruct \
    --quant q4_k_m \
    --context 8192 \
    --vram 12
```

0.3초 만에 구조화된 표가 반환되었습니다:

```text
+-----------------------+--------------------+
| Parameter             | Value              |
+-----------------------+--------------------+
| Model Weights         | 19.85 GiB          |
| KV Cache [8k ctx]     | 2.00 GiB           |
| CUDA Overhead         | 0.55 GiB           |
| Total Required        | 22.40 GiB          |
| Available VRAM        | 12.00 GiB          |
| Fit Status            | FAILED [OOM]       |
| Max Layers on GPU     | 34 / 64            |
| Projected Decode      | 3.8 tokens/s       |
+-----------------------+--------------------+
```

결과는 명백합니다. 12GB 메모리로는 32B Q4 가중치를 감당할 수 없으며, 34개 레이어만 GPU에 올리고 나머지 30개 레이어는 시스템 메모리로 넘겨야 합니다. 예측 디코딩 속도는 초당 3.8토큰으로 떨어집니다. 이 리포트를 미리 확인한다면 20GB짜리 파일을 다운로드하느라 낭비할 시간을 완벽히 아낄 수 있습니다.

### AWQ 규격 측정: 14B 모델의 실전 구동

32B가 어렵다면 14B AWQ 규격 모델은 12GB 그래픽카드에서 16k 컨텍스트를 안정적으로 소화할 수 있을까요? AWQ 모델을 지정해 계산을 수행했습니다:

```bash
# 12GB 그래픽카드를 지정하고 14B AWQ 모델과 16k 컨텍스트로 계산
canfit eval \
    --model Qwen/Qwen2.5-14B-Instruct-AWQ \
    --quant awq \
    --context 16384 \
    --vram 12
```

출력 결과:

```text
+-----------------------+--------------------+
| Parameter             | Value              |
+-----------------------+--------------------+
| Model Weights         | 8.25 GiB           |
| KV Cache [16k ctx]    | 2.00 GiB           |
| CUDA Overhead         | 0.55 GiB           |
| Total Required        | 10.80 GiB          |
| Available VRAM        | 12.00 GiB          |
| Fit Status            | PASSED [100% GPU]  |
| Max Layers on GPU     | 48 / 48            |
| Projected Decode      | 32.5 tokens/s      |
+-----------------------+--------------------+
```

AWQ 가중치가 8.25 GiB, 16k 컨텍스트 KV 캐시가 2.0 GiB, 드라이버 오버헤드가 0.55 GiB로 총 10.80 GiB가 소모됩니다. 12GB 한도 내에 정확히 안착하며 예상 생성 속도는 초당 32.5토큰에 달합니다.

## 4. 그래픽카드 체급별 실전 권장 구성표

반복 측정을 통해 도출한 소비자용 GPU 체급별 권장 기준입니다:

| 하드웨어 규격 | 권장 최대 모델 규모 | 권장 양자화 포맷 | 안전 컨텍스트 한계 | 실측 관찰 메모 [llama.cpp CUDA 환경] |
| :--- | :--- | :--- | :--- | :--- |
| **8GB VRAM** [RTX 4060 / 3060Ti] | 7B / 8B 모델 | Q4_K_M 또는 Q5_K_M | 8,192 컨텍스트 | batch=1 512 ctx 기준 초당 45-55토큰 기록, 일상용 기본 체급 |
| **12GB VRAM** [RTX 4070 / 3060] | 14B 모델 | Q4_K_M 또는 AWQ | 16,384 컨텍스트 | batch=1 기준 초당 28-36토큰 기록, 2병렬 이상 시 여유 공간 필요 |
| **16GB VRAM** [RTX 4080 / 4070TiS] | 14B 원본 또는 27B 가지치기 | Q5_K_M 또는 Q4_K_M | 32,768 컨텍스트 | 긴 기술 문서를 여유 있게 소화하며 초당 22-28토큰 유지 |
| **24GB VRAM** [RTX 4090 / 3090] | 32B 모델 | Q4_K_M | 8,192 컨텍스트 | 8k 컨텍스트에서 초당 40-42토큰 기록, 32k 지정 시 메모리 초과 |

24GB 규격에 주목해야 합니다. 32B 모델을 단일 카드에서 굴릴 때 컨텍스트는 8k 안팎으로 엄격히 제한해야 합니다. 16k나 32k로 늘리면 총소모량이 24GB 한계선을 넘깁니다. 도구를 통해 사전 계산을 거쳐야만 이러한 함정을 피할 수 있습니다.

## 5. 실무 도입 시의 유의점과 한계

`canfit`은 유용한 진단 수단이지만 실제 배포 시에는 몇 가지 변수를 염두에 두어야 합니다:

1. **다중 병렬 요청에 따른 메모리 복제**: `canfit`은 기본적으로 단일 세션 정적 추정을 수행합니다. `llama-server`나 `vLLM`에서 다중 슬롯 병렬 처리를 활성화하면 슬롯 수에 비례하여 KV 캐시가 복제되므로 1.5GB에서 2GB가량의 안전 마진을 두어야 합니다.
2. **KV 캐시 양자화 적용**: 추정 결과가 1GB 안팎으로 초과할 경우 기동 인자에 `-ctk q8_0 -ctv q8_0`를 지정하여 KV 캐시를 8비트로 압축하면 캐시 메모리를 절반으로 줄일 수 있습니다.
3. **데스크톱 환경의 VRAM 변동성**: IDE와 웹 브라우저를 다수 띄워둔 환경에서는 1.5GB 안팎의 VRAM이 상시 점유됩니다. 사전 추정 시 `--os-reserved 1024` 옵션을 활용하여 배경 노이즈를 제하고 평가하십시오.

이 도구는 연산 성능을 창조하지 않으며, 다운로드에 따르는 불필요한 시행착오를 사전에 줄여줄 뿐입니다. 수십 기가바이트 모델을 내려받기 전에 먼저 `canfit list-gpus`를 실행하여 실제 가용 메모리를 점검해 보시기 바랍니다.
