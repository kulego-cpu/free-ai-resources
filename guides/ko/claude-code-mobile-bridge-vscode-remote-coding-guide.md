Claude Code 에 대규모 단위 테스트 묶음을 실행시키면 결과를 확인하기까지 수 분의 대기 시간이 발생합니다.

이 애매한 공백은 개발자를 피로하게 만듭니다. 화면 앞에 경직된 자세로 앉아 있는 것은 지루하고, 소파로 가거나 음료를 가지러 간 사이에 테스트가 실패했을 때 오류 한 줄을 보려고 책상으로 돌아와 키보드를 잡는 것은 번거롭습니다.

이전에는 원격 데스크톱을 시도해 보았습니다. 하지만 작은 스마트폰 화면에서 두 손가락으로 화면을 확대하고 가상 마우스로 터미널을 찾는 작업은 몇 분 만에 피로감을 줍니다. 스마트폰 브라우저에서 새 Claude 대화를 여는 방법도 답답했습니다. 새 대화창에는 현재 작업 문맥이 전혀 없어서 두 번째 오류를 묻더라도 직전에 실행한 명령어와 프로젝트 구조를 되물어오기 때문에 터미널 로그를 일일이 복사해야 했습니다.

얼마 전 V2EX 공유 창조 노드에 오픈소스 VS Code 확장 liliangshan.claude-code-config-helper 가 공개되었습니다. VS Code v1.95 이상과 Node.js v20.18 환경을 지원하며 가벼운 중계 서비스를 대기시킵니다. 작업실 PC 는 Claude CLI v0.2.14 로 작업을 계속 돌리고 스마트폰 브라우저에서 동일한 세션에 접속하여 대화를 그대로 이어갈 수 있습니다.

키보드를 떠난 뒤에도 같은 대화 맥락이 온전히 이어질 수 있을까요. 실제 업무 코드를 수정할 때 스마트폰 조작이 어디까지 유용한지 구독 기간 산정 리팩터링 프로젝트에서 검증했습니다.

## 스마트폰을 방향 지시 리모컨으로 제한하는 경계 설정

스마트폰은 이 워크플로에서 에디터가 아니라 단순한 리모컨입니다. 6 인치 터치 화면에서 긴 파일 경로를 직접 입력하는 것은 무리입니다.

수행할 역할은 세 가지로 압축됩니다. 단위 테스트 합격 여부를 확인하고, 수정 방향을 제시하며, 모델이 엉뚱한 방향으로 나아갈 때 즉시 멈추는 것입니다. 책상으로 돌아와 차이점을 확인한 뒤 승인하고 커밋합니다.

실무 날짜 계산 사례를 살펴보겠습니다. 멤버십 체험 기간을 월말 기준으로 부여하는 로직에서 packages/billing/src/services/subscription.ts 의 2027 년 1 월 31 일 단위 테스트가 실패했다고 가정합니다.

책상 앞에 앉아 있으면 보통 에러를 고쳐달라고 포괄적인 지시를 내리기 쉽습니다. 모델은 테스트를 통과시키려는 목적만으로 테스트 코드의 기대값을 수정해 버리는 실수를 자주 저지릅니다.

스마트폰 중계를 도입하면 작업 흐름이 명확히 나뉩니다:

```text
책상 앞에서의 제약 지시
"npm test -- test/unit/expiry.spec.ts -t subscription-expiry
만료일 계산 테스트만 실행, 첫 실패 입력과 실제값만 보고, 코드 수정 금지"
    │
    ▼
소파에서 스마트폰 브라우저로 확인
입력 2027-01-31T23:59:59Z 에 대해 2 월 31 일 부재로 인한 경계 실패 확인
    │
    ▼
스마트폰에서 업무 규칙 판정
"구현부와 테스트가 각각 어떤 규칙을 상정하는지 먼저 보고하라,
단순 통과를 위해 테스트 기대값을 임의 수정하지 말 것"
    │
    ▼
책상으로 복귀하여 코드 변경 확인
다른 요금제 로직에 영향이 없는지 대조 후 Git 커밋 실행
```

소파에 누워 전송한 한 줄의 제약 명령은 데스크톱에서 실행 중인 Claude Code 터미널 세션으로 곧바로 전달됩니다. 스마트폰에서 로그를 다시 붙여넣을 필요가 없고 모델이 테스트 코드를 훼손하는 것도 막을 수 있습니다. 지시와 대형 화면 검토를 분담하는 작업 방식은 매끄럽습니다.

## 네트워크 토폴로지 구성과 로컬 보안 중계 연결

스마트폰에서 연결할 때 가장 먼저 살펴야 할 부분은 네트워크 토폴로지입니다. 주소 바인딩 설정을 잘못하면 접속 자체가 불가능합니다.

중계 서비스를 127.0.0.1 로 둔 채 실행하면 어떻게 될까요. 같은 Wi-Fi 환경에 연결되어 있어도 스마트폰에서는 접속할 수 없습니다. 루프백 주소는 호스트 컴퓨터 내부 트래픽만 수신하기 때문입니다.

접속 방식은 두 가지입니다. 0.0.0.0 으로 바인딩하고 authKey 토큰을 설정해 로컬 IP 로 접속하거나, 확장이 기본 제공하는 암호화 WebSocket 중계 통로를 활용하는 것입니다.

소스 코드는 GitHub 의 `liliangshan/claude-code-config-helper` 에 공개되어 있습니다. 설정은 세 단계로 완료됩니다:

### 1단계: 데스크톱 개발 환경 준비

VS Code 마켓플레이스에서 확장 ID liliangshan.claude-code-config-helper 를 검색하여 설치합니다. 발행자가 liliangshan 인지 확인해야 하며 로컬에 Node.js 와 Claude CLI 가 준비되어 있어야 합니다.

사이드바의 LLS CCAI 아이콘을 열고 로컬 Claude CLI 실행 경로를 지정한 뒤 모델 API 인증 정보를 입력합니다.

패널에서 테스트 메시지를 보내 응답이 스트리밍되는지 확인합니다.

### 2단계: 작업 대상 폴더 인증 및 연동

VS Code 에서 작업 중인 프로젝트 디렉터리를 엽니다.

대화창 하단의 원격 연동 버튼을 클릭합니다. 기기 식별용 계정으로 로그인한 뒤 현재 열려 있는 프로젝트 폴더를 연동합니다:

```json
// 로컬 네트워크 직결을 구성할 경우 0.0.0.0 에 바인딩하고 인증 토큰을 설정
{
  "remoteBridge.bindHost": "0.0.0.0",
  "remoteBridge.port": 9120,
  "remoteBridge.authKey": "CUSTOM_LOCAL_TOKEN_HEX",
  "remoteBridge.workspace": "current-project-root"
}
```

처음에는 테스트 저장소를 활용해 스마트폰에서 보낸 명령이 어느 터미널 창으로 유입되는지 확인하는 편이 안전합니다.

### 3단계: 스마트폰 브라우저 접속

스마트폰 브라우저에서 중계 주소 또는 192.168.1.120:9120 같은 로컬 IP 주소를 열고 기기 계정이나 설정한 보안 토큰으로 로그인합니다.

화면에 현재 온라인 상태인 PC 이름과 프로젝트 경로, 활성 세션이 표시됩니다. 주 작업영역을 선택하고 읽기 전용 질의를 보내봅니다:

```text
프로젝트의 만료일 계산 로직을 파악하고 싶다, 가장 먼저 확인해야 할 파일을 제시하라, 파일 수정은 하지 말 것
```

책상의 모니터를 바라보면 동일한 문장이 VS Code 터미널에 반영되고 모델의 추론 과정과 권장 파일 경로가 스마트폰 화면으로 실시간 중계됩니다.

## 세션 운용 전략: 주 세션과 병렬 조사의 분리

작업 화면을 다루다 보면 주 작업영역과 병렬 작업이라는 두 가지 경로를 마주하게 됩니다.

이 두 경로를 어떻게 분리해야 할까요. 선택을 잘못하면 대화 맥락이 뒤섞입니다.

원칙은 단순합니다. 직전의, 계속해서, 두 번째 오류와 같은 지시 대명사를 포함한 질의는 반드시 주 세션에 보내야 합니다.

테스트에서 여러 오류가 나왔을 때 두 번째 오류도 같은 원인인지 묻는 질문은 주 세션에서만 성립합니다. 주 세션만이 직전 테스트 종료 코드와 스택 트레이스를 기억하고 있기 때문입니다. 병렬 세션으로 이 질문을 보내면 모델은 맥락을 알지 못합니다.

병렬 세션은 완전히 독립된 읽기 전용 조사에 적합합니다.

주 세션이 코드를 수정하는 동안 병렬 세션은 읽기 전용으로만 활용합니다. 두 세션이 subscription.ts 파일을 동시에 건드리게 해서는 안 됩니다. 변경 내역이 뒤엉켜 기준선을 잃게 됩니다. 병렬 세션에는 파일 경로와 줄 번호 확인만 맡깁니다:

```text
프로젝트 전체에서 한 달을 고정 30 일로 가정한 위치를 찾아라, 파일 경로와 줄 번호만 나열하고 코드는 변경하지 말 것
```

두 작업은 같은 소스코드를 바라보지만 컨텍스트 윈도우는 완벽히 격리되어 있습니다. 한쪽은 수정을 진행하고 다른 한쪽은 조사를 맡습니다.

## 실무 적용 시 부딪힌 4가지 주의점

가볍고 유용한 도구이지만 스마트폰으로 데스크톱 코딩을 조작할 때 주의해야 할 지점이 있습니다.

### 주의 1: 노트북 절전 모드로 인한 연결 끊김

스마트폰은 원격 조작 화면일 뿐 작업을 수행하는 본체는 책상의 PC 입니다.

지시를 전송한 뒤 자리를 비웠다가 스마트폰 화면이 오프라인으로 바뀐 적이 있었습니다. 입력이 없는 상태가 이어지며 MacBook 이 화면을 끄고 네트워크 연결을 일시 중단했기 때문이었습니다.

자리를 비우고 작업을 이어갈 때는 호스트 PC 가 절전 모드로 들어가지 않도록 설정해야 합니다. 터미널에서 caffeinate -dimsu -t 7200 명령을 실행해 임시로 절전을 방지하는 방법이 유용합니다.

### 주의 2: 화면의 중지 버튼은 변경 사항 취소가 아님

스마트폰 화면에는 모델이 잘못된 방향으로 나아갈 때 누를 수 있는 붉은색 중지 버튼이 있습니다.

중지 버튼을 눌러도 이미 파일에 쓰인 변경 사항이 이전으로 되돌아가지 않습니다.

이 버튼은 터미널에서 SIGINT 신호를 보내는 것과 같습니다. 이후 토큰 생성과 도구 호출을 중단할 뿐이며 직전 단계에서 디스크에 기록된 잘못된 코드는 그대로 남습니다. 책상으로 돌아왔을 때 git status 와 git diff --stat HEAD~1 명령으로 변경 내역을 확인하는 과정을 생략해서는 안 됩니다.

### 주의 3: 스마트폰 화면에서 섣부른 커밋 승인 금지

테스트 통과 메시지가 스마트폰 화면에 떴다고 해서 즉각 커밋이나 배포를 지시해서는 안 됩니다.

테스트 통과는 기존 테스트 케이스에 에러가 없다는 것을 의미할 뿐 불필요한 코드 변경이 섞이지 않았는지를 보장하지 않습니다.

모델은 주변 코드 서식을 임의로 바꾸거나 주석을 삭제하는 실수를 종종 저지릅니다. 다음 작업 방향을 판단하는 것은 스마트폰으로 가능하지만 대규모 파일 변경이나 Git 커밋 및 푸시는 책상의 대형 모니터에서 차이점을 완전히 확인한 뒤 승인해야 합니다.

### 주의 4: 기기 계정과 모델 API 키의 혼동

초기 설정 시 기기를 찾지 못하겠다는 문의가 자주 발생합니다.

중계용 기기 계정과 ~/.claude/config.json 에 설정된 모델용 API 키를 혼동하는 경우가 많습니다. 기기 계정은 9120 포트 연결 관리만 담당하며 모델 사용 한도가 포함되어 있지 않습니다. 추론 호출에는 로컬 settings.json 에 등록된 정상적인 서비스 인증 정보가 소비됩니다.

## 실무적 정리와 활용 한계

스마트폰을 개발 워크플로에 도입하는 시도는 실질적인 효율을 제공할까요.

대규모 시스템 아키텍처를 모바일 화면에서 작성하려 한다면 무모한 시도입니다. 터치 화면은 다중 모니터와 기계식 키보드의 생산성을 넘을 수 없습니다.

책상으로 돌아와 diff 를 면밀히 확인합니다. 스마트폰에서 커밋이나 배포 명령을 직접 내리지 않습니다. 테스트가 통과해도 모델이 임의로 주석을 삭제하거나 서식을 바꾸지 않았는지 직접 검토해야 합니다. 스마트폰은 단순 통과를 위해 테스트 기대값을 임의로 바꾸지 말 것과 같은 중요한 판단을 내리는 데 집중하는 편이 안전합니다.

오래 걸리는 테스트를 돌려놓고 소파에서 실패 원인을 확인하며 결정적인 방향 지시를 내리는 것만으로 작업 피로도는 크게 줄어듭니다.
