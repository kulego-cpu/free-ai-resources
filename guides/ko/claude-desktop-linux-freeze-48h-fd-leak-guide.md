수요일 오후, 작업용 Linux 워크스테이션이 갑작스럽게 버벅대기 시작했다.

마우스 커서는 초당 2프레임 수준으로 끊겼다. 키보드를 눌러도 글자가 찍히기까지 3~4초가 걸렸다.

터미널을 열고 uptime 명령을 쳤다. 결과가 나오는 데 20초가 걸렸다. 시스템 부하 수치는 46.34까지 치솟아 있었다. 16코어 머신이었으니 각 코어 대기열에 3개에 가까운 작업이 쌓여있던 셈이다. 도대체 어떤 스크립트가 폭주하면 이 지경이 되는가? 빌드 프로세스의 폭주를 의심하여 ps aux 를 확인했지만 이상 프로세스는 없었다.

커널 I/O 지연 지표를 확인했다:

```bash
# 커널 I/O 압력 지표 확인
cat /proc/pressure/io
```

출력된 full 10초 평균값은 85.3을 기록했다. 초고속 NVMe SSD가 쉴 새 없는 쓰기 작업에 완전히 짓눌려 있었다.

오른쪽 화면의 Claude 데스크톱을 확인하니 화면은 하얗게 변해 있었고, 스켈레톤 로더 플레이스홀더만 덩그러니 남아 있었다:

<img src="https://img.freeaidog.com/images/blog/claude-desktop-frozen-skeleton.webp" alt="Claude 데스크톱 앱 무응답 프리징 화면" />

마우스로 클릭해도 아무 반응이 없었다.

프로세스 목록을 살펴보니 디스크를 무자비하게 긁고 있던 범인은 systemd-coredump 였다. Claude의 렌더러 프로세스가 SIGILL 신호로 충돌했고, 운영체제가 프로세스 전체 메모리 이미지를 디스크로 덤프하려던 것이었다. 5분 동안 92.4GB의 데이터를 쏟아붓다가 타임아웃으로 강제 종료되었고, 정작 분석할 수 있는 온전한 코어 파일은 남기지도 못했다. 이래서야 어떻게 디버깅을 하겠는가?

Linux 환경에서 이 앱을 쓰다 보면 2~3일에 한 번꼴로 어김없이 멈춘다. 화면이 하얗게 날아가거나 그대로 얼어붙는다. 로그에는 메인 웹뷰가 응답하지 않아 다시 로드한다는 뻔한 문장만 반복될 뿐, 실제로 정상 복구된 적은 단 한 번도 없었다.

디버거를 붙이고 2주 동안 추적한 끝에, 27바이트의 사소한 미수신 응답이 불러온 파일 디스크립터 누수 사태의 전말을 밝혀냈다.

## 왜 크래시 덤프가 1.5TB까지 부풀어 오르는가?

채팅 창 렌더러 프로세스가 왜 1.5TB나 되는 덤프를 생성하는가? 이는 Chromium 특유의 가상 주소 공간 예약 메커니즘에서 비롯된다.

이 앱은 Electron 44 기반이며 내부 엔진은 Chrome 152에 해당한다. 시작 시 V8 엔진은 샌드박스용으로 1TB의 가상 주소 공간을 선점하고 앞뒤로 64GB와 288GB의 보호 영역을 둔다. 메모리 할당자와 GC 힙까지 합치면 예약되는 가상 주소만 1.3TB를 훌쩍 넘긴다.

일반적인 Linux 환경이라면 madvise 호출로 DONTDUMP 플래그를 전달하여 덤프 대상에서 제외하도록 커널에 알릴 수 있다.

하지만 렌더러의 seccomp 샌드박스 정책 baseline_policy.cc 는 허용 플래그를 엄격하게 제한한다. DONTNEED, WILLNEED, RANDOM, REMOVE, NORMAL, FREE 의 6가지만 허용된다. MADV_DONTDUMP 는 허용 목록에 없어 커널로부터 EPERM 거절을 당한다.

충돌이 발생하는 순간 커널은 파이프를 통해 데이터를 전달한다. 파이프는 스파스 파일의 빈 구멍을 건너뛸 수 없으므로, 비어있는 거대한 가상 공간이 고스란히 0으로 채워진 물리 디스크 연속 쓰기로 둔갑해 버린다.

원작자인 Vladimir Petrzhikovskii 씨가 blog.dfb.sh/blog/claude-desktop-freeze 에 기록했듯이, 그는 lseek 의 데이터 탐색 기능을 활용한 Rust 툴을 작성하여 1.5TB 스파스 파일 검색 시간을 0.7초로 단축하고서야 본격적인 원인 분석에 들어갈 수 있었다.

## 942개의 공유 메모리와 27바이트의 하트비트

메모리 덤프를 열어보니 렌더러가 물고 있는 파일 디스크립터가 1,000개 가까이 쌓여 있었다:

```bash
# 렌더러 프로세스의 파일 디스크립터 수 확인
ls -l /proc/$RENDERER_PID/fd | wc -l
```

그중 942개가 2MB 크기의 POSIX 공유 메모리 영역이었다. strings 로 스캔해 본 결과 938개 영역에 완벽히 동일한 27바이트의 JSON이 적혀 있었다:

```json
{
  "refresh_after_seconds": 0
}
```

이 고작 27바이트를 위해 프로세스는 900개 이상의 2MB 공유 메모리 핸들을 계속 열어두고 있었다. 사용자 퇴장 알림 응답에 왜 갱신 주기 지시가 들어가 있는 것인가?

내부 가상 함수 테이블과 V8 힙을 역추적하니 이 요청들은 내장된 Code 탭에서 전송된 것이었다.

해당 탭에는 자리비움 체크 로직이 있다. 창을 최소화하거나 방치하면 프론트엔드는 퇴장 알림을 보낸다:

```http
POST /v1/code/channels/session-id/client/presence HTTP/1.1
Host: api.anthropic.com
Content-Type: application/json

{"client_id": "client-token", "clear": true}
```

요청에는 keepalive 플래그가 붙어 있다. 서버에 퇴장을 알리고 백엔드는 27바이트 응답을 돌려준다.

던져놓고 잊어버리는 설계였기에 프론트엔드는 응답 바디를 전혀 읽지 않았다. 빈 catch 문 하나만 달랑 붙여두었다. 백그라운드에 켜두는 동안 이 요청은 시간당 수십 개씩 조용히 누적되었다.

35시간이 넘어가자 열려 있는 핸들은 1,000개에 육박했다.

## 근본 원인: no-store 헤더에서 IPC 데드락까지

서버는 Cache-Control: no-store 를 보냈고, 프론트엔드는 스트림을 읽지 않았다.

Chromium은 데이터를 읽거나 취소하기 전까지 파이프 내에 보관하는 표준을 따른다. 본래 디스크 캐싱을 막기 위한 no-store 가 여기서는 파이프 정리를 가로막는 걸림돌이 되었다. 최소 재현 환경에서 수동 GC를 돌려보니 JS 응답 객체는 수거되었지만 /proc/$PID/fd 카운트는 단 하나도 줄지 않았다. 객체가 GC로 정리되었다면 핸들도 닫혀야 정상이 아닌가?

Chromium의 fetch_manager.cc 에서는 일반적으로 BufferingBytesConsumer 가 파이프 데이터를 메모리로 비워내고 핸들을 닫아준다.

하지만 코드에는 특별한 분기문이 존재한다. 응답 헤더에 Cache-Control: no-store 가 포함되어 있으면 자동 버퍼링을 건너뛴다.

캐시가 금지된 데이터가 메모리를 채우지 않도록 배려한 의도였으나, 그 대가로 데이터는 명시적으로 읽히거나 body.cancel 로 취소될 때까지 Mojo 파이프 안에 갇히게 된다.

서버는 no-store 를 달아 보냈고 프론트엔드는 읽지 않는다. 프론트엔드가 영원히 읽지 않으면 어떻게 되는가? 핸들은 영원히 닫히지 않는다.

Chromium은 규격을 지켰고 V8의 GC는 C++ 단의 Mojo 자원을 해제하지 못한다. 방치된 27바이트마다 2MB 공유 메모리와 파일 디스크립터 하나가 눌러앉았다.

Linux에서 일반 렌더러 프로세스의 소프트 제한 ulimit -Sn 은 통상 1024로 묶여 있다:

```bash
# 파일 디스크립터 제한 확인
ulimit -Sn
```

누수된 파이프가 1,000개 안팎에 도달하자 남은 핸들이 완전히 바닥났다.

이 상황에서 메인 스레드가 IndexedDB 입출력을 처리하려 하자 브라우저 프로세스가 새 핸들을 넘겨주려 시도했다.

하지만 커널에서 고갈 오류가 터지며 소켓에 MSG_CTRUNC 플래그가 찍혔다.

Chrome 152의 구형 Mojo 구현체는 핸들 누락을 정상 복구하지 못하고 무기한 대기 상태에 빠졌다.

이후의 모든 IPC 통신이 줄줄이 막히며 메인 스레드는 완전히 동결되었다. 화면은 응답 불능 상태로 굳어버렸다.

## 업스트림의 반응: 정상 동작이라는 답변과 봇의 즉시 종결

원인을 규명한 Vladimir 씨는 두 업스트림에 이슈를 보고했다.

먼저 Chromium 프로젝트에 파일 디스크립터 고갈 시 엔진 정지 대신 TypeError 를 던져야 한다고 보고했다【Issue 582417463】.

그러나 담당자는 과거 이슈 378822137 의 중복으로 분류하며 당일 종결했다. 이것이 과연 정상적인 동작인가?

담당자의 답변은 단호했다. 응답을 읽을 권한이 있음에도 읽지 않기로 선택한 이상 이는 의도된 정상 동작이다. 브라우저는 향후 데이터를 읽을지 여부를 예단할 수 없으므로 파이프를 유지할 수밖에 없다는 논리였다.

이어서 Anthropic 공식 저장소 anthropics/claude-code 에 이슈를 등록했다.

클라이언트 수정은 매우 간단하며, 읽지 않는 응답 스트림 끝에 cancel 호출 한 줄만 더해주면 된다.

Issue 107887 이 등록되었다.

하지만 사람 엔지니어의 피드백은 없었다. 몇 분 뒤 관리 봇이 invalid 라벨을 붙이며 Claude Code와 무관한 내용으로 보인다는 멘트와 함께 매정하게 닫아버렸다.

브라우저 팀은 규격 준수라고 강변하고 모델 팀의 봇은 버그 리포트를 문전박대했다.

결국 이삼 일마다 강제 재시작을 감수해야 하는 것은 사용자들의 몫이었다.

## 로컬 우회책: Caddy 기반 3분 헤더 재작성 가이드

공식 패치를 마냥 기다리기보다는 로컬 네트워크 단에서 우회책을 적용하는 편이 훨씬 빠르다.

방법은 두 가지다. 프론트엔드 fetch 를 가로채 스트림을 취소하거나, 네트워크 단에서 Cache-Control: no-store 헤더를 떼어내는 것이다.

Claude 데스크톱은 구동 시 웹 자산을 동적으로 불러오므로 바이너리 수정보다는 네트워크 프록시 방식이 깔끔하다.

로컬에서 Caddy를 운영 중이라면 다음 규칙을 추가하면 된다:

```caddyfile
api.anthropic.com {
    reverse_proxy https://api.anthropic.com {
        header_up Host {upstream_hostport}
        @presence path /v1/code/channels/*/client/presence
        handle_response @presence {
            header -Cache-Control
        }
    }
}
```

헤더를 제거하면 Chromium의 BufferingBytesConsumer 가 250밀리초 안에 파이프를 비워내고 핸들을 닫아준다.

디버깅 포트를 열고 실행하는 방법도 가능하다:

```bash
# 원격 디버깅 포트를 열고 클라이언트 실행
claude-desktop --remote-debugging-port=9222
```

패치를 걸고 7일 동안 연속 가동한 결과 파일 디스크립터 수는 36~41 사이를 안정적으로 유지했다. 메모리 사용량도 평온했고 시스템 부하 역시 0.1 아래를 맴돌았다.

두 업스트림의 이슈는 여전히 닫혀 있다. 582417463 은 중복으로, 107887 은 무효로 묶여 있다. dotfiles 저장소의 claude-fix.caddy 에 규칙을 넣어두었으니 머신을 바꿀 때마다 그대로 불러와 쓰면 된다. 공식 수정이 나오기까지 과연 몇 번의 48시간이 더 흘러가야 할까?
