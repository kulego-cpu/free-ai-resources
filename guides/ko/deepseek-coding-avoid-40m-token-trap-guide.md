# DeepSeek 4천만 토큰 청구 폭탄을 피하는 5가지 실전 개발 수칙

DeepSeek 단가가 저렴하다고 해서 무엇이든 척척 만들어주는 소원 수리함처럼 쓰고 계시지는 않습니까?

최근 V2EX 커뮤니티의 t/1255533 게시글에서 한 개발자가 쓰라린 현실의 벽에 부딪혔습니다.

Codex 한도가 소진되자 그는 DeepSeek API를 연결하여 프로젝트 다국어 사전 파일을 9개 언어로 한 번에 일괄 번역하고자 했습니다. 하지만 몇 차례의 배치 작업을 돌린 후 대시보드의 사용량 청구서는 상상을 초월했습니다. 어느새 4200만 개가 넘는 토큰이 허공으로 사라진 것입니다.

작성자는 포럼에 글을 올리며 하소연했습니다. 다들 저렴하다고 했는데 사전 번역 몇 번 돌렸다고 수천만 토큰이 소모되는 게 말이 되는가? 도대체 어디서 비용이 절감된다는 말인가?

저렴하다는 것은 상대적인 개념입니다. 비즈니스 설계와 제약 조건을 명시하지 않은 채 모델이 알아서 맞춰주기를 바라면 끝없는 재시도와 무질서한 컨텍스트 팽창으로 잔고는 순식간에 바닥납니다.

아래 정리한 다섯 가지 원칙은 필자가 현업에서 직접 겪은 시행착오이자 해당 게시글의 숙련된 엔지니어들이 공통적으로 지목한 핵심입니다. 중요도 순이 아니라 개발자가 현장에서 마주치는 순서대로 정리했습니다.

## 수칙 1: 프롬프트 접두사 순서를 절대 바꾸지 마라 —— 캐시가 빗나가면 속도도 손해일 뿐이다

많은 사람들이 9개 언어로 번역할 때 소모되는 토큰이 원문 길이에 9를 곱한 값일 뿐이라고 착각합니다.

계산기는 달콤하지만 청구서는 냉혹합니다.

실제 장애는 이렇게 발생했습니다. 작성자는 매번 요청할 때마다 두꺼운 원본 JSON 사전과 함께 이미 번역된 수천 줄의 이전 문맥을 프롬프트 안에 그대로 집어넣었습니다. 대화 턴이 누적될수록 단일 요청의 입력 컨텍스트는 순식간에 2만에서 3만 토큰으로 팽창했습니다.

더 치명적인 문제는 Prompt Cache의 완전한 무력화였습니다.

DeepSeek 공식 프롬프트 캐시 메커니즘은 문자열 시작 순서에 매우 민감합니다. 시스템 프롬프트 맨 앞부분의 문장 부호 하나를 바꾸거나 대상 언어 순서를 바꾸는 순간 접두사 해시 검증이 즉시 실패합니다.

본래 90% 할인이 적용되어야 할 캐시 적중률이 0으로 떨어지면서 매 요청마다 전액 요금이 청구되었습니다. 수백 번의 API 루프가 돌면서 4200만 토큰이 순식간에 사라진 이유가 바로 여기에 있습니다.

캐시 적중을 극대화하려면 정적 접두사 구조를 엄격하게 고정해야 합니다:

```json
{
  "model": "deepseek-coder",
  "messages": [
    {
      "role": "system",
      "content": "당신은 숙련된 백엔드 엔지니어입니다. 정해진 코드 규격을 준수하여 상태가 없는 순수 함수를 출력하세요."
    },
    {
      "role": "user",
      "content": "【고정 규약】입력 데이터: dict_a, 기대 출력: dict_b\n---\n【동적 작업】대상 파일: services/worker.py, 수정 함수: process_task"
    }
  ],
  "temperature": 0.0,
  "max_tokens": 2048
}
```

터미널 호출 예시:

```bash
curl https://api.deepseek.com/chat/completions \
  -H "Content-Type: application/json" \
  -H "Authorization: Bearer $DEEPSEEK_API_KEY" \
  -d @payload.json
```

고정된 시스템 규칙과 샘플 명세는 맨 위에 완전히 고정하고, 동적으로 변하는 텍스트는 반드시 맨 뒤에 덧붙여야 합니다.

## 수칙 2: 함수는 작성할 수 있어도 아키텍처는 못 만든다 —— 구체적인 작업 명세표로 지시하라

함수는 작성할 수 있어도 전체 아키텍처는 설계하지 못합니다. 이것이 핵심이며 다른 모든 것은 여기서 파생됩니다.

함수 시그니처, 파라미터 타입, 기대하는 단위 테스트 단언문을 명확히 주면 한 번에 통과합니다. 하지만 권한 관리가 포함된 멀티테넌트 시스템을 만들어달라고 막연하게 던지면 첫 번째는 데코레이터, 두 번째는 미들웨어, 세 번째는 컬럼명을 user_id_v2로 바꾸며 표류하기 시작합니다. 세 번의 턴이 돌면 토큰은 바닥나고 코드는 엉망이 되어 결국 처음부터 다시 짜야 합니다.

필자는 먼저 Claude 등을 활용해 4개 열로 구성된 작업 명세서를 작성합니다: 파일 경로 / 수정 대상 함수 / 상하위 의존성 / 단위 테스트 인수 조건. 명세서에는 코드를 쓰지 않고 수정 위치와 경계만 정의합니다.

40개 항목의 작업 목록이라도 입출력을 합쳐 8k 토큰 미만으로 작성할 수 있습니다. 반면 DeepSeek에게 아키텍처를 추측하게 만들면 헛바퀴 도는 데만 20만 토큰이 소모됩니다.

| 파일 경로 | 수정 대상 함수 | 상하위 의존성 | 단위 테스트 인수 조건 |
| :--- | :--- | :--- | :--- |
| services/auth.py | verify_token | redis_pool, jwt | 만료 시 ExpiredTokenError 발생, 정상 시 user_id 반환 |
| services/order.py | calc_discount | models.Promotion | 계단식 할인 계산 시 소수점 둘째 자리까지 정밀도 유지 |
| tasks/sync.py | drain_queue | aiomysql.Pool | 타임아웃 시 자동 재시도 및 상태 중복 제거 |

이 표를 바탕으로 DeepSeek에게 한 번에 한 항목씩 전달합니다. 명확한 입출력을 제공하면 모델이 출력한 코드를 즉시 프로젝트에 반영할 수 있습니다.

## 수칙 3: 스택 추적 로그를 통한 에러 분석이 진정한 주특기다

필자가 가장 크게 체감한 영역은 바로 traceback 에러 로그 분석이었습니다.

지난주 수요일 프로덕션 환경의 asyncio.TaskGroup 작업자에서 KeyError가 발생했고 스택 깊이는 47계층에 aiomysql 커넥션 풀 대기가 두 군데 섞여 있었습니다. 스택 로그와 문제가 된 약 60줄의 함수 코드를 그대로 DeepSeek에 입력했습니다. 추론 단계를 high로 지정하고 40초를 기다리자 finally 블록 내부에서 conn.cursor가 두 번 재사용되고 있는 지점을 정확하게 짚어냈습니다.

한 시간 가까이 쳐다보며 찾지 못했던 원인을 단번에 포착한 것입니다.

```text
Traceback - most recent call last:
  File "/srv/app/services/worker.py", line 142, in process_batch
  File "/srv/app/services/worker.py", line 88, in sync_channel
KeyError: 'cursor_reuse_conflict'
```

구체적인 문법 오류, 누락된 널 방어 코드, 동시성 데드락 탐지에 있어서는 타의 추종을 불허합니다. 대규모 리팩토링을 맡기지 말고 구체적인 에러 로그와 관련 코드 수십 줄을 전달하는 것이 가장 효율적입니다.

## 수칙 4: 추론 단계는 high를 선택하고 max는 피하라 —— 타임아웃과 헛바퀴 방지

많은 개발자들이 추론 깊이 설정을 보면 무의식적으로 최고치인 max를 선택하고 싶어 합니다. 정말 그것이 필요할까요?

max 설정을 맹신해서는 안 됩니다.

DeepSeek의 추론 메커니즘에서 max는 내부적으로 방대한 탐색 트리를 전개합니다. 구체적인 함수 구현과 문법 점검에서 max 설정은 수 분 이상의 긴 대기 시간을 초래합니다. 도중에 네트워크가 끊기면 전체 컨텍스트를 처음부터 다시 계산해야 하므로 또다시 1만 토큰이 허공으로 날아갑니다.

일상적인 개발과 에러 추적에는 high 단계로 충분합니다. 응답 시간은 보통 30초에서 50초 사이에 형성되며 핵심을 향해 곧장 전개되므로 타임아웃 차단도 예방할 수 있습니다.

## 수칙 5: 배치 작업은 독립 슬라이스와 멱등성으로 눈덩이 효과를 끊어라

4200만 토큰이 폭발한 근본 원인은 문맥을 눈덩이처럼 굴렸기 때문입니다.

작성자는 이미 번역된 프랑스어, 독일어, 일본어 기록을 하나의 대화 세션에 계속 누적한 채 새로운 언어를 요청했습니다. 일곱 번째 언어에 도달했을 때는 컨텍스트 창이 가득 차서 짧은 문장 하나를 처리할 때도 매번 수만 토큰의 이전 기록이 오고 갔습니다.

배치 작업은 철저히 격리된 파이프라인 방식으로 처리해야 합니다:

각 하위 작업은 자신에게 필요한 입력과 사전 규칙만을 포함해야 합니다. 출력이 완료되면 즉시 디스크에 기록하고 현재 컨텍스트를 즉시 폐기합니다. 다음 작업은 완전히 새로운 세션에서 시작합니다.

과거 이력과의 연결을 끊고 각 요청에 멱등성 검사를 추가합니다. 중간에 네트워크가 끊기더라도 수백 토큰짜리 단일 슬라이스 하나만 다시 돌리면 되므로 전체 배치 작업이 중단되지 않습니다.

## 요약: 수박은 칼로 썰고 중장비로 자수를 놓지 마라

이 다섯 가지 실전 수칙만 지키면 DeepSeek 코딩이 값비싼 도박으로 변하지 않습니다:

첫째, 시작 접두사를 정적으로 고정하여 프롬프트 캐시의 90% 할인을 확실히 누린다.

둘째, 함수는 작성해도 아키텍처는 못 만든다는 점을 명심하고 4열 작업 명세서로 주도권을 잡는다.

셋째, 장애 분석 시 스택 추적 로그를 투입하여 동시성 버그를 빠르게 포착한다.

넷째, 추론 단계는 high를 선택하여 max로 인한 타임아웃 재시도를 방지한다.

다섯째, 배치 작업은 독립 슬라이스로 실행하여 컨텍스트의 눈덩이화를 차단한다.

전체 설계는 상위 모델에 맡기고 구체적인 함수 구현과 에러 분석은 가성비 모델에 위임하십시오. 문맥과 캐시 접두사를 통제할 수 있다면 개발 비용은 언제나 안전 범위 내에 머물 것입니다.
