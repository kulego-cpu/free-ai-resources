# DeepSeek의 OpenRouter 트래픽 53% 독점: 멀티턴 Agent에서 중계 라우팅을 피해야 하는 이유

모니터링 플랫폼 dirac.run 이 집계한 OpenRouter 의 최신 데이터는 오픈소스 진영에 커다란 충격을 주었습니다.

하루 27조 토큰에 달하는 총 유통량 중 DeepSeek 단일 모델의 점유율이 53%를 기록했습니다. Qwen 과 여타 오픈 가중치 모델을 합산하면 전체 비중은 이미 75% 선을 가볍게 넘어섰습니다.

불과 8개월 전만 하더라도 상위권은 해외 폐쇄형 거대 기업들의 독무대였습니다. 200여 일 만에 시장의 판도가 완전히 뒤집힌 셈입니다.

개발자 커뮤니티에 올라오는 실제 영수증 격차도 놀랍습니다. 하루 종일 백그라운드에서 자동 리팩터링 Agent 를 실행하여 수십만 토큰을 소모해도 DeepSeek 의 청구 비용은 4달러 남짓에 불과합니다. 동일한 작업량을 상용 최고 사양 모델로 구동했을 경우 400달러를 훌쩍 넘기기 일쑤입니다.

100배에 달하는 가격 차이가 존재하는 만큼 대규모 자동화 파이프라인을 오픈소스 인터페이스로 전환하는 것은 합리적인 선택입니다. 극도로 복잡한 아키텍처 설계나 멀티모달 영역에서는 폐쇄형 모델의 안정성이 여전히 유효하지만, 반복적인 리팩터링과 테스트 코드 작성 업무에서는 불필요한 개발 예산 지출을 줄이는 것이 급선무이기 때문입니다.

그러나 중계 플랫폼 엔드포인트만 바꾸면 누구나 하루 4달러의 저렴한 비용을 누릴 수 있다고 생각한다면 심야의 영수증 앞에서 값비싼 대가를 치르게 됩니다.

## 1. 갑작스럽게 청구된 38달러 영수증의 진실

지난 수요일 밤, 저는 2년간 유지해 온 유틸리티 레포지토리의 전면 리팩터링을 시작했습니다.

2만 줄이 넘는 레거시 코드에는 타입 정의가 빠진 함수들이 빼곡했습니다. 수작업으로 검토한다면 이틀 이상 매달려야 하는 분량입니다.

저는 단일 세션 연속 대화 방식으로 자율 실행 스크립트를 작성했습니다. 설정 과정을 아끼기 위해 엔드포인트는 OpenRouter 에서 제공하는 DeepSeek 인터페이스로 지정했습니다. 100만 토큰당 십몇 센트에 불과한 요율인 만큼 아무리 길게 돌아도 예산을 넘기지 않을 것이라 확신했습니다.

처음 15턴까지는 아무런 이상 없이 매끄럽게 동작했습니다.

Agent 는 소스 파일을 하나씩 열어 의존성을 분석하고 테스트 케이스를 생성하며 단언문을 실행했습니다.

컨텍스트는 초기 8K 에서 28K 토큰 수준으로 완만하게 증가했습니다. 콘솔에서 확인한 회당 호출 비용은 2센트 미만으로 극히 저렴했습니다.

야식 시간이 되어 저는 노트북을 덮고 밖으로 나가 식사를 마친 후 샤워를 마쳤습니다. 대략 40분 정도의 시간이 흘렀습니다.

서재로 돌아와 화면을 켜고 스크립트가 16턴부터 30턴까지의 후속 작업을 진행하도록 실행했습니다.

2시간 후 모든 단위 테스트가 통과하며 작업이 끝났습니다.

기분 좋게 시스템을 끄기 전 대시보드를 새로고침한 순간 저는 두 눈을 의심했습니다.

최대 4달러에서 5달러 수준으로 예상했던 작업에 무려 38.60달러가 청구되어 있었습니다.

어떻게 이런 일이 일어났을까요.

자정 무렵 모델 단가가 기습 인상된 것일까요, 아니면 코드에 무한 루프가 발생한 것일까요. 커밋 기록은 지극히 정상이었습니다. 불어난 수십 달러는 대체 어디로 빠져나간 것일까요.

## 2. 10분의 캐시 절벽과 노드 간 라우팅 붕괴

터미널 로그와 HTTP 응답 헤더를 30분 넘게 추적한 끝에 마침내 원인이 밝혀졌습니다.

단서는 응답 헤더에 기록된 백엔드 프로바이더 필드에 숨어 있었습니다.

초반 15턴까지는 특정 연산 호스팅 업체로 프로바이더가 고정되어 있었습니다. 하지만 식사를 마치고 돌아온 16턴 호출부터 프로바이더가 다른 호스팅 인프라로 바뀌어 있었습니다.

이것이 바로 긴 컨텍스트를 다루는 Agent 작업에서 중계 플랫폼이 유발하는 치명적인 구조적 결함입니다.

OpenRouter 와 같은 서비스는 본질적으로 트래픽을 분산 전달하는 지능형 라우팅 계층입니다. 자체적인 대형 데이터센터를 보유하기보다는 Together, Fireworks, DeepInfra, Novita, Lepton 같은 외부 연산 업체로 요청을 전달합니다.

사용자의 연산 비용을 절감하기 위해 플랫폼은 캐시 인지 라우팅 알고리즘을 운영합니다.

하지만 이 메커니즘에는 치명적인 제약이 존재합니다. 세션 선호도 매핑의 유지 시간이 단 10분에 불과하다는 점입니다.

10분 이내에 연속해서 요청을 전송하면 스케줄러는 동일한 호스팅 업체의 동일 GPU 노드로 요청을 유지합니다.

그러나 사용자의 대기 시간이 10분을 넘기거나 대상 업체의 대기열이 급증하면 어떻게 될까요.

스케줄러는 즉각적인 라운드로빈 폴백을 실행하여 다음 요청을 전혀 다른 생소한 서버로 넘겨버립니다.

여기서 엄청난 비용 폭탄이 터집니다.

이전 업체의 GPU 메모리에는 지난 15턴 동안 축적된 28K 토큰의 KV Cache 가 따뜻하게 보존되어 있었습니다. 반면 새로 배정된 서버는 이전 대화 내역에 대해 아무것도 모릅니다. VRAM 은 완전히 비어 있습니다.

맥락 없이 전달된 2만 8천 토큰의 장문에 대해 새 서버가 취할 수 있는 조치는 단 하나뿐입니다.

전달받은 28K 컨텍스트 전체를 처음부터 무거운 Prefill 행렬 연산으로 다시 계산하는 것입니다.

과금 요율은 즉시 요동칩니다.

캐시가 적중하면 100만 토큰당 비용은 0.014달러에 불과합니다. 캐시가 증발하면 미적중 전액 요율인 0.14달러가 적용됩니다.

단가가 순식간에 10배로 뛰어오르는 셈입니다.

Agent 가 코드베이스를 더 깊이 분석할수록 컨텍스트는 30K 에서 50K 로 불어납니다.

작업 도중 10분 이상의 공백이 발생할 때마다 캐시 체인은 깨어지고, 초반에 절약했던 모든 비용 혜택은 흔적도 없이 사라집니다.

응답 지연 역시 극심해집니다.

캐시가 작동하던 초반에는 전송 후 1초대에 첫 토큰이 출력되었습니다. 캐시가 증발한 후에는 2만 8천 토큰을 전량 재계산하느라 터미널 커서가 17초 동안 얼어붙었습니다.

자동화 스크립트가 17초간의 지연을 네트워크 타임아웃으로 오인하지 않는다고 보장할 수 있을까요.

불필요한 재시도가 격발되면 다시 한번 전량 재계산이 발생합니다. 몇 달러로 끝났어야 할 작업이 노드 간 캐시 재계산으로 인해 38달러까지 불어난 것입니다.

## 3. 공식 직결 API 의 영구 프리픽스 캐시 강점

중계 라우팅에 10분의 절벽이 존재하는 반면, DeepSeek 공식 API 직결에서는 왜 이러한 현상이 발생하지 않을까요.

원인은 서버단 VRAM 스케줄링 설계의 철학적 차이에 있습니다.

공식 클러스터는 처음부터 전역 프리픽스 캐시 구조를 바탕으로 설계되었습니다. 전송된 시퀀스의 앞부분이 기존 데이터와 일치하기만 하면 분산 스케줄러는 이미 연산된 어텐션 텐서를 즉시 재사용합니다.

공식 노드의 캐시 보존 기간은 얼마나 될까요. 결코 5분이나 10분 같은 짧은 주기가 아닙니다.

일반적인 운영 환경에서 공식 컨텍스트 캐시는 수 시간에서 다음 날까지 유지됩니다. 밤에 노트북을 닫고 다음 날 아침 작업을 재개해도 수만 토큰의 이전 컨텍스트가 VRAM 에 온전히 남아 있을 확률이 대단히 높습니다.

실제 비용 비교표를 살펴보겠습니다.

```text
DeepSeek 공식 API 캐시 적중 여부에 따른 비용 비교：
┌────────────────────────┬─────────────────────┬─────────────────────┐
│ 비용 및 성능 지표     │ 완전 캐시 적중      │ 완전 캐시 증발      │
├────────────────────────┼─────────────────────┼─────────────────────┤
│ 100만 tok당 입력 단가 │ 0.014 USD           │ 0.140 USD           │
│ 30K 컨텍스트 1회 비용  │ 약 0.00042 USD      │ 약 0.00420 USD      │
│ 40턴 누적 입력 비용    │ 약 0.28 USD         │ 약 3.65 USD         │
│ 첫 토큰 지연 시간 P95 │ 약 1.2 초           │ 약 14.8 초          │
└────────────────────────┴─────────────────────┴─────────────────────┘
```

수치의 격차는 매우 뚜렷합니다.

40턴의 깊은 상호작용에서 캐시가 유지되면 총 입력 비용은 30센트 미만입니다. 캐시가 매번 깨어질 경우 입력 비용만 3달러를 초과합니다.

데이터 보안 정책의 차이도 중요합니다.

중계 플랫폼을 거치는 것은 수많은 독립 서드파티 노드를 경유한다는 뜻입니다. 사내 코드가 어느 업체의 호스트 메모리에 머물렀는지 법적으로 안전한 보장을 받기 어렵습니다.

공식 API 는 제로 데이터 보존 정책을 명시하고 있으며, 사용자 입력 데이터를 향후 모델 훈련에 사용하지 않습니다. 기업의 핵심 코드를 다루는 입장에서 이러한 보장은 매우 든든한 기준선이 됩니다.

## 4. 프리픽스 캐시를 완벽하게 활용하는 엔지니어링 패턴

공식 엔드포인트로 바꾸기만 하면 모든 문제가 해결될까요.

그렇지 않습니다. 코드 내부의 요청 구성 방식이 미흡하다면 개발자 스스로 캐시를 파괴하게 됩니다.

많은 개발자들이 시스템 프롬프트 맨 앞에 현재 시각을 문자열로 무심코 조합하곤 합니다.

매 루프마다 무작위 UUID 를 생성하여 메시지 머리에 주입하는 경우도 흔합니다.

이러한 사소한 습관이야말로 프리픽스 캐시를 무너뜨리는 주범입니다.

프리픽스 캐시는 좌측에서 우측으로 완벽하게 일치하는 토큰 해시를 추적합니다. 맨 앞 10번째 토큰이 초 단위로 바뀌는 타임스탬프라면 뒤에 5만 줄의 동일한 코드가 따라붙더라도 10번째 위치에서 캐시 체인이 끊어집니다.

그 뒤의 모든 문맥은 미적중 처리됩니다.

캐시 적중률을 90% 이상으로 유지하려면 다음과 같이 페이로드를 조립해야 합니다.

```python
import os
import requests

DEEPSEEK_API_KEY = os.environ.get("DEEPSEEK_API_KEY")
API_ENDPOINT = "https://api.deepseek.com/v1/chat/completions"

# 정적 시스템 프롬프트: 동적 타임스탬프나 난수 혼입을 엄격히 금지
STATIC_SYSTEM_PROMPT = (
    "You are a senior code refactoring engineer. "
    "Follow PEP 8 rules and emit only structured diffs."
)

def build_stable_payload(session_history, new_user_msg, current_time_str):
    messages = [
        {"role": "system", "content": STATIC_SYSTEM_PROMPT}
    ]
    # 대화 내역은 시간 순서대로 덧붙이며 이전 메시지를 수정하지 않음
    for item in session_history:
        messages.append(item)
    
    # 동적 메타데이터는 오직 최신 사용자 입력 맨 뒤에만 부착
    decorated_user_msg = f"{new_user_msg}
[Meta: {current_time_str}]"
    messages.append({"role": "user", "content": decorated_user_msg})
    
    return {
        "model": "deepseek-chat",
        "messages": messages,
        "temperature": 0.0,
        "stream": False
    }

def call_deepseek(payload):
    headers = {
        "Authorization": f"Bearer {DEEPSEEK_API_KEY}",
        "Content-Type": "application/json"
    }
    resp = requests.post(API_ENDPOINT, json=payload, headers=headers, timeout=60)
    data = resp.json()
    
    usage = data.get("usage", {})
    cache_hit_tokens = usage.get("prompt_cache_hit_tokens", 0)
    cache_miss_tokens = usage.get("prompt_cache_miss_tokens", 0)
    
    return data, cache_hit_tokens, cache_miss_tokens
```

원리는 지극히 명료합니다.

첫째, 고정된 역할 지시문을 최상단에 고정할 것.

둘째, 이전 대화 기록을 손대지 않고 순차적으로 누적할 것.

셋째, 날짜나 동적 변수는 오직 최신 메시지 말미에만 배치할 것.

앞선 바이트 스트림을 온전히 유지함으로써 스케줄러는 밀리초 단위로 기존 VRAM 을 재사용하고 캐시 적중률을 90% 이상으로 유지할 수 있습니다.

## 5. Google 의 100조 토큰 통계 뒤에 숨겨진 차이

시장 전체의 데이터 비교로 돌아와 보겠습니다.

OpenRouter 의 27조 토큰 기록을 다룬 글 아래에는 Google 의 일일 100조 토큰을 비교 대상으로 거론하며 회의적인 반응을 보이는 목소리도 적지 않습니다.

그러나 측정 기준을 분리하지 않은 단순 비교는 심각한 착시를 부릅니다.

Google 의 100조 토큰 중 95% 이상은 정적인 캐시 읽기 작업입니다.

현대 검색 인프라에서 수억 개에 달하는 인기 검색어의 인덱스와 템플릿은 TPU 메모리에 상시 상주해 있습니다.

사용자가 검색할 때 발생하는 대부분의 과정은 초고속 캐시 인출이며, 새로운 토큰을 만들어내는 순수 연산은 아주 적은 비중에 불과합니다.

또한 Google 연산 자원의 최대 소비자는 검색 요약, 추천 시스템, 사내 서비스 등 자체 인프라입니다.

자체 생태계 내부에서 고도로 캐시화된 읽기 트래픽과, OpenRouter 에서 전 세계 개발자들이 비용을 지불하며 미지의 코드를 검증하는 실연산 트래픽은 차원이 다른 작업입니다.

캐시 적중률을 도외시한 채 총 토큰 수만 바라보는 것은 수치상의 착시에 불과합니다.
