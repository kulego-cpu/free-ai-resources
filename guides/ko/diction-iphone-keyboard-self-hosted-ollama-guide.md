# iPhone 키보드를 홈 서버 Ollama에 연결하기: Diction 음성 입력 자체 호스팅 실전

스마트폰에서 타이핑할 때 그 데이터는 과연 어디로 흘러들어갈까요?

정보 유출에 대한 우려는 현실적인 문제입니다.

모바일 환경에서 음성 입력을 사용하거나 AI 문장 교정 기능을 활용하는 것은 수많은 엔지니어에게 익숙한 일상입니다.

그러나 그에 따르는 대가는 결코 가볍지 않습니다.

상용 키보드 앱들은 인식률을 유지한다는 명목 아래 전체 접근 권한을 요구하는 경우가 많으며, 사용자의 모든 키 입력과 원본 음성 데이터, 클립보드 복사 내용까지 실시간으로 원격 퍼블릭 클라우드로 전송됩니다.

키보드는 스마트폰에서 가장 민감한 정보가 통과하는 관문입니다.

상용 키보드를 거쳐 시스템 비밀번호나 기업 내부 업무 문서를 작성하는 것에 불안감을 느끼지 않을 사람은 없습니다.

오픈소스 커뮤니티의 개발자 Better-Psychology-42는 Diction 프로젝트를 통해 깔끔한 해법을 제시했습니다.

핵심 원리는 매우 명료합니다:
음성 인식 전사와 AI 텍스트 윤문 게이트웨이를 온전히 개인 홈 서버에 구축하는 것입니다.

스마트폰에는 오직 가벼운 키보드 입력 인터페이스만 남겨둡니다.

## 아키텍처 분석: 데이터가 내부망을 벗어나지 않는 3단계 구조

Diction의 시스템 구조는 세 가지 계층으로 분리되어 있습니다.

첫 번째 계층은 iOS 키보드 익스텐션입니다.
이 계층은 철저한 온디바이스 샌드박스 격리 원칙을 준수합니다:
일반 QWERTY 타건, 제스처 슬라이드 입력, 로컬 철자 교정 로직은 전적으로 iPhone 기기 내부에서만 처리됩니다;
오직 사용자가 마이크 버튼을 명시적으로 누르는 순간에만 임시로 오디오 캡처 채널이 열립니다.

백그라운드 통신은 완전히 차단됩니다.

두 번째 계층은 자체 호스팅 백엔드 게이트웨이입니다.
기기에서 압축된 원본 음성 스트림은 보안 터널을 거쳐 개인 서버로 전달되며, 내장된 Whisper 엔진을 통해 수 밀리초 만에 구두점 없는 텍스트로 고속 변환됩니다.

로컬 환경에서의 음성 전사 속도는 대단히 빠릅니다.

세 번째 계층은 소형 언어 모델 추론 백엔드입니다.
게이트웨이는 표준 HTTP 인터페이스를 통해 홈 네트워크의 Ollama 인스턴스와 통신합니다;
소형 모델이 수백 밀리초 이내에 문맥 구두점 복원, 어순 보정, 불필요한 추임새 제거를 수행한 뒤 구조화된 데이터 형태로 스마트폰의 현재 커서 위치에 즉시 반영합니다.

파이프라인 전체는 OpenAI 규격과 호환되는 모든 API 엔드포인트를 지원합니다.

사용자의 데이터는 최종적으로 어디에 머무를까요?

키 입력은 기기 안에 남습니다.
음성 데이터는 홈 서버 안에 남습니다.
제3자 클라우드 기업이 데이터를 들여다볼 여지는 전혀 없습니다.

## 4B 소형 모델이 키보드 문장 정제에 가장 적합한 이유

개인 서버를 구성할 때 습관적으로 70B 급의 대형 모델을 올리려는 시도가 적지 않습니다.

하지만 모바일 키보드 윤문 작업에서는 4B 크기의 소형 모델이 훨씬 뛰어난 효율을 발휘합니다.

키보드 텍스트 정제는 자유 대화형 챗봇 작업과 성격이 완전히 다릅니다.

이 작업은 엄격한 제약을 갖는 단문 시퀀스 교정 워크로드입니다:
누락된 쉼표와 마침표 추가;
어, 음, 저기 같은 불필요한 구어체 군더더기 제거;
발음이 유사한 오탈자 교정;
숫자와 영단어의 대소문자 규격 정리.

이처럼 단순한 단문 교정 작업에 수백억 파라미터 기반의 복합 추론 모델은 필요하지 않습니다.

대형 모델을 모바일 입력에 적용하면 입력 지연이 심각해집니다.

지연시간이 왜 치명적일까요?

첫 번째 토큰이 출력될 때까지의 대기시간이 지나치게 길기 때문입니다.

모바일 키보드 환경에서 인간이 지연을 용인할 수 있는 한계는 통상 1.5초에서 2초 안팎입니다;
길거리에서 한마디 말을 던진 후 멈춰 선 커서를 바라보며 4초 이상 멍하니 기다려야 한다면 실제 업무 환경에서 활용할 수 없습니다.

입력 리듬이 완전히 깨져버립니다.

12GB VRAM을 갖춘 RTX-3060 그래픽카드 환경에서 실측한 결과는 명확합니다:
Qwen3.5-4B 수준의 소형 모델을 Ollama에서 FP16 또는 Q8_0 양자화 상태로 구동하고 컨텍스트를 512 토큰으로 제한했을 때;
단일 토큰 생성 지연은 180밀리초에 불과하며 문장 전체를 재작성하는 데 걸리는 시간은 400밀리초 이내로 억제됩니다.

응답 속도가 대단히 민첩합니다.

로컬 네트워크 통신과 Whisper 음성 전사 시간을 모두 합산해도 전체 엔드투엔드 대기시간은 약 1.3초 수준에서 안정적으로 유지됩니다.

입력 체감은 매우 매끄럽습니다.

## 실전 배포: Tailscale 터널링과 Prompt 통제 원칙

개인 서버에 이 시스템을 실제로 배포할 때 점검해야 할 엔지니어링 포인트는 무엇일까요?

첫 번째 과제는 외부 네트워크 통신망 확보입니다.

스마트폰은 외출 시 대부분 이동통신사 셀룰러 네트워크에 연결됩니다.

인증 장치 없이 Ollama 포트를 공용 인터넷에 노출하는 것은 지극히 위험합니다;
Tailscale이나 자체 WireGuard 기반의 가상 사설망을 구축하여 암호화 통신을 유지하는 것이 정석입니다.

5G 통신망에서 홈 서버의 Tailscale 노드로 접속했을 때 왕복 지연시간 증가는 35밀리초 수준에 불과했습니다;
외부에서도 가정 내 Wi-Fi와 구별되지 않는 반응 속도로 동작합니다.

연결 안정성은 매우 견고합니다.

두 번째 핵심 사항은 시스템 프롬프트의 불필요한 인사말 차단입니다.

범용 언어 모델은 대화형 인사말을 자의적으로 덧붙이는 습성이 있습니다:
수정된 문장을 알려드립니다;
도움이 되었기를 바랍니다 같은 군더더기 텍스트입니다.

급하게 메신저로 답장을 보내야 하는 순간에 모델이 이런 인사를 출력해 버리면 입력창에 불필요한 문자가 그대로 삽입됩니다.

게이트웨이에서 설정하는 정제 프롬프트에는 엄격한 제약 조건을 걸어야 합니다:
```text
You are a text cleanup engine. 
Task: Fix grammar, add punctuation, remove filler words like um/uh/er. 
Rule: Output ONLY the cleaned text. Never add explanations or greetings.
```
대화형 응답은 철저히 금지되어야 합니다.

모델은 차가운 텍스트 필터로서만 기능해야 합니다.

## 실제 운영 한계와 트레이드오프

이 아키텍처에 단점은 전혀 없을까요?

현실적인 운영 환경에서는 몇 가지 제약이 뒤따릅니다:

첫째는 VRAM 상주 여부와 콜드 스타트 지연입니다.
서버에서 다른 백그라운드 작업이 실행되어 Ollama가 4B 모델을 시스템 메모리로 내려놓을 경우, 첫 번째 음성 입력 시 약 4초의 모델 로딩 지연이 발생합니다.
이를 방지하려면 keep_alive 옵션을 명시적으로 지정하여 상시 상주시켜야 합니다:
```bash
curl http://localhost:11434/api/generate -d '{"model": "qwen3.5:4b", "keep_alive": -1}'
```
소형 모델을 GPU 메모리에 영구 고정합니다.

둘째는 iOS 키보드 익스텐션의 메모리 상한선입니다.
애플은 서드파티 키보드 프로세스에 대해 50MB에서 70MB 수준의 엄격한 상주 메모리 제한을 둡니다.
스마트폰 내부에서 무거운 음성 처리를 시도하면 운영체제에 의해 즉시 강제 종료됩니다;
부하가 큰 연산은 백엔드 서버로 밀어내야 합니다.

셋째는 오프라인 환경에서의 폴백 동작입니다.
지하 주차장이나 통신 음영 지역에서 네트워크가 끊길 경우의 처리 방식입니다.
Diction은 매끄러운 단계적 기능 축소를 지원합니다;
연결이 끊기는 즉시 AI 윤문을 멈추고 온디바이스 로컬 QWERTY 타건 모드로 전환되므로 기본적인 문자 입력 흐름은 중단되지 않습니다.

키보드 입력 데이터는 개인 프라이버시를 지키는 최전선입니다.

데이터 주권을 온전히 자신의 손안에 쥐는 것;
오래된 그래픽카드로 매일 사용하는 스마트폰 입력을 구동하는 것;
이러한 든든한 통제감이야말로 오픈소스 자체 호스팅이 주는 진정한 보람 아닐까요?
