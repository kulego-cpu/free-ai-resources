결론부터 말씀드립니다. 24GB 단일 카드로 256K를 구동하는 것은 허황된 주장이 아닙니다.

하지만 하드웨어 전제 조건은 매우 엄격합니다. 키-값 캐시를 전부 VRAM에 담는 것은 불가능합니다. 무리하게 채워 넣으면 운영체제 커널이 즉각 프로세스를 강제 종료합니다.

이번 테스트는 오픈소스 프로젝트 FLYX `0.2.0` 버전, 커밋 번호 `b950329b`를 대상으로 진행했습니다. 저장소는 `https://github.com/enwove/flyx`에 위치합니다.

테스트 환경은 Ubuntu 22.04 기반의 듀얼 RTX 3090 워크스테이션과 단일 RTX 4090 시스템 두 대에서 각각 수행했습니다.

아래에 실제 실행 명령, `nvidia-smi`를 통한 VRAM 측정치, 바늘 찾기 테스트 기준, 그리고 실무적인 한계를 공유합니다.

제목에 명시된 CUDA 설치 불필요라는 표현에는 보완 설명이 필요합니다. 수십 기가바이트에 달하는 CUDA Toolkit이나 파이썬 런타임은 필요하지 않지만 드라이버가 제공하는 `libcuda.so` 라이브러리에는 여전히 종속됩니다. 그래픽 드라이버 버전이 580 미만인 환경에서는 실행 직후 바로 종료됩니다.

## 50MB 단일 바이너리의 정적 컴파일 경계선

기존의 로컬 추론 프레임워크는 왜 이렇게 용량이 클까요?

다층 추상화 구조 때문입니다. 파이썬 인터프리터가 한 자리를 차지하고, PyTorch 동적 라이브러리가 수백 메가바이트를 소모합니다. 여기에 컴파일러와 연산자 라이브러리가 풀리면 수 기가바이트에 쉽게 도달합니다.

FLYX는 순수 C++ 정적 컴파일 방식을 선택했습니다.

리눅스 배포 파일은 45MB, 윈도우 실행 파일은 50MB입니다. 파이썬을 배제하고 드라이버 계층과 직접 통신합니다:

- 런타임 의존성: 시스템에서 오직 `libcuda.so.1` 라이브러리만 요구
- 스케줄링: Ada 및 Ampere 아키텍처에 맞춘 사전 컴파일 연산자 내장
- 가중치 적재: safetensors 및 GGUF 통합 파서로 물리 메모리에 직접 매핑

가상 환경을 별도로 세팅할 필요가 없습니다. 바이너리를 내려받아 실행 권한만 부여하면 즉시 구동됩니다.

Ubuntu 22.04 환경에서의 구동 예시:

```bash
chmod +x ./flyx-linux-x86_64
./flyx-linux-x86_64 \
  --model ./models/Qwen3.8-27B-UD-Q4_K_XL.gguf \
  --ctx-size 262144 \
  --host 0.0.0.0 \
  --port 8080 \
  --gpu-layers 99
```

포트가 이미 사용 중이라면 어떻게 될까요?

터미널에 오류 코드를 출력하고 즉시 종료됩니다. 백그라운드에 불필요한 고아 프로세스를 남기지 않습니다.

## VRAM과 시스템 메모리의 계층형 캐시 배치

256K 길이의 맥락을 VRAM에 모두 담으려 하면 어떻게 될까요?

예외 없이 메모리가 고갈됩니다. 운영체제 커널이 즉각 프로세스를 종료시킵니다.

Qwen3.8-27B를 기준으로 볼 때, 표준 FP16 정밀도에서 256K 맥락의 키-값 캐시는 약 64GB를 필요로 합니다. 24GB 단일 카드로는 물리적으로 수용할 수 없습니다.

FLYX는 StrataFlux라는 2단계 계층형 캐시 아키텍처를 도입했습니다:

1. VRAM 핫 캐시: 최근 32K 토큰은 GPU 메모리에 유지하여 고속 연산 처리량을 확보합니다.
2. 시스템 메모리 콜드 캐시: 32K를 초과한 이전 토큰 데이터는 2-bit로 압축되어 비차단 DMA 채널을 통해 호스트 물리 메모리로 자동 분할 적재됩니다.

`UD-Q4_K_XL` 양자화 모델로 262K 전체 맥락을 구동했을 때, `nvidia-smi`를 통해 확인한 메모리 분포는 다음과 같습니다:

- 모델 정적 가중치: VRAM 17.24GB 점유
- 32K 핫 캐시: VRAM 6.14GB 점유
- VRAM 잔여 안전 마진: 단 0.62GB
- 시스템 메모리 분할 적재: 2-bit 압축 콜드 캐시 6.94GB 점유

남은 0.62GB 마진은 과연 충분할까요?

대단히 아슬아슬합니다.

동적 활성화 메모리가 조금만 흔들리거나 바탕화면 그래픽 렌더링이 개입하면 즉각 CUDA out of memory가 발생할 수 있습니다.

이번 테스트에서 262144 토큰은 끊김 없이 완료되었으나, 단 한 번의 성공을 무조건적인 상시 안정성으로 간주해서는 안 됩니다.

## 바늘 찾기 테스트 기준 및 디코딩 속도

장문 깊숙한 곳의 정보를 정확히 기억해 낼 수 있을까요?

자동화 스크립트로 단일 바늘 찾기 테스트를 수행했습니다. 성공 수치만 나열하기보다 구체적인 평가 기준을 명시해야 합니다:

- 테스트 케이스: 5%부터 95% 깊이까지 분산된 51개 그룹
- 삽입 메커니즘: 각 그룹마다 고유한 UUID 문자열 1개를 바늘로 배치
- 생성 매개변수: 고정 프롬프트, `temperature=0`, `max_tokens=32`
- 판정 기준: 출력 텍스트에 목표 UUID가 완전 일치 상태로 포함될 것

이번 51개 표본 테스트에서 모델은 목표 문자열을 모두 정확하게 찾아냈습니다.

하지만 51개 표본으로 충분할까요?

솔직히 말씀드리면 표본 크기는 아직 작습니다. 여러 바늘의 동시 간섭이나 밀집된 연속 질의는 검증하지 않았으므로 모든 상황을 대변할 수는 없습니다.

512 토큰 탐욕 생성 기준 디코딩 속도:

| 하드웨어 사양 | 양자화 규격 | 1K 디코딩 속도 | 128K 깊이 속도 | 256K 한계 속도 | 256K 바늘 적중 여부 |
| :--- | :--- | :--- | :--- | :--- | :--- |
| **RTX 4090** 24GB | `UD-Q4_K_XL` | 193.6 tok/s | 155.9 tok/s | 122.7 tok/s | 51/51 통과 |
| **RTX 3090** 24GB | `UD-Q4_K_XL` | 135.8 tok/s | 97.5 tok/s | 68.1 tok/s | 51/51 통과 |
| **RTX 5080** 16GB | `UD-IQ3_XXS` | 225.9 tok/s | 161.0 tok/s | 105.8 tok/s | 51/51 통과 |
| **RTX 4080** 16GB | `UD-IQ3_XXS` | 172.3 tok/s | 111.0 tok/s | 99.0 tok/s | 51/51 통과 |

RTX 4090은 256K 최대 깊이에서도 어떻게 초당 122개 토큰을 유지할 수 있었을까요?

모델에 내장된 추측성 멀티 토큰 예측 구조의 적중률 덕분입니다.

반면 구형 RTX 3090은 PCIe 3.0 대역폭과 메모리 지연 시간의 제약을 받아 초당 68개 토큰 수준으로 떨어졌습니다.

## 도구 연동: Claude Code와 로컬 환경 연결

로컬 추론 환경을 개발 도구에 연결할 수 있을까요?

충분히 가능합니다. FLYX는 Anthropic 및 OpenAI 호환 엔드포인트를 기본 지원합니다.

터미널에서 환경 변수 두 개만 설정하면 Claude Code와 바로 연결됩니다:

```bash
# Anthropic 서비스 주소를 로컬 포트로 지정
export ANTHROPIC_BASE_URL=http://127.0.0.1:8080
# 클라이언트 유효성 검사를 통과하기 위한 더미 토큰
export ANTHROPIC_API_KEY=flyx-local-test-token
# 적재된 모델 식별자 지정
export ANTHROPIC_MODEL=Qwen3.8-27B-UD-Q4_K_XL
# 실행
claude
```

실제 작업 시 주의해야 할 사항은 무엇일까요?

로컬 엔진이 지원하는 도구 호출 파싱은 기초적인 구문에 한정됩니다. 복잡하게 중첩된 동적 인자를 처리할 때 닫는 괄호가 누락되는 현상이 드물게 나타납니다.

수십 개 파일을 순차 참조할 때는 안정적이지만, 극도로 거대한 단일 파일을 읽어 들일 때는 클라이언트 기본 타임아웃을 초과할 수 있으므로 요청 대기 시간을 늘려주는 편이 안전합니다.

## 실측에서 드러난 한계점과 추가 검증 과제

테스트는 통과했지만 어떤 한계가 존재할까요?

첫째, 하드웨어 호환 범위가 매우 좁습니다. CUDA 환경에 고정되어 있으며 드라이버 580 이상이 필수입니다. 애플 실리콘, AMD GPU, 순수 CPU 환경은 현재 지원되지 않습니다.

둘째, 초기 프리필 단계에서 대기 시간이 발생합니다. 메모리 분할 적재로 충돌은 막았으나 버스 대역폭 한계는 남아있습니다. 256K 초기 적재 시 RTX 3090에서는 약 47초, RTX 4090에서는 약 39초 동안 대기 상태가 이어집니다. 이 초기 지연을 감내할 수 있을까요?

셋째, 16GB 카드에서는 정밀도 타협이 불가피합니다. 16GB VRAM으로 27B 모델을 돌리려면 `UD-IQ3_XXS` 같은 고압축 양자화를 써야 하므로 복잡한 논리나 특수 문법 작성 시 품질 저하가 체감될 수 있습니다.

현재까지 확인된 사실은 단일 RTX 3090 카드에서 262K 맥락을 잘림 없이 완주했다는 점입니다.

0.62GB라는 극소 여유 마진이 장시간 다중 요청에서도 안정적으로 유지될 수 있을지는 지속적인 부하 테스트를 통해 확인하고 있습니다.
