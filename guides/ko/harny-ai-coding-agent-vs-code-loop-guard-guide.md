현장의 현실부터 짚어보겠습니다. 로컬 소형 모델로 자율 코딩 Agent를 구동하면 열에 여덟은 실패합니다.

많은 개발자가 Mac이나 16GB VRAM을 갖춘 PC에서 Ollama나 llama.cpp를 이용해 Qwen2.5-Coder-7B Q4_K_M이나 Llama-3.1-8B-Instruct를 실행합니다. 한두 번의 코드 자동완성이나 일상 대화는 꽤 매끄럽습니다. 하지만 VS Code 내에서 도구 호출 권한을 부여하고 자율적으로 코드를 수정하게 두면 금세 통제 불능 상태에 빠집니다.

가장 흔한 실패 유형은 두 가지입니다：

첫째는 무한 루프입니다. 소형 모델은 동일한 오류 주위를 맴돌며 같은 도구를 반복 호출하고 컨텍스트 한계를 다 채울 때까지 멈추지 않습니다.

둘째는 디스크 강제 덮어쓰기입니다. 모델이 지시를 조금만 잘못 이해해도 기존 소스 파일 전체를 뼈대만 남긴 채 덮어써 버려 되돌리기 어렵게 만듭니다.

오픈소스 확장 프로그램 Harny는 이 두 가지 고질병을 해결하기 위해 개발되었습니다. GitHub의 spltek/harny 저장소에 MIT 라이선스로 공개되어 있으며 현재 실측 버전은 v0.3.2입니다. VS Code 및 VSCodium 사이드바에서 동작하는 이 도구는 모델의 지능을 과장하기보다 Loop Guard와 Analyze 사전 점검 모드라는 확실한 브레이크를 제공합니다.

로컬 모델이 일상적인 리팩터링 작업을 감당할 수 있을까요. 이 방어 체계가 과연 위험을 제대로 막아낼 수 있을까요.

## 소형 모델이 Agent 작업에서 겪는 구조적 한계

수천억 파라미터를 갖춘 클라우드 모델은 자기 수정 능력과 장기 계획 역량이 뛰어납니다. 도구 실행이 실패하더라도 보통 두 턴 이내에 다른 접근법을 찾습니다.

그렇다면 7B에서 14B급 로컬 소형 모델은 어떨까요.

소형 모델이 Agent 환경에서 실패하는 원인은 치명적인 세 가지에 있습니다：

가장 가벼운 문제는 주의력 분산입니다. 대화 턴이 늘어남에 따라 터미널 명령 출력과 파일 내용이 컨텍스트에 계속 쌓입니다. 수천 토큰이 차오르면 모델은 초기 지시사항을 잊어버립니다. 스펙 시트에 적힌 32K 컨텍스트는 벤치마크 수치일 뿐 실전 약속이 아닙니다.

더 심각한 문제는 같은 오류의 반복입니다. 첫 번째 도구 호출이 실패하고 에러를 확인했을 때 소형 모델은 추론을 되돌리지 못합니다. 무의식적으로 동일한 매개변수를 넣어 다시 실행하고 똑같은 답변을 반복합니다. 탐욕적 샘플링의 국소 해가 블랙홀처럼 모델을 가둡니다.

가장 치명적인 것은 확인 없는 덮어쓰기입니다. 대다수 통합형 Agent는 작업 공간의 파일을 바로 수정합니다. 논리가 흔들린 소형 모델은 정상 코드를 지워버려 프로젝트를 훼손합니다.

Harny의 접근법은 명확합니다. 모델이 스스로 똑똑하게 대처하지 못한다면 외부 런타임 하네스가 확정적인 안전장치를 제공해야 한다는 것입니다.

## 핵심 분석 1：Loop Guard로 무한 루프 강제 차단

Agent 실측에서 토큰을 가장 많이 낭비하고 스트레스를 주는 상황은 단연 무한 루프입니다.

Harny는 실행 레이어에 실시간 Loop Guard를 탑재했습니다. 모델이 스스로 깨닫기를 기다리는 대신 슬라이딩 지문 테이블을 유지하여 패턴을 추적합니다.

```text
모델이 도구 호출 발생
       │
       ▼
┌──────────────────┐
│ 호출 지문 해시 계산 │  함수명 + 매개변수 해시 + 출력 유사도
└────────┬─────────┘
       │
       ▼
       / 반복 패턴 감지？ \
     <                     > ── 아니오 ──▶ 정상 실행 허용
       \       예          /
       │
       ▼
┌──────────────────┐
│ Loop Guard 발동  │
└────────┬─────────┘
       │  단계별 개입
       ├─▶ 1단계：반복을 경고하고 조사 방식 변경을 요구하는 프롬프트 주입
       ├─▶ 2단계：현재 도구 실행을 차단하고 호출 스택 롤백
       └─▶ 3단계：세션을 중단하고 수동 조작으로 제어권 반환
```

실제 테스트 환경에서 Ollama의 Qwen2.5-Coder-7B에게 TypeScript 타입 오류 수정을 지시했습니다. 터미널에는 다음 오류가 출력되었습니다：

```text
src/index.ts:14:7 - error TS2322: Type 'string' is not assignable to type 'number'.
npm run build exited with code 2
```

모델은 잘못된 수정을 가했습니다. 두 번째 빌드도 실패했습니다. 모델은 반성 없이 세 번째에도 완전히 같은 명령을 호출하려 했습니다.

평소라면 터미널이 헛도는 것을 지켜봐야 했겠지만 이번에는 세 번째 실행 직전 Harny 화면에 차단 경고가 표시되었습니다：

```text
[Loop Guard] Detected repeated tool execution: npm run build
Action blocked. Injecting steering prompt to switch investigation approach.
```

도구 실행 권한을 강제로 회수하고 tsconfig.json과 소스 타입 선언을 read_file로 확인하도록 유도하는 지침이 주입되었습니다.

이 단계에서 무의미한 반복이 끊어지며 한정된 컨텍스트 공간이 보존되었습니다.

## 핵심 분석 2：Analyze 모드의 Dry-run 방어벽

코드 수정에서 가장 두려운 것은 실수로 인한 코드 손실입니다.

Harny는 작업 모드를 **Analyze 분석 모드**와 **Build 빌드 모드** 두 가지로 분리했습니다.

세션은 기본적으로 Analyze 모드로 동작합니다. 이 상태에서는 파일 생성, 수정, 삭제와 관련된 모든 도구가 Dry-run 시뮬레이션 상태로 돌아갑니다.

이것이 의미하는 바는 무엇일까요.

추론과 실제 디스크 쓰기 사이에 물리적 장벽이 생깁니다. Analyze 모드에서 모델은 코드를 수정했다고 착각하지만 실제 파일은 전혀 변하지 않습니다. 모델이 엉뚱한 판단을 내려도 한 글자도 지워지지 않습니다.

Harny는 사이드바에 정확한 Unified Diff 차이점 뷰를 띄웁니다. Git 커밋 전 코드 리뷰를 하듯 변경된 변수와 함수를 한 줄씩 점검할 수 있습니다.

차이점을 사람이 직접 확인하고 Build 모드로 전환해야만 실제 디스크 저장이 이루어집니다.

쓰기 권한을 사람의 손에 쥐여주는 설계가 심리적 안정감을 제공합니다.

## 핵심 분석 3：관찰 마스킹과 컨텍스트 메모장 운영

무한 루프 외에도 로컬 환경에서 자주 발생하는 문제는 메모리와 컨텍스트 고갈입니다. Apple Silicon M2 Pro 16GB 환경에서 8K 컨텍스트를 돌릴 때 긴 로그가 유입되면 메모리 압박이 심해집니다.

관찰 마스킹 Observation Masking은 널리 검증된 기법입니다. Anthropic의 컨텍스트 엔지니어링 분석과 JetBrains의 연구 보고서에서 입증되었듯 오래된 명령 출력을 요약으로 대체하고 최근 응답만 유지하면 긴 작업에서도 성능 저하가 거의 없습니다.

Harny의 구현 방식은 간결합니다：

첫째, 오래된 관찰 결과의 자동 마스킹입니다. 여러 턴의 대화에서 가장 최근 1회에서 2회의 명령 출력만 원형 그대로 보존합니다. 이전의 긴 출력은 상태 요약으로 자동 변환되어 사실 관계만 남기고 불필요한 문자열을 걸러냅니다.

둘째, 구조화된 Scratchpad 작업 메모장 유지입니다. 수정한 파일 목록과 현재 검증 단계만 별도 메모에 기록하고 이전 20턴 분량의 불필요한 대화는 컨텍스트에서 완전히 제거합니다.

8K 컨텍스트 모델에서 실측한 결과 지시사항 유실 없이 10턴 이상의 다중 파일 디버깅을 안정적으로 마칠 수 있었습니다.

## 실전 구성：Ollama에서 Harny 연결하기

로컬에서 안전한 Harny 환경을 구축하는 과정은 간단합니다：

### 1. 로컬 모델 엔드포인트 준비

Ollama나 llama.cpp를 실행합니다. Ollama의 경우 기본적으로 11434 포트가 열립니다：

```bash
ollama run qwen2.5-coder:7b
```

### 2. Harny 확장 프로그램 설정

VS Code 확장 메뉴에서 Harny를 설치하고 사이드바 설정을 엽니다：

- **API Protocol**: OpenAI Compatible 선택
- **Base URL**: `http://localhost:11434/v1`
- **API Key**: `ollama` 등 임의의 문자열 입력
- **Model Name**: `qwen2.5-coder:7b`

### 3. 디버깅 권장 운영 방식

로컬 모델을 다룰 때는 다음 수칙을 권장합니다：

반드시 Analyze 모드로 시작하십시오. 목표를 제시하고 모델이 파일을 읽어 Unified Diff를 제안하도록 만듭니다. 이 확인 단계를 생략해서는 안 됩니다.

Diff 경계를 눈으로 확인하십시오. 무관한 파일이 수정되지 않았는지, 기존 주석이 지워지지 않았는지 점검합니다.

확인 후 Build 모드로 전환하여 적용하십시오. 한 번의 클릭으로 반영한 뒤 로컬 터미널에서 테스트를 돌려 작업을 마무리합니다.

## 요약

초대형 클라우드 모델이 넘쳐나는 시대에 굳이 로컬 환경에서 모델을 실행할 이유가 있을까요.

이유는 분명합니다. 소스코드를 외부에 유출하지 않는 보안성, 오프라인 작업 가능성, 매달 청구되는 API 비용 절감입니다. 화려하지는 않지만 모두 포기하기 어려운 실질적 장점입니다.

Harny가 주는 교훈은 현실적입니다. 모델이 완벽한 범용 지능에 도달하기 전 과도기에는 견고한 실행 하네스와 방어적 아키텍처가 파라미터 규모의 한계를 효과적으로 보완해 줍니다.

남는 로컬 VRAM이 있다면 안전한 틀을 씌워 작업을 맡겨보시길 바랍니다.

확실한 브레이크와 안전 경계를 설정하면 로컬 모델도 훌륭한 조력자가 되어줍니다.
