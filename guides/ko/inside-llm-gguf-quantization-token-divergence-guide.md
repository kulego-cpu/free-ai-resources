로컬 환경에서 거대 언어 모델을 구동할 때 양자화 버전을 고르며 고민해 본 경험은 누구나 있을 것입니다.

가중치를 내려받기 전 망설임이 앞섭니다.

Q8_0을 받자니 파일 크기가 십수 기가바이트에 달합니다. 그래픽카드 VRAM에 다 들어가지 못해 시스템 메모리로 넘쳐나는 순간 생성 속도는 초당 2~3토큰으로 곤두박질치고 슬라이드 쇼처럼 멈칫거립니다.

그렇다고 Q2_K나 Q3_K를 받자니 용량은 VRAM에 여유롭게 들어가지만 마음 한구석이 찜찜합니다. 극단적으로 압축된 2비트나 3비트에서 모델의 지능이 얼마나 잘려 나갔는지 가늠하기 어렵습니다. 학술 논문에는 정연한 퍼플렉시티 통계표가 실리지만 실제 코드 작성과 논리 추론에서 그 수치가 무엇을 의미하는지 수치만으로는 알 길이 없습니다.

그 누구도 속을 꿰뚫어 보지 못합니다.

모델이 둔해지는 과정은 결코 완만하게 진행되지 않습니다. 긴 문맥 추론의 특정 전환점에서 확률 분포가 평탄해지며 겉보기에는 매끄럽지만 사실관계가 어긋난 후보 단어를 한 번 잘못 고르는 순간, 바로 그 한 단어를 기점으로 이후의 모든 생성이 환각으로 무너져 내립니다.

왜 갑자기 궤도를 이탈하는 것일까요?

지금까지 두 양자화 버전 간의 결정 차이를 확인하려면 엔지니어가 직접 파이썬 스크립트를 짜서 훅을 걸고 로짓을 수집해야 했습니다. 코드를 작성하는 것만으로도 머리가 아프고 문제 추적 효율도 극히 낮았습니다.

최근 GitHub에 공개된 오픈소스 프로젝트 inside-llm은 이 번거로운 분석 작업을 단일 바이너리 대화형 도구로 해결해 줍니다.

## 1. 하드웨어 환경과 단일 바이너리 아키텍처: 어떻게 구동되는가

측정 데이터의 기준점을 명확히 하기 위해 테스트 환경을 먼저 정리합니다:
- 운영체제: Ubuntu 24.04 LTS, Linux 6.8 커널
- 그래픽카드 및 드라이버: GeForce RTX 3060 12GB GDDR6, NVIDIA 드라이버 550.54.14, CUDA 12.4
- 프로세서 및 메모리: AMD Ryzen 5 5600 6코어, 32GB DDR4 물리 메모리
- 빌드 버전: inside-llm release v0.2.1, Git 커밋 a9f4c21, llama.cpp b3800 코어 내장

대다수의 시각화 분석 도구는 초기 설정이 몹시 번거롭습니다. 파이썬 가상환경을 만들고 PyTorch를 설치하며 빌드 의존성을 맞추다 CUDA 드라이버 버전이 어긋나면 환경 구축에만 반나절이 날아갑니다.

inside-llm의 설계 방식은 실용적인 C++ 엔지니어의 철학을 잘 보여줍니다. 백엔드 엔진은 C++17로 작성되어 llama.cpp 및 ggml 라이브러리와 정적으로 링크됩니다. 웹 프론트엔드는 Svelte 5 프레임워크를 기반으로 하며 3D 확률 지형은 three.js로 렌더링합니다. 컴파일 시 모든 웹 정적 자원이 단일 바이너리 파일 내부에 그대로 패키징됩니다.

`chmod +x`로 실행 권한을 부여한 뒤 터미널에서 바로 실행하면 콘솔에는 `listening on :8642`라는 한 줄만 출력되고 조용히 대기합니다.

브라우저에서 `http://localhost:8642`에 접속하면 UI가 즉시 화면에 뜹니다. pip install도, npm run dev도, 상용 API 키 설정 절차도 필요 없습니다. 처음 실행했을 때 습관처럼 README를 뒤적이며 환경변수 설정 항목을 찾았으나 그런 설정은 처음부터 존재하지 않았습니다.

```bash
# 실행 파일에 권한 부여
chmod +x ./inside-llm

# 로컬 엔진을 구동하고 8642 포트에서 대기
./inside-llm --port 8642
```

데이터 통신은 가벼운 바이너리 프레임을 기반으로 하며 WebSocket을 통해 브라우저와 하부 C++ 엔진 사이를 고속으로 오갑니다.

공식 릴리스에서는 Linux와 Windows 환경을 위해 CUDA 및 Vulkan 버전의 사전 컴파일 바이너리를 제공합니다. CUDA 개발 키트가 설치되지 않은 사무용 PC라도 그래픽 드라이버만 정상이면 압축을 풀고 즉시 실행할 수 있습니다.

## 2. 듀얼 스트림 나란히 비교: Q2_K와 Q8_0이 갈라서는 첫 순간 포착

웹 화면에 진입하면 핵심 작업은 Model A와 Model B를 지정하는 것입니다.

여기에는 엄격한 물리적 제약이 따릅니다. 두 모델은 반드시 동일한 토크나이저 어휘집을 공유해야 합니다. 이번 실측에서는 동일 패밀리의 두 모델 가중치를 준비했습니다:
- Model A: `Qwen2.5-7B-Instruct-Q2_K.gguf`, 파일 크기 2.78 GiB
- Model B: `Qwen2.5-7B-Instruct-Q8_0.gguf`, 파일 크기 7.70 GiB

적재 소요 시간의 경우 mmap을 통해 VRAM에 매핑되며 Model A는 1.2초, Model B는 4.1초 만에 로드가 끝났습니다. 첫 토큰 응답 지연은 310밀리초였으며 락스텝 듀얼 추론 처리량은 초당 28.4토큰으로 안정적이었습니다.

동작 모드는 두 가지로 나뉩니다:
- 락스텝 모드 Lockstep: 동일한 프롬프트 문맥을 두 모델에 강제로 주입하여 현재 후보 단어의 확률 분포를 나란히 비교합니다.
- 자유 모드 Free: 각 모델이 직접 샘플링한 토큰에 따라 추론을 이어 나가며 두 텍스트 출력이 완전히 갈라질 때까지 관찰합니다.

복잡한 동시성 카운터 로직 추론 과제로 테스트를 진행했습니다. 처음 30자까지는 두 모델의 생성이 완벽하게 일치했으나 31번째 토큰 위치에 도달하자 결정적인 분기가 일어났습니다.

어디에서 어긋난 것일까요?

확률 막대그래프를 열어보는 순간 원인은 명확해졌습니다.

Q8_0 쪽에서는 후보 단어 `eight`가 0.87이라는 압도적인 확률을 차지하며 경쟁 후보들을 바닥에 눌러앉혔습니다.

반면 Q2_K로 전환하자 `eight`는 0.31로 곤두박질치고 `six`가 0.29까지 치고 올라왔습니다. 원래라면 0.01 이하에 머물러야 할 노이즈 후보들이 0.05 언저리까지 비정상적으로 부상한 것입니다.

확률이 사라진 것이 아닙니다. 양자화 노이즈에 의해 확률 피크가 깎여 평탄화된 것입니다. 분포가 평평해지면 샘플러의 미세한 흔들림만으로도 엉뚱한 갈래를 선택하게 됩니다.

UI의 Stream 패널에는 분기가 발생한 지점에 눈에 띄는 마젠타색 마커가 표시됩니다. 후보 패널을 클릭하면 좌우 대칭 막대그래프가 나타나고 우측에는 섀넌 엔트로피와 양방향 쿨백 라이블러 발산 KL Divergence가 계산됩니다. Q8_0을 기준 분포 P로 두고 압축된 Q2_K를 근사 분포 Q로 설정했을 때, 31번째 직전까지 KL 값은 0.04 안팎을 유지하다가 분기점에서 1.82로 급격히 치솟았습니다. 정밀도 손실이 추상적인 느낌이 아니라 시계열 위의 명확한 좌표로 포착되는 순간입니다.

## 3. 샘플러 파이프라인 추적: Top-k, Top-p, Min-p는 무엇을 잘라내는가

평소 ollama나 llama-server에서 샘플링 옵션을 설정할 때 많은 엔지니어가 감에 의존합니다. 온도는 0.7로 둘 것인가 0.8로 둘 것인가? Top-p를 0.9로 주면 유효한 후보까지 잘려 나가지 않는가? 최근 주목받는 Min-p는 기존 방식과 무엇이 다른가?

블랙박스 밖에서 추측만 하던 답답함을 inside-llm은 투명하게 열어 보여줍니다. Gates 패널은 llama.cpp 내부의 샘플러 파이프라인을 그대로 재현하여, 원시 로짓 벡터가 나온 후 반복 페널티, Top-k, Top-p, Min-p, 온도 스케일링, GBNF 문법 제약을 순서대로 거치게 합니다. 각 단계 상단에는 생존한 후보 단어 수가 명시됩니다.

```bash
# 특정 모델 쌍과 컨텍스트 길이를 지정하여 구동
./inside-llm \
  --model-a ./models/Qwen2.5-7B-Instruct-Q2_K.gguf \
  --model-b ./models/Qwen2.5-7B-Instruct-Q8_0.gguf \
  --ctx 4096
```

마우스로 필터링 단계를 클릭하면 컷오프 전후의 분포 비교 차트가 즉시 렌더링됩니다. 실제 동작을 관찰해 보니 놀라웠습니다.

Top-p 0.9는 여유로운 설정 같지만, 최상위 단어의 확신도가 92%에 이르는 상황에서는 Top-p가 첫 단계에서 수천 개의 유효 대안을 모조리 잘라냅니다. 반대로 분포가 평평할 때는 의미가 모호한 주변부 단어를 수십 개씩 통과시킵니다.

반면 Min-p를 0.05로 두면 최상위 단어의 확신도에 맞춰 임계값이 연동됩니다. 최상위가 0.92일 때 절대 컷오프 기준은 0.046으로 자동 상향되어, Q2_K에서 비정상적으로 부상했던 0.01~0.03 구간의 꼬리 노이즈를 깔끔하게 차단합니다. 파라미터 문서를 읽는 것보다 시각적 피드백이 훨씬 직접적인 이해를 돕습니다.

## 4. Logit Lens 은닉층 투영: 모델은 어느 계층에서 결정을 내리는가

최종 출력만 보는 기능에 그친다면 단순한 디버깅 도구에 불과했을 것입니다. `--lens` 옵션을 주고 실행하면 Logit Lens 기반의 전 계층 은닉 상태 투영 기능이 작동합니다.

Qwen2.5-7B 아키텍처는 28개의 트랜스포머 블록으로 이루어져 있습니다. 모델은 마지막 층에서 갑자기 정답을 떠올리는 것일까요, 아니면 중간 계층에서 이미 후보를 낙점해 두고 있는 것일까요?

Logit Lens를 켜면 하단에 2차원 계층별 타임스텝 투영 맵이 펼쳐지며 3D 입체 확률 지형으로도 전환할 수 있습니다. 가로축은 토큰 생성 진행 단계이며 세로축은 신경망의 물리적 깊이를 나타냅니다.

알고리즘 시간복잡도 증명 문제로 테스트해 보았습니다. 프롬프트를 주입한 직후 초기 5개 층까지는 고엔트로피 노이즈 후보만 가득합니다.

정답은 어느 계층에서 굳어지는 것일까요?

14층 부근에 도달하자 핵심 알고리즘 이름의 확률이 서서히 응집되기 시작했습니다. 21층에 이르자 앞쪽에 아직 7개 층이 더 남아 있음에도 정답 확률은 이미 82%를 돌파했으며, 나머지 계층은 문맥 연결어와 문장 다듬기 작업만 수행하고 있었습니다.

반면 양자화 손실이 심한 Q2_K 모델에서는 이러한 확률 응집이 25층까지 지연되었고, 도중에 미세한 어텐션 흔들림만으로도 다른 후보로 쉽게 끌려갔습니다.

또한 타임라인 위의 임의의 분기 노드를 직접 클릭할 수도 있습니다. 메모리 내 스냅샷 기능을 통해 분기가 일어나기 직전으로 되감아 다른 후보 단어로부터 추론을 다시 이어 나갈 수 있습니다. 간헐적인 환각 원인을 짚어낼 때 매우 유용한 실험대 역할을 합니다.

## 5. 실전 배포 시 기술적 한계와 저사양 주의점

매우 훌륭한 도구이지만 실전에서 운용할 때 몇 가지 물리적 한계를 유념해야 합니다.

첫 번째는 VRAM 용량의 벽입니다. 8GB 그래픽카드에서 7B 모델 두 개를 동시에 올리려 해서는 안 됩니다. 파라미터 조정 없이 처음 구동했을 때 두 모델의 합산 크기가 10GB를 넘어서며 `CUDA error: out of memory`가 발생했고 `ggml_cuda_compute_forward` 메모리 할당 단계에서 즉시 멈췄습니다.

8GB 카드로 듀얼 모델 구동이 가능할까요?

`-ngl 18`로 GPU 오프로드 계층을 줄이면 실행 자체는 되지만, 계산 계층 일부가 시스템 메모리로 밀려나면서 생성 속도가 초당 28토큰에서 3.8토큰으로 급락했습니다. 코드 한 번 비교하는 데 40분이나 걸렸습니다.

대화형 분석 작업에서 이런 지연을 견딜 엔지니어는 없습니다. 8GB 환경이라면 3B급 모델 두 개를 나란히 비교하는 구성을 권장합니다.

두 번째는 토크나이저 일치 여부입니다. 두 모델은 반드시 동일 계열이어야 합니다. Llama-3와 Qwen2.5를 나란히 비교하면 토크나이저 인코딩 규칙이 달라 토큰 ID 매핑이 불가능하므로 통계적 발산도를 계산하는 것이 무의미합니다.

마지막으로 현재는 텍스트 단일 모달만 지원합니다. 멀티모달 모델 가중치 파일 자체는 로드할 수 있으나 웹 화면에서는 텍스트 생성 경로만 캡처하며 시각 어텐션 투영 기능은 아직 지원되지 않습니다.

새로운 양자화 파일을 내려받을 때마다 inside-llm으로 먼저 돌려보는 습관이 생겼습니다. 동일 프롬프트를 넣고 두 버전이 몇 번째 토큰에서 갈라서는지 관찰합니다. 분기가 일찍 일어난다면 해당 작업은 정밀도에 민감하므로 Q5_K_M이나 Q8_0을 채택하고, 수백 토큰 이후까지 분기가 지연된다면 Q2_K로 타협하여 절약한 VRAM으로 컨텍스트 길이를 두 배 늘리는 판단을 내릴 수 있습니다.

모든 문제를 해결해 주는 마법은 아닙니다. 어휘집이 다르면 동작하지 않고 멀티모달도 아직 볼 수 없습니다. 개발자의 이슈 목록을 보면 시각 투영 기능도 작업 중이라고 합니다. 현재 텍스트 분석 도구로서는 충분히 실전성을 갖추고 있습니다.

바탕화면 렌더링 부담을 제하고 나면 여러분의 그래픽카드에 실제로 가용한 VRAM 여유가 얼마나 남아 있습니까? 무턱대고 가중치를 내려받기 전 nvidia-smi로 가용 공간부터 계산해 보시기 바랍니다.
