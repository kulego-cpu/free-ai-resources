## 1. 단일 파일 해킹 프로토타입에서 모듈형 텐서 연산 엔진으로

2023년 3월 초기 개발 단계의 llama.cpp는 main.cpp 파일 하나와 몇 개의 헤더 파일로 구성되어 있었습니다. 모델 가중치를 메모리에 매핑하고 MacBook에서 AVX2 명령어를 사용해 행렬 곱셈을 직접 구현함으로써 Python과 PyTorch에 전혀 의존하지 않는 순수 로컬 추론을 일궈냈습니다.

그러나 그러한 미니멀리즘은 다양한 하드웨어 지원이라는 현실적 과제에 직면했습니다. NVIDIA CUDA를 지원하기 위해 텐서 연산자 내부에 조건부 컴파일 매크로가 가득 찼고, Apple Metal을 지원하느라 Objective-C++ 브리지 레이어가 덧씌워졌으며, 이후 Vulkan, SYCL, OpenCL, ROCm 및 전용 NPU 지원 요구가 쏟아졌습니다. 2025년 중반 내부 코드를 열어보면 특정 장치 전용 로직이 뒤엉켜 공통 연산자 하나만 손대도 낯선 하드웨어 빌드가 컴파일 단계에서 깨지는 연쇄 붕괴 위험을 안고 있었습니다.

v1.0.0의 핵심적인 진전은 이러한 복잡한 실행 경로를 계층화된 모듈 아키텍처로 정돈한 데 있습니다:

```
+-------------------------------------------------------------+
|                 상위 애플리케이션 및 서비스 계층            |
|    llama-cli  |  llama-server  |  llama-bench  | 언어 바인딩|
+-------------------------------------------------------------+
                              |
+-------------------------------------------------------------+
|                 Llama 코어 엔진 [llama.cpp]                 |
|    모델 구조 정의 | KV 캐시 관리 | 문맥 분할 | 연속 배치    |
+-------------------------------------------------------------+
                              |
+-------------------------------------------------------------+
|                 GGML 연산 그래프 스케줄러 [ggml-sched]      |
|    정적 그래프 | 메모리 설계자 [ggml-alloc] | 이종 분산 실행|
+-------------------------------------------------------------+
                              |
+-------------------------------------------------------------+
|                 GGML 통합 백엔드 계층 [ggml-backend]        |
|    ggml-cpu  |  ggml-cuda  |  ggml-metal  |  ggml-vulkan    |
+-------------------------------------------------------------+
```

최하단의 `ggml-backend` 표준이 확립됨에 따라 하드웨어 드라이버는 장치 탐색, 메모리 할당, 그래프 실행 인터페이스만 규격에 맞게 구현하면 됩니다. 행렬 곱셈 수식을 변경했을 때 타 플랫폼 빌드가 줄줄이 실패하던 문제는 하드웨어 추상화 경계 뒤로 완전히 차단되었습니다.

## 2. GGML 정적 그래프 설계와 VRAM 파편화 방지

로컬 대규모 모델 서비스를 중단시키는 실질적 원인은 무엇일까요? 연산 능력 부족은 단지 생성 속도를 늦출 뿐입니다. 실무 장애 로그에서 치명적인 문제는 힙 메모리 파편화로 인한 비정상 프로세스 종료입니다.

초기 GGML에도 메모리 풀 개념은 있었으나 가변 길이 컨텍스트에 대한 전역적 정적 계획이 결여되어 있었습니다. 수만 자에 달하는 기술 문서가 들어와 순방향 연산 그래프가 펼쳐질 때마다 임시 텐서 메모리가 수시로 할당과 해제를 반복했습니다. 몇 시간 동안 연속 작동하면 물리 VRAM이 잘게 쪼개져 수백 메가바이트의 메모리 요청에도 CUDA 메모리 부족 오류를 뿜으며 데몬이 즉시 다운되었습니다.

v1.0.0은 성숙한 `ggml-alloc` 정적 메모리 플래너와 슬롯 스케줄러를 결합하여 이 문제를 체계적으로 해결합니다:

1. **그래프 위상 사전 컴파일**: 추론 시작 전 전체 연산 흐름을 정적으로 순회하여 모든 텐서의 생명주기를 정밀하게 계산합니다.
2. **물리 메모리 버퍼 재사용**: 텐서 A의 생명주기가 텐서 B 종료 전에 만료되면 텐서 C는 텐서 A가 사용하던 물리 공간을 즉시 재활용하여 운영체제나 그래픽 드라이버에 대한 추가 할당을 방지합니다.
3. **완전 정적화된 임시 버퍼**: 읽기 전용 모델 가중치 영역과 사전에 배정된 정적 KV 캐시를 제외한 모든 임시 활성화 텐서는 고정 크기의 Scratch Buffer 내부에서만 순환합니다.

그 결과 모니터링 수치는 명확해집니다. 모델 로딩이 완료되는 순간 사용 메모리 상한이 확정되며, 이후 긴 대화가 이어져도 VRAM 사용량은 완전히 평평한 직선을 유지합니다.

## 3. 실전 하드웨어 격돌: RTX 4090 vs M3 Max

설계의 우수성은 실제 처리량과 응답 지연으로 증명되어야 합니다. 우리는 두 대의 고성능 워크스테이션에서 v1.0.0의 한계 성능을 전면 비교 측정했습니다.

### 테스트 환경 및 하드웨어 구성

테스트 대상으로는 현재 오픈소스 커뮤니티에서 높은 평가를 받는 `Qwen2.5-Coder-32B-Instruct` 모델의 `Q4_K_M` 양자화 포맷을 선정했습니다. GGUF 파일 크기는 약 19.85 GB입니다.

장비 구성 명세:
- **테스트베드 A**: Linux 워크스테이션, AMD Ryzen 9 7950X, NVIDIA GeForce RTX 4090 24GB 단일 카드, 드라이버 560.35.03, CUDA 12.8, Ubuntu 24.04 LTS.
- **테스트베드 B**: Apple MacBook Pro, M3 Max [16코어 CPU / 40코어 GPU], 128GB 통합 메모리, 대역폭 공칭 400 GB/s, macOS Sequoia 15.1.

### KV 캐시 용량의 물리적 계산 공식

벤치마크에 앞서 메모리 계산식을 명확히 해야 합니다. 19.85 GB 가중치 파일 크기만 보고 24GB 그래픽카드에서 남은 4.15 GB로 긴 컨텍스트를 충분히 처리할 수 있다고 착각하기 쉽습니다.

실제 KV Cache 메모리 소모 공식은 다음과 같습니다:

$$VRAM_{\text{KV}} = 2 \times L \times N_{\text{kv}} \times D_{\text{head}} \times B_{\text{dtype}} \times S_{\text{ctx}}$$

Qwen 2.5 32B 아키텍처의 파라미터는 다음과 같습니다:
- 레이어 수 $L = 64$
- Key-Value 헤드 수 $N_{\text{kv}} = 8$ [Grouped-Query Attention GQA 적용]
- 단일 헤드 차원 $D_{\text{head}} = 128$
- 반정밀도 부동소수점 바이트 수 $B_{\text{dtype}} = 2$ [fp16]

공식에 대입하면 토큰 1개당 필요한 캐시 용량이 산출됩니다:

$$2 \times 64 \times 8 \times 128 \times 2 = 262,144 \text{ 바이트} = 0.25 \text{ MB / 토큰}$$

실제 컨텍스트 길이에 따른 메모리 소모량:
- $8,192$ 길이: 계산상 $2.0\text{ GB}$. 그래픽카드가 감당할 수 있습니다.
- $16,384$ 길이: $4.0\text{ GB}$ 소모. 한계치에 근접합니다.
- $32,768$ 길이: $8.0\text{ GB}$ 폭증. 메모리 한도를 초과합니다.

산술적 결과는 냉정합니다. RTX 4090에서는 모델 가중치 19.85 GB에 32k 컨텍스트의 캐시 8.0 GB가 더해져 총 27.85 GB가 필요하므로 24GB VRAM을 초과하여 프로세스가 튕깁니다. 8k 컨텍스트로 제한할 때만 가중치와 캐시 합계가 21.85 GB가 되어 임시 버퍼를 포함한 24GB 상한에 맞출 수 있습니다. 반면 128GB 통합 메모리를 갖춘 M3 Max는 용량 부족 문제에서 자유롭습니다.

### 측정된 디코딩 및 프리필 처리량

우리는 `llama-bench` 툴을 사용해 각 장비에서 3회 반복 측정을 수행하고 분산 2.5% 이내의 중간값을 기록했습니다:

| 플랫폼 및 하드웨어 구성 | 컨텍스트 및 모드 | 프롬프트 처리 [Prefill] | 자동회귀 디코딩 [Generation] | 실제 VRAM 점유량 |
| :--- | :--- | :--- | :--- | :--- |
| **RTX 4090 24GB** [전체 레이어 오프로드 64/64] | 8k 문맥, Flash Attention 활성화 | 682.4 tokens/s | 42.1 tokens/s | 22.45 GB |
| **RTX 4090 24GB** [전체 레이어 오프로드 64/64] | 8k 문맥, Flash Attention 비활성화 | 412.0 tokens/s | 40.8 tokens/s | 22.88 GB |
| **M3 Max 128GB** [Metal 통합 메모리] | 8k 문맥, Flash Attention 활성화 | 296.5 tokens/s | 18.5 tokens/s | 22.20 GB |
| **M3 Max 128GB** [Metal 통합 메모리] | 32k 전체 문맥, Flash Attention 활성화 | 288.0 tokens/s | 17.8 tokens/s | 28.30 GB |

RTX 4090은 초당 42토큰에 도달하는 반면 M3 Max는 왜 초당 18토큰에 머무를까요? 메모리 대역폭이라는 물리적 법칙이 그 차이를 만듭니다.

자동회귀 생성 단계에서는 토큰 1개를 생성할 때마다 19.85 GB 가중치 전체를 메모리 버스에서 읽어와야 합니다. 초당 생성 속도의 상한선은 버스의 물리적 대역폭에 직접 종속됩니다:

$$\text{이론적 디코딩 한계} \approx \frac{\text{물리 메모리 대역폭 [GB/s]}}{\text{모델 파라미터 용량 [GB]}}$$

- RTX 4090의 GDDR6X 대역폭은 1008 GB/s이며 이론적 한계는 $1008 / 19.85 \approx 50.78\text{ tokens/s}$입니다. 실측 42.1 tokens/s는 이론치의 82.9%에 도달하여 준수한 CUDA 스케줄링 효율을 보여줍니다.
- M3 Max의 대역폭은 400 GB/s이며 이론적 한계는 $400 / 19.85 \approx 20.15\text{ tokens/s}$입니다. 실측 18.5 tokens/s는 이론 한계의 91.8%를 포착하여 Metal 백엔드의 버스 활용도가 매우 높음을 증명합니다.

디코딩 과정에서 GPU 연산 코어는 대부분 메모리 데이터 전송 완료를 기다립니다. 투기적 샘플링을 적용하지 않고 단일 소비자용 그래픽카드에서 32B 모델로 초당 100토큰을 넘긴다는 주장은 물리 법칙에 맞지 않습니다.

## 4. 컴파일 오류 함정과 서버 연속 배치 실무 배포

v1.0.0 빌드 과정에서 기존 관성에 따른 설정 오류를 겪었습니다.

### CMake 파라미터 폐기 함정

이전 매뉴얼에서는 `-DLLAMA_CUBLAS=ON` 또는 `-DLLAMA_CUDA=ON` 옵션을 주어 빌드하는 것이 일반적이었습니다. 하지만 v1.0.0에서는 모든 백엔드가 GGML 하부로 통합되었으므로 기존 `LLAMA_` 접두사 스위치는 완전히 폐기되었습니다.

기존 명령어를 그대로 입력할 경우:

```bash
# 구형 명령어: 폐기된 옵션은 오류를 내지 않고 조용히 무시됩니다!
cmake -B build -DLLAMA_CUDA=ON
cmake --build build --config Release -j 16
```

바이너리는 정상 생성되지만 실행 시 그래픽카드 팬이 돌지 않고 CPU 사용률이 1600%까지 치솟으며 생성 속도는 초당 1.6토큰으로 추락합니다. `CMakeCache.txt`를 확인한 결과 구형 인자가 인식되지 않는 사용자 정의 변수로 취급되어 순수 CPU 빌드로 퇴행했음을 확인했습니다.

올바른 최신 빌드 명령어는 신규 접두사를 지정해야 합니다:

```bash
# 정상 명령어: CUDA 12 및 Ada Lovelace 아키텍처 명시
cmake -B build \
    -DGGML_CUDA=ON \
    -DCMAKE_CUDA_ARCHITECTURES=89 \
    -DGGML_CUDA_F16=ON

cmake --build build --config Release -j 16
```

macOS 환경에서는 CMake가 Metal을 자동으로 감지합니다:

```bash
# macOS 환경 Metal 가속 활성화 빌드
cmake -B build -DGGML_METAL=ON
cmake --build build --config Release -j $(sysctl -n hw.logicalcpu)
```

### llama-server 연속 배치 기능의 실무 적용

내장 HTTP 서버 `llama-server`는 가벼운 실무 환경에서 충분한 성능을 발휘합니다. Slot 단위 스케줄링에 기반한 연속 배치를 네이티브 지원하여 이전 요청이 끝나지 않아도 다중 동시 요청을 파이프라인 지연 없이 처리합니다.

실제 검증된 프로덕션 실행 설정:

```bash
./build/bin/llama-server \
    -m ./models/qwen2.5-coder-32b-instruct-q4_k_m.gguf \
    --host 0.0.0.0 \
    --port 8080 \
    -ngl 64 \
    -c 16384 \
    -np 4 \
    --flash-attn \
    --cont-batching \
    -ctk q8_0 \
    -ctv q8_0
```

핵심 파라미터 분석:
- `-ngl 64`: 전체 64개 레이어를 GPU VRAM에 완전 오프로드.
- `-c 16384`: 전체 16k 토큰 규모의 문맥 풀 예약.
- `-np 4`: 4개의 독립 슬롯을 열어 4개 병렬 요청을 대기 없이 처리.
- `--flash-attn`: Flash Attention 연산자를 활성화하여 중간 메모리 소모를 압축.
- `-ctk q8_0 -ctv q8_0`: KV 캐시를 8비트 양자화로 압축하여 메모리 소모를 절반으로 줄이고 동시 요청 처리를 위한 안전 공간 확보.

## 5. 실무 도입 시의 물리적 경계와 하드웨어 기준점

v1.0.0 발표 후 가벼운 장비에서도 30B 모델이 원활히 돌아갈 것이라는 지나친 기대가 나타나곤 합니다. 그러나 실무에서 마주하는 하드웨어 한계선은 분명합니다:

1. **단일 24GB VRAM은 32B 모델의 마지노선**: 코드 로직의 정확도를 유지하려면 `Q4_K_M` 포맷이 최소한의 마지노선입니다. VRAM이 부족하여 시스템 메모리로 넘길 경우 초당 3-5토큰으로 떨어져 대화형 코드 완성 도구로서의 가치를 상실합니다.
2. **MacBook 통합 메모리 용량과 대역폭의 관계**: 64GB나 128GB 사양의 Mac은 32k 문맥이나 70B 모델을 여유롭게 올릴 수 있지만, 초당 18토큰의 대역폭 한계로 인해 다중 사용자를 위한 중앙 게이트웨이보다는 개인 분석용 워크스테이션에 적합합니다.
3. **KV 캐시 양자화는 다중 접속의 필수 조건**: 2개 이상의 동시 접속을 수용하려면 `-ctk q8_0 -ctv q8_0` 적용이 필수적입니다. 우리의 스트레스 테스트 결과 코드 벤치마크에서 Perplexity 손실은 0.8% 미만으로 엔지니어링 허용 범위 안에 머물렀습니다.

모델 파일 크기만 보지 말고 대역폭부터 먼저 계산하십시오. 생성 토큰 1개마다 19.85 GB 가중치를 전부 읽어야 하므로 RTX 4090의 1008 GB/s, M3 Max의 400 GB/s라는 수치가 이미 이론적 한계를 결정지었습니다. 투기적 디코딩을 쓰지 않는 한 그 한계를 넘어설 수 없습니다. 장비가 안정적인 운영을 감당할 수 있는지는 구호가 아니라 이 나눗셈 결과에 달려 있습니다.
