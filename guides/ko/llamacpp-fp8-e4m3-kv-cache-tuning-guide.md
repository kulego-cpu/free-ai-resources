# 8GB VRAM으로 32k 문맥 OOM 없이 완주하기: llama.cpp 네이티브 FP8 KV 캐시 실전 튜닝 가이드

새벽 2시 17분, 터미널이 갑자기 다운되었습니다.

일반적인 오류 메시지도 없이 창 전체가 암전되었고, 커서가 사라질 틈조차 없었습니다.

2초 동안 멍하니 있다가 황급히 `nvidia-smi`를 확인했습니다.

프로세스는 이미 사라졌고, VRAM 사용량 그래프는 수직으로 바닥을 향해 떨어져 있었습니다.

당시 실행 중이던 모델은 Qwen2.5-7B-Instruct, Q4_K_M 양자화, 모델 가중치 4.65GB였습니다.

장착된 그래픽카드는 데스크톱용 RTX 4060, VRAM은 정확히 8GB입니다.

2만 토큰 정도의 아키텍처 문서는 무난히 처리할 수 있을 것으로 생각했습니다.

그 생각은 너무나 단순한 착각이었습니다.

로컬 대형 언어 모델을 구동할 때, 많은 이들이 가중치가 4-bit인지 8-bit인지에만 집중합니다.

모델이 VRAM에 올라가기만 하면 모든 준비가 끝났다고 믿기 쉽습니다.

하지만 장문 문서 분석이나 다중 턴 검색을 실행하는 순간, 가중치보다 더 많은 메모리를 집어삼키는 진짜 암살자가 정체를 드러냅니다.

그것이 바로 키-값 캐시--KV Cache입니다.

다행히 llama.cpp 메인 브랜치에 네이티브 FP8 E4M3 캐시 기능이 공식 병합되었습니다.

이 기능이 과연 8GB 그래픽카드를 장문 OOM의 벼랑 끝에서 구해낼 수 있을까요?

빌드부터 구동 인자, 샘플링 온도 튜닝까지 하루 종일 수십 차례의 벤치마크를 수행했습니다.

물리 VRAM 계산서, 실제 크래시 로그, 트러블슈팅 과정을 모두 공개합니다.

## 1. 물리 VRAM 계산서: 2만 토큰이 8GB 메모리를 어떻게 폭파시키는가

장문 처리 도중 OOM을 마주하면 다들 의아해합니다.

겨우 1-2만 단어를 넣었을 뿐인데, 왜 수 기가바이트의 메모리가 갑자기 증발하는 것일까요?

이것은 직접 손으로 계산해 보아야 합니다.

모델이 자기회귀 추론을 수행할 때, 이전의 모든 토큰에 대한 키 벡터와 값 벡터는 VRAM에 상주해야 합니다.

만약 저장해 두지 않는다면 어떻게 될까요?

새로운 토큰을 하나 생성할 때마다 이전의 모든 텍스트에 대해 어텐션을 처음부터 다시 계산해야 합니다.

이러한 중복 계산을 방지하기 위해 메모리에 보관하는 행렬이 바로 KV Cache입니다.

Qwen2.5-7B의 아키텍처 설정을 확인해 보겠습니다.

총 레이어 수: 28개 층;

어텐션 구조: GQA 적용, KV 헤드 수는 4개;

각 헤드의 은닉 차원: 128.

기본 설정 상태의 llama.cpp는 캐시를 표준 FP16 정밀도로 저장하므로 값 하나당 2바이트를 소모합니다.

단 하나의 토큰이 28개 층 전체를 통과할 때 확보되는 메모리를 계산해 봅니다:

$$2 \times 28 \text{ 층} \times 4 \text{ 헤드} \times 128 \text{ 차원} \times 2 \text{ 바이트} = 57,344 \text{ 바이트}$$

즉, 단 하나의 토큰이 들어오는 순간 약 56 KB의 VRAM이 고정 할당됩니다.

수천 토큰 수준의 일상 대화에서는 문제가 되지 않습니다.

하지만 문맥 길이가 32,768 토큰에 달하면 어떻게 될까요?

$$32,768 \times 57,344 \text{ 바이트} = 1,879,048,192 \text{ 바이트} \approx 1,792 \text{ MiB} \approx 1.88 \text{ GB}$$

모델 가중치가 4.65GB, 캐시가 1.88GB로 합산 6.53GB입니다.

RTX 4060의 물리 VRAM은 8,192 MB입니다.

이론상 1.6GB의 여유가 남아 있어야 하는데, 왜 2만 토큰을 넘기자마자 뻗어버렸을까요?

실제 런타임 메모리 소비는 서류상의 수학보다 훨씬 가혹합니다.

첫 번째 요인, 드라이버 기본 점유--CUDA 컨텍스트를 초기화하는 것만으로 500MB에서 700MB가 사라집니다.

두 번째 요인, 스크래치 버퍼--행렬 곱셈의 중간 텐서를 임시 전개하기 위한 고속 메모리가 필수적입니다.

세 번째 요인, 블록 사전 할당--메모리 단편화를 방지하고 연속 처리 속도를 유지하기 위해 할당자가 물리 페이지를 미리 큼직하게 묶어 둡니다.

이러한 운영 메모리가 1.88GB의 순수 캐시 위에 얹히는 순간, 피크 메모리는 8.4GB를 가볍게 돌파합니다.

8GB라는 물리적 한계에 부딪힌 드라이버는 프로세스를 OOM으로 강제 종료하는 것 외에 다른 방법이 없습니다.

<img src="https://img.freeaidog.com/images/blog/llamacpp-fp8-e4m3-kv-cache-tuning-guide.webp" alt="RTX 4060 8GB VRAM 배분 비교: 32k 문맥에서 네이티브 FP8 E4M3와 표준 FP16의 동작 차이" />

이 지점에서 FP8 E4M3 형식의 결정적인 가치가 드러납니다.

FP8은 수치 하나당 정확히 1바이트만 소비합니다.

FP16과 비교하여 순수 데이터 볼륨을 절반으로 압축합니다.

원래 1,792 MiB를 요구하던 32k 캐시가 약 896 MiB 수준으로 줄어듭니다.

절약된 약 900 MiB의 공간이 드라이버 오버헤드와 스크래치 버퍼 스파이크를 완충해 주는 방파제가 됩니다.

## 2. 트러블슈팅: 인자만 바꾸고 융합 커널을 켜지 않았을 때 발생하는 4배 속도 폭락

먼저 테스트 환경과 빌드 버전을 명시합니다:

```text
llama.cpp b4821 [git rev-parse HEAD 확인]
CUDA 12.6 / 드라이버 560.35.03 / Ubuntu 24.04 LTS
```

리눅스 환경에서 CMake 빌드 시 주의할 점이 있습니다.

기본 생성기는 Makefile 또는 Ninja이며, 단일 구성 모드로 작동합니다. `cmake --build build --config Release`를 실행하면 `--config` 옵션은 완전히 무시됩니다.

구성 단계에서 빌드 타입을 지정해야 합니다:

```bash
# 올바른 CMake 빌드 명령어
cmake -B build -DGGML_CUDA=ON -DCMAKE_BUILD_TYPE=Release
cmake --build build -j$(nproc)
```

빌드가 정상 완료되었습니다.

커뮤니티 가이드에 맞춰 캐시 타입을 지정하고 서버를 올렸습니다:

```bash
# 처음에 시도했던 잘못된 구동 명령어
./build/bin/llama-server \
  -m models/qwen2.5-7b-instruct-q4_k_m.gguf \
  -c 32768 \
  -ctk f8_e4m3 \
  -ctv f8_e4m3 \
  -ngl 99 \
  --port 8080
```

서버가 구동되었고 초기 메모리 점유도 줄어들었습니다.

구동 로그에서 다음 줄을 반드시 확인해야 합니다:

```text
llama_kv_cache_init:      CUDA0 KV buffer size =   960.00 MiB (f8_e4m3)
```

**만약 1836 MiB 이상의 수치가 찍힌다면, 옵션이 적용되지 않고 여전히 FP16으로 돌고 있는 것입니다.** 이 단계를 확인하지 않고 넘어가면 이후의 모든 벤치마크는 허상이 됩니다.

2만 토큰 분량의 문서를 투입했습니다.

그런데 진행률 표시줄이 멈춰 섰습니다.

평소 20초 안팎이면 끝나던 프롬프트 처리가 1분이 지나도 겨우 20%를 넘겼습니다.

왜 이렇게 느린 것일까요?

다른 터미널에서 `nvidia-smi dmon`을 확인했습니다.

GPU 코어 사용률이 20%에서 95% 사이를 요동쳤고, 메모리 대역폭은 거의 사용되지 않았습니다.

측정된 프롬프트 처리 속도는 58 token/s로 곤두박질쳤습니다.

처리 속도가 4분의 1로 폭락한 것입니다.

메모리를 아꼈다고 한들 4배의 지연 시간을 감수해야 한다면 실무에서 쓸 수 없습니다.

상세 로그를 활성화하고 다시 실행했습니다:

```text
ggml_cuda_flash_attn: flash attention disabled or unsupported for current tensor types, falling back to legacy batched gemm...
ggml_cuda_op_mul_mat: non-aligned memory striding detected, dequantizing fp8 on the fly to fp16 registers
```

원인은 명확했습니다.

FlashAttention을 켜지 않아 전용 융합 커널이 동작하지 않았던 것입니다.

GPU는 연산 직전에 VRAM에 있는 FP8 데이터를 그 자리에서 FP16 레지스터로 역양자화한 뒤 레거시 연산을 수행하고 있었습니다.

Tensor Core의 하드웨어 가속은커녕, 빈번한 데이터 변환과 메모리 정렬 불일치로 연산 장치가 마비된 상태였습니다.

FlashAttention 연계는 필수입니다.

수정된 구동 명령어입니다:

```bash
# 검증된 정상 구동 명령어
./build/bin/llama-server \
  -m models/qwen2.5-7b-instruct-q4_k_m.gguf \
  -c 32768 \
  -ctk f8_e4m3 \
  -ctv f8_e4m3 \
  --flash-attn \
  -ngl 99 \
  --parallel 1 \
  --port 8080
```

로그가 정상적인 상태를 출력합니다:

```text
llama_new_context_with_model: n_ctx = 32768, n_batch = 2048, n_ubatch = 512, flash_attn = 1
llama_kv_cache_init:      CUDA0 KV buffer size =   960.00 MiB (f8_e4m3)
```

문서를 다시 입력했습니다.

2만 토큰 프롬프트 처리는 약 82초 만에 완료되었고, 평균 처리 속도는 243.9 token/s로 안정화되었습니다.

피크 VRAM은 7.11GB에서 멈췄습니다.

8GB 물리 한계 대비 약 900MB의 안전 마진이 확보되었습니다.

## 3. 정밀도 분석: JSON 키의 따옴표 유실과 진짜 범인

메모리가 안정되고 속도가 회복되었습니다. 이것으로 완벽할까요?

그렇지 않았습니다.

그날 오후, 법률 계약서에서 구조화 데이터를 추출하는 업무를 검증했습니다.

수천 토큰의 짧은 문서에서는 완벽한 JSON을 출력했습니다.

하지만 대화가 15회차를 넘어가고 문맥이 28,000 토큰을 돌파하는 순간 출력이 흔들리기 시작했습니다:

```json
{
  "service_level_agreement": {
    "uptime_guarantee": 99.9,
    latency_threshold_ms: 250,
    "penalty_clause: "applicable within 30 days"
  }
}
```

`latency_threshold_ms` 키의 시작 따옴표가 빠져 있고, `penalty_clause`에서는 닫는 따옴표가 증발했습니다.

검증 스크립트가 즉시 에러를 내며 멈췄습니다.

FP8 양자화가 정밀도를 깨뜨린 것일까요?

엄격한 대조 실험을 진행했습니다.

동일한 28k 문맥에 대해 캐시를 `-ctk f16`으로 되돌리고 온도 0.8로 10회 실행했습니다. 그 결과 3회 따옴표 유실이 발생했습니다.

`f8_e4m3`로 교체하고 동일하게 온도 0.8로 10회 실행했을 때, 2회에서 3회 유실이 발생했습니다.

양쪽의 실패율은 거의 같았습니다.

이것이 의미하는 바는 무엇일까요?

**진짜 변수는 샘플링 온도였습니다.**

28,000 토큰 규모의 문맥 후반부는 확률 분포가 자연스럽게 불안정해지는 구간입니다. 온도 0.8을 그대로 두면 낮은 확률의 구두점 탈락을 허용하게 됩니다.

FP8 E4M3는 지수부 4비트, 가수부 3비트로 구성되어 표현 가능한 최댓값이 448로 제한됩니다.

장거리 누적에 따른 미세한 반올림 오차는 확률 분포를 살짝 흔드는 증폭기였을 뿐, 근본적인 원인이 아니었습니다.

API 요청 인자를 수정했습니다:

```bash
# 온도를 낮춘 고정밀 추출 요청 예시
curl http://127.0.0.1:8080/v1/chat/completions \
  -H "Content-Type: application/json" \
  -d '{
    "model": "qwen2.5-7b-instruct",
    "messages": [
      {"role": "system", "content": "당신은 엄격한 데이터 추출 엔진입니다. 반드시 유효한 JSON 형식만 출력하십시오."},
      {"role": "user", "content": "다음 문서에서 기술 규격 목록을 추출하십시오:\n\n[본문 생략...]"}
    ],
    "temperature": 0.15,
    "top_p": 0.95
  }'
```

온도를 0.15로 고정하고 `top_p`를 0.95로 맞췄습니다.

이후 28k 규모 추출을 20회 연속 실행했지만, 따옴표 유실은 0회였습니다.

문법 오류가 완전히 사라졌습니다.

| **표준 FP16 ［기본값］** | 8.42 GB 초과 | -- | -- | ❌ **OOM 크래시** | 24,500 토큰 부근에서 메모리 고갈로 강제 종료 |
| **양자화 Q8_0** | 7.65 GB | 186.2 token/s | 36.8 token/s | ⚠️ **턱걸이 통과** | 동일 1바이트지만 FA 융합 부재로 임시 작업 버퍼 큼 |
| **네이티브 FP8 E4M3 + FA** | 7.11 GB | 243.9 token/s | 40.3 token/s | ✅ **완벽한 안정 통과** | 여유 공간 약 900MB 확보, 하드웨어 텐서 가속 |

Q8_0과 FP8이 모두 1바이트 데이터임에도 VRAM 피크에 0.54GB의 차이가 발생하는 이유는 무엇일까요?

그 차이는 전적으로 FlashAttention에 있습니다.

네이티브 FP8과 FlashAttention의 결합은 중간 어텐션 행렬의 메모리 전개를 생략하지만, 레거시 Q8_0은 여전히 큰 스크래치 버퍼를 필요로 합니다.

결론은 분명합니다.

8GB 그래픽카드에서 기존 FP16으로 32k 문맥을 처리하는 것은 불가능합니다.

Q8_0은 통과는 하지만 메모리 여유가 없어 백그라운드 프로세스로 인해 언제든 튕길 수 있습니다.

FP8 E4M3와 FlashAttention의 조합만이 가성비 그래픽카드에서 안정성을 보장합니다.

## 5. 실전 권장 사항 및 하드웨어 경계선

하루 동안의 실측을 통해 정리된 지침은 세 가지입니다:

**구형 아키텍처에서는 무리하게 켜지 말 것.**

FP8 E4M3의 제 성능은 Ada Lovelace SM 8.9 이상 하드웨어에서만 발휘됩니다.

RTX 3060이나 3070 같은 Ampere 아키텍처는 하드웨어 수준에서 FP8 텐서 명령을 지원하지 않습니다.

구형 카드에서 억지로 켜면 역양자화 오버헤드로 인해 오히려 속도가 떨어집니다. 이 경우 Q8_0을 사용하는 것이 맞습니다.

**FlashAttention은 반드시 묶어서 실행할 것.**

`-ctk f8_e4m3`를 넣고 `--flash-attn`을 빠뜨리면 속도는 58 token/s 수준으로 추락합니다. 두 옵션은 한 세트로 다루어야 합니다.

**장문 추출에서는 온도를 0.2 이하로 낮출 것.**

초장문 문맥 후반부의 반올림 오차는 결정론적 샘플링으로 억제해야 합니다. 정확도가 중요한 작업에서는 온도를 낮추십시오.

마지막으로 한 가지 덧붙입니다:

본문의 벤치마크 수치는 데스크톱용 RTX 4060에서 측정한 결과입니다.

노트북용 모바일 그래픽이나 외장 eGPU 독은 전력 제한과 쿨링 환경이 다르므로 측정값에 차이가 나는 것은 자연스러운 현상입니다. 절대적인 수치가 아닌 아키텍처 가이드로 참고하시기 바랍니다.

여러분의 8GB 그래픽카드는 오늘 32k 문맥을 맞이할 준비가 되셨습니까?
