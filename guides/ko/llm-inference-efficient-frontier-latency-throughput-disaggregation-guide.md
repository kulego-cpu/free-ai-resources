지난겨울 저는 2노드 8장의 RTX 4090 카드로 구성된 추론 클러스터 운영을 넘겨받았습니다.

Grafana 모니터링 대시보드의 곡선은 믿을 수 없을 만큼 매끄러웠습니다: VRAM 점유율 70%, GPU 사용률은 상시 90% 안팎을 유지했습니다.

당시 저는 8장의 GPU를 남김없이 쥐어짜고 있다며 꽤나 뿌듯해했습니다.

프론트엔드 연동 팀 개발자들이 메신저에서 저를 마구 호출하기 전까지는 말입니다.

커서가 세 번째 줄에서 완전히 멈춰 서서 움직이지 않습니다. 이것이 첫 번째 제보였습니다.

저는 당연히 WebSocket 연결이 끊긴 줄 알고 HAR 네트워크 패킷을 떠서 보내달라고 했습니다.

하지만 패킷 로그상 세션은 아주 정상적으로 연결되어 있었고, 패킷 손실률도 0%였습니다. 단지 서버에서 첫 번째 토큰이 끝내 떨어지지 않고 있었을 뿐입니다.

프론트엔드 동료 한 명이 스톱워치로 시간을 쟀는데, 엔터를 누르고 화면에 첫 글자가 뜰 때까지 걸린 시간이 탕비실에 가서 믹스커피 한 잔을 타 오기에 충분했다고 합니다.

IDC 스위치 장비가 고장 났을까요? 저는 이틀 내내 사내망 회선을 의심했습니다.

패킷 덤프, NIC 설정 점검, 광 트랜시버 모듈 교체…… 전부 헛수고였습니다.

사흘째 되던 날 밤에야 진짜 병목이 어디서 엉켰는지 마침내 실체를 파악했습니다.

## 대시보드가 보여준 신기루: 평균 480ms 뒤에 숨어 2초로 치솟은 p99

하드웨어의 진짜 한계를 확인하기 위해 저는 Locust를 사용해 부하 테스트를 작성했습니다.

허세를 뺀 순수 실전 세팅이었습니다.

64개의 비동기 코루틴을 띄우고 HumanEval 앞단 코드 조각을 동시 주입하며, 출력 상한을 512 토큰으로 묶어 10분간 지속 실행해 정상 상태 수치를 수집했습니다.

시작 파라미터에서 동시 처리 상한을 한계치까지 끌어올렸습니다:

```bash
# 최대 동시 배치 설정으로 vLLM 구동
vllm serve Qwen/Qwen2.5-Coder-32B-Instruct \
  --tensor-parallel-size 4 \
  --max-num-seqs 128 \
  --max-model-len 16384 \
  --gpu-memory-utilization 0.92
```

표면적인 수치는 극도로 매혹적이었습니다: `max_num_seqs`를 4에서 128로 올리자 클러스터 전체 처리량이 초당 320 토큰에서 1280 토큰 이상으로 치솟았습니다.

정확히 4배 증가였습니다. 이걸 보고 최적화 성공이라고 생각하지 않을 사람이 어디 있겠습니까?

전체 지표만 봐서는 아무런 결점도 찾을 수 없었습니다.

하지만 제가 간과한 치명적인 사실이 있었습니다: 화면에 그려지던 곡선은 첫 글자 생성 지연 시간 [TTFT]의 산술 평균이었다는 점입니다.

평균치는 480ms로 너무나 온화해 보였습니다.

그러나 Prometheus에서 백분위수 분포를 꺼내 든 순간 등골이 오싹해졌습니다: p90은 1.2초로 치솟았고, p99는 무려 1.95초를 뚫고 올라갔습니다.

컨테이너 표준 출력 로그를 열어보니 터미널 화면이 동일한 노란색 경고로 도배되고 있었습니다:

```text
WARNING [vllm.core.scheduler] Sequence group 1422 is preempted by PreemptionMode.RECOMPUTE.
```

경고 메시지가 쉴 새 없이 밀려들었습니다.

24GB 용량의 RTX 4090 4장, 노드 1대의 총 물리 VRAM은 96GB입니다.

32B 규격의 bfloat16 순정 모델을 올리면 순수 가중치만으로 대략 64GB를 차지합니다.

KV 캐시에 할당 가능한 여유 공간은 아무리 긁어모아도 24GB 안팎이며, 문맥으로 따지면 8만에서 9만 토큰 분량밖에 담지 못합니다.

동시 접속이 128개로 늘어나면 각 세션의 평균 문맥이 600에서 700 토큰을 넘어서는 순간 메모리 풀이 완전히 바닥납니다.

캐시 풀이 텅 비어버렸습니다.

vLLM 스케줄러는 프로세스가 CUDA OOM으로 튕기는 것을 막기 위해 어쩔 수 없이 재연산 선점 로직을 발동합니다.

뒤쪽 세션의 캐시를 강제로 비워버리고, 앞선 요청이 끝나면 처음부터 Prefill을 다시 계산하는 방식입니다.

2초 동안 멍하니 기다리던 프론트엔드 동료들은 바로 자기 세션이 메모리에서 강제로 쫓겨난 그 재수 없는 타이밍에 걸렸던 것입니다.

이런 버벅거림을 참아낼 개발자가 세상에 어디 있겠습니까?

그날 밤 저는 롤링 업데이트로 `max_num_seqs`를 24로 되돌렸고, 부하 테스트를 다시 돌리자 p99는 340ms로 안정되었습니다.

메신저에서 불만 섞인 호출은 완전히 사라졌습니다.

128 동시 접속 상태에서 캐시 강제 반환 없이 처리량을 지키는 설정값은 현재 장비에서는 끝내 찾지 못했습니다. 언젠가 더 큰 메모리 장비가 들어오면 다시 검증하기로 하고 일단 기록해 둡니다.

## 4090에는 NVLink가 없다: PCIe 토폴로지 아래 All-Reduce 통신의 덫

병렬화 전략을 손볼 때도 저는 안이한 착각에 빠져 있었습니다.

한 장으로 느리다면 여러 장에 연산을 나누어 처리하면 당연히 빨라져야 하는 것 아닌가?

텐서 병렬 [TP]이 지연 시간을 극단적으로 줄여준다는 글은 넘쳐나며, 수백 기가바이트 대역폭의 NVLink 연결을 전제로 든 설명도 많습니다.

하지만 소비자용 그래픽 카드에는 그런 전제가 성립하지 않습니다.

Ada Lovelace 아키텍처부터 엔비디아는 40 시리즈 게이밍 카드에서 물리 NVLink 브릿지 단자를 완전히 제거했습니다.

이 세대 소비자용 카드에는 금손가락이 없습니다.

테스트 머신에서 토폴로지 확인 명령어를 실행해 봅니다:

```bash
nvidia-smi topo -m
```

출력된 매트릭스는 온통 `SYS`로 도배되어 있었습니다.

카드 간 통신이 고속 P2P 직결로 흐르지 못하고, CPU 루트 컴플렉스와 메인보드의 PCIe 4.0 x16 슬롯, 그리고 시스템 메모리를 거쳐 우회해야 한다는 뜻입니다.

양방향 이론 대역폭 상한은 겨우 64GB/s에 불과합니다.

더 치명적인 것은 리눅스 순정 드라이버 환경에서 하드웨어 P2P가 비활성화되어 있어, 카드 간 통신이 기본적으로 호스트 시스템 메모리로 튕겨 나간다는 점이었습니다.

당시 저는 32B 모델의 응답 속도를 높이겠다며 단일 노드 4장의 카드에 억지로 TP=4를 적용했습니다.

그 결과 실측된 토큰 간 생성 지연 시간 [ITL]은 기존 22ms에서 58ms로 오히려 악화되었습니다.

연산 코어가 4배로 늘었는데 글자 출력이 2배 이상 느려졌습니다. 저는 몹시 당황했습니다.

Nsight Systems로 순방향 연산 커널 궤적을 캡처해 보니 진상이 낱낱이 드러났습니다.

트랜스포머의 매 어텐션 블록과 피드포워드 계층 연산이 끝날 때마다 4개의 GPU 프로세스 사이에서 `all_reduce` 집합 통신 동기화가 발생합니다.

계산 자체는 1.2ms 만에 끝났는데, PCIe 버스에서 데이터를 맞추느라 무려 3.8ms를 허비하고 있었습니다.

GPU 코어들은 버스 전송이 끝나기만을 멍하니 기다리고 있었습니다. 좁은 버스에 과밀 통신을 쏟아부었으니 막히지 않을 재간이 있겠습니까?

고속 패브릭이 없는 소비자용 하드웨어에서 높은 TP 배수를 거는 것은, 골목길에 대형 덤프트럭 행렬을 밀어 넣는 꼴입니다.

이후 저는 아키텍처를 2장씩 묶어 TP=2로 나누고, 두 그룹 사이는 HTTP 요청 단위 데이터 병렬로 분산시켰습니다. 1글자당 생성 시간은 즉시 26ms로 복구되었습니다.

4090을 만지는 엔지니어라면 슈퍼컴퓨터용 튜닝 지침을 맹신하지 말고, 메인보드 슬롯의 물리 대역폭부터 차분히 계산해 보아야 합니다.

## 양자화의 절벽: 인덴트 붕괴로 인한 HumanEval 28점 폭락

VRAM이 부족할 때 가장 먼저 손이 가는 해결책은 양자화입니다.

많은 글들이 양자화를 손실 없는 마법처럼 포장합니다: VRAM은 반으로 줄고, 속도는 2배로 뛰며, 벤치마크 점수 하락은 소수점 단위에 불과하다고 말입니다.

그런 달콤한 말을 순진하게 믿어도 될까요?

엄격한 코드 엔지니어링 현장에서는 전혀 다른 현실이 기다리고 있습니다.

동일한 검증 환경에서 Qwen2.5-Coder-32B를 3가지 양자화 규격으로 HumanEval pass@1 벤치마크를 돌려보았습니다:

```text
HumanEval 50문제 자동 코드 생성 벤치마크 [commit: 4e7b8a1]
- FP16 순정 기준치: 82.0%
- FP8 동적 양자화: 80.4% [단 1.6% 미세 하락]
- 표준 INT4 규격: 54.2% [27.8% 처참한 폭락]
```

FP16에서 FP8로의 전환은 정적 가중치든 `--kv-cache-dtype fp8`을 통한 캐시 압축이든 믿기 힘들 만큼 안정적이었습니다.

VRAM 점유율이 절반으로 줄었습니다.

KV 캐시 수용 공간은 2배로 늘었습니다.

메모리 대역폭 숨통이 트이자 토큰 출력 속도는 80% 가까이 상승했습니다.

그러나 FP8 방어선을 넘어 일반 INT4 가중치로 들어서는 순간, 코드 추론 로직은 절벽 아래로 곤두박질칩니다.

54.2%의 통과율은 2문제 중 1문제가 무조건 틀린다는 의미입니다.

절약한 6GB 메모리가 과연 이 파멸과 맞바꿀 가치가 있었을까요?

저는 실패한 20개의 케이스를 하나하나 diff를 떠서 분석했습니다.

무려 17개의 실패 케이스가 깊은 들여쓰기 정렬 실패로 사망했습니다.

파이썬 코드에서 루프나 조건문이 3단계를 넘어가면, INT4 버전 모델은 스페이스 4칸을 6칸으로 찍거나 다중 try-except 블록 스코프를 제멋대로 조기 종료해 버렸습니다.

나머지 3개 에러는 따옴표가 포함된 복잡한 f-string 안에서 터졌으며, 모델은 같은 코드 라인을 끝없이 반복 재생하는 루프에 빠졌습니다.

이런 코드는 CI 파이프라인의 flake8 정적 검사조차 통과하지 못합니다. 단위 테스트를 돌려볼 수준도 못 됩니다.

겨우 6GB의 VRAM을 아낀 대가로 코딩 어시스턴트 기능 전체를 쓰레기통에 처박은 셈이었습니다.

사내 문서 요약이나 벡터 검색 리랭킹이 목적이라면 INT4로 비용을 아끼는 편이 합리적입니다.

하지만 실시간 코딩 어시스턴트 환경에서 FP8은 물러설 수 없는 절대 마지노선입니다.

NVFP4나 MXFP4처럼 블록 단위 독립 스케일링을 갖춘 차세대 포맷으로 증류 재학습되지 않은 일반 INT4 모델로 긴 코드를 다루는 것은 재앙을 자초하는 일입니다.

## Prefill과 Decode 물리 분리: 긴 프롬프트와 고주파 생성이 공존할 수 없는 이유

단일 노드 안에서 파라미터를 맞추는 작업이 두더지잡기 같다면, 최근 업계에서 밀고 있는 P/D 분리는 과연 무엇을 해결해 줄까요?

물리적 본질은 매우 명쾌합니다: 특성이 완전히 다른 계산 단계를 물리적으로 다른 서버로 격리하는 것입니다.

Prefill 단계는 행렬 곱 연산 밀도에 좌우되는 계산 바운드이며, 요구되는 것은 GPU의 Tensor Core 연산 능력 TFLOPS입니다. 수천 자의 문맥이 한꺼번에 밀려들어 연산 코어를 꽉 채웁니다.

Decode 단계는 고주파 메모리 읽기에 좌우되는 대역폭 바운드이며, 요구되는 것은 초당 몇 기가바이트의 데이터를 퍼 올릴 수 있는가입니다. 1글자를 뱉을 때마다 전체 가중치와 누적된 KV 캐시를 메모리에서 통째로 긁어 읽어야 합니다.

이 상반된 두 작업을 같은 카드에 몰아넣는 것이 바로 커서 멈춤 현상의 근본 원인입니다.

한 사용자를 위해 초당 50 토큰으로 순조롭게 함수 코드를 생성하던 중, 다른 사용자가 2만 줄짜리 OpenAPI 문서를 던져 넣었다고 상상해 보십시오.

스케줄러는 거대한 어텐션 투영 행렬을 계산하기 위해 생성용 연산 코어를 즉시 넘겨주어야 합니다.

출력 중이던 디코드 작업은 강제로 일시 정지됩니다.

화면을 바라보던 엔지니어의 눈에는 커서가 1.5초 동안 얼어붙는 현상으로 나타납니다.

커서가 굳어버린 화면을 보며 작업을 이어갈 엔지니어가 어디 있겠습니까?

P/D 분리는 클러스터를 2개의 이기종 노드 군으로 완전히 쪼갭니다:

```text
클라이언트 요청
    │
    ▼
[API 로드밸런서 게이트웨이]
    │
    ├─► [Prefill 전담 클러스터]: 밀집 부동소수점 연산 카드로 긴 프롬프트 행렬을 단숨에 소화
    │         │
    │         ▼ [RDMA / 초고속 내부망으로 KV Cache 상태 직송]
    └─► [Decode 전담 클러스터]: H100 등 초고대역폭 메모리 장비 [3.35TB/s]로 토큰 출력에 전념
```

Prefill이 끝나면 KV 캐시 패킷이 고속 내부망을 타고 Decode 클러스터로 곧바로 전달되며, Decode 노드는 어떠한 방해도 받지 않고 일정한 박자로 글자를 찍어냅니다.

복잡한 다단계 에이전트 환경에서 이 분리 아키텍처는 p99 지연 시간 출렁임을 60% 이상 깎아냅니다.

물론 대가도 확실합니다: 노드 간 KV 캐시 전송을 제어할 미들웨어를 운영해야 하며, 트래픽 쏠림에 대비해 장비 풀을 최소 20% 이상 넉넉히 확보해야 합니다.

대형 클라우드가 사랑하는 구조이지만, 충분한 트래픽 규모가 전제되어야 합니다.

장비 서너 대로 꾸려가는 작은 팀이라면 분산 KV 전송의 늪에 뛰어들기보다 chunked prefill로 입력 스파이크를 눌러 담는 편이 훨씬 실용적입니다.

## 투기적 디코딩의 현실: 코드 생성에서의 채택률과 온도 감쇠

마지막으로 추론 효율의 물리적 천장을 진정으로 확장할 수 있는 기술을 짚어봅니다: 바로 투기적 디코딩입니다.

일상적인 대화 시나리오에서 투기적 디코딩을 시험해 보았다가 실망하고 꺼버린 엔지니어가 부지기수입니다.

자유 입력은 발산하기 쉬워서 작은 초안 모델이 내놓은 예측 채택률이 30% 안팎에서 맴돕니다.

틀릴 때마다 주력 모델의 검증과 롤백이 발생해 시간을 아끼기는커녕 헛수고 연산만 늘어납니다.

이건 오히려 손해가 아닐까요?

하지만 엄격한 규칙 아래 돌아가는 코드 생성 환경에서는 데이터의 규칙성이 완전히 달라집니다.

코드에는 확고한 템플릿이 있습니다: 클래스 선언, 표준 라이브러리 임포트, 괄호 닫기, 일정한 인덴트.

동일 계열의 경량 모델 Qwen2.5-Coder-0.5B를 초안 헤드로 삼아 32B 주력 모델과 연동해 실측한 결과입니다:

단어 토크나이저의 물리적 정렬이 완벽해야 하며, 어휘 사전이 조금이라도 틀어지면 초안 예측은 전멸합니다.

샘플링 온도를 0.2로 묶어둔 저랜덤성 환경에서 평균 채택 길이는 3.8에서 4.1 토큰에 달했습니다.

주력 모델이 4번 순차 실행해야 했을 순방향 계산을 검증 단계의 단 1회 배치 계산으로 일괄 통과시킬 수 있다는 뜻입니다.

메모리 데이터 전송 3회분을 통째로 건너뛰어 얻는 이득은 고스란히 물리적 하드웨어 여유 공간으로 환원됩니다.

하지만 샴페인을 너무 일찍 터뜨려서는 안 됩니다.

투기적 디코딩에는 온도 상승에 따른 극도로 가파른 감쇠 곡선이 도사리고 있습니다:

온도가 0.2일 때는 채택률이 70% 안팎을 유지하며 체감 속도가 2배 가까이 빨라집니다;

그러나 개발자가 창의적인 코드를 짜게 하겠다고 온도를 0.7로 올리는 순간, 채택 길이는 순식간에 1.6 토큰으로 추락합니다.

더 골치 아픈 문제는 검증 시점의 일시적인 메모리 팽창입니다.

검증 단계에서 주력 모델은 초안이 던진 K개의 후보 분기를 병렬 처리해야 하므로, 검증 배치 크기가 순간적으로 K배 폭증합니다.

이 급격한 부하는 간신히 버티고 있던 여유 VRAM 풀을 단숨에 낭떠러지로 몰아넣습니다.

기본 KV 캐시 점유율이 이미 90% 임계치에 도달해 있다면, 투기적 디코딩을 켜는 것은 성능 향상은커녕 조기 재연산 선점이나 OOM 튕김 현상을 앞당길 뿐입니다.

고온 세팅에서는 초안 헤드를 꺼두는 편이 훨씬 깔끔하지 않을까요?

현재 저희 클러스터에서는 2개의 작업 노드가 돌고 있습니다.

`max_num_seqs`는 24로 고정했고; 가중치 FP8 양자화를 적용했으며; 동적 FP8 KV 캐시도 유지하고 있지만; 투기적 디코딩은 잠시 꺼두었습니다. 신규 엔드포인트의 온도가 프론트엔드 단에서 0.75로 세팅되어 있어 켜두어 봐야 메모리만 축내기 때문입니다.

요청의 샘플링 온도에 따라 초안 헤드를 동적으로 껐다 켜는 지능형 프록시를 어떻게 구현할지 최적의 아키텍처는 아직 고민 중입니다.

사내 코드 어시스턴트 클러스터를 운영 중인 분이라면 지난주 p99 모니터링부터 열어보십시오. 모니터 앞에 앉은 엔지니어들이 도대체 무엇을 기다리며 시간을 태우고 있는지 바로 확인하실 수 있을 것입니다.
