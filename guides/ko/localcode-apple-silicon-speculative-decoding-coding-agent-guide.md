개발자를 로컬 오프라인 환경으로 이끄는 계기는 기술적 결벽증이 아닙니다. 이전에 두 차례 고객사에서 보내온 저장소에 엄격한 역외 반출 금지 조항이 붙어 있었고 사내 보안 규정을 검토한 끝에 결국 사내망의 낡고 느린 서버로 버텨야 했습니다. 정규식 세 개를 고치는 데 오후 반나절을 고스란히 날린 경험이 있습니다.

따라서 LocalCode 가 GitHub 에 등장했을 때 곧바로 내려받아 실행해 보았습니다. 확인하고 싶었던 것은 단 하나였습니다. 16GB 메모리를 탑재한 일반 M3 노트북으로 네트워크가 차단되고 테더링조차 쓸 수 없는 환경에서 일상적인 코딩 업무를 어디까지 마칠 수 있는지 알고 싶었습니다.

로컬 환경에서 코딩 에이전트를 자율 구동하려면 두 가지 고질적인 난관을 넘어야 했습니다. 첫째는 추론 속도입니다. 일반 양자화 모델은 초당 10여 개 토큰을 출력하는 데 그쳐 깜빡이는 커서를 기다리느라 맥이 끊깁니다. 둘째는 긴 컨텍스트로 인한 메모리 부족입니다. 여러 소스 파일을 조금만 길게 입력해도 가용 메모리가 즉시 바닥납니다.

LocalCode 는 Apple Silicon 통합 메모리 구조에 초점을 맞추어 최적화를 구현했습니다. 사전 컴파일된 Metal GPU 커널을 탑재하고 공식 경량 Drafter 모델을 연계해 투기적 샘플링을 진행하며 기존 코드 수정을 가속하는 Copy Drafting 기능을 지원합니다.

단일 명령어로 원활히 구동되며 외부 인터넷 없이 실무를 어디까지 감당할 수 있을까요. 16GB 사양 장비에서 하루 종일 성능을 직접 측정했습니다.

## 하드웨어 제원과 메모리 점유 실측

테스트 환경은 16GB 통합 메모리가 탑재된 M3 MacBook Pro 기본 모델이며 운영체제는 macOS 15 환경입니다.

Astral 의 uv 패키지 매니저를 활용하면 설치는 단 한 줄로 끝납니다:

```bash
uv pip install localcode
```

설치는 빠르지만 프롬프트를 작성하기 전에 메모리 점유율을 먼저 파악해야 합니다.

실행 전 `vm_stat` 로 기준선을 확인해 보니 여유 페이지에서 환산한 실제 가용 메모리는 약 4.2 GB 였습니다. 즉 모델 가중치와 추론 프레임워크에 할당 가능한 물리적 여유 공간은 12 GB 미만입니다.

테스트 모델로는 Qwen2.5-Coder-14B-Instruct-Q4_K_M 을 채택했고 투기적 레이어에는 공식 1.5B Drafter 가중치를 연결했습니다. 설정을 적극적으로 끌어올려 `-ngl 99` 로 모든 레이어를 GPU 로 오프로드하고 컨텍스트 길이 `--ctx-size` 는 8192 로 지정했으며 KV Cache 는 통합 메모리 보호를 위해 기본 fp16 대신 q8 로 낮추었습니다.

실행 후 활성 상태 보기를 확인하자 유선 메모리 영역이 순식간에 11.2 GB 까지 올라갔습니다:

```text
Qwen2.5-Coder 14B 메인 모델 가중치: 약 7.1 GB
동반 1.5B 공식 Drafter 모델: 약 1.3 GB
8-bit KV Cache 예약 할당: 약 2.2 GB
에이전트 작업 공간 및 컨텍스트 버퍼: 약 0.6 GB
─────────────────────────────────────────────
실행 중 최대 메모리 점유: 약 11.2 GB
```

남은 약 육백 메가바이트의 여유는 실무에서 어떤 의미일까요.

문법을 확인하려 브라우저 탭을 하나 띄우는 순간 메모리 압박 그래프는 녹색에서 노란색으로 바뀌었습니다. 운영체제는 SSD 로 스왑 아웃을 즉시 시작했고 `swapouts` 수치는 초당 수백 페이지 단위로 치솟았습니다. 초당 38 토큰이던 생성 속도는 19 토큰으로 떨어졌고 이어 11 토큰까지 주저앉았습니다.

이는 여유가 있는 상태가 아니라 메모리 한계선 위에서 줄타기를 하는 형국입니다. 백그라운드에서 실행되는 모든 프로세스가 추론 처리량을 직접 잠식합니다.

## 2단계 가속 메커니즘: Drafter 투기 디코딩과 Copy Drafting

이 도구의 기술적 특징은 신규 코드 작성과 기존 파일 수정에서 가속 방식을 나누어 처리한다는 점입니다.

### 1. 공식 Drafter 기반 전방 투기적 샘플링

기존 대형 모델의 일반적인 생성 방식은 엄격한 자기회귀이므로 토큰을 하나 생성할 때마다 전체 행렬 곱셈을 반복해야 하여 연산 부담이 큽니다.

투기적 디코딩의 구조는 명료합니다. 가벼운 1.5B 모델이 앞장서서 3 개에서 5 개 토큰을 미리 추측하고 후방의 14B 메인 모델이 단 한 번의 순전파 연산으로 후보 토큰들의 정합성을 한꺼번에 판별합니다. 일치하는 토큰은 즉시 확정되고 빗나간 부분만 다시 계산합니다.

신규 라우팅 로직을 작성할 때 측정한 수치는 다음과 같습니다:

- 14B 단일 모델 구동 시: 평균 생성 속도 약 21.4 tok/s
- 1.5B Drafter 연계 투기 디코딩 적용 시: 평균 속도 약 38.6 tok/s
- 후보 토큰 채택률: 대체로 58% 에서 64% 사이 유지

생성 처리량이 약 80 퍼센트 향상되었습니다. 통합 메모리 아키텍처 덕분에 PCIe 버스 복사 지연이 없어 모델 간 후보 전달에 추가 손실이 없습니다.

### 2. 코드 리팩터링을 위한 Copy Drafting

신규 코드 생성 속도 개선보다 실무에서 더 유용한 것은 기존 코드 수정 작업입니다.

실제 개발에서 빈 파일에 처음부터 코드를 작성하는 일은 많지 않습니다. 대부분 기존 500 줄 스크립트에서 메서드 두 개를 고치거나 예외 처리를 덧붙이는 작업입니다. 기존 에이전트는 수정되지 않은 수백 줄의 기존 코드도 한 글자씩 다시 출력하므로 대기 시간이 길었습니다.

LocalCode 의 Copy Drafting 은 복잡한 블랙박스가 아닙니다. 실행 구조를 살펴보면 초안 생성 단계에서 로컬 디스크의 원본 파일을 후미 컨텍스트로 주입하고 메모리의 토큰 캐시와 대조하여 고속 검증을 진행합니다:

```text
기존 파일 캐시
    │
    ▼
[병렬 후보 토큰 주입] ───> 변경 없는 원본 코드와 일치
    │                               │
    ▼                               ▼
메인 모델 일괄 검증 ─────> 70+ tok/s 로 고속 스킵
    │
    ▼
로직 변경 지점 도달 ─────> 일반 Drafter 추측으로 전환
```

480 줄 파이썬 스크립트 수정 테스트에서 변경 없는 선언문들이 초당 70 개에서 85 개 토큰 속도로 순식간에 지나갔습니다. 수정 소요 시간은 기존 24 초에서 7 초 미만으로 단축되어 타이핑 흐름이 끊기지 않는 쾌적함을 제공합니다.

## 개발 실무 적용 시 부딪힌 3가지 장애

테스트 환경에서 잘 돌아간다고 해서 장애가 없는 것은 아닙니다. 실제 프로젝트 저장소에서 실행하자 세 가지 구체적인 문제에 부딪혔습니다.

### 장애 1: 초기 구동 시 Metal Shader 컴파일 멈춤 현상

설치 후 구동 명령을 내리자 loading metal kernels 문구가 나온 뒤 터미널 커서가 멈추었습니다.

진행률 표시줄도 없고 냉각팬도 돌지 않았습니다. 프로세스가 멈추었거나 패키지가 잘못 설치된 줄 알았습니다.

몇 초간 기다리다 Ctrl+C 를 두 번 눌러 강제 종료했습니다. 다시 실행해도 같은 줄에서 멈췄습니다. 다른 창에서 `top` 을 띄워 확인해 보니 `localcode-metal-cc` 프로세스가 CPU 단일 코어를 98% 점유하며 셰이더 머신코드 컴파일을 진행하고 있었습니다.

```bash
# 첫 설치 후 사전 웜업 실행 권장
$ time localcode --warmup-only
real    0m23.418s
```

약 23 초 동안 터미널 화면에는 아무런 반응이 없었습니다. 사전 정보가 없으면 멈춤으로 오해하기 쉬운 동작입니다. 컴파일된 Metal 캐시는 `~/Library/Caches/localcode/metal/` 에 저장되므로 두 번째 실행부터는 1.2 초 만에 즉시 켜집니다.

### 장애 2: 모노레포 심층 디렉터리 경로 인식 이탈

단일 폴더 구조에서는 정확했습니다. 하지만 여러 패키지로 구성된 모노레포 환경에 투입하자 문제가 발생했습니다.

요청 작업: `packages/backend/src/utils/formatter.ts` 파일에 대한 단위 테스트 추가.

14B 모델은 올바른 테스트 코드를 작성했으나 파일 저장 도구를 호출할 때 긴 상대 경로를 잘못 계산했습니다. 지정된 `tests` 폴더가 아니라 프로젝트 최상위 루트에 `src_utils_formatter.test.ts` 라는 평면 파일을 생성해 버렸습니다.

소형 오픈 모델은 대형 상용 모델에 비해 도구 호출 매개변수 정밀도에서 여전히 격차가 있습니다. 로직은 맞아도 파일 저장 위치가 빗나갈 수 있으므로 화면 한쪽에 `git status` 를 상시 띄워두고 변경 위치를 점검해야 합니다.

### 장애 3: 32B 모델 구동 시 메모리 스왑 폭풍

호기심에 Qwen2.5-Coder-32B 4비트 양자화 버전을 시도해 보았습니다.

가중치 용량만 19 GB 에 육박하여 KV Cache 를 더하자 16GB 물리 메모리가 즉각 포화되었습니다. macOS 는 시스템 메모리 부족 경고창을 띄웠고 스왑 쓰기로 본체가 뜨거워졌습니다.

생성이 멈추지는 않았으나 속도는 38 토큰에서 2.8 tok/s 로 폭락했습니다. 키보드 입력 반응조차 밀릴 정도로 환경이 느려졌습니다. 16GB 사양 장비에서 14B 모델은 물리적인 한계선입니다.

## 3가지 과제에 대한 실측 벤치마크 결과

동일 장비에서 동일 프로젝트의 세 가지 과제에 대한 측정 데이터를 정리했습니다:
- 과제 1: FastAPI 라우팅 구조 생성
- 과제 2: 480 줄 데이터 정제 스크립트 리팩터링 및 예외 처리 보강
- 과제 3: 수치 계산 모듈에 대한 경계값 단위 테스트 12 개 추가

측정 결과 비교표는 다음과 같습니다:

| 구성 | 평균 처리량 | 첫 토큰 지연 | 리팩터링 소요시간 | 16G 메모리 피크 |
| :--- | :--- | :--- | :--- | :--- |
| 기준 1: 기본 Ollama 14B 단일 구동 | 21.4 tok/s | 1.8 초 | 24.2 초 | 8.3 GB |
| 기준 2: LocalCode 및 1.5B Drafter 연계 | 38.6 tok/s | 2.1 초 | 14.5 초 | 11.2 GB |
| 기준 3: LocalCode 및 Copy Drafting 연계 | 74.2 tok/s | 1.4 초 | 6.8 초 | 11.4 GB |

투기적 샘플링으로 입력 대기 시간이 개선되었으며 Copy Drafting 덕분에 기존 파일 수정 소요 시간은 대폭 단축되었습니다.

## 도입 권장 사항과 실무적 적용 범위

상용 모델을 완전히 대체하는 것은 현시점에서 비현실적입니다.

하지만 현재 운영 방식은 명확합니다. KTX 나 비행기 이동 중, 또는 네트워크 연결이 금지된 고객사 보안 구역에서 진가를 발휘합니다. 단위 테스트 작성, 예외 처리 보강, 단일 함수 수정 같은 작업은 충분히 소화하며 초당 70 토큰 이상의 속도로 대기 시간도 거의 없습니다.

여러 마이크로서비스에 걸친 대규모 아키텍처 개편을 맡기는 것은 피해야 하며 16GB 환경에서 32B 모델을 억지로 구동하는 것도 무리입니다. 주력 도구를 대체하기보다 극단적인 오프라인 환경에서도 코딩을 마칠 수 있는 엔지니어링 안전망으로 활용하는 것이 합리적입니다. 평소에는 체감하기 어려워도 보안 규정에 부딪혔을 때 손에 쥐고 있는 도구가 있다는 사실은 개발 작업에 큰 든든함을 줍니다.
