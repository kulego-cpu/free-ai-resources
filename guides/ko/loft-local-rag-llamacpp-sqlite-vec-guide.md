## 아키텍처 분석: 왜 독립된 두 개의 llama-server 프로세스로 분리해야 하는가

로컬 RAG 파이프라인을 구축할 때 대다수는 단일 인스턴스를 띄워 대화와 임베딩 모델을 하나의 프로세스에 몰아넣는 방식을 먼저 떠올립니다.

그렇게 띄워도 정말 아무 문제 없을까요?

실무 환경에서는 심각한 큐 병목 현상이 발생합니다.

텍스트 임베딩 모델의 풀링 레이어 연산과 대화 모델의 토큰 단위 스트리밍 생성은 하드웨어 스케줄링 특성이 판이하게 다릅니다. 단일 프로세스에서 특징 추출과 텍스트 생성을 동시에 실행하면 내부 연산 스레드 간에 치열한 자원 경합이 일어납니다. 메모리 관리 역시 까다롭습니다: 대화 생성에는 방대한 양의 KV 캐시 슬롯이 필요하지만, 임베딩은 배치 처리량을 선호합니다. 양쪽이 한 프로세스 안에서 충돌하면 둘 다 최대 성능을 내지 못합니다. 꼼짝없이 막히게 됩니다.

Loft는 이 지점에서 매우 깔끔한 아키텍처 격리를 구현했습니다.

Rust 메인 프로그램은 백그라운드에 두 개의 독립된 자식 프로세스를 상주시킵니다:

- 프로세스 1: 대화 생성 전담, 2.2GB의 Qwen 2.5 3B Instruct Q4_K_M 적재.
- 프로세스 2: 특징 추출 전담, 24MB의 bge-small 모델 적재.

이미지 인덱싱을 활성화하면 시스템은 SmolVLM-500M-Instruct를 적재한 임시 비전 프로세스를 띄웁니다. 이미지 분석이 끝나면 즉시 프로세스를 종료하여 운영체제에 메모리를 반환합니다. 지체 없이 깔끔하게 빠집니다.

처음에는 두 프로세스를 따로 띄우면 메모리 소모가 두 배로 늘지 않을까 우려했습니다.

htop을 켜두고 두 시간 동안 모니터링해본 결과, 두 프로세스를 합쳐도 상주 메모리는 3.8GB에 불과했습니다. 이전의 단일 프로세스 혼용 방식보다 오히려 낮았습니다. 유휴 상태의 임베딩 프로세스는 KV 캐시를 잡지 않으므로 RSS가 600MB 초반까지 내려갔습니다. 쓸데없는 걱정이었습니다.

설치 도중 맞닥뜨린 설정 트러블도 있었습니다.

llama-server의 -np 기본값이 4로 잡혀 있었고 임베딩 프로세스의 -b 및 -ub 설정이 조율되지 않아, 처음에 200 청크를 자르자마자 OOM이 발생하며 콘솔에 failed to allocate compute buffer 에러가 쏟아졌습니다.

대화 프로세스의 컨텍스트 길이 -c를 8192에서 4096으로 낮추고, 임베딩 배치 크기를 512로 제한하자 안정적으로 안착했습니다. 공식 문서에는 없는 실전 경험입니다.

## 벡터 스토리지 선택: 무거운 외부 DB 대신 sqlite-vec 단일 파일 적용

로컬 지식 베이스 구축에서 일반 개발자를 가장 지치게 만드는 요인은 온갖 외부 벡터 데이터베이스 설치입니다.

문서 수백 장을 검색하자고 수백 메가바이트 메모리를 잡아먹는 전용 벡터 데몬을 띄우는 것은 낭비입니다. 포트 감시와 네트워크 설정까지 얽히면 시스템의 잠재적 장애 지점만 늘어납니다. 데이터베이스 포트 디버깅으로 휴일을 날리고 싶은 개발자는 없습니다.

Loft는 SQLite의 벡터 확장인 sqlite-vec을 채택했습니다.

디렉터리 메타데이터, 파일 해시값, 텍스트 청크, 고차원 벡터 임베딩이 모두 단 하나의 loft.db 파일에 저장됩니다. 단일 파일 하나로 전부 해결됩니다.

문서 분할에 대해서도 물리적 상한선이 설정되어 있습니다: 파일당 최대 2000 청크 [텍스트 기준 약 3MB]로 엄격히 제한됩니다.

검증을 위해 8000 청크 분량의 대용량 로그 파일로 무제한 분할을 시도해 보았습니다. 임베딩 연산에만 14분이 소요되었고, 기기가 뜨거워져 손을 댈 수 없을 정도였습니다. 검색된 6개 청크 중 5개가 중복된 로그 헤더 조각이었으며, 최종 답변도 완전히 빗나갔습니다. 2000 청크로 제한하자 3분 만에 인덱싱이 끝났고, 상위 6개 청크 중 4개가 실제 규정 조항을 정확하게 가리켰습니다.

2000이라는 수치는 즉흥적으로 정해진 것이 아닙니다. 일반적인 노트북이 버틸 수 있는 실질적 상한선이며, 그 이상 늘려봤자 늘어나는 것은 회수율이 아니라 노이즈뿐입니다:

| 분할 전략 및 규모 | 최초 벡터화 소요 시간 | 상위 6개 검색 지연 | 실제 답변 정확도 |
| :--- | :--- | :--- | :--- |
| **무제한 8000 청크 분할** | 약 14분 | 420ms 내외 | 희소 노이즈 유입, 답변 왜곡 |
| **Loft 2000 청크 제한** | 약 3분 | 28ms | 압축된 문맥, 핵심 조항 적중 |

방대한 로그나 거대한 표 데이터에 대해 무제한 분할을 돌리면 임베딩 연산이 30분 이상 멈출 뿐 아니라, 벡터 검색 공간이 무의미한 조각들로 오염됩니다. 2000 청크 상한선은 노트북 배터리를 보호하면서 프롬프트 문맥의 신호 대 잡음비를 지켜내는 방어선입니다.

## 환각 방지와 후속 질문 재구성: 접지 프롬프트와 엄격한 거절 로직

소형 파라미터 로컬 모델로 RAG를 구동할 때 가장 치명적인 약점은 근거가 부족할 때 엉뚱한 지어내기를 한다는 점입니다.

단순한 오픈소스 프로젝트들은 검색된 청크를 프롬프트에 그대로 욱여넣습니다. 소형 모델은 근거가 희박하면 즉시 거짓 답변을 지어내기 시작합니다. 그런 환각 답변을 믿고 계약서나 영수증 규정을 검토할 수는 없습니다.

어떻게 막아야 할까요? 간단치 않습니다.

Loft의 질의응답 파이프라인은 3단계 방어책을 갖추고 있습니다.

1단계는 유사도 점수 바닥 필터링입니다.

질문이 벡터화되면 sqlite-vec에서 가장 가까운 청크 6개를 추출합니다. 유사도 점수가 최고 매칭 항목보다 크게 떨어지면 해당 조각은 강제로 제외되며, 최대 6KB의 검증된 청크만 문맥 버퍼에 진입할 수 있습니다.

2단계는 접지 시스템 프롬프트 고정입니다.

청크 내용으로 답변을 뒷받침할 수 없을 때, 시스템 프롬프트가 추측 생성을 엄격히 통제합니다. 인덱싱된 문서에서 관련 내용을 찾을 수 없으며, 제공된 문서에 근거해서만 답변할 수 있습니다라는 표준 거절 문구로 안전하게 종결합니다.

3단계는 문맥 기반 후속 질문 재구성입니다.

경비 처리 규정을 물어본 뒤 영수증은 어디로 제출해라고 덧붙여 질문할 경우, 주어가 생략된 짧은 구문 그대로 벡터 검색을 돌리면 일치하는 결과를 거의 찾을 수 없습니다.

주어가 생략된 구문을 만났을 때 시스템은 어떻게 대응해야 할까요?

Loft는 대화 모델을 호출해 짧은 의미 보정을 거쳐 모호한 대명사를 완전한 검색 쿼리로 재작성한 뒤 sqlite-vec 검색을 수행합니다.

그 대가로 후속 질문마다 한 번의 추가 추론 비용이 발생합니다. 3B 모델이 질문을 재작성하는 데 약 400밀리초가 걸리지만, 실제 정산 규정을 확실하게 찾아내는 이점이 있습니다. 최신 환경에서는 충분히 지불할 가치가 있지만, 구형 CPU에서 7B 모델을 돌려 2초가 소요된다면 고민해볼 대목입니다.

답변 하단에는 전용 출처 서랍이 제공되어 클릭 한 번으로 해당 파일과 단락을 확인할 수 있습니다. 문서 열람 시에는 OS 기본 편집기를 호출하지만, 실행 파일이나 스크립트는 파일 탐색기에서 위치만 표시할 뿐 백그라운드에서 임의로 실행하지 않습니다.

## 하드웨어 부하 실측: 슬림형 노트북과 배터리 구동 벤치마크

일반 보급형 기기에서 실제로 쾌적하게 구동될까요? 자원 소모 내역을 점검해 봅니다.

테스트 환경은 외장 그래픽이 없는 일반적인 16GB 통합 메모리 노트북입니다. 모델은 Qwen 2.5 3B와 경량 임베딩 모델의 조합입니다.

콜드 스타트 및 연속 질의응답 시 실측 데이터는 다음과 같습니다:

- 상주 물리 메모리: 대화 프로세스와 임베딩 프로세스를 합쳐 약 3.8GB 점유.
- 텍스트 임베딩 속도: 순수 CPU 연산 기준 초당 약 45개 텍스트 청크 처리.
- 스트리밍 생성 속도: 최초 토큰 지연 시간 약 1.2초, 이후 초당 22에서 28토큰 속도 유지.

인상적인 부분은 전원 상태 감지 로직입니다.

충전기를 분리하여 배터리 전원으로 전환된 것을 감지하면, 내장 상태 머신이 디바운스 지연을 늘리고 동시 실행 스레드 할당을 능동적으로 낮춥니다. 쿨링 패드 없이도 노트북 키보드 상판 온도는 39도 안팎을 안정적으로 유지했습니다. 팬이 굉음을 내며 돌거나 쓰로틀링으로 버벅이는 현상은 없었습니다.

## 물리적 한계와 현실적 제약: 어떤 용도에 적합하지 않은가

장점을 살펴본 만큼 한계점도 명확하게 짚고 넘어가야 합니다.

OCR 기능이 운영체제에 종속되어 있습니다. 스캔 PDF나 이미지 속 문자 인식과 관련하여, Loft는 Windows에 내장된 시스템 OCR 엔진을 직접 호출합니다. macOS나 Linux에서 실행할 경우 이미지 레이어에서 텍스트를 추출할 수 없습니다. 크로스 플랫폼 사용자는 이 간극을 감안해야 합니다.

경량 비전 모델의 인식 정밀도 역시 제한적입니다.

SmolVLM-500M-Instruct를 연동해 이미지 요약을 생성할 수는 있지만, 이 정도 소형 모델은 호수, 산맥, 단순 막대그래프 수준의 거친 윤곽만 구분할 수 있습니다. 복잡한 추세선이 얽힌 재무 차트 이미지를 넣으면 소형 모델 특유의 환각 발생률이 급격히 치솟습니다. 정밀한 전산 데이터 입력 도구로 기대해서는 안 됩니다.
