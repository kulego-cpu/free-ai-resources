며칠 전 Thinking Machines Lab에서 Inkling-2-Mini 가중치를 오픈소스 저장소에 조용히 공개했습니다.

전직 OpenAI 엔지니어링 팀이 주도해 설계한 이 모델은 보기 드문 아키텍처를 취하고 있습니다. 순환형 혼합 전문가라 불리는 Looped MoE 구조를 도입하여 물리적 총 파라미터는 26.4B에 달하지만 토큰당 활성화 파라미터는 3.4B 수준에 머뭅니다. 중간 계층의 신경망이 단일 추론 과정에서 세 번 연속 반복 호출되도록 설계되어 있어, 물리적 메모리 용량을 늘리지 않고도 더 깊은 추론 능력을 이끌어내는 방식입니다.

발상은 훌륭합니다. 그러나 배포된 FP16 원본 가중치를 내려받아 디스크 용량을 확인해 보니 18.89GB에 달했습니다.

8GB VRAM을 장착한 데스크톱 그래픽카드나 8GB 통합 메모리를 탑재한 MacBook Air에서는 베이스 가중치조차 올리지 못하고 실행 단계에서 튕겨 나갑니다.

테스트를 접으려던 찰나 Hacker News 메인에 관련 글이 올라왔습니다. 개발자 ShinMegamiBoson이 LookAtMyQuant 컴파일러 툴체인을 공개하며 Inkling-2-Mini를 단 5.4GB 메모리 환경에 올려 구동하는 실측 결과를 발표한 것입니다. 평균 가중치 비트 폭은 1.63 bpw까지 깎여 있었습니다.

1.63 bpw가 실무에서 어떤 의미를 지닐까요. 일반적인 GGUF 포맷을 IQ2나 IQ1 수준까지 내리면 문맥이 망가지며 횡설수설하기 일쑤입니다. 5.4GB 크기로 정상적인 문장을 생성할 수 있을지, 아니면 단순한 수치상의 보여주기에 불과할지 직접 확인해 보기로 했습니다.

저장소를 로컬에 복제하고 두 대의 실제 물리 하드웨어에서 벤치마크를 진행했습니다.

## 1. 극단적 압축 메커니즘: 표준 양자화가 1.63비트에서 붕괴하는 이유

많은 엔지니어가 의문을 가질 수 있습니다. 평소 사용하는 AWQ나 GPTQ는 4-bit 수준에서 제법 안정적인데, 왜 2-bit 미만으로 내려가면 완전히 붕괴하는 것일까요.

신경망 텐서 내부에서 각 가중치가 지니는 중요도가 극단적으로 불균일하기 때문입니다.

전통적인 균일 양자화는 텐서 전체를 고정된 격자 크기로 잘라내어 반올림합니다. 비트 폭이 넉넉할 때는 잉여 정보가 많아 손실이 두드러지지 않습니다. 그러나 2-bit 밑으로 떨어지는 순간, 어텐션의 방향성을 유지하는 극소수의 핵심 가중치까지 강제로 뭉개지면서 추론 로직이 즉시 무너집니다.

LookAtMyQuant 2는 컴파일러 기반의 새로운 파이프라인을 채택했습니다. 소스코드를 분석해 보면 핵심은 두 가지 기법에 기반합니다. Fisher 정보량에 따른 동적 비트 할당과 트렐리스 상태 그래프 최적화입니다.

### 1.1 Fisher 정보량 민감도 프로파일링

LAMQ는 모든 신경망 레이어가 동등하다는 가정을 거부합니다.

컴파일러는 C4 코퍼스와 오픈소스 코드에서 추출한 소량의 캘리브레이션 텍스트를 흘려보내며 각 가중치 블록에 대한 손실 함수의 2계 도함수, 즉 Fisher 정보 행렬을 연산합니다.

곡률이 가파른 영역은 가중치에 미세한 변화만 생겨도 출력 의미가 요동치는 구간입니다. 반대로 곡률이 평탄한 구간은 큰 폭으로 쳐내더라도 결과에 미치는 영향이 미미합니다.

이 곡률 분포를 바탕으로 LAMQ는 정밀도 예산을 유연하게 배분합니다.

토큰 임베딩 레이어, 출력 프로젝션, 그리고 초기 어텐션 행렬에는 3-bit 또는 4-bit를 배정해 집중 보호합니다.

순환 루프 내부에서 호출 빈도가 낮은 마이크로 FFN 전문가 레이어는 1-bit 또는 1.5-bit까지 과감하게 깎아냅니다.

전체 모델 가중치를 가중평균하면 정확히 1.63 bpw 언저리에 안착합니다.

### 1.2 트렐리스 인코딩과 계층별 증류 복원

비트 폭이 결정되면 단순 근접 반올림 대신 트렐리스 상태 그래프 탐색을 적용합니다.

알고리즘은 동적 계획법을 통해 전체 텐서 차원에서 반올림 오차를 상쇄할 수 있는 최적의 양자화 경로를 찾습니다. 인코딩이 끝나면 원본 고정밀도 출력과의 간극을 메우기 위해 계층별 사후 증류 미세조정을 수행합니다.

종이 위에 수식을 전개할 때는 깔끔해 보였습니다. 그러나 실제 장비에 얹어 돌려보니 가장 먼저 부딪힌 장벽은 메모리 대역폭이었습니다. 비트 연산을 통한 압축 해제 루틴이 돌기 시작하자 지연시간이 층층이 누적되었습니다. 남은 과정은 투박한 삽질의 연속이었습니다.

## 2. 로컬 실행 환경과 Metal 커널 트러블슈팅

이번 실측에는 두 가지 물리 하드웨어를 교차 투입했습니다.

첫 번째 환경은 단일 NVIDIA GeForce RTX 4060 8GB 구성입니다. 드라이버 550.127.05와 CUDA 12.4 환경입니다.

두 번째 환경은 Apple Silicon M3 칩과 16GB 통합 메모리를 갖춘 MacBook으로, macOS 15.1 환경입니다.

### 2.1 빌드 과정의 헤더 누락 예외 처리

LookAtMyQuant는 Apple Silicon 환경을 위해 전용 Metal 압축 해제 커널을 제공합니다. 명령어를 입력해 CLI 패키지를 설치했습니다.

```bash
pip install git+https://github.com/ShinMegamiBoson/lookatmyquant.git
```

미리 컴파일된 양자화 가중치를 내려받고 추론 명령을 호출했습니다.

```bash
lamq generate shinmegamiboson/Inkling-2-Mini-LookAtMyQuant-5.4GB \
  --prompt "Write a quicksort in Python."
```

텐서 샤드가 몇 개 로드되더니 터미널에 컴파일 오류가 발생하며 멈춰 섰습니다.

```text
MetalCompilerError: Compilation failed: unknown type name 'half4x4'
  Device::newLibraryWithSource failed to compile custom kernel: lamq_trellis_unpack.metal
```

압축 해제 셰이더의 JIT 컴파일 단계에서 프로세스가 중단된 상태였습니다.

macOS 15 변경 로그를 추적해 보니 Sequoia 환경에서 Xcode Command Line Tools의 기본 Metal 헤더 경로 구조가 개편되어 있었습니다. 명시적 경로가 지정되지 않으면 내장 행렬 타입을 찾지 못하는 문제였습니다.

해결책은 명료했습니다. 셸 환경변수에 툴체인 경로를 주입해 주었습니다.

```bash
export METAL_XCODE_TOOLCHAIN_PATH="/Applications/Xcode.app/Contents/Developer/Toolchains/XcodeDefault.xctoolchain"
```

실행 명령을 다시 입력했습니다.

터미널에 셰이더 캐시 기록 로그가 정상 출력되며 추론 생성 단계로 매끄럽게 넘어갔습니다.

### 2.2 실제 가동 시의 물리 메모리 점유율

추론 가동 상태에서 측정한 물리 리소스 수치는 다음과 같습니다.

- 베이스 모델 가중치 순수 점유량 5.38GB.
- 4,096 토큰 컨텍스트 환경에서 KV 캐시 할당량 약 1.15GB.
- 런타임 및 프레임워크 오버헤드 약 0.35GB.
- 시스템 전체 피크 메모리 점유율 6.88GB로 유지.

8GB RTX 4060 환경에서 VRAM 부족으로 인한 비정상 종료는 발생하지 않았으며, 16GB Mac에서도 디스크 스왑 현상은 전혀 관측되지 않았습니다.

공언된 5.4GB 체급 안에 물리적으로 들어간다는 점은 입증되었습니다.

## 3. 실측 처리량: 순환 아키텍처가 요구하는 시간 비용

메모리에는 들어갔습니다. 그렇다면 생성 속도는 어떨까요.

5.4GB 크기이니 쾌적하게 날아다닐 것이라 속단하기 쉽습니다. 측정을 마친 후 한동안 말을 잃었습니다. 5.4GB 안에 들어간 것은 맞지만 속도는 결코 가볍지 않았습니다.

프롬프트 길이를 달리하며 5회 반복 측정한 중앙값은 다음과 같습니다.

| 입력 컨텍스트 길이 | Prefill 처리량 | Decode 생성 처리량 | 피크 VRAM 점유량 |
| :--- | :--- | :--- | :--- |
| 512 토큰 | 74.2 tokens/s | 23.8 tokens/s | 6.42GB |
| 2,048 토큰 | 68.5 tokens/s | 22.4 tokens/s | 6.68GB |
| 4,096 토큰 | 59.1 tokens/s | 20.6 tokens/s | 6.88GB |
| 8,192 토큰 | 46.3 tokens/s | 18.2 tokens/s | 7.35GB |

디코딩 속도가 왜 초당 20에서 23토큰 수준에 묶여 있을까요.

순환 MoE 구조가 치러야 하는 필연적인 물리적 대가입니다.

가중치 용량은 5.4GB에 불과하지만, 토큰 하나를 뱉어낼 때마다 중간 핵심 레이어가 세 차례 연속해서 순방향 연산을 수행합니다. 이는 하드웨어 입장에서 70개 레이어가 넘는 거대한 단일 모델을 매 스텝 돌리는 것과 맞먹는 연산량을 의미합니다.

여기에 트렐리스 코드를 셰이더 단에서 비트 연산으로 풀어내는 탈양자화 연산 오버헤드까지 얹어집니다.

돌아가기는 하지만 결코 빠르지 않습니다. 문서 요약이나 코드 초안 작성에는 쓸 만하지만, 극도의 반응성이 필요한 스트리밍 음성 비서 환경에는 적합하지 않습니다.

## 4. 실제 정밀도 한계 측정

그 어떤 기술적 설명도 출력 텍스트의 품질을 보증하지 못하면 의미가 없습니다.

1.63 bpw 가중치의 실전 활용성을 파악하기 위해 난이도가 다른 세 가지 과제를 테스트했습니다.

### 4.1 기본 코드 작성과 로직 설명

타입 힌트가 포함된 비동기 요청 제어 클래스 작성을 지시했습니다.

출력된 코드는 구조적으로 탄탄했습니다. asyncio.Semaphore를 바르게 다루었고, 예외 처리와 단위 테스트 케이스까지 구비되어 문법 오류가 없었습니다. 일반적인 소프트웨어 개발 작업에서는 추론 뼈대가 단단히 버텨줍니다.

### 4.2 엄격한 수치 계산과 기호 추론

과제를 4단계 연속 행렬 연산으로 바꾸고 엄격한 포맷 출력을 요구했습니다.

이 지점에서 1.63 bpw의 한계가 명확하게 드러났습니다.

3단계 수치 전개 과정에서 연산 부호가 뒤집히는 오류가 발생했습니다. 세 차례 재시도한 결과 4-bit 버전에서 96퍼센트에 달하던 규격 일치율이 88퍼센트까지 하락했습니다.

솔직히 말해 정밀한 수치 추론 영역에서 1.63 bpw는 역부족입니다. 계산 깊이가 깊어지면 기호가 흔들리기 시작합니다. 안정적인 정형 데이터 출력을 기대하고 몇 차례 돌리다 보면 금세 밑천이 드러납니다.

## 5. 하드웨어 마지노선과 선택 가이드

테스트를 마치며, 이 구성은 누구에게 유효할까요.

첫째, 8GB 그래픽카드나 8GB 메모리 Mac만 보유하고 있으면서도 로컬에서 26B 체급의 논리 전개를 꼭 경험해 보고 싶은 엔지니어라면 LAMQ 2는 현재 몇 안 되는 실질적인 대안입니다.

정말 돌아가느냐고 묻는다면 분명히 돌아갑니다.

둘째, 16GB나 24GB 이상의 VRAM을 확보하고 있다면 주저 없이 일반적인 4-bit 버전을 사용하는 편이 낫습니다. 메모리가 허용되는 환경에서 굳이 1.63 bpw의 손실을 감수할 까닭이 없습니다.

셋째, 벤치마크 수치에 현혹되지 말아야 합니다. 저장 공간은 아꼈습니다. 그 대가는 무엇일까요. 토큰을 생성할 때마다 중간 계층 연산을 세 번 더 돌려야 합니다. 아낀 공간만큼 시간을 고스란히 더 지불하게 됩니다.

향후 업스트림에 더욱 최적화된 어셈블리 압축 해제 커널이 안착할지는 미지수입니다. 실기기의 물리적 동작과 메모리 셈법을 냉철하게 직시하는 것이 무모한 시도보다 훨씬 값진 결과를 낳습니다.
