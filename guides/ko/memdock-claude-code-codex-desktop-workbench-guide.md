# Claude Code와 Codex의 기억과 Skill을 통합 관리하기: MemDock 데스크톱 워크벤치 실전 활용기

Claude Code나 Codex로 코드를 작성하면서 기억 오염으로 골머리를 앓아본 적이 있으신가요?

많은 프로젝트의 루트 경로에는 규칙 파일이 장기간 방치되어 있습니다: `CLAUDE.md` 또는 `AGENTS.md`입니다.

초기에는 무척 유용합니다. 코딩 컨벤션, 테스트 스크립트, 빌드 명령을 상세히 적어 두면 비서 역할을 훌륭히 수행합니다. 하지만 보름쯤 지나면 테스트 프레임워크는 Jest에서 Vitest로 변경되고, 빌드 파이프라인도 전면 개편됩니다. 그럼에도 새로운 대화를 시작하면 모델은 영리해지기는커녕 과거의 낡은 규칙을 따라 폐기된 명령어를 실행하려 듭니다.

텍스트로 테스트 명령어를 정정해 주어도 모델은 고집스럽게 예전 방식을 반복합니다.

지난 대화에서 남겨진 잘못된 경험이 자동 메모리 캐시에 남아 신규 대화의 판단을 계속 흐려 놓습니다. 이 지루한 실랑이에 피로감을 느껴본 개발자가 적지 않을 것입니다.

더 큰 문제는 두 주력 도구 간의 단절입니다.

터미널에서 실행되는 Claude Code는 민첩하고 가볍습니다. 반면 여러 파일에 걸친 대규모 코드 변경 사항을 검토할 때는 Codex의 다중 열 그래픽 인터페이스가 훨씬 직관적입니다. 하지만 두 환경의 확장 기능과 기억은 철저히 격리되어 있습니다. Claude Code에 자동화 Skill을 잔뜩 세팅해 두어도 Codex로 전환하면 시스템 디렉토리를 일일이 뒤져가며 재설정해야 합니다. 노트북을 교체할 때마다 양쪽 개발 환경이 초기화되는 번거로움도 만만치 않습니다.

커뮤니티 개발자 cturing이 오픈소스 워크벤치 MemDock을 공개했습니다. GitHub 저장소 주소: `LingyiChen-AI/MemDock`.

먼저 이 도구가 수행하지 않는 역할을 명확히 짚고 넘어가겠습니다.

코드를 대신 작성하지 않으며, 프롬프트를 대필하지도 않고, 외부 서드파티 모델로 중계하지도 않습니다. 설치 후에도 기존의 Claude Code는 그대로 유지되며, 터미널 명령어 역시 `claude` 그대로입니다. 프로젝트 루트에 `.memdock/` 폴더가 추가되어 규칙의 변경 이력이 보관될 뿐입니다. 잘못 수정했을 때 이전 상태로 되돌릴 수 있다는 점이 이 도구의 본질적인 기능입니다.

담당하는 작업은 세 가지로 압축됩니다:

어떤 규칙을 유지할 것인가. 세션을 어느 도구에서 실행할 것인가. 다른 컴퓨터로 설정을 어떻게 이전할 것인가.

오직 이 세 가지 작업만 수행하며, 그 외의 영역은 전혀 건드리지 않습니다.

## 기억 부패 방지: 왜 【검토 대기】 버퍼가 필수적인가

대다수 자동 메모리 기능의 가장 치명적인 설계 결함은 대형 언어 모델에게 영구 규칙 파일에 대한 직접 쓰기 권한을 무제한으로 열어 준다는 점입니다.

야간 작업 도중 일시적인 에러를 넘기기 위해 임시방편으로 작성한 거친 코드를 모델이 핵심 원칙으로 오인하여 프로젝트 규칙 저장소에 몰래 추가해 버립니다. 그 결과 이후의 코드 생성이 모두 오염된 기억에 휘둘려 동일한 함정에 반복해서 빠지게 됩니다.

MemDock의 해결 방식은 매우 보수적입니다: 검토 대기 버퍼링 구조입니다.

소프트웨어는 글로벌 및 프로젝트 단위로 `CLAUDE.md`, `AGENTS.md`, Claude Code의 로컬 자동 메모리를 통합 검색할 수 있습니다. 오래된 규칙이 발견되면 화면 분할을 통해 차이점을 비교하며 수정할 수 있고 언제든 과거 리비전으로 롤백할 수 있습니다.

가장 실용적인 기능은 주간 경험 추출 파이프라인입니다.

시스템은 최근의 실제 대화 기록을 자동으로 분석하여 향후 유지할 만한 기술적 노하우와 수정이 필요한 레거시 규칙을 선별합니다.

하지만 추출된 제안 사항이 디스크 파일에 즉시 자동 저장되지는 않습니다.

추출된 항목들은 모두 검토 대기 큐로 들어갑니다. 개발자는 화면을 열고 좌측에는 기존 규칙, 중앙에는 신규 제안, 우측에는 당시의 대화 원문을 나란히 띄워 두고 검토합니다.

승인 버튼을 눌러야만 비로소 파일에 반영되며, 거절하면 부적절한 기억은 그 자리에서 폐기됩니다.

초기 사용 당시 겪었던 시행착오로, 빌드 결과물인 `dist/` 폴더 내부의 에러 로그가 규칙 후보로 잘못 수집된 적이 있었습니다. MemDock의 무시 목록에 `dist/`와 `coverage/`를 즉각 추가함으로써 후보 풀을 깨끗하게 유지할 수 있었습니다.

메모리 의존성 그래프 기능을 활용하면 현재 활성화된 각 규칙이 어떤 대화 세션에서 비롯되었는지 역추적할 수 있습니다. 규칙 개정을 더 이상 감에 의존해 진행할 필요가 없습니다.

## 도구 간 가교: Claude Code와 Codex 간 양방향 세션 전환

두 도구 중 하나만을 골라야 할 이유는 없습니다.

실무 개발자는 작업 성격에 따라 두 환경을 수시로 넘나듭니다.

터미널 환경은 반응 속도가 즉각적이어서 명확한 목표를 두고 테스트를 수행하거나 단일 파일을 수정하고 대규모 리팩토링을 실행할 때 유리합니다. 반면 여러 모듈이 얽힌 아키텍처를 점검할 때는 Codex의 다중 창 화면이 인지 부담을 덜어 줍니다.

MemDock의 핵심 축은 양방향 세션 전환입니다.

Claude Code 터미널에서 대화를 나누다가 여러 모듈에 걸친 수정이 필요해지면 클릭 한 번으로 Codex 세션으로 변환하여 시각적으로 작업을 이어갈 수 있습니다.

역방향 전환도 마찬가지로 매끄럽습니다. Codex에서 사양과 구조를 확정한 후 클릭 한 번으로 네이티브 터미널로 복귀하여 대량의 배치 작업을 명령어 환경에서 처리할 수 있습니다.

확장 기능인 Skill 관리 역시 통합됩니다.

두 도구에 설치된 글로벌 및 프로젝트 전용 Skill 목록이 한눈에 표시되며, Superpowers 플러그인 팩도 패키지 단위로 정리됩니다. GitHub 저장소 링크, 로컬 디렉토리 경로, ZIP 압축 파일을 통한 직접 설치를 지원합니다.

Claude Code에서 검증을 마친 디버깅 Skill은 복사 버튼 하나로 Codex 환경에 설정 파일 수정 없이 복제할 수 있습니다.

## 병렬 개발 격리: Git Worktree와 기기 간 동기화의 현실적 비용

단일 작업 트리에서 여러 AI 어시스턴트를 동시에 구동하면 파일 충돌이 빈번하게 일어납니다.

한 세션에서 어시스턴트에게 백엔드 스키마 전면 수정을 맡긴 상태에서 다른 세션을 통해 프론트엔드 입력 폼 수정을 지시하면, 하나의 Git 작업 공간 안에서 커밋되지 않은 변경 사항들이 뒤섞여 작업이 마비됩니다.

MemDock은 Git Worktree 병렬 처리 구조를 UI 내부에 직접 통합했습니다.

기능 단위별로 독립된 디렉토리를 생성하여 `git worktree add ../feat-schema feat/schema` 명령을 통해 병렬 개발을 진행할 수 있습니다. 터미널에서 상태를 조회하면 다음과 같이 구성됩니다:

```text
$ git worktree list
/Users/cool/work/project-core       b39a1c2 [main]
/Users/cool/work/feat-schema        d7e4120 [feat/schema]
/Users/cool/work/feat-ui-auth       a199f03 [feat/ui-auth]
```

하지만 충돌이 마법처럼 사라진다고 맹신해서는 안 됩니다.

Worktree는 작성 시점의 작업 디렉토리를 격리할 뿐이며, 브랜치 병합 시점의 충돌을 자동으로 없애 주지는 않습니다. 지난주 브랜치를 합칠 때도 파일 두 개에서 충돌 표시가 발생했습니다. 다행히 변경점이 서른 줄 남짓한 스키마 정의부에 집중되어 있어 해결은 수월했습니다.

진정한 장점은 작업 컨텍스트의 완벽한 분리에 있습니다. 한 브랜치에서 테스트를 구동하고 다른 브랜치에서 화면을 개발하더라도 서로의 `node_modules` 의존성이 간섭받지 않습니다.

비용 측면도 감안해야 합니다. Worktree를 3개 생성하면 디스크 점유율은 배로 증가합니다. 각 폴더마다 패키지를 별도로 보관해야 하므로 저장 공간 관리에 신경 써야 합니다.

개발 장비 이전도 간편합니다. 메모리 규칙과 Skill 목록을 JSON으로 패키징하여 GitHub 비공개 저장소를 통해 일괄 동기화할 수 있습니다.

다만 보안 측면의 주의사항이 있습니다:

`CLAUDE.md`를 GitHub에 푸시하기 전 내용을 육안으로 반드시 점검하십시오. 사내 테스트 서버 IP 주소나 스테이징 API 키 접두사를 규칙 파일에 직접 적어 두는 개발자가 적지 않습니다. 비공개 저장소라 할지라도 사내 인트라넷 수준의 안전 구역은 아니므로 민감 정보 유출에 각별히 유의해야 합니다.

또한 MemDock은 source-available 라이선스를 따릅니다. 개인적인 무료 사용은 자유로우나, 무단 2차 배포나 상업용 패키지 재판매는 엄격히 금지됩니다.

## 실무 루틴과 현주소

현재 필자의 작업 루틴은 다음과 같습니다: Claude Code로 테스트 구동과 단일 파일 수정을 진행하고, Codex로 코드 차이점을 검토하며, 규칙 변경 사항은 검토 대기 큐에 모아 두었다가 주 1회 정리합니다. 금요일 퇴근 전 비공개 저장소로 밀어 두면 주말에 집의 MacBook에서 작업을 그대로 이어받을 수 있습니다.

완벽한 형태는 아닙니다. 장비를 바꿀 때마다 액세스 토큰을 수동으로 다시 입력해야 하는 번거로움이 남아 있으며, 개발자가 예고한 OS 키체인 통합 기능은 아직 출시되지 않았습니다.

여러분은 현재 AI 개발 도구들의 기억과 규칙을 어떻게 관리하고 계신가요? 더 간결한 노하우가 있다면 댓글로 의견을 나눠 주십시오.
