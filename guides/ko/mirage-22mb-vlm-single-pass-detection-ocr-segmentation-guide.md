# 22MB 이하 단일 패스 시각 모델로 검출과 OCR 동시 처리: Mirage의 아키텍처 검증

엣지 기기나 가벼운 클라우드 가상머신에서 멀티모달 모델을 구동할 때 메모리와 대역폭 부족은 항상 치명적인 걸림돌이 됩니다.

주류 모델은 단일 그래픽카드에서도 기본 8GB의 VRAM을 차지합니다. 일반 1080p 스크린샷 하나만 넣어도 패치 분할 단계에서 수천 개의 시각 토큰이 소모됩니다. 이 긴 시퀀스를 자기회귀 디코더에 밀어 넣으면 냉각팬이 최고 속도로 회전하며 커서가 수초 동안 멈춥니다. 터미널이 그대로 정지합니다. 현장에서 필요한 작업은 사진 속 전원 스위치 좌표 두 개와 문패에 적힌 짧은 글자열을 가져오는 것뿐인 경우가 많습니다.

바운딩 박스 몇 개와 짧은 문자열을 얻기 위해 수십 GB짜리 거대 모델을 상시 상주시키면 서버 비용이 감당되지 않고 기기 배터리도 빠르게 소모됩니다.

전용 그래픽카드가 없는 엣지 노드에서 엔지니어가 진정으로 필요로 하는 것은 가중치 용량을 수십 메가바이트 이하로 압축하고 객체 위치 검출, OCR 문자 추출, 공간 기하 위상 관계만을 분리해 내는 것입니다. 전통적인 자기회귀 구조에서 이것이 가능할까요.

오랫동안 그 답은 부정적이었습니다.

최근 오픈소스 생태계에 극단적인 경량 아키텍처를 갖춘 모델이 등장했습니다. Cactus Compute 팀이 공개한 Mirage는 Apache 2.0 라이선스로 가중치를 완전 공개한 엣지용 멀티모달 모델입니다.

커뮤니티의 1차 논의와 개발자 피드백은 다음 기술 스레드에 기록되어 있습니다:
https://www.reddit.com/r/LocalLLaMA/comments/1xpm8mw/

전체 배포 용량은 22MB에 불과합니다. 총 파라미터 수는 약 51.3M 수준으로 제어되었습니다. 더 중요한 점은 단 한 번의 전방 추론 패스로 장면 묘사, 객체 검출 박스, 텍스트 인식, 세그멘테이션 마스크, 공간 위상 관계를 동시에 출력한다는 사실입니다.

이렇게 작은 모델이 어떻게 수많은 시각 작업을 단일 패스로 처리해 낼까요. 실제로 그렇게 가벼울까요.

직접 실측하기 전까지는 저 역시 의구심을 거두지 못했습니다.

## 하드웨어 예산과 51.3M 파라미터 분배

전통적인 멀티모달 모델이 비대해진 이유는 범용 디코더 하나에 모든 작업을 떠넘기려 했기 때문입니다.

디코더가 이미지를 설명하는 산문을 생성하는 동시에 연속된 텍스트 스트림 속에서 부동소수점 좌표를 억지로 출력해야 합니다. 이러한 방식은 소형 모델의 귀중한 용량을 비효율적인 좌표 문자 생성에 낭비하게 만듭니다.

Mirage는 완전히 다른 방식으로 문제에 접근합니다. 디코더에 과도한 자기주의 계층을 쌓는 대신 51.3M 전체 파라미터의 역할을 엄격히 분리했습니다:

- 이미지 인코더. 파라미터 약 7.8M. HConvGLU 모듈을 적용하여 고정 아다마르 행렬 변환으로 다채널 특징을 혼합하고 소형 학습 가능 합성곱 커널로 보정；
- 언어 디코더. 파라미터 약 40.8M. Simple Attention과 아다마르 다층 퍼셉트론 기반의 컴팩트 구조로 Needle 및 Whistle 아키텍처에서 계승；
- 전용 출력 헤드. 파라미터 약 2.6M. 경량 텍스트 판독 헤드와 공간 기하 헤드로 구성.

파라미터 장부를 계산해 보면 설계 의도가 뚜렷하게 드러납니다.

공간 좌표와 마스크 생성을 텍스트 디코더의 자기회귀 예측에 맡기지 않습니다. 2.6M 크기의 병렬 전용 헤드가 구조화된 결과를 직접 출력합니다. 언어 디코더는 객체의 의미 라벨, 기본 속성, 공간적 인과관계를 출력하는 본연의 역할에만 집중합니다.

문자 인식 역시 동일한 메커니즘을 따릅니다. 모델 내부에 전용 텍스트 스캔 경로를 갖추고 문자 특징을 추출한 뒤 의미 정렬을 수행합니다.

이러한 명확한 분업 덕분에 40.8M 크기의 언어 디코더는 불필요한 부담 없이 가볍게 작동합니다.

장면 묘사 출력 언어로 영어, 독일어, 프랑스어, 스페인어, 이탈리아어, 네덜란드어, 폴란드어 총 7개 언어를 지원합니다. 생성되는 텍스트는 간결하며 군더더기가 없습니다.

## 모바일 NPU 74ms와 일반 CPU 5.8초의 실측 격차

초소형 모델의 성능을 평가할 때는 실행 하드웨어 환경을 투명하게 밝혀야 합니다.

원작자가 제시한 대표 수치는 삼성 Galaxy S26 스마트폰 기준입니다:

- 온보드 신경망 처리 장치 NPU에서 실행할 때 전체 작업의 단일 추론 시간은 약 74밀리초；
- 스마트폰 CPU에서 실행할 때 단일 추론 시간은 약 107밀리초.

100밀리초 이내의 응답 속도라면 스마트폰 로컬 환경에서 앨범 자동 분류나 카메라 자동 초점 보조 용도로 충분히 실용적인 속도입니다.

하지만 가속기가 없는 클라우드 가상머신이나 사무실의 노후 PC에서 구동할 때도 동일한 성능이 유지될까요. 성능 타협점이 존재하지 않을까요.

커뮤니티 개발자 MagoViejo는 하드웨어 가속기가 없는 일반 x86 개인용 컴퓨터에 이 가중치를 올려 테스트했습니다. 듀얼코어 CPU의 부동소수점 연산에만 의존한 환경에서 이미지 한 장의 전체 해석 시간은 5.8초까지 늘어났습니다.

모바일 NPU의 74밀리초에서 일반 PC의 5.8초로 지연 시간이 약 80배 급증합니다. 원인은 연산 장치의 차이에 있습니다. Galaxy S26은 고정소수점 텐서 연산을 전담하는 NPU를 탑재한 반면 구형 x86 PC는 하드웨어 벡터 가속이 없는 CPU 코어로 부동소수점 행렬을 직접 처리하므로 연산 한계가 즉시 드러납니다.

이 수치들은 명확한 하드웨어 경계선을 제시합니다. 하드웨어의 반응은 정직합니다.

기기에 최신 NPU가 포함되어 있다면 수십 밀리초의 지연 시간은 실질적인 활용 가치를 지닙니다.

반대로 저가형 단일 코어 가상머신에서 실시간 영상 감시를 수행하려 한다면 초당 0.2프레임의 처리량으로는 감시 파이프라인이 즉시 지연됩니다. 약 6초에 달하는 대기 시간을 두고 실시간 영상 스트림에 통합할 수 있는 환경이 과연 존재할까요. 어떤 프로덕션 시스템이 이러한 지연을 감내할 수 있을까요.

유휴 상태의 저사양 Linux 머신에서 직접 구동해 보았습니다. 냉각팬이 즉시 최고 속도로 회전했습니다.

백그라운드 이미지 오프라인 분류, 콜드 스타트 전처리, 독립 그래픽카드가 없는 경량 에이전트의 저부하 시각 모듈로 배치하는 것이 현실적인 엔지니어링 판단입니다. 오프라인 배치 작업이라면 클라우드 인프라 비용을 대폭 절감할 수 있습니다.

## 커뮤니티 논쟁과 컨테이너 환경 오류 대처

어떤 오픈소스 프로젝트든 프로덕션에 도입되기 전 커뮤니티의 현미경 검증을 거치게 됩니다.

Mirage 공개 직후 커뮤니티에서 두 가지 주요 쟁점이 제기되었습니다.

첫 번째 쟁점은 커뮤니티 자동 검열 봇의 판정에서 시작되었습니다. stylome-ai-detection 계정이 배포 스레드에 AI 생성 텍스트 의심 경고를 부착했습니다. 원작자가 즉시 기술적 세부 사항을 답변하며 해명했으나 홍보성 문구로 인해 신중한 개발자들 사이에서 우려가 제기되었습니다.

이것이 진짜 기술적 성과인가 아니면 마케팅 포장인가.

두 번째 쟁점은 전통적인 객체 검출 알고리즘 YOLO와의 비교였습니다.

산업용 PC의 CPU 환경에서 순수 검출 프레임레이트만 따진다면 경량화된 YOLO nano가 여전히 훨씬 빠릅니다. Mirage의 진정한 차별점은 절대적인 FPS 경쟁이 아니라 22MB라는 극소형 크기 안에 문자 추출과 다중 객체 간 공간 위상 해석을 통합했다는 데 있습니다.

로컬 환경에서의 설치 과정은 간단합니다. Python 3.10 이상 환경에서 공식 패키지를 설치합니다:

```bash
pip install cactus-compute
```

Python 인터페이스를 통해 기본 파이프라인을 호출합니다:

```python
import cactus_compute

pipeline = cactus_compute.MiragePipeline.from_pretrained("cactus-compute/mirage-v1")
outputs = pipeline.analyze_image("test_sample.jpg")

print("Detected Boxes:", outputs.boxes)
print("OCR Text:", outputs.text_segments)
print("Spatial Topology:", outputs.relationships)
```

클린 상태의 Ubuntu 22.04 컨테이너에서 첫 테스트 코드를 실행하자 터미널에 즉시 오류가 발생했습니다: ImportError: libGL.so.1: cannot open shared object file: No such file or directory.

실행이 그 자리에서 중단되었습니다.

환경 로그를 확인한 결과 내부적으로 그래픽 렌더링 라이브러리에 의존하고 있었습니다. 컨테이너 내부에서 apt-get update && apt-get install -y libgl1 명령으로 누락된 환경을 보완하자 정상적으로 추론이 완료되었습니다.

누락된 라이브러리만 추가해 주면 해결됩니다.

이 초기 설정만 거치면 추론 과정은 안정적으로 이어집니다.

## 기술적 한계와 엔지니어링 선택 기준

이번 분석을 통해 Mirage와 같은 22MB급 멀티태스크 모델의 도입 기준이 명확해졌습니다.

적합한 활용 시나리오:
- 모바일 및 웨어러블 하드웨어 개발. 저전력 NPU를 갖추고 카메라 간판 문자 및 객체 외곽선을 오프라인으로 해석하는 기기；
- 엣지 에이전트 연산 분산. 라즈베리 파이나 산업용 기기에 전면 필터로 배치하여 무의미한 프레임을 걸러내고 이상 징후만 클라우드로 전송；
- 비공개 사진 오프라인 인덱싱. 이미지를 외부로 전송하지 않고 백그라운드에서 여유롭게 검색 태그를 구축.

적합하지 않은 시나리오:
- 고프레임 산업용 결함 검사. 초당 수십 프레임의 연속 영상 검사가 필요한 경우 YOLO나 전용 검출 헤드를 선택해야 합니다；
- 복잡한 개방형 도메인 시각 이해. 복잡한 차트 논리나 수십 장의 재무제표를 해석해야 한다면 클라우드 대형 멀티모달 API를 사용하는 것이 안전합니다.

구조적 사전 지식을 문제 정의에 내재화하고 전용 공간 헤드로 언어 디코더의 부담을 분산시킨 아키텍처는 매우 합리적입니다.

하지만 22MB라는 물리적 한계가 존재하는 만큼 만능 시각 지능을 기대해서는 안 됩니다. 가볍고 목적이 뚜렷한 엣지용 다목적 나이프로 다룰 때 트래픽 급증 상황에서도 안정적인 프로덕션 시스템을 유지할 수 있습니다.

엣지 하드웨어에서 이 파이프라인을 매끄럽게 구동하기 위해 일반 CPU 환경의 약 6초 처리 대기 시간을 감내할 준비가 되셨습니까. 아니면 사용하시는 장비에 이미 전용 NPU가 탑재되어 있습니까.
