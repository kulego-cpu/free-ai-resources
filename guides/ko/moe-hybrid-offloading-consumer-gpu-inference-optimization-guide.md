중고 RTX 3090 두 장, 총 48GB VRAM。

수십억 개의 활성 매개변수를 가진 MoE 모델을 VRAM 에 전부 올리려 하면 즉시 CUDA out of memory 에러가 발생합니다。

뼈대 네트워크는 GPU 에 남기고 사용 빈도가 낮은 전문가를 메인 메모리로 넘긴다。 구동이 가능한가。 구동은 됩니다。

하지만 실제 추론을 시작하면 생성 속도가 초당 2 에서 3 토큰으로 곤두박질칩니다。 CPU 사용률은 100% 에 달하는데 GPU 사용률은 고작 3% 에서 멈춰 있습니다。

먼저 nvidia-smi 를 확인하고 PCIe 버스 대역폭을 점검해야 합니다。 문제는 연산 커널이 아니라 버스를 통한 가중치 이동에 있습니다。

검증 데이터는 GitHub 공개 기술 문서 https://github.com/alesha-pro/inference-optimization-playbook 에 기반합니다。

테스트 환경은 Ubuntu 22.04 LTS, 300W 로 제한된 RTX 3090 4 장, PCIe 3.0 x16, 8 채널 DDR4-2133 메모리, 드라이버 580.12 및 CUDA 12.8 입니다。 런타임에는 자체 패치를 적용한 llama.cpp 커밋 1cd7102 와 맞춤형 엔진 maya-ik2 r5 를 사용했습니다。 DeepSeek, Qwen, 훈위안 등의 모델을 대상으로 115 가지 가설을 검증하여 97 가지 비교 실측치를 기록했습니다。

이 기록에서 가장 가치 있는 부분은 속도 향상 수치가 아니라 상세히 기술된 실패 목록입니다。 인터넷 커뮤니티에서 추천되는 여러 튜닝 기법이 실제 오프로딩 환경에서는 아무런 효과가 없거나 오히려 성능을 무너뜨리는 것으로 드러났습니다。

## 가중치 이동이 직면하는 물리적 한계

MoE 하이브리드 오프로딩이 극도로 느려지는 원인은 무엇인가。 물리적 수치를 따져보아야 합니다。

MoE 모델은 토큰을 하나 생성할 때마다 라우터가 수십 개의 전문가 중 극소수를 선택합니다。 수천 장의 GPU 를 갖춘 클라우드 환경에서는 모든 전문가가 VRAM 에 상주하지만, 일반 데스크톱 메인보드에서는 PCIe 대역폭이 턱없이 부족합니다。

선택된 전문가가 VRAM 에 없으면 PCIe 를 통해 메인 메모리에서 가져와야 합니다。 비용을 계산해 봅니다：

- 양자화된 전문가 1 개의 가중치 크기는 약 150MB 에서 300MB
- 1 토큰 생성 시 보통 4 개에서 8 개의 전문가 활성화
- 전부 메모리에 있는 전문가가 선택될 경우 1 스텝마다 1.2GB 의 데이터 전송 발생
- 일반적인 PCIe 3.0 x16 의 실제 유효 전송 대역폭은 초당 약 12GB 에서 14GB 수준

이것이 무엇을 뜻하는가。

순수한 데이터 이동 시간만으로도 이론상 생성 속도는 초당 십여 토큰 이하로 제한됩니다。 여러 장의 GPU 가 메모리 채널을 두고 경쟁하면 지연 시간은 더욱 늘어납니다。

어느 지점을 개선해야 실질적인 성과를 거둘 수 있는가。

## 실질적인 성과를 입증한 4 가지 핵심 개선

97 개 대조군 중에서 의미 있는 성능 도약을 기록한 기법은 4 가지뿐이었습니다。

### 1. 가상 메모리 페이징을 배제하고 Pinned RAM 으로 DMA 전송 직결

일반적인 프로그램은 페이징 가능한 가상 메모리를 사용합니다。 드라이버가 GPU 로 데이터를 전송할 때 운영체제 내부의 잠금 버퍼로 복사한 후 DMA 를 실행합니다。 이 중복 복사 과정이 메모리 대역폭을 소모합니다。

해결책은 명확합니다。 초기화 시점에 메모리 고정 시스템 콜을 호출하여 전문가 가중치를 물리 메모리에 직접 고정시킵니다。

실측 결과는 어떠했는가。

4 장의 GPU 에서 DeepSeek V4.1 Flash 를 오프로딩 구동했을 때, 프롬프트 청크 분할과 결합하여 32K 컨텍스트의 사전 연산 속도가 초당 430 토큰에서 2,199 토큰으로 급증했습니다。 CPU 내부 복사 오버헤드를 제거하여 달성한 5 배의 속도 향상입니다。

### 2. 파이프라인 레이어 분할을 폐기하고 텐서 병렬화로 전환

카드마다 층을 나누는 레이어 분할은 직관적이지만 오프로딩 환경에서는 심각한 파이프라인 정체를 유발합니다。

이전 층의 전문가가 메모리 전송을 기다리는 동안 다음 층의 GPU 는 대기 상태에 머뭅니다。 카드 간 동기가 어긋나면서 전체 시간의 40% 이상을 유휴 상태로 소모합니다。

연구팀은 GLM-5.3-Flash 2.05bpw 환경에서 층 분할 방식을 버리고 텐서 병렬화로 전면 교체했습니다。 각 GPU 가 모든 전문가 가중치 행렬의 4 분의 1 씩 보유하여 DMA 전송과 행렬 연산을 동시에 실행한 후 All-Reduce 로 결합합니다。

4 카드 구성에서 생성 속도는 초당 48.3 토큰에서 67 토큰 선으로 안정적으로 상승했습니다。 GPU 간 대기 시간이 완전히 해소되었습니다。

### 3. 미적재 전문가는 CPU 로 즉시 연산하고 상주 전문가만 GPU 에서 처리

PCIe 버스 대역폭이 부족하다면 다중 코어 CPU 를 활용해 메인 메모리에서 직접 연산하는 편이 합리적이지 않은가。

훈위안 Hy4 Flash 2 카드 환경에서 스케줄러를 개편했습니다：

```text
               ┌───────────────────────────────┐
               │    Router 토큰 라우팅         │
               └───────┬───────────────┬───────┘
                       │               │
             [VRAM 상주 전문가]      [메인 메모리 전문가]
                       │               │
                       ▼               ▼
               ┌───────────────┐┌───────────────┐
               │ GPU 코어 연산 ││ CPU 멀티스레드│
               │ 병렬 GEMM     ││ 메모리 직접연산│
               └───────┬───────┘└───────┬───────┘
                       │               │
                       ▼               ▼
               ┌───────────────────────────────┐
               │    은닉 상태 결합 배리어       │
               └───────────────────────────────┘
```

선택된 8 개의 전문가 중 6 개가 VRAM 에 있고 2 개가 메모리에 있다면 가중치 이동을 중단합니다。 VRAM 측 6 개는 GPU 에서 연산하고 메모리 측 2 개는 CPU 스레드로 병렬 처리합니다。 연산 후 버스를 통과하는 것은 가벼운 활성화 벡터뿐입니다。

코드 생성 테스트에서 훈위안의 생성 속도는 초당 24.6 토큰에서 70.4 토큰으로 크게 올랐습니다。

### 4. 단일 그래프 컴파일：수천 번의 커널 호출을 단일 CUDA Graph 로 압축

모델 전체가 24GB 단일 GPU 에 들어가는 크기라면 병목은 버스 대역폭에서 커널 호출 지연으로 이동합니다。

Inkling 2 Mini 의 경우 24 개 층의 MoE 에 3,072 개의 전문가가 존재합니다。 기본 llama.cpp 환경에서는 토큰 하나를 만들 때마다 드라이버 계층을 1,404 번 왕복합니다。 커널 자체는 수 마이크로초 만에 끝나지만 호출 대기열 지연으로 인해 속도가 초당 57 토큰에 머뭅니다。

해결책은 명확합니다。 maya-ik2 r5 엔진에서 전체 전문가 연산과 잔차 결합을 단일 CUDA Graph 로 통합하여 호출 횟수를 781 회로 줄였습니다。

양자화 정밀도를 낮추지 않고도 토큰 생성 속도가 초당 57 토큰에서 112 토큰으로 2 배 향상되었습니다。

## 데이터 앞에서 드러난 최적화 미신

성공적인 개선 사례 이면에는 아무런 이득이 없었던 실패 사례가 다수 기록되었습니다。

### 1. 정적 전문가 사용 프로파일은 다른 작업에 통용되는가?

일반적인 테스트 문장을 실행하여 사용 빈도 순위를 뽑고 상위 20% 를 VRAM 에 고정하면 80% 가 적중한다는 주장이 있습니다。

현실은 다릅니다。 MiniMax 테스트에서 단일 질문을 기반으로 작성한 프로파일은 원본 질문에 대해 90% 적중률을 보였지만, 동일 분야의 다른 질문에서는 적중률이 64% 로 떨어졌습니다。 프로파일 없이 무작위로 전문가를 배치했을 때도 적중률이 61% 였습니다。

### 2. 소형 모델을 활용한 투기적 디코딩은 항상 이득인가?

작은 모델로 후보 토큰을 빠르게 생성하고 메인 모델이 일괄 검증하는 방식은 논리적으로 보입니다。 하지만 3 종의 오픈소스 모델에서 자체 튜닝한 소형 모델의 속도 향상은 거의 0 에 수렴했습니다。

초안 모델의 채택률이 조금만 떨어져도 재연산 롤백이 발생하여 일괄 검증의 이점을 상쇄하기 때문입니다。

### 3. 짧은 벤치마크 결과가 긴 문맥에서도 유지되는가?

128 토큰 길이의 짧은 테스트에서 27% 속도 향상을 보였던 어텐션 설정이 8K 길이의 실제 디버깅 세션에 들어가자 4 회차 턴에서 부동소수점 오버플로를 일으키며 유효 속도가 2% 하락한 사례가 기록되어 있습니다。

## 단계별 실전 트러블슈팅 가이드

소비자용 카드로 대형 MoE 를 구동할 때는 터미널에서 다음 명령어로 병목 구간을 먼저 파악하십시오：

```bash
# GPU 부하와 PCIe 버스 사용량을 실시간 모니터링
nvidia-smi dmon -s et -d 1
# 메인보드 물리 슬롯이 16x 대역폭으로 정상 인식되었는지 확인
sudo lspci -vv -s $(lspci | grep -i nvidia | head -n 1 | awk '{print $1}') | grep LnkSta:
# NUMA 노드 구조와 메모리 경합 여부 점검
numactl --hardware
# 대용량 페이지 메모리를 활성화하여 물리 메모리 버퍼 확보
sudo sysctl -w vm.nr_hugepages=1024
```

첫째, 버스를 점검하십시오。 PCIe 사용률이 90% 를 웃돌고 있다면 병목은 데이터 이동에 있습니다。 대용량 페이지 활성화와 Pinned 전송 적용을 우선해야 합니다。

둘째, 라우팅 특성을 분석하십시오。 전문가 선택이 고르게 분산되어 있다면 정적 프로파일에 매달리지 말고 텐서 병렬화나 CPU 직접 연산을 구성해야 합니다。

셋째, 실제 업무 분량의 로그로 검증하십시오。 수만 자에 달하는 긴 문맥 세션에서도 메모리 오버플로나 성능 저하 없이 끝까지 작동하는 설정만이 실무에서 신뢰할 수 있는 환경입니다。
