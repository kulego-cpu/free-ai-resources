# Natively 3.0 및 Ollama 로컬 회의록 어시스턴트 실측 리뷰: 완전 오프라인 전사, 하드웨어 비용과 로컬 MCP 보안 경계

지난주 금요일 오후 3시, 기술 아키텍처 리뷰 회의.
협력업체 세 곳의 핵심 조달 단가가 화면에 공유되고 있었습니다.
참석자 중 한 명이 클라우드 회의록 어시스턴트를 켜려 하자 법무 책임자가 즉시 제지했습니다. 작년 상용 회의록 SaaS 데이터 유출 사건으로 8만 3000여 명의 녹음본과 화면 캡처가 외부로 노출된 사례가 보도된 바 있습니다. 핵심 단가와 시스템 설계안을 외부 클라우드로 보낼 수는 없는 상황이었습니다.
두 시간에 걸친 회의는 키보드로 일일이 수기 기록했지만 두 건의 주요 결정 사항이 누락되었습니다.
회의 직후 저는 Natively 3.0 실측에 착수했습니다. 회의록 자동화는 필요하되 오디오는 단 1바이트도 호스트 PC 밖으로 내보내지 않는 것이 전제였습니다.

## 1. 클라우드 회의 어시스턴트의 위협 모델과 로컬 격리 설계

시중의 클라우드 회의록 소프트웨어는 데이터를 어떻게 처리할까요.
패킷을 분석해 보면 세 단계 구조로 작동합니다.
브라우저 확장 프로그램이나 가상 드라이버가 마이크와 스피커 오디오 스트림을 캡처합니다.
조각난 오디오 파일이 공용 클라우드 오브젝트 스토리지로 업로드됩니다.
클라우드 클러스터의 음성인식 및 거대언어모델이 요약 텍스트를 생성하여 클라이언트로 반환합니다.

보안 관점의 허점은 명확합니다.
원본 오디오가 제3자 스토리지에 영구 저장됩니다.
버킷 권한 설정 오류나 인증 토큰 유출이 발생할 경우 조달 가격, 미공개 아키텍처, 내부 논의 내용이 평문으로 유출될 위험이 상존합니다.
기밀을 보호하기 위한 확실한 방법은 외부 네트워크 연결을 차단하는 것입니다.

Natively 3.0의 설계는 명료합니다.
오디오 수집, 음성 전사, 모델 요약, 기록 검색의 전 과정을 단일 PC 내부에 가둡니다.
모든 요청을 127.0.0.1 루프백 주소에 고정하여 외부 오디오 전송을 물리적으로 차단합니다.

## 2. 아키텍처 분석: 완전 오프라인 가동을 뒷받침하는 3요소

인터넷 연결이 차단된 PC에서 2시간 연속 회의를 처리하기 위해 다음 세 가지 구성요소가 유기적으로 맞물립니다.

### 1. Rust 기반 듀얼 트랙 네이티브 오디오 분류
웹 브라우저의 WebAudio는 부하 발생 시 버퍼 누락이나 음성 왜곡이 발생하기 쉽습니다.
Natively는 오디오 수집 파이프라인을 Rust로 작성했습니다.
한 갈래는 시스템 코어 오디오 출력을 후킹하여 원격 참석자 음성을 수집합니다.
다른 한 갈래는 물리 마이크 입력을 독립적으로 수집하여 로컬 발언을 캡처합니다.
두 채널을 물리적으로 분리하여 스피커 출력이 마이크로 유입되어 화자 분리를 방해하는 현상을 차단합니다.

### 2. 온디바이스 Whisper 및 Parakeet 음성 전사 엔진
분할된 오디오 프레임은 외부 API를 거치지 않고 로컬 추론 엔진으로 직접 전달됩니다.
Apple Silicon 환경에서는 CoreML 및 Metal 파이프라인을 통해 하드웨어 가속을 수행합니다.
Windows 환경에서는 DirectML 인터페이스를 사용합니다.
음성인식 지연 시간은 450밀리초에서 600밀리초 수준을 유지하며 분당 사용료도 발생하지 않습니다.

### 3. Ollama 모델 백엔드 및 임베디드 MCP 서버
전사된 실시간 텍스트 스트림은 로컬에서 구동 중인 Ollama 프로세스로 전송됩니다.
요약 모델로는 Qwen2.5 7B 또는 경량 Llama3.2 3B를 선택할 수 있습니다.
3.0 버전에서는 로컬 루프백 네트워크상에 경량 Model Context Protocol 즉 MCP 서버가 내장되었습니다.
로컬 개발 도구나 에이전트가 지난 회의 결과를 질의할 때 표준 프로토콜을 통해 즉시 데이터를 조회할 수 있습니다.

## 3. 워크스테이션 실측: 45분 회의 자원 장부와 한계

로컬 하드웨어가 실시간 회의 부하를 온전히 감당할 수 있을까요.
자원 소모 지표를 먼저 확인해 보겠습니다. 테스트 장비는 M2 Max 칩 탑재 MacBook Pro, 32GB 통합 메모리입니다. Whisper large-v3-turbo 양자화 모델과 Ollama Qwen2.5 7B 지시 미세조정 버전을 구동했습니다.
참석자 5명, 45분간 진행된 회의에서 피크 메모리 점유율은 22GB에 도달했고 쿨링 팬 회전수가 증가하며 SoC 온도는 85도 안팎을 기록했습니다.
16GB 장비에서 전사와 7B 요약을 동시에 실행하는 것은 권장하지 않습니다. 8GB 장비에서는 시도하지 않는 것이 좋습니다.
아래 표는 다섯 차례 회의의 중간값이며 인위적인 벤치마크 결과가 아닙니다.

| 평가 항목 | 기존 상용 클라우드 SaaS | Natively 3.0 로컬 파이프라인 | 엔지니어링 분석 및 경계 조건 |
| :--- | :--- | :--- | :--- |
| 오디오 외부 전송량 | 시간당 수백 메가바이트 업로드 | 외부 전송 제로, 로컬 IPC 통신만 수행 | 클라우드 데이터 유출 경로 차단 |
| 음성 전사 응답 지연 | 800밀리초에서 1500밀리초 변동 | 450밀리초에서 600밀리초 범위 | Rust 로컬 파이프라인으로 네트워크 지연 배제 |
| 회의 요약 생성 시간 | 원격 클러스터에서 약 4초 소요 | 로컬 7B 모델 구동 시 8초 소요 | 로컬 연산 자원 한계로 클라우드 대비 다소 지연 |
| 호스트 시스템 피크 메모리 | 데스크톱 앱 기준 약 450MB | 시스템 총 메모리 점유율 22GB 도달 | Whisper 및 로컬 모델 동시 상주 비용 |
| 장시간 연속 구동 발열 | 본체 미온, 팬 소음 거의 없음 | 본체 발열 뚜렷, SoC 온도 약 85도 | 지속적인 고부하 연산에 따른 자연스러운 발열 |

완전한 오프라인 환경은 탁월한 보안을 제공하지만 명확한 물리적 비용을 요구합니다.
화상회의 자체가 GPU 렌더링과 비디오 디코딩을 소모합니다.
여기에 로컬 Whisper가 오디오를 지속 전사하고 Ollama가 추론 컨텍스트를 메모리에 상주시킵니다.
이 세 요소가 맞물리면서 22GB의 메모리를 점유합니다.
16GB 메모리 장비에서 이 워크플로를 구동할 경우 가상 메모리 스왑이 급증하여 화면 버벅임이 발생할 가능성이 높습니다.

## 4. 트러블슈팅 및 보안 통제 경계

연속 테스트 과정에서 확인된 주의 사항은 다음과 같습니다.

### 1. 마이크 독점 모드로 인한 녹음 누락
초기 설정 시 상대방 음성은 정상 전사되나 자신의 발언이 누락되는 현상이 발생했습니다.
원인 확인 결과 화상회의 클라이언트가 물리 마이크 장치 핸들을 독점 잠금한 것이 원인이었습니다.
설정에서 오디오 캡처 소스를 직접 마이크 감시에서 시스템 오디오 믹스 입력으로 변경하여 해결했습니다.

### 2. 장시간 회의 시 컨텍스트 속도 저하
회의가 30분을 넘어가며 텍스트가 누적되면 모델의 추론 속도가 점차 저하됩니다.
컨텍스트를 제한하지 않을 경우 7B 모델의 텍스트 생성 속도가 초당 40자에서 10자 수준으로 떨어집니다.
슬라이딩 컨텍스트 윈도우를 8192 토큰 이내로 고정하고 주기적인 구간 요약을 병행하는 방식이 안정적입니다.

### 3. 로컬 MCP 서버의 보안 노출면
MCP 구현체를 집중 점검했습니다. 3.0 버전은 루프백 인터페이스에 경량 MCP 서버를 구동합니다. 현재 세부적인 접근 제어나 읽기 전용 격리 기능은 확인되지 않았습니다. 포트를 파악한 로컬 프로세스는 회의록 조회가 가능합니다. 머신에 신뢰할 수 없는 에이전트 스크립트가 실행 중일 경우 회의록 수정이나 삭제가 일어날 위험이 있습니다. 공식적인 접근 제어 기능이 추가되기 전까지는 외부 자동화 파이프라인에 연결하지 말고 바인딩 주소를 0.0.0.0으로 변경하지 않도록 유의해야 합니다.

### 4. 프로젝트 설명서 내 스폰서 링크 확인
깃허브 README 상단에 상용 녹음 API 홍보 링크가 포함되어 있습니다.
클라이언트 자체는 오픈소스이지만 환경 설정 시 외부 유료 클라우드를 선택하지 말고 로컬 127.0.0.1 포트 설정을 유지해야 합니다.

## 5. 실전 구축 및 인수 점검 목록

로컬 회의록 파이프라인 구축 단계는 다음과 같습니다.

### 1. 로컬 Ollama 구동
Ollama를 설치하고 검증된 모델을 내려받습니다.

```bash
ollama run qwen2.5:7b
```

### 2. 데스크톱 앱 설치
macOS 환경에서 Homebrew로 클라이언트를 설치합니다.

```bash
brew install --cask Natively-AI-assistant/tap/natively
```

### 3. 오프라인 설정 적용
클라이언트 환경설정에 진입합니다.
- 모델 제공자로 Ollama를 지정하고 로컬 포트 11434 입력.
- 음성 엔진으로 로컬 Whisper를 선택하여 초기 가중치를 로컬 캐시에 저장.
- 클라우드 동기화 설정을 끄고 오프라인 상태 표시등 활성화 확인.

### 4. 오프라인 인수 및 포트 보안 점검
Wi-Fi를 끄고 비행기 탑승 모드에서 테스트 음성을 녹음합니다. 자막이 실시간으로 출력되고 할 일 목록이 생성되며 파일은 로컬에 저장됩니다. 22GB 메모리와 팬 소음이 수반됩니다. 터미널에서 `lsof -i :11434` 명령을 실행하여 Ollama가 127.0.0.1에서만 수신 대기하는지 확인하고 MCP 포트의 외부 노출 여부와 로컬 SQLite 저장 상태를 점검하면 설정이 완료됩니다.
