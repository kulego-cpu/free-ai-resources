## 1. 용량 산정의 참사: 12명이 쓰는데 8장의 H100이 필요했을까

먼저 우리 스스로 저지른 어리석음을 되짚어봐야 합니다.

지난달 초 우리는 사내 문서 지능형 검색 및 검증 파일럿 프로젝트를 수주했습니다.

사전 회의에서 발주처 기술 책임자가 정식 출시 후 수백 명의 동시 접속이 발생할 수 있다고 구두로 언급했습니다.

안전하게 가자는 마음과 기술 보고 자리에서 그럴듯한 구성을 보여주고 싶다는 허영심이 겹쳐, 우리는 단계적 부하 테스트를 건너뛰었습니다.

퍼블릭 클라우드에서 8장의 Nvidia H100 80GB SXM5 인스턴스를 온디맨드로 바로 계약했습니다.

당시의 시간당 과금 내역은 다음과 같았습니다:
- GPU 1장당 시간당 단가: 3.85 달러;
- 8장 전체의 시간당 비용: 30.80 달러;
- 30일 연속 가동 총비용: 30.80 × 24 × 30 = 22,176 달러;
- 위안화 환산 총지출: 약 159,600 위안, 한화로 3,000만 원이 넘는 거액입니다.

16만 위안에 육박하는 예산을 태운 결과, 실제 운영 현장은 어떠했을까요.

파일럿이 시작되고 실제로 접속한 사내 인원은 단 12명이었습니다.

낮 시간대 평균 동시 요청은 3건에서 5건에 불과했습니다.

12명이 쓰는데 8장의 H100이 필요했을까요.

전혀 필요하지 않았습니다.

순전한 예산 낭비였습니다.

매일 밤 10시가 넘어가면 인스턴스의 GPU 사용률은 0퍼센트로 떨어졌습니다.

데이터센터의 냉각 팬만이 텅 빈 640GB VRAM을 향해 밤새도록 공회전했습니다.

이것은 연산 자원의 부족 문제가 아니라 전형적인 용량 산정 실패 사고였습니다.

사내 오피스 업무용이라면 합리적인 대안이 얼마든지 있었습니다.

단일 L4나 A10G 인스턴스를 대여하면 시간당 1달러에서 1.5달러 선에서 해결됩니다.

그편이 훨씬 현명하지 않았을까요.

당연히 그렇습니다.

혹은 상용 API를 호출하여 소비한 토큰만큼 결제했다면 월 수백 달러로 충분했을 것입니다.

8장의 H100을 가동한 것은 모기를 잡으려고 대포를 쏜 격이었습니다.

클라우드 제공업체가 스스로 다운그레이드를 권해줄까요.

절대 그렇지 않습니다.

값비싼 교훈을 얻은 저는 클라우드 환경을 즉시 폐기하고 사무실 책상 밑으로 테스트 장비를 들여왔습니다.

## 2. 전기세만 계산하는 오류 거부: 로컬 워크스테이션의 완전한 TCO 장부

로컬 추론을 논할 때 온라인에서는 종종 불공정한 비교가 이루어집니다. 가정용 전기세만 떼어내어 값비싼 클라우드 청구서와 단순 대조하는 방식입니다.

실제 엔지니어링에서 하드웨어 자체 구축 비용은 전기세에 머물지 않습니다.

장비 감가상각, 네트워크 회선, 백업 체계, 그리고 일상 유지보수 인건비 모두가 총소유비용 TCO에 포함됩니다.

전기세만 계산하는 것은 자기기만이 아닐까요.

명백한 자기기만입니다.

책상 밑의 장비를 꺼내어 실제 자산 내역을 계산해 봅니다:
- 핵심 가속기: MSI RTX 4060 Ti 16GB, 구매가 2,850 위안; 표준 4060은 8GB 모델만 존재하므로 16GB를 확보하려면 반드시 4060 Ti를 선택해야 합니다;
- 호스트 플랫폼: 중고 B650 베어본 본체 및 32GB 메모리, 구매가 1,300 위안;
- 보조 노드: Mac mini M4 24GB 통합 메모리, 정부 보조금 적용 후 4,100 위안;
- 고정자산 초기 투자 총액: 2850 + 1300 + 4100 = 8,250 위안 정액.

이 하드웨어 고정자산을 일반적인 36개월 균등 감가상각으로 계산합니다:
`8250 ÷ 36 ≒ 월 229.17 위안`.

줄일 수 없는 고정 지출입니다.

이어서 실제 전력 소모를 측정합니다.

콘센트에 정밀 전력 측정기를 연결했습니다.

RTX 4060 Ti 호스트가 Qwen 2.5 7B 추론을 전속력으로 실행할 때 순간 소비전력은 약 162W로 안정되었고 대기 전력은 42W였습니다.

낮 8시간 동안 최대 추론을 돌리고 나머지 16시간 동안 대기한다고 가정합니다:
하루 총소비전력: `0.162 × 8 + 0.042 × 16 ≒ 1.968 kWh`.

가정용 전력 단가를 kWh당 0.65 위안으로 계산하면 하루 전기세는 1.28 위안, 30일 기준 약 38.4 위안입니다.

보조 Mac mini의 대기 소비전력 약 8 위안을 더하면 총전력 비용은 월 47 위안 미만입니다.

마지막으로 부대시설과 유지보수 예비비를 반영합니다:
- 600W 가정용 무정전 전원장치 UPS, 월 감가상각 15 위안;
- 기가비트 LAN 포트 및 일일 디스크 증분 백업 스크립트, 월 20 위안; 백업을 생략할 엔지니어가 있을까요; 장애 발생 시 책임을 감당할 수 없습니다;
- 매주 30분 로그 점검에 소요되는 엔지니어 유지보수 공수, 월 50 위안.

이 항목들을 모두 합산합니다:
`하드웨어 감가상각 229 위안 + 전기세 47 위안 + 부대시설 35 위안 + 유지보수 예비비 50 위안 = 월 총 TCO 약 361 위안`.

퍼블릭 클라우드 인스턴스 1대 계약 시 수천 위안, 클러스터 계약 시 수만 위안이 드는 것과 뚜렷이 대비됩니다.

외부에 수백만 동시 접속을 보장해야 하는 환경이 아니라면, 내부 소규모 팀에게 이 장부는 충분히 설득력이 있습니다.

## 3. 모델 선택의 진실: 90퍼센트의 업무에 70B 거대 모델이 불필요한 이유

많은 팀이 클라우드 비용에 얽매이는 이유는 70B나 수천억 규모의 MoE를 도입해야만 문제를 해결할 수 있다는 맹신 때문입니다.

일상적인 사내 업무에서 고난도 수학 올림피아드 문제를 매일 풀어야 할까요.

전혀 필요 없습니다.

우리는 코드 생성, 계약서 조항 추출, 다회차 고객 응대 업무를 두고 내부 블라인드 비교 테스트를 진행했습니다.

실측 데이터는 다음과 같습니다:

| 모델 규격 및 양자화 설정 | 파일 용량 | 최소 VRAM 요구치 | 실측 생성 처리율 | 지시 수행 정확도 |
| :--- | :--- | :--- | :--- | :--- |
| **Qwen 2.5 7B Instruct Q4_K_M** | 4.68 GB | 6.5 GB VRAM | 38.5 tokens/s | 94.2% |
| **Qwen 2.5 14B Instruct Q4_K_M** | 9.24 GB | 12.0 GB VRAM | 24.2 tokens/s | 96.8% |
| **Qwen 2.5 32B Instruct Q4_K_M** | 19.8 GB | 24.0 GB VRAM 또는 통합 메모리 | 12.8 tokens/s | 97.5% |
| **Llama 3.3 70B Instruct Q4_K_M** | 42.5 GB | 48.0 GB 듀얼 GPU 구성 | 6.4 tokens/s | 98.1% |

표의 첫 번째 줄과 네 번째 줄을 대조해 보십시오:
적절한 Q4 양자화를 거친 7B 모델은 5GB 미만의 용량으로 보급형 그래픽카드에 온전히 적재되며, 초당 40토큰에 근접한 속도로 출력하고, 지시 수행 정확도는 94.2퍼센트에 달합니다.

70B로 올리더라도 정확도 상승은 4퍼센트포인트 미만에 불과합니다.

반면 장비 도입 비용은 열 배로 폭등하고 생성 속도는 초당 몇 글자 수준으로 주저앉습니다.

사용자들은 깜빡이는 커서를 보며 답답함에 발을 구르게 됩니다.

극히 드물게 발생하는 예외 처리를 위해 거대한 허영의 유지비를 계속 지불하는 것은 합리적인 엔지니어링이 아닙니다.

## 4. 로컬 배포 실전: RTX 4060 Ti와 llama.cpp를 통한 초고속 기동

Ubuntu 24.04 환경에서 경량 추론 기반으로 llama.cpp를 빌드합니다.

먼저 대상 GPU의 CUDA 아키텍처에 맞추어 소스에서 컴파일합니다:

```bash
# GPU 드라이버 및 CUDA 런타임 상태 확인
nvidia-smi

# 소스코드 복제 후 CUDA 백엔드를 활성화하여 빌드
git clone https://github.com/ggml-org/llama.cpp.git
cd llama.cpp
cmake -B build -DGGML_CUDA=ON
cmake --build build --config Release -j8
```

이어서 공식 양자화가 완료된 GGUF 가중치를 다운로드합니다:

```bash
# huggingface-cli를 사용하여 models 디렉토리에 저장
huggingface-cli download Qwen/Qwen2.5-7B-Instruct-GGUF qwen2.5-7b-instruct-q4_k_m.gguf --local-dir ./models
```

로컬 추론 서버 데몬을 구동합니다:

```bash
# Flash Attention 및 다중 슬롯을 지정하여 기동
./build/bin/llama-server \
  -m ./models/qwen2.5-7b-instruct-q4_k_m.gguf \
  --port 8080 \
  --host 0.0.0.0 \
  -ngl 99 \
  -c 32768 \
  -fa \
  --cache-type-k q4_0 \
  --cache-type-v q4_0 \
  -np 4
```

지정된 각 실행 옵션의 의미는 다음과 같습니다:
- `-ngl 99` 모델의 28개 레이어 전체를 RTX 4060 Ti의 16GB VRAM에 완전 오프로드합니다;
- `-c 32768` 단일 세션의 최대 컨텍스트 길이를 32k 토큰까지 확장합니다;
- `-fa` Flash Attention을 강제 활성화하여 중간 어텐션 텐서의 과도한 할당을 차단합니다;
- `--cache-type-k q4_0` 및 `--cache-type-v q4_0` KV 캐시를 4비트로 압축합니다;
- `-np 4` 사내 여러 클라이언트의 동시 호출을 처리하기 위해 4개의 슬롯을 분할 할당합니다.

터미널에서 응답성과 처리 속도를 검증합니다:

```bash
curl http://localhost:8080/v1/chat/completions \
  -H "Content-Type: application/json" \
  -d '{
    "model": "qwen2.5-7b-instruct",
    "messages": [
      {"role": "system", "content": "당신은 Linux 성능 분석 전문가입니다."},
      {"role": "user", "content": "페이지 폴트와 Swap 스래싱 방지 방안을 설명해 주세요."}
    ],
    "temperature": 0.2
  }'
```

단일 접속 환경에서 첫 번째 토큰 응답 시간은 약 170밀리초, 이후 텍스트 생성 속도는 초당 38.6토큰으로 안정되었습니다.

내 자리 책상 밑에서 이 정도 응답 속도가 나온다면 일상적인 업무에 부족함이 없습니다.

## 5. 트러블슈팅의 교훈: GQA 캐시 계산의 함정과 OOM 분석

메모리 튜닝 과정에서 저 역시 전형적인 이론 계산 오류에 빠졌습니다.

### 5.1 쿼리 헤드 수로 캐시를 계산한 오산

테스트 첫날, 동료가 가져온 28,000단어 분량의 계약서를 전달하자마자 화면에 VRAM 고갈 오류가 출력되었습니다:

```text
CUDA error: out of memory
  current allocated: 15.38 GB, max allocated: 15.82 GB
  failed to allocate 256.00 MB for KV Cache tensor
Aborted - core dumped
```

저는 처음에 Qwen 2.5 7B의 28개 어텐션 헤드 전체가 캐시를 유지한다고 착각하여, 토큰당 392KB, 32k에서 12GB에 달할 것으로 오판했습니다.

그러나 모델 저장소 내 `config.json` 파일을 확인하고 설계를 파악했습니다.

Qwen 2.5 7B는 GQA [Grouped Query Attention] 구조를 적용했습니다:
- `num_attention_heads = 28` 쿼리 헤드 수;
- `num_key_value_heads = 4` 실제 KV 캐시 헤드 수;
- `head_dim = 128` 단일 헤드 차원 수;
- `num_hidden_layers = 28` 총 레이어 수.

FP16 정밀도에서 단일 토큰의 실제 물리적 KV 캐시 크기는 다음과 같습니다:
`2 × 28 × 4 × 128 × 2 바이트 = 57,344 바이트 ≒ 56 KB`.

단일 세션에서 32k 컨텍스트를 채우더라도 이론치는 불과:
`32000 × 56 KB ≒ 1.75 GB`.

단일 세션에 1.75GB면 충분한데 왜 16GB VRAM이 폭발했을까요.

튜닝 없이 4개 슬롯의 동시 유입을 그래픽카드가 감당할 수 있을까요.

해답은 실행 매개변수의 `-np 4`에 있었습니다.

Flash Attention과 KV 양자화가 없는 상태에서 4개 슬롯의 FP16 풀이 사전에 확보되어:
`4 × 1.75 GB = 7.0 GB`.

7GB의 KV 캐시에 모델 가중치 4.68GB, CUDA 런타임, 그리고 비연속적인 메모리 파편화가 누적되어 전체 요구량이 즉시 15.5GB를 초과했습니다.

해결책은 실행 명령에 포함된 두 가지 설정이었습니다:
첫째, `-fa` 플래그를 추가하여 Flash Attention을 활성화하는 것;
둘째, `--cache-type-k q4_0 --cache-type-v q4_0`을 지정하는 것.

Key와 Value를 4비트로 압축하자 토큰당 캐시가 약 14KB로 줄어들었고, 4개 슬롯이 32k를 가득 채워도 총 1.75GB 안팎에 수렴했습니다.

상주 VRAM 사용량은 8.2GB 선으로 내려앉았습니다.

다중 세션 동시 처리 시에도 메모리 부족 오류는 다시 발생하지 않았습니다.

안도감이 밀려왔습니다.

### 5.2 Swap 과열로 인한 NVMe 스로틀링 절벽

또 다른 뼈아픈 실수는 경량 노트북 테스트에서 발생했습니다.

16GB 메모리 노트북에서 Swap을 활용하여 32B 모델을 구동했을 때, 처음 몇 분 동안은 초당 8토큰을 유지했습니다.

그러나 4분이 경과하자 생성 속도가 갑자기 초당 0.5글자로 폭락하며 마우스 조작이 멈추었습니다.

스토리지 센서 정보를 확인했습니다:

```bash
# NVMe 컨트롤러 동작 온도 확인
smartctl -a /dev/nvme0n1 | grep Temperature
```

출력된 컨트롤러 온도는 76도에 달했습니다.

76도의 고온에 SSD를 방치하고 싶은 엔지니어가 있을까요.

구리 히트싱크와 냉각 팬이 없는 경량 하우징에서 과도한 페이징은 75도 한계 온도에 즉시 부딪힙니다.

드라이브 펌웨어가 칩 보호를 위해 강제 스로틀링을 발동했고, IOPS 성능이 80퍼센트 이상 깎여나갔습니다.

방열 설계가 없는 가벼운 기기에서 가상 메모리로 거대 모델을 돌리는 것은 하드웨어를 손상시킬 뿐 실용성이 없습니다.

## 6. 현실적인 선택 기준과 의사결정 체크리스트

매개변수와 비용 검증을 마친 후 우리는 세 가지 명확한 기술적 경계선에 도달했습니다:

- **첫 번째 기준: 8GB 메모리 경량 노트북 또는 구형 PC**
  3B 또는 7B Q4 모델에 집중하십시오. 컨텍스트 길이는 4096토큰 이내로 제한하십시오. SSD Swap으로 32B 모델을 돌린다는 인터넷 글을 믿지 마십시오. 과열로 인한 성능 저하로 실사용이 불가능합니다.

- **두 번째 기준: 12GB에서 16GB VRAM을 갖춘 데스크톱**
  RTX 4060 Ti 16GB가 최적의 가성비 구간입니다. 7B 또는 14B 모델에 양자화 캐시와 Flash Attention을 조합하면, 5명에서 15명 규모 팀의 사내 일상 업무를 월 TCO 400위안 [약 7만 원] 미만으로 안정적으로 처리할 수 있습니다.

- **세 번째 기준: 퍼블릭 클라우드와 상용 API를 선택해야 하는 조건**
  고객 계약에서 99.99퍼센트의 SLA 가동률을 보장해야 하거나, 수천 명 규모의 돌발 동시 트래픽이 예상되거나, 엄격한 데이터 규정 준수 및 다중 리전 백업이 필수인 경우에는 망설이지 말고 대형 퍼블릭 클라우드나 공식 기업용 API를 채택해야 합니다. 엣지 자체 구축은 예측 가능한 사내 비용을 통제하고, 클라우드는 탄력성과 위험 대비를 담당합니다.

GPU 연산 자원의 품귀 현상은 거대 자본이 움직이는 거시적 현상이며, 은행 계좌에서 빠져나가는 매월의 청구서야말로 각자의 미시적 현실입니다.

동시 접속 피크, 실제 컨텍스트 길이, 장비 감가상각, 그리고 소비전력을 정확히 계산한다면, 불안감에 휩쓸리지 않고 명확한 아키텍처를 선택할 수 있을 것입니다.
