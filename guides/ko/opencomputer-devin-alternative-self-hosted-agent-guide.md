저희 개발팀은 작년에 Devin을 직접 도입하여 검증해 보았습니다.

사용자 경험은 솔직히 놀라웠습니다. Slack 채널에 요구사항을 던지면 스스로 가상 환경을 띄우고 테스트를 수행한 뒤 Pull Request를 올려주었습니다.

다시는 이전 방식으로 돌아갈 수 없을 것 같았습니다.

하지만 라이선스 갱신 시점이 되자 재무팀에서 연락이 왔습니다.

계정 하나당 월 500달러.

개발자 10명 기준 연간 6만 달러였습니다. 이 예산이면 최고 사양의 RTX 4090 워크스테이션을 두 대 구매하고도 돈이 남습니다.

도대체 그 막대한 비용이 어디로 들어가는지 납득하기 어려웠습니다. 임시 샌드박스 가상 머신의 순수 연산비인지, 아니면 폐쇄형 독점 소프트웨어의 좌석세일 뿐인지 의문이 가시지 않았습니다.

결국 저희는 자체 인프라를 구축하기로 결심했습니다.

비용 문제보다 더 심각했던 것은 데이터 보안과 컴플라이언스였습니다.

회사의 핵심 비즈니스 코드가 모두 닫힌 클라우드로 전송됩니다. 어떤 물리 서버에서 실행되는지, 라이브러리 설치 스크립트가 권한을 탈취하지는 않는지, 실행 로그가 언제까지 보관되는지 아무도 명확하게 답변해 주지 못했습니다.

오픈소스 진영에서도 대안을 모색하려는 시도는 있었습니다. 초기 OpenDevin과 다양한 로컬 쉘 스크립트를 테스트해 보았지만, 실무 환경에서는 심각한 기술적 한계에 부딪혔습니다.

호스트 OS 환경을 망가뜨리거나, 과거 전화선 모뎀 접속처럼 응답이 느려 터지는 식입니다.

어제 GitHub에 오픈소스로 공개된 OpenComputer는 지극히 실용적인 해법을 제시했습니다.

저장소 주소는 `https://github.com/diggerhq/opencomputer`이며, Apache 2.0 라이선스를 따릅니다.

자체 호스팅 가상 머신에서 Devin 대비 PR 생성 속도를 3.3배까지 끌어올렸다고 발표했습니다.

이 아키텍처는 실제로 어떻게 설계되었으며 과장된 마케팅은 없는지, 게이트웨이 코드를 분석하고 로컬 가상 환경에서 실측 검증을 진행했습니다.

## 1. 기존 클라우드 기반 Agent는 왜 답답할 정도로 느렸을까?

코딩 에이전트 최적화를 시도하는 엔지니어들은 종종 인지적 함정에 빠집니다.

에이전트가 느린 이유가 LLM 모델의 토큰 생성 속도가 느리기 때문이라고 단정하는 것입니다.

저 역시 한때 이 착각에 빠졌었습니다.

응답 속도를 높이기 위해 가장 가벼운 경량 모델로 교체해 보았지만, 간단한 명령어 하나를 전달해도 터미널 커서는 여전히 30초 이상 멈춰 있었습니다.

병목이 정말 모델 추론 속도에 있었을까요?

전혀 아니었습니다.

실제 코딩 작업 파이프라인에서 가장 많은 시간을 낭비하는 주범은 환경의 콜드 스타트와 네트워크 I/O 왕복입니다.

기존 클라우드 에이전트의 워크플로우는 지나치게 무거웠습니다.

작업을 수신합니다.

원격 오브젝트 스토리지에서 스냅샷을 내려받습니다.

새로운 마이크로 가상 머신을 콜드 부팅합니다.

공용 네트워크를 통해 소스 저장소를 다시 클론합니다.

의존성 설치 스크립트를 처음부터 실행합니다.

코드를 수정하고 마지막으로 전체 가상 환경을 묶어 원격 스토리지로 업로드합니다.

이 과정만으로도 2분에서 3분이 훌쩍 지나갑니다.

10초 이상 멍하니 기다려야 하는 환경에서 개발자의 집중력이 온전히 유지될 수 있을까요?

불가능합니다.

사람의 작업 컨텍스트는 순식간에 휘발됩니다. 브라우저의 다른 탭을 열거나 메신저에 답장하는 순간 머릿속 설계도는 지워집니다.

다시 화면으로 돌아왔을 때, 에이전트는 엉뚱한 가정을 바탕으로 폭주하며 대여섯 개 파일의 구조를 엉망으로 망쳐 놓기 일쑤입니다.

그 난장판을 수습하는 비용은 결국 사람의 몫입니다.

OpenComputer 개발팀은 이 지점을 정확히 짚었습니다. 즉각적인 상호작용성을 상실한 에이전트는 결국 비동기 배치 작업 도구로 전락합니다.

노트북 로컬 환경의 Claude Code처럼 매끄러운 반응성을 얻기 위해서는, 실행 환경을 디스크 가장 가까운 곳으로 끌어내려야 합니다.

## 2. 역방향 게이트웨이 Calvin：인바운드 포트를 열지 않아도 되는 원리

자체 호스팅 에이전트를 사내 프라이빗 클라우드나 사내 전산실 서버에 배포할 때 가장 큰 장벽은 보안 부서의 정책 검토입니다.

외부 공격 노출 표면을 어떻게 통제할 것인가.

기존 오픈소스 도구들은 외부 Webhook 알림을 수신하기 위해 방화벽 인바운드 포트를 열거나 터널링 솔루션을 설치하도록 요구했습니다.

공용 인터넷을 향해 포트가 개방되는 순간, 비인가 스캔과 권한 침해 위험은 피할 수 없습니다.

공인 IP가 반드시 필요하다는 생각은 오랜 고정관념이었습니다.

아웃바운드 장기 연결 방식을 구현해 본 뒤에야 깨달았습니다. 협업의 본질은 메시지를 수신하는 데 있지, 외부에서 나를 찾아내도록 주소를 노출하는 데 있지 않다는 점입니다.

OpenComputer의 핵심 게이트웨이는 Calvin이라고 불립니다.

설계 철학은 매우 단순합니다. 가상 머신은 인바운드 수신 포트를 단 하나도 열지 않습니다.

시스템은 역방향 WebSocket 기반의 아웃바운드 연결을 사용합니다.

조율 레이어는 Cloudflare Workers와 Durable Objects에 배포되어 가벼운 메시지 중계와 라우팅만 처리합니다.

프라이빗 네트워크 내부의 가상 머신은 기동 시 Cloudflare 엣지 노드를 향해 선제적으로 아웃바운드 WebSocket 연결을 맺습니다.

개발자가 Slack 채널에서 `@Computer`를 호출하여 작업을 지시하면, Slack의 Webhook 이벤트는 Cloudflare Workers로 전달됩니다.

Workers는 미리 수립된 역방향 WebSocket 채널을 통해 지침을 사내 가상 머신의 Calvin 게이트웨이로 내려보냅니다.

방화벽에서는 아웃바운드 443 포트 통신만 허용하면 충분합니다.

사설 VPC 서브넷, 사내 NAT 내부망, 고정 공인 IP가 없는 워크스테이션 환경에서도 밀리초 단위로 외부 작업 요청에 즉각 응답합니다.

외부 해커가 인터넷 전체를 스캔하더라도 열려 있는 포트를 단 하나도 발견할 수 없습니다.

## 3. rootless Podman 격리：단일 머신 로컬 NVMe의 대역폭 활용

지침이 가상 머신 내부로 들어오면 다음 기술적 과제가 발생합니다. 코드 실행 환경을 어떻게 안전하게 격리할 것인가.

호스트 OS 위에서 코드를 직접 실행할 수는 없습니다.

자율 에이전트가 오동작하여 파괴적인 명령어를 실행하면 운영체제 전체가 붕괴할 수 있기 때문입니다.

그렇다고 무거운 하이퍼바이저 기반 가상화를 쓰기에는 기동 속도가 너무 느립니다.

OpenComputer의 선택은 rootless Podman 컨테이너였습니다.

Slack 스레드마다 권한이 없는 독립 컨테이너 인스턴스가 1 대 1로 생성됩니다.

주목할 만한 엔지니어링 설계는 세 가지입니다.

첫째, 비특권 사용자 공간 격리입니다. 컨테이너 내부 프로세스가 탈출을 시도하더라도 호스트 관점에서는 권한이 없는 일반 시스템 계정에 불과하여 커널 설정을 바꾸거나 다른 세션의 데이터를 건드릴 수 없습니다.

둘째, 로컬 물리 디스크 우선 저장입니다. 코드 분석과 빌드 과정에서 발생하는 모든 임시 파일은 가상 머신의 로컬 고속 NVMe SSD에 직접 기록되며, 지연율이 높은 네트워크 파일 마운트를 우회합니다.

셋째, Git 기반 증분 스냅샷 이중 백업입니다. 작업 단계가 완료될 때마다 변경 사항이 로컬 Git 저장소에 커밋되어 버전을 고정하고 비동기로 원격 동기화됩니다.

Ubuntu 24.04 머신에서 실측한 결과, 지시 수신부터 Podman 컨테이너 마운트 완료까지 380밀리초 내외가 소요되었습니다.

기본 런타임 레이어가 사전에 캐시되어 있어, 매번 가상 머신을 콜드 부팅하던 기존 방식과 비교할 수 없을 정도로 민첩하게 동작합니다.

```bash
# Podman rootless 런타임을 지정하여 Calvin 게이트웨이 기동
calvin-gateway --runtime podman --isolation rootless --max-concurrent 4
```

## 4. 실전 시나리오 검증：최소 재현 프로젝트에서의 디버깅 워크플로우

아키텍처 구조도만 살펴보는 것으로는 부족합니다.

Node 환경의 전형적인 비동기 메모리 누수 진단 시나리오를 바탕으로 실측을 진행했습니다.

외부 네트워크 변수를 배제하기 위해 이벤트 리스너와 캐시 해제 로직을 포함한 최소 재현 테스트 프로젝트를 구성했습니다.

베이스 이미지를 사전 캐싱한 컨테이너 환경에 저장소 접근 권한을 부여하고, Slack 테스트 채널에 메시지를 전송했습니다.

```text
@Computer 지속적인 부하 테스트 시 메모리가 해제되지 않고 증가합니다. leak_detector.js를 분석하여 수정하고, npm test 통과 확인 후 PR을 생성하세요.
```

메시지를 전송했습니다.

약 4초 뒤, Slack 채널에 `@Computer`의 확인 카드가 도착했습니다.

왜 이렇게 빠를까요?

기본 Node 런타임과 의존 패키지들이 Podman 볼륨 내에 이미 사전 마운트되어 있었기 때문입니다. 외부 재다운로드 단계를 건너뛰고 즉시 브랜치를 체크아웃하여 정적 분석에 착수했습니다.

약 15초 뒤, 스레드에 구체적인 진단 스택 트레이스가 보고되었습니다.

`leak_detector.js` 내부의 글로벌 이벤트 리스너가 연결 종료 시점에 정상적으로 등록 해제되지 않아 클로저 참조가 힙 메모리에 영구 잔류하고 있음을 정확히 포착했습니다.

제시된 패치는 깔끔했으며, `cleanup` 훅 함수 내부에 리스너 해제 로직이 추가되었습니다.

이후 십여 초 뒤 자동으로 실행된 `npm test`가 모두 통과되었고, GitHub 저장소에 표준 Pull Request 링크가 자동으로 생성되었습니다.

지시 하달부터 PR 생성까지 전체 워크플로우는 약 35초가 소요되었습니다.

## 5. 3.3배 성능 향상의 측정 조건과 실질적인 분석

공식 문서에서는 Devin 대비 3.3배 빠르다고 주장합니다.

측정 조건을 명확히 공개하지 않은 수치는 기술적으로 무의미합니다.

저희 테스트 환경은 8코어 16GB 메모리의 ThinkCentre 데스크톱에 1TB NVMe SSD를 장착하고 사내 500Mbps 회선에 연결한 구성이었습니다. `expressjs/express`, `node-fetch/node-fetch`와 같이 성숙한 테스트 스위트를 갖춘 프로젝트를 대상으로 4가지 수정 작업을 각각 3회씩 측정하여 중앙값을 산출했습니다.

OpenComputer 환경에서는 Slack 작업 지시부터 PR 생성까지 중앙값 56초, 첫 번째 푸시 응답까지 24초를 기록했습니다.

Devin 환경에서는 전체 프로세스 완료까지 185초가 소요되었습니다.

하지만 이 3.3배라는 수치에 대해 저는 개인적인 유보 의견을 갖고 있습니다.

Devin은 폐쇄형 서비스이므로 당시 백엔드에서 어떤 모델 티어가 작동 중이었는지, 사전 컨테이너 예열이 적용되었는지 외부에서 통제하여 검증할 수 없습니다.

테스트 당일 저희 회선에서도 일시적인 네트워크 지터가 발생하여 해당 이상치 데이터는 폐기하고 재측정하기도 했습니다.

엄밀히 말해 3.3배는 저희의 특정 하드웨어와 비교적 양호한 네트워크 조건에서 관측된 결과이며, 최상단 수치로 측정되었을 가능성이 큽니다.

실제 업무 환경에서의 체감 격차는 2배 안팎으로 수렴할 것으로 봅니다. 로컬 NVMe 기반 빌드 시간 절감 효과는 네트워크 조건이 열악한 환경일수록 도드라지며, 초고속 클라우드 전용선 환경에서는 격차가 줄어들기 마련입니다.

## 6. 실제로 마주친 3가지 장벽과 도입 시 고려사항

자체 호스팅 구축은 결코 마법이 아닙니다. 공식 문서에 자세히 적혀 있지 않은 문제들에 저 역시 차례대로 부딪혔습니다.

첫 번째 장벽은 현재 Slack 생태계에 강하게 결속되어 있다는 점입니다.

Calvin 게이트웨이는 Slack을 기본 연동 대상으로 삼고 있습니다. 개발팀이 Discord, Teams, 잔디 등을 사용하고 있다면 현재로서는 공식 어댑터가 존재하지 않습니다. 프로토콜에 맞춰 직접 이벤트 중계 계층을 작성해야 합니다.

두 번째 장벽은 rootless Podman의 호스트 권한 설정 난이도입니다.

Ubuntu 환경에서 rootless Podman을 구동하려면 호스트의 `subuid`와 `subgid` 매핑 범위를 올바르게 구성하고 cgroups v2를 활성화해야 합니다.

초기 기동 시 AppArmor 보안 정책에 의해 볼륨 마운트가 차단되며 디바이스 노드를 찾을 수 없다는 에러가 발생했습니다. 권한 설정을 바로잡는 데만 30분 이상을 소모했습니다.

```bash
# 실행 계정에 충분한 하위 UID 매핑 범위를 할당
sudo usermod --add-subuids 100000-165535 --add-subgids 100000-165535 devin-agent
# 로그아웃 상태에서도 데몬 프로세스가 유지되도록 설정
sudo loginctl enable-linger devin-agent
```

세 번째 장벽은 모델 추론 토큰 비용은 여전히 사용자 부담이라는 사실입니다.

OpenComputer가 해결하는 영역은 에이전트의 컨테이너 샌드박스, 협업 파이프라인, 자동화 워크플로우입니다. 모델 추론 크레딧을 무상으로 지원하는 것은 아닙니다.

환경설정 파일에 Anthropic이나 OpenAI의 API 키를 등록하거나 호환되는 오픈소스 프록시를 연동해야 합니다.

에이전트가 테스트 실패와 자율 수정을 반복하는 루프에 빠지면 토큰 청구 비용은 고스란히 개발팀의 몫으로 청구됩니다.

절감되는 것은 비싼 소프트웨어 좌석 라이선스 비용이지, 기저의 물리적 연산 비용이 아닙니다.

모델 선정에 따른 실패도 직접 경험했습니다. 초기에 가벼운 소형 모델로 버그 수정을 시도했을 때, 생성된 코드 diff를 세 번 검토하고도 신뢰할 수 없어 결국 롤백했습니다.

추론 능력이 Claude 3.5 Sonnet, GPT-4o, DeepSeek V3와 같은 최상위 티어에 미치지 못한다면, 에이전트가 코드를 건드릴수록 기술 부채만 가중될 뿐입니다.

블랙박스를 열고 코드와 실행 환경의 주권을 자체 인프라로 되찾아오는 것은 분명 매력적인 선택지입니다.

하지만 컨테이너 권한 관리부터 네트워크 안정성, 모델 비용 모니터링에 이르기까지 모든 엔지니어링 디테일을 개발팀 스스로 책임질 준비가 되어 있어야 합니다.
