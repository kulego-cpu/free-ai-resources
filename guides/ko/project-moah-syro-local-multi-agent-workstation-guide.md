# 파편화된 기억과의 작별: Project Moah와 Syro로 구축하는 순수 로컬 멀티 Agent 협업 워크스테이션

16GB 메모리 노트북 한 대에서 두세 개의 명령줄 코딩 에이전트를 동시에 지휘하면 현실적인 한계가 즉시 드러납니다.

냉각 팬이 맹렬하게 돕니다. 스로틀링이 걸립니다. 터미널 커서 입력 반응도 눈에 띄게 둔해집니다. 작업을 편하게 하려고 대형 에디터 창을 서너 개 띄우고 각 창의 터미널에서 에이전트를 돌리는 경우가 흔합니다. 이런 작업 방식은 시스템 응답성을 순식간에 떨어뜨립니다.

추론이 길어질수록 바탕에 깔린 Chromium 렌더러 프로세스와 확장 플러그인이 3.8GB 이상의 물리 메모리를 집어삼킵니다. 스왑 영역 쓰기가 폭증하고 디스크 부하가 위험 수준에 도달합니다. 에이전트 병렬 협업을 하려면 반드시 고가의 워크스테이션이 필요한 것일까요.

하드웨어 제약보다 더 심각한 것은 에이전트 간의 완벽한 인지 고립입니다.

왼쪽 터미널의 Claude Code는 인증 모듈을 재설계하여 토큰 검증 방식을 세션 상태에서 무상태 서명으로 바꾸었습니다. 반면 오른쪽의 Codex는 주문 테스트 코드를 작성하고 있으며, 직전의 구조 변경을 알지 못해 이미 폐기된 구형 세션 mock 코드를 가득 생성합니다. 각자의 블랙박스 안에서 따로 달리다가 Git 병합 단계에서 47건의 문법 충돌을 던집니다.

흔히 쓰는 해결책은 공용 Markdown 문서를 던져주는 것입니다. 하지만 평문 텍스트는 디스크에 놓인 정적 문자열에 불과합니다. 수천 줄의 문서를 매번 처음부터 다시 읽으면 토큰 비용만 낭비됩니다.

진퇴양난. 파편화된 기억과 과도한 자원 소비 사이에서 어떻게 돌파구를 찾아야 할까요.

핵심 해결책은 두 가지입니다. 데스크톱 작업대는 무거운 외피를 완전히 벗겨내야 하며, 지식 공유 중추는 가중치 기반 그래프 구조로 인과관계를 순환시켜야 합니다.

## 탈 Electron의 고집: Syro의 Worktree 네이티브 작업대 편성

다중 에이전트의 터미널 혼잡을 줄이기 위해 많은 개발자가 시각화 도구를 찾습니다. 기존 관리 도구들은 어떤 모습일까요.

대부분 Webview 기반 래퍼 앱입니다. 상주 메모리만 수백 메가바이트를 차지하며 여러 개를 띄우면 멈춥니다. 가벼운 대안은 늘 존재해 왔습니다.

오픈소스 생태계에서 개발자 osdodo는 불필요한 군더더기를 철저히 제거한 Syro를 공개했습니다.

GitHub 저장소:
https://github.com/osdodo/syro

이 도구는 Electron, Chromium, Node 런타임을 완전히 배제했습니다. Rust 언어와 GPUI 그래픽 라이브러리로 직접 구축되었습니다. 고속 에디터에 익숙한 분들에게 GPUI는 낯설지 않습니다. 운영체제 그래픽 인터페이스와 직접 통신합니다. 콜드 스타트 시간은 얼마나 걸릴까요. 0.2초 미만입니다. 대기 시 상주 메모리는 48MB 수준에 불과합니다.

왜 Syro는 멀티 에이전트 협업에 자연스럽게 들어맞을까요.

핵심은 바인딩입니다. 작업대 관리를 Git Worktree 네이티브 메커니즘에 직접 묶었습니다. 기존 병렬 작업에서는 checkout 전환을 반복하거나 저장소를 여러 개 복제했습니다. 커밋되지 않은 변경 사항이 충돌하고 디스크 공간이 낭비됩니다. 그런 수고를 계속 감당해야 할까요.

Syro의 해결책은 명확합니다. 단일 기본 저장소를 유지하면서 기능별 Worktree 디렉터리를 병렬 생성합니다. Syro의 단일 창 안에서 각 Worktree는 독립된 컨텍스트를 가진 병렬 작업대가 됩니다.

화면에서 전용 터미널, 파일 트리, 변경 차이, 명령어 기록을 나란히 관찰할 수 있습니다. 세 가지 핵심 상태 표시등이 지원됩니다:

- 실행 중: 에이전트가 추론, 파일 수정, 로컬 테스트를 진행 중인 상태;
- 대기 중: 현재 작업이 끝나 CPU와 메모리가 쉬고 있는 상태;
- 입력 대기: 민감한 쓰기 작업 전 사람의 확인 입력을 기다리는 상태.

세 표시등이 나란히 배치됩니다. 화면을 한 번 훑어보면 어느 작업대가 돌고 있고 어느 작업대가 키 입력을 기다리는지 한눈에 보입니다.

하지만 현실적인 한계도 명확히 짚어야 합니다. GitHub 스타 수가 1개에 불과한 초기 개인 도구입니다. macOS 15.1 이상에 최적화되어 있으며 Windows 빌드는 제공되지 않습니다. 외장 고해상도 디스플레이 연결 시 뷰포트 문제로 비정상 종료되거나 수천 줄의 로그 출력 시 1.5초가량 멈추는 현상이 확인되었습니다. 설정 변경 시 재시작이 필요합니다. 비 macOS 환경에서는 tmux와 Git Worktree 스크립트를 조합하는 방식이 확실한 대안입니다.

## 인지 그래프 순환: Project Moah가 해결하는 흩어진 메모 문제

물리적 작업 공간이 분리된 후 에이전트들은 어떻게 하나의 두뇌를 공유할까요.

평문 메모의 치명적인 약점은 인과관계 결핍입니다. 특정 데이터 필드가 폐기 처리되었다면, 직접적인 원인은 일주일 전의 샤딩 결정이고 간접 영향은 하위 엔드포인트의 직렬화 제거입니다. 단순 키워드 검색으로는 이런 연결망을 파악하기 어렵습니다.

개발자 Namache가 공개한 Project Moah는 이를 해결하는 로컬 두뇌입니다:
https://github.com/Namache/project-moah

MIT 라이선스로 배포되며 로컬 환경에서 구동되고 표준 MCP를 통해 에이전트와 통신합니다. 데이터는 로컬 SQLite에 보관되며 Windows, Debian, Ubuntu, Fedora를 지원합니다.

히브리어로 Moah는 뇌를 뜻합니다. 평문 폴더 방식을 버리고 네트워크 위상 구조로 재편성합니다:

```text
Project Moah 그래프 전파 계산 규칙:

1. 선반 계층 활성화:
   Knowledge > Architecture > Authentication
   현재 작업과 일치하는 선반만 깨어나고 무관한 노드는 깊이 잠듭니다.

2. 다단계 홉 감쇠:
   1 홉 연관도 = 기본 링크 가중치 × 확신도
   n 홉 연관도 = 기본 링크 가중치 × 확신도 × 0.85의 n-1 제곱

3. 독립 경로 확률 합산:
   서로 다른 두 경로가 같은 규칙을 가리키고 각 확률이 0.5일 때:
   통합 연관도 = 1 - (1 - 0.5) × (1 - 0.5) = 0.75
   이론적 한계는 1.0에 무한히 수렴하지만 100% 만점은 주지 않습니다.

4. 동적 링크 가중치 가감:
   테스트 통과에 기여한 채택: 가중치 +0.08
   문법 오류를 유발한 채택: 가중치 -0.08
   30일간 참조되지 않은 연결: 자동으로 감쇠되어 제외됩니다.
```

지식은 트리 형태의 선반에 보관됩니다. 결제 로직을 작성할 때 오디오 드라이버 규칙은 호출되지 않습니다. 무관한 선반이 잠들어 있어 컨텍스트를 소모하지 않습니다.

다단계 감쇠 알고리즘은 정밀하게 작동합니다. 인접 노드는 가중치를 유지하지만 단계가 멀어질수록 0.85 배수로 연관도가 떨어집니다.

복수의 추론 경로가 동일 규칙에 도달하면 독립 확률 모델로 결합합니다. 두 경로가 0.5를 제시할 때 통합 점수는 0.75입니다. 왜 1.0 만점을 주지 않을까요. 확률 그래프에 절대적 진리는 없으므로 여유 공간을 남겨 과도한 확신으로 인한 오류를 방지합니다.

통합 연관도가 0.20 미만으로 떨어지면 컨텍스트 묶음에서 자동 제외됩니다.

톰슨 샘플링도 실무적 가치가 큽니다. 탐색 기능을 켜면 과거 강한 링크뿐 아니라 낮은 확률로 주변 노드도 탐색합니다.

실제 검증에서 구체적인 가중치 변화를 확인했습니다. Claude Code가 비호환 서명 검증 알고리즘을 도입하여 단위 테스트에서 14건의 AssertionError가 발생했습니다. Moah는 실패 신호를 포착하고 해당 노드의 가중치를 0.08 차감하여 0.50에서 0.42로 낮췄습니다. 이후 Codex가 구형 호환 선반을 찾아 테스트를 통과시키자 가중치가 0.08 더해져 0.58로 복귀했습니다. 이 메커니즘은 고정된 정적 문서보다 개발 현장의 실제 피드백에 훨씬 부합합니다.

## 일탈 방지: 규칙 잠금과 체크포인트

공유 두뇌가 있어도 에이전트가 사고를 칠 수 있을까요.

권한 밖의 수정은 얼마든지 일어날 수 있습니다. 코딩 에이전트의 가장 위험한 문제는 코드를 못 짜는 것이 아니라 기반 아키텍처 규칙을 제멋대로 고치는 점입니다.

예외 처리는 공통 인터셉터를 거치도록 지침을 내려도, 타입 오류에 직면한 에이전트가 편의를 위해 기반 예외 클래스를 수정해 스택 트레이스를 숨겨버리는 경우가 발생합니다.

Project Moah는 인간 아키텍트에게 최종 방어선을 제공합니다. 그것이 규칙 잠금입니다.

핵심 원칙은 등록 시 잠금 표기를 할 수 있습니다. 잠긴 노드에 대해 에이전트는 읽기 전용 권한만 갖습니다. 임의 수정은 불가능합니다.

수정을 원할 경우 MCP를 통해 인간의 전용 Inbox로 개정안을 제출해야 합니다.

경계는 명확합니다. 사유, 이점, 잠재 영향 범위를 적어 제출하고 인간이 화면에서 승인해야 비로소 노드가 변경됩니다.

체크포인트 기능 역시 장기 작업 인수인계를 매끄럽게 돕습니다.

상용 모델 토큰이 바닥났을 때 새 터미널에서 처음부터 배경을 다시 설명하는 작업은 시간 낭비입니다.

Moah에서는 중요 단계를 체크포인트로 저장할 수 있습니다. 미완료 작업, 확정된 결정, 지식 그래프가 통째로 보관됩니다.

메인 모델이 기반을 잡은 후 경량 오픈 모델이 동일 체크포인트에 연결되어 이전 맥락 설명 없이 단위 테스트 작성을 이어갑니다.

## 실전 구축: MCP 연결부터 Worktree 2면 운용까지

구축 과정은 단순하며 15분 이내에 끝납니다. 16GB 메모리의 일반 개발 환경을 기준으로 합니다.

1단계: Project Moah 데몬을 실행합니다. 백그라운드에 상주하며 로컬 MCP 인터페이스를 엽니다. 에이전트 설정 파일에 선언을 추가합니다:

```json
{
  "mcpServers": {
    "project-moah": {
      "command": "moah",
      "args": ["serve", "--local-db", "/Users/cool/data/moah-brain.db"]
    }
  }
}
```

설정 후 구동 시 그래프 DB가 자동 감지되어 조회 및 제안 도구가 활성화됩니다.

2단계: Git 명령으로 분리 디렉터리를 생성합니다:

```bash
git worktree add ../freeai-cache-layer feature/cache-opt
git worktree add ../freeai-e2e-suite feature/e2e-test
```

저장소 기반은 동일합니다. 상위 경로에 두 개의 폴더가 생기며 커밋 기록을 공유하면서 브랜치 작업 트리가 완전히 분리됩니다.

3단계: Syro 창을 열고 좌우 분할 화면에 위 두 Worktree를 연결합니다. 왼쪽에 Claude Code, 오른쪽에 Codex를 배치합니다.

두 에이전트 병렬 구동 시 자원 소모는 어떨까요.

측정 결과는 명확합니다. Syro 인터페이스의 상주 메모리는 48MB 미만입니다. 무거운 렌더링 레이어를 배제했기 때문에 양쪽에서 빌드를 돌려도 시스템 전체 메모리 점유율은 9.2GB 이하로 안정 유지됩니다.

왼쪽 에이전트가 캐시 설계를 변경하면 Moah에 결정 사항이 기록됩니다. 오른쪽 에이전트는 0.85 감쇠 계산을 통해 변경된 규격을 감지하고 테스트를 자동 조정합니다. 인간이 문서를 복사해 나를 필요가 없습니다.

## 현실적 한계: 무조건적인 자동화 만능 도구가 아니다

이 아키텍처는 완전무결할까요.

그렇지 않습니다. 공짜 점심은 없습니다. 현실적인 주의 사항을 숙지해야 합니다.

첫째, 지식 베이스의 초기 진입 비용입니다. 빈 데이터베이스를 주면 감쇠 계산도 선반 선별도 작동하지 않습니다. 초기에 인간 아키텍트가 최소 15개 이상의 핵심 설계 원칙을 입력해야 뼈대가 갖춰집니다.

둘째, 그래프 관리의 규율입니다. 자잘한 코드 변경까지 무차별 등록하도록 두면 데이터베이스는 며칠 만에 노이즈로 오염됩니다. 신뢰도가 떨어진 노드를 정기적으로 정리하는 작업은 필수적입니다.

도구의 진화는 개발 생산성을 높이기 위함이지 인간이 설계 판단을 포기하기 위함이 아닙니다. Syro는 하드웨어 자원을 지키고 Project Moah는 다중 브랜치 간의 일관성을 지킵니다.

이 두 가지를 지켜낼 때 멀티 에이전트 편대는 제 몫을 다합니다. 다중 브랜치 병렬 협업 환경에서 당신의 로컬 설정은 실제 부하를 견뎌낼 준비가 되어 있습니까?
