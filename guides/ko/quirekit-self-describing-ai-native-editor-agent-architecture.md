# 50개 Tiptap 확장을 Function Calling에 밀어 넣고 통과율 48%에 그친 이유：QuireKit의 list/explain/call 리팩터링 기록

AI 기반 리치 텍스트 에디터를 개발하는 팀들은 대개 비슷한 난관에 봉착합니다。

에디터에 AI copilot을 붙여 서식 지정、표 생성、제목 계층 수정을 자동화하려 할 때、누구나 가장 먼저 떠올리는 방법은 기존 확장 기능을 하나씩 Function Calling 도구로 감싸서 노출하는 것입니다。

굵은 글씨 설정에 함수 하나。

표 삽입에 함수 하나。

제목 계층 변경에 또 다른 함수 하나。

에디터에 수십 개의 플러그인이 있다면 시스템 프롬프트 안에 수십 개의 Tool Schema를 순진하게 나열하게 됩니다。

우리 역시 처음에는 정확히 이 방식을 택했습니다。

하지만 실제 문서 편집 동작을 모사한 100건의 복합 테스트셋을 실행해 본 결과、성공률은 충격적으로 낮았습니다。

100건 중 정상 처리된 작업은 48건에 불과하여 종합 통과율은 48%에 그쳤습니다。

모델은 오류와 매개변수 재시도의 늪에 빠져 작업당 평균 4.2회의 왕복 통신을 소모했습니다。

더욱 치명적인 문제는 27건의 작업에서 인터페이스는 성공을 보고했으나 에디터 상의 DOM은 전혀 변경되지 않는 사일런트 장애가 발생했다는 점입니다。

오픈소스 프로젝트 QuireKit의 제작자가 V2EX 게시판 t/1253992 글에서 짚어낸 것이 바로 이 구조적 결함이었습니다。

그들은 프롬프트를 무한정 키우는 대신 극도로 정제된 자기 기술형 메타 능력 아키텍처를 제안했습니다。

우리는 그 설계 사상에 맞춰 로컬 테스트 환경의 통신 레이어를 전면 재구축했습니다。

동일한 100건의 복합 작업을 실행한 결과、작업 통과 수는 48건에서 98건으로 급증했고 평균 왕복 횟수는 1.1회로 수렴했습니다。

## 1. 툴 나열 방식의 3대 치명적 결함：에러 로그와 원인 분석

통신 프로토콜 개편의 가치를 이해하려면 기존 나열 방식이 리치 텍스트 엔진 내부 어디에서 무너졌는지 짚어보아야 합니다。

최신 리치 텍스트 에디터의 기저에는 엄격한 추상 구문 트리 상태 머신이 자리 잡고 있습니다。

ProseMirror 가 그렇습니다。

Tiptap 도 그렇습니다。

Lexical 역시 마찬가지입니다。

단순한 HTML 문자열 결합이나 Markdown 텍스트 스트리밍과는 차원이 다릅니다。

수십 개의 인터페이스를 대형 언어 모델 앞에 그대로 늘어놓으면 통신 경로는 곧바로 세 가지 장벽에 부딪힙니다。

### 결함 1：프롬프트 컨텍스트 폭증과 도구 선택 편차

기능이 어느 정도 갖춰진 에디터라면 노드와 마크 확장은 손쉽게 50개를 넘어섭니다：

- 블록 노드：문단、1단계부터 6단계까지의 제목、글머리 기호 목록、번호 매기기 목록、할 일 목록、인용 블록、코드 블록
- 인라인 마크：굵게、기울임、취소선、밑줄、인라인 코드、글자 색상、배경 강조색、링크
- 복합 위젯：데이터 표、행 병합、열 분할、이미지 삽입、차트 카드、접기 패널、수식 블록

이 기능들을 표준 OpenAI 도구 형식으로 작성하면 매 요청마다 2,400개 이상의 프롬프트 토큰이 소모됩니다。

50개 이상의 병렬 함수 스키마 앞에서 모델의 주의력은 납작하게 분산됩니다。

50개의 선택지 중에서 모델이 매번 올바른 함수를 골라낼 수 있을까요？

불가능에 가깝습니다。우리의 실제 테스트 로그에서도 DeepSeek Flash의 선택 편차가 빈번하게 목격되었습니다：

3장의 마지막 표에 행을 추가하라고 요청했음에도 불구하고 모델은 행 삽입 대신 `table.splitCell`을 호출하거나、텍스트 강조를 요청했을 때 표 셀 배경색 채우기를 선택해 버렸습니다。

### 결함 2：이중 직렬화 손실과 메타데이터 소실

50개 스키마의 유지보수 부담을 피하기 위해 일부 팀은 절충안을 택합니다：

모델에게 정형화된 Markdown만 출력하게 하고 프런트엔드에서 파서를 거쳐 HTML로 변환한 뒤 에디터에 주입하는 방식입니다。

이 접근법이 정말 유지보수를 줄여줄까요？

자멸에 가까운 타협입니다。Markdown은 복잡한 리치 텍스트 구조를 표현하기에 표현력이 턱없이 부족합니다。

여러 행에 걸친 셀 병합을 표현할 수 없습니다。

블록 노드에 부여된 비즈니스 식별자나 권한 잠금을 표현할 수 없습니다。

동시 편집 시의 커서 위치도 유지할 수 없습니다。

결국 데이터는 두 차례의 손실 변환 파이프라인을 거치게 됩니다：

```text
문서 AST 상태 머신 -> 간이 Markdown 으로 내보내기 -> 모델이 텍스트 재작성 -> 정규식으로 HTML 변환 -> ProseMirror 에 주입하여 AST 재구축
```

이 두 번의 변환 깔때기를 거치면서 원본 문서가 보존하던 메타데이터는 완전히 소실됩니다。

문단 한 줄을 굵게 처리하려던 단순한 동작이 문서 전체의 재파싱을 유발하여、하단에 잘 배치되어 있던 복잡한 중첩 표가 산산이 부서진 일반 텍스트로 강등되는 참사가 흔히 발생합니다。

### 결함 3：1차원 좌표 추측 실패와 사일런트 장애

벤치마크에서 확인된 27건의 사일런트 장애의 주범은 바로 좌표 처리 방식이었습니다。

ProseMirror 내부의 문서 위치 지정은 노드 태그의 열림과 닫힘에 따라 계산되는 1차원 정수 오프셋에 엄격히 의존합니다。

문단 시작이 12이고 끝이 48인 식입니다。

대형 언어 모델이 DOM 트리 내부의 정확한 1차원 정수 오프셋을 스스로 산출해 낼 수 있을까요？

전혀 그렇지 않습니다。모델은 DOM 바이트의 물리적 공간을 인지하지 못하며 오직 토큰 확률에 기반해 위치 숫자를 추측할 뿐입니다。

모델이 표 끝 위치로 120을 지정했으나 실제 표가 84에서 닫혀 있는 경우、ProseMirror 코어는 즉시 예외를 발생시킵니다：

```text
RangeError: Position 184 out of range 0..126
    at Object.replaceRange [node_modules/prosemirror-transform/dist/index.js:1042:15]
    at handleLegacyToolCall [src/editor/legacy-bridge.ts:68:12]
```

더 심각한 문제는 프런트엔드 래퍼 구현입니다。

화면 충돌을 막기 위해 개발자들은 dispatch 외부에 관행적으로 try-catch를 둘러두고 결국 성공 응답을 내려버립니다：

```text
POST /api/editor/dispatch 200 OK
Response: {"status": 200, "message": "command executed successfully"}
```

API는 200을 반환하고 대화창에서 모델은 처리가 완료되었다고 친절하게 답하지만 에디터 캔버스는 아무런 변화가 없습니다。

이러한 가짜 성공 현상을 사용자가 신뢰할 수 있을까요？우리의 테스트에서 이 문제는 무려 27번이나 발생했습니다。

## 2. QuireKit 자기 기술형 프로토콜：50개 도구를 3개의 메타 명령으로 압축

QuireKit의 해법은 모델 튜닝이 아니라 도구 레이어의 통신 규약 개혁이었습니다。

시스템 프롬프트에 상주하던 50개 이상의 정적 스키마를 모두 걷어내고 모델에게 세 가지 메타 인터페이스만 제공합니다：

- `list`：현재 캔버스 인스턴스에 탑재된 기능 목록을 동적으로 탐색
- `explain`：필요한 동작의 매개변수 구조와 제약 조건을 온디맨드로 조회
- `call`：기저 상태 머신에 원자적 트랜잭션을 발행하고 구조화된 결과 수신

```text
호출 라이프사이클：
1. 편집 의도 수신 -> list 를 발행하여 활성화된 기능을 최소 토큰으로 탐색
2. 대상 동작 확정 -> explain 을 발행하여 매개변수 규약을 온디맨드로 습득
3. 페이로드 조립 -> call 을 발행하여 ProseMirror 트랜잭션 직접 주입
```

### 1단계：list 를 통한 기능 목록 동적 탐색

시스템 프롬프트에는 개별 플러그인 정의를 일절 나열하지 않고 단일 통신 프로토콜 규격만 남깁니다。

문서 편집이 필요할 때 모델은 먼저 에디터 환경으로 탐색 요청을 전송합니다：

```bash
cli api list --target editor --json
```

에디터 환경은 현재 마운트된 확장 기능 요약 목록을 반환합니다：

```json
{
  "capabilities": [
    {"id": "doc.structure", "desc": "문서 아웃라인 및 AST 블록 계층 구조 조회"},
    {"id": "heading.set", "desc": "지정 블록 또는 선택 영역의 제목 계층 설정"},
    {"id": "table.insertRow", "desc": "지정 테이블 인덱스 또는 현재 포커스 뒤에 빈 행 추가"},
    {"id": "callout.create", "desc": "지정 위치에 경고 또는 메모용 콜아웃 카드 삽입"}
  ]
}
```

이 경량 인덱스는 식별자와 한 줄 설명만 담고 있습니다。

플러그인이 60개 이상이라도 목록 전체의 토큰 소모량은 180토큰 미만입니다。

프롬프트 정적 점유율이 90% 이상 줄어들며 모델은 혼란스러운 스키마 더미 대신 깔끔한 디렉터리를 마주하게 됩니다。

### 2단계：explain 을 통한 매개변수 규약 온디맨드 조회

목록에서 `table.insertRow`가 적합함을 파악한 모델은 해당 동작 전용 명세를 에디터에 요청합니다：

```bash
cli api explain table.insertRow --target editor --json
```

에디터는 해당 기능의 스키마만 선별하여 반환합니다：

```json
{
  "capability": "table.insertRow",
  "parameters": {
    "type": "object",
    "properties": {
      "tableIndex": {
        "type": "integer",
        "description": "문서 내 테이블의 0부터 시작하는 순차 인덱스"
      },
      "position": {
        "type": "string",
        "enum": ["before", "after"],
        "default": "after"
      },
      "targetRow": {
        "type": "integer",
        "description": "기준 행 번호이며 미지정 시 맨 끝에 추가"
      }
    },
    "required": ["tableIndex"]
  },
  "constraints": {
    "requiresFocus": false,
    "transactionType": "atomic"
  }
}
```

한 번의 호출에 하나의 규약만 로드하므로 모델의 집중도는 극대화됩니다。

우리의 테스트 기록에서 이 단계의 매개변수 환각 생성률은 0%에 수렴했습니다。

### 3단계：call 을 통한 네이티브 트랜잭션 직접 발행

규약을 확인한 모델은 매개변수를 조립하여 직접 실행을 지시합니다：

```bash
cli api call table.insertRow --target editor --input '{"tableIndex": 0, "position": "after", "targetRow": 2}' --json
```

에디터 내부에서 QuireKit은 이 입력을 ProseMirror 네이티브 트랜잭션에 곧바로 매핑합니다：

```ts
// 구현 예시：import, 보조 함수, 타입 정의 생략
export function handleInsertRowCommand(
  editor: Editor,
  input: InsertRowInput
): CommandResult {
  const { tableIndex, position, targetRow } = input;
  const state = editor.state;

  const tableNode = findTableNodeByIndex(state.doc, tableIndex);
  if (!tableNode) {
    return {
      success: false,
      errorCode: "ERR_TABLE_NOT_FOUND",
      errorMsg: `인덱스 ${tableIndex} 에 해당하는 테이블 노드를 찾을 수 없습니다`,
    };
  }

  let tr = state.tr;
  try {
    tr = addRowAtPosition(tr, tableNode.pos, targetRow, position);
    editor.view.dispatch(tr);

    return {
      success: true,
      affectedRange: [tableNode.pos, tableNode.pos + tableNode.node.nodeSize],
      docVersion: editor.state.version,
    };
  } catch (err: unknown) {
    const message = err instanceof Error ? err.message : String(err);
    return {
      success: false,
      errorCode: "ERR_TRANSACTION_FAILED",
      errorMsg: `트랜잭션 실행 오류：${message}`,
    };
  }
}
```

테이블 인덱스가 범위를 벗어나면 실행은 즉시 중단되고 `ERR_TABLE_NOT_FOUND`를 반환합니다。

에러 응답에는 문서 내 존재하는 테이블 수와 유효 인덱스 범위가 명확히 명시됩니다。

명확한 진단 정보를 받은 모델은 사용자에게 거짓 성공을 보고하지 않고 그 자리에서 매개변수를 교정하여 재시도합니다。

---

## 3. 벤치마크 테스트셋 설계와 실측 데이터

두 방식의 차이를 객관적으로 검증하기 위해 100건의 복합 편집 작업으로 구성된 테스트셋을 구축했습니다。

이 100건의 테스트 케이스는 어떻게 설계되었을까요？

실제 프로덕션 환경의 고난도 편집 시나리오를 고르게 다루기 위해 5개 범주에 각 20건씩 균등 배분했습니다：

- 범주 A：다단계 중첩 목록 들여쓰기 조정 및 할 일 완료 상태 일괄 전환——20건
- 범주 B：다단계 섹션 요약 내용 추출 및 경고 콜아웃 카드 자동 생성——20건
- 범주 C：3행 4열 테이블 데이터 보완、동적 수식 수정、헤더 행 고정——20건
- 범주 D：인라인 마크 적용 및 외부 비즈니스 엔터티 ID 메타데이터 바인딩——20건
- 범주 E：대형 기술 문서 내 교차 참조 링크 자동 갱신 및 앵커 복구——20건

평가 모델로는 DeepSeek Flash를 사용했고 temperature는 0.2로 고정했으며 작업당 최대 5회까지 재시도를 허용했습니다。

합격 판정에는 헤드리스 브라우저를 도입하여 ProseMirror의 AST 노드 구조가 기대치대로 변이되었는지를 검증했습니다。

실측 비교 결과는 다음과 같습니다：

```text
========================================================================================
벤치마크 지표            툴 나열 방식 (50+ Schemas)       QuireKit 자기 기술형 프로토콜
========================================================================================
총 테스트 케이스          100 건                          100 건
작업 성공 수              48 건                           98 건
종합 작업 통과율          48.0%                           98.0%
평균 상호작용 왕복 횟수   4.2 회 / 작업                   1.1 회 / 작업
작업당 평균 토큰 소모량   3,840 토큰                      620 토큰
평균 엔드투엔드 지연 P95  6.8 초                          1.4 초
사일런트 장애 발생 건수   27 건                           0 건 (본 평가에서 미관측)
신규 확장 추가 유지보수   수동 프롬프트 및 스키마 수정    완전 제로 (리플렉션으로 자동 노출)
========================================================================================
```

나열 방식에서 통과된 48건 중 31건은 여러 차례의 재시도를 거치며 P95 지연 시간이 6.8초까지 치솟았습니다。

반면 자기 기술형 프로토콜은 작업당 평균 토큰 소모량을 3,840토큰에서 620토큰으로 획기적으로 낮췄습니다。

모델이 첫 시도에서 올바른 동작과 매개변수를 선택할 수 있어 통과된 98건의 대다수가 단 1회 왕복만으로 트랜잭션을 완수했습니다。

## 4. 현장 엔지니어링 손익 계산서：실측 지연 시간과 마이그레이션 비용

자기 기술형 아키텍처 도입에는 분명한 트레이드오프가 존재합니다。

### 손익 1：추가 왕복에 따른 네트워크 지연과 클라이언트 캐싱 효과

explain 추가 호출로 인해 지연 시간이 급증하지 않을까요？

캐시되지 않은 드문 동작을 호출할 때 사전 스키마 조회로 인한 오버헤드는 불가피합니다。

로컬 네트워크에서 DeepSeek API를 측정한 결과 HTTP 단일 왕복 시간은 평균 약 120밀리초였습니다。

사전 explain을 거치면 작업 완료까지 약 240밀리초의 추가 대기 시간이 발생합니다。

이 지연을 억제하기 위해 프런트엔드 Agent 레이어에 인메모리 캐시를 구축했습니다。

초기화 시점에 문단、굵게、2단계 제목、글머리 기호 목록、표 행 추가라는 5대 고빈도 작업의 스키마를 메모리에 상주시킵니다。

100건의 테스트 실행에서 이 5개 고빈도 동작의 캐시 적중률은 76%에 달했습니다。

캐시 적중 시 explain을 건너뛰고 즉시 call을 실행하므로 P95 지연 시간은 1.4초에서 1.1초로 더욱 단축되었습니다。

### 손익 2：에디터 상태 머신의 정형성과 레거시 코드 리팩터링 비용

innerHTML로 DOM을 직접 조작하는 기존 프로젝트에 바로 적용할 수 있을까요？

불가능합니다。이 아키텍처는 에디터 코어가 원자적 트랜잭션 처리와 리플렉션 기능을 지원할 때만 성립합니다。

기존 프로젝트의 마이그레이션 공수 추산은 다음과 같습니다：

- 아웃라인 탐색용 읽기 전용 API 구현：약 1인일
- 주요 5개 기본 동작에 대한 ProseMirror 트랜잭션 경계 보호 구현：약 2인일
- 테이블 및 복합 중첩 컴포넌트의 에러 가로채기 및 롤백 메커니즘：약 3~5인일

DOM을 직접 수정하는 레거시 코드가 남아 있다면 그대로 자기 기술형 아키텍처를 적용할 수 없습니다。

DOM 조작을 엄격히 통제되는 트랜잭션으로 전면 수렴시킨 뒤에야 자기 기술형 레이어가 안정적으로 안착할 수 있습니다。

## 5. 단계별 마이그레이션 로드맵과 실무 권장 사항

프롬프트 비대화와 도구 선택 혼란을 겪고 있는 팀이라면 다음 3단계로 점진적 이전을 추진할 것을 권장합니다：

1단계：프롬프트 다이어트。

프롬프트에서 방대한 Tool 정의를 과감히 삭제하고 읽기 전용 `doc.structure`만 남깁니다。모델이 문서 전체의 구조를 먼저 파악하도록 유도합니다。

2단계：탐색 게이트웨이 구축。

`list`와 `explain` 엔드포인트를 구현하고 제목、목록、굵은 글씨 등 기본 동작의 JSON Schema를 독립된 명세 파일로 분리합니다。

3단계：트랜잭션 예외 처리 강화。

백엔드에서 예외를 뭉개지 말고 범위 초과나 노드 누락에 대해 명확한 에러 코드를 반환하도록 설계합니다。

모델이 API 문서를 온디맨드로 조회하고 에러 발생 시 명확한 스택 추적을 돌려받을 수 있어야 비로소 AI copilot은 깨지기 쉬운 장난감에서 믿을 수 있는 프로덕션 도구로 거듭납니다。

수십 개의 도구를 프롬프트에 몰아넣고 확률에 기대기보다 자기 기술형의 깔끔한 API 게이트웨이를 제공하는 것이 훨씬 건강한 Agent 개발 방식입니다。
