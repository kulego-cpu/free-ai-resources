# Qwen 4.0과 5.0도 오픈소스 지속 공개：압사라 컨퍼런스에서 공식 루머 일축

지난주 금요일 오후, 저희 인프라팀은 서버실에서 긴급 장애 대비 회의를 진행했습니다.

발단은 개발자 커뮤니티에 올라온 스크린샷 한 장이었습니다. Qwen4가 알리바바의 마지막 오픈소스 모델이며, 향후 팀 전체가 상용 클라우드 API로 완전 전환할 것이라는 주장이었습니다.

공식 출처 링크는 없었습니다. 포럼 글과 채팅 캡처뿐이었습니다.

하지만 저희는 최악의 상황을 가정하고 시뮬레이션을 진행해야만 했습니다.

사내 추론 클러스터에서는 듀얼 RTX 4090 노드 3대와 64GB 통합 메모리의 Mac Studio 2대가 운영되고 있습니다. 실제 프로덕션 코드는 Qwen2.5 72B 미세조정 버전을 기반으로 돌아갑니다. 시맨틱 검색, 사내 지식 기반 QA, 단위 테스트 자동화 파이프라인 전체가 이 모델에 묶여 있습니다.

상류 모델 공급이 중단되면 단순히 모델 이름만 바꾸는 것이 아니라, 추론 스케줄링 로직 전체를 밑바닥부터 다시 작성해야 합니다.

당시 저희는 대체 후보인 Llama 3.3 70B 양자화 브랜치를 로컬로 내려받아 긴 문맥 코드 완성 검증을 준비하고 있었습니다.

그리고 오늘 오전, 압사라 컨퍼런스 메인 무대에서 최신 현장 소식이 전해졌습니다.

통이치엔원 팀은 메인 발표 슬라이드를 통해 명확한 약속을 공개했습니다：향후 Qwen 4.0 및 Qwen 5.0 역시 오픈소스 공개 기조를 확고하게 유지한다.

대체 마이그레이션 계획의 우선순위는 잠시 낮출 수 있게 되었습니다. 하지만 실기 검증 작업은 이제부터가 시작입니다.

---

## 1. 사전에 듀얼 4090 부하 테스트가 필요했던 이유

운영 엔지니어가 가장 두려워하는 것은 예고 없는 공급망 단절입니다.

소프트웨어 개발은 기본 라이브러리에 의존합니다. 로컬 대규모 모델 운영은 오픈 가중치의 지속적인 공급에 전적으로 의존합니다.

최근 몇 년간 업계의 변화를 돌아보면, 초기에 오픈소스를 표방하다가 성숙 후 가중치를 닫아버리거나, 주력 모델을 유료 클라우드 뒤로 숨겨버린 사례는 드물지 않습니다.

온프레미스에서 워크로드를 운영하는 팀에게 구두 약속이나 소문만으로 안심할 수 있는 여유는 없습니다.

지난주 저희는 듀얼 4090 장비에서 Qwen2.5 72B AWQ 4-bit 버전을 부하 테스트했습니다.

실행 명령어는 다음과 같습니다：

```bash
python3 -m vllm.entrypoints.openai.api_server \
  --model Qwen/Qwen2.5-72B-Instruct-AWQ \
  --quantization awq \
  --tensor-parallel-size 2 \
  --max-model-len 32768 \
  --gpu-memory-utilization 0.95
```

24GB 메모리 그래픽카드 2장으로 총 48GB 용량입니다. 정적 AWQ 가중치가 로드된 시점에 약 38.2GB가 점유됩니다. 동적 KV 캐시로 할당 가능한 공간은 9.8GB에 불과합니다.

동시 요청을 8개 긴 세션으로 늘리고 각 컨텍스트가 8K 토큰에 도달했을 때, VRAM 사용량은 46.8GB까지 치솟았습니다.

이 시점에 p99 디코드 지연 시간은 단일 세션 기준 24밀리초에서 176밀리초로 급증했습니다. GPU 간 PCIe 4.0 버스 통신에서 병목 현상이 발생하기 시작했습니다.

만약 Qwen4가 오픈소스로 공개되지 않고 상용 클라우드 API 전환을 강요받는다면, 매달 늘어나는 토큰 비용도 문제지만 내부 커밋 기록이 외부망으로 전송되면서 사내 보안 컴플라이언스 심사에서 즉시 반려됩니다.

오픈소스 지속성은 저희에게 감성적 구호가 아닙니다. 실제 프로덕션 라인이 유지될 수 있는가에 직결된 생존 문제입니다.

## 2. 공개된 생태계 지표와 검증해야 할 실무 항목

컨퍼런스 현장에서는 최신 운영 통계도 함께 공유되었습니다：

- 전 세계 누적 모델 다운로드 수：30억 회 돌파
- 공식 자체 개발 오픈소스 모델：460종 이상
- 커뮤니티 파생 파인튜닝 모델 총수：30만 개 돌파

수치의 방대함은 분명합니다. 하지만 현장 엔지니어에게 숫자 나열만으로 환호할 수는 없습니다.

저희가 주목하는 실무 검증 포인트는 3가지입니다：

첫째, 7B 및 14B 크기가 24GB 단일 GPU에서 AWQ 양자화 후 32K 컨텍스트를 유지할 KV 캐시 메모리를 충분히 확보하는가.

둘째, 32B 크기를 카드 2장으로 텐서 병렬 분할할 때 PCIe 4.0 버스를 거치면서 처리량이 얼마나 감소하는가.

셋째, 고부하 다중 세션 동시 요청 환경에서 72B 모델이 긴 문맥 처리 도중 메모리 부족 오류를 일으키지 않는가.

무대에서 오픈소스 방침이 발표된 만큼, 이제 HuggingFace와 GitHub에 실제 가중치 디렉터리와 라이선스 파일이 등록되는 시점을 주시해야 합니다.

## 3. 커뮤니티의 차분한 시선：물리적 통제권과 남겨진 의문

슬라이드 공개 이후 개발자 커뮤니티의 반응은 엇갈렸습니다.

자체 호스팅 진영은 안도했습니다. 가장 큰 가치는 물리적 통제권입니다.

가중치 파일이 로컬 NVMe SSD에 온전히 보관되고, 추론 데이터가 사내 로컬 스위치 외부로 나가지 않습니다. 토큰별 종량제 요금도 발생하지 않으며, 공급자가 야간에 필터링 정책을 변경하여 정상 코드가 누락될 걱정도 없습니다.

그러나 현장 경험이 풍부한 엔지니어들은 보다 본질적인 의문을 제기합니다：

첫째, 모델 크기 인위적 분할 여부입니다. 최상위 플래그십 모델 전체가 공개되는지, 아니면 가벼운 증류 모델에 그치는지 여부입니다.

만약 조 단위 파라미터의 초대형 MoE 모델이 상용 클라우드 전용으로 묶인다면, 오픈소스의 실질적 가치는 크게 줄어듭니다.

둘째, 공개 시점의 시차 문제입니다. 상용 API 서비스 개시 시점과 오픈소스 가중치 업로드 시점 사이에 몇 주 혹은 몇 달간의 상업적 보호 기간이 존재하는지 여부입니다.

이러한 의문에 대해 현재 공식적인 확답 문서는 없습니다. 기조연설 한 번으로 모든 것이 끝난 것이 아니며, 저장소 배포가 완료될 때까지 지켜보아야 합니다.

## 4. 주관적 평가를 배제한 5가지 객관적 검증 기준

저희는 모호한 주관적 점수 매기기를 지양하고, Qwen4 공개 현황을 다음 5가지 명확한 기준으로 검증합니다：

1. **라이선스 완전성**：상용 이용이 자유로운 Apache 2.0이 유지되는지, 혹은 추가 제약 조건이 붙는지 여부.
2. **전체 파라미터 포괄성**：주력 크기와 MoE 구조가 모두 공개되는지, 경량 모델에 한정되는지 여부.
3. **동일 날짜 제공 여부**：클라우드 상용 서비스 오픈 당일 오픈소스 저장소에 가중치가 동시 배포되는지 여부.
4. **체크섬 무결성**：공식 제공 sha256 체크섬 목록이 온전하며, 분할 파일 검증이 문제없이 통과하는지 여부.
5. **추론 엔진 대응 속도**：vLLM, SGLang, llama.cpp 공식 메인 브랜치가 48시간 내에 호환 PR을 병합하는지 여부.

## 5. 향후 추적 계획

압사라 컨퍼런스에서 공식 약속이 발표되었으므로, Llama 3.3으로의 긴급 전환 작업은 일단 우선순위를 낮춥니다.

향후 실무 일정은 명확합니다：

1. GitHub 공식 저장소의 릴리스 동향과 풀 리퀘스트를 지속 모니터링합니다.
2. 가중치가 정식 공개되는 즉시 듀얼 4090 환경에서 위 vLLM 부하 테스트 명령을 재실행하여 메모리 곡선, 첫 토큰 응답 시간, 처리량을 측정합니다.
3. llama.cpp 환경에서 GGUF 양자화 손실을 측정하여 일반 워크스테이션에서 바로 참고할 수 있는 배포 가이드를 정리합니다.

모든 것은 가중치 파일의 실제 배포를 기준으로 판단합니다. 상세한 검증 로그와 설정 스크립트는 준비되는 대로 신속히 공유하겠습니다.
