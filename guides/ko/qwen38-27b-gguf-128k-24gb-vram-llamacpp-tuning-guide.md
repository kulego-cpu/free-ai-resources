실행 옵션을 무작정 복사하기 전에, 먼저 테스트 장비의 실제 상황부터 살펴보겠습니다.

테스트 환경은 단일 RTX 4090, 드라이버 버전 550.54.14, CUDA 12.4입니다.

로컬에서 27B급 고밀도 모델을 공식 표준 16비트 부동소수점 버전으로 구동하려고 하면 첫 단계에서 즉시 메모리 부족으로 튕깁니다.

정적 모델 가중치 용량만 54GB에 달합니다.

소비자용 그래픽 카드에서는 모델 파일 로드조차 완료되지 못하고 터미널이 종료됩니다.

일반적인 4비트 정수 양자화인 Q4_K_M을 선택하면 어떨까요?

가중치 크기는 약 16.8GB로 줄어들어 겉보기에는 24GB 물리 VRAM에 들어갈 것처럼 보입니다.

하지만 컨텍스트 길이를 32k 이상으로 늘리거나 긴 기술 문서 두 개를 입력하는 순간, 할당 메모리가 급격하게 치솟습니다.

화면이 약 2초간 멈춘 뒤 다음과 같은 오류가 출력됩니다:

```text
CUDA error: out of memory
current device: 0, total: 24564 MB, allocated: 23890 MB, free: 674 MB
cudaMalloc failed: out of memory
```

프로세스는 즉시 강제 종료됩니다.

왜 27B 모델의 긴 문맥 추론은 단일 카드에서 이토록 까다로울까요?

많은 엔지니어가 정적 가중치 파일 용량만 신경 쓰고, 동적 Key-Value [KV] 캐시의 메모리 팽창을 간과하기 때문입니다.

128k [131,072 토큰] 환경에서는 비양자화 FP16 KV 캐시 단독으로만 약 18GB의 전용 VRAM을 소모합니다.

정적 가중치 16.8GB에 캐시 18GB를 더하면 필요한 메모리는 34GB를 초과합니다. 24GB 단일 카드가 이를 견딜 수는 없습니다.

이번 실측에서는 파일 크기 14.9GB의 `Qwen3.8-27B-UD-Q4_K_XL.gguf` 를 사용했습니다. 런타임은 commit `b3842` 로 빌드한 `llama.cpp` 를 적용했습니다.

단일 24GB 카드에서 131,072 전체 컨텍스트를 실제로 안정 구동할 수 있을까요?

결론부터 말하면 가능하지만, 아무런 타협 없이 매끄럽게 돌아가는 것은 아닙니다.

테스트 도중 OOM 크래시를 두 번 겪었고, 마이크로 배치 버퍼 설정을 세 번 조정한 끝에 안정화에 성공했습니다.

연산 메모리 회계 계산, 실제 로그, 그리고 성능 측면에서 감수해야 했던 타협점을 정리합니다.

## 메모리 회계 분석: 왜 과거에는 24GB로 128k가 튕겼는가

문제를 해결하려면 VRAM이 실제로 어디에 쓰이는지 파악해야 합니다.

로컬 환경에서 대형 언어 모델 추론 시 물리 VRAM은 크게 세 블록으로 분할됩니다:

첫 번째는 파일 크기에 비례하는 정적 모델 가중치입니다.

두 번째는 문맥 길이에 따라 선형으로 증가하는 동적 KV Cache 풀입니다.

세 번째는 CUDA 런타임, Flash Attention 계산 임시 작업 영역, 그리고 메모리 파편화 공간입니다.

많은 이들이 세 번째 영역의 존재를 잊어버립니다.

초장문 문맥을 처리할 때 어텐션 연산 작업 영역으로 128k 환경 기준 1.5GB에서 2.5GB 수준의 버퍼가 사전에 확보되어야 합니다.

Qwen3.8-27B는 64개 레이어, 히든 디멘션 5120의 GQA 구조를 갖추고 있습니다.

캐시 양자화 없이 기본 16비트 부동소수점으로 유지할 경우:

토큰이 하나 진행될 때마다 고정 바이트의 컨텍스트 메모리가 누적됩니다.

계산해보면 1,000토큰마다 약 145MB의 VRAM이 소모됩니다.

131,072 토큰을 전부 채울 경우 과거 대화 기록을 보관하는 데만 18.5GB의 VRAM이 할당됩니다.

전체 회계를 다시 보면:

표준 Q4_K_M 정적 가중치가 16.8GB입니다.

여기에 동적 캐시 18.5GB를 더하면 35.3GB가 필요합니다.

여기에는 임시 계산 영역조차 포함되지 않았습니다.

단일 24GB 카드에 이 작업을 맡기면 컨텍스트가 40k를 넘어서는 순간 메모리 오류로 강제 종료됩니다.

24GB 물리 한계 내에 들어가려면 정적 가중치와 동적 캐시를 모두 줄여야 합니다.

## 1단계: UD-Q4_K_XL을 통한 가중치 절감

모든 레이어를 일률적으로 양자화하면 불필요한 품질 저하가 발생합니다.

언어 모델 내부 레이어는 위치에 따라 가중치 민감도가 크게 다릅니다.

입력부 임베딩과 어텐션 쿼리 프로젝션 레이어의 비트를 무리하게 잘라내면 논리적 추론력과 지시문 준수 능력이 급격히 떨어집니다.

반면 중간 및 심층부 피드포워드 네트워크는 비교적 강하게 압축해도 출력 품질에 미치는 영향이 적습니다.

UD-Q4_K_XL은 비균일 중요도 슬라이싱 방식을 사용합니다:

핵심 어텐션 가중치는 5비트에서 6비트 혼합 정밀도를 유지하고, 덜 민감한 피드포워드 레이어는 그래디언트 점수에 따라 Q3 및 Q4 수준으로 선택적 압축을 진행합니다.

RTX 4090에서의 실측 메모리:

| 양자화 형식 | 파일 크기 | 로드 후 순수 점유량 | 동작 상태 및 문맥 한계 |
| :--- | :--- | :--- | :--- |
| 순정 FP16 | 54.2 GB | 로드 불가 | 구동 시 즉시 OOM 크래시 |
| 일반 Q4_K_M | 16.8 GB | 약 17.5 GB | 35k 부근에서 메모리 경고 |
| 동적 UD-Q4_K_XL | 14.9 GB | 약 15.6 GB | 캐시용으로 약 8GB 여유 확보 |
| 극한 UD-IQ3_XXS | 11.2 GB | 약 11.9 GB | 16GB GPU 최소 생존선 |

UD-Q4_K_XL을 통해 기본 VRAM 점유량을 17.5GB에서 15.6GB로 낮출 수 있었습니다.

확보된 약 2GB의 공간이 긴 문맥 캐시를 구동하기 위한 결정적인 완충선이 됩니다.

## 2단계: KV 캐시를 16비트에서 8비트로 압축

정적 가중치를 15.6GB로 줄여도 18.5GB 용량의 FP16 캐시를 수용할 수는 없습니다.

이때 llama.cpp의 양자화 플래그인 `--cache-type-k` 와 `--cache-type-v` 를 변경해야 합니다.

기본값은 둘 다 `f16` 입니다.

구동 시 `q8_0` 로 지정하여 Key와 Value를 대칭 8비트 정수로 변환합니다.

`q8_0` 역시 마법의 만능열쇠는 아닙니다.

요소당 크기를 2바이트에서 1바이트로 줄이는 수치적 계산이지만, 실제로는 스케일 계수, 메모리 정렬, 어텐션 작업 영역의 오버헤드가 추가됩니다.

131,072 컨텍스트 실측에서 `q8_0` 활성화 시 KV 캐시 점유량은 18.5GB에서 약 9.4GB로 줄어들었습니다. 정확히 50% 절감되는 것은 아닙니다.

그럼에도 9.4GB 수준이라면 전체 메모리 예산 안에서 수용 가능한 범위에 들어옵니다.

더 극단적인 `q4_0` 캐시를 쓰지 않는 이유는 무엇일까요?

비교 테스트 결과, 4비트 캐시 환경에서는 컨텍스트가 64k를 넘어가면서 특정 변수명이나 숫자에 대한 검색 재현율이 급격히 떨어졌습니다.

반면 `q8_0` 에서는 장문 검색 정확도가 안정적으로 유지되어 FP16과의 기억력 차이가 거의 체감되지 않았습니다.

따라서 실무적인 주력 구성으로는 `q8_0` 가 적합합니다.

## 실전 크래시 기록: 계산상 들어가는데 왜 OOM이 났는가

15.6GB 가중치에 9.4GB 캐시를 더하면 약 25GB로 여전히 24GB를 초과합니다.

여기에 많은 엔지니어가 빠지는 함정이 있습니다.

초장문 컨텍스트를 입력할 때 일반적인 큰 배치 단위로 처리하면 순간적인 메모리 스파이크가 발생합니다.

초기에 실행했던 명령어는 다음과 같습니다:

```bash
./build/bin/llama-server \
  --model ./models/qwen3.8-27b-UD-Q4_K_XL.gguf \
  --n-gpu-layers 99 \
  --ctx-size 131072 \
  --cache-type-k q8_0 \
  --cache-type-v q8_0 \
  --flash-attn on \
  --batch-size 2048 \
  --ubatch-size 512
```

긴 프롬프트를 입력하자 프리필 단계에서 팬이 급격히 돌며 `CUDA error: out of memory` 오류와 함께 프로세스가 강제 종료되었습니다.

원인은 `--ubatch-size 512` 옵션에 있었습니다.

128k 고부하 환경에서 Flash Attention은 방대한 임시 활성화 버퍼를 요구합니다. 512 단위의 마이크로 배치가 순간적으로 메모리를 할당하면서 잔여 여유 공간을 단번에 초과해 버린 것입니다.

해결책으로 `--ubatch-size` 를 512에서 256으로 줄였습니다.

`nvidia-smi` 로 모니터링한 결과:

총 할당 메모리는 물리적 한계 24,564 MB 대비 23,210 MB에서 안정화되었고, 약 1.3GB의 안전 마진이 확보되었습니다.

다만 마이크로 배치를 절반으로 줄임으로써 프롬프트 프리필 속도가 30~40% 정도 느려지는 성능 타협은 불가피합니다.

## 속도 측정: MTP 투기적 디코딩의 체감 성능

메모리가 안정된 후 생성 속도를 점검했습니다.

단일 4090에서 27B 모델을 실행할 때 GDDR6X 메모리 대역폭 한계로 인해 일반 자기회귀 출력 속도는 초당 13~15토큰 수준에 머뭅니다.

Qwen3.8은 네이티브 Multi-Token Prediction [MTP] 구조를 지원합니다.

한 단어씩 순차적으로 계산하는 대신, 메인 네트워크 출력과 병렬로 보조 예측 헤드가 후속 2~3번째 토큰을 동시에 추론합니다.

예측이 적중하면 그대로 통과됩니다.

약 3,000줄의 TypeScript 코드 리팩터링 작업 실측 결과:

순수 자기회귀 모드:

초당 약 14.1토큰 출력.

MTP와 Flash Attention을 결합한 모드:

코드나 JSON처럼 구조적 규칙성이 강한 텍스트에서는 토큰 예측 적중률이 약 60%에 달해 초당 21.8 ~ 24.3토큰으로 속도가 향상되었습니다.

반면 자유로운 서술형 문장 작성에서는 적중률이 40% 이하로 떨어지며 초당 17토큰 내외로 낮아졌습니다.

실제 속도는 프롬프트의 결정론적 특성에 크게 좌우됩니다.

## 실전 재현용 실행 구성

단일 RTX 4090, Ubuntu 22.04 LTS, CUDA 12.4 환경에서 검증된 파라미터 구성입니다.

먼저 32k에서 테스트하고, `nvidia-smi` 추이를 보면서 64k, 131,072로 단계별 확장을 권장합니다.

```bash
./build/bin/llama-server \
  --model ./models/qwen3.8-27b-UD-Q4_K_XL.gguf \
  --n-gpu-layers 99 \
  --ctx-size 131072 \
  --cache-type-k q8_0 \
  --cache-type-v q8_0 \
  --flash-attn on \
  --batch-size 2048 \
  --ubatch-size 256 \
  --threads 8 \
  --host 0.0.0.0 \
  --port 8080
```

주요 옵션 설명:

`--n-gpu-layers 99`: 전체 레이어를 GPU VRAM에 오프로드합니다.

`--ctx-size 131072`: 128k 컨텍스트 영역을 할당합니다.

`--cache-type-k q8_0` 및 `--cache-type-v q8_0`: 8비트 KV 캐시 압축을 활성화합니다.

`--flash-attn on`: 임시 연산 버퍼의 중복 생성을 막는 필수 플래그입니다.

`--ubatch-size 256`: 메모리 스파이크를 방지하는 안전 임계치입니다.

## 16GB GPU 환경 운영 안내

RTX 4080이나 16GB VRAM 노트북을 사용하는 경우 설정을 낮춰야 합니다.

가중치를 용량 11.2GB의 `UD-IQ3_XXS` 로 변경합니다.

컨텍스트 길이를 65,536 [64k] 로 줄이고 KV 캐시를 `q4_0` 로 설정합니다:

```bash
./build/bin/llama-server \
  --model ./models/qwen3.8-27b-UD-IQ3_XXS.gguf \
  --n-gpu-layers 99 \
  --ctx-size 65536 \
  --cache-type-k q4_0 \
  --cache-type-v q4_0 \
  --flash-attn on \
  --ubatch-size 256 \
  --port 8080
```

총 VRAM 사용량은 약 15.1GB 내외로 제한됩니다. 문서 요약이나 긴 텍스트 검색 용도로는 유용하지만, 복잡한 다단계 논리 추론에서는 4비트 양자화 대비 정밀도가 떨어집니다.

## 맺음말

튜닝 과정에 기적이나 마법은 없습니다.

모든 것은 현실적인 연산 자원의 타협입니다:

덜 민감한 레이어의 정밀도를 양보하여 가중치 공간을 확보합니다.
