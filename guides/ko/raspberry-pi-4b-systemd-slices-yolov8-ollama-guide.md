# 8GB 라즈베리 파이에서 시각 모델과 LLM 동시 구동: systemd slices로 실시간 계측 지연 해결하기

저전력 엣지 장비에서 하드웨어 성능을 한계까지 끌어올릴 때 가장 경계해야 할 문제는 필수 실시간 작업에 대한 스케줄링 기아 현상입니다.

오픈소스 해양 모니터링 시스템에 장착된 8GB 메모리의 Raspberry Pi 4B 단일 보드가 있습니다. 헤드리스 Debian 기반의 이 단말은 3가지 핵심 부하를 동시에 감당하고 있습니다. 첫째는 선박 계측 장비에서 침로, 수심, 풍속, RPM 데이터를 초당 고주파수로 수집하는 Signal K 텔레메트리 서비스입니다. 둘째는 ONNX 런타임으로 선수 카메라 영상을 초당 5프레임 속도로 분석하는 백그라운드 YOLOv8 nano 모델입니다. 셋째는 해양 정비 매뉴얼을 로컬에서 검색하기 위해 Llama 3.2 1B를 적재한 Ollama입니다.

이러한 멀티태스킹 배치는 단일 보드의 연산 능력을 상시 과부하의 임계점으로 몰아넣어 동시 요청 시 처리 지연을 유발합니다.

평소 시각 모델만 작동할 때는 4코어 CPU 점유율이 50% 안팎을 유지하며 알루미늄 외장 케이스 온도는 68도 수준에서 억제되어 스로틀링 기준선 아래를 간신히 유지합니다.

그러나 현장 작업자가 웹 대시보드를 통해 Ollama에 매뉴얼 질의를 전송하는 순간, 대형 모델이 다중 스레드 추론을 시작하며 4개 CPU 코어 점유율은 즉시 100%로 치솟습니다.

심각한 장애가 즉각 발생합니다. 제어 화면의 응답이 정지합니다.

안정적으로 갱신되던 계측 데이터 흐름에서 심각한 패킷 누락이 발생하기 시작합니다. 데이터 갱신 지연 시간은 수십 밀리초에서 수초 단위로 폭증하고 계기판 화면에는 통신 단절 경고가 반복해서 울립니다.

항해 중이거나 산업 현장 순찰 시 대형 모델의 답변 생성을 기다리느라 핵심 계측 데이터가 단절되는 상황은 안전상 용납할 수 없는 사고입니다. 계측기가 멈추는 상황을 누가 감내할 수 있겠습니까.

8GB 라즈베리 파이에서 시각 모델과 로컬 대형 모델을 동시에 운영하는 것은 정말 불가능한 일일까요.

최근 오픈소스 엔지니어링 커뮤니티에서 실전적 가치가 매우 높은 시스템 설계가 제시되었습니다. Linux의 systemd slices 메커니즘을 활용하여 이 3중 작업 충돌을 완벽히 해결하는 방법이 공유되었습니다.

최신 Linux 커널이 제공하는 cgroups v2 메커니즘을 활용하여 정밀한 자원 분할을 수행해야 합니다.

## CPUAffinity 코어 고정이 완전히 실패하는 이유

다중 작업이 CPU 자원을 두고 경합할 때 경험 많은 시스템 관리자일수록 코어 고정 기법을 먼저 적용합니다.

본 프로젝트의 원작자 역시 초기에는 동일한 방식을 시도했습니다.

서비스 정의 파일에 CPUAffinity 옵션을 선언하여 실시간 Signal K 서비스를 코어 0에 강제 할당하고 나머지 연산 작업을 다른 3개 코어로 몰아내려 했습니다.

동시에 8GB 물리 메모리가 모델 가중치로 포화되는 현상을 막기 위해 2GB 스왑 공간을 확보하고 swappiness 값을 10으로 낮춰 물리 메모리를 활성 프로세스에 우선 배정했습니다.

이 표준적인 조치를 적용한 결과 실시간 데이터 누락 문제가 해결되었을까요.

결과는 참담한 실패였습니다. 지연 현상은 전혀 개선되지 않았습니다.

Ollama와 YOLOv8이 최대 부하로 작동할 때 주 스레드는 코어 0을 회피하지만, 하부 장치 인터럽트, 디스크 입출력, 타이머, 네트워크 소프트 인터럽트는 여전히 전체 코어를 넘나들며 빈번하게 호출됩니다.

나머지 3개 코어가 100%까지 완전히 소진되면 운영체제의 컨텍스트 스위칭 오버헤드가 기하급수적으로 폭증합니다.

코어 0에서 실행 중인 텔레메트리 프로세스가 시스템 콜을 호출하거나 공유 락을 요청할 때마다 스케줄러는 다른 코어의 자원 해제를 기다릴 수밖에 없습니다.

캐시 라인이 지속적으로 무효화됩니다. 컨텍스트 스위칭 횟수가 폭증합니다.

코어 고정은 실시간 작업에 온전한 격리 환경을 제공하지 못하고 코어 간 불균형만 심화시켰습니다.

4개 코어가 모두 포화된 상태에서 단일 스레드 코어 고정만으로 밀리초 이하의 응답성을 보장하는 것은 불가능합니다. 현장의 화면 멈춤은 지속되었습니다.

공급되는 총 연산 자원 자체에 근본적인 제동을 걸어야 합니다. 과연 연산 부하를 확실히 억제할 방법이 있을까요. 초기에는 누구도 확신을 갖지 못했습니다.

## 핵심 해결책: systemd slices로 구축하는 2중 방어선

커뮤니티 기여자 Geekomcomputer가 제안한 해법은 현대 Linux 자원 관리의 핵심을 정확히 짚어냈습니다.

Raspberry Pi 4B에 탑재된 Broadcom 4코어 프로세서의 총 연산력은 정해져 있습니다. 개별 프로세스에 빈 코어를 찾아주는 것이 아니라, 추론 작업이 동시에 최대 속도로 자원을 독점하지 못하도록 막는 데 핵심이 있습니다.

구체적인 구현은 systemd의 사용자 정의 슬라이스를 생성하여 2중 방어선을 구축하는 방식으로 진행됩니다:

- 1차 방어선: CPUWeight를 통한 절대적 스케줄링 우선순위 지정；
- 2차 방어선: CPUQuota를 활용한 추론 작업 연산 상한 강제.

설정 절차는 직관적입니다. systemd 설정 디렉터리에 2개의 슬라이스 단위를 새로 생성합니다.

첫 번째는 텔레메트리 전용인 telemetry.slice입니다:

```ini
[Unit]
Description=Telemetry and Critical Realtime Slice

[Slice]
CPUWeight=1000
```

두 번째는 추론 프로세스를 수용할 inference.slice입니다:

```ini
[Unit]
Description=AI Inference Background Slice

[Slice]
CPUWeight=50
CPUQuota=200%
```

이 2중 방어선의 자원 분배 효과를 계산해 봅니다.

기본 환경에서 Linux 일반 서비스가 상속받는 CPU 가중치는 100입니다. 텔레메트리 슬라이스의 가중치를 1000으로 대폭 올리고 추론 슬라이스는 50으로 낮춥니다.

자원 경합이 발생할 때 텔레메트리 프로세스에 패킷이 도착하면 커널 스케줄러는 주저 없이 최우선으로 CPU 실행 시간을 배정합니다.

더욱 결정적인 설정은 CPUQuota=200%라는 상한 제한입니다.

4개 코어를 갖춘 라즈베리 파이는 전체 코어 합산 400%의 CPU 시간 슬롯을 갖습니다. 추론 슬라이스의 몫을 200%로 고정한다는 것은 질의가 아무리 몰려도 YOLOv8과 Ollama의 합계 연산량이 최대 2개 코어 수준을 절대 넘지 못함을 의미합니다.

이를 통해 운영체제 기반 시스템, 네트워크 통신, 로그 기록, 실시간 텔레메트리 작업을 위한 2개 코어의 여력이 영구적으로 보존됩니다.

## 실무 검증과 발열 감소 효과

슬라이스 파일을 저장한 뒤 시스템 데몬 설정을 재적재하고 대상을 해당 슬라이스에 연결합니다.

systemd 데몬을 재적재합니다:

```bash
sudo systemctl daemon-reload
```

서비스 단위 파일 내부에서 슬라이스를 지정하거나 명령어를 통해 프로세스를 직접 실행합니다:

```bash
sudo systemd-run --slice=inference.slice ollama serve
```

동일한 Raspberry Pi 단말에서 부하 테스트를 다시 수행했습니다.

웹 화면에서 장문 추론 질의를 전송했을 때 모니터링 화면의 반응은 완전히 달랐습니다:

추론 작업이 실행되어도 htop 모니터링의 전체 CPU 사용량은 250% 수준에서 엄격하게 제한되었습니다.

코어 0과 코어 1의 점유율은 대단히 여유롭게 유지되었습니다.

계측 화면의 텔레메트리 데이터 흐름을 확인하자 침로와 수심 그래프가 부드럽게 갱신되었으며 통신 지연 시간은 15밀리초 이하로 안정화되어 패킷 누락 경고가 완전히 사라졌습니다.

실행은 정상적으로 완료되었습니다. 계측 시스템은 다시 평온을 되찾았습니다.

더불어 매우 고무적인 부수적 이점으로 동작 온도 개선이 확인되었습니다.

이전에는 추론이 병행될 때 4개 코어가 장시간 포화되면서 외장 케이스 온도가 스로틀링 위험 기준인 70도에 근접했습니다.

200% 상한 제한을 적용한 후에는 10분간 연속 질의를 실행해도 외장 온도가 61도 안팎으로 안정되어 클럭 강제 다운 위험에서 완전히 벗어났습니다.

추론 생성 속도의 사소한 감소를 대가로 임베디드 시스템 전체의 안정성을 확보하는 선택은 지극히 타당합니다. 계측 장비가 멈추는 상황에서 누가 침착함을 유지할 수 있겠습니까. 속도를 희생하고 신뢰성을 취할 가치는 충분합니다.

## 엣지 혼합 환경의 기술적 한계와 선정 기준

이번 실측을 통해 저전력 단일 보드에서 실시간 시스템과 대형 모델을 병행 운용하기 위한 원칙이 정립되었습니다.

Raspberry Pi 4B나 유사한 소형 보드를 운영할 때는 다음 3가지를 확인하십시오:
- 하드웨어의 물리적 한계를 인정할 것. 복수 모델을 제한 없이 최대 출력으로 구동하려 해서는 안 되며 연산량에 상한선을 강제해야 합니다；
- 단순 코어 고정에 대한 맹신을 버릴 것. 인터럽트가 집중되는 환경에서는 cgroups 가중치와 쿼터 제어를 우선 적용합니다；
- 동작 온도를 상시 감시할 것. 65도를 초과하는 상태는 스로틀링의 전조이며 적절한 연산 제한은 쿨링팬 추가보다 훨씬 근본적인 대책이 됩니다.

하드웨어 성능이 제한적일지라도 체계적인 운영체제 관리를 적용하면 소형 단일 보드는 뛰어난 신뢰성을 발휘합니다.

추론 부하로 어려움을 겪는 소형 장비를 운영할 때 다음 엣지 환경 구축에서는 백그라운드 추론 작업에 얼마의 CPUQuota를 설정하시겠습니까.
