결론부터 말하자면 실행은 되지만 절대 따라 하지 마십시오.

클라우드 엔지니어들에게는 익숙한 직관이 있습니다. 서버리스 구조가 동영상 인코딩 같은 수백 개의 작업을 잘게 쪼개어 처리할 수 있다면 대형 언어 모델도 그렇게 실행할 수 있지 않을까 하는 생각입니다.

전용 GPU 인스턴스를 계속 켜두면 쉬는 시간에도 초당 비용이 빠져나갑니다. 모델을 마이크로서비스처럼 필요할 때만 띄우고 밀리초 단위로 비용을 낸다면 청구서를 크게 줄일 수 있지 않을까 기대하게 됩니다.

엔지니어 Noah Lindner는 이 가설을 검증하기 위해 Qwen 아키텍처 기반의 결정 모델을 계층별로 분해하여 AWS Lambda 위에 파이프라인을 구축했습니다.

결과는 처참했습니다. 문서 하나를 추론하는 데 17초가 걸렸고 처리 비용은 3.4센트에 달했습니다. 일반적인 매니지드 GPU 엔드포인트에서 0.04센트 수준인 것과 비교하면 속도는 지나치게 느리고 비용은 무려 80배나 치솟았습니다.

이는 서버리스의 탄력성 부족 문제가 아닙니다. 계층 간 텐서 상태를 객체 스토리지로 전달해서는 안 된다는 근본적인 물리적 한계 때문입니다.

## 왜 Lambda로 모델을 조립하려 했는가

서버리스 컴퓨팅의 가장 큰 장점은 사용한 만큼만 지불하는 종량제에 있습니다.

동영상 분할 변환이나 썸네일 생성, 이벤트 기반 데이터 정제 작업에서 Lambda는 비용을 극한까지 줄여줍니다.

반면 대형 언어 모델 추론 환경에서는 기존 인프라에 두 가지 큰 고민거리가 있습니다：

첫째는 콜드 스타트와 상시 가동 비용 사이의 충돌입니다. A10G나 A100을 탑재한 인스턴스는 야간에 요청이 거의 없더라도 시간당 고정 비용이 청구됩니다.

둘째는 트래픽 폭증 시의 탄력성 한계입니다. 갑자기 수천 건의 요청이 몰릴 때 일반 인스턴스의 오토스케일링은 이미지 다운로드와 가중치 로드에 2분에서 3분이 걸려 요청이 타임아웃에 걸리기 쉽습니다.

모델을 완전히 서버리스화할 수 있다면 유휴 비용 없이 즉각적인 확장이 가능할 것이라는 기대를 모았습니다.

하지만 함수 런타임의 물리적 규격 한계가 곧바로 걸림돌이 되었습니다.

## 9.3GB 가중치를 34개 함수로 분할한 파이프라인

첫 번째 장벽은 배포 패키지 용량 제한이었습니다. AWS Lambda는 압축 해제 후 용량에 엄격한 제한이 있어 직접 업로드는 250MB, 컨테이너 이미지도 몇 GB 수준으로 묶여 있습니다.

실험에 사용된 Qwen 기반 모델은 가중치 용량이 약 9.3GB였습니다. 9.3GB 단일 모델 전체를 단일 Lambda 함수에 넣는 것은 메모리와 초기화 한계로 인해 불가능합니다.

이에 따라 저자는 Transformer 구조의 계층적 특성을 활용했습니다：

Transformer는 계층이 직렬로 쌓이는 구조입니다. 이 모델은 32개의 직렬 Transformer 계층으로 이루어져 있으며 계층당 크기는 약 225MB입니다. 전면의 Embedding 계층과 후면의 LM Head 계층을 합쳐 총 34개의 독립된 Lambda 함수로 쪼갰습니다. 계층당 225MB라면 개별 Lambda 실행 환경에 충분히 들어갑니다.

토폴로지는 다음과 같은 직렬 릴레이 구조로 설계되었습니다：

```text
프롬프트 입력
     │
     ▼
┌─────────────┐
│ Lambda 0    │  Embeddings 어휘 로드
└──────┬──────┘
       │  활성화 텐서를 S3에 저장
       ▼
┌─────────────┐
│ Lambda 1    │  Transformer Layer 0 처리, 약 225MB 가중치
└──────┬──────┘
       │  활성화 텐서를 S3에 저장
       ▼
      ... 중간 30개 계층 함수 직렬 릴레이
       │  활성화 텐서를 S3에 저장
       ▼
┌─────────────┐
│ Lambda 32   │  Transformer Layer 31 처리
└──────┬──────┘
       │  활성화 텐서를 S3에 저장
       ▼
┌─────────────┐
│ Lambda 33   │  LM Head 로드, 출력 토큰 및 예측 확률 생성
└─────────────┘
```

파이프라인이 정상 동작했을 때 저자는 비용보다 출력을 먼저 대조했습니다.

동일한 프롬프트에서 로컬 PyTorch와 Lambda 파이프라인의 top-1 토큰이 일치했습니다. 순전파 연산 자체는 정상적으로 수행된 것입니다.

그러나 배치 작업과 다중 실행, 계층 분할을 거치면서 전체 체인에서 누적 5600회의 Lambda 함수 호출이 발생했습니다.

그리고 청구 내역을 열었을 때 문서 하나당 17초와 3.4센트라는 숫자가 찍혔습니다. 연산이 성공하는 것과 실전 배포가 가능한 것은 전혀 다른 문제입니다.

## 17초와 3.4센트：80배 역마진 청구서 분석

실행이 된다고 해서 프로덕션에 쓸 수 있을까요.

클라우드 관리 화면의 지표는 냉혹했습니다.

문서 1건 추론에 17초가 소요되었고 연산 시간과 스토리지 요청으로 3.4센트의 비용이 발생했습니다.

동일한 체급의 Qwen을 매니지드 GPU 인스턴스에서 돌릴 경우 추론 시간은 수십에서 수백 밀리초에 불과하며 단일 요청당 비용은 약 0.04센트 수준입니다.

3.4센트와 0.04센트를 비교하면 비용이 무려 80배 폭증했습니다.

비용을 아끼려던 서버리스 실험이 예산을 갉아먹는 구멍이 된 원인은 어디에 있었을까요.

### 원인 1：S3 텐서 중계로 인한 네트워크 지연

GPU 내부에서는 계층 간 텐서가 SRAM과 HBM을 통해 초당 수 테라바이트 대역폭으로 이동합니다.

하지만 34개의 독립된 Lambda 함수 사이에는 메모리가 전혀 공유되지 않습니다. 이전 계층의 결과를 다음 계층으로 넘기려면 직렬화하여 네트워크로 전송해야 합니다.

실험에서는 중간 텐서 교환에 Amazon S3를 사용했습니다. 32개 계층이 직렬로 연결되어 각 계층마다 텐서를 직렬화하여 S3에 저장하고 다음 계층이 이를 다운로드하여 압축을 풉니다.

토큰당 계층당 PUT 1회와 GET 1회를 계산하면 32개 계층에서 64회의 객체 요청이 일어납니다. 175개 토큰을 생성하면 11000회 이상의 S3 왕복이 발생합니다.

이는 지수 폭발은 아니지만 선형 누적만으로도 17초의 대부분을 채우기에 충분했습니다. 대부분의 시간은 행렬 계산이 아니라 S3와 Lambda 사이의 데이터 왕복 대기에 소모되었습니다.

### 원인 2：CPU 밀집 행렬 연산으로 인한 시간 가산

AWS Lambda는 기본적으로 범용 CPU 환경입니다. 최대 메모리를 할당하여 CPU 할당량을 늘리더라도 범용 x86이나 ARM 명령어로 고밀도 부동소수점 행렬을 처리하는 속도는 전용 텐서 코어를 따라갈 수 없습니다.

GPU에서 수 밀리초면 끝날 행렬 곱셈이 CPU에서는 수백 밀리초씩 걸립니다.

Lambda의 과금 방식은 실행 시간과 할당 메모리의 곱입니다. 실행 시간이 수십 배 늘어나면 수천 번의 호출을 거치며 청구 금액이 가파르게 치솟습니다.

### 원인 3：콜드 스타트와 직렬 스케줄링의 지연 누적

5600회의 호출은 고르게 실행되지 않습니다. 컨테이너 할당, 225MB 가중치 다운로드, 런타임 초기화 단계에서 콜드 스타트 편차가 발생합니다.

엄격한 직렬 의존성 체인에서는 전체 소요 시간이 가장 느린 노드의 합에 의해 결정됩니다. 중간에 몇 개 계층만 스케줄링 지연을 겪어도 뒤따르는 모든 함수가 대기 상태에 머물러야 합니다.

## 이 실험이 남긴 대형 모델 추론의 물리적 경계

비즈니스적으로는 완전히 실패한 시도였지만 시스템 엔지니어링 관점에서는 명확한 설계 기준을 남겼습니다.

### 연산 집약형과 IO 집약형의 물리적 차이

서버리스 구조가 동영상 변환이나 로그 처리에 적합한 이유는 데이터가 상태가 없는 파이프라인 형태이고 노드 간 통신보다 개별 노드의 연산량이 훨씬 크기 때문입니다.

반면 대형 언어 모델은 메모리 대역폭과 극소 지연시간 통신에 극도로 민감합니다. Transformer의 자기회귀 생성은 토큰 하나를 만들 때마다 전체 가중치를 훑고 직전 은닉 상태에 의존합니다. 강하게 결합된 상태를 끊어내어 느슨한 네트워크 노드에 넘기는 구조는 하드웨어 친화적 설계와 정면으로 배치됩니다.

### 겉보기 탄력성과 실제 비용의 저울질

많은 팀이 유휴 자원을 낭비로 여겨 복잡한 분산 중계를 통해 유휴 상태를 없애려는 유혹에 빠집니다.

그러나 낮은 빈도의 워크로드라 하더라도 소형 GPU 인스턴스를 80퍼센트 놀려두는 편이 수천 번의 서버리스 콜드 스타트를 조립하는 것보다 월 총비용이 훨씬 저렴합니다. 유휴 비용은 눈에 보이지만 분산 아키텍처의 네트워크 비용과 직렬화 부하, 운영 복잡도는 눈에 띄지 않게 누적됩니다.

### 현실적인 서버리스 추론 형태

그렇다면 대형 모델 환경에서 서버리스는 전혀 쓸모가 없는 것일까요.

그렇지 않습니다. 적절한 서버리스 형태는 단일 모델을 34개로 조각내는 것이 아니라 플랫폼 인프라 차원에서 인스턴스를 웜 풀로 유지하는 방식이어야 합니다：

첫째는 GPU 컨테이너 인스턴스의 초 단위 과금입니다. 가중치는 호스트 공유 캐시에 사전 탑재되어 있고 라우팅 계층만 요청을 분배하여 토폴로지를 해치지 않습니다.

둘째는 프롬프트 렌더링, 민감어 필터링, 인증, JSON 파싱 같은 가벼운 보조 작업을 서버리스에 맡기고 고부하 행렬 연산은 고대역 연결된 전용 칩에 고정해 두는 구조입니다.

## 요약

이 실험이 남긴 교훈은 명확합니다：

첫째, Transformer 계층을 동영상 조각처럼 취급해서는 안 됩니다. 계층 간 상태는 강하게 결합되어 있어 S3를 중계로 쓰면 지연과 호출 비용이 함께 폭증합니다.

둘째, 저빈도 추론에는 소형 GPU 인스턴스를 사용하는 것이 바람직합니다. 80퍼센트 놀고 있더라도 5600회의 콜드 스타트를 반복하는 것보다 훨씬 저렴합니다.

셋째, 탄력성이 필요하다면 플랫폼의 GPU 웜 풀을 활용하고 순수 함수 컴퓨팅으로 모델을 자작 분할하지 마십시오.

낮은 빈도의 추론을 위해 순수 서버리스 환경을 고집할 이유가 있을까요.

절약해야 할 것은 가상 모니터링 수치가 아니라 월말 청구서의 실제 금액입니다.
