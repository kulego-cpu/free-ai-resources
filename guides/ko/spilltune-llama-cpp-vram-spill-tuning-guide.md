# VRAM 부족으로 느려진 로컬 LLM 구출하기: spilltune으로 llama-server 메모리 누수 최적값 자동 탐색

RTX 3060 12GB나 RTX 4060을 장만하고 로컬에서 30B급 중대형 모델을 돌려보려던 사람들은 대부분 차가운 현실을 마주합니다.

17.1GB 용량의 31B Q4_K_M 모델을 예로 들어보겠습니다. GPU의 VRAM은 12GB뿐입니다. 아무리 VRAM을 쥐어짜도 약 7GB 분량의 가중치는 시스템 RAM으로 밀려날 수밖에 없습니다.

메모리 오버플로가 일어나는 순간, llama-server의 생성 속도는 GPU 대역폭에서 시스템 메모리 대역폭의 한계로 수직 낙하합니다.

터미널 커서는 초당 3.4개의 단어를 간신히 뱉어냅니다.

커피를 한 잔 타고 돌아와도 몇백 자짜리 코드 설명조차 다 출력되지 않습니다.

처음에는 그래픽 드라이버 문제인 줄 알았습니다. 구버전으로 롤백해도 소용없었습니다. Windows 창 관리자가 백그라운드에서 VRAM을 갉아먹는 줄 알고 nvidia-smi를 확인했으나 프로세스는 깨끗했습니다.

결국 llama.cpp 커뮤니티 토론에서 해답을 찾았습니다: 기본 fit 전략이 VRAM에 안전 버퍼를 과도하게 잡아둡니다. 12GB 그래픽카드에서 낭비되는 1GB의 여유 공간은 GPU가 레이어 두 개를 더 품을 수 있느냐를 가르는 결정적인 경계선이었습니다.

어째서 단 2GB 부족으로 속도가 반 토막 나는 것일까요?

이것은 기분 탓이 아닙니다. 360GB/s의 GDDR6 대역폭에서 20GB/s의 DDR4 메모리 대역폭으로 떨어지는 물리적 격차입니다. 토큰을 하나 생성할 때마다 CPU는 버스를 가로질러 7GB 가중치를 매번 옮겨야 합니다. 물리 법칙은 타협을 모릅니다.

llama.cpp에 수많은 튜닝 옵션이 있다는 사실은 잘 알려져 있습니다: fit-target을 줄여 GPU 레이어를 늘리기, MTP나 DFlash 보조 모델을 붙여 투기적 샘플링 적용하기, 추측 단계 늘리기, 신뢰도 컷오프 조절하기 등이 있습니다.

하지만 경우의 수가 너무 방대합니다.

VRAM 여유는 몇 메가바이트가 적당할까요? 보조 모델은 4단계를 추측해야 할까요, 아니면 16단계를 추측해야 할까요? 신뢰도 컷오프는 0.5가 나을까요, 0.7이 나을까요?

지난주 저는 스무 번 넘게 수동 테스트를 돌렸으나 초반 일곱여덟 번은 완전히 헛수고였습니다. 최악의 경우 VRAM이 고갈되어 llama-server가 OS 강제 종료를 맞았고, 보조 모델을 붙였더니 오히려 속도가 3.4에서 2.2로 떨어지기도 했습니다.

그러던 중 GitHub에 이 골치 아픈 문제를 해결해 주는 오픈소스 도구가 등장했습니다: 0xydendrum이 공개한 spilltune입니다. 저장소 주소는 github.com/0xydendrum/spilltune입니다.

헛된 이론을 늘어놓지 않습니다. 오후 내내 매달려야 했던 고된 수동 튜닝을 전자동 등산 알고리즘 작업으로 압축해 줍니다.

## 1. 근본적인 병목: 메모리 유출 시의 버스 전송 대가

spilltune의 가치를 체감하려면 VRAM과 시스템 메모리의 물리 스펙을 비교해 보아야 합니다.

RTX 3060 12GB의 메모리 대역폭은 약 360GB/s입니다. 듀얼 채널 DDR4-3200 메모리의 이론상 최대 대역폭은 25.6GB/s이며, 실제 운영체제 위에서는 20GB/s 안팎이 한계입니다.

열여덟 배에 달하는 거대한 성능 격차입니다.

모델 전체가 VRAM에 안착해 있다면 GPU 텐서 코어는 최고 속도로 가중치를 읽어옵니다.

그러나 전체 레이어의 3분의 1이 시스템 메모리로 밀려나면, 자기회귀 디코딩을 진행할 때마다 CPU는 느린 버스를 거쳐 7GB 데이터를 다시 실어 날라야 합니다.

물통의 가장 짧은 널빤지가 시스템 메모리 버스가 됩니다. 가장 느린 전송로가 전체 생성 속도를 옭아매는 것입니다.

기본 llama-server는 지나치게 보수적인 할당을 수행합니다. 긴 컨텍스트에서 즉시 OOM이 터지는 일을 막기 위해 fit-on을 켜두고 1024MB의 여유 공간을 무조건 비워둡니다.

12GB 그래픽카드 입장에서 1GB를 비워둔다는 것은, 원래 GPU에 들어갈 수 있었던 두세 개 레이어를 시스템 메모리로 쫓아내는 셈입니다.

우리가 귀중한 1GB VRAM을 그냥 놀려둘 이유가 있을까요? 레이어 두 개가 빠지면 생성 속도는 20%에서 30%씩 깎여나갑니다.

투기적 샘플링 역시 함정이 도사리고 있습니다. DFlash나 MTP 보조 모델을 붙이기만 하면 무조건 빨라질 것이라 믿기 쉽습니다.

하지만 실제로는 속도가 더 떨어지는 경우가 흔합니다.

이유가 무엇일까요? 신뢰도 컷오프 설정이 빠졌기 때문입니다. 가벼운 보조 모델은 코드나 수학에서는 훌륭한 추측을 내놓지만, 서술형 글쓰기나 일상 대화에서는 엉뚱한 추측을 쏟아냅니다. 본 모델이 매번 이를 기각하면서 메모리 버스 대역폭만 낭비하게 됩니다.

구체적인 하드웨어와 모델 조합을 바탕으로 실측을 거치지 않는다면 모든 계산은 어림짐작에 불과합니다.

## 2. spilltune의 측정 방식: 네 가지 평가 과제와 자동 등산 탐색

spilltune의 구조는 간결합니다.

무거운 딥러닝 종속성 없이 순수 파이썬 스크립트로 로컬의 llama-server 바이너리를 직접 호출합니다.

탐색 과정은 세 단계로 명확히 나뉩니다:

```text
1단계: VRAM 한계 경계 측정
기본 1024MB 예약에서 512MB, 256MB로 좁혀가며 튕기지 않는 최대 GPU 레이어 탐색

2단계: 투기적 샘플링 보조 파라미터 등산
보조 모델 규격 감지, 초기 추측 수 탐색, 신뢰도 임계값 스위프를 통한 최적 수락률 탐색

3단계: 다분야 종합 평가
수학, 코드 생성, 개념 설명, 창작 글쓰기 네 영역에서 출력을 검증하고 최종 명령어 도출
```

평가 설계를 눈여겨볼 만합니다. 시중의 벤치마크 스크립트들은 귀찮다는 이유로 Hello World 같은 단발성 문장만 돌리곤 합니다. 단순한 인사말 하나로 실제 코딩 생성 속도를 가늠할 수 있을까요? 짧은 질문에서는 보조 모델 적중률이 왜곡되어 숫자가 부풀려집니다.

spilltune은 수학적 추론, 코드 작성, 개념 설명, 서사 창작이라는 완전히 성격이 다른 네 가지 내장 프롬프트를 갖추고 있습니다.

각 시험 라운드는 192개 토큰 생성을 고정적으로 수행합니다.

왜 네 가지 분야를 모두 측정해야 할까요?

실측 경험상 투기적 샘플링 보조 모델은 코드와 수학 문제에서 70% 이상의 수락률을 기록하지만, 발산적인 창작 영역에서는 30% 이하로 급락하기 일쑤이기 때문입니다.

특정 분야에서 보조 모델이 오히려 손해를 끼치는 경우, spilltune은 터미널에 두 가지 권장 명령어를 솔직하게 내놓습니다: 코딩 작업 시에는 보조 모델 파라미터를 활성화하고, 창작 작업 시에는 보조 모델을 끄라는 식입니다.

## 3. 실전 투입: RTX 3060 12GB 환경에서 31B 모델 한계 돌파

spilltune의 실제 성능을 검증하기 위해 Windows 11 환경의 테스트 머신에서 전체 파이프라인을 구동했습니다.

하드웨어 제원은 다음과 같습니다:

- 프로세서: Intel Core i5-14600KF
- 그래픽: NVIDIA GeForce RTX 3060 12GB
- 메모리: 32GB DDR4-3200 듀얼 채널
- llama.cpp 빌드: b11798
- 대상 모델: Gemma 4 31B Instruct Q4_K_M, 용량 17.1GB, 60레이어
- 보조 모델: Gemma 4 31B DFlash Q4_K_M, 용량 0.85GB

튜닝 명령을 내리기 전 필수적인 전처리 과정이 있습니다: VRAM을 점유하는 백그라운드 프로그램을 완전히 정리해야 합니다. 브라우저 하드웨어 가속과 그래픽 툴을 모두 종료하고 GPU를 빈 상태로 둡니다.

설치 및 실행 명령어:

```bash
# GitHub 최신 커밋에서 직접 설치
pip install git+https://github.com/0xydendrum/spilltune

# 메인 모델과 보조 모델을 지정하여 전자동 튜닝 시작
spilltune gemma-4-31B-it-Q4_K_M.gguf --draft gemma4-31b-it-dflash-Q4_K_M.gguf
```

터미널이 실행되면 하드웨어 감지 정보가 출력됩니다:

```text
Hardware: NVIDIA GeForce RTX 3060 12 GB (0.4 GB in use); RAM 32 GB (25 GB free)
Model:    gemma-4-31B-it-Q4_K_M.gguf: 17.1 GB, 60 layers, dense
Helper:   gemma4-31b-it-dflash-Q4_K_M.gguf: 0.85 GB, --spec-type draft-dflash
          6.9 GB of it has to live in system RAM.
```

상황이 투명하게 드러납니다: 6.9GB 분량의 가중치는 시스템 RAM에 남을 수밖에 없습니다.

자동 탐색이 본격적으로 시작됩니다.

첫 라운드는 llama-server 기본 설정값 기반의 기준선 측정입니다:

```text
Stage 1/3: where the model's layers go (GPU vs RAM)
  trial  1  baseline: llama-server defaults ...
            3.4 tokens/sec, 31/61 layers on GPU
```

기본 상태에서는 GPU에 31개 레이어만 올라가며, 출력 속도는 초당 3.4토큰에 머물렀습니다.

이어서 spilltune은 VRAM 예약 마진을 1024MB에서 512MB, 384MB로 점진적으로 깎아 내려갑니다.

GPU 쪽 레이어는 31개에서 38개로 착실히 늘어납니다.

2단계에 접어들며 보조 모델이 개입하고, 추측 단계 수와 신뢰도 컷오프 임계값이 조합됩니다.

15번째 시험에서 등산 알고리즘이 최대 속도 지점을 포착했습니다:

```text
  trial 15  dflash helper, 6 guesses, confidence cut-off 0.7, 384 MiB less VRAM held back ...
            6.5 tokens/sec, 66% of guesses accepted, 21/61 layers on GPU

BEST for one chat: 6.5 tokens/sec (1.92x the defaults' 3.4)
```

추측 6회, 신뢰도 컷오프 0.7, VRAM 예약 384MB.

생성 속도는 초당 3.4토큰에서 초당 6.5토큰으로 껑충 뛰었습니다.

1.92배에 달하는 성능 도약입니다.

VRAM 여유 공간을 384MB까지 줄여도 정말 안정적일까요?

실행 도중 갑자기 튕기지는 않을까요?

전체 테스트를 마치는 동안 오류 없이 안정적으로 완주했습니다. 품질 저하도 관찰되지 않았습니다. 전량 VRAM 구동 결과와 코드 및 수학 문제 출력을 일일이 대조해 보았으나, 샘플링 무작위성에 따른 미세한 어휘 차이를 제외하면 답변 정확도에 결함은 없었습니다.

보조 모델을 MTP 형식으로 교체했을 때는 13번째 시험에서 초당 8.9토큰을 기록하며 기본 설정 대비 2.61배의 가속을 달성했습니다.

전체 과정은 32분 만에 무인으로 완료되었으며, 터미널에는 즉시 복사해 사용할 수 있는 최종 구동 명령어가 출력되었습니다:

```bash
# spilltune이 권장하는 실전 구동 원라이너 명령어
llama-server.exe -m gemma-4-31B-it-Q4_K_M.gguf -c 4096 -np 1 \
  --fit on --fit-target 2098 \
  -md gemma4-31b-it-dflash-Q4_K_M.gguf -ngld 99 \
  --spec-type draft-dflash --spec-draft-n-max 6 --spec-draft-p-min 0.7
```

동시에 로컬 경로에 report.html 파일이 생성되어 각 라운드의 레이어 배치율, 추측 수락률, 메모리 점유율을 한눈에 확인할 수 있습니다.

## 4. MoE 모델의 특수성: 많이 추측할수록 왜 오히려 느려질까

Gemma 4 26B-A4B 같은 MoE 전문가 혼합 모델을 테스트할 때 직관을 거스르는 현상을 목격했습니다.

상식적으로는 보조 모델이 멀리 내다보고 추측할수록, 적중률만 받쳐준다면 더 빨라져야 마땅합니다. 그렇지 않을까요?

하지만 MoE 구조에서는 이 규칙이 정반대로 작용합니다.

실측 데이터 표를 살펴보겠습니다:

| 설정 | 수학 과제 | 코딩 과제 | 개념 설명 | 창작 글쓰기 |
| :--- | :--- | :--- | :--- | :--- |
| MoE 기본값 보조 모델 없음 | 39.8 t/s | 40.4 t/s | 40.1 t/s | 39.7 t/s |
| DFlash 보조 모델 8단계 추측 | 37.4 t/s | 45.7 t/s | 23.4 t/s | 20.5 t/s |
| DFlash 보조 모델 2단계 추측 | 50.8 t/s | 51.8 t/s | 37.7 t/s | 31.8 t/s |

맨 오른쪽 열에 주목해 보십시오.

추측 단계를 8단계로 잡았을 때 창작 글쓰기 속도는 기존의 40 안팎에서 초당 20.5토큰으로 반 토막이 났습니다.

왜 많이 내다볼수록 느려지는 것일까요? 메인 메모리에서 전문가 가중치를 교체하느라 시간을 허비하는 것은 득보다 실이 크지 않을까요?

이유는 MoE의 전문가 가중치가 방대하여 시스템 메모리에 상주할 수밖에 없기 때문입니다. 추측된 8개 토큰이 각기 다른 전문가 경로로 분기되면, CPU는 메모리에서 서로 다른 전문가 가중치를 쉴 새 없이 스왑해야 합니다.

가혹한 메모리 버스 경합이 투기적 샘플링의 작은 이득을 완전히 집어삼켜 버립니다.

오히려 추측 단계를 2단계로 제한하자 전문가 라우팅 빈도가 안정되며 코딩과 수학 생성 속도가 초당 50토큰을 가뿐히 돌파했습니다.

보고서는 명확한 결론을 내립니다: MoE 환경에서는 투기 단계를 보수적으로 잡아야 하며, 글쓰기 작업에서 병목이 생기면 보조 모델을 과감히 꺼야 합니다. 직접 실측해 보는 것이 방대한 문서를 뒤적이는 것보다 훨씬 빠르고 명확합니다.

## 5. 실전 제약과 주의 사항

유용한 도구이지만 물리적인 한계선도 뚜렷합니다.

시작하기 전 다음 네 가지 제약을 확인해야 합니다:

첫째, 컨텍스트 길이 문제입니다. spilltune은 기본적으로 4096 컨텍스트를 기준으로 VRAM 여유분을 계산합니다. 실무에서 32K 이상의 장문을 주로 다룬다면 명령어에 명시적으로 `--ctx 32768`을 주어야 합니다. 이 옵션을 빼먹으면 4K 기준으로 쥐어짠 VRAM 할당 때문에 긴 문서를 넣자마자 OOM으로 서버가 즉사합니다. 실제 업무 환경에 맞는 컨텍스트 길이를 설정하셨습니까?

둘째, 보조 모델의 혈통 문제입니다. 보조 모델은 메인 모델과 아키텍처 및 토크나이저 계보가 완전히 일치해야 합니다. Qwen 보조 모델을 Gemma에 붙이면 첫 로딩 단계에서 즉각 에러를 내며 멈춥니다.

셋째, 단일 GPU 한계입니다. 현재 spilltune은 단일 그래픽카드 환경의 오프로딩만 지원하며, 멀티 GPU 분산 탐색 기능은 아직 지원하지 않습니다.

넷째, 플랫폼 호환성입니다. 이번 검증은 Windows 11과 CUDA 환경에서 진행했습니다. Apple Silicon 장비는 통합 메모리 구조이므로 PCIe 버스 대역폭 병목 자체가 존재하지 않아 이 도구를 통한 튜닝의 실익이 적습니다.

하드웨어 스펙은 고정되어 있지만 파라미터 조율은 엔지니어의 손에 달려 있습니다.

30분간 스크립트를 돌려 보수적인 설정으로 낭비되던 메모리 대역폭을 되찾아오는 것이 초당 3.4토큰에 만족하는 것보다 훨씬 생산적입니다. 그래픽카드가 메모리 벽에 부딪히기 전에 물리적 한계치를 한 번쯤 탐색해 보지 않으시겠습니까?
