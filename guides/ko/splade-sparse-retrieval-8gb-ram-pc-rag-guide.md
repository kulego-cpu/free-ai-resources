# 8GB 메모리 구형 PC에서 개인 지식 베이스 구축하기: SPLADE 희소 검색으로 고밀도 벡터 대체 실측

고성능 외장 그래픽카드가 없는 구형 산업용 PC나 5년 전 구매한 8GB 메모리 노트북에서 로컬 지식 베이스를 구축할 때 VRAM 부족은 가장 먼저 마주하는 물리적 장벽입니다.

오프라인 문서 검색 파이프라인을 구성할 때 일반적인 구현 방식은 고밀도 임베딩 모델에 의존합니다. 파라미터 수가 비교적 작은 Qwen3-Embedding-0.6B를 선택하더라도 대량의 문서 청크를 한 번에 처리하면 시스템 메모리와 VRAM은 즉시 한계에 도달합니다. 커뮤니티에서 자주 언급되는 8B급 모델을 시도할 경우 정적 가중치를 적재하는 것만으로도 8GB 메모리 환경은 즉시 정지합니다.

물리 메모리는 8GB에 불과하며 운영체제 자체가 2GB 이상을 기본 점유합니다. 임베딩 파이프라인에 할당할 수 있는 용량은 기껏해야 1GB에서 2GB 수준입니다.

이러한 하드웨어 제약 속에서 로컬 프라이빗 지식 베이스를 구동하려면 고가의 그래픽카드를 추가 구매하는 길뿐일까요. 저사양 장비는 RAG 구현에서 완전히 배제되어야 할까요.

최근 오픈소스 커뮤니티에서 매우 실용적인 대안이 공유되었습니다. 기술 포럼에서 SPLADE 희소 신경망 검색을 활용하여 기존 고밀도 임베딩 모델을 대체한 정밀 실측 결과가 공개되었습니다.

커뮤니티의 1차 논의와 상세 벤치마크 기록은 다음 스레드에서 확인할 수 있습니다:
https://www.reddit.com/r/LocalLLaMA/comments/1xpdk0i/

수백 건의 실제 다국어 질의를 통한 평가 결과, SPLADE는 다국어 검색 정확도에서 Qwen3-0.6B 고밀도 모델을 앞서면서도 추론 시 VRAM 사용량을 1.5GB 미만으로 엄격히 억제했습니다.

신경망 의미 해석과 키워드 역색인을 결합한 이 희소 검색 방식이 구형 장비에서 실질적인 프로덕션 성능을 낼 수 있을까요. 실제로 그렇게 가볍게 작동할까요.

직접 실측하기 전까지는 저 역시 의구심을 거두지 못했습니다.

보관 중이던 구형 PC를 꺼내 실제 테스트 파이프라인을 구축하고 하드웨어 자원 소모량을 검증했습니다.

## 하드웨어 예산과 고밀도 벡터의 숨은 비용

검색 증강 생성을 처음 다루는 엔지니어는 벤치마크 점수의 화려함에 현혹되기 쉽습니다.

벡터 차원 수가 높고 모델 크기가 클수록 검색 품질이 우수할 것이라 가정하지만, 실무에서 고차원 고밀도 벡터는 무거운 자원 비용을 수반합니다:

- 정적 VRAM 점유의 과다. bfloat16 정밀도 기준에서도 0.6B 고밀도 모델은 단일 질의를 처리하기 전 정적 가중치만으로 1.2GB 이상의 메모리를 차지합니다；
- 배치 색인 처리 시 메모리 급증. 수만 건의 문서 청크에 대해 고차원 내적과 코사인 유사도 연산을 수행할 때 순간 메모리 사용량은 3GB를 쉽게 초과합니다；
- 역색인 구조 활용 불가. 고밀도 벡터는 근사 최근접 탐색을 위한 전용 벡터 데이터베이스를 요구하므로 색인 생성 시 막대한 CPU 연산이 소모됩니다.

이 하드웨어 비용을 면밀히 검토해야 합니다.

검색 모델을 SPLADE와 같은 희소 신경망 검색으로 전환하면 데이터 표현 방식이 근본적으로 바뀝니다.

SPLADE의 핵심 메커니즘은 2021년 NAVER Labs Europe에서 발표한 어휘 확장 아키텍처에 기반합니다. 사전 학습 모델을 활용하여 전체 어휘집에 대한 각 단어의 가중치 분포를 예측하고 희소 벡터를 직접 출력합니다.

더 직관적으로 설명하자면, 출력 결과는 의미를 파악하기 힘든 수천 차원의 조밀한 부동소수점 배열이 아니라 문서 내 주요 키워드와 유의어에 직접 매겨진 중요도 가중치입니다.

이 가중치는 안정적인 기존 역색인 엔진에 그대로 적재할 수 있습니다.

순수 CPU 환경이나 1.5GB 미만의 가용 메모리 환경에서 검색 연산은 단어 빈도 가중치 표를 조회하는 가벼운 사전 참조 작업으로 전환됩니다. 방대한 고차원 유사도 계산이 생략되고 작업 메모리는 매우 낮은 수준에 고정됩니다.

구형 PC에서도 연산에 여유가 생기며 메모리 부담이 크게 감소합니다.

## BEIR-13 벤치마크 실상과 다국어 격차

검색 알고리즘의 우수성을 평가할 때는 실제 업무 환경의 데이터에 기반해야 합니다.

원작자의 테스트 데이터는 실제 데스크톱 환경을 충실히 반영하여 시스템 매뉴얼, 로그, 메모 등 한국어를 중심으로 영어가 혼합된 다국어 문서를 대상으로 구성되었습니다.

수백 건의 평가 질의에서 SPLADE는 Qwen3-Embedding-0.6B 모델 대비 높은 재현율을 달성했습니다. 질의 응답 시간은 대등한 밀리초 수준을 유지했습니다.

VRAM 점유 차이는 매우 뚜렷했습니다. SPLADE의 최대 VRAM 점유는 1.5GB 미만에 머문 반면, 고밀도 모델은 동시 요청 시 4GB 한계에 육박했습니다.

그러나 학술 표준인 BEIR-13 다중 작업 벤치마크로 시야를 넓히면 냉정한 현실이 드러납니다:

- SlideOn 희소 모델: 종합 점수 58.7；
- KURE-Sparse-base 모델: 종합 점수 58.6；
- linkup-sparseup 모델: 종합 점수 58.1；
- KURE-Sparse-nano 모델: 종합 점수 53.2.

원작자는 초기 테스트에서 가장 크기가 작은 KURE-Sparse-nano를 적용했습니다.

하지만 벤치마크 결과를 대조해 보면 SlideOn 모델은 거의 동일한 파라미터 규모를 유지하면서도 5포인트 이상 높은 검색 품질을 기록했습니다.

이것이 무엇을 의미할까요. 모델 크기를 줄이면 검색 품질 저하가 필연적으로 따르는 것일까요.

사실은 명확합니다.

다국어 검색 환경에서 초소형 희소 모델은 학습에 사용된 토크나이저 어휘집에 극도로 민감합니다. 대상 언어의 어휘가 충분히 반영되지 않은 경우 미등록 단어에 대한 어휘 확장이 즉시 무력화됩니다.

BEIR-13 기준 5.5포인트의 점수 차이는 실무에서 20회 검색 중 1회 꼴로 핵심 기술 문서를 놓치는 결과로 이어집니다. 수십 메가바이트의 디스크 용량을 아끼기 위해 핵심 문서의 재현율을 포기하는 것은 합리적인 엔지니어링 선택이 아닙니다.

적합한 모델 변형을 선별하는 작업은 필수적입니다. 모델 선정 과정을 임의로 생략해서는 안 됩니다.

## 커뮤니티 논쟁과 기존 기술의 재평가

이번 실측 결과는 기술 커뮤니티에서 활발한 토론을 촉발했습니다.

첫 번째 쟁점은 기술적 참신성에 관한 지적이었습니다. 일부 시니어 엔지니어들은 SPLADE가 5년 전 발표된 기술이며 현대의 다국어 표준인 BGE-M3에도 이미 희소 검색 경로가 기본 탑재되어 있음을 강조했습니다.

개인 PC 환경에서 8B 임베딩 모델을 구동하는 것이 과연 합리적인 선택인가.

이러한 지적에 대해 기업 프라이빗 구축을 담당하는 실무 엔지니어들이 반론을 제기했습니다. 하드웨어 자원이 제한적인 환경에서도 8B급 최고 사양 모델을 요구하는 고객이 여전히 다수 존재한다는 현실입니다.

파라미터 규모에 대한 맹신은 실제 구축 현장에서 심각한 하드웨어 낭비를 초래합니다.

두 번째 쟁점은 검색 파이프라인의 계층화 설계에 관한 실질적인 제언이었습니다. 단일 모델 크기에 집착하기보다 전체 파이프라인 구조를 정교화해야 한다는 분석입니다.

예를 들어 33M 수준의 경량 모델인 gte-small을 적용하고 적절한 청크 중첩, 메타데이터 필터링, BM25 1차 선별을 결합할 경우 대형 모델을 단독으로 구동하는 방식보다 우수한 검색 품질을 얻을 수 있습니다.

일부 커뮤니티 사용자는 상업적 홍보성 게시물이 아니냐는 의문을 제기하기도 했습니다.

그러나 지나치게 경계할 이유는 없다고 판단합니다.

5년 전 검증된 학술 성과를 활용하여 구형 하드웨어에서 1.5GB 미만의 추론 환경을 구현한 것은 이론적 논쟁보다 훨씬 실용적인 가치를 지닙니다.

## 실기 배포: 최소 구성과 환경 오류 대처

구형 PC에서 SPLADE 희소 검색을 구동하는 과정은 가볍습니다.

공식 권장 환경은 HuggingFace 라이브러리나 경량화된 fastembed 도구를 활용하는 방식입니다. Python 3.10 환경에서 종속성 패키지를 설치합니다:

```bash
pip install fastembed
```

Python 인터페이스를 통해 모델을 초기화하고 단어 가중치를 추출합니다:

```python
from fastembed import SparseTextEmbedding

model = SparseTextEmbedding(model_name="prithivida/Splade_PP_en_v1")

documents = [
    "Ubuntu 22.04 LTS kernel configuration for low memory systems",
    "How to manage Docker network bridge on local workstations"
]

embeddings = list(model.embed(documents))
print("Sparse Indices:", embeddings[0].indices[:8])
print("Sparse Values:", embeddings[0].values[:8])
```

구형 Linux 테스트 머신에서 처음 실행했을 때 터미널에 즉시 오류가 발생했습니다.

오류 내용은 명확했습니다: RuntimeError: Failed to import onnxruntime for sparse token inference.

프로세스가 그 자리에서 중단되었습니다.

환경 종속성을 확인한 결과 구형 x86 환경용 미니멀 배포판에는 C++ 런타임 라이브러리가 기본 누락되어 있었습니다. apt-get install -y libgomp1 명령을 통해 OpenMP 런타임을 보완하자 정상적으로 추론이 완료되었습니다.

누락된 라이브러리만 추가하면 즉시 해결되며 벡터 추출 과정의 메모리 점유는 800MB 미만에 머물렀습니다. 냉각팬도 조용하게 유지되었습니다.

## 엔지니어링 한계와 선택 기준

이번 실측을 통해 저사양 환경에서 SPLADE 희소 검색의 도입 기준이 명확해졌습니다.

적합한 도입 시나리오:
- 메모리가 제한된 구형 장비. 8GB 메모리 환경에서 상주 모델에 2GB 이상의 VRAM을 할당할 수 없는 장비；
- 키워드 정확도가 핵심인 업무. 법률 조항, 시스템 오류 로그, 부품 품번 등 단 한 글자의 오차도 허용되지 않는 문서군；
- 장기 운용되는 오프라인 환경. 분산 벡터 DB를 운영하지 않고 SQLite나 기존 역색인에 직접 저장하려는 환경.

적합하지 않은 시나리오:
- 추상적 의미에 기반한 교차 검색. 키워드 일치가 전무하며 감정이나 비유적 표현에 의존하는 질의；
- 초대형 문서의 단일 청크 처리. 수만 자의 문서를 사전 분할 없이 입력할 경우 어휘 확장에 의해 색인 용량이 급증합니다.

파라미터 규모 경쟁에서 벗어나 시스템 메모리와 VRAM의 실질적 비용을 냉정하게 계산해야 합니다.

8GB 메모리의 구형 PC에서 초대형 고밀도 모델을 구동할 수 없다면 1.5GB 미만으로 작동하는 희소 검색 아키텍처를 도입하여 로컬 지식 베이스를 안정적으로 운영할 수 있습니다. 정확한 키워드 검색을 요구하는 업무 환경이라면 다음 프라이빗 시스템 구축 시 희소 검색 모듈을 테스트해 볼 가치가 충분하지 않을까요.
