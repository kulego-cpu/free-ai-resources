# 8GB VRAM 콘솔 게임기로 MoE 대규모 모델 구동: 단 하나의 설정만 효과가 있었던 이유

보급형 하드웨어로 로컬 모델을 구동할 때 가장 빠지기 쉬운 함정은 다른 사람의 설정값을 무비판적으로 따라 하는 것입니다.

커뮤니티에서 기적의 튜닝이라 불리는 수치도 내 메인보드에 적용하면 효과가 없거나, 오히려 토큰 처리 속도를 떨어뜨리는 일이 흔합니다.

작업대에 올린 기기는 거실에서 퇴역한 Valve Steam Machine 커스텀 모델입니다.
운영체제는 순정 SteamOS 3.9.5.
핵심 GPU는 8GB 독립 VRAM을 갖춘 AMD Navi 33 구성입니다.
메인보드에는 DDR4 램 2개가 장착되어 총 32GB 용량을 갖추었습니다.
저장장치는 평범한 NVMe 솔리드 스테이트 드라이브를 사용합니다.

일반적인 기준에서 8GB VRAM으로 방대한 혼합 전문가 모델을 구동한다는 것은 상상하기 어렵습니다.

하지만 극저비트 3진법 양자화 기술의 발전은 대단히 빠릅니다.

최근 공개된 Qwen3.8 Flash-Next Gyro S는 TQ1_0 수준의 3진법 압축을 적용했습니다.
전체 가중치 용량이 10여 기가바이트 수준으로 대폭 축소되었습니다.
8GB VRAM과 시스템 메모리를 결합하여 실제 구동 가능한 환경이 마련된 것입니다.

LocalLLaMA 포럼의 실전 테스터가 이 하드웨어 스택에 대한 상세한 벤치마크를 공개했습니다:
https://www.reddit.com/r/LocalLLaMA/comments/1xq8s2n/

작성자는 여러 미세 조정 옵션의 실제 디코딩 속도 변화를 기록했습니다.

결과는 대단히 흥미로웠습니다. 유명한 추천 설정들이 줄줄이 무용지물로 판명된 반면, 단 하나의 옵션만이 압도적인 속도 상승을 이끌어냈습니다. 이 옵션에는 과연 어떤 비밀이 숨어 있었을까요.

## 1. 기준 테스트 환경과 순정 기본 성능

테스트 환경은 Strata 터미널 0.2.9 버전을 기반으로 하며, 하부에서는 AMD 하드웨어에 맞춰 빌드된 HIP 추론 엔진 0.1.55 브랜치를 호출합니다.

한계 성능을 시험하기 위해 문맥 윈도우는 128K까지 늘렸습니다.
멀티모달 시각 모듈은 비활성화했습니다.
투기적 멀티 토큰 예측도 껐습니다.
KV 캐시는 메모리 절약을 위해 q4_0 정밀도로 양자화했습니다.

초기 기준 테스트는 어떠한 수동 조정도 배제한 순정 기본 상태로 진행했습니다.

입력 프롬프트 길이는 약 8,000 토큰으로 고정했습니다.
테스트는 연속 3회 실행하여 콜드 스타트의 영향을 제외한 중앙값을 산출했습니다.

수동 조정을 거치지 않은 순정 상태에서 Navi 33 콘솔이 기록한 수치는 다음과 같습니다:

프롬프트 프리필 속도는 초당 219에서 240 토큰 사이를 안정적으로 유지했습니다.

이어지는 자기회귀 디코딩 속도는 초당 15.1에서 15.9 토큰 수준을 맴돌았습니다.

8GB VRAM을 갖춘 구형 거실 콘솔에서 128K 문맥을 유지하며 초당 15자 안팎을 처리한다면, 작은 스크립트 작성이나 오프라인 기술 문서 검색용으로는 충분히 합격점입니다.

하지만 커뮤니티에 다양한 가속 비법이 공유되는 상황에서 기본값에만 안주할 테스터는 없습니다. 호기심이 발동하면 테스트를 멈추기 어렵습니다.

## 2. 커뮤니티 튜닝 옵션 검증: 실효성이 없었던 3가지 설정

가장 먼저 시험한 것은 엔진 자체에 내장된 고속 자동 튜너였습니다.

명령어를 실행하자 몇 줄의 하드웨어 감지 로그가 스쳐 지나간 뒤, 현재 구성이 이미 가장 빠른 상태라는 안내와 함께 튜닝 단계가 곧바로 생략되었습니다.

실측 데이터 역시 이를 증명했습니다.
프리필 속도는 초당 237에서 239 토큰을 기록했습니다.
디코딩 속도는 초당 14.5에서 17.2 토큰 사이를 오르내렸습니다.
편차가 기본 상태보다 오히려 커졌을 뿐 실질적인 개선은 없었습니다.

두 번째 시도는 많은 이들이 권장하는 PCIe 버스 대역폭 분할 비율 매개변수였습니다:

```bash
strata-server --model qwen3.8-flash-next-gyro-s-tq1_0.gguf --set pcie-frac=0.35
```

휴대용 게임기 커뮤니티에서는 이 설정이 메인 메모리와 VRAM 간의 전송 병목을 줄여준다고 널리 알려져 있었습니다.

하지만 실제 측정 결과는 어떠했을까요.
3회 측정 중앙값에서 프리필은 초당 239 토큰, 디코딩은 초당 14.8에서 16.0 토큰에 머물렀습니다.

속도 그래프는 기본 상태와 오차 없이 겹쳤습니다.

아무런 변화도 없었습니다.

원작자가 측정한 0.35라는 수치는 자신의 메인보드 대역폭과 컨트롤러 지연 특성에 맞춘 고유 결과물에 불과합니다. 다른 기기에서 이를 맹목적으로 모방해 봐야 심리적 위안 외에 실측상의 이득은 없습니다.

세 번째 시도는 직관적으로 선택하기 쉬운 VRAM 예약 공간 확대였습니다.

VRAM이 부족하다면 중요 가중치를 단단히 고정하고 900MB 정도의 안전 마진을 강제로 남겨두는 편이 메모리 스왑 충격을 완화할 것이라 생각하기 쉽습니다.

```bash
strata-server --set kv-resident=20480 --set vram-reserve=900
```

실측 결과는 이러한 기대를 벗어났습니다.
프리필 속도는 초당 227에서 229 토큰으로 하락했습니다.
디코딩 속도 역시 초당 14.8에서 15.5 토큰에 그쳤습니다.

빨라지기는커녕 미세하게 속도가 떨어졌습니다.

헛수고였습니다.

VRAM 예약 공간을 무리하게 늘리면 연산용 작업 공간이 좁아집니다. 셰이더 코어가 어텐션 행렬 곱셈을 수행할 때 가용 버퍼가 축소되어 병목이 발생한 것입니다.

기대했던 3가지 옵션이 모두 성과를 내지 못한 상황에서, 이 기기의 성능은 초당 15 토큰에서 고정된 것일까요.

## 3. 유일한 돌파구: 전문가 레이어를 엔진 자체 메모리 영역에 잠금

테스트가 난관에 부딪혔을 때, 포럼 목록에 적혀 있던 네 번째 매개변수를 터미널에 입력했습니다:

```bash
strata-server --model qwen3.8-flash-next-gyro-s-tq1_0.gguf --set resident-budget-gib=64
```

8,000 토큰 프롬프트로 재측정을 진행하자 놀라운 수치가 출력되었습니다:

프리필 속도는 초당 232에서 242 토큰을 유지했습니다.

디코딩 속도는 단숨에 초당 17.3에서 19.8 토큰까지 급등했습니다.
평균 수치는 초당 18 토큰 선에 안착하며 약 20%의 확실한 성능 향상을 입증했습니다.

다른 매개변수들은 반응이 없었는데, 어째서 이 수치를 64로 지정한 것만으로 속도 한계를 돌파할 수 있었을까요.

원인은 운영체제의 메모리 관리 메커니즘과 혼합 전문가 모델의 동작 특성 사이의 충돌에 있었습니다.

이 설정을 적용하기 전, 시스템 모니터로 메모리 상태를 확인했습니다:

```bash
free -m
cat /proc/meminfo | grep -E "Active|Inactive|Cached"
```

기이한 상황이 관찰되었습니다.
물리 메모리는 32GB에 달하지만, 시스템에서 사용 중으로 잡힌 메모리는 줄곧 5GB 미만이었습니다.

반면 파일 캐시 항목에는 28GB에 달하는 데이터가 가득 차 있었습니다.

이것은 무엇을 의미할까요.

명시적인 상주 예산이 지정되지 않으면 리눅스 커널은 VRAM에 들어가지 못한 전문가 가중치를 일반 파일로 취급하여 OS 페이지 캐시로 넘겨버립니다.

특정 전문가 네트워크가 호출되면 엔진은 메모리에 데이터를 요청합니다. 커널은 페이지 캐시에서 이를 찾아 활성 메모리로 올리고, 토큰 연산이 끝나면 다시 비활성 데이터로 분류합니다.

운영체제는 페이지 교체와 상태 관리, 유저 공간과 커널 공간 사이의 데이터 복사에 계속해서 시간을 허비하고 있었습니다.

이 지연 시간은 1회당 수십 마이크로초에 불과하지만, MoE 모델은 토큰 1개를 생성할 때마다 여러 전문가를 넘나듭니다. 수만 번의 데이터 이동이 누적되면서 전체 연산 처리량의 20%를 잠식하고 있었던 것입니다.

이 설정을 추가하는 것은 런타임 할당자에게 전문가 레이어를 유저 공간의 전용 메모리 풀에 상주시키고, 커널이 이를 파일 캐시로 내쫓지 못하도록 지시하는 것과 같습니다.

불필요한 데이터 교환이 사라지면서 초당 3토큰의 정직한 속도 상승이 나타난 것입니다.

## 4. 128K 극한 문맥 부하 테스트와 현실적인 한계

단문 테스트에서 효과를 보았더라도 실제 128K 극한 문맥에서 메모리 부족 현상 없이 버틸 수 있을까요.

안정성을 검증하기 위해 58,000 토큰과 61,000 토큰이라는 대규모 테스트 입력을 연이어 주입했습니다.

이것은 연산력뿐 아니라 물리 메모리의 한계를 정면으로 시험하는 과정입니다.

약 6만 토큰의 입력에 대해 두 테스트 모두 약 4분간의 프리필을 거쳐 각각 초당 234 토큰 및 236 토큰을 기록했습니다.

이어지는 디코딩 단계에서 생성 속도는 초당 17.6에서 17.9 토큰 사이를 안정적으로 유지했습니다.

프로세스 강제 종료는 발생하지 않았습니다. 스왑 사용량은 0.2GB에서 0.3GB로 소폭 증가하는 데 그쳤고, 가용 물리 메모리도 3.4GB 이상을 지켜냈습니다. 128K 문맥 창을 무리 없이 완주한 것입니다.

이후 커뮤니티의 다른 사용자가 16GB 메모리 사양의 Steam Deck에서 동일한 테스트를 재현했습니다.
디코딩 속도는 초당 21 토큰까지 올라갔습니다.

하지만 대가도 분명했습니다. 전체 메모리가 16GB에 불과하여 메모리 압박으로 인해 KV 캐시가 약 4GB로 제한되었고, 긴 문맥 수용 능력은 크게 줄어들었습니다. 한정된 하드웨어에서 속도와 문맥 길이 중 무엇을 취할지는 사용자의 판단에 달려 있습니다.

또한 1비트 3진법 가중치의 실용성에 대해서도 정상적인 문장 생성이 가능한지 의문이 제기되곤 합니다.

실측 결과 일상적인 대화에서는 문체가 다소 단조로울 수 있으나, 코드 문맥 해석이나 파이썬 도구 함수 작성, JSON 구조화 변환 같은 작업에서는 대단히 안정적인 완성도를 보여주었습니다. 로컬 보조 도구로 활용하기에 충분한 실용성입니다.

## 5. 구형 게임기 활용 실전 요약과 주의사항

이번 테스트를 바탕으로 AMD 그래픽카드나 구형 콘솔을 활용하려는 엔지니어를 위해 몇 가지 핵심 주의사항을 정리합니다:

첫째, 타인의 버스 분할 비율이나 미세한 VRAM 예약 설정을 모방하는 데 시간을 쓰지 말 것. 보드 칩셋과 드라이버 환경이 다르면 미세 수치는 대부분 효과가 없습니다.

둘째, MoE 모델 추론 시 전문가 가중치가 OS 파일 캐시에 갇혀 있지 않은지 점검할 것. 물리 메모리가 충분하다면 상주 예산을 명시하여 전문가 레이어를 유저 공간에 묶어두는 것이 핵심입니다.

셋째, 초저비트 양자화는 저사양 기기를 위한 진입로라는 점을 분명히 인식할 것. 코드 작성이나 정형화된 작업에는 훌륭하지만, 클라우드 최고 성능 모델과 같은 심층 철학적 추론을 기대해서는 안 됩니다.

야심한 밤 거실 구석에서 컨트롤러를 내려놓은 게임기가 터미널 텍스트를 경쾌하게 쏟아냅니다. 서랍 속 구형 기기를 꺼내 실질적으로 작동하는 이 단 하나의 옵션을 적용해 보시겠습니까.
