# 완전 오프라인 구동 NotebookLM：SurfSense 2.3.0 과 로컬 Ollama 연동 실전 가이드

어제 오후 4시、재무팀 동료가 외주 정산 시트 하나를 들고 찾아왔습니다。

200줄이 넘는 데이터가 세 개의 시트에 나뉘어 복잡한 수식으로 얽혀 있었습니다。

동료는 로직 오류를 자동 점검하고 싶어 했지만 우측 하단의 대외비 워터마크를 보며 한숨을 쉬었습니다：법인 인감이 찍힌 계약서나 미공개 재무 문서를 제3자 클라우드 서버에 올릴 수 있는 사람이 어디 있겠습니까？

Google NotebookLM 의 교차 문서 검색은 강력하지만 데이터가 사내망을 벗어나는 순간 보안 감사 관점에서는 명백한 유출 사고로 간주됩니다。

이에 우리는 새로 업데이트된 오픈소스 프로젝트 SurfSense 2.3.0 에 주목했습니다。

Apache-2.0 라이선스로 완전 공개된 이 프로젝트는 NotebookLM 을 로컬에서 대체할 수 있다고 표방합니다。로컬에서 구동 중인 Ollama 모델과 연동하여 질의응답을 수행할 뿐만 아니라 Word 와 Excel 을 직접 수정하는 문서 Agent 기능까지 내장하고 있습니다。

RTX 4070 12GB 그래픽카드와 32GB 메모리를 탑재한 테스트 머신을 준비하고 외부 인터넷 게이트웨이를 차단하여 순수 로컬 오프라인 실측을 시작했습니다。

## 1. 컨테이너 통신과 컨텍스트 길이의 함정：첫 단계부터 터진 에러

일반적인 절차에 따라 테스트 머신에서 SurfSense 2.3.0 단일 컨테이너 이미지를 다운로드했습니다。

최신 버전의 가장 큰 진보는 아키텍처 단순화입니다。모든 의존성이 하나의 컨테이너 이미지로 통합되어 이전처럼 별도의 Postgres 데이터베이스나 Redis 큐를 구성할 필요가 없습니다。로컬 데이터 디렉토리 하나만 마운트하면 즉시 실행됩니다。

공식 실행 명령어는 다음과 같습니다：

```bash
docker run -d \
  --name surfsense \
  -p 3000:3000 \
  -v /opt/surfsense/data:/data \
  ghcr.io/modsetter/surfsense:latest
```

컨테이너는 빠르게 구동되었습니다。웹 대시보드에 접속하여 모델 엔드포인트에 `http://localhost:11434/v1` 을 입력했습니다。

연결 테스트를 누르자마자 콘솔에 붉은 에러가 출력되었습니다：Connection refused。

연결되지 않는 것은 당연합니다。컨테이너 내부의 localhost 는 컨테이너 자체 네트워크를 가리키며 호스트 머신에서 구동 중인 Ollama 와는 완전히 분리되어 있습니다。

호스트의 Ollama 는 기본적으로 127.0.0.1 만 수신 대기합니다。서비스 실행 전에 환경 변수를 지정해야 합니다：

```bash
export OLLAMA_HOST=0.0.0.0
ollama serve
```

이어서 주소를 `http://host.docker.internal:11434/v1` 로 변경하고 다시 테스트했습니다。

화면에는 또 다른 에러가 나타났습니다：dial tcp: lookup host.docker.internal: no such host。

이번에는 왜 또 실패했을까요？

테스트 머신은 Ubuntu 22.04 네이티브 리눅스 환경입니다。`host.docker.internal` 도메인은 Mac 과 Windows 의 Docker Desktop 에서만 기본 지원됩니다。순수 리눅스 Docker 환경에서는 컨테이너에 호스트 게이트웨이 매핑을 수동으로 주입해야 합니다。

실행 명령어에 호스트 매핑 옵션을 추가해야 합니다：

```bash
docker run -d \
  --name surfsense \
  --add-host=host.docker.internal:host-gateway \
  -p 3000:3000 \
  -v /opt/surfsense/data:/data \
  ghcr.io/modsetter/surfsense:latest
```

기존 컨테이너를 삭제하고 옵션을 추가하여 재실행하자 마침내 초록색 연결 성공 표시가 켜졌습니다。

터미널에서 통신 상태를 확인했습니다：

```bash
curl http://host.docker.internal:11434/v1/models
```

설치된 모델 목록이 정상적으로 반환되었습니다。네트워크 연결 작업은 끝났습니다。

그러나 더 심각한 난관이 기다리고 있었습니다。

80페이지 분량의 PDF 입찰 규격서를 업로드하고 Agent 모드로 핵심 요건을 분석시키자 로그에 에러가 쏟아졌습니다：Context window exceeded。모델은 완전히 멈추었고 커서는 그 자리에 얼어붙었습니다。

이 단계에서 모델의 지능 부족을 탓할 수 있을까요？

모델의 추론 역량 문제가 아닙니다。Ollama 가 기본 할당하는 컨텍스트 윈도우는 고작 4096 토큰에 불과합니다。문서 Agent 는 수만 자의 규격서를 읽는 동시에 긴 도구 호출 프롬프트를 앞에 붙여야 합니다。기본 4096 토큰으로는 Agent 의 첫 번째 루프조차 버티지 못합니다。

Agent 전용 Modelfile 을 작성하여 컨텍스트 상한을 확장했습니다：

```dockerfile
FROM qwen2.5:14b-instruct-q4_K_M
PARAMETER num_ctx 32768
PARAMETER temperature 0.2
```

ollama create 로 32K 윈도우 지원 모델을 빌드했습니다。

32K 컨텍스트 유지는 공짜가 아닙니다。Qwen2.5 14B 모델은 40개 레이어、GQA 8개 헤드、head_dim 128 구조입니다。fp16 기준 토큰당 약 160KB 를 소비하므로 32768 토큰이면 KV 캐시만으로 5.2GB 가 필요합니다。q4_K_M 의 8.9GB 가중치와 합치면 VRAM 총점유율은 14.6GB 로 치솟습니다。

12GB 용량의 RTX 4070 에는 전부 올라가지 않습니다。Ollama 는 일부 레이어를 시스템 메모리로 넘겼고 토큰 생성 속도는 초당 31토큰에서 초당 9토큰 안팎으로 떨어졌습니다。초고속은 아니지만 충분히 쓸 만합니다。창 크기를 32K 로 묶어둔 뒤에야 문서 Agent 가 안정적으로 동작하기 시작했습니다。

## 2. 실전 Agent 문서 편집：Word 변경 내용 추적과 Excel 수식 복구

시중의 많은 오픈소스 래퍼 도구들은 문서를 작성해 준다면서 채팅창에 마크다운 코드 블록만 뱉어내고、이를 Word 에 붙여 넣으면 서식이 전부 깨져버립니다。

SurfSense 2.3.0 이 실전에서 돋보인 지점은 바로 이 실무 편집 능력이었습니다。

기존 용역 계약서를 업로드하고 Agent 입력창에 지시를 내렸습니다：

제3조 대금 지급 조건을 수정하라：선급금 비율을 30퍼센트에서 20퍼센트로 낮추고、지체상금 요율을 일 1000분의 5로 변경하며、관련 조항 참조 번호를 자동 정합하라。

약 30초가 지나며 터미널에서 세 번의 도구 호출이 왕복했습니다。

화면에는 단순 텍스트가 아닌 새 문서 다운로드 링크가 나타났습니다。

LibreOffice 로 다운로드된 docx 파일을 열자 붉은 취소선과 푸른 메모가 포함된 네이티브 변경 내용 추적 서식이 완벽하게 적용되어 있었습니다。선급금 수치가 20퍼센트로 변경되고 타임스탬프까지 찍혀 있었습니다。이러한 네이티브 검토 서식이 채팅창 복사 붙여넣기보다 훨씬 실무적이지 않겠습니까？

Excel 수식 복구 테스트는 더욱 인상적이었습니다。

재무팀의 수식 오류 시트를 투입했습니다。원래 시트는 세율 변수를 누락하여 합계 열 전체에 VALUE 에러를 내고 있었습니다。

명령을 입력했습니다：

계산 오류를 발생시키는 모든 셀을 찾아 시트 간 참조 관계를 교정하고 수정한 새 시트를 생성하라。

모델은 내장된 분석 로직을 통해 약 40초 만에 작업을 완료했습니다。

다운로드한 xlsx 파일의 깨진 셀들은 전부 IFERROR 함수로 감싼 동적 참조 수식으로 복구되어 있었습니다。첫 번째 시트의 미편집 원본 데이터와 폰트 스타일은 완벽히 보존되었고 원본을 덮어쓰지 않고 안전하게 사본으로 출력되었습니다。시트를 넘나드는 참조 관계를 모델이 엉뚱하게 계산하지는 않았을까요？5개 수식을 무작위 추출하여 확인한 결과 셀 상대 좌표가 정확히 일치했습니다。

## 3. 로컬 음성 전사 기능과 저사양 하드웨어 퇴출선

2.3.0 버전에 추가된 또 다른 기능은 로컬 음성 파일 전사입니다。

MP3、WAV、FLAC 음성을 업로드하면 내장 엔진이 텍스트로 변환하여 지식 베이스의 인용 출처로 등록합니다。

17분 분량의 기술 회의 녹음 파일로 성능을 테스트했습니다。

외장 그래픽카드가 탑재된 머신임에도 SurfSense 의 음성 처리는 주로 CPU 자원을 사용했습니다。

16코어 CPU 사용률이 88퍼센트까지 치솟았고 쿨링팬이 최고 속도로 회전했습니다。17분 음성을 처리하는 데 3분 20초가 소요되었습니다。

텍스트 변환 품질은 훌륭했습니다：전문 기술 용어의 오인식은 단 3회에 불과했고 대부분 정확히 인식되었습니다。하지만 저사양 사무용 노트북으로 이 기능을 돌리는 것은 권장하지 않습니다。

8코어 사무용 노트북에서 동일한 17분 음성을 처리하자 키보드 표면이 손을 대기 힘들 정도로 뜨거워졌고 완료까지 12분이 걸렸습니다。도중에 메모리가 부족하여 프로세스가 강제 종료될 뻔했습니다。이것은 하드웨어를 불필요하게 혹사시키는 일이 아니겠습니까？

VRAM 역시 마찬가지입니다。6GB 나 8GB 그래픽카드에서 14B 모델과 32K 컨텍스트를 억지로 실행하면 대부분의 레이어가 시스템 메모리로 넘어가 속도가 초당 2~3토큰으로 급락합니다。

커서가 한 글자씩 멈추며 나오는 환경에서 무거운 문서 Agent 를 돌릴 이유가 어디 있겠습니까？

로컬 VRAM 안에서 쾌적하게 구동하고 싶다면 7B 모델로 내려가는 것이 현명합니다。Qwen2.5 7B 의 32K 컨텍스트는 가중치 4.7GB 와 KV 캐시 2.6GB 를 합쳐 약 7.3GB 수준입니다。12GB 그래픽카드에서 아주 여유롭게 돌아갑니다。

## 4. 장애 방지를 위한 배포 체크리스트와 현실적 한계선

완전한 오프라인 환경을 세팅한 뒤 정리한 실전 지침입니다：

첫째：설치 즉시 사용 가능이라는 문구를 맹신하지 마십시오。공식 문서에는 주소만 넣으면 된다고 적혀 있지만 리눅스 Docker 네트워크 매핑과 32K 컨텍스트 설정은 전혀 언급되지 않았습니다。이 두 설정을 잡지 않으면 첫 관문조차 통과할 수 없습니다。

둘째：하드웨어 하한선을 인정하십시오。VRAM 이 12GB 미만이라면 14B 모델에 집착하지 말고 Qwen2.5 7B 모델로 일상적 질의응답을 수행하는 것이 합리적입니다。

셋째：Agent 의 결과물은 반드시 사람이 최종 검토해야 합니다。Word 수정과 Excel 수식 복구를 자동으로 해준다고 해도 법적 책임을 지는 것은 AI 가 아니라 바로 본인입니다。

이 도구를 모든 사용자에게 무조건 권장하지는 않습니다。

12GB 그래픽카드가 기본 입장권이며 설정에 반나절을 쏟을 수 있는 끈기가 필요합니다。둘 중 하나라도 부족하다면 상용 클라우드 서비스를 사용하는 편이 시간을 아끼는 길입니다。

마지막 한마디：Agent 가 수정한 계약서는 육안으로 한 줄씩 직접 확인하십시오。책임은 모델이 아닌 사람이 집니다。

문서를 직접 꼼꼼히 검토할 준비가 되셨습니까？
