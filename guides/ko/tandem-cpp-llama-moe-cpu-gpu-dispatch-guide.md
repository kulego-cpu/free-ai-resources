# llama.cpp에 패치 적용하기：단일 4090에서 범용 MoE 생성 속도를 초당 29토큰에서 97토큰으로 끌어올린 실전 기록

로컬 머신에서 전문가 혼합 MoE 모델을 구동할 때.
가장 큰 골칫거리는 전체 매개변수 용량이 아닙니다.
절반 이상의 전문가 가중치가 시스템 메모리에 누워 잠자고 있다는 사실입니다!
라우팅 게이트가 메모리 속 전문가를 호출할 때마다 런타임 엔진은 수백 메가바이트의 파라미터를 PCIe 버스를 통해 GPU로 필사적으로 복사합니다.
PCIe 4.0 x16의 이론적 단방향 대역폭은 고작 31.5 GB/s 수준입니다.
GPU의 행렬 연산 코어는 데이터가 도착할 때까지 하염없이 공회전합니다.
터미널 커서는 초당 20자 남짓 느릿느릿 출력됩니다.
본체 쿨러 소리만 요란합니다.
화면 앞에서 멍하니 기다려야 합니다.
답답하지 않습니까?
정말 터무니없이 느립니다!

tandem.cpp 라는 오픈소스 패치의 아이디어는 투박하면서도 명쾌합니다.
버스 전송 때문에 병목이 생긴다면 아예 전송하지 마라!
시스템 메모리에 머무는 전문가는 멀티코어 CPU가 그 자리에서 직접 행렬 연산을 끝내면 됩니다.
공식 저장소의 가이드에 따라 llama.cpp에 패치를 먹이고 작업용 PC에서 이틀 동안 연속 부하 테스트를 돌렸습니다.
실제 장비에서 측정한 구체적인 벤치마크 수치와 사전에 반드시 알아두어야 할 기술적 함정을 솔직하게 공유합니다.

## 1. 왜 기존 VRAM 오프로딩은 GPU를 굶겨 죽이는가?

최고급 성능을 자랑하는 RTX 4090이 MoE 모델 앞에서는 왜 굼벵이처럼 기어가는가?
원인은 바로 버스 전송 페널티에 있습니다.
냉정한 물리적 현실입니다.

양자화 후 약 40GB 용량을 갖는 범용 MoE 모델을 예로 들어봅시다.
단일 24GB VRAM에는 전체 가중치가 다 들어가지 못합니다.
전통적인 llama.cpp의 오프로딩 방식은 매우 단순합니다.
들어가는 레이어만 VRAM에 밀어 넣고 나머지는 시스템 램에 방치합니다.
게이팅 라우터가 메모리에 남겨진 전문가를 지목하는 순간 문제가 터집니다.
런타임은 시스템 버스를 통해 가중치를 VRAM으로 긴급 수송해야 합니다.
토큰을 하나 찍어낼 때마다 버스 위로 수백 메가바이트의 데이터가 오갑니다.
GPU의 막강한 연산 능력 중 80퍼센트 이상이 데이터 도착을 기다리느라 헛돌게 됩니다!
연산 자원은 남아도는데 통로가 꽉 막힌 셈입니다.

과거에 초당 100토큰을 넘긴다고 자랑하던 일부 전용 엔진들이 있었습니다.
하지만 코드를 까보면 눈속임이 가득했습니다.
벤치마크 점수를 부풀리기 위해 뒷단 전문가 계산을 멋대로 생략했거나；
커뮤니티의 수많은 표준 GGUF 모델을 배제하고 전용 독점 포맷을 강제했거나；
심지어 그리디 디코딩을 강제 고정해 점수를 날조했습니다.
모델의 두뇌를 잘라내어 얻은 가짜 속도는 진지한 실무 환경에서 아무런 의미가 없습니다!

## 2. tandem.cpp의 핵심 구조：CPU와 GPU의 진정한 이종 병렬 연산

README에 적힌 핵심 논리는 사실상 두 줄로 요약됩니다.
비상주 전문가 가중치를 버스로 전송하지 않는다；
CPU와 GPU가 연산 역할을 명확히 분담한다.
과연 효과가 있을까요?
확실하게 작동합니다.

패치의 작동 파이프라인은 두 가지 축으로 구성됩니다.

### 1. 고빈도 핵심 전문가의 VRAM 상주
가장 자주 호출되는 핵심 전문가들을 4090의 VRAM에 단단히 고정합니다.
테라바이트급 초고속 그래픽 메모리 대역폭을 풀가동하여 행렬 곱셈을 초고속으로 처리합니다.

### 2. 메모리 즉석 연산과 호스트 측 텐서 합성
라우팅이 시스템 램에 있는 차가운 전문가를 선택했을 때는 버스 전송을 일절 발생시키지 않습니다.
해당 전문가의 행렬 연산 작업을 멀티코어 CPU로 곧장 넘깁니다.
GPU는 핵심 전문가를 연산합니다.
CPU는 보조 전문가를 현장에서 처리합니다.
양쪽 연산이 끝나는 즉시 호스트 메모리 측에서 활성화 텐서를 곧바로 합산합니다.
버스 전송 오버헤드가 제로가 됩니다!

제작자는 문서에서 단호하게 밝혔습니다. 본 패치는 전문가를 건너뛰지 않으며 라우터 가중치 편향도 왜곡하지 않는다.
출력되는 결과물의 품질은 순정 llama.cpp 와 완전히 대등합니다.

하지만 여기서 잘못 알려진 소문을 바로잡아야 합니다.
수학적으로 완벽히 일치한다는 말은 이종 연산 커널을 직접 작성해 본 적 없는 비전문가의 착각입니다!
동일한 시드로 200회 샘플링 정렬 테스트를 진행했습니다.
초반 100개 토큰은 완벽하게 일치합니다.
하지만 그 이후부터는 가끔씩 미세한 비트 단위 차이가 발생합니다.
왜 그럴까요?
CPU와 GPU의 부동소수점 누적 순서가 물리적으로 완전히 다르기 때문입니다!
하드웨어 부동소수점 덧셈은 결합법칙을 엄격하게 만족하지 않습니다.
병렬 타일의 누적 순서가 바뀌면 맨 끝자리 절삭 오차가 반드시 달라집니다.
그러나 이 미세한 차이는 산업적 허용 오차 내에 완벽히 머물며 GSM8K 수학 벤치마크 편차는 0.3퍼센트 미만에 불과했습니다.

## 3. 실기 벤치마크：5회 측정 중앙값과 하드웨어 부하

실제 체감 성능은 어떠했을까요?
뜬구름 잡는 소리를 배제하고 작업용 데스크톱 실기에서 측정한 부하 데이터를 공개합니다.

### 테스트 하드웨어 환경
- CPU：i5-12400F 6코어 4.4GHz 올코어 고정
- GPU：RTX 4090 24GB VRAM
- 시스템 램：64GB DDR4-3200 듀얼 채널
- 운영체제：Ubuntu 24.04 LTS
- 평가 모델：Qwen2-57B-A14B 표준 GGUF IQ3_S 양자화 버전

### 5회 측정 중앙값 비교 데이터

측정 조건은 통일했습니다. n_predict는 512, 배치 크기는 2048, 온도 설정은 모델 권장값을 적용했습니다.

| 모델 구조와 구동 환경 | 순정 llama.cpp 오프로딩 | tandem.cpp 병렬 패치 | 측정 속도 향상비 | 실기 부하 및 시스템 상태 |
| :--- | :--- | :--- | :--- | :--- |
| Qwen2-57B-A14B 그리디 모드 | 초당 29.8토큰 | 초당 97.3토큰 | 3.26배 | GPU 210W 소모 및 CPU 6코어 96% 점유 |
| Qwen2-57B-A14B 랜덤 샘플링 | 초당 29.4토큰 | 초당 96.1토큰 | 3.27배 | 샘플링 지연 시간 증가 2ms 미만 |
| Mixtral-8x7B-Instruct Q4_K_M | 초당 33.5토큰 | 초당 68.2토큰 | 2.03배 | 활성 전문가 수 증가로 CPU 부하 증가 |
| 64k 장문 프롬프트 Prefill 단계 | 기본 지연 기준치 | 약 1.4배 속도 개선 | 1.42배 | 사전 계산 병목은 어텐션 자체에 기인 |

초당 29.8토큰에서 97.3토큰으로 3배 이상 폭증했습니다.
솔직히 말해 원래 제 예상치를 훌쩍 뛰어넘는 성적이었습니다.
보급형 6코어 i5가 버텨봐야 기껏해야 초당 60토큰 정도일 것이라 여겼기 때문입니다.
백그라운드에서 `htop` 과 `perf stat` 을 띄워보고 단번에 납득했습니다.
CPU 물리 6코어가 전부 한계까지 갈려 나가고 있었습니다!
시스템 메모리 버스 대역폭 점유율도 75퍼센트를 넘겼습니다.
이 패치의 본질은 허공에서 연산력을 창조하는 마술이 아닙니다.
놀고 있던 멀티코어 CPU와 램 대역폭을 총동원하여 숨통이 끊겨 있던 PCIe 전송 병목을 우회하는 현실적인 공학적 해법입니다!

## 4. 도입을 피해야 할 환경과 미해결 과제

무턱대고 시도해서는 안 됩니다.
아래 조건에 해당하는 분들은 일찌감치 포기하시는 것을 권장합니다.

첫째, 노트북이나 16GB 램 미니 PC에서 이 기적을 바라면 안 됩니다!
40GB 가중치가 물리 메모리에조차 들어가지 못하면 mmap 가상 메모리 스왑에 의존하게 됩니다.
디스크 스왑이 터지는 순간 토큰 생성 속도는 한 자릿수로 주저앉고 컴퓨터 전체가 얼어붙습니다.
메모리가 부족한 환경에서는 절대 시도하지 마십시오!

둘째, 그래픽 메모리가 빠듯하면 여전히 OOM 에러로 꺼집니다.
VRAM 할당 옵션인 `--moe-cache-mib` 수치는 본인 카드 사양에 맞게 수동 조절해야 하며 문맥 확장을 위해 최소 3GB 이상의 안전 여유 공간을 남겨두어야 합니다.

셋째, 더 거대한 모델을 돌릴 때 6코어 CPU는 힘에 부칩니다.
70B를 넘는 대형 MoE 모델을 원하신다면 CPU는 최소 8코어 이상, 메모리는 고대역폭 DDR5나 4채널 구성을 갖추어야 병목을 막을 수 있습니다.

넷째, 긴 문맥의 사전 계산 Prefill 단계 개선 폭은 약 1.4배에 그칩니다.
토큰 생성 속도가 3배 빨라졌다고 해서 첫 토큰 대기 시간까지 3배 빨라질 것이라 착각하지 마십시오.

## 5. 빌드 가이드와 실행 명령어

패치 소스코드는 GitHub의 github.com/ewhacc/tandem.cpp 저장소에 등록되어 있습니다.
수정되는 코드는 저수준 소스 파일 단 3개뿐입니다.
패치 적용과 빌드 절차는 다음과 같습니다.

```bash
git clone https://github.com/ggml-org/llama.cpp
cd llama.cpp && git checkout b3920
git clone --depth 1 https://github.com/ewhacc/tandem.cpp /tmp/tandem
git apply /tmp/tandem/patches/*.patch
cmake -B build -DGGML_CUDA=ON -DCMAKE_BUILD_TYPE=Release
cmake --build build --config Release -j8
./build/bin/llama-cli -m ./models/qwen2-57b-a14b.gguf --n-gpu-layers 33 --moe-cache-mib 6144 -p "파이썬으로 고성능 동시성 크롤러를 작성해 줘" -n 512
```

직접 빌드하여 테스트해 보시기 바랍니다.
혹시 본인 환경에서 세그멘테이션 오류가 발생한다면 이슈 탭에 로그를 남겨 주십시오. 함께 원인을 파헤쳐 봅시다!
