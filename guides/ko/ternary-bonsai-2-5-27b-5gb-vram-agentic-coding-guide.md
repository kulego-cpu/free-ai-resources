8GB 그래픽카드로 27B 파라미터 코딩 에이전트를 정말 돌릴 수 있을까요?

처음에는 저 역시 반신반의했습니다. 53.8GB에 달하는 FP16 모델을 5.93GB까지 눌러 담으면 가중치당 약 1.76 bit만 남습니다. 추론 능력이 그대로 붕괴하지 않을까 의심이 들었습니다.

11월 24일 PrismML이 `Ternary Bonsai 2.5 27B`를 공개했고, 출시 당일 Hacker News 메인에서 400개 가까운 추천을 받았습니다.

공식 백서와 Hugging Face 저장소 `prism-ml/Ternary-Bonsai-2.5-27B-GGUF` 안내를 교차 확인했습니다.

결론은 쓸 만합니다. 다만 기존에 쓰던 구버전 `llama.cpp`로 무작정 실행하면 높은 확률로 삽질을 겪게 됩니다.

## 이번 삼진 양자화는 왜 무너지지 않았는가

기존의 극저비트 양자화는 다중 턴 도구 호출만 들어가면 쉽게 망가졌습니다.

이전 세대인 Bonsai 2 27B는 DeepSWE 코딩 평가에서 0점을 받았고, AppWorld 다단계 작업도 51.2점에 머물렀습니다. 도구 실행에서 오류가 한 번 나면 무한 루프에 빠지거나 가짜 완료 응답을 내뱉곤 했습니다.

Bonsai 2.5 역시 `Qwen3.8-27B` 기반입니다. 언어 백본 24.35B, 비전 타워 0.47B, 임베딩 2.54B 구성에 선형 어텐션 약 75%와 전체 어텐션 25%가 섞여 있습니다.

저장 포맷은 전작과 같습니다. g128 그룹 단위 FP16 스케일링을 적용한 1.58-bit 삼진 가중치로 `-1`, `0`, `+1` 세 값만 가집니다. 블록 단위 직교 Hadamard 회전을 오프라인에서 가중치에 미리 접어 넣었기 때문에, 추론 시에는 활성화 값만 회전시켜 추가 메모리 대역폭을 쓰지 않습니다.

성능 손실은 어느 정도일까요? 통일된 `xhigh` 사고 모드 기준 벤치마크 비교표입니다:

| 평가 벤치마크 | 용량 비교 | Qwen3.8 FP16 | GSQ-RCO IQ2_XS | Bonsai 2 27B | Bonsai 2.5 27B |
| :--- | :--- | :--- | :--- | :--- | :--- |
| 모델 크기 | GB | 53.8 | 8.4 | 5.93 | 5.93 |
| 가중치당 비트 | bpw | 16.0 | 2.50 | 1.76 | 1.76 |
| SWE-bench Verified | 코딩 | 80.6 | 74.4 | 60.8 | 75.6 |
| DeepSWE v1.1 | 코딩 | 30.1 | 17.7 | 0.0 | 27.0 |
| Terminal-Bench 2.1 | 터미널 | 70.8 | 53.4 | 52.8 | 60.1 |
| AppWorld | 도구 활용 | 93.2 | 46.5 | 51.2 | 90.5 |
| τ³-Bench | 다중 턴 | 72.8 | 67.5 | 69.1 | 73.9 |

`GSQ-RCO IQ2_XS` 열을 눈여겨볼 필요가 있습니다. 용량은 Bonsai 2.5보다 40% 더 크지만 AppWorld 점수는 46.5점으로 추락했습니다. 반면 Bonsai 2.5는 5개 도구 호출 평균 77.2점을 기록하며 FP16의 77.7점을 0.5점 차로 바짝 추격했습니다.

그렇다면 원본 FP16을 완전히 뛰어넘은 것일까요?

아닙니다. Terminal-Bench 2.1에서는 FP16보다 10.7점 낮고 BFCL v4도 3.6점 뒤처집니다. HN 댓글 창에서도 전작의 무한 루프에 데였던 개발자들이 벤치마크 과적합 가능성을 의심하는 목소리를 냈습니다.

9분의 1 VRAM으로 FP16의 90% 수준 코딩 실력을 챙긴다면 로컬 자동완성 용도로는 충분히 남는 장사입니다.

## 실제 속도는 얼마나 빠른가: MTP와 기본판 구분

여러 커뮤니티 글이 204 tok/s라는 수치만 내세우지만 측정 전제가 빠져 있는 경우가 많습니다.

저장소에는 초안 헤드가 없는 기본 GGUF와 다중 토큰 예측 헤드를 포함한 `-mtp.gguf` 두 계열이 나뉘어 올라와 있습니다.

MTP 추측 디코딩을 쓰지 않은 순수 `PTQ1_0` 및 `PQ2_0` 기본 속도는 다음과 같습니다:

- RTX 4090: `PTQ1_0` 디코딩 112 tok/s, 프롬프트 프리필 3,452 tok/s
- RTX 5090: `PTQ1_0` 디코딩 163 tok/s. 프리필 4,198 tok/s
- Apple M5 Pro: Metal 백엔드는 `PQ2_0`만 측정, 디코딩 30.2 tok/s

`-mtp.gguf` 파일과 공식 `presets/llama.cpp/mtp-cuda.json` 설정을 함께 얹어야 비로소 RTX 4090에서 204 tok/s까지 올라갑니다. 비전 타워 `mmproj-Q8_0.gguf`는 별도 분리되어 있어 텍스트 기반 코딩 작업 시에는 로드하지 않아 VRAM 630MB를 아낄 수 있습니다.

## 로컬 실행 전 반드시 피해야 할 네 가지 함정

벤치마크 표보다 실제 환경에서 마주치는 아래 4가지 함정이 훨씬 치명적입니다.

### 5.99GB PTQ1_0을 받았는데 순정 llama.cpp가 거부할 때

저장소에는 런타임에 따라 세 가지 패킹 포맷이 올라와 있습니다:

- `PTQ1_0`: 5.99 GB, 1.76 bpw 밀집 삼진 포맷으로 NVIDIA에서 가장 빠르지만 `PrismML-Eng/llama.cpp` 포크 필수
- `PQ2_0`: 7.25 GB, Apple Metal용 2-bit 슬롯 포맷으로 역시 포크 버전 필요
- `Q2_0`: 7.67 GB, 표준 `llama.cpp` 순정 호환 포맷

포크 빌드를 따로 컴파일하기 귀찮아서 `Q2_0`을 순정 바이너리로 돌리고 싶다면 가능할까요?

가능합니다. 단 **빌드 `b11556` 이상**이라는 버전 커트라인을 지켜야 합니다. 이 빌드부터 Hadamard 활성화 런타임이 포함되었습니다.

더 심각한 점은 구버전 순정 `llama.cpp`로 `Q2_0`을 열면 **아무런 오류 경고 없이 로드된 뒤 엉망진창인 문자열만 출력**한다는 사실입니다. 실행 전 `llama-cli --version`부터 확인하세요.

### 기본 4슬롯 할당으로 10GB VRAM이 터지는 현상

모델 크기는 6GB 남짓인데 10GB RTX 3080에서 서버를 켜자마자 바탕화면 렌더링까지 멈출 뻔했다는 사례가 있습니다.

원인은 병렬 슬롯 기본값입니다. `llama-server`는 별도 제한을 주지 않으면 통합 KV 캐시를 공유하는 슬롯 4개를 기본으로 엽니다. Hugging Face 토론 글에서도 기본 실행 시 VRAM 점유율이 9.5 GB까지 치솟았다가 `-np 1`로 단일 슬롯을 고정하자 7.8 GB로 내려갔다는 실측이 올라왔습니다.

### --min-p 0 누락 시 샘플링 편향 발생

표준 `llama.cpp`는 기본적으로 `min_p=0.05` 절단을 켭니다. Bonsai 2.5는 Qwen3.8 권장 사고 파라미터를 따르므로 `min_p`를 0으로 꺼야 합니다. 이를 빼먹고 돌리면 긴 코드 생성 과정에서 같은 구문을 맴도는 현상이 잦아집니다.

### -n 256 제한은 사고 도중 출력을 끊어버림

이 모델은 기본값이 `xhigh` 사고 강도이며 `low` 모드를 지원하지 않습니다. 강제로 `low`를 넘겨도 내부적으로는 `xhigh`에 가까운 사고 체인을 생성합니다.

터미널 테스트 시 무심코 `-n 256`을 주면 `<think>` 태그 안에서 오류를 분석하다가 토큰 예산을 다 써버려 실제 코드는 한 줄도 나오지 않습니다.

## 바로 복사해 쓰는 로컬 서버 구동 스크립트

PrismML 포크 또는 `b11556` 이상 순정 `llama.cpp`를 준비했다면 아래 옵션으로 띄우면 됩니다:

```bash
# 방안 A: PrismML 포크로 최소 용량 5.99GB PTQ1_0 구동
git clone https://github.com/PrismML-Eng/llama.cpp && cd llama.cpp
cmake -B build -DGGML_CUDA=ON && cmake --build build -j

hf download prism-ml/Ternary-Bonsai-2.5-27B-GGUF Ternary-Bonsai-2.5-27B-PTQ1_0.gguf --local-dir .

./build/bin/llama-server -m Ternary-Bonsai-2.5-27B-PTQ1_0.gguf \
  -ngl 99 -fa on -np 1 -c 32768 -n 16384 \
  --temp 1.0 --top-p 0.95 --top-k 20 --min-p 0 \
  --host 127.0.0.1 --port 8080
```

16GB 메모리 Mac 환경에서는 `Ternary-Bonsai-2.5-27B-PQ2_0.gguf`를 내려받고 빌드 시 `-DGGML_CUDA=ON`을 제외하면 Metal 가속이 적용됩니다. 컴파일 과정 자체를 건너뛰고 싶다면 7.67GB `Q2_0` 파일을 받아 `b11556+` 순정 `llama-server`에 연결하세요.

## 일상 개발 도구로 편입할 가치가 있는가

8GB 그래픽카드나 16GB 노트북 환경에서는 그동안 Qwen3.8-27B 구동 자체를 엄두내기 어려웠습니다. 6GB 안팎의 디스크 공간으로 SWE-bench 75.6 수준의 코딩 에이전트를 오프라인에 둘 수 있다는 점은 분명한 무기입니다.

하지만 1.76 bpw가 완전 정밀도의 완벽한 대체재가 아니라는 한계도 명확합니다. Terminal-Bench에서 10점 넘게 빠진 대가는 결코 가볍지 않습니다. 수십 턴 이상 이어지는 복잡한 다중 파일 리팩토링에서도 끝까지 안정성을 지켜낼 수 있을지는 개인 비공개 저장소에서 계속 부하 테스트를 이어가며 확인하고 있습니다.
