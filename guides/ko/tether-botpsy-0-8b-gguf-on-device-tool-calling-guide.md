스테이블코인 발행사 Tether가 온디바이스 소형 모델을 오픈소스로 풀었다. 이름은 `BotPsy-0.8B`다. `Qwen3.5-0.8B`를 파인튜닝해 스마트폰과 저사양 노트북에서 로컬 함수 호출을 돌리는 데 초점을 맞췄다.

크기가 어느 정도냐면 `Q4_K_M` 양자화 파일이 `0.53 GB` — 정확히 `504.8 MiB`다. `Q8_0` 버전도 `0.81 GB`밖에 안 된다.

`BFCL v4`에서 `44.0`점, `ToolSandbox`에서 `64.6`점을 찍어 파라미터가 `2.5`배 큰 `Qwen3.5-2B-Think`를 눌렀다. 숫자만 보면 솔깃하다. 하지만 지금 당장 `gguf`를 휴대폰에 넣어 돌리면 깨진 JSON만 쏟아질 가능성이 높다. 메인 모델 카드와 `GGUFs` 저장소 주석을 끝까지 읽어보면 먼저 짚어야 할 세 가지가 나온다.

근거 자료는 세 곳이다. `huggingface.co/qvac/BotPsy-0.8B`, `huggingface.co/qvac/BotPsy-0.8B-GGUFs` 모델 카드, 그리고 공식 블로그 `huggingface.co/blog/qvac/botpsy`다. 안드로이드 실기에서 `32768` 컨텍스트 메모리 피크나 발열 스로틀링을 직접 재지는 못했으므로 배터리나 초당 토큰 수치는 적지 않는다.

## 왜 0.8B가 2B를 이기면서 지식 벤치마크에서는 무너지는가

`BotPsy-0.8B`의 기반은 `Qwen3.5-0.8B`다. `Gated DeltaNet`과 게이트 어텐션이 섞인 하이브리드 구조이며 텍스트 전용, Apache 2.0 라이선스로 공개됐다.

같은 평가 하네스에서 베이스 모델 `Qwen3.5-0.8B-Think`와 비교하면 `BFCL v4`는 `23.4`에서 `44.0`으로, `ACEBench`는 `30.1`에서 `58.7`로, `τ-bench` 리테일·통신·은행 평균은 `23.2`에서 `51.5`로 거의 두 배 뛰었다. 범용 지능이 올라간 게 아니라 파인튜닝이 툴 콜링 경로만 집중적으로 깎아낸 결과다. 적절한 도구가 없을 때 호출을 거부하는지 보는 BFCL v4 환각 억제 테스트에서도 `86.1`점을 기록했다.

반면 지식 영역 표로 내려가면 바닥이 바로 드러난다.

`GPQA Diamond`는 `38.1`점으로 `Qwen3.5-2B-Think`의 `59.9`점에 20점 넘게 뒤진다. `MMLU-Pro` 역시 `48.9`점 대 `65.5`점이다. 특히 `BrowseComp-Plus`는 최고 점수가 `4.5`점에 그친다. 열린 다단계 웹 리서치는 기대하기 어렵고, 의도가 분명하며 도구 목록이 제한된 짧은 체인 호출에만 강점이 있다.

## 첫 실행 함정: 내장 템플릿은 thinking 모드가 꺼져 있다

처음 테스트할 때 엉뚱한 결과가 나오기 가장 쉬운 지점이 여기다.

`BotPsy-0.8B`는 thinking 모드로 학습되고 평가됐다. 그런데 `GGUFs` 저장소 설명을 보면 내장 채팅 템플릿은 기본값이 비사고 모드다. 옵션을 넘기지 않고 `llama-cli`에 그대로 올리면 추론 단계를 건너뛰고 바로 JSON을 뱉으면서 정확도가 떨어진다.

공식 `llama.cpp` 서버 실행 명령은 샘플링 파라미터를 꽤 깐깐하게 고정한다.

```bash
hf download qvac/BotPsy-0.8B-GGUFs botpsy-0.8b-q8_0.gguf --local-dir .

llama-server -m botpsy-0.8b-q8_0.gguf --jinja -c 32768 \
    --temp 0.3 --top-p 0.95 --top-k 20 --presence-penalty 1.5 \
    --chat-template-kwargs '{"enable_thinking": true}' --port 8080
```

두 가지 플래그를 눈여겨봐야 한다. 하나는 `--chat-template-kwargs '{"enable_thinking": true}'`로, 빠지면 벤치마크 표에 나온 모델과 전혀 다른 동작을 한다. 다른 하나는 `--presence-penalty 1.5`다. 일반 소형 모델에서 좀처럼 이렇게 높게 잡지 않는 값인데, 클라이언트 기본값 `0`이나 `1.0`을 그대로 두면 thinking 구간에서 반복 루프에 빠지기 쉽다.

추가로 GGUF 변환본은 베이스 모델의 멀티 토큰 예측 `MTP` 레이어를 제거했고 권장 언어는 영어다. 비영어 입력에서 정확도가 얼마나 떨어지는지는 문서에 나와 있지 않다.

## 양자화 수지: Q8_0으로 용량 절반, 그러나 엔진 차이가 양자화 손실보다 크다

저장소에는 GGUF 파일 세 개가 올라와 있으며 선택 기준은 단순하다.

`botpsy-0.8b-bf16.gguf`는 `1446.5 MiB`, 약 `1.52 GB`인데 10개 벤치마크 평균이 `50.4`점으로 오히려 `Q8_0`보다 `0.3`점 낮다. 평가 기준선 비교 목적이 아니면 받을 이유가 없다. 실사용은 둘 중 하나다. 데스크톱이나 8GB 램 스마트폰이라면 `botpsy-0.8b-q8_0.gguf`를 쓰면 된다. `774.2 MiB`, KL 발산 `0.001`, 평균 `50.7`점으로 용량은 절반이고 점수 손실이 없다. 메모리가 극도로 빠듯할 때만 `botpsy-0.8b-q4_k_m-imat.gguf`의 `504.8 MiB`를 고른다. imatrix 보정으로 KL을 일반 `Q4_K_M`의 `0.048`에서 `0.036`까지 줄였지만 10개 평균은 `48.9`점으로 내려가고 `GPQA Diamond`와 `MMLU-Pro`가 각각 3~4점씩 빠진다. 270 MiB를 아끼자고 지식 점수를 내주는 건 램 한계가 닥쳤을 때만 택할 일이다.

여기서 흥미로운 대조 수치가 하나 있다. 손실 없는 똑같은 BF16 가중치를 두고 `vLLM`과 `llama.cpp` CUDA `b12169`에서 돌렸을 때 `τ-bench`는 `4.0`점, `Claw-Eval`은 `3.1`점, `IFBench`는 반대로 `2.8`점 차이가 난다. `0.8B` 모델에서는 추론 엔진과 샘플링 변동이 `BF16`에서 `Q8_0`으로 낮출 때의 오차보다 크다. 소수점 첫째 자리 양자화 순위에 크게 매달릴 필요가 있을까.

## 맡길 만한 작업과 피해야 할 작업

포지션은 분명하다. 데스크톱용 `7B`나 `14B` 범용 모델을 대체하는 물건이 아니다.

오프라인 음성 비서, 일정 트리거, 로컬 파일 정리처럼 도구 목록이 고정돼 있고 스키마가 정돈되어 있으며 몇 턴 안에 끝나는 작업이라면 `800MB` 남짓한 메모리로 Apache 2.0 로컬 툴 콜링 엔진을 돌리는 계산이 맞는다.

반대로 여러 파일을 건드리는 코드 리팩터링이나 긴 비영어 문서 분석, 웹 전체 탐색을 `0.8B`에 맡기는 건 무리다. `BrowseComp-Plus` `4.5`점이 이미 한계선을 그어 놓았다.

가중치를 내려받기 전에 세 가지만 먼저 점검하자.

1. 쓰는 클라이언트가 `llama-server`에 `enable_thinking: true`를 넘길 수 있는지 확인한다. 기본 템플릿 상태는 전혀 다른 모델에 가깝다.
2. 메모리에 `1GB` 여유가 있다면 `Q4_K_M`으로 지식 저하를 감수하기보다 `botpsy-0.8b-q8_0.gguf`를 우선 선택한다.
3. 실행 예시에 `-c 32768`이 적혀 있더라도 모바일 기기에서 32K 컨텍스트와 긴 thinking 출력을 버틸지는 별개다. 짧은 컨텍스트부터 부하를 재고 올리는 편이 안전하다.
