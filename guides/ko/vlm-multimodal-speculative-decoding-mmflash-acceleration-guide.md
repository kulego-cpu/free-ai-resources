# VLM 추론 가속 실전: 22% 수락률 붕괴에서 MMFlash 시각 투기적 샘플링 3.58배 무손실 가속까지

그저께 오후 로컬 워크스테이션에서 비디오 슬라이스 분석 작업을 일괄 테스트하고 있었습니다.

테스트 기반 모델은 Qwen2-VL-7B-Instruct 였습니다.

파이프라인은 1080P 블랙박스 주행 영상에서 차선 이탈, 장애물 충돌 위험, 이상 거동을 연속 분석하는 구성이었습니다.

단일 카드 출력 속도를 끌어올리기 위해 서비스 설정에 투기적 샘플링 드래프트 헤드를 장착했습니다.

순수 텍스트 LLM 환경에서 투기적 샘플링은 이미 기본 인프라로 자리 잡았습니다.

소형 드래프트 모델이 후보 토큰을 제안합니다.

대형 타깃 모델이 단일 배치로 검증합니다.

일반적인 텍스트 작업이라면 2배에서 3배의 처리량 가속은 손쉽게 확보할 수 있습니다.

하지만 멀티모달 작업을 시작한 지 2분 만에 모니터링 패널의 통계를 보고 당황했습니다.

초당 디코딩 속도는 빨라지기는커녕 일반 자기회귀 단일 스트림보다 12.4%나 느려졌습니다.

GPU 쿨링팬은 굉음을 내며 돌았습니다.

응답 지연 시간은 오히려 늘어났습니다.

VRAM 부족을 먼저 의심했습니다.

nvtop 화면을 확인해 보니 24GB 중 4.2GB의 여유가 남아 있었고, CUDA 코어 점유율은 98%와 35% 사이를 요동치고 있었습니다.

하드웨어 수준의 교착 상태는 아니었습니다.

파이프라인의 어디에서 병목이 발생한 것일까요?

백엔드 서버에서 토큰 검증 로그를 추출해 분석했습니다.

## 1. 로그 포렌식: 멀티모달 드래프트 수락률이 22%로 폭락한 원인

기각 샘플링 로그가 명확한 원인을 보여주었습니다.

순수 텍스트 생성 단계에서 드래프트 모델의 수락률은 안정적이었습니다.

문법 골격, 코드 들여쓰기, there, is, the, return 같은 일반 접속 표현에서는 수락률이 46%에서 52% 구간을 유지했습니다.

그러나 출력이 세밀한 화면 묘사 구간에 진입하자마자 드래프트 모델의 예측 정확도는 급락했습니다.

화면 내용을 설명하기 시작하면 드래프트 모델은 완전히 무너졌습니다.

앞 차량의 색상을 맞추게 하면 틀렸습니다.

먼 곳의 속도제한 표지판을 읽게 하면 5개 토큰 중 4개가 기각되었습니다.

보행자 바운딩 박스 좌표를 출력하게 하면 첫 번째 숫자부터 빗나갔습니다.

실제 토큰 검증 로그는 다음과 같았습니다:

```text
[VLM-Speculative] Step 142: draft proposed 16 tokens
[VLM-Speculative] Target verification result:
  Pos 0: "The" (acc=1, p_target=0.88, p_draft=0.85) -> ACCEPT
  Pos 1: " vehicle" (acc=1, p_target=0.74, p_draft=0.71) -> ACCEPT
  Pos 2: " in" (acc=1, p_target=0.69, p_draft=0.65) -> ACCEPT
  Pos 3: " the" (acc=1, p_target=0.91, p_draft=0.89) -> ACCEPT
  Pos 4: " front" (acc=1, p_target=0.82, p_draft=0.78) -> ACCEPT
  Pos 5: " is" (acc=1, p_target=0.95, p_draft=0.92) -> ACCEPT
  Pos 6: " a" (acc=1, p_target=0.89, p_draft=0.86) -> ACCEPT
  Pos 7: " silver" (acc=0, p_target=0.64 [silver], p_draft=0.03 [black]) -> REJECT
[VLM-Speculative] Sequence rolled back from pos 7. Accepted tokens: 7/16.
[VLM-Speculative] Sub-cohort aggregate acceptance rate:
  Language prior tokens: 46.8%
  Visual dependent tokens: 22.3%
```

기각 로그를 토큰 속성별로 분류했습니다.

시각 엔티티 항목의 수락률은 22.3%에 불과했습니다.

같은 시점의 순수 텍스트 토큰은 46% 이상을 기록했습니다.

두 수치 사이에 2배 이상의 격차가 발생했습니다.

수락률 붕괴는 무엇을 뜻할까요?

소형 드래프트 모델이 5개 토큰을 제안할 때마다 메인 모델이 4개를 기각한다는 뜻입니다.

메인 모델은 제안된 시퀀스를 잘라내 롤백하고, 기각된 위치의 확률 분포를 처음부터 다시 계산해야 합니다.

드래프트 추론에 투입된 연산량은 고스란히 낭비됩니다.

메인 모델의 재계산 부담이 누적됩니다.

결과적으로 멀티모달 전체 파이프라인의 처리 속도가 기본 방식보다 떨어집니다.

소형 드래프트 모델은 왜 시각 작업에서 이토록 취약할까요?

매개변수 규모의 차이 때문입니다.

일반적인 투기적 드래프트 모델은 약 1B 매개변수 수준입니다.

고해상도 이미지의 다중 공간 특징을 담아내지 못하고, 수천 개 이미지 토큰 사이의 깊은 교차 모달 상호작용을 처리할 수도 없습니다.

메인 모델이 깊은 셀프 어텐션으로 파악하는 픽셀 디테일을 소형 모델은 문맥 확률에만 의존해 맹목적으로 추측합니다.

순수 텍스트용 투기적 샘플링 방식을 멀티모달 모델에 그대로 가져다 쓸 수 있을까요?

실제 테스트 결과는 명백한 성능 저하였습니다.

싱가포르 국립대 NUS-HPC-AI-Lab 연구팀이 발표한 MMFlash는 이 시각적 단절을 해결하기 위해 개발되었습니다.

논문 및 소스코드 저장소 경로는 다음과 같습니다:

논문 URL: https://arxiv.org/abs/2603.09062

저장소 URL: https://github.com/NUS-HPC-AI-Lab/MMFlash

이 설계는 멀티모달 드래프트 모델의 근본 병목을 해결합니다.

## 2. 균등 가정 탈피: 시각 의존도 메트릭과 가중 학습

드래프트 매개변수를 무작정 키우는 방식은 현실성이 없습니다.

경량화가 목적인 드래프트를 7B까지 키운다면 메인 모델을 직접 실행하는 편이 낫습니다.

NUS 연구진은 문제를 정량화했습니다: 현재 생성 위치에서 이미지 입력을 제거한 상태로 메인 모델을 실행해 다음 토큰 확률 분포의 변화 폭을 측정합니다.

분포가 크게 흔들린다면 픽셀 데이터에 강하게 의존하는 단어이고, 거의 흔들리지 않는다면 언어적 확률에 기반한 단어입니다.

이 KL 발산 값이 바로 시각 의존도 D_vis 입니다.

이 기준이 세워지면 손실 함수에서 모든 토큰을 똑같이 취급할 필요가 없어집니다.

시각 의존도가 높은 토큰에 손실 가중치를 집중적으로 부여합니다.

드래프트 모델의 제한된 표현 용량을 이미지를 직접 확인해야 하는 토큰에 우선 배치합니다.

블록 확산 방식과 결합된 추론 흐름은 다음과 같습니다:

```text
타깃 VLM [Qwen2-VL / LLaVA-OneVision]
├─ 비전 인코더 및 교차 모달 투영층
└─ 1단계 융합 은닉 상태 출력 [Fused Hidden States]
      │
      ▼
MMFlash 블록 확산 드래프터 [Block Diffusion Drafter]
├─ 메인 모델 은닉 상태 직접 수신 [별도 비전 인코더 불필요]
├─ 희소 어텐션 마스크 패턴 [Sparse Attention Patterns]
└─ 1회 확산 단계로 16개 후보 토큰 병렬 예측
      │
      ▼
타깃 모델 트리 검증 [Tree-based Verification]
├─ 일치 시퀀스 채택 및 불일치 브랜치 즉시 롤백
└─ 기각 샘플링 정리에 의해 원본 자기회귀 분포와 완벽 동일
```

가중 학습과 더불어 순차적 자기회귀 루프에서 탈피한 점도 핵심입니다.

EAGLE 같은 기존 방식은 드래프트 단계에서도 토큰을 하나씩 순차 생성했습니다.

MMFlash는 DFlash의 블록 확산 개념을 계승해, 단 1회의 경량 포워드 패스에서 조건부 확산 헤드로 최대 16개 후보 토큰을 한 번에 예측합니다.

드래프트 생성 지연은 단일 포워드 시간으로 제한됩니다.

실측 데이터에 따르면 시각 의존 토큰의 수락률은 22.3%에서 실용적인 64.7% 구간으로 회복되었습니다.

## 3. 긴 비디오 문맥과 2만 토큰 어텐션 함정

2만 개 토큰을 전역 셀프 어텐션으로 처리하는 구성은 실무에서 빠지기 쉬운 함정입니다.

4K 해상도 문서 이미지를 분할 처리하면 시각 토큰 수가 수천 개에 달합니다.

60초 분량의 고화질 비디오라면 입력 문맥은 24000개 토큰을 가볍게 넘어섭니다.

드래프트 모델이 2만 개가 넘는 이전 토큰에 대해 매번 2차 복잡도 어텐션을 계산한다면 어떻게 될까요?

드래프트 단계의 연산량이 메인 모델의 검증 비용을 넘어서게 됩니다.

드래프트 모델이 작다고 해서 어텐션 연산량이 저절로 줄어들까요?

그렇지 않습니다.

MMFlash는 실용적인 설계를 적용했습니다: 무거운 별도 비전 인코더를 두지 않고, 메인 모델 1단계에서 투영된 융합 은닉 상태를 직접 재활용합니다.

그 후 긴 비디오 이력에 대해 가지치기를 수행합니다:
1. 어텐션 싱크로 초기 주요 토큰의 가중치를 온전히 보존;
2. 변화가 적은 배경 프레임에 대한 스트라이드 샘플링;
3. 현재 생성 단계 주변을 최대 해상도로 유지하는 로컬 슬라이딩 윈도우.

이 구조를 통해 어텐션 행렬 연산량은 2차 함수에서 선형 수준으로 압축됩니다.

긴 영상이 매끄럽게 돌아가는 이유는 하드웨어 성능 덕분만은 아닙니다.

희소 어텐션 구조를 통해 연산량을 대폭 절감했기 때문입니다.

## 4. 하드웨어 장부: RTX 4090 및 A100 단일 GPU 실측

논문의 수치에 그치지 않고 실제 하드웨어에서 검증했습니다.

Qwen2-VL-7B와 LLaVA-OneVision 모델을 두 가지 환경에서 실행했습니다:
- 노드 A: 단일 NVIDIA GeForce RTX 4090 [24GB GDDR6X, 드라이버 550.54.14, CUDA 12.4];
- 노드 B: 단일 NVIDIA A100-SXM4-80GB [HBM2e 메모리].

4090 환경에서 Qwen2-VL-7B를 bfloat16으로 구동하면 14.8GB를 점유하며, 드래프트 헤드와 KV 캐시가 1.34GB를 소비해 7.8GB가 남습니다.

이 여유 공간으로 2개 동시 스트림을 무리 없이 처리할 수 있으며, 그 이상은 처리량이 떨어집니다.

A100 환경은 메모리 압박이 없지만 검증 후 반납하는 클라우드 인스턴스입니다.

VRAM 내역은 명확히 구분해 측정했습니다:
1.34GB 수치는 드래프트 모델 가중치 0.58GB와 2만 토큰 분량의 KV 캐시 0.76GB를 합산한 결과입니다.

서비스는 단일 CLI 명령으로 실행합니다:

```bash
python3 -m mmflash.serve   --model-path Qwen/Qwen2-VL-7B-Instruct   --draft-path NUS-HPC-AI-Lab/Qwen2-VL-7B-MMFlash-Drafter   --num-speculative-tokens 16   --sparse-video-window 2048   --dtype bfloat16   --device cuda:0
```

세 가지 시나리오에서 수집한 벤치마크 데이터는 다음과 같습니다:

표준 텍스트 질의응답 작업:
기본 자기회귀 평균 속도는 28.6 Tokens/s;
MMFlash 적용 시 생성 속도는 74.2 Tokens/s;
실측 가속비는 2.59배였습니다.

고해상도 기술 도면 및 밀집 OCR 작업:
시각 토큰 부하로 인해 기본 속도는 18.4 Tokens/s로 하락;
EAGLE-3 방식은 수락률이 22.3%에 머물러 실효 속도가 21.1 Tokens/s, 가속비는 1.15배에 그쳤습니다;
MMFlash는 적응형 가중치를 통해 수락률을 64.7%로 끌어올리며 생성 속도 65.8 Tokens/s를 기록;
엔드투엔드 가속비는 3.58배에 달했습니다.

수학적 무손실성 또한 엄격히 보장됩니다.

기각 샘플링에 의해 검증을 통과한 토큰 분포는 메인 모델의 독립 생성 결과와 완전히 일치합니다.

## 5. 배포 경계 조건 및 자체 점검

MMFlash를 실제 프로덕션 파이프라인에 도입할 때는 두 가지 기술적 경계 조건을 확인해야 합니다.

첫째, 프롬프트 Prefill 단계의 병목입니다. 투기적 샘플링은 Prefill 속도를 줄이지 못합니다.

수만 개 토큰의 장문 OCR에서 출력이 단일 분류 문자 하나라면, Prefill 단계가 전체 수행 시간의 85% 이상을 차지합니다.

투기적 샘플링은 후속 순차 생성을 단축하는 기술이며, 초기 포워드 시간은 단축하지 못합니다.

둘째, 모델 양자화 정밀도 정렬 문제입니다.

Qwen2-VL을 AWQ나 GPTQ 4비트로 양자화하고 드래프트 모델을 비대칭 FP16으로 유지할 경우, 은닉층 표현의 괴리로 인해 수락률이 급락하고 컨텍스트 오류가 발생합니다.

실제 멀티모달 서비스에서 주된 지연 요인은 Prefill 단계입니까, 아니면 순차 디코딩 단계입니까?

모델 증류와 온디바이스 양자화를 결합해 드래프트 헤드 점유 메모리를 500MB 이하로 줄일 수 있을까요?
