# 음성 AI는 왜 항상 '다시 말씀해 주시겠어요'라고 되묻는가: WebRTC의 Target Delay와 의미론적 마감 시한의 충돌을 MoQ로 해결하기

지하 주차장이나 엘리베이터 앞에서 음성 AI를 사용해 본 사람이라면 누구나 이런 답답함을 겪어보았을 것입니다.

마이크 버튼을 누르고 신중하게 긴 문장을 전달합니다: 두 구매 계약서의 위약금 조항을 비교하고, 납기 지연 시 배상 한도를 정리해 주세요.

휴대전화 안테나가 다섯 칸에서 세 칸으로 떨어집니다. 차량 블루투스나 이동통신망이 찰나의 순간 흔들립니다.

음성 모델은 2초간 침묵합니다.

이어서 정중하지만 속을 뒤집어놓는 답변이 돌아옵니다: 죄송합니다, 연결이 고르지 못했습니다. 다시 말씀해 주시겠어요?

조수석으로 전화를 던져버리고 싶은 순간입니다. 소음이 심한 환경에서 누가 똑같은 긴 프롬프트를 세 번이나 반복하고 싶을까요?

백엔드에서는 200B 매개변수의 첨단 모델이 구동 중입니다. 수십 장의 H100 가속기가 밀리초 단위로 토큰을 쏟아냅니다. 추론 자체의 지연 시간은 450ms 이내로 억제되어 있습니다.

도대체 무슨 일이 일어난 것일까요? 천문학적인 비용이 투입된 첨단 시스템이 어째서 30년 전 무전기보다 못한 모습을 보일까요?

대부분은 통신사 기지국 탓을 합니다. Whisper 모델의 음향 잡음 내구성이 약하다고 탓하는 사람도 있습니다. 단말기의 노이즈 캔슬링 알고리즘을 의심하기도 합니다.

정말로 AI 모델이 그렇게 취약한 것일까요?

지난주 우리는 Ubuntu 22.04 LTS 테스트 서버에서 패킷 캡처를 진행했습니다.

테스트 구성은 단순했습니다: 가상 이더넷 쌍을 통해 두 대의 서버를 연결했습니다. Linux tc 명령어를 사용하여 netem 매개변수를 주입했습니다: 10% 패킷 손실, 40ms 기본 지연, 10ms 지터. 64kbps 단일 채널 Opus 오디오를 20ms 프레임 단위로 스트리밍했습니다.

Wireshark 필터에 rtp와 rtcp를 걸었습니다. 붉은색과 흰색의 재전송 및 순서 역전 패킷 표시가 순식간에 화면을 뒤덮었습니다.

우리는 세 차례의 테스트 로그를 대조했습니다.

문제는 기지국에도, 언어 모델의 지능에도 있지 않았습니다. 병목은 전송 계층에 있었습니다: 인간 회의용 target delay 전략과 LLM이 요구하는 의미론적 마감 시한이 정면으로 충돌하고 있었던 것입니다.

## 1. 인간 화상회의 지향 설계: WebRTC의 Target Delay는 누구를 보호하는가

음성 데이터 유실의 본질을 이해하려면 WebRTC의 설계 전제로 돌아가야 합니다.

<img src="https://img.freeaidog.com/images/blog/webrtc-moq-context-loss-architecture.webp" alt="맥락 유실과 지연 예산 관점에서의 WebRTC와 MoQ 아키텍처 비교" />

이 구조는 2011년경 정립되었습니다. Google이 Global IP Solutions를 인수한 뒤 미디어 엔진을 오픈소스로 공개하여 Chromium에 탑재한 것이 바로 오늘날의 libwebrtc입니다.

대상 사용자는 철저하게 생체 인간이었습니다.

두 사람이 화면을 마주보고 Google Meet이나 Zoom으로 대화합니다. 인간 간 대화의 지연 허용 범위는 극히 좁습니다. 지연이 200ms를 초과하는 순간 두 사람이 동시에 입을 열어 말이 엉키는 민망한 상황이 발생합니다. 수백 밀리초의 지연 속에서 누가 자연스럽게 회의를 진행할 수 있을까요?

초저지연을 확보하기 위해 WebRTC는 엄격한 target delay 정책을 확립했습니다.

오디오 파이프라인의 중심에는 NetEQ 지터 버퍼가 있습니다. NetEQ는 지터 흡수, 시간 신축, 패킷 손실 은닉, 재전송 제어를 총괄합니다.

인간 회의에서는 실시간성이 완전성을 압도합니다. 지터로 인해 20ms짜리 Opus 오디오 패킷이 35ms 늦어져 예정된 재생 윈도우를 넘기면, NetEQ는 이를 기다리지 않습니다. 즉시 손실 은닉 알고리즘을 호출하여 전후 파형을 보간하거나 무음을 삽입합니다.

WebRTC는 SDP를 통해 a=rtcp-fb:* nack 협상을 맺고 재전송을 요청할 수 있습니다. 그러나 이 메커니즘은 비디오 키프레임 위주로 동작합니다. 오디오 스트림에서 NetEQ 재생 스케줄러가 지연된 패킷 하나를 받으려고 수백 밀리초 동안 재생을 멈추는 일은 절대 없습니다. 오디오가 끊겼다가 배속으로 쏟아진다면 인간의 귀는 견디지 못하기 때문입니다.

인간의 일상 대화에서는 자음 몇십 밀리초가 빠져도 뇌가 앞뒤 문맥을 통해 알아서 복원합니다. 정 이해하지 못하면 다시 물어보면 그만입니다.

WebRTC의 네트워크 전략은 패킷 손실 복원의 책임을 그대로 인간의 뇌로 떠넘겼습니다.

하지만 수신자가 AI 모델로 바뀌는 순간, 이 전제는 무너집니다.

## 2. 문맥 블로킹의 역설: 실리콘 모델은 문장 완성을 기다린다

대규모 언어 모델은 인간의 귀와 다릅니다. 20ms 단위의 잘게 쪼개진 소리를 실시간으로 들을 필요가 없습니다.

음성 AI 모델에는 엄연한 물리적 특성이 존재합니다: 문맥 블로킹.

일상적인 질문의 발화 타임라인을 살펴보겠습니다:

```text
0.0s : 프랑스의
1.0s : 프랑스의 수도는
2.0s : 프랑스의 수도는 어디에
3.2s : 프랑스의 수도는 어디에 있나요?
```

이 3.2초의 물리적 과정을 주목해 보십시오. 인간이 마지막 물음표를 발음하기 전까지 모델은 파리라는 답변 계산을 시작할 수 없습니다. 문맥 전체가 온전하게 도착하는 것이 추론 착수의 필수 조건이기 때문입니다.

인간이 발화하는 몇 초 동안, 전송 계층에는 매우 넉넉한 지연 허용 공간이 존재합니다.

만약 1.0초 시점에 패킷 손실이 발생하여 수도라는 핵심 단어의 패킷이 누락되면 WebRTC는 어떻게 반응할까요?

1. 핵심 명사가 포함된 RTP 패킷이 손실됩니다.
2. NetEQ는 패킷이 재생 시점을 놓쳤다고 판단하여 폐기합니다.
3. 이후 NACK 패킷이 도착하더라도 재생 스케줄러는 이미 해당 시점을 지나쳤습니다.
4. Whisper 음성 인식기에는 왜곡된 파형이 입력되어 프랑스의 어디에 있나요로 변환됩니다.
5. 주어를 잃어버린 언어 모델은 당황하며 다시 말씀해 주시겠어요라고 되물을 수밖에 없습니다.

주어를 빼앗긴 모델이 추측 외에 무엇을 할 수 있을까요? 이런 폐기 방식은 논리적으로 맞지 않습니다.

대역폭 관점에서도 모순입니다. 표준 64kbps Opus 오디오는 1초에 8KB에 불과합니다. 20ms 패킷 하나는 160바이트 수준입니다.

사용자가 문장 뒷부분을 마저 발음하는 데는 2초 이상이 걸립니다. 그 여유로운 2초 동안 네트워크는 한가합니다. 패킷 손실률이 10%에 달해도 RTT 40ms 환경에서 160바이트를 세 번 재전송하는 데는 120ms도 걸리지 않습니다.

사용자가 다음 숨을 쉬기도 전에 손실된 데이터는 여유 있게 복구될 수 있습니다.

사용자가 발화를 끝마친 직후 서버 측 오디오 인코더는 복구된 음성을 5ms 만에 모델로 전달합니다. 사용자는 지연을 전혀 느끼지 못합니다.

패킷 손실 자체가 치명적인 것이 아닙니다. 150ms짜리 화상회의 재생 창을 지키겠다고, 모델이 몇 초 뒤에나 필요로 할 문맥 데이터를 미리 쓰레기통에 버리는 행위가 치명적인 것입니다.

이것은 지연 시간 단축이 아닙니다. 의미론적 마감 시한을 무시한 설계 미스입니다.

## 3. 다운링크 재생의 딜레마: 서버 스레드는 왜 time.sleep을 호출하는가

다운링크 오디오 생성 라인 역시 동일한 구조적 한계에 묶여 있습니다.

최신 Cartesia Sonic이나 ElevenLabs Turbo 같은 음성 합성 엔진은 매우 빠릅니다. 10초 분량의 음성이라면 GPU 메모리에서 200ms 만에 합성이 끝납니다.

단말기 RAM은 매우 저렴합니다. 2분 분량의 비압축 오디오도 1MB 남짓한 메모리만 차지합니다. 왜 로컬에 미리 버퍼를 채워두지 않는 것일까요?

합성된 오디오를 일괄 전송하고 단말기 로컬 플레이어가 타임스탬프에 맞춰 재생하는 것이 상식적인 구조입니다.

그렇게 하면 차량이 터널에 진입하여 3초간 통신이 두절되어도 이미 받아둔 버퍼로 끊김 없이 음성을 재생할 수 있습니다.

하지만 표준 WebRTC 파이프라인은 패킷 도착 시점의 물리 클록에 의존합니다.

WebRTC AudioTrack은 애플리케이션 주도의 돌발 프리버퍼링을 지원하지 않습니다. 서버가 200ms 만에 10초 분량의 오디오를 쏟아부으면 수신 측 지터 버퍼가 즉각 넘쳐 소리가 찢어지거나 배속으로 재생됩니다.

이런 제약을 피하기 위해 일부 백엔드 엔지니어링 팀은 기형적인 회피 코드를 작성합니다:

```python
# 인간 발화 속도를 흉내 내어 프레임을 천천히 보내는 타협 코드
# 클라이언트 지터 버퍼 오버플로를 막기 위해 불가피하게 사용
while not audio_queue.empty():
    chunk = audio_queue.get()
    webrtc_track.send_frame(chunk)
    time.sleep(0.0195)  # 인위적으로 스레드를 재워 전송 속도를 억제
```

서버는 강제로 잠들고, 오디오 데이터는 이동통신망을 거북이처럼 기어가게 됩니다.

터널이나 음영 지역을 지나는 순간 천천히 가던 패킷은 사라집니다. 사용자는 반 토막 난 답변을 듣고 침묵을 맞이합니다.

연산 자원을 소모하고 토큰 비용을 지불했음에도, 전송 계층의 경직성 때문에 사용자 경험이 망가지는 것입니다.

## 4. Media over QUIC 도입: 전송 제어권을 의미론적 마감 시한으로 되돌리기

이러한 구조적 충돌을 극복하기 위해 오픈소스 커뮤니티가 주목하는 대안이 바로 Media over QUIC, 즉 MoQ입니다.

IETF RFC 9000 규격의 QUIC 위에서 동작하는 MoQ는 단일 연결 내에서 가벼운 객체와 트랙을 다중화합니다. 각 오디오 패킷에 명시적인 수명 주기와 우선순위를 부여할 수 있습니다.

```text
WebRTC 파이프라인:
PCM 오디오 -> UDP 데이터그램 -> 30ms 초과 시 강제 폐기 -> 문맥 파괴 -> 재질문 발생

MoQ 파이프라인:
PCM 오디오 -> QUIC 우선순위 스트림 -> 발화 종료 전 무음 재전송 -> 문맥 보존 -> 정확한 추론
```

이 방식은 두 가지 핵심 난제를 해결합니다.

### 1. 의미론적 마감 시한 기반 업링크 재전송

사용자가 발화하는 동안 MoQ는 context_deadline 마감 시한을 부여합니다. 발화가 완전히 끝나는 시점을 넘기지 않는 한, 유실된 오디오 패킷은 최우선 순위로 재전송됩니다.

우리는 테스트 클러스터에서 정밀한 비교 측정을 진행했습니다:

- 테스트 코퍼스: Common Voice 중국어 테스트 세트에서 추출한 100개 음성, 길이는 3.5초에서 6.2초.
- 네트워크 환경: Linux tc netem을 통해 10% 패킷 손실, 40ms 기본 지연, 10ms 지터 주입.
- 음성 인식: Whisper-large-v3 모델 사용, 탐욕적 디코딩 적용.
- 비교 대상: Pion WebRTC v4.0.0 대비 QUIC 기반 MoQ 프로토타입 게이트웨이.

실측 데이터는 명확했습니다:

WebRTC 환경에서는 100회 중 21회에서 중요 음성이 손실되어 재질문이 발생했습니다. JiWER 기준 3회 평균 단어 오류율은 16.8%, 분산은 1.4%였습니다.

반면 의미론적 재전송을 활성화한 MoQ 환경에서는 유실된 패킷이 발화 종료 120ms 전에 조용히 복구되었습니다. 평균 재전송 왕복 시간은 58ms였습니다. 단어 오류율은 무손실 환경의 3.1%에 근접한 3.4%를 기록했습니다. 100회 호출 중 재질문은 단 한 번도 발생하지 않았습니다. 불안정한 무선망에서 이러한 결정론적 복구는 엄청난 체감 차이를 만듭니다.

### 2. 가벼운 제어 플레인을 통한 즉각적인 인터럽트

클라이언트가 오디오를 미리 버퍼링해 두었을 때, AI가 말하는 도중 사용자가 말을 끊고 끼어들면 어떻게 될까요? 옛날 음성이 계속 재생될까요? 연결 자체를 끊어야 할까요?

MoQ는 매우 가벼운 제어 플레인을 통해 즉각적인 인터럽트를 처리합니다:

MoQ 규격에서 트랙의 생성과 취소 비용은 매우 저렴합니다. 서버가 사용자의 끼어들기 음성을 감지하면, 제어 스트림으로 UNSUBSCRIBE 명령을 보내 구 트랙을 종료하고 새 Track ID를 발급합니다.

수신 측 플레이어는 제어 프레임을 수신하는 즉시 밀리초 단위로 로컬 FIFO 버퍼를 비우고 새 트랙을 재생합니다. 하부 네트워크 소켓을 초기화할 필요가 전혀 없습니다.

```python
# 비동기 QUIC 세션에서의 동적 트랙 취소 제어 예시
import asyncio

class MoQAudioSession:
    def __init__(self, quic_connection, context_deadline_ms=4500):
        self.conn = quic_connection
        self.deadline_ms = context_deadline_ms
        self.current_track_id = 0

    async def handle_user_interruption(self):
        # 연결 리셋 없이 구 트랙 취소 제어 프레임 발송
        self.current_track_id += 1
        control_packet = {
            "type": "TRACK_ABORT",
            "old_track_id": self.current_track_id - 1,
            "new_track_id": self.current_track_id
        }
        await self.conn.send_control_frame(control_packet)
        # 클라이언트는 수신 즉시 기존 버퍼를 완전히 비움
```

## 5. 실전 도입을 위한 경계 조건과 기술적 한계

내일부터 프로덕션 환경의 WebRTC를 완전히 걷어낼 수 있을까요?

그렇지 않습니다.

새로운 전송 프로토콜을 도입할 때는 세 가지 장애물을 마주해야 합니다:

첫째, 기업 네트워크의 UDP 443 포트 차단입니다. 보수적인 기업 사내망이나 공용 와이파이는 보안을 이유로 비인가 UDP 트래픽을 차단합니다. QUIC 핸드셰이크가 실패하면 WebSocket이나 TCP로 폴백해야 하며, 헤드 오브 라인 블로킹 방지 이점이 반감됩니다. 차단 환경에 대한 폴백 대책은 준비되어 있습니까?

둘째, 브라우저 생태계의 성숙도입니다. WebRTC는 지난 15년간 브라우저에 최적화되었습니다. WebTransport와 브라우저 측 MoQ 라이브러리는 구형 Android WebView나 임베디드 브라우저에서 여전히 폴리필을 요구합니다.

셋째, 클라우드 백엔드 인터페이스 파편화입니다. 외부 음성 인식이나 합성 공급자가 원시 RTP 스트림만 지원한다면, 에지 게이트웨이에서 패킷 재포장과 타임스탬프 보정을 수행해야 하므로 메모리 복사 오버헤드가 발생합니다.

실측 데이터에 기반한 엔지니어링 권고는 명확합니다:

차량용 인포테인먼트, 산업용 핸디 터미널, 전용 스마트 하드웨어 등 네트워크 정책을 완전히 통제할 수 있는 환경이라면 QUIC 기반 오디오 전송을 우선 도입하여 통신 장애를 뿌리 뽑아야 합니다.

반면 불특정 다수 브라우저를 상대하는 일반 웹 애플리케이션의 경우, WebRTC를 안전한 폴백으로 유지하면서 네이티브 iOS 및 Android 앱부터 단계적으로 QUIC 오디오 전송을 확장하는 것이 합리적입니다.

모델 매개변수를 8B에서 70B로 키우더라도, 화상회의 시절의 target delay 규칙에 묶여 패킷을 버린다면 AI는 영원히 되묻기를 반복할 것입니다. 전송 배관을 새로 정비할 준비가 되셨습니까?
