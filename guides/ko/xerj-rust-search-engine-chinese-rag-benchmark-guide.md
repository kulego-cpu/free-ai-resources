온프레미스 사내 지식 베이스를 구축하는 엔지니어들 사이에서 GitHub 스타 약 2만 개를 기록한 싱글 바이너리 Rust 검색 엔진 XERJ 가 큰 주목을 받고 있습니다. 단일 실행 파일로 즉시 구동되며 표준 Elasticsearch 프로토콜과 호환되고 메모리 점유율도 수십 메가바이트 수준에 불과합니다. 영문 문서나 API 레퍼런스를 검색할 때는 밀리초 단위의 빠른 응답 속도가 무척 쾌적합니다.

하지만 실제 동아시아 한자 및 규정 비즈니스 코퍼스를 다루는 순간, 기본 설정은 심각한 한계에 부딪혔습니다.

우리는 208 건의 실제 엔터프라이즈 컴플라이언스 문서를 33,575 개 청크로 분할하고 60 개 문항으로 구성된 엄격한 종단간 벤치마크를 수행했습니다. 터미널에 출력된 결과는 충격적이었습니다. 네이티브 XERJ 의 BM25 어휘 검색에서 실제 증거 청크의 Top 3 재현율은 22.22% 에 불과했습니다. 종단간 업무 판정 달성률 역시 5.3% 로 급락했습니다.

어디서 문제가 발생했을까요. 약 2만 스타의 Rust 엔진이 기본적인 역색인조차 제대로 처리하지 못한 것일까요.

원시 청크와 검색 로그를 대조하며 원인을 추적한 결과, Rust 코어 엔진 자체의 검색 로직에는 아무런 문제가 없음을 확인했습니다. 검색 정확도를 무너뜨린 것은 동아시아권 비정형 텍스트에 내재된 세 가지 교묘한 전처리 함정이었습니다. 숫자 표기 방식의 불일치, 구형 PDF 폰트 CMap 매핑 오류, 단일 글자 기반 역색인 분할로 인한 과잉 리콜 현상이 원인이었습니다.

우리는 XERJ 의 Rust 코드를 단 한 줄도 수정하지 않고, 순수 Python 표준 라이브러리만으로 클라이언트 쿼리 어댑터를 구현했습니다. 동일한 33,575 개 청크로 벤치마크를 다시 실행했습니다. 결과는 완전히 반전되었습니다. Top 3 증거 청크 재현율은 91.11% 로 수직 상승했고 종단간 판정 달성률은 97.4% 로 회복되었습니다.

벤치마크 평가 리포트는 PR #3371, 코퍼스 추가는 PR #3372 로 xerj-org/xerj 메인 저장소에 병합되었습니다. 커널 차원의 네이티브 CJK 다국어 지원은 공식 Issue #3377 에서 추적 중입니다. 벤치마크 도구인 vericorpus 또한 GitHub 에 오픈소스로 공개되어 있습니다. 본 글에서는 우리가 직면했던 세 가지 실무 함정과 클라이언트 측 텍스트 복구 구현을 상세히 정리합니다.

## 벤치마크 환경과 코퍼스 규격

장난감 데이터 과적합을 방지하기 위해 이번 벤치마크에 사용된 33,575 개 청크는 전량 실제 컴플라이언스 문서에서 추출하여 단일 네임스페이스에 색인했습니다:

- 테스트 머신: Apple Silicon 칩, 통합 메모리 환경, macOS 운영체제
- 엔진 버전: XERJ v1.0.0-rc.101, 로컬 9200 포트 수신, XERJ_DISABLE_QUERY_CACHE=1 환경변수로 쿼리 캐시 완전 비활성화
- 코퍼스 청크 구성:
  1. 법규 코퍼스: 유효 법령 29 종, 총 3,204 개 조항을 개별 조항 단위로 보존
  2. 임상시험 테이블: NIH 및 Europe PMC 오픈 액세스 논문 55 편에서 추출한 271 개 정형 테이블
  3. 상장사 공시 문서: 텐센트 홀딩스 0700.HK 분기 보고서, 미국 SEC 10-K 공시, 커촹반 상장 투자설명서
- 검증 파이프라인: 검색된 Top 3 증거 청크를 로컬 엄격 검증 모델에 직결하며, 근거가 불충분할 경우 반드시 응답을 거부하도록 강제

33,575 개 청크를 색인하는 데 걸린 시간은 약 9.2 초에 불과했습니다. 빌드 처리량은 대단히 훌륭했으며 Rust 의 고성능 동시성 처리가 돋보였습니다. 하지만 법 조항, 재무 수치, 임상 지표를 묻는 쿼리가 전달되자 실제 검색 정밀도는 심각하게 무너졌습니다.

## 네이티브 검색이 직면한 세 가지 실무 장애

검색 실패 로그를 처음 열었을 때는 BM25 어휘 빈도 통계의 문제라고 짐작했습니다. 그러나 원시 텍스트를 한 줄씩 대조해 보니 문제는 입력단과 전처리 계층에 집중되어 있었습니다.

### 1. 아라비아 숫자와 한자 표기 간의 조항 번호 불일치

법률 조문의 원문은 대부분 한자 표기로 엄격하게 기재됩니다.

하지만 실제 비즈니스 환경에서 인간 사용자는 어떻게 검색할까요. 번거롭게 한자 숫자를 직접 입력하는 사용자는 드뭅니다. 대부분 "회사법 제 147 조가 규정한 이사의 책임은 무엇인가" 처럼 아라비아 숫자로 질의합니다.

기본 XERJ 의 어휘 분절기는 "제 147 조" 를 "제", "147", "조" 로 분해했습니다. 반면 인덱스 저장소에는 한자 숫자로 분해된 텀만 보관되어 있었습니다. 토크나이저는 색인 어휘 사전에서 147 을 매칭하지 못했고 핵심 한정 수치 가중치는 즉시 0 으로 떨어졌습니다. 결국 검색 결과로는 포괄적인 문맥만 포함된 무관한 단락들이 쏟아져 나왔습니다. 진짜 핵심 조항은 30 위권 밖으로 밀려났습니다.

핵심 조항이 누락되었습니다. 아무리 검색해도 찾을 수 없었습니다. 이 결함 하나만으로 법규 관련 질의의 정확한 적중률은 0 에 수렴했습니다.

### 2. 홍콩 증권거래소 PDF 폰트 CMap 오류와 줄바꿈 분절

금융 분야에서는 홍콩 증권거래소 공시 PDF 문서를 자주 다룹니다. 이는 비정형 RAG 에서 가장 까다로운 장애 요인입니다.

텐센트 0700.HK 분기 보고서를 분석할 때 기이한 현상이 나타났습니다. 월 표기가 포함된 모든 단락에서 키워드 검색이 모조리 빗나갔습니다. 추출된 텍스트를 터미널에 출력해 본 뒤에야 원인을 알 수 있었습니다:

```text
2026년 9월 30일 기준 3개월 -> 추출 결과 -> 2026년 9시 30일 기준 3개시
```

홍콩 증권거래소 일부 과거 문서에 내장된 폰트에서 달 월 자의 유니코드 CMap 매핑이 표준 코드표에서 벗어나 있었습니다. 텍스트 추출 시 해당 문자가 주검 시 자로 기계적으로 치환된 것입니다. 보고서 전체에서 이러한 오기재가 341 회나 나타났으며 표준 글자는 단 한 글자도 없었습니다. 사용자가 분기 실적을 검색해도 검색기가 찾아낼 리 없었습니다.

이러한 전면적 오타 앞에서 하부 엔진 성능이 아무리 뛰어난들 소용이 없었습니다. 검색 자체가 불가능했습니다.

페이지를 넘어가는 표의 줄바꿈 끊김 현상도 골칫거리였습니다. 재무상태표나 손익계산서에서 부동소수점 숫자가 소프트 줄바꿈으로 깨지는 일이 잦았습니다:

```text
매출 총계 39.\n9 억 달러
회계 음수 표기 \n1,234.5 백만 원
```

기본 분절을 거치면 소수점과 뒤따르는 숫자가 둘로 쪼개졌습니다. 39.9 억을 검색해도 색인에는 분절된 숫자만 남아 수치 구조가 완전히 파괴되었습니다.

### 3. 단일 글자 분절과 답변 불가 함정 질문의 과잉 리콜

시스템의 환각 억제 능력을 검증하기 위해 벤치마크에는 답변할 수 없는 함정 질문 4 개가 포함되어 있었습니다. 가령 해외 자회사 재무 데이터가 공시되지 않은 보고서에 대해 구체적인 해외 매출액을 묻는 방식입니다.

이상적인 시스템이라면 근거가 없음을 확인하고 거절 응답을 반환해야 합니다.

하지만 기본 BM25 규칙에서 엔진은 단일 글자 폴백 매칭을 작동시켰습니다. 질의에 포함된 개별 한 글자들이 보고서 내 수천 개 무관한 단락에 각각 매칭되었습니다. 쿼리마다 엔진은 15 개에서 최대 3,319 개에 이르는 무관한 청크를 긁어모았습니다. 언어 모델의 컨텍스트 윈도우는 노이즈로 가득 찼습니다. 모델은 억지로 답변을 조합하다 심각한 환각을 일으켰고 함정 질문 4 개 전부에 대해 오답을 생성했습니다.

## 순수 표준 라이브러리 기반 쿼리 자가 복구 솔루션

이러한 문제에 직면했을 때 많은 엔지니어링 팀은 하부 Rust 분절 플러그인을 새로 작성하거나 GPU 부하가 큰 Rerank 모델을 추가하려고 합니다. 하지만 엣지 배포나 저비용 환경에서 단순 문자 오류 때문에 GPU 인프라를 증설하는 것은 비효율적입니다.

우리는 클라이언트 진입 계층에 경량 어댑터 query_cn 을 작성했습니다. 서드파티 의존성 없이 Python 표준 라이브러리의 re, unicodedata, 딕셔너리 연산만으로 작동합니다.

처리 흐름은 세 단계로 명확히 나뉩니다:

```text
사용자 원시 질의
    │
    ▼
[1단계: 숫자 표기 양방향 확장]
"제 147 조" 를 한자 숫자 조항과 아라비아 숫자 형태로 동시 확장
    │
    ▼
[2단계: PDF CMap 및 회계 표 텍스트 복구]
오매핑 문자 보정 및 깨진 소수점 수치 결합
    │
    ▼
[3단계: 고신뢰도 구문 제약 및 함정 차단]
최소 단어 길이 강제 및 연관도 미달 시 빈 결과 반환
    │
    ▼
XERJ 검색 엔드포인트 전달
```

### 핵심 구현: 법률 조항 번호 양방향 변환

아라비아 숫자와 한자 숫자를 상호 변환하는 매핑을 구축했습니다. 정규식으로 법률 조항 패턴을 감지했을 때 두 표기를 동시에 multi_match 후보군으로 전달합니다:

```python
import re

CN_NUM_MAP = {
    '零': 0, '一': 1, '二': 2, '三': 3, '四': 4,
    '五': 5, '六': 6, '七': 7, '八': 8, '九': 9
}

def int_to_cn_clause(num_str: str) -> str:
    val = int(num_str)
    if val <= 10:
        return list(CN_NUM_MAP.keys())[val]
    if val < 20:
        return '十' + (list(CN_NUM_MAP.keys())[val - 10] if val > 10 else '')
    if val < 100:
        tens, units = divmod(val, 10)
        return list(CN_NUM_MAP.keys())[tens] + '十' + (list(CN_NUM_MAP.keys())[units] if units > 0 else '')
    if val < 1000:
        hundreds, rem = divmod(val, 100)
        tens, units = divmod(rem, 10)
        res = list(CN_NUM_MAP.keys())[hundreds] + '百'
        if tens > 0:
            res += list(CN_NUM_MAP.keys())[tens] + '十'
        elif units > 0:
            res += '零'
        if units > 0:
            res += list(CN_NUM_MAP.keys())[units]
        return res
    return num_str

def expand_legal_query(query: str) -> str:
    def replacer(match):
        raw_num = match.group(1)
        if raw_num.isdigit():
            cn_ver = int_to_cn_clause(raw_num)
            return f'第{raw_num}条 第{cn_ver}条'
        return match.group(0)

    return re.sub(r'第\s*(\d+)\s*条', replacer, query)
```

이 간단한 변환을 적용하자 사용자가 아라비아 숫자로 질문해도 두 표기가 함께 검색 엔진에 전달되어 역색인을 정확히 타격했습니다. 관련 조항이 즉시 검색 결과 최상단에 노출되었습니다.

### 핵심 구현: CMap 폰트 오류 안전 복구

홍콩 증권거래소 PDF 의 오매핑을 전역 문자 치환으로 처리하면 안 됩니다. 전체 문서에서 특정 글자를 무조건 바꾸면 의료나 법의학 문서의 정상 단어가 왜곡될 수 있습니다.

문맥 정규식을 활용하여 날짜와 기간 표현으로 복구 범위를 한정했습니다:

```python
def repair_hkex_cmap_safe(text: str) -> str:
    # 날짜 문맥으로 한정하여 치환
    pattern = r'([零一二三四五六七八九十百千0-9]{1,4})\s*尸\s*([零一二三四五六七八九十百千0-9]{1,2})\s*[日號号]'
    
    def repl_date(m):
        return f'{m.group(1)}月{m.group(2)}日'

    res = re.sub(pattern, repl_date, text)
    
    # 3개월, 6개월 등 재무 주기 표현 복구
    res = re.sub(r'([三六九十二\d]+)\s*箇\s*尸', r'\1箇月', res)
    res = re.sub(r'([三六九十二\d]+)\s*个\s*尸', r'\1个月', res)
    
    # 줄바꿈으로 끊어진 부동소수점 결합
    res = re.sub(r'(\d+)\.\s*\n\s*(\d+)', r'\1.\2', res)
    return res
```

테스트 셋에서 이 코드는 텐센트 보고서 내 341 개 날짜 오류를 완벽히 복구하면서도 다른 도메인의 전문 용어를 훼손하지 않았습니다. 가볍고 확실한 해결책이었습니다.

## 60 문항 벤치마크 결과 비교

동일한 Apple Silicon 머신에서 인덱스를 재생성하지 않고 클라이언트 쿼리 어댑터만 전환하며 33,575 개 청크에 대해 세 차례 정밀 벤치마크를 수행했습니다.

60 개 벤치마크 문항은 다음을 포함합니다:
- SEC 공시 및 XBRL 데이터 기반 20 문항
- 딥테크 기업 IPO 투자설명서 기반 10 문항
- 현행 법규 및 컴플라이언스 질의 15 문항
- 답변이 불가능하도록 설계된 함정 질의 15 문항

세 분기의 측정 데이터는 다음과 같습니다:

| 평가 분기 | 정답 판정 | 오답 판정 | 거절 적중 | 순 점수 | 증거 R@1 | 증거 R@3 | 검색 p50 지연 |
| :--- | :--- | :--- | :--- | :--- | :--- | :--- | :--- |
| 기준 1: 사람 검수 표준 단락 직접 공급 | 52 | 7 | 1 | 38 | 100.0% | 100.0% | 0.0 ms |
| 기준 2: 기본 XERJ 네이티브 BM25 검색 | 24 | 11 | 25 | 2 | 17.78% | 22.22% | 113.67 ms |
| 기준 3: query_cn 어댑터 적용 검색 | 49 | 6 | 5 | 37 | 77.78% | 91.11% | 102.50 ms |

R@3 는 22.22% 에서 91.11% 로 상승했고 거절 관련 오판은 25 건에서 5 건으로 대폭 줄었습니다. 정답 단락 직접 공급을 만점 기준으로 볼 때 기본 BM25 의 순 점수율은 5.3% 에 불과해 실사용이 불가능했으나 경량 어댑터 도입 후 97.4% 수준까지 회복되었습니다.

p50 지연 시간은 오히려 113.67 밀리초에서 102.50 밀리초로 소폭 단축되었습니다. 무의미한 과잉 리콜이 조기에 차단되었기 때문입니다. 함정 질문 4 개도 거절 판정을 정확히 이끌어냈으며 단일 글자 노이즈로 인한 환각은 전혀 발생하지 않았습니다.

## 도입 시 체크포인트와 기술적 한계

다국어 및 비영어 RAG 를 구축할 때 검색 품질 문제가 발생하면 모델 크기부터 키우려는 경향이 있습니다.

문제가 생겼을 때 무턱대고 임베딩 모델을 바꾸거나 무거운 리랭커를 붙이기 전에 세 가지를 먼저 점검해야 합니다. PDF 폰트 인코딩 오류가 복구되었는지, 조항 번호 정규화가 이루어졌는지, 단일 글자 과잉 리콜이 제어되고 있는지 확인해야 합니다. 이 기초 작업이 선행되지 않으면 어떤 대형 모델을 투입해도 성과는 미미합니다.

XERJ 나 Elasticsearch 등 가벼운 오픈소스 검색 엔진으로 사내 지식 베이스를 구축하고 있다면 다음 항목을 우선 점검해 보길 권합니다:

- 텍스트 전처리 파이프라인에 PDF 특수 폰트 인코딩 복구 로직이 포함되어 있는가
- 조항 및 번호 필드가 인덱싱과 질의 단계에서 상호 정규화되고 있는가
- 비영어 입력에 대해 무분별한 단일 글자 폴백이 활성화되어 노이즈를 양산하고 있지 않은가

현재 XERJ 커널 차원의 CJK 다국어 지원 논의는 공식 Issue #3377 에서 이어지고 있습니다. 그러나 엔진 코어가 갱신되기 전이라도 진입 계층의 텍스트 정제와 쿼리 확장에 집중하는 것이 가장 적은 비용으로 확실한 품질을 확보하는 실무적 해법입니다.
