## 1. 두뇌 선정: 범용 인스트럭트 모델 대신 왜 Hermes 3인가

데스크톱 동반자의 두뇌를 고르는 작업은 대단히 까다롭습니다.

초심자들은 흔히 Llama나 Qwen의 공식 범용 인스트럭트 튜닝 버전을 그대로 붙이곤 합니다.

실제 일상 대화 테스트를 반복해 보면 범용 모델은 지나치게 경직되어 있습니다.

조금만 감정적인 주제를 꺼내도 인공지능 어시스턴트라는 정형화된 서두를 꺼내며 고객센터 챗봇처럼 딱딱한 어조로 응답합니다.

소설 창작 데이터로 미세조정된 초소형 모델은 어떨까요?

말투는 생동감 있지만 명령 이행 능력이 크게 떨어집니다. 프롬프트 제약이 길어지거나 기억 정보를 조회해야 할 때 출력이 쉽게 망가집니다.

개발자가 최종 선택한 엔진은 Llama 3.1 8B 기반으로 학습된 Hermes 3의 Q4_K_M 양자화 모델입니다.

왜 이 모델일까요?

오픈소스 생태계에서 Hermes 3는 뛰어난 롤플레잉 몰입도와 엄격한 구조화 출력 제어로 높은 평가를 받습니다.

캐릭터 설정을 벗어나 훈계를 늘어놓지 않으며, 복잡한 인물 배경과 어투 제한을 단단하게 유지합니다.

무거운 엔터프라이즈 추론 서버 대신 가벼운 Ollama 런타임을 바이너리에 내장했습니다.

단일 모델의 VRAM 점유량은 5GB 미만입니다.

하지만 단일 GPU 환경에서는 물리적 메모리 한계에 곧바로 부딪힙니다: 8GB나 6GB 카드를 장착한 상태에서 후속 음성 및 시각 모델을 함께 올리면 8B 모델만으로도 메모리 할당 실패 오류가 뜹니다.

메모리 부족 에러를 방지하기 위해 개발자는 적응형 계층화를 도입했습니다:

시스템 시작 시 가용 GPU 비디오 메모리를 점검합니다.

전용 VRAM이 12GB 이상이면 전체 8B Q4 모델을 로드합니다.

메모리가 안전 수치 미만이면 Llama 3.2 3B 경량 모델로 자동 후퇴합니다.

3B로 낮추면 깊은 유머 감각은 다소 줄어들지만, 보급형 카드에서도 충돌 없이 부드러운 텍스트 생성을 유지합니다.

비디오 메모리 여유분에 따라 모델을 자동 전환함으로써 저사양 그래픽카드에서도 안정적인 구동이 가능해집니다.

## 2. 청각, 시각, 음성 복제: 단일 기기 멀티모달 파이프라인 조립

두뇌가 준비되었다면 귀와 눈, 입 역할을 할 모듈을 연결해야 합니다.

여기서 가장 경계해야 할 점은 기능을 늘리기 위해 무거운 외부 프레임워크를 무작정 끌어오는 것입니다.

<img src="https://img.freeaidog.com/images/blog/yozakura-local-3d-ai-companion-architecture.webp" alt="Yozakura fully local 3D desktop AI companion architecture and multimodal memory tiering" />

개발자가 엮어낸 미니멀한 멀티모달 퍼즐은 다음과 같습니다:

첫 번째 블록은 귀, 즉 음성 인식 텍스트 변환입니다.

순수 C 언어로 작성된 whisper.cpp를 채택했습니다.

왜 더 큰 음성인식 모델을 올리지 않았을까요?

로컬 실시간 대화에서는 지연 시간 단축이 최우선이기 때문입니다.

base.en 모델은 비디오 메모리를 수십 메가바이트만 사용하며, 음성 조각의 변환 지연 시간은 200밀리초 미만입니다.

사양이 넉넉하다면 인식률이 더 높은 small.en으로 변경할 수도 있습니다.

두 번째 블록은 눈, 데스크톱 화면 캡처 인식입니다.

파이프라인에 Qwen3-VL 4B 시각 멀티모달 모델을 연결했습니다.

궁금한 이미지를 플로팅 창으로 끌어다 놓으면 캐릭터가 시각 정보를 즉시 분석하여 자신이 보고 있는 내용을 실시간으로 설명합니다.

세 번째 난제는 입, 즉 자연스러운 음성 합성입니다.

상용 도구들은 폐쇄형 클라우드 API에 의존하여 오프라인에서 먹통이 되며 글자당 청구 비용도 부담스럽습니다.

이 프로젝트는 MIT 라이선스의 Chatterbox Turbo와 초경량 Kokoro-82M 음향 가중치를 결합해 제로샷 음성 복제를 구현했습니다.

추론 속도가 매우 빨라 한 문장의 음성 합성이 보통 300밀리초 이내에 완료됩니다.

가장 중요한 점은 음소 단위 타임스탬프를 함께 추출한다는 사실입니다.

이 타임스탬프를 통해 프론트엔드 렌더러가 3D 캐릭터의 입술 메시를 밀리초 단위로 제어하여 정확한 립싱크를 구현합니다.

네 개의 인공신경망을 단일 장비에서 동시에 돌리려면 메모리 장부를 명확히 계산해야 합니다:

Hermes 3 8B 점유량 4.9GB.

Qwen3-VL 4B 점유량 3.1GB.

whisper.cpp와 Kokoro 상주 메모리 합계 약 1.2GB.

전체 VRAM 소모량은 약 9.5GB 선에서 안정적으로 유지됩니다.

즉 평범한 RTX 4070 12GB나 RTX 3060 12GB 그래픽카드 한 장으로 외부 연산 자원 없이 전체 파이프라인이 완전 로컬 구동됩니다.

## 3. 프론트엔드 렌더링과 로컬 기억: 투명 오버레이 인터페이스

많은 인공지능 데스크톱 실험작들이 버려지는 이유는 인터페이스 조작감이 나쁘기 때문입니다.

전체화면은 에디터 코드를 가리고, 일반 팝업창은 마우스 클릭을 가로막습니다.

표현 계층에는 Unity 6 엔진을 사용하고 캐릭터는 범용 VRM 표준 규격 파일을 불러옵니다.

VRM 형식을 채택하면 커뮤니티의 방대한 애니메이션 캐릭터 에셋을 자유롭게 교체할 수 있습니다.

윈도우 데스크톱 상호작용 측면에서는 운영체제 네이티브 API를 활용해 투명 채널이 적용된 무테 최상위 고정 창을 구현했습니다.

여기에 마우스 클릭 관통 토글을 지원합니다.

대화하지 않을 때는 코드 에디터나 브라우저 창 모서리에 조용히 앉아 있는 인형처럼 머뭅니다.

마우스 클릭이 캐릭터를 관통해 뒤쪽 활성 창으로 전달되므로 코딩 작업에 전혀 방해가 되지 않습니다.

입력 방식은 버튼 누르고 말하기, 상시 백그라운드 청취, 키보드 텍스트 입력의 세 가지 통로를 지원합니다.

또 하나의 실용적인 부분은 로컬 기억 저장소입니다.

많은 프로젝트들이 거대한 벡터 데이터베이스를 붙이고 컨테이너를 별도로 띄우곤 합니다.

일상적인 책상 대화에 무거운 벡터 검색 엔진이 정말로 필요할까요?

데스크톱 환경에서는 과도한 데이터베이스 구성이 오버헤드만 키우는 경우가 많습니다.

Yozakura는 플랫 텍스트 메모 방식을 사용합니다:

캐릭터마다 텍스트 파일 하나를 로컬에 둡니다.

한 턴의 대화가 끝나면 백그라운드 소형 모델이 좋아하는 음악이나 작업 중인 프로젝트 이름 같은 사실을 요약해 파일 끝에 덧붙입니다.

다음 대화 시작 시 이 간결한 노트를 시스템 프롬프트 컨텍스트로 주입합니다.

기억 초기화도 간편합니다. 초기화 버튼을 누르면 텍스트 파일이 즉시 0바이트로 비워지며 모든 데이터는 로컬 파일시스템의 엄격한 통제 하에 남습니다.

## 4. 실전 트러블슈팅: TTS가 행동 지문까지 읽어버리는 사고

이러한 파이프라인을 직접 조립하다 보면 예상치 못한 문제를 겪게 됩니다.

유사한 대화 파이프라인을 구축할 때 황당한 오작동을 경험한 적이 있습니다.

롤플레잉 언어모델은 별표 기호로 감싼 행동 묘사를 즐겨 출력합니다.

예를 들어 모델이 "안녕, *눈을 깜빡이며 고개를 갸웃거린다*" 같은 문장을 생성합니다.

이 가공되지 않은 텍스트를 음성 합성 엔진에 그대로 넘기면 낭패를 봅니다.

TTS 모듈은 대사와 무대 연출 지문을 구분하지 못합니다.

스피커에서 무미건조한 목소리로 "안녕 별표 눈을 깜빡이며 고개를 갸웃거린다 별표"라고 글자 그대로 소리 내어 낭독해 버립니다.

이 기계적인 낭독이 나오는 순간 공들여 만든 몰입감이 산산조각 납니다.

텍스트 정리를 위해 또 다른 LLM을 호출하면 원치 않는 수백 밀리초의 지연이 추가됩니다.

개발자는 파이프라인에 스트리밍 정규식 필터를 배치해 이를 해결했습니다.

언어모델이 토큰을 스트리밍하는 도중 이중 포인터 버퍼로 별표로 둘러싸인 행동 지문을 실시간 감지합니다.

행동 지문이 감지되면 즉시 Unity 애니메이션 상태 머신으로 분기하여 캐릭터의 깜빡임, 미소, 손 흔들기 모션으로 변환합니다.

순수한 대사 텍스트만 음성 합성 엔진으로 전달되어 음성을 생성합니다.

스트리밍 청크 경계에서 별표가 잘려 들어오면 어떻게 처리할까요?

오른쪽 별표가 닫힐 때까지 버퍼에서 출력을 잠시 보류하고 다음 토큰이 도착한 뒤 라우팅을 진행하면 대사에 지문이 섞여 들어가는 문제를 막을 수 있습니다.

이 스트리밍 필터링 덕분에 불필요한 2차 추론 비용이 들지 않습니다.

엔드투엔드 응답 속도는 쾌적한 밀리초 단위를 유지합니다.

## 5. 현실적인 한계: 패키징된 배포판과 직접 구축의 갈림길

이 아키텍처를 검토할 때 엔지니어다운 냉정한 시선이 필요합니다.

단일 GPU 환경에서 메모리 계층화를 무시하고 거대 모델을 강제로 구동하면 1회 응답 지연이 5초 이상으로 늘어나 작업 리듬이 크게 끊깁니다.

Yozakura는 마이크로소프트 스토어를 통해 배포되는 1인 개발 소프트웨어로 핵심 코드가 완전히 공개되어 있지는 않습니다.

완전한 코드 자율성과 투명성을 원한다면 공개된 기술 설계를 바탕으로 직접 구축하는 편이 확실합니다:

추론 백엔드는 Ollama로 실행.

음성 합성은 오픈소스 Chatterbox 연동.

표현 계층은 오픈소스 Unity VRM 오버레이 연결.

직접 검증하며 정리한 실전 기준 세 가지는 다음과 같습니다:

첫째, 8GB 미만 VRAM 환경에서 8B 모델을 무리하게 돌리지 말 것.

3B 4-bit 모델로 낮추는 편이 렌더링 프레임레이트와 음성 생성 반응성 측면에서 훨씬 쾌적합니다.

둘째, 지문 텍스트와 대사 음성의 분리 파이프라인을 반드시 갖출 것.

스트리밍 정규식 처리를 생략하면 데스크톱 동반자는 대본 지문을 그대로 읊는 기계가 되고 맙니다.

셋째, 소형 모델에 지나치게 복잡한 논리 추론을 기대하지 말 것.

코딩 중 머리를 식혀주는 친근한 데스크톱 동반자로 대하는 것이 좋습니다. 본격적인 알고리즘 구현에는 주력 코드 전용 모델로 전환해야 합니다.

VRAM 분배를 명확히 하고 스트리밍 텍스트 정제를 거친다면 일반 그래픽카드 한 장으로도 외부 의존 없는 로컬 멀티모달 환경을 구축할 수 있습니다.
