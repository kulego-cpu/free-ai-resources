## 通用运行时的抽象折中与作弊流派的分化

当下的本地推理框架，走到了极其尴尬的分岔路口。

以 llama.cpp 为代表的大一统工程，本质上是个兼顾全平台的模型动物园。

它要照顾的东西太多了：CPU、Apple Metal、NVIDIA CUDA、AMD ROCm、Intel SYCL、Vulkan……

代码库不得不充斥海量通用抽象。

任何一个针对特定架构的深度汇编补丁，想合并进主干都难如登天。

主干维护者必须顾虑跨硬件兼容；一旦动了底层内存排布，旧架构可能直接报段错误。这就导致主干代码更新虽然频繁，但在特定消费级显卡上的执行效率，往往只能维持在勉强能用的温吞状态。

各路坐不住的工程师，自然开始自立门户。

过去这半年，社区里涌现出大量专有小引擎。

有的专门用 Swift 与 Zig 榨干苹果芯片统一内存；有的专门针对移动端 NPU 做静态算子熔合。

但在这些林立的分支里，跑偏的流派也不在少数。

最扎眼的，莫过于某些在社交媒体上狂刷跑分的激进分支——比如 Strata 与 Basalt。

它们宣称能在 16GB 显存的单卡上，以不可思议的超高速度跑动上千亿参数的大型混合专家模型。

天下真有这等凭空掉馅饼的好事吗？

我扒了代码才发现：为了把速度指标刷高，它们偷偷篡改了混合专家模型的路由调度逻辑。

当模型原本判定某个词元需要调度存放在系统内存甚至固态硬盘中的专家权重时，推理引擎居然强行违抗逻辑，把词元就近硬塞给显存里的常驻专家。

字吐得确实像机关枪一样飞快。

可输出的回答呢？上下文全失，逻辑彻底乱套。

这种靠劣化模型思考质量换来的虚高跑分，除了发自媒体视频博眼球，在严谨的技术工作流里有什么实质用处呢？

你敢让一个连路由都被篡改过的引擎，替你写生产环境的业务代码吗？

我肯定不敢。

## 补丁改动面梳理：波面调度与片上缓存

`llama-cpp-rdna-boosts` 这个分支的改动面其实很窄。

量化表没动。

混合专家路由没动。

采样器算法也没动。

主要改动集中在两处：GEMM 矩阵乘法的 Wave32 路径，以及 attention 前向计算时的局部片上内存搬运。

这涉及到两代硬件微架构的差异：

AMD 数据中心专用的 CDNA 架构——例如 MI100 与 MI300 系列——在底层采用传统的 Wave64 宽波面组织形式；

而消费级 RDNA 系列——从 RX 6000 到 7900 系列——从硬件诞生起就是原生的 Wave32 架构，并且配备了双发射算术逻辑单元。

官方的 ROCm 后端，基本沿袭了 HIP 兼容层的通用折中方案。

许多核心矩阵乘法内核，依然按照较宽的波面组织线程块。

这在专业计算卡上跑得很顺，但在 7900 XTX 这种游戏卡上，就会引发严重的波面分流延迟：显存控制器在频繁等待换入，计算核心却在干等数据。

`llama-cpp-rdna-boosts` 的补丁直接重写了核心 GEMM 矩阵算子。

波面尺寸全面锁死在 RDNA 最习惯的 Wave32 规格。

同时重新规整了注意力前向传播时的局部内存数据搬运通道。让中间计算结果尽可能滞留在计算核心附近的片上高速缓存内，不必每次都跑回全局物理显存去兜圈子。

收益直接体现在硬件监控曲线上：

显卡功耗从之前的两百瓦刚出头，直接顶到了额定功耗墙；

显存读取带宽终于拉出了一条饱满平直的高原曲线。

## 真实测试环境与版本链踩坑实录

不交代完整测试环境与版本链的评测全是耍流氓。

我这次用来压测的硬件平台，是一台外接独立显卡拓展坞的高性能测试机：

- 显卡核心：AMD Radeon RX 7900 XTX。显存规格 24GB GDDR6。核心代号 Navi 31 与 gfx1100。
- 宿主驱动：AMD ROCm 6.2.4 用户态驱动包。操作系统 Linux 6.11 内核。
- 通道拓扑：雷电 4 外接显卡拓展坞。物理接口协商为 PCIe 4.0 x4。系统识别为独立 GPU 渲染节点。
- 拓扑损耗：雷电 4 实际通道带宽约 3.2 GB/s。解码阶段权重全部常驻显存，总线带宽几乎零影响；预填阶段大段提示词通过主机向设备端搬运，受限于总线吞吐，导致预填性能相比直插主板约有 8% 的损耗。
- 压测模型：ukisai 发布的 Swift-1.5-Qwen3.8-27B-GGUF。量化等级 Q6_K_L。总权重文件体积约 21.4 GB。
- 解码选项：开启投机预测。设置参数 `--draft 2`。

这里需要澄清一个版本链细节：

容器镜像的 tag 写作 `server-rocm-10.1`。这里的 10.1 是维护者自动化构建仓库的内部流水线编号，而非 AMD 官方的 ROCm 版本。容器镜像内部实际预装了针对 gfx1100 架构编译的 ROCm 6.2 基础运行库，与宿主机的 6.2.4 驱动完全兼容。

拉取镜像：

```bash
podman pull ghcr.io/stew675/llama-cpp-rdna-boosts:server-rocm-10.1
```

挂载本地模型目录并把显卡设备节点完整映射进去：

```bash
podman run --rm -it \
    --network=host \
    --device /dev/kfd \
    --device /dev/dri \
    --group-add video \
    -v "$HOME/models:/models" \
    "ghcr.io/stew675/llama-cpp-rdna-boosts:server-rocm-10.1" \
    /llama-server \
    -m /models/Swift-1.5-Qwen3.8-27B-Q6_K_L.gguf \
    --host 0.0.0.0 \
    --port 8080 \
    -ngl 99 \
    -c 16384 \
    --ubatch-size 512 \
    --flash-attn \
    --draft 2
```

部署过程中我踩过一个明显的坑：

第一次运行时命令漏掉了 `--flash-attn`，终端日志立刻输出警告：

```text
ggml_cuda_op_flatten: flash attention disabled, falling back to unoptimized rocm attention kernel
```

此时逐词元解码速度只有 38 tokens 每秒，提升极其有限。

必须显式补上 `--flash-attn` 参数，专为 Wave32 架构重写的片上共享内存注意力算子才会被真正激活。

## 性能账本与质量交叉核验

先看测试账本。

在同一台测试机上，我针对官方原生镜像与补丁分支镜像，连续进行了五轮长文本代码生成测试，取各项读数的中位数进行硬核对照：

| 运行时引擎版本 | 上下文预填吞吐 | 逐词元解码速度 | 显存常驻占用 | 代码回归测试通过率 |
| :--- | :--- | :--- | :--- | :--- |
| 上游原生 llama.cpp b4120 | 712 t/s | 35.2 t/s | 21.8 GB | 100% |
| rdna-boosts 专用补丁版 | 1318 t/s | 55.4 t/s | 22.1 GB | 100% |

先说这组数字的客观事实：

预填阶段吞吐从 712 提升到 1318 tokens 每秒；

逐词元解码速度从 35.2 提升到 55.4 tokens 每秒；

常驻显存开销从 21.8GB 微增至 22.1GB，增加的约 300MB 主要来自针对 Wave32 展开的静态显存工作区。

必须强调的是：这组读数只代表当前单卡、Q6_K_L 量化以及 16k 上下文设置下的表现。严禁盲目外推到所有硬件与超长上下文场景。

在输出质量侧，我运行了一套包含 50 道复杂 Python 正则表达式与类型注解的基准题目进行回归测试：

两边生成的代码语法树完全一致，通过率全部为 100%；

在包含两百条技术问答的验证集上，困惑度 PPL 评测数值波动小于万分之三。

要彻底排除极端边界条件下的降精度风险，后续仍需针对 32k 以上的长上下文表现以及逐层 logits 分布做进一步差分采样。

但至少在当前开发工作流下，代码生成与日常对话未见任何语义漂移。

## 适用边界与版本锁死代价

这个分支适合锁版本跑。

改动集中在 RDNA3 的 GEMM 和片上缓存搬运，没碰路由和量化，排查起来相对清楚。

但代价也很直接：

补丁高度绑定上游特定的提交节点——比如官方 b4120 节点。

上游 llama.cpp 几乎每周都在重构底层代码实现。前不久刚重构了上下文内存池，过几天又要调整批处理流水线。上游一旦变动核心接口，这些汇编补丁就必须重新经历痛苦的变基与适配。

在生产或日常主力环境使用该方案，我强烈建议采取以下防御策略：

第一，锁死经过验证的容器镜像 tag 或镜像摘要，切勿盲目跟随最新提交拉取；

第二，如果使用直插主板的 PCIe 4.0 x16 插槽，预填吞吐预计还能比拓展坞形态高出约 8% 到 10%，值得在固定工作站上深入测试；

第三，若遇到模型更新或架构变体报错，果断切回稳定成熟的官方主干镜像兜底。

你愿意为了这二十个 tokens 每秒的解码提速，在本地测试机上维持一套独立于主干的补丁镜像吗？

面对上游持续演进的架构洪流，这种微架构特化的外挂补丁究竟能维持多久的生命力呢？
