## 一、 为什么仅看模型文件大小必然翻车

显存到底被谁吃掉了？我们必须先算清真实的显存结构。

在实际推理中，显存开销由多块互不妥协的刚性账目叠加而成：系统桌面渲染常驻、CUDA 基础运行时、模型量化权重，以及随序列长度暴涨的动态 KV 缓存：

```
+-------------------------------------------------------------+
|                 GPU 物理显存总体结构 [例如 12GB]            |
+-------------------------------------------------------------+
|  1. 操作系统与桌面渲染常驻 [600MB - 1.2GB]                  |
+-------------------------------------------------------------+
|  2. 运行时与 CUDA Context 基础开销 [300MB - 600MB]          |
+-------------------------------------------------------------+
|  3. 模型静态权重只读区 [GGUF / AWQ / EXL2 量化数据]         |
+-------------------------------------------------------------+
|  4. 动态 KV Cache 缓存池 [随序列长度与并发线性增长]         |
+-------------------------------------------------------------+
|  5. 算子前向传播 Scratch Buffer [临时激活值复用区]          |
+-------------------------------------------------------------+
```

很多人忽视了第一项与第四项。在 Windows 操作系统下，DWM 桌面窗口管理器和后台浏览器硬件加速会静默吞掉将近 1GB 显存。在 Linux 桌面环境下，X11 或 Wayland 合成器通常也常驻数百兆空间。

更凶险的是动态 KV 缓存。以常见的 32B 模型架构为例：64 层注意力、8 对 GQA 键值头、单头维度 128。采用 fp16 半精度时——每 1024 个 token 上下文就要吃掉整整 256MB 物理显存。

算盘打得挺响吧？初看还剩 2GB 余量。一旦把上下文拉到 8k，仅 KV Cache 就要吞掉 2GB。再加上显卡驱动的基础 Context 开销，显存当场击穿。进程除了暴毙，没有别的退路。

## 二、 canfit 的核心机制：只读元数据秒级推演

传统做法为了验证显存占用，必须先把动辄数十 G 的模型权重完整下载到本地，拉起引擎后才能在日志里看到分配结果。如果显存溢出，几个小时的等待与带宽消耗全部打了水漂。

`canfit` 的机制并不复杂。它通过 Hugging Face API 仅仅读取目标模型的 `config.json` 与元数据，完全不需要下载任何张量权重。

它抓取的核心字段极其明确：
- `num_hidden_layers`：网络总层数
- `num_key_value_heads`：键值注意力头数，用于判定 GQA 比例
- `head_dim` 或 `hidden_size`：单头维度与隐层宽度
- 量化类型：结合 GGUF 或 AWQ 的位宽折算权重体积

```
[canfit 执行流]
输入模型 ID 与量化精度
   ↓
拉取远端 config.json [仅耗费几 KB 流量]
   ↓
解析层数、注意力头数、隐藏层维度与 GQA 比例
   ↓
代入目标上下文长度 [例如 4096 / 8192 / 16384]
   ↓
结合本地 GPU 硬件规格，直接输出拟合度报表
```

我们在 Ubuntu 24.04 与单卡 RTX 4070 12GB [驱动版本 560.35.03，CUDA 12.8] 下测试 `canfit v0.2.1`。请求只有几 KB。用 `time` 测了一次：`real 0.31s`，`user 0.04s`，`sys 0.02s`。终端直接给出关键决策：能不能全层卸载、最大上下文是多少、需要切多少层到系统内存。

## 三、 实操演练：GGUF 与 AWQ 双格式实测

`canfit` 采用纯 Rust 编写，编译出来的单二进制文件没有任何外部依赖。

### 极速安装与环境检测

在已经配置好 Rust 工具链的开发机上，直接通过 Cargo 安装：

```bash
cargo install canfit
```

安装完成后，首先查看本地显卡硬件规格：

```bash
canfit list-gpus
```

终端会输出当前物理显卡的显存总量与已被系统占用的残存容量。这一步必须先做。它能让你看清被桌面环境吃掉的真实开销。

### GGUF 格式推演：32B 模型的触顶现场

我们模拟在单卡 RTX 4070 12GB 显卡上，推演 `Qwen2.5-Coder-32B-Instruct` 在 GGUF 格式下的运行边界：

```bash
# 模拟 12GB 显卡，推演 Q4_K_M 量化精度与 8k 上下文
canfit eval \
    --model Qwen/Qwen2.5-Coder-32B-Instruct \
    --quant q4_k_m \
    --context 8192 \
    --vram 12
```

终端在 0.3 秒内返回了结构化表格：

```text
+-----------------------+--------------------+
| Parameter             | Value              |
+-----------------------+--------------------+
| Model Weights         | 19.85 GiB          |
| KV Cache [8k ctx]     | 2.00 GiB           |
| CUDA Overhead         | 0.55 GiB           |
| Total Required        | 22.40 GiB          |
| Available VRAM        | 12.00 GiB          |
| Fit Status            | FAILED [OOM]       |
| Max Layers on GPU     | 34 / 64            |
| Projected Decode      | 3.8 tokens/s       |
+-----------------------+--------------------+
```

数据一目了然。12GB 显存根本无法完整吃下 32B 的 Q4 权重，强制加载只能把 34 层放进 GPU，剩余 30 层必须卸载到系统内存。预测解码速度直接跌到每秒 3.8 个词。这速度拿来写代码，谁顶得住？看到这份报表，就完全没必要浪费半天时间去下载这个 20GB 的文件。换做是你，还会硬着头皮下吗？

### AWQ 格式实测：14B 模型的甜点落地

既然 32B 跑不动，那么 14B 的 AWQ 格式能否在 12GB 显卡上稳妥吃下 16k 满血上下文？我们直接推演 AWQ 模型：

```bash
# 针对 12GB 显卡推演 14B AWQ 模型与 16k 上下文
canfit eval \
    --model Qwen/Qwen2.5-14B-Instruct-AWQ \
    --quant awq \
    --context 16384 \
    --vram 12
```

终端输出如下：

```text
+-----------------------+--------------------+
| Parameter             | Value              |
+-----------------------+--------------------+
| Model Weights         | 8.25 GiB           |
| KV Cache [16k ctx]    | 2.00 GiB           |
| CUDA Overhead         | 0.55 GiB           |
| Total Required        | 10.80 GiB          |
| Available VRAM        | 12.00 GiB          |
| Fit Status            | PASSED [100% GPU]  |
| Max Layers on GPU     | 48 / 48            |
| Projected Decode      | 32.5 tokens/s      |
+-----------------------+--------------------+
```

AWQ 权重占 8.25 GiB，16k 上下文下 KV 占 2.0 GiB，算上驱动 0.55 GiB，总占用 10.80 GiB。这严丝合缝卡进了 12GB 显存安全线内，并给出每秒 32 个词的预期解码速度。单并发代码补全完全能流畅运行。

## 四、 常见量化格式的显存拟合实测对照

为了摸清不同消费级显卡的真实选型，我们在常见硬件档位上做了多轮推演对照，总结出这份参考账本：

| 显卡硬件规格 | 推荐最大模型参数量 | 推荐量化格式 | 安全上下文上限 | 真实落地点评 [基于 llama.cpp CUDA] |
| :--- | :--- | :--- | :--- | :--- |
| **8GB 显存** [RTX 4060 / 3060Ti] | 7B / 8B 模型 | Q4_K_M 或 Q5_K_M | 8,192 上下文 | batch=1 下 512 ctx 实测 45 到 55 t/s，日常主力配置 |
| **12GB 显存** [RTX 4070 / 3060] | 14B 模型 | Q4_K_M 或 AWQ | 16,384 上下文 | batch=1 下实测 28 到 36 t/s，并发若开两路 KV 翻倍需留余量 |
| **16GB 显存** [RTX 4080 / 4070TiS] | 14B 满血 或 27B 剪枝 | Q5_K_M 或 Q4_K_M | 32,768 上下文 | 吃下长篇技术文档，实测 22 到 28 t/s，无需妥协精度 |
| **24GB 显存** [RTX 4090 / 3090] | 32B 模型 | Q4_K_M | 8,192 上下文 | 8k ctx 下实测 40 到 42 t/s；若强开 32k 必爆显存 |

注意 24GB 显存那一栏。32B 模型在 24GB 单卡上，必须将上下文死死控制在 8k 左右。只要把上下文开到 16k 或 32k，总开销就会跨过 24GB 红线。提前用工具跑一遍，心里能没底吗？

## 五、 生产环境与并发推演的真实局限

虽然 `canfit` 能在下载前替我们挡掉九成以上的踩坑，但在实际落地服务时，仍有几处物理边界需要保持清醒：

1. **多并发连续批处理需要留出弹性余量**。canfit 默认基于单序列做静态推演。一旦你在 llama-server 或 vLLM 中开启多插槽并发，每个额外的并发 Slot 都会成倍克隆 KV 缓存。推演结果出来后，手动预留 1.5GB 到 2GB 冗余才保险。
2. **KV Cache 量化能救命但需显式指定**。如果推演显示显存刚好溢出 1GB 左右，别急着弃坑。在启动参数里加上 `-ctk q8_0 -ctv q8_0`。把 KV 缓存压成 8 位存储。开销直接砍半。
3. **桌面环境随时吃显存**。工作站开着 IDE，浏览器挂几十个标签页，轻松吃掉 1.5GB。推演时最好加上 `--os-reserved 1024`。提前把背景噪声从显存里剔除出去。

这工具不生产算力。它只干一件事：下权重前告诉你这张卡跑不动。我现在习惯下模型前先跑 `canfit eval`，OOM 就换 14B，别等几个小时下完再骂驱动。你手头显卡扣掉桌面占用后到底还剩多少？先跑一次 `canfit list-gpus`，别拍脑袋。
