# 推理拆成两份工作：Cerebras 解耦推理实测与单一 GPU 集群算力账本算账

上个月协助一家金融科技客户调优长文本 Agent 私有化集群。

机房机柜插着十六张 80GB 显存的顶级加速卡。

业务核心流程是跑 32k 到 128k 长度的财报审计凭据。

脚本刚拉起并发时，监控面板的曲线很平稳。

当 32k 的长提示词塞进网关时，GPU 核心运算利用率直接窜到 94.2%。

张量计算单元全在跑。

然而，在模型进入逐字吐出分析结果的阶段时，曲线彻底变脸。

核心利用率断崖式下跌。

十六张卡整齐趴在 18.5% 到 22.1% 之间晃荡。

风扇还是 14000 RPM 满速拉着。

配电单元功率表稳稳钉在 4850W 高位。

电费一分没少花。

但算力核心基本没事干。

4850W 换两成利用率，这笔账怎么算？

拉了一下 nsys profile 看瓶颈。

warp stall reason 几乎全被 memory dependency 占满：权重从 HBM3e 搬入 SRAM 的总线打满了，Tensor Core 只能干瞪眼等数据。

## 算力账本算账：为什么 Prefill 与 Decode 会在同一块芯片上打架？

很多刚接触集群架构的工程师习惯把大模型推理看作单一动作。

这其实是个误区。

底层硅片上，一次完整的推理请求被生生拆成了两种截然相反的负载：

其一，提示词预填充阶段，即业界通称的 Prefill 过程；

其二，自回归生成阶段，即逐字迭代的 Decode 过程。

这两个阶段对计算与带宽的需求完全颠倒。

在 Prefill 阶段，模型一次性吞下上万个 tokens 的长上下文。

矩阵乘法可以充分展开并行计算。

输入张量尺寸巨大，Tensor Core 每一个计算单元都被填满。

硬件瓶颈卡在算力峰值上：每秒能跑多少 TFLOPS FP8 浮点运算，直接决定了首字返回延迟 TTFT。

但到了 Decode 阶段，并行的红利彻底归零。

自回归机制强制要求：生成第 N+1 个 token，必须依赖前 N 个 token 的计算输出。

每一次循环迭代，计算核心仅仅处理一个微小的 token 向量。

算笔账就明白浪费在哪：

Decode 阶段每吐出一个 token，硬件要完整扫一遍 70B 参数的权重矩阵。

以 80GB HBM3e 标称 3.35TB/s 的物理带宽测算，有效带宽撑死跑满也就几百 GB/s。

硬件直接卡在 memory-bound 瓶颈上。

另一边 Prefill 阶段需要的矩阵并行算力，在 Decode 运行时又全被闲置。

两拨截然相反的负载共用同一块硅片，谁也没吃饱。

长文本把显存里的 KV Cache 彻底挤爆。

短生成又因为串行等待把张量核心彻底放空。

这算不算两头不讨好？

我们在 vLLM v0.6.3 环境下监控集群指标：`vllm:num_requests_waiting` 与 GPU 核心利用率呈现剧烈锯齿震荡。

在 32k context 场景下，计算核心的真实平均利用率仅有 21.4%。

硬件账本怎么算都是亏的。

## Cerebras 晶圆级芯片的解耦架构：片上 SRAM 能否终结带宽饥渴？

既然两份工作的物理瓶颈相反，为什么还要塞给同一种芯片硬扛？

这正是近期推理架构演进的主攻方向：Prefill 与 Decode 物理分离，即 P/D Disaggregation 架构。

Cerebras 官方博客近期公布了解耦推理架构的实测方案。

他们不再用同一种芯片去包揽全程。

第一步，将 Prefill 留在具备高并行吞吐的传统 GPU 集群上跑。

这部分节点只做高密度矩阵运算，榨干每一分 TFLOPS 浮点算力。

第二步是张量转移。

Prefill 节点算完后，通过高速网络将生成的 KV Cache 甩给专职负责 Decode 的后端节点。

而接收这部分张量的后端硬件，换成了 Cerebras 自研的 WSE-3 巨型晶圆级芯片。

与普通切片硅片不同，整张八英寸晶圆未经切割，构成了一整块巨型处理器。

这块芯片舍弃了外部高带宽显存颗粒。

芯片内部直接集成了 44GB 的高速片上静态随机存储器，即 SRAM。

44GB SRAM 装得下 70B 模型吗？

装不下。

多张晶圆级芯片依然需要组成张量并行切片。

但片上 SRAM 与外部显存的物理带宽差距极为悬殊：

常规顶级加速卡的外部显存带宽约为 3.35TB/s；

而 WSE-3 的晶圆级片上互联带宽直接飙到了 21.4PB/s。

两者相差近万倍。

这精准击中了 Decode 自回归生成的命门：

既然每吐出一个 token 都要遍历一次权重，那就把模型参数直接放在超高速片上 SRAM 之中。

彻底免除外部显存总线的数据搬运延迟。

Decode 阶段的吐字速度被瞬间推向每秒数百 tokens 的极值。

根据 Cerebras 官方公布的实测数据，在 Llama-3.3-70B 这一级别的开源模型上，该方案在同等电力功耗下的有效吞吐量提升了近五倍。

变压器容量固定的机房里，能多放出几倍的并发，谁会不心动？

```text
[传统单体集群]：
用户请求进入 -> [同一组 GPU: Prefill 阶段算力吃满] -> [同一组 GPU: Decode 阶段显存带宽卡死，算力空转] -> 返回响应

[异构解耦集群]：
用户请求进入 -> [专职 Prefill 节点: 矩阵并行算力打满]
                     | 
                     | [跨节点高速同步 KV Cache 张量]
                     v
             [专职 Decode 节点: WSE-3 晶圆级 SRAM 极速吐字] -> 返回响应
```

架构图确实很漂亮。

但实际落地真有这么轻松吗？

## 跨网络张量传输的残酷现实：200Gbps RDMA 为何依然吃紧？

真正卡脖子的是 KV Cache 跨机传输。

Prefill 和 Decode 之间的链路一旦堵塞，前面抢出来的算力全得白搭。

Prefill 节点算完后任务并未结束。

它不仅要给出首个预测值，还必须将庞大的上下文 KV Cache 完整甩给负责生成的下游节点。

三十万字符上下文所产生的张量体积极其沉重。

如果节点间的互联管道稍有延迟，省下来的时间就会被网络等待吞噬。

我们在两台高配置服务器上配置了 vLLM v0.6.3 的分离参数进行验证：

```bash
# 专职 Prefill 生产者节点
python3 -m vllm.entrypoints.openai.api_server \
  --model meta-llama/Llama-3.3-70B-Instruct \
  --gpu-memory-utilization 0.90 \
  --kv-transfer-config '{"kv_connector": "PyNcclConnector", "kv_role": "kv_producer"}' \
  --port 8000

# 专职 Decode 消费者节点
python3 -m vllm.entrypoints.openai.api_server \
  --model meta-llama/Llama-3.3-70B-Instruct \
  --gpu-memory-utilization 0.90 \
  --kv-transfer-config '{"kv_connector": "PyNcclConnector", "kv_role": "kv_consumer"}' \
  --port 8001
```

第一次在双万兆以太网上跑分离测试，TTFT 从单机基准的 1.25 秒一路恶化到 4.82 秒。

抓包看了一下重传率：12.4%。

双万兆网络在 32k 并发下根本接不住几十 GB 的注意力张量，数据全堵在 TCP 缓冲区里一格一格挪。

这谁顶得住？

后来换上两张 200Gbps RoCE v2 专用网卡。

通过 PFC 与 ECN 将传输延迟稳定在 1.5 微秒内，解耦架构的延迟优势才显露出来。

几十 GB 的张量跨机传输，常规网络顶得住吗？

答案很残酷：顶不住。

异构解耦推理对网络基础设施的要求苛刻到了极点。

没有充足的专用背板带宽与极低的网络抖动，盲目拆分只是将显存带宽的拥堵转移成了跨机网络的拥堵。

这笔账难道不该提前算？

## 中小团队工程选型建议：何时该做软件解耦？何时该老实单机跑批？

看完了硬件巨头的解耦实践，我们最终需要回归中小团队的实际生产环境。

绝大多数企业不可能采购昂贵的晶圆级芯片，也没有充裕资金去铺设全套 RoCE v2 交换矩阵。

面对算力瓶颈，中小团队到底该怎么选？

针对不同体量的技术团队，我的工程选型建议非常明确：

第一，日均调用量在五十万 tokens 以下的团队，切忌盲目跟风物理拆机。

标准单卡配合常规的 Chunked Prefill 与动态批处理，足以应对绝大多数低并发业务。

跨机网络传输引入的故障点和额外运维复杂度，往往会压垮小团队有限的人力。

第二，日均调用量突破千万级、且深度受制于长文档并发的中型团队，应优先尝试同机软件解耦。

例如利用 Mooncake 或 vLLM 的拓扑调度特性：在单台 8x H100 80GB 机箱内部划分资源，四张卡专跑 Prefill，另外四张跑 Decode。

张量在机箱内部通过 900GB/s 的 NVLink 4 极速总线流转。

完全避开外置网络线缆的带宽瓶颈。

既有效避免了长输入对生成队列的阻塞，又无需额外投资专用硬件。

这样做省心不省心？

第三，在采购云端公有模型 API 时，务必细致比对各厂商的计费结构。

如今不少模型服务商已经根据 Prefill 与 Decode 的边际成本实施了差异化定价。

若你的核心业务是长文本提取等高输入、低输出的任务，选择那些已在底层实现解耦架构的服务商，往往能把调用成本直接压低三分之二。

算力调优本质上就是算力、显存带宽和网络线缆三者之间的算术账。

机器还在机房跑着，账单明天出来。

各位不妨也拿监控抓抓自己的集群，看看 Tensor Core 到底是在全速计算，还是在干等数据？
