# 避开 DeepSeek 四千万 Token 账单的五条实战规矩

你是不是也以为 DeepSeek 便宜，就能放心大胆拿它当代码许愿池？

V2EX 社区热帖 t/1255533 里的楼主，结结实实挨了一记现实闷棍。

手头的 Codex 额度见底了。他转头接上 DeepSeek 接口，想一口气把项目的国际化语言包翻译成 9 门外语。结果几轮批量处理跑下来，后台账单当场炸裂：不知不觉烧掉了四千两百多万个 Token。

楼主在论坛发帖倒苦水：都说它单价低，怎么跑个翻译能吃掉几千万 Token？真没看出省在哪。

便宜是相对的。把它当成了能凭空猜透业务的许愿机，反复重试与上下文无序膨胀会把额度掏空。

下面这几条，是我自己踩出来的，也是那个帖子里十几个回复反复提到的。顺序按踩坑的先后排，不是按重要程度。

## 规矩一：提示词前缀顺序不能动——不中缓存，跑得越快亏得越惨

很多人以为调用大模型翻译 9 种语言，消耗的 Token 纯粹是原文长度乘以 9。

算盘打得挺顺。现实却很残酷。

真实的工程灾难是这样发生的：楼主每次发请求，都把厚厚的原始 JSON 字典连带几千行已经翻译完的上下文原样塞进 Prompt 里面；多轮对话越聊越长，单次请求的输入上下文迅速膨胀到两三万 Token。

最要命的是前缀缓存彻底击穿。

DeepSeek 官方的前缀缓存 Prompt Cache 机制对字符串顺序极其敏感。只要你在提示词开头改动了一个标点，或者把英文放到了中文前面？整段哈希校验直接失效。

原本享受一折费率的缓存命中直接归零。每次调用都被全额计费。几百次 API 循环跑下来，四千万消耗就是这么被无情堆出来的。

想要吃满缓存，必须采用严格的静态前缀结构：

```json
{
  "model": "deepseek-coder",
  "messages": [
    {
      "role": "system",
      "content": "你是资深后端工程师。遵循既定代码规范，输出符合无状态约束的纯函数。"
    },
    {
      "role": "user",
      "content": "【固定静态协议】输入数据结构: dict_a, 期望输出: dict_b\n---\n【动态任务输入】文件: services/worker.py, 待改函数: process_task"
    }
  ],
  "temperature": 0.0,
  "max_tokens": 2048
}
```

配合终端请求：

```bash
curl https://api.deepseek.com/chat/completions \
  -H "Content-Type: application/json" \
  -H "Authorization: Bearer $DEEPSEEK_API_KEY" \
  -d @payload.json
```

把固定的系统规则和静态样例焊死在最前端。动态变化的待处理文本，永远挂在末尾。

## 规矩二：它能写函数写不了架构——用任务清单取代无脑许愿

它能写函数，写不了架构。就这一条，别的都是衍生。

你把函数签名、入参类型、期望的测试用例摆齐，它基本一次过。你丢一句做个带权限的多租户系统——第一版它给你上装饰器，你说不对，第二版全换成中间件，第三版把字段名改成 user_id_v2。三轮下来 token 烧光了，代码也废了，你还得从头写。

我一般先用 Claude 出一份任务清单，格式固定成四列：文件路径 / 要改的函数 / 依赖 / 验收条件。清单里不写代码，只写改哪儿。

一份 40 条任务的清单，输入输出加起来不到 8k token。同样的活让 DeepSeek 自己猜架构？光返工就能烧掉二十万。

| 文件路径 | 目标修改函数 | 上下游依赖 | 单元测试验收条件 |
| :--- | :--- | :--- | :--- |
| services/auth.py | verify_token | redis_pool, jwt | 过期抛出 ExpiredTokenError，合法返回 user_id |
| services/order.py | calc_discount | models.Promotion | 阶梯满减计算精度保留两位小数 |
| tasks/sync.py | drain_queue | aiomysql.Pool | 超时自动重试且状态去重 |

拿着这份表格，一段一段喂给 DeepSeek。单次只喂一个任务。给明确入参出参。它吐出来的代码可以直接贴进工程。

## 规矩三：给堆栈日志排查底层报错才是甜区

真正让我改观的只有一个场景：贴 traceback。

上周三线上挂了个 asyncio.TaskGroup 里的 KeyError，栈深 47 层，中间夹着两段 aiomysql 的连接池等待。整段日志连同出事的那个函数——60 来行——一起丢进去。high 档，四十几秒，它直接指到第三处 conn.cursor 在 finally 里被复用了两次。

这个问题我盯了快一小时没看出来。它一眼。

```text
Traceback - most recent call last:
  File "/srv/app/services/worker.py", line 142, in process_batch
  File "/srv/app/services/worker.py", line 88, in sync_channel
KeyError: 'cursor_reuse_conflict'
```

查具体语法错、找漏写的空指针防御、拆解并发死锁，这是它的绝活。别让它大刀阔斧重构代码。把几十行具体报错和相关代码喂给它，省时省力。

## 规矩四：推理档位选 high 别碰 max——避免超时卡死与无意义递归

很多开发者一看到模型提供思考深度设置，本能地想拉到最高。真的有必要吗？

千万别迷信 max。

在 DeepSeek 的推理档位设计里，max 档会引发冗长的内部树状展开。对于具体函数实现与语法排错，思考深度拉到 max 往往会导致长达数分钟的等待。一旦连接中断？整个上下文重新计算，又是上万 Token 打水漂。

日常开发与查错，选 high 档就足够了。响应时间通常在三十秒到五十秒之间。推理过程直奔要害。既不会漫无边际地发散，也不会因为步数过多触发超时熔断。

## 规矩五：批量任务做幂等切片与上下文裁剪——绝不带全量历史滚雪球

四千万 Token 翻车的根源，是上下文当成了滚雪球。

楼主把已经翻译好的法语、德语、日语连同新的西班牙语全堆在一个会话里。跑到第七门语言时，上下文窗口已经吃满。每次发几句话都要传输整整几万 Token 的历史包袱，真的吃得消吗？

处理这类批量任务，必须采用切片流水线。

每一个子任务只携带它自己所需的输入与字典规则。输出完成后立即落盘。当前上下文当场销毁。下一个任务另起全新会话。

切断历史关联。再给每个请求加上幂等检查。中途即便某个网络请求断开，也只需要重新跑这一个几百 Token 的小切片，不会拖累整个批处理任务。

## 总结：用小刀切西瓜，别拿推土机绣花

梳理清楚这五条硬规矩，用 DeepSeek 敲代码才不会变成昂贵的试错游戏：

第一，前缀必须静态固定，靠前缀缓存吃下一折费率。

第二，它能写函数写不了架构，必须先用 Claude 或手动列出四列任务清单。

第三，排障找 bug 尽管喂堆栈日志，深层异步死锁一分钟挑出。

第四，推理档位选 high 别碰 max，省下超时悬挂与无谓重试。

第五，批量批处理必须做切片与独立幂等，绝不把全量历史当滚雪球上下文。

让昂贵的模型做脑力规划，让单价低的模型做执行与语法排错；管好你的上下文与缓存前缀，账单自然就回到可控区间了。
