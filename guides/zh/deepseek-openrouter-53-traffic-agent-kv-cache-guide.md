# DeepSeek 独占 OpenRouter 53% 流量背后：为什么多轮 Agent 绝不能乱用聚合中转？

监控网站 dirac.run 抓出的最新大盘，甩出了一串极具冲击力的数据。

单日 27 万亿 token 的吞吐。DeepSeek 独占 53% 份额。算上 Qwen 以及其他团队，开源阵营总体占比已经稳稳越过 75% 大关。

八个月前是什么光景？那时候榜单前几名几乎全被闭源大厂把持。短短两百多天，风向彻底变了。

社区里晒出的账单更是吓人。有人挂机跑了一整天自动化重构脚本，后台刷掉几十万 token，结账只要 4 美元出头。同样的工作量交给商业闭源主力模型，账单往往直奔 400 美元往上。

面对一百倍的价差，把自动化批处理任务切到开源接口在账面上确实显得格外诱人。闭源模型在极端复杂架构规划或者特殊多模态对齐上固然仍有长处，但对日常跑重构、刷单元测试的枯燥活计来说，谁也不愿跟研发经费过不去。

可真要在生产流水线里贪图方便乱选中转路由，账单很可能会在深夜给你上一堂极度昂贵的工程课。这笔看似便宜的开销到底藏着什么玄机？

## 一、 突然多出来的 38 美元账单

上周三深夜，我打算彻底重构一个维护两年的老工具库。

两万多行老旧代码。里面堆满了没有类型标记的遗留函数。纯靠人工肉眼排查，至少得耗掉整整两三天。

我写了个自主循环脚本。模式很简单：单会话多轮交互。为了省事，我随手把端点配成了 OpenRouter 上的 DeepSeek 接口。当时我想：每百万 token 才一毛多钱，随便跑能花几个钱？

刚开始跑的前 15 轮，体验挑不出毛病。

Agent 逐个读取源文件。分析模块依赖。生成配套测试用例。执行断言检查。

上下文从起步的 8K 逐渐涨到了 28K 上下。我切去后台刷了一眼账单流水：单次请求都在两分钱以内。极其便宜。

这时候夜宵时间到了。我合上笔记本，去楼下吃了碗牛肉面，顺便洗了个热水澡。前后耽搁了四十分钟左右。

回到书房重新点亮屏幕。终端还在原地待命。我敲下回车，让脚本继续推进第 16 轮到第 30 轮的任务。

两个小时后脚本跑完。测试全部通过。

我伸了个懒腰准备关机睡觉，顺便刷新了一下后台看板。账单数字跳出来的瞬间，我当场愣住了。

原本预估顶多四五美元的活，后台赫然扣掉了 38.6 美元。

怎么会这样？

模型在半夜偷偷涨价了？还是代码逻辑死循环了？可生成的提交记录分明一切正常。这多出来的几十美元究竟扣到哪里去了？

## 二、 10 分钟缓存断崖与跨节点穿透

我坐回椅子上拉取完整的 HTTP 响应日志。翻了半个多小时，猫腻终于浮出水面。

关键破绽在响应头里的底层服务商字段。

前 15 轮调用的响应头里，后端服务商固定为某一家算力公司。吃完夜宵回来的第 16 轮，后端服务商悄悄变成了另一家。

问题就出在这里。

OpenRouter 这类聚合服务本质上是一层流量分发调度器。它自身很少自建超大规模机房，而是把请求转发给底层的独立托管方——例如 Together、Fireworks、DeepInfra、Novita 以及 Lepton。

为了摊薄后端重复计算开销并给调用方让利，平台设计了一套基于会话哈希的节点亲和映射策略。

但这个机制存在一道硬伤：它只保留 10 分钟内的节点亲和映射。

在这 10 分钟之内，你连续发送请求，调度器会尽量把你发给同一家托管商的同一批 GPU 节点。

可如果思考时间超过了 10 分钟呢？又或者目标节点的并发队列暂时挤压满了呢？

调度器会立刻触发轮询降级。它会把你的下一个请求，直接甩给另一家完全陌生的机器。

这下麻烦大了。

上一家托管商的显存里，明明热着你前 15 轮累积下来的 28K 上下文 KV Cache。新接单的机器对此一无所知。新节点的显存完全是冷的。

面对凭空送过来的两万八千字长文本，新机器能怎么办？

它只能咬着牙，把这整整 28K 上下文从头到尾重跑一遍繁重的 Prefill 矩阵乘法。

计费瞬间失控了。

按照官方设计：命中缓存时，每百万 token 只要 0.014 美元；一旦缓存被击穿，只能按未命中的全量单价 0.14 美元结算。

价格瞬间涨了十倍。

这还只是单次调用的单价。随着 Agent 继续往下排查，上下文越来越长，从 30K 一路堆到 50K。

中间但凡再停顿超过 10 分钟，整条缓存链条就会再次崩塌。前面积累的所有优惠瞬间归零。

更折磨人的是等待时间。

前几轮由于缓存命中，回车敲下去一秒多就能吐字。缓存击穿之后呢？两万多 token 当场重算，光标死死卡在终端里整整 17 秒。

面对这种几十秒的停顿，脚本内部的超时重试难道不会误判吗？

重试一旦触发，就是又一次全量重算。原本几美元的活，硬生生被各家节点的反复冷启动刷成了 38 美元。面对这种隐形账单，谁愿意默默咽下这口闷气？

## 三、 官方接口的原生前缀缓存与寿命对比

既然中转聚合存在 10 分钟断崖，为什么直连 DeepSeek 官方 API 反而没有这种顾虑？

核心区别在于两者的显存调度架构完全不同。

官方集群原生围绕全局前缀缓存进行深度设计。只要你发送的文本序列前半段能够与历史数据严格重合，分布式调度器就会精准复用已经算好的注意力张量。

官方节点的缓存寿命有多久？绝非区区五分钟或者十分钟。

在大部分非极度拥堵的时段，官方缓存可以平稳留存数小时甚至更久。夜里关掉电脑，第二天上午重新唤醒继续提问，前序累积的几万字上下文依然能够高概率直接命中。

我们直接算一笔账：

```text
DeepSeek 官方 API 缓存命中与击穿计费对照：
┌────────────────────────┬─────────────────────┬─────────────────────┐
│ 费用与性能指标         │ 缓存完全命中        │ 缓存完全击穿        │
├────────────────────────┼─────────────────────┼─────────────────────┤
│ 输入单价 每百万 token  │ 0.014 美元          │ 0.140 美元          │
│ 30K 上下文单次输入成本 │ 约 0.00042 美元     │ 约 0.00420 美元     │
│ 40 轮多步 Agent 累积开销│ 约 0.28 美元        │ 约 3.65 美元        │
│ 首字生成延迟 P95       │ 约 1.2 秒           │ 约 14.8 秒          │
└────────────────────────┴─────────────────────┴─────────────────────┘
```

看清楚这个数据落差。

四十轮深层交互。缓存全命中的总开销不到三毛钱；一旦频频击穿，仅输入成本就会飙升十倍以上。

更关键的是安全底线。

聚合中转经过了多层网络跳转与第三方私有节点。你的私有业务代码究竟在谁的机器内存里短暂停留过？谁能给出具备法律效力的合规保证？

官方直连白纸黑字承诺零数据留存政策：用户输入的内容绝不落盘训练新模型。对于商用代码库来说，这份确定性难道不值钱吗？

## 四、 榨干前缀缓存的工程构造技巧

换上官方端点之后，是不是就万事大吉了？

没那么简单。代码里的请求习惯不改，缓存一样会被你自己亲手破坏掉。

很多同学在封装 Agent 提示词时，习惯顺手在开头拼上一行当前时间戳：形如当前执行时间 2026 年 11 月 6 日 20 点 15 分。

又或者在循环中动态给每一轮请求生成一个随机的 UUID 作为会话标记。

这些随手写下的小动作，正是前缀缓存的头号天敌。

前缀缓存是严格自左向右逐字哈希匹配的。一旦你开头的第十个词是一个每秒都在跳变的时间戳，哪怕后面跟着五万字完全一致的代码正文，整条缓存链条也会在第十个位置当场碎裂。

后面几万字全部白费。

想要让缓存命中率稳定拉上 90% 高位，必须老老实实改造请求体构造逻辑：

```python
import os
import requests

DEEPSEEK_API_KEY = os.environ.get("DEEPSEEK_API_KEY")
API_ENDPOINT = "https://api.deepseek.com/v1/chat/completions"

# 静态系统前置提示词：严格禁止注入动态时间戳或随机数
STATIC_SYSTEM_PROMPT = (
    "You are a senior code refactoring engineer. "
    "Follow PEP 8 rules and emit only structured diffs."
)

def build_stable_payload(session_history, new_user_msg, current_time_str):
    messages = [
        {"role": "system", "content": STATIC_SYSTEM_PROMPT}
    ]
    # 历史消息严格按时间线顺序追加，切勿中途修改旧消息内容
    for item in session_history:
        messages.append(item)
    
    # 动态变量统一作为单轮附加说明挂在最新一条用户发言最末端
    decorated_user_msg = f"{new_user_msg}
[Meta: {current_time_str}]"
    messages.append({"role": "user", "content": decorated_user_msg})
    
    return {
        "model": "deepseek-chat",
        "messages": messages,
        "temperature": 0.0,
        "stream": False
    }

def call_deepseek(payload):
    headers = {
        "Authorization": f"Bearer {DEEPSEEK_API_KEY}",
        "Content-Type": "application/json"
    }
    resp = requests.post(API_ENDPOINT, json=payload, headers=headers, timeout=60)
    data = resp.json()
    
    usage = data.get("usage", {})
    cache_hit_tokens = usage.get("prompt_cache_hit_tokens", 0)
    cache_miss_tokens = usage.get("prompt_cache_miss_tokens", 0)
    
    return data, cache_hit_tokens, cache_miss_tokens
```

逻辑其实极其朴素：

第一步：静态角色设定焊死在最顶端。

第二步：历史上下文原封不动向下追加。

第三步：动态时间或者会话元数据，只作为后缀塞在最新单条指令之后。

只要保持头部字节雷打不动，分布式调度器就能在毫秒级捞出旧显存。缓存命中率自然能常年咬死在九成以上。

## 五、 Google 100 万亿背后的统计泡沫

回到最开始的数据话题。

在讨论 OpenRouter 27 万亿 token 的帖子底下，不少跟帖不以为然地拉出 Google 日均 100 万亿 token 的大盘进行对比。言下之意：开源阵营这点规模在巨头面前依然只是小打小闹。

这种直接类比忽略了测量口径。

两者测量的根本不是同一种算力开销。Google 每天统计到的 100 万亿 token 里，超过 95% 全是只读缓存命中。OpenRouter 上的 27 万亿 token 则是每次都在处理不同的代码逻辑。

在大型搜索引擎架构中，海量热门搜索词的索引模板常年常驻在专用 TPU 显存中。

用户每敲下一个搜索词，后台跑的大部分是超高速的缓存读取。真正引发前向推理计算的新增输入只占很小一部分。

更进一步看：Google 算力池最大的消耗方，本质上就是它自家的搜索引擎、内部推荐流以及自研办公生态。

拿巨头自家产品体系内部、高度重复且绝大部分靠缓存应付的读流量，去生硬对比 OpenRouter 上数万名独立开发者真金白银掏钱、每一笔都在探索未知业务逻辑的真实算力调用，这难道是一回事吗？

剥离掉命中率去看总吞吐，得到的终归只是一张纸面上的数字泡沫。

## 六、 选型底线与工程自检

折腾完这一整套流程，我给自己的日常选型划出了一条极其清晰的分界线。

如果只是日常做做单轮对话、偶尔查查冷门函数用法、或者单纯想在同一个界面里尝鲜各大开源机构的新权重，OpenRouter 依然是目前最省心的试验场。它抹平了繁琐的支付门槛，单次问答也不会受到节点切换的困扰。

如果你的工作流包含长程自主编码，或者需要频繁多步往返调试大型代码库，建议尽早关掉中转路由开关。

贪图那两分钟配置 API Key 的便利，换来的往往是深夜被突发击穿的数十倍虚高账单，以及动辄十几秒的严重卡顿。

直连原厂接口，把静态前缀死死焊在最前面，才是跑顺开源 Agent 的清醒姿势。
