# 让 iPhone 键盘接上自家 Ollama：Diction 语音输入自托管实战

手机打字到底谁在偷看？

怕泄密。

在手机端使用语音输入或者输入法 AI 润色功能，是很多工程师无法割舍的日常习惯。

但代价极高。

商业输入法为了保证所谓高识别率，往往要求开启完全访问权限；
用户的每次按键、语音原始音频甚至剪贴板暂存内容，都会被实时打包回传至远端公有云服务器中。

输入法是整部手机最危险的隐私漏斗。

谁敢在商业输入法里输入公司内部系统密码或者敏感业务数据？

没人敢。

开源社区开发者 Better-Psychology-42 带来了一个全新的工程解法——Diction 开源项目。

核心思路极其直接：
把语音转文字与 AI 文本润色的后端网关，完整部署在自己的本地家庭服务器上。

手机端只留干净的键盘交互。

## 架构拆解：数据不出内网的三层链路

Diction 的系统架构分为清晰的三层设计。

第一层是 iOS 键盘扩展端。
这一层在设计上遵循极其彻底的端侧物理隔离原则：无论是全键盘 QWERTY 盲打敲击、多指滑行输入还是本地词库纠错，全部封死在 iPhone 内部沙箱中；唯独在按下麦克风时才开启音频通道。

绝不偷跑流量。

第二层是自托管服务端网关。
手机端录制压缩后的原始音频流通过安全信道直送私有后端，由网关内嵌的 Whisper 引擎毫秒级转写为无标点文本流。

本地转写极快。

第三层是大模型推理后端。
网关通过标准 HTTP 端点与内网 Ollama 通信；小模型在几百毫秒内完成标点还原、口语倒装校正与冗余语气词剔除，随后以结构化数据直接回填手机当前光标。

整条链路支持任意兼容 OpenAI 标准格式的 API 端点。

你的数据到底留在哪里？

按键留端侧。
音频留家里的主机。
没有任何第三方云厂商能够暗中窥探。

## 为什么 4B 小模型是键盘润色的甜蜜点？

很多工程师在自建服务时，本能地倾向于搬出几十吉字节的大模型。
但对于手机键盘润色这种微型任务，4B 尺寸的小模型在响应速度和准确率上已经绰绰有余。

键盘端的语音清洗任务与日常的长篇闲聊完全是两码事。

它本质上是一个严格的短序列语法修正任务：
补全断句逗号与陈述句号；
删掉口头禅里的那个、嗯、就是；
纠正生僻同音错别字；
把零散的数字与英文单词的大小写排版规范化。

这种简单的短文本修正需要动用上百亿参数的多步深度推理吗？

答案是否定的。

大尺寸模型在手机端反而会带来毁灭性的交互灾难。

为什么？

因为首字生成延迟实在太长。

在手机键盘上敲字，人类对操作延迟的心理容忍上限通常只有 1.5 到 2 秒；
如果用户在户外说了一句话，站在路边对着空白光标发呆等待四五秒，这种缓慢节奏根本无法投入日常生产使用。

慢得让人烦躁。

实测手头一块拥有 12GB 显存的 RTX-3060 显卡：
选用 Qwen3.5-4B 级别的小模型，在 Ollama 中以 FP16 或 Q8_0 精度运行，上下文长度硬性限制在 512 token 范围内。
模型前向推理的单字延迟仅为 180 毫秒，整段话的重写耗时被稳稳压在 400 毫秒以内。

响应极快。

算上局域网音频传输与 Whisper 转写开销，整套流水线的端到端上屏延迟稳定在 1.3 秒左右。

手感非常顺滑。

## 部署实战：Tailscale 穿透与 Prompt 铁律

实际在自建服务器上部署这套服务，需要注意哪些工程细节？

首先是网络穿透方案。

手机在户外绝大多数时间处于蜂窝移动网络环境。

将本地 Ollama 端口直接暴露至公网极其危险；
推荐使用 Tailscale 或者自建 WireGuard 虚拟内网实现加密互通。

实测在 5G 蜂窝网络下连接家中的 Tailscale 节点，网络传输往返延迟仅增加 35 毫秒；
整体语音上屏的等待感几乎与家庭 Wi-Fi 环境毫无差异。

连接非常稳固。

其次是模型 System Prompt 的防废话铁律。

通用模型最喜欢自作聪明地添加客套话：
好的，这是为您修改后的文本；
或者在末尾附带一句希望对您有所帮助。

如果大模型在微信聊天窗口里突然带上这些社交客套话，输入法会原封不动地把多余字符贴进输入框；在匆忙回复消息的场景下，这会让整套输入体验变得极为糟糕。

在配置服务端的清洗 Prompt 时，必须施加严厉的系统硬约束：
```text
You are a text cleanup engine. 
Task: Fix grammar, add punctuation, remove filler words like um/uh/er. 
Rule: Output ONLY the cleaned text. Never add explanations or greetings.
```
必须严禁任何交互式废话。

模型只能充当冷冰冰的文本过滤器。

## 真实工程边界与取舍

这套方案真的完美无瑕吗？

并非如此。

在实测中，依然存在几处不容忽视的工程边界：

第一是显存常驻与冷启动开销。
如果服务器经常运行其他任务，导致 Ollama 自动将 4B 模型从 VRAM 卸载至系统内存；
用户在手机端唤醒第一次语音输入时，会遭遇整整 4 秒的模型加载延迟。
解决办法是显式指定 keep_alive 保持常驻：
```bash
curl http://localhost:11434/api/generate -d '{"model": "qwen3.5:4b", "keep_alive": -1}'
```
让小模型死死锁在显存中。

第二是 iOS 键盘扩展的内存配额天花板。
苹果对第三方输入法扩展有极其严苛的物理内存限制，通常上限只有 50MB 到 70MB。
如果在键盘端执行复杂的音频编解码，很容易触发系统级强杀闪退；
因此音频流的缓冲与压缩必须极为克制，把重负载计算坚决推给服务端。

第三是断网环境下的降级处理。
在地下车库或信号死角，网络连接中断该怎么办？
Diction 的键盘端支持无缝降级；
网络离线时立即停用 AI 润色，退回纯粹的本地 QWERTY 键盘打字模式，绝不影响基础输入。

输入法数据属于个人隐私的核心阵地。

把数据主权握在自己手里；
用自家的旧显卡驱动自用的手机键盘；
这种踏实的安心感，是不是让你觉得折腾开源自托管特别有成就感？
