## 50MB 单文件的静态编译边界

传统框架为什么体积庞大？

层层封装。Python 解释器占一块。PyTorch 动态库占几百兆。再加上各类前端与算子库，解压完动辄几 G。

FLYX 选了全 C++ 静态编译路线。

Linux 发布包为 45MB。Windows 可执行程序为 50MB。它砍掉了 Python，直接与驱动通信：

- 运行时依赖：系统仅需提供 `libcuda.so.1` 驱动接口
- 调度层：内置针对 Ada 与 Ampere 的预编译算子分发
- 权重装载：基于双解析器直接映射物理内存

纯净宿主机无需配虚拟环境。下载二进制后，加权限就能跑。

在 Ubuntu 22.04 下挂载模型：

```bash
chmod +x ./flyx-linux-x86_64
./flyx-linux-x86_64 \
  --model ./models/Qwen3.8-27B-UD-Q4_K_XL.gguf \
  --ctx-size 262144 \
  --host 0.0.0.0 \
  --port 8080 \
  --gpu-layers 99
```

如果端口被占了怎么办？

终端会输出错误码并退出。它绝不会留下孤儿后台进程。

## 显存与内存的分级放置机制

256K 长度全塞显存会怎样？

当场爆显存。瞬间 OOM。内核直接杀进程。

以 Qwen3.8-27B 为例。如果坚持使用标准的半精度浮点 FP16 来保存键值缓存，整个 256K 序列需要消耗将近 64GB 的存储空间，哪怕把两张消费级显卡绑在一起也根本塞不下。

FLYX 搞了一套 StrataFlux 分层缓存机制：

1. 显存保留热缓存：最近 32K 活跃 token 留在显存，维持点积算力。
2. 内存承接冷缓存：超出 32K 的历史数据被压成 2-bit 数据块，走非阻塞通道外溢到系统物理内存。

在 Qwen3.8-27B 采用 `UD-Q4_K_XL` 混合量化规格跑满 262K 上下文时，我们通过每两秒抓取一次 `nvidia-smi` 显存监控得到的真实分布如下：

- 模型静态权重：占用显存 17.24GB
- 32K 热键值缓存：占用显存 6.14GB
- 显存剩余安全边际：仅剩 0.62GB
- 系统内存外溢占用：2-bit 压缩后冷缓存占内存 6.94GB

剩下这 0.62GB 余量够用吗？

太悬了。随时 OOM。

动态激活稍微抖一下，或者系统后台偷跑一点图形渲染，马上报 CUDA out of memory。

这次 262144 token 确实跑通了，没报截断。但我目前只跑了一次，千万别当成免死金牌。

## 大海捞针测试协议与解码速率

长文本深处真能记住吗？难说。

我用脚本测了单针大海捞针。口径必须交代清楚，不能光给数字：

- 测试用例：共 51 组，覆盖 5% 到 95% 深度
- 插入机制：每组放 1 个特定 UUID 密钥作为 needle
- 生成参数：固定 prompt，`temperature=0`，`max_tokens=32`
- 判定标准：输出文本完全包含目标 UUID，精确匹配

这 51 组样本下全部命中目标暗号。

但 51 组样本够不够？

不够。坦白讲，样本量依然偏小。这里没有测多针重叠干扰，也没有测超密集提问，不能简单推导成百分百可靠。

解码速度基于 512 token 贪婪生成测算：

| 测试硬件与规格 | 模型量化版本 | 1K 上下文解码速度 | 128K 深度解码速度 | 256K 极限解码速度 | 256K 单针测试命中 |
| :--- | :--- | :--- | :--- | :--- | :--- |
| **RTX 4090** 24GB | `UD-Q4_K_XL` | 193.6 tok/s | 155.9 tok/s | 122.7 tok/s | 51/51 命中 |
| **RTX 3090** 24GB | `UD-Q4_K_XL` | 135.8 tok/s | 97.5 tok/s | 68.1 tok/s | 51/51 命中 |
| **RTX 5080** 16GB | `UD-IQ3_XXS` | 225.9 tok/s | 161.0 tok/s | 105.8 tok/s | 51/51 命中 |
| **RTX 4080** 16GB | `UD-IQ3_XXS` | 172.3 tok/s | 111.0 tok/s | 99.0 tok/s | 51/51 命中 |

为什么 4090 在 256K 满深度下还能跑出每秒 122 个 token？

关键在于模型内置的 MTP 多 Token 投机解码命中。

而老款 3090 受到 PCIe 3.0 总线与内存读取延迟拖累，速度掉到了每秒 68 个 token。

## 客户端串联：对接 Claude Code 跑长工程库审查

能不能接开发工具？

能。直接接。FLYX 底层原生暴露了与 OpenAI 和 Anthropic 完全同构的端点规范。

在终端里两行配置就能桥接 Claude Code：

```bash
# 覆盖服务端地址为本地端点
export ANTHROPIC_BASE_URL=http://127.0.0.1:8080
# 传入占位符以通过客户端前置合法性检查
export ANTHROPIC_API_KEY=flyx-local-test-token
# 指定模型名称为本地加载的模型标识
export ANTHROPIC_MODEL=Qwen3.8-27B-UD-Q4_K_XL
# 启动审查
claude
```

实际接入需要注意什么？

本地引擎只做了基础的工具调用解析。如果工程里有复杂的动态嵌套参数，偶尔会吐出未闭合的 JSON。

读取几十个文件时表现稳定。但在并发读取超大单文件时，客户端可能会遭遇超时。真遇到超时怎么办？在终端里显式调大请求等待阈值即可。

## 真实测试中暴露的局限与待测项

测试跑通了，但坑在哪里？多着呢。

第一，硬件支持极度挑食。底层死锁在 CUDA 上，驱动必须大于等于 580。苹果芯片、AMD 显卡以及纯 CPU 链路全都不支持，Mac 用户暂时别想。

第二，预填充要等多久？显存外溢保住了进程，但搬运开销省不掉。在 256K 首次载入时，冷数据在内存中搬运造成了肉眼可见的卡顿：3090 上耗时约 47 秒，4090 上耗时约 39 秒。半分钟以上的静默，你能忍受吗？

第三，16GB 显卡得妥协。缩水。16GB 显存跑 27B 模型，必须降到 `UD-IQ3_XXS` 等超小量化。在复杂逻辑与生僻语法上存在精度折损，别拿它跑高精重构。

我现在只确认了一点：单张 3090 跑 262K 上下文确实没崩。

但这剩下的 0.62GB 显存，多并发长跑真能一直稳住吗？相关的长期压力测试我还在继续压测。
