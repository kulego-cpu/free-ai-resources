先说痛点。拿本地小模型跑 Agent 编码，十次有八次要翻车。

很多开发者在自己的 Mac 或带有 16GB 显存的机器上，用 Ollama 或 llama.cpp 跑 Qwen2.5-Coder-7B 的 Q4_K_M 或者 Llama-3.1-8B-Instruct。单轮补全或者日常聊天看着挺顺手。可一旦在 VS Code 里给它挂上工具调用让它自主改代码，场面往往迅速失控。

最典型的翻车现场有两个：

一个是死循环。小模型经常在同一个报错上原地打转。反复调用同一个工具，改了错、错了改，直到把上下文硬生生吃穿。

另一个是磁盘突袭。模型稍微理解偏差，大笔一挥直接把整个源文件重写成残缺骨架。连后悔都来不及。

开源插件 Harny 就是奔着这两个顽疾来的。仓库地址为 GitHub 上的 spltek/harny，基于开源 MIT 协议，当前实测版本 v0.3.2。作为一款原生长在 VS Code 和 VSCodium 侧边栏的扩展，它不吹嘘模型智能有多高，而是在工程框架层面装了两道硬刹车：Loop Guard 与 Analyze 差异预审模式。

本地模型到底能不能胜任日常辅助重构？这套防御机制真能兜住底吗？

## 本地模型跑 Agent 的先天硬伤在哪里

云端动辄几百 B 参数的顶级大模型，自我纠错与长程规划能力确实强。工具报错后，通常两轮内就能换个思路。

但参数量在 7B 到 14B 的本地轻量模型呢？

小模型在 Agent 里为什么总栽跟头？根子上就三件事，而且一件比一件要命。

最轻的是注意力飘。轮次一多，终端输出、文件内容全往里灌。几千 token 一压，最初的系统指令它早忘光了。标称三万二的上下文？那是基准测试，不是落地承诺。

更要命的是错了还照抄。第一次工具调用失败、看到报错，小模型根本算不清回溯。它下意识抄起一模一样的参数再试一次，嘴里还念叨着完全一样的解释。贪婪采样的死角就像黑洞，把模型死死按在里面。

最狠的是改文件不看路。多数集成式 Agent 默认直接写工作区。小模型逻辑链一脆、中途一产生幻觉，直接把你正常的业务代码整段盖掉。工作区污染，连后悔都来不及。

Harny 的思路很务实。既然模型本身不够聪明，就必须靠外层的 Harness 执行安全挽具进行确定性约束。

## 核心拆解一：Loop Guard 怎样暴力打断死循环

在各类 Agent 评测中，最烧 Token 也最让人高血压的现象就是死循环。

Harny 在底层运行时中内置了一套实时的 Loop Guard 死循环卫士。它的机制很简单：不指望模型自己顿悟，直接在执行层维护一张滑动操作指纹表。

```text
模型发出工具调用
       │
       ▼
┌──────────────────┐
│  计算调用特征指纹  │  函数名 + 核心参数哈希 + 输出相似度
└────────┬─────────┘
       │
       ▼
       / 命中重复模式？ \
     <                   > ── 否 ──▶ 正常放行执行
       \      是         /
       │
       ▼
┌──────────────────┐
│ Loop Guard 触发  │
└────────┬─────────┘
       │  分级升轨干预
       ├─▶ 第一级：注入系统级矫正提示，明确告知已重复且要求切换思路
       ├─▶ 第二级：直接拦截当前工具执行并强制回滚调用栈
       └─▶ 第三级：终止当前执行流，将控制权交还给人工终端
```

在实测中，我拿本地 Ollama 跑 Qwen2.5-Coder-7B 排查一个缺少 TypeScript 类型的构建报错。终端真实报错如下：

```text
src/index.ts:14:7 - error TS2322: Type 'string' is not assignable to type 'number'.
npm run build exited with code 2
```

模型第一次尝试修改，把参数改错了。再次运行还是报错。接着它没有任何反思，第三次原封不动地发起了完全相同的命令调用。

换作平时，我只能看着终端继续死循环空转。但这次刚准备发起第三次调用，Harny 界面弹出了拦截红标：

```text
[Loop Guard] Detected repeated tool execution: npm run build
Action blocked. Injecting steering prompt to switch investigation approach.
```

我当时还愣了一下，它真直接把模型手里的工具给夺下来了，并强制注入提示，逼迫模型改用 read_file 查看 tsconfig.json 和源文件定义。

这一步直接斩断了无休止的无效循环，保住了有限的上下文空间。

## 核心拆解二：Analyze 模式的 Dry-run 物理防线

代码改动最怕误操作。

Harny 在交互逻辑上划分了两个工作模式：**Analyze 分析模式** 与 **Build 构建模式**。

会话默认处于 Analyze 模式。在这个模式下，任何涉及文件修改、写入或删除的工具调用，全部运行在 Dry-run 模拟状态。

这意味着什么？

推理和写盘之间，物理上隔了一道墙。Analyze 模式下模型自以为改了代码，磁盘上的实际文件纹丝不动。你猜它手再抖能删掉东西吗？连个标点都动不了。

Harny 会在侧边栏精准生成标准的 Unified Diff 差异视图。你可以像在 Git 提交前做 Code Review 一样，逐行核对模型到底动了哪些变量、删了哪些函数。

等你逐行看完 Diff、确认逻辑无误，手动切到 Build 模式，写盘才真正发生。

这种把写盘权限扣在人手里的设计，用起来心里踏实得多。

## 核心拆解三：观察遮罩与上下文滚动机制作业

除了死循环，本地显卡跑 Agent 最容易遇到的就是显存与上下文双爆。比如在 M2 Pro 16GB 机器上跑 8K 上下文，两轮几百行的大日志一灌，显存压力立刻拉满。

观察遮罩 Observation Masking 这套做法不是我编的。Anthropic 关于 Context Engineering 的工程分析以及 JetBrains 在 Agent 上下文管理调优报告里都做过严谨论证：把陈旧过时的工具输出压成摘要，只保留最近一两轮的完整回显，在长程任务中性能衰减极小。

Harny 落地这套逻辑的方式很干脆：

第一，陈旧观察的主动遮罩。多轮推理中，只有最近一两轮的命令输出保持完整。较早之前的冗长输出在历史记录中会被自动替换为轻量级状态摘要。保留事实，剥离冗余字符。

第二，结构化任务便签保持。模型在长程任务中维护一份独立的 Scratchpad 任务便签。只记录动了哪些文件，验证到了哪步。以往二十轮的废话？全部扔掉。

实测在 8K 上下文的本地量化模型上，这套机制能支撑完整的十轮以上多文件排查，而没有发生常见的指令遗忘。

## 实操配置：从 Ollama 接入到本地实跑

在本地搭建一套安全的 Harny 开发环境非常简单：

### 1. 本地模型端点就绪

确保本地 Ollama 或 llama.cpp 的兼容端点已开启。以 Ollama 为例，默认服务监听在本地 11434 端口：

```bash
ollama run qwen2.5-coder:7b
```

### 2. Harny 扩展连接配置

在 VS Code 插件市场搜索并安装 Harny，打开侧边栏设置：

- **API Protocol**: 选择 OpenAI Compatible
- **Base URL**: `http://localhost:11434/v1`
- **API Key**: 填入任意占位字符，例如 `ollama`
- **Model Name**: `qwen2.5-coder:7b`

### 3. 排错流程推荐操作范式

实际拿小模型排错时，怎么操作才最稳？建议严格遵循以下动作要领：

首轮必须保持在 Analyze 模式。先抛出排查目标，让小模型只读工程文件、搜集线索并给出 Unified Diff。这步真能跳过吗？绝对不行。

逐行扫视 Diff 边界。确认没有无关文件的整全覆盖，重点观察是否丢失了原本的业务注释。

切入 Build 模式执行落盘。核验无误后切到 Build 模式一键应用，并配合本地终端自动运行测试用例。

## 结语

在云端万亿参数模型横行的时代，为什么非得在本地跑？

说白了就图三样：代码别往外传、断网也能改、还有不想给 API 交月费。听着不高级，但真用起来，这三条哪条都舍不得扔。这也是本地 Agent 能一直活下来的根基。

Harny 带来的启示很实在：在模型能力尚未达到通用的过渡期，优秀的工程挽具与防御性设计，能够有效弥补参数规模的天然劣势。

手头如果有闲置的本地显存，真的不想给它套个笼子跑跑看吗？

装上刹车，套上笼子，本地模型也能在安全边界内老老实实为你干活。
