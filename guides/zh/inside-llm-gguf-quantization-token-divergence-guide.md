## 一、 硬件环境与单二进制架构：怎么跑起来的？

先交代测试环境，不然数据没有锚点：
- 系统环境：Ubuntu 24.04 LTS，内核 6.8
- 显卡驱动：RTX 3060 12GB，驱动 550.54.14，CUDA 12.4
- 处理器内存：Ryzen 5 5600，32GB DDR4
- 构建版本：inside-llm v0.2.1，commit a9f4c21，基于 llama.cpp b3800

很多可视化分析工具刚上手时配置极繁琐。

要先配 Python 虚拟环境。再装 PyTorch 和一大堆编译依赖。中途碰上 CUDA 驱动版本不匹配，光配环境就能折腾大半天。

非得搞这么重吗？

inside-llm 的架构选择极具老派 C++ 工程师的务实作风。

底层引擎用 C++17 编写。直接静态链接 llama.cpp 与 ggml 库。

前端界面采用 Svelte 5 框架；三维概率地貌借助 three.js 渲染。编译时直接把整个 Web 静态资源打包嵌在单一二进制文件内部。

`chmod +x` 赋予权限之后直接在终端跑。控制台只吐出一行 `listening on :8642`，然后就没别的动静了。

打开浏览器敲 `http://localhost:8642`，界面瞬间渲染完成。

没有 pip install。没有 npm run dev。更没有配置 API Key 那套商业过场。这省了多少麻烦？

我第一次跑的时候还习惯性去翻 README 找环境变量，翻了半天发现真不需要。

```bash
# 下载可执行文件并赋予权限
chmod +x ./inside-llm

# 启动本地双模型透视引擎并监听 8642 端口
./inside-llm --port 8642
```

数据通信走轻量二进制帧。通过 WebSocket 在浏览器和底层 C++ 引擎之间高速传输。

官方预编译包直接提供了 Linux 与 Windows 两个版本。CUDA 与 Vulkan 都有现成文件。

即使办公机没配 CUDA 环境，只要显卡驱动正常，解压就能直接跑。

## 二、 双流并排比对：捕捉 Q2_K 与 Q8_0 分道扬镳的第一枪

进入 Web 界面后，核心玩法是选定 Model A 与 Model B。

这里有一个硬性物理约束：两套权重必须共享同一套 Tokenizer 词表。

我选了同一模型谱系下的两套权重做受控比对：
- Model A：`Qwen2.5-7B-Instruct-Q2_K.gguf`，文件体积 2.78 GiB
- Model B：`Qwen2.5-7B-Instruct-Q8_0.gguf`，文件体积 7.70 GiB

加载耗时方面，两套模型通过 mmap 映射进显存。Model A 耗时 1.2 秒完成载入；Model B 耗时 4.1 秒。

首字延迟 310 毫秒。双流锁定推演吞吐稳定在 28.4 tokens/s。

界面提供了两种运行模式：
- 锁定模式 Lockstep：两套模型强制阅读完全相同的前置 Prompt 上下文；并排比对当前候选词的概率分布。
- 自由模式 Free：每个模型按照各自采中的 Token 往下推演，直到两者输出文本彻底分叉。

以一段复杂的并发计数器逻辑推演为例。

前三十个字符，两者的生成完全咬合。

但到了第 31 号位置，分歧爆发了。

偏在哪儿了？

柱子一出来就明白了。

Q8_0 那边 eight 的柱子顶到 0.87，旁边几个候选全被压成地毯。

切到 Q2_K，eight 掉到 0.31，six 爬到 0.29。中间那堆原本该在 0.01 以下的垃圾词，全被抬到了 0.05 上下。

概率没丢。是被量化噪声摊平了。

摊平之后采样器稍有扰动，就挑中错误分支。

在 UI 的 Stream 文本流面板中，分歧处被标上了一道醒目的洋红色标记。

点开候选词面板，两侧呈现出镜像排列的柱状图。

右侧给出了香农熵 Entropy 与双向相对熵 KL 散度：我们把 Q8_0 视为参考基准分布 P，把极度压缩的 Q2_K 视为拟合分布 Q。

在第 31 号位置之前，KL 散度始终稳定在 0.04 附近。

而到了这一步，散度数值骤然跳跃至 1.82。

信息损失不再是抽象评语，而是精确锁定在时间线上的跳变坐标。

## 三、 采样器过滤阶段追踪：Top-k、Top-p 与 Min-p 到底砍掉了什么？

日常在 ollama 或 llama-server 里配采样参数，很多团队全凭玄学手感。

温度设 0.7 还是 0.8？

Top-p 设 0.9 到底有没有把有效创意给掐死？

最近很多开发者力推的 Min-p 阈值，比传统截断好在哪里？

平时调参就像在黑盒外面瞎猜。

inside-llm 把这套黑盒切开了一道透明天窗。

它的 Gates 门控面板完整复刻了 llama.cpp 底层的 Sampler 过滤流水线。

一个原始 Logits 向量吐出来，要依次通过惩罚项、Top-k、Top-p、Min-p、温度缩放以及 GBNF 语法约束。

在每个过滤阶段上方，系统直接用数字标出有多少个候选词活了下来。

```bash
# 启动时直接挂载特定模型对与自定义上下文窗口
./inside-llm \
  --model-a ./models/Qwen2.5-7B-Instruct-Q2_K.gguf \
  --model-b ./models/Qwen2.5-7B-Instruct-Q8_0.gguf \
  --ctx 4096
```

用鼠标点击某一个过滤阶段，面板立即切出该阶段截断前后的分布对比图。

实际观察大大出乎我的意料：

很多时候你以为 Top-p 0.9 很宽松？

但在高置信度语境下，首选词概率占了 92%，Top-p 在第一级就把剩下的几千个潜在选项一刀切光了。

而在平坦分布下，Top-p 又会放进来几十个语义模糊的边缘词。

反观 Min-p 设为 0.05 时，它的截断门槛会随着顶端词置信度动态联动：当顶端词置信度为 0.92 时，绝对截断阈值被自动抬高到 0.046，把 Q2_K 异常抬升的 0.01 到 0.03 的尾部噪音切得干干净净。

这种即时可视的截断反馈，胜过反复翻阅参数文档。

## 四、 Logit Lens 隐层投射：大模型在哪一层暗自做出了决定？

如果仅仅能看最终输出，它充其量算个精美的调试面板。

加挂 `--lens` 参数启动，它会激活底层基于 Logit Lens 的全层隐状态投射机制。

Qwen2.5-7B 架构包含 28 层 Transformer 块。

模型是在最后一层才突然悟出答案，还是在中间某一处就早已锁定了候选词？

启动 Logit Lens 之后，界面下方展开了一张二维层级投射图谱，也能切成三维立体概率地貌。

横轴是生成文本的时间步；纵轴是神经网络的物理层数。

测试一段算法复杂度证明题。

输入 Prompt 的瞬间，前 5 层的候选预测全是高熵噪声。

答案藏在哪一层？

到了第 14 层左右，关键算法名称的概率开始隐约凝聚。

到了第 21 层，即便后续还有 7 层网络未走完，正确答案的概率已经飙升到了 82% 以上；后续层数仅仅是在微调句式与语法连接词。

而在量化残损严重的 Q2_K 模型上，这种概率凝聚一直拖延到第 25 层才勉强成型；中途极易被微弱的注意力权重抖动带偏。

甚至你可以直接在时间线上点击任意一个历史分支的分叉点。

引擎借助内存中的上下文快照机制，能让光标瞬间穿越回分歧发生的前一秒，从另一个备选词重新分支推演。

这给排查偶发幻觉提供了极其顺手的实验台。

## 五、 真实部署时的技术边界与低配避坑

这套工具虽然好用，但实际测试时有几处必须注意的物理边界。

首先是显存容量的硬约束。

8G 显存的显卡别想着并排跑两个 7B。

我第一次没改参数直接启动，两套权重加起来破了 10GB，当场吃了个 `CUDA error: out of memory` 报错。调用栈停在 `ggml_cuda_compute_forward` 显存申请那一行。

卡里塞得下吗？

降到 `-ngl 18` 之后能跑了，但部分计算层被甩到了系统内存里，生成速度从 28 tok/s 直坠到 3.8 tok/s。一次完整的代码比对跑了我四十分钟。

面对这种龟速等待，日常排障谁受得了？

所以这东西在 8G 卡上不是不能跑，是没法用来做交互式排查。点一下要等半天。如果显卡只有 8G，建议拿两个 3B 模型并排做比对，体验会好得多。

其次是词表一致性红线。

两套模型必须来自同一模型谱系。不能拿着 Llama-3 去和 Qwen2.5 并排比对；两者的 Tokenizer 编码规则根本不同，Token ID 映射不上，强行比对数学散度没有任何意义。

最后是目前仅支持纯文本模态。

虽然多模态权重文件能够被载入，但浏览器界面上目前只针对文本生成分支进行概率捕获，图片理解与视觉注意力的投影目前暂未支持。

我现在挑量化版本会先拿它跑一遍。

同一个 prompt 灌进去，看两边从第几个 token 开始分叉。

分叉来得早的，说明这类题目对精度极度敏感，老老实实上 Q5_K_M 或 Q8_0；分叉拖到几百个 token 之后的，Q2_K 也能凑合，省下来的显存还能把上下文窗口拉大一倍。

当然这工具也不是万能的。词表不一致它直接罢工，多模态它现在也看不了。作者在 issue 里说视觉注意力投影还在做。

你手头的显卡扣掉桌面占用后还剩多少显存？先用 nvidia-smi 算清楚，别盲目拉权重。
