去年冬天我接手一套双机八卡的推理节点。

Grafana 看板很漂亮：显存吃满七成，GPU util 常年在 90% 上下徘徊。

当时我还挺得意。我觉得这八张卡被榨得一滴不剩。

直到前端那帮人开始在群里疯狂艾特我。

光标卡在第三行不动了。这是第一句反馈。

我第一反应是 WebSocket 断连，让他们抓 HAR 包回传。

结果长连接挂着好好的；网络丢包率也是零；只是首个 token 迟迟不落地。

有个哥们数过时间。从按下回车到屏幕跳出第一个字符，够他去茶水间泡一杯速溶。

难道机房丢包了？我查了两整天网络。

抓包、查网卡、测链路、换光模块……全是无用功。

直到第三天夜里，我才真正摸清楚问题到底卡死在哪。

## 压测看板的障眼法：均值 480 毫秒，p99 悄悄冲上两秒

为了测出机器极限，我用 Locust 写了一套压测。

压测没搞虚架子。

起 64 个异步协程；并发灌入 HumanEval 前置代码片段；输出上限锁死在 512 token；持续跑满十分钟取稳态。

启动参数里，我把每批次并发上限拉得极满：

```bash
# 启动 vLLM 并发满载配置
vllm serve Qwen/Qwen2.5-Coder-32B-Instruct \
  --tensor-parallel-size 4 \
  --max-num-seqs 128 \
  --max-model-len 16384 \
  --gpu-memory-utilization 0.92
```

数字看起来极诱人。

`max_num_seqs` 从 4 提到 128，集群吞吐直接从 320 tok/s 蹿升到 1280 tok/s。

整整四倍吞吐。这难道不算优化成功吗？

光看大屏监控，几乎挑不出任何毛病。

但我当时忽略了一点：大屏默认画的折线是平均首字延迟 TTFT。

均值显示 480ms，看着极稳当。

直到我拉出 Prometheus 里的百分位分位数，当场惊出一身冷汗：p90 到了 1.2 秒，p99 更是直接炸到了 1.95 秒。

翻开服务端的标准输出日志，屏幕上开始疯狂刷屏同一行黄色警告：

```text
WARNING [vllm.core.scheduler] Sequence group 1422 is preempted by PreemptionMode.RECOMPUTE.
```

警告密密麻麻。

四张 24GB 显存的 RTX 4090，单机总显存只有 96GB。

跑 32B 规格的 bfloat16 原生模型，仅静态权重就要切走 64GB 空间。

剩下分给 KV 缓存的显存满打满算只有 24GB；最多只能塞下八到九万个 token 的上下文。

当并发拉到 128 时，每个序列上下文只要超过六七百字，显存池就会当场告罄。

缓存池彻底空了。

vLLM 调度器为了防止 CUDA OOM 崩溃，只能强制触发重算抢占逻辑。

它把靠后序列的缓存直接抹掉；等前面跑完，再从头重算一遍预填充。

那些等两秒才吐字的前端同学，正是碰上了会话被当场踢出显存的倒霉时刻。

谁受得了这种顿挫？

那天晚上我把 `max_num_seqs` 灰度改回 24，压测重跑，p99 稳在 340ms。

群里没人再报卡顿了。

至于 128 并发下的调度阈值，我到现在也没调出一个既不踢缓存又保吞吐的平衡点。先记在这，回头换了硬件再测。

## 4090 没有金手指：PCIe 拓扑下的 All-Reduce 阻塞噩梦

在调整并行策略时，我还犯过另一个想当然的错误。

既然单卡算得慢，多卡并行分摊算力难道不应该更快吗？

很多文章张口闭口就是张量并行 TP 能把延迟压缩到极致，甚至引用几百吉字节带宽的 NVLink 互联作为佐证。

但在消费级显卡上，压根不存在这个前提。

从 Ada 架构开始，英伟达就把 40 系列游戏卡的物理 NVLink 接口全部切除了。

这代消费卡没有金手指。

在测试机上敲一行拓扑探测：

```bash
nvidia-smi topo -m
```

终端打印出来的矩阵清一色标着 SYS。

跨卡通信根本走不了高速直连；数据必须通过 CPU 根复合体、主板插槽与内存总线硬转。

双向理论带宽上限只有 64GB/s。

更要命的是在 Linux 原生驱动下，由于缺少硬件级 P2P 支持，卡间传输默认退回通过系统主内存中转。

当时我强行在单机四卡上把 TP 度数开到了 4。

结果压测出来的单字生成耗时 ITL，从原来的 22ms 倒退到了 58ms。

核心算力翻倍了，吐字为什么反而慢了一倍多？我百思不得其解。

用 Nsight Systems 抓了一段前向传播的内核执行轨迹，真相彻底露底。

在 Transformer 每一层计算结束后，四个 GPU 进程之间都必须执行一次 `all_reduce` 规约同步。

计算花了 1.2ms，但卡在 PCIe 总线等数据同步硬生生花了 3.8ms。

GPU 核心全在空转等待。全走廉价总线，怎么可能不堵死？

没有专用高速互联，在消费级硬件上搞高阶张量并行，就是拿廉价总线去硬碰密集的集合通信。

后来我把架构改成单节点两两分组跑 TP=2。两组之间走 HTTP 数据并行分流。单字生成耗时立刻压回到了 26ms。

手头摸着 4090 的人，别去硬套那些属于超算机柜的调优参数；老老实实算清插槽的物理带宽，比什么都强。

## 量化精度断崖：HumanEval 暴跌 28 个点的缩进车祸

显存吃紧，最先想到的解法自然是量化。

很多文章把量化描述成几乎无损的魔法：显存砍半，速度翻倍，评测只降零点几。

这种好话能全信吗？

放到严苛的代码工程场景，完全是另一回事。

我们在同一套测试环境下，对比了 Qwen2.5-Coder-32B 在三种不同量化格式下的 HumanEval pass@1 代码评测：

```text
HumanEval 50 题自动化代码生成基准 [commit: 4e7b8a1]
- FP16 原生基线：82.0%
- FP8 动态量化：80.4% [仅微跌 1.6%]
- 传统 INT4 格式：54.2% [断崖下跌 27.8%]
```

切到 FP8 这一档，无论是静态权重还是开 `--kv-cache-dtype fp8`，都极其稳健。

显存开销直接少了一半。

KV 缓存槽位多出一倍。

访存带宽缓解后，每秒吐字速度拉升了差不多八成。

但一旦迈过 FP8 走到普通 INT4 权重，代码逻辑会直接断崖式坠毁。

54.2% 的通过率，等于每两道题就要挂掉一道。

这 6G 显存省得到底值不值？

我把那 20 个挂掉的失败 case 逐个拉出 diff 排查。

整整 17 个失败用例死在深层缩进上。

Python 代码里但凡嵌套超过三层，INT4 版本的模型就会把四个空格打成六个。在多重 try-except 块里更是提前关闭作用域。

另外 3 个错误出在带引号的复杂 f-string 上。模型写着写着就开始陷入同一行代码的死循环复读。

这种代码丢进流水线，连 flake8 静态检查都通不过，更别说跑单元测试了。

省了 6GB 显存，换来的是整个工程助手的报废。

如果你的场景是离线处理海量内部文档摘要或者向量库重排，INT4 省下的算力成本确实划算。

但如果是给程序员当实时辅助，FP8 就是眼下能退守的最底线。

除非上游模型用 NVFP4 或者 MXFP4 这类带分块独立缩放因子的新型格式重新微调；否则在普通 INT4 上跑复杂长程代码，纯属自己给自己找别扭。

## Prefill 与 Decode 物理分离：为什么不能让长 Prompt 和高频吐字混跑

既然在单机上调参数总是按倒葫芦起了瓢，那工程界力推的 P/D 分离到底解决了什么？

它的物理内核其实非常直白：彻底将不同特性的计算阶段隔绝在物理机器之外。

预填充 Prefill 阶段吃的是矩阵乘法的计算密集度，考验的是算力核心 TFLOPS，数千字的上下文一次性灌入，把张量核心压得满满当当。

自回归解码 Decode 阶段吃的则是高频访存带宽，考验的是显存每秒能搬出多少数据，每吐一个新词，都要把庞大的权重矩阵与整条 KV 缓存重新读刷一遍。

把这两拨任务塞进同一套显卡混跑，就是前台光标卡顿的罪魁祸首。

你正顺畅地以每秒 50 个 token 写着函数体，后台突然甩进来一个包含两万行 Swagger 文档的长 Prompt 请求。

调度器必须立刻让出流处理器去算那两万字的注意力投影。

正在吐字的解码序列被瞬间挂起。

在人类工程师的屏幕上，这就表现为光标莫名其妙地僵直了一秒半。

光标定在那里，谁受得了？

P/D 分离则是直接架设两组异构节点：

```text
客户端请求
    │
    ▼
[API 负载网关]
    │
    ├─► [Prefill 专职集群]：堆叠密集浮点算力卡，快速吞掉长上下文矩阵乘法
    │         │
    │         ▼ [通过 RDMA / 内部高速私网传输 KV Cache 状态]
    └─► [Decode 专职集群]：挂载 H100 等拥有 3.35TB/s 高带宽内存实例，专注高频吐字
```

当预填充算完之后，通过高速内网把 KV 缓存数据包直传给解码集群接力，解码集群从头到尾只负责稳定吐字。

在典型的智能体多步调用场景下，这种物理拆分能直接把 p99 的交互抖动抹掉六成以上。

不过代价也很实在：你需要额外维护一套跨机 KV 传输的中间件网络，而且机器总配额起码要多预留两成来兜底流量潮汐。

大厂的这套架构好使，但它属于重度流量业务。

手头只有两三台机器的小团队，别轻易去踩分布式 KV 传输的网络暗坑；老老实实用 chunked prefill 分块预填充压制突发延迟，更稳当。

## 投机采样的真实折损：代码场景的接受率与温度衰减

最后说一条真正能把推理效率天花板往外推的技术：投机采样。

很多人在开放式对话场景测过投机采样，最后都失望地关掉了它。

因为用户的问题千奇百怪，小模型去猜大模型的输出，接受率经常卡在 30% 左右。

每猜错一次，主力模型就要重新前向核对并回滚指针，不仅不省时间，反倒白白浪费了显存与计算周期。

这难道不是吃力不讨好吗？

但在严格受控的代码补全场景下，数据的规律性完全变了。

代码有固定模板：类的声明、标准库引入、括号闭合与常见缩进。

我们实测用一个同源轻量的 Qwen2.5-Coder-0.5B 作为草稿头，去辅助 32B 主力模型推演：

词表必须做到严格的物理级对齐。分词逻辑若有半点差池，草稿预测就会全盘报废。

在采样温度锁死在 0.2 的极低随机性设置下，代码生成的平均接受长度可以达到 3.8 到 4.1 个 token。

主力模型原本要跑四次串行前向传播，现在只需要在验证阶段做一次批处理计算，就能把这四个字符一次性通过。

省去的那三次全局显存数据搬运，就是实打实挤出来的硬件冗余。

但别高兴得太早。

投机采样在代码场景里有一根极度敏感的温度衰减曲线。

温度在 0.2 时，接受率维持在七成上下；整体交互提速接近两倍——

一旦用户把温度拉到 0.7 试图让模型发挥创造力，接受长度会当场断崖式暴跌到 1.6 个 token。

更麻烦的是显存的二次放大。

在核验阶段，大模型需要并行处理草稿模型吐出来的 K 个候选分支，这会在极短时间内把验证批处理尺寸膨胀 K 倍。

显存里原本就吃紧的临时缓存池，在这一瞬间极易被推到崩溃边缘。

如果底层 KV 缓存池已经处于 90% 警戒线，开启投机采样不仅不会提速，还会直接诱发更早的抢占重算甚至 OOM 闪退。

把草稿头关掉，是不是反而更划算？

这套双机八卡的集群我现在还挂着两个节点在跑——

`max_num_seqs` 定在 24；我开了 FP8 权重量化；动态 FP8 KV 缓存也开着；投机采样先关了。因为新业务的采样温度被前端设成了 0.75。开着也是白白浪费显存。

什么时候能有一套动态调度的代理？我还没想好。
