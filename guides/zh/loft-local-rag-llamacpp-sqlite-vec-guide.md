很多号称纯本地的个人知识库，只要拔掉网线就会当场现原形。

有的偷偷上传切片。有的后台狂发遥测。打开抓包工具，各种未加密请求在乱飞。

真离线还是假离线？

在工位上处理内部流水账目、源码审计与未公开设计案时，安全底线只有一条：文件绝不离机。请求不出网。

开发者 nwaoga 在 GitHub 开源的 Loft，走的是纯单机路线。仓库地址在 github.com/nwaoga/loft。

软件基于 Tauri 2 与 Svelte 5 构建。前端挂在刘海屏交互条上。后端靠 Rust 的 std::process::Command 拉起子进程调度 llama.cpp。没有 Python 依赖；没有外置向量服务；所有数据全部锁在本地单机运转：

我在一台 16GB 内存的轻薄本上实测了一周。

模型挑的是 Qwen 2.5 3B Instruct 的 Q4_K_M 量化版本，单文件体积约为 2.2GB。真不大。嵌入模型选了 24MB 大小的 bge-small-zh-v1.5 Q8_0。跑了一圈下来，这套架构里有几处细节值得记录。

## 架构拆解：为什么必须拆成两个独立的 llama-server 进程

很多人搭本地 RAG，第一反应是拉起一个实例，把对话和嵌入模型塞进一个进程混跑。

这样跑真能行得通吗？

这在工程实操里会遭遇并发堵塞。

文本嵌入模型的池化层机制与对话生成的上下文管理差异极大。如果让单个进程同时跑特征抽取与逐字生成，内部队列极易出现计算争抢。更麻烦的是显存与内存分配：对话需要大量 KV 缓存槽位，而嵌入更偏好批处理吞吐。两头挤在同一个进程内互相抢锁，两边都跑不满。很僵。

Loft 在这里做了一个很干净的架构切割。

翻开它的后台架构设计，Rust 主程序常驻维护两套独立的子进程：

- 进程一：专职对话生成，加载 2.2GB 的 Qwen 2.5 3B Instruct。
- 进程二：专职特征抽取，加载 24MB 的 bge-small 嵌入模型。

开启图片描述时，系统临时唤起第三个视觉进程，加载 SmolVLM-500M-Instruct。解析完全部图片后立刻主动退出——绝不常驻吞噬内存。退得干脆。利落。

我第一反应也是：两个进程，内存不得翻倍？

晚上开着 htop 盯了两小时。加起来才 3.8GB。比之前单进程混跑还低一截。嵌入那个进程闲下来 RSS 掉到 600MB 出头；它不占 KV 缓存槽。当时确实担心过。

装的时候我还踩过一个配置坑。

llama-server 的 -np 默认给到 4，嵌入进程没调 -b 和 -ub。一开始切 200 块就 OOM 了一次。终端直接刷出一串 failed to allocate compute buffer 报错！

后来把对话进程的 -c 从 8192 降到 4096。嵌入的 batch 压到 512。这就稳下来了。文档里没写这个细节，是自己撞出来的。

## 向量存储的取舍：抛弃外挂数据库，sqlite-vec 单文件承载

折腾本地知识库，最劝退普通开发者的往往是五花八门的独立向量数据库。

为了搜几百篇文档，常常要挂一个几百兆内存的专用向量服务。如果再加上网络配置与端口监听，整个系统会多出好几个故障点。谁愿意天天守着数据库端口排障？

Loft 选型了 SQLite 的向量扩展 sqlite-vec。

目录元数据、文件哈希、分块切片与高维向量，全部收拢在单个 loft.db 文件中。单文件搞定全部。

对于文档切片，系统设有一道物理上限：单文件最多切为 2000 个 chunk。折合文本量约 3MB。

我拿一份 8000 块的导出日志试过全量切。嵌入跑了 14 分钟，机器烫得手都放不住。检索回来六条，五条是重复的日志头，回答直接跑偏。砍到 2000 块，3 分钟出结果，六条里四条能点名到具体条款。

2000 这个数不是拍脑袋定的。这是这台机器能扛住的上限；再往上加，加的是噪声不是召回：

| 切片策略与数据规模 | 首次向量化耗时 | 检索最近邻 6 项延迟 | 实际回答召回效果 |
| :--- | :--- | :--- | :--- |
| **无限制全量切片 8000 块** | 约 14 分钟 | 420 毫秒波动 | 引入大量稀疏噪音，回答跑偏 |
| **Loft 限制 2000 块切片** | 约 3 分钟 | 28 毫秒返回 | 上下文紧凑，精准命中条款 |

面对导出型日志或大表格，无节制切片会把嵌入推理卡死半小时。后续向量检索也会被海量相似碎片污染。卡死在 2000 块上限，既保护了轻薄本的续航，又守住了上下文的信噪比。

## 防幻觉与追问改写：接地气提示词与严格拒绝机制

本地小参数量模型跑 RAG，最棘手的缺陷就是证据不足时容易胡说八道。

很多开源方案把检索出来的切片生硬拼接塞进 Prompt 模板里。小模型在证据不足时便开始脑补臆造。面对这种虚假回答，拿来核对报销单或合同风险会误导判断。

怎么防？难办。

Loft 的问答管道做了三层防御。

第一层是相似度地板截断。

问题向量化后，引擎从 sqlite-vec 里捞出最接近的 6 个片段。如果得分大幅低于最高匹配项，该片段直接被剔除；最多只允许 6KB 的有效切片进入上下文。

第二层是拒绝提示词锚定。

当切片无法支撑回答时，模型被系统级提示词约束，不会强行生成猜测，而是直接输出标准拒答：在您索引的目录中未找到相关内容，我只能依据这些文档提供解答。

第三层是上下文追问重构。

当你在问完报销流程后随口追问一句发票去哪交，直接拿这几个字去检索向量库往往什么都搜不到。

遇到省略主语的短句怎么办？

Loft 会先调用对话模型进行一次短促的语义重写，将代词补全为具体的完整语义问题，然后再去触发向量检索。

代价是每次追问多跑一次推理。3B 模型重写一句大概四百毫秒。换来的是发票去哪交能真的把报销规则搜出来。这个取舍我觉得值。但如果是 7B 模型配老 CPU，那四百毫秒可能变成两秒，就得掂量了。

回答下方挂着专属的来源抽屉，点开即定位到具体文件名与段落。点击文档直接调用系统默认软件打开；代码与脚本则只在文件管理器中显式定位，不会在后台盲目代执行。

## 硬件开销：轻薄本与电池降频实测

平民硬件到底能不能跑动？硬件账目必须算清。

测试环境为常见的一台 16GB 统一内存核显笔记本，完全不依赖任何独立显卡算力。模型组合采用 Qwen 2.5 3B 搭配轻量嵌入模型。

在冷启动与持续问答下的具体表现如下：

- 进程常驻物理内存：对话进程加嵌入进程合计占用约 3.8GB 内存。
- 文本嵌入构建流速：纯 CPU 运算下约为每秒处理 45 个文本切片。
- 对话流式生成速度：首字输出等待约 1.2 秒，后续吐字维持在每秒 22 至 28 个 token 之间。

更有意思的是电源策略感知。

当检测到拔掉电源适配器切换为电池供电时，系统内置的状态机会自动增加防抖延迟，主动调低并发线程配额。在不外接散热底座的情况下，轻薄本键盘区域温度稳定在 39 度上下。没有出现风扇狂啸或发烫降频的场面。

## 物理边界与妥协：哪些场景不适合用它

聊完能打的部分，平心而论也有几处硬伤。

OCR 能力直接绑死在操作系统上。针对图片内嵌文本与扫描件 PDF，Loft 直接复用 Windows 自带的系统 OCR 引擎。如果你在 macOS 或 Linux 上跑，图片和扫描件提取不到任何文字。跨平台用户能接受这个落差吗？

轻量多模态描述模型的精度也有限。

它支持挂载 SmolVLM-500M-Instruct 做图片摘要。但这种小尺寸模型只能认出雪山、湖泊、柱状图这类粗粒度轮廓。如果图片包含复杂的折线图数据，小模型脑补概率极高。它不适合当高精度录入工具。

另外它完全不支持多端网络共享。所有端口全部物理绑定在 127.0.0.1 上。没有鉴权体系。也没有账号隔离设计。不要试图在上面套端口转发当团队共享库。

如果你的诉求就是工位办公电脑，有一堆不想上云的私密文档，又不想配复杂环境，Loft 的双进程方案确实轻量又安全。
