# 22MB 视觉模型单次跑完检测与 OCR：Mirage 怎么做到的

在边缘设备或者轻量云主机上跑多模态模型，显存与带宽总是捉襟见肘。

主流模型单卡跑下来基本要占 8GB 显存。随便丢一张 1080P 界面截图，Patch 分词切片就吃掉两千多个视觉 token。自回归解码器每前进一步都在硬算全注意力矩阵，风扇满速尖叫，光标定格好几秒。终端卡在那儿。排查下来，手头这套流水线其实只要拿两个坐标框，外加一行门牌号字符串。

为此在后台常驻一个十几 GB 的重型大模型，服务器账单根本吃不消。设备电池电量也掉得飞快。

在没有独立显卡的边缘节点上，我们真正想要的是把权重文件压缩到几十兆以内，只把实体定位、OCR 文本抓取与空间几何关系剥离出来。但这在传统自回归架构下行得通吗？

过去很长一段时间，答案基本是否定的。

开源社区最近出现了一个有趣的极端架构。Cactus Compute 团队释出了一款名为 Mirage 的端侧多模态模型，在 Apache 2.0 协议下开放了完整权重。

项目讨论与社区一手反馈发布在开源技术阵地：
https://www.reddit.com/r/LocalLLaMA/comments/1xpm8mw/

整个模型打包后仅有 22MB 权重体积。总参数量控制在 51.3M 上下。更关键的是，它在单次前向推理中同步输出场景描述、目标检测框、文本识别、语义分割掩码以及物体空间拓扑关系。

这么小的模型，究竟是怎么把这么多视觉任务塞进去的？真有这么轻？

我心里直犯嘀咕。

## 硬件账目与 51.3M 参数分工

传统多模态模型之所以庞大，是因为大家总试图让通用解码器包揽一切。

解码器既要负责看图写散文，又要硬生生在连续文本流里吐出一串串浮点数坐标。这种做法把小模型宝贵的容量，全浪费在了低效率的坐标字符生成上。

Mirage 的解题思路彻底变了。它没有给解码器堆砌过多的自注意力层，而是将 51.3M 整体参数做了严格切分：

- 图像编码器。参数量约 7.8M，采用 HConvGLU 模块，使用固定的阿达玛变换混合通道特征，辅以少量轻量卷积核；
- 语言解码器。参数量约 40.8M，采用 Simple Attention 与阿达玛感知机紧凑结构，核心衍生自 Needle 与 Whistle 序列架构；
- 专用输出头。参数量约 2.6M，由轻量文字读取头与空间几何定位头构成。

仔细算这笔账。

空间坐标与分割掩码根本不交由文本解码器去逐字猜算。并行的 2.6M 专用结构头直接输出结果。语言解码器只负责给出实体的语义标签、基础属性与空间因果关系。

文字识别也是同样的处理机制。模型内置了专用的文本扫描通路，提取字符后再做语义对齐。

这种分流让 40.8M 的语言解码器得以轻装上阵。

在输出场景描述时，它支持英语、德语、法语、西班牙语、意大利语、荷兰语与波兰语七种语言。文本简短利落。没有多余废话。

## 端侧 74 毫秒与无显卡 CPU 实测落差

谈论极小模型的性能，必须把运行平台和硬件环境放在明处。

原作者给出的高光数据，基于三星 Galaxy S26 手机平台：

- 挂载板载神经网络处理单元 NPU 运行时，单次全任务推理耗时约 74 毫秒；
- 切换至手机中央处理器 CPU 运行时，单次推理耗时约 107 毫秒。

百毫秒以内的响应速度，在手机本地做相册分类或者辅助对焦确实足够轻快。

但是，普通工程师在机房无显卡云主机、或者办公室老旧电脑上跑，情况真的会这么美好吗？难道真的没有性能妥协？

社区开发者 MagoViejo 把这套权重拉到了一台没有硬件加速单元的普通 x86 个人电脑上测试。在纯粹依靠双核 CPU 进行浮点计算的工况下，单张图片的完整解析耗时直接拉长到了 5.8 秒。

从手机端 74 毫秒直接跳水到 PC 端 5.8 秒，耗时翻了近八十倍。原因全在计算单元上：Galaxy S26 依赖专用 NPU 处理定点张量，而老款 x86 主机纯靠双核 CPU 跑全量浮点矩阵运算，缺少硬件向量指令加速，算力瓶颈立刻暴露无遗。

面对这组数字，大家心里就该有一杆秤了。硬件很诚实。

如果你的设备自带现代 NPU 芯片，这几十毫秒的延迟具有实用价值。

但如果你打算把它部署在廉价的单核虚拟主机上做视频流实时监控，每秒处理零点二帧的吞吐，会让实时分析当场脱节。面对接近六秒的漫长等待，谁能把它挂到实时视频流里？哪家业务能忍受这种卡顿？

我拿手里一台闲置的低配 Linux 主机试跑了一下。风扇呼呼吹。

把它拿来做后台离线相册聚类、冷启动预处理、或者给无独立显卡的轻量 Agent 充当低开销眼睛，才是贴合现实的工程定位。离线跑批处理，它能省下一大笔服务器开销。

## 社区争议与真实排坑记录

任何开源项目在真实工程落地前，都要经过社区放大镜般的挑刺。

Mirage 发布后，讨论区产生了两个明显的争议点。

第一个争议来自社区风控工具。账号 stylome-ai-detection 在发布帖下方打上了疑似由 AI 辅助生成的警示标记。虽然作者很快现身交流具体的技术细节，但文本层面的宣传辞令，确实给一部分严谨的开发者留下了疑虑。

这到底是真干货还是营销包装？

第二个争议来自与传统目标检测算法 YOLO 的对比。

纯粹论目标定位的吞吐帧率，在工控机 CPU 上精简版的 YOLO nano 依旧遥遥领先。Mirage 的真正差异化不在于拼绝对帧率，而在于它在 22MB 的极限体积内，一并带上了文字提取与跨实体空间语义拓扑。

想要验证这套流程，安装并不复杂。在 Python 3.10 以上环境下，直接拉取官方发布的软件包：

```bash
pip install cactus-compute
```

通过 Python 接口调用内置的推理流水线：

```python
import cactus_compute

pipeline = cactus_compute.MiragePipeline.from_pretrained("cactus-compute/mirage-v1")
outputs = pipeline.analyze_image("test_sample.jpg")

print("Detected Boxes:", outputs.boxes)
print("OCR Text:", outputs.text_segments)
print("Spatial Topology:", outputs.relationships)
```

我在纯净的 Ubuntu 22.04 容器里第一次跑这段测试代码，终端当场弹出了报错：ImportError: libGL.so.1: cannot open shared object file: No such file or directory。

代码当场崩了。

我查了环境日志。原来是底层依赖了图形渲染库。在容器中必须先执行 apt-get update && apt-get install -y libgl1 补全环境，模型才顺利跑通。

补齐依赖即可。

踩过这个小坑之后，推理过程就顺畅了。

## 技术边界与工程师选型考量

经过这轮拆解，我对 Mirage 这类 22MB 极小多任务模型的选型结论就非常收敛了。

它适用的工况很清晰：
- 移动端与可穿戴设备。设备自带低功耗 NPU，离线解析招牌文字与物体轮廓；
- 边缘 Agent 算力削峰。给树莓派配本地前置过滤，先过滤掉无意义画面，异常帧再传云端；
- 私密相册离线索引。不想把私人照片传上云端，后台每张图慢慢跑搜索标签。

不适用的工况同样刺眼：
- 工业级高帧率质检。要求每秒几十帧连续视频流检测缺陷，请退回 YOLO 或专属轻量检测头；
- 开放域深度图文理解。需要模型看懂复杂图表逻辑、艺术画作隐喻或者几十页财报长图，请老老实实调用云端大模型接口。

把结构放进任务本身，用专用空间头分担语言解码器的负担，这种架构思路确实巧妙。

但二十多兆的体积摆在这里，不必期待它成为无所不能的全知视觉大脑。把它当成一把体积轻巧、功能专一的端侧瑞士军刀，你的生产环境才不至于在并发涌入时手忙脚乱。

真要想在端侧把这套方案跑顺，你准备好给无显卡主机预留六秒的处理等待了吗？还是说，你的设备本就自带一块高算力 NPU 呢？
