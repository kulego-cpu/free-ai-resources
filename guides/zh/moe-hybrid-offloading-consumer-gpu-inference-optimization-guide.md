## 搬运权重的物理死穴

MoE 混合卸载为什么会奇慢无比？先算物理账。

MoE 每吐一个 token，路由器都要挑选少数几位专家。在云端万卡集群里，专家全在显存，寻址极快。但在普通主板上呢？PCIe 通道非常拥挤。

选中的专家不在显存，就必须穿过 PCIe 从内存现搬。算一笔细账：

- 单个专家权重在量化后大约 150MB 到 300MB
- 单个 token 往往激活 4 到 8 个专家
- 全命中冷门专家，每一步就要在总线上搬运 1.2GB 数据
- 常见的 PCIe 3.0 x16 实际传输带宽每秒仅有 12GB 到 14GB

这意味着什么？

光是搬运数据，理论速度就被焊死在每秒十来个 token。若多张显卡还要争抢内存通道，延迟更是成倍上升。

## 真正见效的四项底层改造

翻看 97 组对照，实打实带来跨级飞跃的改造只有四项。

### 1. 废除系统分页，用 Pinned RAM 锁定物理内存执行 DMA

普通程序给显卡传数据，走的是虚拟内存。驱动想拿数据，先得把数据拷贝到锁定的中转区，再发给 GPU。这一步内存倒手，直接吃掉了双通道的大半带宽。

排错手段非常干脆。初始化时调用底层锁页接口，强制把内存中的专家权重钉在物理内存上，严禁系统换出。

效果如何？

在 DeepSeek V4.1 Flash 混合卸载测试里，结合分块跳层，32K 提示词预填充速度从每秒 430 个 token 暴增至 2,199 个。五倍提速，全靠省掉 CPU 内存倒手损耗。

### 2. 扔掉层级切分，改用全节点张量并行

按层切卡是很多人的第一直觉。卡 1 负责前十层，卡 2 负责后十层。真跑起来会怎样？流水线灾难。

前一层的专家还在等内存搬运，后一层的显卡只能干等。卡与卡节奏不合，流水线停顿时间高达 40% 以上。

团队推翻了流水线分层，全面改用张量并行。每张显卡同时持有所有专家权重的四分之一，同步触发 DMA 搬运与矩阵计算，最后规约汇总。

4 卡配置下，生成速度从每秒 48.3 个稳稳涨到了每秒 67 个。四张卡功耗曲线完全重合，再无卡顿等待。

### 3. 冷专家由 CPU 就地计算，热专家留给 GPU

既然把冷专家搬进显存要耗费带宽，为什么不让多核心 CPU 在本地内存里算完？

在混元 Hy4 Flash 的双卡压测中，团队改写了调度逻辑：

```text
               ┌───────────────────────────────┐
               │    Router 路由判定 Token       │
               └───────┬───────────────┬───────┘
                       │               │
            [命中显存驻留热专家]    [命中内存冷专家]
                       │               │
                       ▼               ▼
               ┌───────────────┐┌───────────────┐
               │ GPU 显存核心   ││ CPU 多线程核心 │
               │ 并行矩阵计算   ││ 本地内存计算  │
               └───────┬───────┘└───────┬───────┘
                       │               │
                       ▼               ▼
               ┌───────────────────────────────┐
               │     隐层特征汇合 Barrier       │
               └───────────────────────────────┘
```

一个 token 选中的 8 个专家若有 6 个在显存、2 个在内存，调度器不再搬运权重。显存里的 6 个交给 GPU 跑，内存里的 2 个分给 CPU 多线程就地推演。计算完成，总线上只传极轻量的中间结果。

短代码续写场景下，混元的生成速度从每秒 24.6 个 token 飙升至每秒 70.4 个。

### 4. 单图编译：把千次核函数压进单个 CUDA Graph

当模型已经能塞进单张 24GB 显卡时，瓶颈就变成了核函数发射排队开销。

以针对单卡适配的 Inkling 2 Mini 为例，24 层 MoE 拥有 3,072 个专家。在原始运行时里，每一步生成要在驱动层往返发射 1,404 次。单次核函数只需微秒级，发射排队却把吐字拖死在每秒 57 个。

解法很明确。在自编译引擎源码中把专家计算与残差合并编译进单个 CUDA Graph，发射次数直接砍到 781 次。

量化精度没动分毫，吐字速度从每秒 57 个蹦到 112 个，直接翻倍。

## 那些被吹上天的优化玄学

失败清单比跑分表有用得多。备忘录里记录了大量毫无收益甚至负优化的做法。

### 1. 静态专家热度文件能直接跨场景套用吗？

很多工具宣称：挂上参数 `--expert-profile` 跑一遍通用测试集，提取专家热度排行榜，把前 20% 的热门专家锁在显存，就能命中八成计算。

真的吗？

实测数据很残酷。针对单个提问统计出的热专家，在原问题里命中率确实高达 90%。换到同领域的另一个提问，命中率立刻跌至 64%。更讽刺的是，完全不分析、随机乱放专家，命中率也有 61%。

模型路由具有极强的上下文依赖。没有全局倾斜特征时，所谓的静态字典和抛硬币毫无二致。

### 2. 自制小模型做投机解码稳赚不赔吗？

用小模型在前飞速猜词，大模型在后批量验证，逻辑很严密。很多团队花几天时间微调了一个小 Drafter，结果如何？

在 3 款开源模型的实测中，自制小模型带来的提速基本为零。

草稿模型的接收率门槛太高。小模型与主模型稍有偏差，就会触发大量拒绝重算，回滚开销彻底吃掉了批量验证的红利。

### 3. 微基准跑赢的参数长文本同样管用吗？

很多开发者习惯用 128 个 token 的短序列调参数。某项注意力缓存微调在短文本压测里展现出 27% 的提升，但一进 8K 长文本排错会话，立刻在第四轮触发数值溢出，实际有效吞吐反而倒退 2%。短测试集的结论，往往经不起真实长文本的敲打。

## 照着抄作业的排障建议

手头有消费级显卡想跑大尺寸 MoE，该从哪下手？

先别急着改配置。在终端执行这几条命令，找准瓶颈到底在哪：

```bash
# 监控显卡吞吐与 PCIe 实时带宽占用
nvidia-smi dmon -s et -d 1
# 检查主板物理插槽实际协商速率是否跑满 16x
sudo lspci -vv -s $(lspci | grep -i nvidia | head -n 1 | awk '{print $1}') | grep LnkSta:
# 查看 CPU 内存节点分布与 NUMA 跨节点争用
numactl --hardware
# 开启大页内存支持并预留静态物理大页
sudo sysctl -w vm.nr_hugepages=1024
```

第一步，盯紧总线。PCIe 占用常年打满 90% 以上，瓶颈就在数据搬运，别盲目折腾算子。先排查内存是否开启大页支持，权重是否通过 Pinned 机制锁定在物理内存。

第二步，看路由特征。模型路由若极其分散，不要手工标定热专家。老老实实配张量并行，或者把冷专家分给 CPU 多线程在本地消化。

第三步，给测试集加码。用真实开发中几万字的长日志、多轮报错去检验每一次改动。
