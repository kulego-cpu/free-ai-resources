# Qwen 4.0 与 5.0 都会继续开源：官方在云栖大会正式定心辟谣

上周五下午，机房临时拉了个排障同步会。

起因是技术群里的一张截图。帖子里传言 Qwen4 可能是最后一代开源权重，后续团队将全面转入闭源商业服务。

没有原始链接。全是聊天截图。真假难辨。

但我们还是得按最坏情况做推演。机房里三台双卡 4090 节点一旦停摆，几百个内部任务全部面临瘫痪。

机房里有三台双卡 RTX 4090 节点，还有两台 64GB 统一内存的 Mac Studio 主机。业务代码跑的是 Qwen2.5 72B 衍生微调版。语义检索、知识库问答、单测流水线全压在上面。

一旦上游断更，首当其冲要重写的是底层推理调度系统，改个模型名字根本不管用。

当时我们甚至把备选的 Llama 3.3 70B 量化分支拉到了本地。我们原本准备通宵做长上下文代码召回测试。

今天上午，云栖大会主论坛现场传出演讲实况。

通义千问团队在主论坛演示幻灯片中打出明确承诺：未来 Qwen 4.0 与 Qwen 5.0 将继续保持开源开放。

备用迁移方案可以先降级。但我们的硬件实测才刚刚开始。

---

## 1. 为什么我们此前必须做双卡节点压测预案

一线运维排障最怕什么？最怕依赖的核心上游大模型供应链在毫无预警的情况下突然闭源甚至停更权重文件。太被动了。手足无措。

软件工程向来极度依赖底层开源库，而本地自托管大模型更是将整条业务线的生命力全部系于上游开放权重的持续交付。

回顾大模型行业近几年的剧烈动荡，早期打着开源普惠旗号聚拢生态的技术机构在商业化成熟后几乎无一例外地关门封锁核心权重。这是明摆着的事实。必须防患于未然。有些大厂甚至把核心旗舰架构转为仅限云端的计费接口。这类先例并不罕见。

把私有业务跑在本地的团队，谁也不可能仅凭外界几句口头讨论就高枕无忧。

上周我们在双卡 4090 宿主机上反复实测 Qwen2.5 72B 的 AWQ 4-bit 量化版本。排障工作量极大。

启动命令如下：

```bash
python3 -m vllm.entrypoints.openai.api_server \
  --model Qwen/Qwen2.5-72B-Instruct-AWQ \
  --quantization awq \
  --tensor-parallel-size 2 \
  --max-model-len 32768 \
  --gpu-memory-utilization 0.95
```

两张 24GB 显存卡合并提供 48GB 物理寻址空间，但光是静态 AWQ 权重加载进显存就会直接吞噬掉整整 38.2GB 的宝贵容量。仅剩 9.8GB 留给动态 KV 缓存。极度吃紧。

当并发会话从单条逐步推高到八条长文本时，GPU 显存使用率一路飙升直至临界阈值，终端输出的显存分配日志几乎瞬间被红色警告填满。整整 46.8GB 显存被死死吃满。警报大作。毫无冗余。

此时 p99 解码延迟从单会话的 24 毫秒跳到了 176 毫秒。GPU 之间的 PCIe 4.0 总线通信开始出现排队现象。

如果 Qwen4 不再开源，转去公有云调用商业接口，每月 token 账单增加还在其次。内部代码提交记录直接跨网送去公有云，在安全合规审计环节根本通不过。

因此，开源承诺对本地团队而言是纯粹的生产线可用性问题。

## 2. 官方披露的生态数据与待核验清单

大会现场同步给出了几组官方口径的生态统计：

- 全球累计模型下载总量突破 30 亿次。
- 官方自主研发开源模型超过 460 款。
- 社区衍生适配模型总数突破 30 万个。

数据规模确实庞大。但对一线干活的工程师而言，数字梯队先不急着叫好。

我们只盯着三项实打实的技术验证：

第一，7B 与 14B 尺寸在 24GB 单卡上完成 AWQ 量化后，能不能留下足够显存给 32K 上下文？

第二，32B 尺寸做双卡张量并行切分时，跨 PCIe 4.0 总线到底损失多少解码吞吐？

第三，72B 尺寸在多会话高并发注入下，会不会再次撞上长上下文显存溢出？

官方口头承诺了开源。接下来就看 HuggingFace 组织主页和 GitHub 仓库何时上架实际的权重目录和 license 文件。

## 3. 社区讨论降温：自托管收益与未决疑问

现场幻灯片传出后，海外论坛与本地算力群里的情绪迅速分化。

部分自托管开发者松了一口气。自托管的核心价值在于物理掌控。

权重文件完完整整地存放在本地机房的高速 NVMe 固态硬盘阵列里，所有推理交互数据完全被锁在本地内网交换机内部。毫无泄露风险。不花一分钱 API 账单。运维人员也不用担心服务商深夜调整敏感词拦截规则。

但技术社区里冷静的工程师很快追问了更深层的细节：

第一，尺寸是否做人工切分？开源的是全量旗舰大模型，还是只放蒸馏后的小尺寸？

如果数千亿甚至上万亿参数规模的旗舰级 MoE 混合专家模型最终被悄悄封锁在公有云网页端专供商业付费客户，那所谓全量开源的真实成色就不得不大打折扣。这是最关键的试金石。绝不能含糊。

第二，发布时间是否存在时间差？商业 API 正式上线和开源权重上传之间，到底会留出多长的商业保护窗口？

这些问题现在没有任何官方文档给出最终答案。光听一场演讲不能算结项。必须等代码库和权重元数据正式就位。

---

## 4. 不做主观打分，只看五项硬核可验证指标

我们不搞不可验证的主观评级，只列出接下来核验 Qwen4 开源交付的五个硬指标：

1. **开源协议完整性**。核心权重继续沿用 Apache 2.0 协议，还是附加限制。
2. **全尺寸覆盖度**。主力大参数与 MoE 架构是否全放，还是仅给小模型。
3. **同日交付时间线**。商业服务上线当天，开源仓库是否同步放出权重。
4. **校验哈希清单**。官方 sha256 清单是否完整，切片文件能否校验通过。
5. **引擎兼容速度**。vLLM 与 llama.cpp 主干分支能否两天内合并 PR。

## 5. 我们的后续跟踪计划

既然云栖大会现场给出了开源承诺，我们机房的 Llama 3.3 切换计划暂时调低优先级。

接下来的工作节奏非常明确：

1. 监控 GitHub 仓库的 Release 与主干分支提交。
2. 在双卡 4090 节点复跑 vLLM 命令。抓取显存曲线、首字延迟与解码吞吐。
3. 测 llama.cpp 在 GGUF 格式下的各级损耗。整理出普通工作站配置。

一切以权重文件落地为准。后续测试脚本与显存抓取日志，我们将在第一时间整理发布。
