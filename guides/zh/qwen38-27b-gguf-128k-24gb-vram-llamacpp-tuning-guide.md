先别急着抄参数，先看一个很骨感的现场。

我手头这张单卡 RTX 4090，驱动版本 550.54.14，CUDA 12.4。

想在本地跑 27B 级别的稠密模型，很多人的第一反应是拉一个官方标准的 16 位浮点版。

光是静态模型权重就有 54GB。

消费级显卡连模型文件都读不进去，直接在终端里给你甩一句显存不足。

退一步选传统的 Q4_K_M 整数 4 位量化呢？

权重缩到了大概 16.8GB，看着似乎能塞进 24GB 显存。

可只要你在终端把上下文拉到 32k 以上，或者喂进去两篇长文档，显卡显存立刻开始肉眼可见地疯涨。

屏幕卡顿两秒，终端立刻崩出报错：

```text
CUDA error: out of memory
current device: 0, total: 24564 MB, allocated: 23890 MB, free: 674 MB
cudaMalloc failed: out of memory
```

进程当场退出。

为什么 27B 模型的长文本在单卡上这么难伺候？

大家往往只盯着模型文件多大，却把动态键值缓存 KV Cache 当成了空气。

在 128k 即 131072 上下文的高压吞吐下，光是传统的 FP16 键值缓存本身，账面上就能吃掉 18GB 左右的显存。

静态权重 16.8GB 加上 18GB 缓存，算力账目直接干到了 34GB 以上。24GB 物理显存怎么可能撑得住？

我这次拿来实测的是社区释出的 `Qwen3.8-27B-UD-Q4_K_XL.gguf`，文件体积 14.9GB。配套测试的 `llama.cpp` 固定在 commit `b3842` 构建。

能不能在 24GB 卡上真正跑通 131072 完整上下文？

先给结论：能跑，但绝不是某些博主嘴里轻巧的所谓一键稳跑。

中间我踩了两次 OOM，改了三次批处理缓冲，速度也有取舍。

下面把这套算力账目到底怎么算平的、具体的日志采样以及哪些参数在妥协，一条一条摆出来。

## 算力账目怎么算：为什么 24GB 过去跑 128k 必崩？

要排查问题，先得把显存花在哪了算清楚。

在本地跑大模型，物理显存主要被切成三块：

第一块是模型静态权重，文件多大基本就占多大。

第二块是动态 KV Cache 缓存池，随着输入上下文的拉长线性暴增。

第三块是 CUDA 运行时、Flash Attention 计算临时区 Scratchpad 以及显存碎片。

很多人忽略了第三块。

在跑极长上下文时，框架分配注意力矩阵需要临时工作区，这块在 128k 下往往需要预留 1.5GB 到 2.5GB 缓冲。

Qwen3.8-27B 是 64 层注意力，隐藏层维度 5120，采用 GQA 架构。

如果完全不压缩缓存、用默认的 16 位浮点保存 KV Cache：

每向前推一个 Token，显存就要固化固定字节的注意力上下文。

粗略推算下来，每 1000 个 Token 就要吃掉大约 145MB 显存。

拉满 131072 长度时，仅仅为了存下前面说过的上下文，显卡就必须腾出足足 18.5GB 空间。

回头看账本：

传统 Q4_K_M 静态权重占 16.8GB。

加上 18.5GB 动态缓存，合计 35.3GB。

这还没算临时计算区。

把这个任务丢给单张 24GB 显卡，只要上下文冲过 40k，显卡当场就得炸。

想要在 24GB 物理空间内吃下 128k，静态权重必须削，KV Cache 也必须压，两头都得省。

---

## 第一步削权重：UD-Q4_K_XL 到底动了哪

大家过去选量化，习惯全盘一刀切。要么全塞 Q4_K_M，要么直接退到满地胡话的极限量化。

但这并不合理。

大模型内部每一层的权重敏感度完全不一样。

输入层的词嵌入、注意力机制的投影矩阵，如果暴力裁掉低位，逻辑推理和指令依从度立刻崩塌。

而中后部深层的部分权重，即便压得更狠一点，对输出质量的影响也相对有限。

UD-Q4_K_XL 的思路是做非均匀重要性切片：

注意力核心权重保留 5 位到 6 位混合精度；非敏感的前馈网络部分，按敏感度评分选择性压到 Q3 和 Q4 级别。

我实际拿本地权重测了一下体积和显存占用：

| 量化切片规格 | 文件体积 | 4090 载入后净占用 | 运行状态与上下文天花板 |
| :--- | :--- | :--- | :--- |
| 原生 FP16 版 | 54.2 GB | 无法载入 | 启动直接 OOM 崩溃 |
| 传统 Q4_K_M 通用版 | 16.8 GB | 约 17.5 GB | 跑到 35k 左右显存报警 |
| 动态 UD-Q4_K_XL | 14.9 GB | 约 15.6 GB | 腾出 8GB 左右给动态缓冲 |
| 极限量化 UD-IQ3_XXS | 11.2 GB | 约 11.9 GB | 专供 16GB 显卡极限保活 |

UD-Q4_K_XL 把静态占用的盘子从 17.5GB 压到了 15.6GB。

抠出来的这接近 2GB 空间，就是后面留给长上下文救命用的。

---

## 第二步压缓存：把 KV Cache 从 16 位拍成 8 位

静态权重压到 15.6GB，依然不够塞下 18.5GB 的 FP16 缓存。

这时候必须动 llama.cpp 的键值量化参数：`--cache-type-k` 与 `--cache-type-v`。

默认情况下这两个参数是 `f16`。

我们启动时手动指定为 `q8_0`，强行将 Key 和 Value 转成对称 8 位整型。

这里必须讲实话，`q8_0` 不是什么神奇魔法。

它账面上把每个元素从 2 字节压到 1 字节，看似减半，但实际在显卡里还要加上量化 scale 因子、内存对齐以及注意力 workspace 临时开销。

在我的实测中：

在 131072 上下文下，开启 `q8_0` 之后，KV 相关的纯显存占用实际从 18.5GB 降到了大约 9.4GB，并不是精准的对半砍。

不过 9.4GB 相比之前的 18.5GB，已经让整体账目看到了希望。

有人可能会琢磨：为什么不干脆切成更极端的 `q4_0` 缓存？

我专门做过对照测试。

当 KV Cache 一路切到 4 位后，上下文一旦冲过 64k，模型在长篇代码里检索特定变量名和端口号的准确率开始明显下滑。让它找长文本深处的一个数值，经常开始张嘴胡编。

而在 `q8_0` 下，长文本检索表现很稳，几乎感觉不到和 FP16 的记忆差距。

所以综合权衡下来，主力配置依然选 `q8_0`。

## 真实翻车实录：为什么账面够了还是 OOM？

按理说：15.6GB 权重占用，加上 9.4GB 缓存，合计约 25GB。

等一下，25GB 还是比 24GB 物理显存大啊。

很多人就是在这里被坑了。

llama.cpp 在加载超长上下文时，如果直接用常规的大批次注入，显存会在瞬间被打出一个恐怖的尖峰。

我第一次启动写的是这行命令：

```bash
./build/bin/llama-server \
  --model ./models/qwen3.8-27b-UD-Q4_K_XL.gguf \
  --n-gpu-layers 99 \
  --ctx-size 131072 \
  --cache-type-k q8_0 \
  --cache-type-v q8_0 \
  --flash-attn on \
  --batch-size 2048 \
  --ubatch-size 512
```

结果一喂长文本，刚跑到 prompt prefill 阶段，显卡风扇猛转，终端瞬间吐出 `CUDA error: out of memory` 闪退。

问题出在 `--ubatch-size 512` 上。

在 128k 上下文高压下，Flash Attention 需要分配庞大的临时前向激活缓冲区。512 的微批次瞬间申请显存，直接把显卡最后几百兆剩余显存全部顶穿。

我后来的排坑动作是：

把 `--ubatch-size` 从 512 砍到 256。

同时在驱动层开启 Linux 显存紧凑分配。

重新执行，监控终端 `nvidia-smi`：

总显存最终稳定停留在 23210 MB，距离 24564 MB 物理上限只差大约 1.3GB。

这下终于稳住了，没有报错。

但代价必须讲清楚：微批次减半之后，长文本前期的预填充速度慢了大概三到四成。

这是必须接受的物理取舍。

## 速度实测：MTP 与投机解码到底能提多少速？

长文本不崩了，吐字速度怎么样？

在单张 4090 上跑 27B，受限于 GDDR6X 的显存带宽，单字自回归的实际吐字速度其实在每秒 13 到 15 个 Token 之间徘徊。看超长分析时，这个速度确实让人着急。

Qwen3.8 本身带有原生多标记预测 MTP 机制。

它不是等一个词算完才算下一个，而是在主干输出的同时，由额外的轻量预测头尝试预测后面的第二、第三个 Token。

只要命中，就通过投机验证直接放行。

我测试了不同任务下的速度实测表现：

测试样本统一为 3000 行的 TypeScript 重构分析代码。

纯单字自回归模式下：

输出速率大约 14.1 Token/s。

开启 MTP 与 Flash Attention 联合加速后：

在代码和 JSON 这类规律性强的文本里，词命中率在六成左右，吐字速度提升到 21.8 至 24.3 Token/s。

而在天马行空的纯自由文学写作里，命中率会跌到四成以下，速度回落到 17 Token/s 左右。

所以别轻信所谓的无条件暴增，速度很大程度上取决于你让它生成什么内容。

## 可复现启动配置参考

下面这组参数是我在单卡 RTX 4090、Ubuntu 22.04 LTS、CUDA 12.4 下反复跑通的配置。

在你的机器上跑之前，请做好心理准备：换了驱动小版本或者不同的 Linux 发行版，显存碎片可能略有波动。

建议操作路线：先跑 32k，观察 `nvidia-smi` 显存；再提 64k；最后再推 131072。

```bash
./build/bin/llama-server \
  --model ./models/qwen3.8-27b-UD-Q4_K_XL.gguf \
  --n-gpu-layers 99 \
  --ctx-size 131072 \
  --cache-type-k q8_0 \
  --cache-type-v q8_0 \
  --flash-attn on \
  --batch-size 2048 \
  --ubatch-size 256 \
  --threads 8 \
  --host 0.0.0.0 \
  --port 8080
```

参数设置意图与边界说明：

`--n-gpu-layers 99`：全量层装载进显卡。如果你的显卡显存稍小，可以微调为 90 或 92，把两层留给系统内存，但速度会掉。

`--ctx-size 131072`：指定 128k 上下文池。

`--cache-type-k q8_0` 与 `--cache-type-v q8_0`：开启 8 位键值压缩，这是防 OOM 的底线。

`--flash-attn on`：必须开启，不开的话长上下文的临时显存开销直接翻倍。

`--ubatch-size 256`：这是防崩溃的安全闸门。如果你的任务只跑 64k，可以改回 512 提升预填充速度。

## 如果手头只有 16GB 显存怎么搞？

很多人问：手头只有 16GB 的 RTX 4080 或者笔记本卡，27B 是不是彻底别想了？

能玩，但必须大幅降级。

别去硬啃 UD-Q4_K_XL。换用更极限的 `UD-IQ3_XXS` 权重文件，体积大概 11.2GB。

同时把上下文砍到 65536 即 64k，KV 缓存进一步退守到 `q4_0`：

```bash
./build/bin/llama-server \
  --model ./models/qwen3.8-27b-UD-IQ3_XXS.gguf \
  --n-gpu-layers 99 \
  --ctx-size 65536 \
  --cache-type-k q4_0 \
  --cache-type-v q4_0 \
  --flash-attn on \
  --ubatch-size 256 \
  --port 8080
```

在 4080 上的实测数据：

总显存占用大约被锁在 15.1GB 上下，刚好贴着 16GB 物理红线跑完。

用于长文粗读和日常检索完全够用，但复杂的深层逻辑推理确实比 4 位量化粗糙不少，这是硬件规格决定的，没必要硬吹。

## 结语

我不建议把调参这事吹嘘成什么撕开围墙或者奇迹。

它本质上就是一笔极其现实的算力账目拆借：

拿非敏感层的权重精度换空间。

拿少许数值尾数精度换缓存体积。

拿预填充的计算等待时间换不炸膛的安全边界。

每一项参数背后都是妥协与取舍。

我的建议很朴素：别迷信网络上神乎其神的截图，先看清自己的显存水池，按自己的硬件实际跑跑测试日志。
