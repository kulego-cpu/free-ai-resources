# 8GB 树莓派同时跑视觉与本地大模型：用 systemd slices 拯救实时任务抖动

在边缘计算设备上压榨硬件性能，最怕遇到不可预测的实时任务调度饥饿。

手头有一块 8GB 内存的树莓派 4B 单板，挂载在开源海事监控项目中。这台无头 Debian 设备同时扛着三套负载。第一是 Signal K 遥测服务，每秒高频摄取 NMEA 仪表的航向、深度、风速与转速。第二是后台的 YOLOv8 nano 模型，通过 ONNX 跑船头画面，每秒五帧。第三是用 Ollama 加载 Llama 3.2 1B 模型，在本地检索海事操作手册。

这种边缘混布组合让树莓派的四核负载常年处于过载临界点，一旦出现并发峰值就会出现算力断供。

平时只有视觉模型在跑。四核 CPU 占用率稳定在 50% 上下——铝合金外壳被烘烤到 68 度，勉强维持在温控降频线以下。

然而，只要现场人员在网页端向 Ollama 提问一个问题，大模型启动多线程推理，CPU 四个核心瞬间全线飚红到 100%。

现场失控了。可怕的事情立刻发生。

原本平稳跳动的仪表遥测流当场开始严重丢包。数据更新延迟从几十毫秒骤然飙升到数秒。前台仪表盘频频断连报警。

在船舶航行或者工业巡检场景下，为了等一段大模型问答生成，导致最基础的实时传感器数据出现断档，这在工程上是绝对不能接受的事故。这谁顶得住？

难道 8GB 的树莓派真的没办法同时跑视觉与本地大模型吗？

开源社区最近给出了极具实战价值的系统级解决方案。开发者在技术论坛记录了如何利用 Linux 系统的 systemd slices 机制优雅解决这套三负载冲突。

原始一手讨论记录在开源阵地：
https://www.reddit.com/r/ollama/comments/1xpeb8t/

经过深入剖析就会发现，常规思路中的绑核技巧在多任务算力耗尽时基本形同虚设。

必须利用现代 Linux 内核的 cgroups v2 机制进行精细化资源切片。

## 为什么仅靠 CPUAffinity 绑核会彻底失效

遇到多任务抢占 CPU，很多有经验的运维工程师第一反应通常是使用绑核。

原作者最初也是这么尝试的。

他在系统服务配置文件中写下了 CPUAffinity 参数。他把核心实时服务 Signal K 强制绑定在 0 号核心，试图把其他计算任务赶到其余三个核心。

为了防止 8GB 内存被并发推理挤爆，他配了 2GB 虚拟内存交换文件。同时将 swappiness 压低到 10，尽力把物理内存留给活跃进程。

这套常规手段打下去，实时遥测流的丢包问题解决了吗？

答案是令人失望的否定。完全没有效果。

当 Ollama 与 YOLO 两个重型推理任务同时满载时，主线程虽然避开了 0 号核心，但底层驱动中断、磁盘读写、定时器与网络软中断依然在全核之间频繁调度。

当其余三个计算核心被完全榨干到 100% 之后——操作系统的上下文切换开销急剧攀升。

一旦 0 号核心上的遥测进程发起系统调用或者申请共享锁，调度器不得不等待其他核心释放全局资源。

缓存行频繁失效。上下文切换次数暴增。

绑核并没有给实时任务换来清净的运行环境，反而人为制造了核心间的负载不均衡。

把四个核全部拉满后，光靠单线程绑核怎么可能保证亚毫秒级的调度响应？现场该卡顿还是卡顿。

必须从总算力供给的源头上踩下刹车。真有办法踩住吗？

## 核心解法：用 systemd slices 建立两道防线

社区开发者 Geekomcomputer 给出的解决方案，切中了现代 Linux 资源控制的命脉。

树莓派 4B 的博通四核处理器总算力就摆在那里。解题的关键根本不在于给单个进程硬抠空闲核心，首要原则是坚决阻止两个推理任务同时全速抢占总算力。

具体落地方案通过 systemd 的自定义资源切片实现，并在调度层面构筑了两道防线：

- 第一道防线：利用 CPUWeight 设立绝对的调度优先级；
- 第二道防线：利用 CPUQuota 为推理任务戴上紧箍咒。

落实到具体的系统配置非常清晰。在系统目录新建两个切片单元文件。

第一个切片为 telemetry.slice，专门分配给 Signal K 等关键遥测服务：

```ini
[Unit]
Description=Telemetry and Critical Realtime Slice

[Slice]
CPUWeight=1000
```

第二个切片为 inference.slice，专门用来承载 YOLOv8 与 Ollama 等计算密集型任务：

```ini
[Unit]
Description=AI Inference Background Slice

[Slice]
CPUWeight=50
CPUQuota=200%
```

仔细算算这两道防线的工程账目。

在默认情况下，Linux 系统的普通服务继承的 CPU 权重为 100。我们将遥测切片的权重直接拔高到 1000，而将推理切片的权重压低至 50。

当系统处于竞争状态时，遥测进程只要有数据包需要处理，内核调度器会毫不犹豫地优先分配 CPU 时间片。

更为关键的是 CPUQuota 等于 200% 这一条硬性限制。

树莓派的四个 CPU 核心总计拥有 400% 的时间片额度。把推理切片限制在 200%，意味着无论前台有多少请求，YOLOv8 与 Ollama 加起来最多只能榨取两个物理核心的总算力。

这为宿主系统、网络驱动、日志写入与实时遥测服务，永久预留了整整两个核心的算力余量。

## 落地验证与现场降温收益

配置好切片文件之后，重载系统配置并将服务挂载到对应的切片下运行。

重新加载 systemd 守护进程：

```bash
sudo systemctl daemon-reload
```

在服务单元文件中指定 Slice 归属，或者通过命令行直接启动受控进程：

```bash
sudo systemd-run --slice=inference.slice ollama serve
```

改完配置后在同一台树莓派上进行了高压复测。

此时再次在网页端发起大模型长文本推理，终端监控画面截然不同：

推理切片内的进程无论怎么发力，htop 监控中的整体 CPU 使用率牢牢停留在 250% 附近，四个核心错落分配。

0 号核心与 1 号核心的负载极为轻快。

此时再看前台仪表盘的遥测数据流。航向角度与水深曲线持续平滑跳动，网络封包延迟稳定保持在 15 毫秒以内，再也没有发生过一次数据超时报警。

代码顺利跑通。数据流丝滑如初。

除了网络延迟稳定，温控数据也出现了明显的同步改善。

过去双重推理全速并发时，由于四核长时间满载，铝合金外壳温度会迅速逼近 70 度降频警戒线。

而在增加了 200% 的配额限制后，即便进行长达十分钟的连续问答测试，外壳温度也稳定降到了 61 度上下，彻底远离了硬件降频的风险区间。

牺牲微不足道的推理生成速度，换来整套嵌入式系统的稳定可靠，这笔工程置换划算吗？谁能在仪表失效时保持淡定？答案不用多说。

## 边缘混布场景的技术边界与选型清单

经过这套实战调试，在低功耗单板上混布实时系统与大模型推理的选型准则就非常明确了。

如果你的设备同样是树莓派 4B 或者类似的低算力单板，请先对照以下三条防线：
- 认清硬件物理极限。不要幻想单板能同时全速跑两个算力怪兽，必须人为设置算力天花板；
- 放弃单一绑核幻想。在中断和上下文密集的环境中，优先采用 cgroups 权重与配额机制进行分流；
- 紧盯工作温度。温度冲破 65 度是系统即将降频卡死的危险信号，合理限流往往比加装风扇更治本。

硬件性能虽然有限，但严密的系统治理能让边缘单板爆发出超预期的可靠性。
