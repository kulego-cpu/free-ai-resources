先说结论：能跑通，但别学。

云计算圈子里有种刻在骨子里的直觉。既然无服务器架构能切碎成百上千个小任务跑视频转码，那为什么不能拿来跑大语言模型？

模型常驻云端，闲时每一秒都在烧钱。要是能让模型像微服务一样按需拉起，按调用毫秒数付费，账单岂不是能直接腰斩？

工程师 Noah Lindner 偏不信邪。他真把一套基于 Qwen 架构的开源决策模型拆开，塞进了 AWS Lambda。

结果很骨感。单次文档推理耗时 17 秒，单次文档的处理成本达到 3.4 美分。相较于常规托管 GPU 端点约 0.04 美分的水平，这套架构慢得让人抓狂，推理成本直接拉高了整整 80 倍。

这不是无服务器不够弹性的问题。是层间状态根本不该走对象存储。

## 为什么有人想用 Lambda 拼模型

无服务器计算最吸引人的地方永远是按需计费。

对于视频分块转码、缩略图生成或者事件驱动的数据清洗，Lambda 确实能把成本压缩到极致。

但在大语言模型推理领域，传统方案有两大痛点：

第一是冷启动与保活成本的冲突。一台带 A10G 或 A100 的云服务器，只要开机运行，哪怕整夜只有零星几个内部调用，每小时几美元的固定账单依然照扣不误。谁的预算能经得起这么烧？

第二是流量峰值的弹性困境。突发两千个并发请求时，常规实例必须依赖预设的自动扩容策略。拉起镜像、加载权重往往需要两到三分钟。等它扩容完毕，业务早就超时熔断了。

如果能把模型完全 Serverless 化，岂不是能做到零闲置成本加无限瞬间并发？

想法很丰满。现实给出的第一道铁壁，直接砸在函数运行时的物理规格上限上。

## 9.3GB 权重拆成 34 个函数的流水线

做这个实验首先要面对部署包上限。AWS Lambda 对函数解压后的代码与依赖有严厉的体积约束，通常不能超过 250MB 直传或几 GB 的容器镜像。

实验选用的模型基于 Qwen 架构微调，权重文件完整体积约 9.3GB。把 9.3GB 的单体权重直接塞进单个 Lambda 函数？从初始化到冷启动都是死路一条。

作者采取了分层切片的策略：

大语言模型由逐层堆叠的 Transformer 结构组成。这套 Qwen 模型包含 32 个串行的 Transformer 层，单层权重约 225MB。加上前置 Embedding 词表层与尾部 LM Head 预测头，一共拆成 34 个独立的 Lambda 函数。单层 225MB 刚好能轻松塞进单个 Lambda 的轻量运行环境中。

拓扑结构被设计成了一条串行接力流水线：

```text
Prompt 输入
     │
     ▼
┌─────────────┐
│ Lambda 0    │  加载 Embeddings 词表
└──────┬──────┘
       │  激活张量写入 S3
       ▼
┌─────────────┐
│ Lambda 1    │  处理 Transformer Layer 0，约 225MB 权重
└──────┬──────┘
       │  激活张量写入 S3
       ▼
      ... 中间 30 级函数串行接力
       │  激活张量写入 S3
       ▼
┌─────────────┐
│ Lambda 32   │  处理 Transformer Layer 31
└──────┬──────┘
       │  激活张量写入 S3
       ▼
┌─────────────┐
│ Lambda 33   │  加载 LM Head 输出预测概率
└─────────────┘
```

链路跑通那天，作者先没看账单，先对了输出。

同一段 prompt，本地 PyTorch 和 Lambda 管道的 top-1 token 能对上。能算对，说明前向传播没被拆坏。

但在处理批量任务、多轮试跑以及跨层依赖切分下，整个流水线累计触发了高达 5600 次 Lambda 函数调用。

随后作者打开成本页。单文档处理 17 秒，综合成本 3.4 美分。能跑，和能用，完全是两回事。

## 17 秒与 3.4 美分：80 倍亏本账单是怎么算出来的

能跑通等于能用吗？

实测数据摊开在控制台账单里时，数字极其残酷。

单次文档推理耗时约为 17 秒，处理一个文档累计产生的算力与存储调用开销约为 3.4 美分。

对比常规方案：在常规托管 GPU 实例比如专有云端小卡上跑同等尺度的 Qwen 推理，单次前向推理通常在数十毫秒至数百毫秒之间。折算到单次请求的摊销成本，通常只有 0.04 美分上下。

3.4 美分对比 0.04 美分。成本直接暴涨了 80 倍。

原本奔着省钱去的 Serverless 实验，变成了吞噬预算的无底洞。钱到底花在哪了？

### 第一笔账：S3 激活张量中继的网络泥潭

在显卡内部，层与层之间的激活张量通过高速显存带宽传输，SRAM 与 HBM 之间的吞吐高达数 TB 每秒。

但在 34 个独立的 Lambda 函数之间，进程内存根本不共享。前一层算完的激活值，下一层怎么拿？

必须序列化后传出去。

实验使用了对象存储 S3 来中转中间层张量。32 层串行，每层都要把激活张量序列化，写进 S3，下一层再拉出来。

按每 token 每层一次 PUT 加一次 GET 粗算，32 层就是 64 次对象请求。生成 175 个 token，就是一万一千多次 S3 往返。

这不是指数爆炸，是线性叠加。但这种线性叠加已经足够把 17 秒全部耗光。绝大部分时间不是在算矩阵乘法，而是在等待中间张量在 S3 与 Lambda 之间来回搬运。

### 第二笔账：纯 CPU 算矩阵乘法的时间溢价

AWS Lambda 长期以标准 CPU 为主。即便配置了最高内存规格来换取更高的 CPU 配额，用通用的 x86 或 ARM 架构指令集跑稠密浮点矩阵计算，效率依然无法与专用张量核心相提并论。

GPU 几毫秒就能刷完的矩阵乘法，CPU 需要耗费数百毫秒。

Lambda 的计费模式是执行时间乘以内存规格。单次执行拉长数十倍，哪怕单毫秒单价看起来是微小的零点几美分，乘上数千次调用后也会迅速质变。

### 第三笔账：冷启动与层间调度同步开销

函数实例从被调用到分配容器、加载 225MB 层权重、初始化运行时环境，存在不可避免的冷启动抖动。

在严格串行的依赖链条里，流水线的整体耗时取决于最慢的那一个节点。哪怕其中有两三个切片遭遇了调度延迟，整条链条的所有后续函数都必须挂起等待。

## 从这场实验看 LLM 推理的真实工程边界

把大模型塞进 34 个 Lambda 的尝试虽然在商业上彻底失败，但它为系统工程师划定了几条非常清醒的技术红线。

### 算力密集型与 IO 密集型的物理分野

Serverless 架构为什么能在视频转码和日志过滤上大获全胜？

因为那些任务属于典型的无状态数据管道。切片之间互不依赖，且单个切片内的数据吞吐远大于跨节点通信。

而大语言模型本质上是重度显存带宽受限与极低通信延迟受限的密集计算。Transformer 架构的自回归机制要求每产生一个 Token，就要完整访问一次权重并依赖上一刻的完整隐状态。把强耦合的状态切断并扔给松散的网络节点，完全违背了硬件亲和性的客观规律。

### 伪弹性与真成本的权衡

很多团队在做架构选型时，容易陷入追求零空闲的极端执念。认为只要有闲置算力就是浪费，宁可用极度复杂的分布式中继去消除空载。

但这真的划算吗？

低频场景下，一台小规格 GPU 实例哪怕闲置 80% 的时间，按月计费的综合成本依然远低于数千次高开销的分布式冷启动拼装。闲置成本是显性的，而分布式架构的通信消耗、序列化损耗与运维复杂度全是隐性的。

### 无服务器推理的合理姿态

这是否意味着 Serverless 在大模型时代毫无用处？

当然不是。但合理的无服务器形态绝不是把单个单体模型剁成 32 块放在无状态函数里裸跑，而是平台底层的实例级热池化调度：

第一种形态是近来云厂商演进的 GPU 容器实例按秒计费。权重已经预热挂载在物理节点共享只读缓存中，调度层只负责路由请求，不拆散层间拓扑。

第二种形态是把轻量级辅助任务留给 Serverless，比如前置的 Prompt 模板渲染、敏感词过滤、鉴权校验以及后置的结构化 JSON 提取。重型模型本身依然稳稳地留在具备高带宽互联的专用加速芯片上。

## 结语

这事的教训不复杂。

第一，别把 Transformer 当视频切片。层间状态是强耦合的，拿 S3 当中继只会把延迟和请求费一起放大。

第二，低频推理就老老实实租一张小卡。闲置 80% 也比 5600 次冷启动拼装便宜。

第三，要弹性，等平台把 GPU 热池做好。别自己拿函数计算拼模型。

手头如果有低频的大模型推理需求，真的还有必要死磕纯函数计算吗？

省下来的不是架构图上的空转，是账单上的真金白银。
