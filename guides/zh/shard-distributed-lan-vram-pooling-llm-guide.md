# 局域网显存拼多多：Shard 拼合旧笔记本与迷你主机多端运行 70B 大模型实操

工位和书房里常年闲置着两三台旧设备。

一台退役旧游戏本，配着 6GB 显存的 RTX 3060 移动版显卡。

一台做软路由的迷你主机，板载 16GB DDR5 内存。

外加一台写代码的台式机，插着 12GB 显存的 RTX 4070 显卡。

先算一笔硬件账本：文件很大。

Llama-3.3-70B-Instruct-Q4_K_M 的 GGUF 体积约 43GB。

单卡连权重都塞不进去。

RTX 3060 移动版 6GB、4070 12GB，迷你主机 16GB 内存也扛不住。

单机强行加载必死。

终端直接抛出 OOM 崩溃：`CUDA out of memory: failed to allocate 43210 MiB`。

直接卡死。

但如果把这三台机器的显存和内存连成一个池子呢？

12GB 加 6GB 显存，算上迷你主机划出来的 16GB 内存；可用池化容量直接拉到 34GB 以上。

容量足够了。

开源项目 Shard [仓库: avelone123123/shard，基于 v1.8.1 版本] 走的就是这条路。

架构很轻。

它封装底层 llama.cpp 的分布式 RPC 架构，把零散算力拼成虚拟大模型服务器。

## 为什么层间切分不需要昂贵的高带宽网络：隐藏状态 8KB 跳步真相

聊到多机分布式推理，很多人的第一反应是机房里昂贵的高速交换机。

如果做张量并行，每一层注意力计算都要在机器间同步全部张量，百兆或千兆局域网会当场瘫痪。谁能承受？

但 Shard 采用的是流水线层间切分模式。

一个 70B 模型通常包含 80 层 Transformer Block 结构。

Shard 把前 30 层放在台式机的 12GB 显存里；中间 15 层塞进笔记本的 6GB 显存；剩下的 35 层交给迷你主机的系统内存承载。

分工明确。

在自回归解码生成阶段，数据在机器之间到底传递什么？

它不需要同步全量权重；也不需要广播注意力矩阵。

前序节点只需要把计算完成的隐藏状态输出向量甩给下一个节点。

8KB 的 hidden states 到底要传多久？

按千兆 125MB/s 算，8KB 理论传输耗时仅 0.064 毫秒。

内网交换机 ping 延迟通常在 0.3 到 0.6 毫秒之间；传输加协议开销不到 0.1 毫秒。

三个节点切分两次，生成一个 token 仅发生两次网络跳步。

总网络传输延迟被压在 1.5 毫秒以内——这非常轻巧。

相比于在内存里搬运几十 GB 权重所耗费的几百毫秒，这 1.5 毫秒的网络开销微乎其微。

但看网络指标要盯紧 p99 延迟，别只看平均值。

只要内网没有出现大面积丢包重传，千兆以太网跑层间流水线完全绰绰有余。

## Shard 快速组网实操：Master 调度节点与 Worker 算力节点配置

实际搭建这套局域网集群非常轻量。

所有机器只需安装 Python 3.10 环境与 Shard 客户端。

第一步，选定性能最好的台式机作为 Master 协调节点。

我们在台式机终端执行后台启动命令：

```bash
# 启动 Master 调度守护进程
shard start --daemon

# 创建局域网集群并公布服务
shard lan create HomeCluster --open
```

Master 节点会自动在 UDP 8001 端口广播局域网探活信标。

同时在 8000 端口拉起兼容 OpenAI 规范的 FastAPI 服务网关。

第二步，将笔记本与迷你主机作为计算节点接入。

在笔记本和迷你主机上分别执行探测与加入指令：

```bash
# 自动扫描同一网段内的可用协调节点
shard lan status

# 加入集群并共享可用显存与内存资源
shard lan join 192.168.1.100 --share
```

加入指令执行后，Worker 节点拉起本地 ggml-rpc-server 进程。

心跳正常。

Worker 不用提前下载 43GB 的 GGUF 大文件，省下本地磁盘空间。

但这有代价。

第一次执行 deploy 时，Master 需要从本地把切片通过内网流式分发过去。

分发需要时间。

在千兆网络下按 85MB/s 实际吞吐测算，分发耗时大概需要 7 到 9 分钟。

百兆交换机耗时更久。

在 Master 执行加载命令时，底层引擎会自动计算各节点的显存预算比例，并将对应层数的模型权重流式切片分发至各节点的 RPC 进程：

```bash
# 查看全局池化显存与内存账本
shard cluster status

# 载入模型切片并启动分布式推理
shard cluster deploy
```

部署时如果遇到 Worker 掉线，先检查路由器是否开启了 AP 隔离。

## 局域网分布式推理的真实速度与物理延迟底牌

把分散的硬件连起来确实很酷，但真实生成速度能用吗？

我们使用 Llama-3.3-70B-Instruct 做了一组连续实测。

在台式机单机环境下，12GB 显存连模型加载的第一道内存分配都无法跨过。

当接入笔记本与迷你主机组成 34GB 联合池后，模型成功加载就绪。

实测生成速度稳定在每秒 4.2 到 5.8 个 tokens 之间。

这个速度跟机房单台八卡顶级集群动辄上百 tokens 的吞吐量自然无法相提并论。

差距非常悬殊。

但对于每秒阅读速度仅有五六个汉字的人类而言，5 tokens/s 已经足够支撑日常终端代码问答与深度总结。够不够用？

瓶颈出在哪里？

瓶颈完全不在 8KB 的内网传输上。

真正的性能短板在于迷你主机的 DDR5 内存带宽。

权重落入内存后，CPU 解码时可用带宽只有 60GB/s 左右。

这和动辄数百 GB/s 的 GPU 显存没法比。

通过 `shard cluster status` 看层分配，再结合 `free -h` 与 `nvidia-smi` 观察占用。

排查顺序很关键：

调优顺序要严谨——先消灭 OOM，再尽量减少系统内存里的层数，最后才去查网线。

## 多机分布式推理适合你的工作流吗？边缘算力选型清单

局域网显存池化并不是万能方案。

在决定组网折腾之前，建议对照以下场景清单评估：

第一，文字阅读与编程辅助是其核心价值场景。

每秒四五个词的吐字速度，对于配合 Claude Code 或 Cursor 充当本地代码解释器完全够用。

私密代码无需上传公有云网关——所有数据只停留在内网。

第二，如果你打算跑高并发服务或者大规模长文本批处理，请趁早放弃这套方案。

流水线切分只能承载单并发低延迟任务。

一旦并发数上来，多台机器串行等待的队列排队延迟会指数级恶化。谁能顶得住？

第三，组网介质尽量选用千兆双绞线或 Wi-Fi 6 路由器。

老旧的 Wi-Fi 4 路由器丢包率波动较大，偶发的高时延会破坏心跳包探活机制，导致协调节点误判 Worker 掉线。

闲置设备放在抽屉里只会慢慢贬值。

插上网线，先跑 `shard lan status` 看延迟和丢包，再用小参数模型跑一遍链路验证。

链路稳了再上 70B。

面对工位上的闲置设备，你准备好测测局域网的真实延迟了吗？
