买了一张 12GB 显存的 RTX 3060 或者 RTX 4060，兴冲冲想在本地跑一跑 30B 级别的中大模型。

现实往往迎头浇上一盆冷水。

以 17.1GB 体积的 31B Q4_K_M 模型为例。显存只有 12GB。无论怎么抠显存，至少有接近 7GB 的权重必须溢出到系统内存里。

一旦发生内存溢出，llama-server 的生成速度立刻从显存级吞吐暴跌到系统内存的带宽瓶颈。

终端光标一秒钟蹦出 3.4 个词。

泡一杯咖啡回来，一段几百字的代码解释还没吐完。

一开始我以为是显卡驱动的问题。滚回旧版驱动，没用。又怀疑是 Windows 的桌面窗口管理器在后台偷吃显存，翻了一圈 nvidia-smi 监控，前台进程干净得很。

最后才在社区里翻到线索。默认的 fit 策略会预留缓冲。12GB 显存上白扔 1GB，正好卡在多吃两层权重的关键线上。

差那两吉字节，速度为什么直接腰斩？

这不是玄学，是 360GB/s 显存带宽跌到 20GB/s 内存带宽的巨大落差。模型每吐出一个词元，CPU 都得跨越系统总线把 7GB 权重重新搬运一遍。物理账目摆在这里，没有任何商量余地。

很多人知道 llama.cpp 有不少调优参数可以救场：调小 fit-target 留白显存多塞两层到 GPU、挂载 MTP 或者 DFlash 辅助小模型搞投机采样、调高投机步数、调整置信度截断阈值。

可参数组合实在太多了。

显存留多少兆合适？辅助模型猜 4 步还是 16 步？置信度阈值设 0.5 还是 0.7？

那天下午我开了二十多轮测试，前七八轮基本是白跑。最惨一次显存直接打满，llama-server 整个进程被操作系统强杀；还有几次投机采样挂上去反而更慢，速度从 3.4 跌到 2.2，白搭功夫。

直到几天前，GitHub 上冒出一个开源工具：spilltune。作者是 0xydendrum。项目开源地址就在 github.com/0xydendrum/spilltune。

它不讲空洞理论。它把我们手动调优一个下午的脏活累活，压缩成了一条全自动执行的爬山算法任务。

## 一、 核心症结：内存溢出时的总线换页代价

搞懂 spilltune 的价值之前，得先看清显存与内存之间的物理账目。

RTX 3060 12GB 显卡的显存带宽大约是 360GB/s。双通道 DDR4-3200 内存的理论极限带宽不过 25.6GB/s；实际跑在操作系统里，能跑满 20GB/s 就不错了。

两者相差十四倍以上。

当一个模型全部塞在显存里时，GPU 内部张量核心可以全速吸纳权重。

一旦有三分之一的层数被甩给系统内存，每次自回归解码生成一个词元，CPU 就必须在几十微秒内从慢吞吞的内存总线里把这 7GB 数据重新搬一遍。

水桶的最短板变成了内存通道。决定生成速度的，成了那截最慢的总线。

llama.cpp 官方默认的 llama-server 启动逻辑非常保守。为了防止长上下文把显存挤爆，它默认开启 fit-on 策略，并在显存里硬性保留 1024MB 的缓冲余量。

对于 12GB 显卡来说，白白空出 1GB 显存，意味着原本能放进 GPU 的两三层权重，被活生生踢到了系统内存里。

难道我们真只能任由这 1GB 显存白白空着吗？多掉落两层权重，每秒吐字速度就要再跌两三成。

更让人烦躁的是投机采样的参数配置。很多人给大模型挂上 DFlash 或者 MTP 辅助模型，以为挂上就能加速。

结果跑起来一看，速度竟然更慢。

为什么？因为没有加置信度截断参数。辅助小模型在写代码和做数学题时猜得很准；但在写散文或通用闲聊时胡乱猜测，导致大模型每次前向验证全部拒绝，白白增加了显存搬运负担。

不针对具体的模型与硬件组合做实机探测，任何纸面配置都是盲人摸象。

## 二、 spilltune 怎么测：四套试卷与自动爬山

spilltune 的代码结构很简单。

它是一个纯 Python 编写的自动化调优调度器。没有复杂的深度学习环境依赖，直接调用本机已有的 llama-server 可执行文件。

既然要调优，为什么不直接跑网格搜索？

那得试探上百种排列组合，谁有耐心等四五个小时？

它把调优拆解为清晰的三个阶段：

```text
阶段一：显存极限边界勘测
从默认保留 1024MB 探测 -> 逐步收窄至 512MB / 256MB -> 寻找不崩溃的最大 GPU 层数

阶段二：投机采样辅助参数爬山
自动探测辅助模型类型 -> 初始猜测步数探测 -> 置信度阈值梯度测试 -> 寻找接受率甜点

阶段三：真实题库多维评测
数学算术 / 逻辑代码 / 概念解释 / 故事创作 -> 验证生成一致性 -> 导出最佳命令
```

注意它的评测设计。很多基准脚本为了省事，只拿一句你好世界来跑吞吐。只测一句你好世界，真能反映实际写代码的吞吐吗？在极短提问下，投机采样猜中率虚高，跑出来的数字全是泡沫。

spilltune 自带了四套完全不同题材的内建题库：数学推理、代码编写、概念解释与故事创作。

每个试探轮次固定生成 192 个词元。

为什么测四种题材？

因为实战经验证明：投机采样辅助模型在代码和数学题上，接受率往往能冲上 70% 以上；但在文学创作等发散场景下，接受率经常跌到 30% 以下。

如果辅助模型在某些题材上帮倒忙，spilltune 会实事求是地在终端里给出双重建议：写代码时挂载辅助参数，日常文学创作时关闭辅助模型。

## 三、 实机上阵：在 RTX 3060 12GB 上跑满 31B 模型

为了检验 spilltune 的真实调优效果，我们在 Windows 11 环境下的测试机上跑了完整流程。

硬件配置如下：

- 处理器：Intel Core i5-14600KF
- 显卡：NVIDIA GeForce RTX 3060 12GB
- 内存：32GB DDR4-3200 双通道
- llama.cpp 构建版本：b11798
- 目标模型：Gemma 4 31B Instruct Q4_K_M，文件体积 17.1GB，总层数 60 层
- 辅助模型：Gemma 4 31B DFlash Q4_K_M，文件体积 0.85GB

在跑调优命令之前，有一道必做动作：彻底关闭后台占用显存的所有程序。浏览器硬件加速、后台画图工具全部退干净。显卡必须处于初始空载状态。

安装与执行命令：

```bash
# 从 GitHub 直接拉取安装最新提交版本
pip install git+https://github.com/0xydendrum/spilltune

# 指定主模型与辅助模型，启动全自动调优
spilltune gemma-4-31B-it-Q4_K_M.gguf --draft gemma4-31b-it-dflash-Q4_K_M.gguf
```

终端启动后，spilltune 迅速打印出底层硬件检测信息：

```text
Hardware: NVIDIA GeForce RTX 3060 12 GB (0.4 GB in use); RAM 32 GB (25 GB free)
Model:    gemma-4-31B-it-Q4_K_M.gguf: 17.1 GB, 60 layers, dense
Helper:   gemma4-31b-it-dflash-Q4_K_M.gguf: 0.85 GB, --spec-type draft-dflash
          6.9 GB of it has to live in system RAM.
```

信息亮得很直接：整整 6.9GB 的数据必须常驻系统内存。

接着，自动探测轮次开跑。

第一轮基准线测试，使用 llama-server 官方默认参数：

```text
Stage 1/3: where the model's layers go (GPU vs RAM)
  trial  1  baseline: llama-server defaults ...
            3.4 tokens/sec, 31/61 layers on GPU
```

默认情况下，GPU 只吃下了 31 层，吐字速度每秒 3.4 个词。

随后，spilltune 开始沿着保留显存梯度向下试探。它把保留显存从 1024MB 压缩到 512MB，再压到 384MB。

显存里的层数从 31 层上升到 38 层。

进入第二阶段，辅助模型介入。它开始测试不同的推测步数与置信度截断阈值。

测试到第 15 轮时，爬山算法找到了吞吐极值点：

```text
  trial 15  dflash helper, 6 guesses, confidence cut-off 0.7, 384 MiB less VRAM held back ...
            6.5 tokens/sec, 66% of guesses accepted, 21/61 layers on GPU

BEST for one chat: 6.5 tokens/sec (1.92x the defaults' 3.4)
```

六次猜测、0.7 置信度截断、留出 384MB 显存。

生成速度从每秒 3.4 词提升到了每秒 6.5 词。

提速达到 1.92 倍。

等等，显存真能压到只留 384MB 吗？

会不会跑着跑着突然闪退？

实测连续跑完题库完全稳定。质量这块我不敢吹。抽了测试题库里的一批代码题和数学题，和全显存跑出来的答案逐条对了一遍，能看出明显差异的极少，基本是采样随机性带来的细微措辞不同。

如果把辅助模型换成 MTP 架构的辅助权重，在第 13 轮测试中，吞吐最终定格在每秒 8.9 词，相比默认配置实现了 2.61 倍的加速。

调优任务耗时 32 分钟，全程不需要人守在旁边看。调优完毕后，终端当场吐出一条可以直接复制启动的命令：

```bash
# spilltune 最终推荐的一键启动生产命令
llama-server.exe -m gemma-4-31B-it-Q4_K_M.gguf -c 4096 -np 1 \
  --fit on --fit-target 2098 \
  -md gemma4-31b-it-dflash-Q4_K_M.gguf -ngld 99 \
  --spec-type draft-dflash --spec-draft-n-max 6 --spec-draft-p-min 0.7
```

同时，当前目录下自动生成了一份 report.html 诊断报告，将各轮测试的层分配、猜测接受率与内存占用完整归档。

## 四、 混合专家模型的特殊性：为什么猜得越多反而越慢

在测试 Gemma 4 26B-A4B 这种 MoE 混合专家模型时，我们遇到了反常识的现象。

常理下，辅助模型每次猜得越远，只要猜中率高，加速应该越大。难道不是这样吗？

但在 MoE 架构下，这个规律完全变了。

看一组实测数据记录：

| 测试配置 | 数学题吞吐 | 代码题吞吐 | 概念解释 | 创意写作 |
| :--- | :--- | :--- | :--- | :--- |
| MoE 默认参数无辅助 | 39.8 t/s | 40.4 t/s | 40.1 t/s | 39.7 t/s |
| 挂载 DFlash 辅助，猜 8 步 | 37.4 t/s | 45.7 t/s | 23.4 t/s | 20.5 t/s |
| 挂载 DFlash 辅助，猜 2 步 | 50.8 t/s | 51.8 t/s | 37.7 t/s | 31.8 t/s |

注意看后两列。

当推测步数设定为 8 步时，创意写作的吐字速度从默认的接近 40 词每秒跌到了 20.5 词每秒。

为什么猜得多了反而慢了？多花时间在内存里倒腾专家权重，难道不是得不偿失吗？

因为 MoE 模型的专家权重巨大，必须常驻在系统内存里。主模型每一次推测验证，如果 8 个词元涉及不同的专家路由，CPU 就必须在内存里频繁调度不同的专家权重。

频繁的跨内存换页与总线争抢，抵消了投机采样的微小增益。

反而当步数压缩到 2 步甚至 1 步时，专家路由切换频率可控，数学和代码吞吐顺利突破了 50 词每秒。

报告最后一行直接给出了结论：MoE 场景下投机步数别超过 2。写作场景如果发现降速，干脆关掉辅助模型。剩下的，自己跑一遍比看十篇文档来得实在。

## 五、 局限与避坑清单

工具好用，但边界很硬。

上手前得先看清四条限制：

第一条是上下文长度约束。spilltune 默认基于 4096 长度的上下文来测算显存余量。如果你日常需要用 32K 的长上下文，必须在命令行显式传入 ctx 参数，比如 `--ctx 32768`。不传这个参数，按 4K 测出来的显存留白一旦遇到长文档，推理第一步就会当场 OOM 崩溃。面对几万字的长文档，你的上下文参数配对了吗？

第二条是辅助模型匹配性。辅助模型必须与主模型在架构分词器上严格同源。拿 Qwen 的辅助模型去带 Gemma，spilltune 在加载第一步就会报错退出。

第三条是单卡局限。目前 spilltune 仅支持单张 GPU 的调度优化，多卡切分并行的拓扑寻优功能尚未支持。

第四条是跨平台支持度。目前我只在单张 3060 的 Windows 11 环境上完整验证过。脚本底层针对 CUDA 做了适配。手头没有 Mac，Apple 芯片走统一内存，没有传统的 PCI-E 总线溢出瓶颈，拿这套工具测意义不大。

显卡在手，参数在人。

花半小时让脚本跑一遍参数探测，把原本被保守策略浪费掉的显存与总线带宽榨出来，总好过对着 3.4 的龟速叹气。面对动辄几万词的生产长上下文，在显卡再次被塞爆前，摸清物理底牌难道不是最稳妥的第一步吗？
