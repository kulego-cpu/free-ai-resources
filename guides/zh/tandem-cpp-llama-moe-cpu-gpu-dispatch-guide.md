# 给 llama.cpp 打个补丁：单卡 4090 跑通用 MoE 从 29 到 97 词元每秒实测复盘

本地跑混合专家 MoE 模型。
最烦人的根本算不上总参数量大。
真正卡脖子的，是一大半专家权重躺在系统内存里睡大觉！
每次路由命中，推理引擎就得把几百兆参数跨过 PCIe 总线死命搬运一次。
PCIe 4.0 x16 理论单向带宽不过 31.5 GB/s。
显卡矩阵单元只能在那儿傻傻空转。
干等数据送过来。
光标每秒吐二三十个字。
机箱风扇呼呼吹。
人坐在屏幕前干等着。
卡不卡？
简直太慢了！

tandem.cpp 这个开源补丁的想法很土也很直接：
既然跨总线搬运这么卡，干脆别搬了！
直接让多核 CPU 在系统内存里就地算！
我照着官方说明打了补丁。
在手头这台主机上连续压测了两天。
下面是我这台机器跑出来的实测数字，以及几个必须提前说清楚的硬核坑点。

## 一、 为什么传统的显存卸载会把 GPU 活活饿死？

好端端的 4090 旗舰卡，跑起混合专家为什么会沦为老牛拉破车？
答案全在总线搬运惩罚上。
难受。

以一个量化后 40GB 体量的通用 MoE 为例。
单张 24GB 显存根本吞不下全部权重。
传统 llama.cpp 的经典卸载逻辑非常直白：
把放得下的层硬塞进显存，放不下的就老老实实留在系统内存。
门控路由一旦相中内存里的专家，麻烦就来了。
引擎只能通过系统总线硬拉权重进显存。
每生成一个 token，总线上就要来回倒腾几百兆数据。
显卡强大的矩阵算力，八成时间全在无所事事地等数据过桥！
算力严重过剩。
总线严重便秘。
谁受得了？

以前社区里确实出现过一些专精提速的独立引擎，号称能跑一百多词元每秒。
结果翻看实现细节才发现满是猫腻：
有的偷偷在后台启用了尾部专家跳过逻辑，为了刷榜直接把难度较高的计算扔掉；
有的强制绑定专属私有格式，开源社区海量的通用 GGUF 权重一个都用不了；
甚至还有的锁死贪婪解码伪造跑分。
这种靠切除模型脑叶换来的所谓极速，在严肃生产环境里真没必要！

## 二、 拆解 tandem.cpp：CPU 与 GPU 真正异构并行

README 里的核心逻辑其实就两句话：
绝不跨总线搬运非驻留专家；
让 CPU 与 GPU 真正并行分工。
管用吗？
真管用。

整套补丁的运行逻辑包含两大协同基石：

### 1. 热点专家常驻显存
将全局最常被激活的高频核心专家锁定在 4090 显存内。
利用显卡恐怖的 TB 级显存带宽，以全速执行矩阵乘法。

### 2. 内存就地计算与主机端归并
当门控路由命中了驻留在内存中的冷门专家时，系统绝不启动跨总线搬运。
而是把该专家的矩阵乘法任务，直接下发给多核心 CPU 处理。
GPU 负责核心专家。
CPU 原地啃辅助专家。
两者各自计算完毕之后，在主机内存侧完成最终激活值的汇总相加。
总线搬运彻底归零！

作者在项目说明里写得明明白白：补丁不搞跳过专家，也不篡改路由器的权重倾向。
说句大白话，跑出来的文本质量跟原生 llama.cpp 基本没有出入。

不过这里我必须主动认错辟谣：
网上有人吹嘘什么数学上绝对一致，完全是没写过异构并行算子的外行话！
我拿同一个随机种子跑了 200 次采样对齐测试。
前 100 个 token 完全一致。
往后偶尔会出现微小的位级差异。
为什么？
因为 CPU 和 GPU 的浮点累加顺序根本不可能完全一样！
现代浮点加法并不满足严格结合律。
只要并行分块累加顺序变动，末位浮点截断就必然不同。
但这种微小扰动完全在工业容差范围内，GSM8K 数学基准评测偏差不到千分之三。

## 三、 实机压测：五轮中位数与真实硬件开销

数据管用吗？
拒绝无源吹水，直接看手头这台真实主机的压测表现。

### 测试平台硬件清单
- 处理器：i5-12400F 六核全开 4.4GHz
- 图形卡：RTX 4090 24GB 显存
- 系统内存：64GB DDR4-3200 双通道
- 操作系统：Ubuntu 24.04 LTS
- 评测模型：Qwen2-57B-A14B 通用 GGUF

### 五轮实测中位数对照表

测试参数统一设定：n_predict 为 512，批处理大小为 2048，温度采用模型默认推荐值。

| 模型规格与运行场景 | llama.cpp 原生卸载 | tandem.cpp 协同补丁 | 相对提速倍率 | 实测开销与状态判读 |
| :--- | :--- | :--- | :--- | :--- |
| Qwen2-57B-A14B 贪婪解码 | 29.8 词元每秒 | 97.3 词元每秒 | 3.26 倍 | GPU 功耗 210W 且 CPU 六核占满 96% |
| Qwen2-57B-A14B 随机采样 | 29.4 词元每秒 | 96.1 词元每秒 | 3.27 倍 | 采样阶段引入额外延迟不到两毫秒 |
| Mixtral-8x7B-Instruct Q4_K_M | 33.5 词元每秒 | 68.2 词元每秒 | 2.03 倍 | 激活专家数较多导致 CPU 侧耗时上升 |
| 64k 长文本 Prefill 预填充 | 基准基线耗时 | 提速约 1.4 倍 | 1.42 倍 | 预填充瓶颈在注意力而非显存卸载 |

从 29.8 飙到 97.3，提速整整三倍出头。
说实话，这个实测成绩比我最初的心理预期高出一大截。
我原本估摸着能跑到 60 就顶天了。
毕竟区区一颗六核 i5 到底能扛下多少脏活累活？
后来我把 `htop` 和 `perf stat` 挂在后台一盯，瞬间全明白了：
CPU 六个物理核心全被占得满满当当！
系统内存通道总线利用率直冲百分之七十五以上！
这套补丁的本质，哪是什么无中生有变出算力？
其实就是赤裸裸地拿多核 CPU 算力与系统内存带宽，直接顶替掉那个被活活卡死的 PCIe 搬运瓶颈！

## 四、 哪些机器别白费力气？未解决的工程缺陷

看到这里，千万别脑子一热就冲动去折腾。
以下这几种情况，我劝你提前死心：

第一，别指望笔记本或 16GB 内存的小主机能复现这个神话！
40GB 的 MoE 权重如果连物理内存都塞不进，就只能走 mmap 落盘靠虚拟内存硬撑。
一旦发生疯狂的磁盘换页，吞吐当场暴跌到个位数，伴随严重的系统卡死。
内存容量不够的，千万别瞎折腾！

第二，显存极度紧绷时依然会触发 OOM 崩溃。
显存分配参数 `--moe-cache-mib` 必须根据你的实际显存手调。
必须至少给上下文预留 3GB 以上的安全缓冲。

第三，六核 CPU 在面对更大尺寸的模型时明显有些力不从心。
如果你想玩更庞大的 MoE，建议处理器至少 8 核心起步。
换上 DDR5 甚至四通道高带宽内存才能喂饱数据。

第四，长上下文预填充 Prefill 阶段提升非常有限，实测只有 1.4 倍左右。
别拿解码阶段的翻倍数字去盲目幻想首字时间也能跟着飞跃。

## 五、 实操指南：代码获取与编译命令

补丁源码托管在 GitHub，仓库地址为 github.com/ewhacc/tandem.cpp。
仅仅修改了三个底层源码文件。
拉取代码打补丁与编译步骤如下：

```bash
git clone https://github.com/ggml-org/llama.cpp
cd llama.cpp && git checkout b3920
git clone --depth 1 https://github.com/ewhacc/tandem.cpp /tmp/tandem
git apply /tmp/tandem/patches/*.patch
cmake -B build -DGGML_CUDA=ON -DCMAKE_BUILD_TYPE=Release
cmake --build build --config Release -j8
./build/bin/llama-cli -m ./models/qwen2-57b-a14b.gguf --n-gpu-layers 33 --moe-cache-mib 6144 -p "请用 Python 编写并发抓取器" -n 512
```

想试的兄弟自己拉代码编译。
如果在你的显卡上遇到段错误崩溃，欢迎来 issue 留言对线抓虫！
