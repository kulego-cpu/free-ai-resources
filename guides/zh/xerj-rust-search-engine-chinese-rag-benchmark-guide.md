很多做私有化知识库的同行，在挑拣本地检索后端时，都盯上过 GitHub 上那个两万星的单文件 Rust 搜索引擎 XERJ。单二进制文件开箱即用，兼容标准 Elasticsearch 协议且内存占用仅有几十兆，终端敲一行命令就能跑起来。跑英文维基或者接口文档，毫秒级的响应确实顺手。

但在真实的中文业务语料面前，这套默认配置差点把我们整崩溃。真坑。

我们把 208 份真实企业级合规文档切成 33,575 个分块，跑了一轮包含 60 道题目的严苛端到端评测基准。测完终端打印出来的命中数据，让人心里一凉。原生 XERJ 的 BM25 词法检索，真实证据块的 Top 3 召回率只有 22.22%。端到端的业务判定达成率，更是直接掉到了 5.3%。

到底哪儿出了问题？难道这颗将近两万星的 Rust 引擎连最基本的中文倒排索引都没做好？

带着这个疑问，我们花了一整天逐题比对原始切片与查询链路。排查完才发现，底层引擎本身的倒排逻辑完全没坏。真正把检索精度拖垮的，是三处极其隐蔽的中文工程暗坑。第一个是数字表达习惯割裂，第二个是港交所历史 PDF 排版字体错码，第三个是单字倒排切分引发的恶性过召回。

在不改动底层引擎一行 Rust 代码的前提下，我们写了一套纯 Python 标准库实现的客户端查询适配层。同一批 33,575 个分块重跑一遍基准。结果完全变了。Top 3 证据块召回率直接拉升到了 91.11%。端到端判定达成率回升到了 97.4%。

基准评测报告对应 PR #3371，两套脱敏语料仓合规收录对应 PR #3372，均已合入 xerj-org/xerj 主库。内核原生 CJK 支持在官方 Issue #3377 中跟进。评测工具包 vericorpus 也在 GitHub 开源。这篇文章完整复盘我们在排查过程中撞上的三个真实暗坑，以及客户端文本自愈的核心实现细节。

## 真实测试环境与语料规格

为了防止测试过拟合玩具数据，这次评测使用的 33,575 个分块全部来自真实合规语料，并且在单命名空间内完成建索：

- 测试机器：Apple Silicon 芯片。统一内存环境。macOS 系统。
- 引擎版本：XERJ v1.0.0-rc.101。本地监听 9200 端口。开启环境变量 XERJ_DISABLE_QUERY_CACHE=1 彻底禁用查询缓存。
- 核心语料分块组成：
  1. 法规语料：收录 29 部中国现行核心民商法与公司法。共计 3,204 条。每条单独切片保存。
  2. 临床试验表：收录 NIH 与 Europe PMC 开放获取的 55 篇临床研究。抽取 271 张规范临床三线表。
  3. 港股美股财报：包含腾讯控股 0700.HK 历年季报。外加美股 10-K 以及科创板上市招股书。
- 验证流程：检索出来的 Top 3 证据块直接推给本地严谨验证模型。若证据不足，模型必须主动拒答。

在 33,575 个分块建索过程中，建索总耗时约 9.2 秒，构建吞吐确实强悍，Rust 的高并发底子相当硬核。可是当涉及法条条款、财报数据与临床指标的测试题发过去时，实际召回表现几乎全面翻车。

## 原生检索撞墙的三大硬伤复盘

翻开召回失败的排错日志，我们原以为是 BM25 词频统计的问题。肉眼一行行对完原始文本，才发现问题全出在输入端与预处理层。

### 1. 阿拉伯数字与中文大写的法条错排

中文法律条文的正文，绝大多数严格写作“第一百四十七条”、“第三百二十条”。

但在真实业务场景中，人类用户提问会怎么搜？谁会一字不差敲出大写汉字？大家习惯输入的几乎全是“公司法第 147 条规定的董事责任是什么”。

原生 XERJ 默认的词法切分，把“第 147 条”拆成了“第”、“147”、“条”。而在索引库里，倒排索引存的全是“百”、“四十”、“七”。分词器在词表里根本对不上 147。这个最核心的限定数字权重直接归零。最后召回出来的，全是包含“公司法”、“董事”、“责任”的泛化泛读段落。真正的第 147 条核心法条被挤到了三十名开外。

核心条文漏召了。找都找不着。这一项缺陷，直接导致法规类查询的精确命中率归零。

### 2. 港交所 PDF 字体 CMap 错字与表格换行

金融人员经常处理港交所披露的繁体中文 PDF 报告。这正是非结构化 RAG 最大的痛点来源。

分析腾讯控股 0700.HK 季报时，我们发现一个离奇现象。所有涉及月份的段落，关键词检索全部落空。把提取出来的分块打印在终端，我们才看清根因：

```text
截至二零二六年九月三十日止三箇月 -> 提取成 -> 截至二零二六年九尸三十日止三箇月
```

港交所部分历史文件的嵌入字体中，字符“月”的 Unicode CMap 编码与标准字表发生了偏离。提取文本时，字符被机械解析成了“尸”。整份财报里足足出现了 341 处“九尸三十日”、“三箇尸”。标准的“月”字一处都没有。用户输入“第三季度三个月业绩”，检索器自然什么都搜不到。

遇到这种全篇错别字，底层引擎算力再强又有何用？根本搜不出。

更头疼的还有跨页表格的换行断字。财报资产负债表与收入表里，浮点数字经常发生软换行：

```text
收入总计为 39.\n9 亿美元
会计负数格式 (\n1,234.5) 百万元
```

经过默认文本切分后，小数点与后面的数字直接断裂成两半。搜索“39.9 亿”，倒排索引里只有“39.”和“9”。数字结构彻底粉碎。

### 3. 单字切分在不可回答陷阱题中的灾难性过召回

为了验证系统的抗幻觉能力，基准测试里专门埋了 4 道不可回答的陷阱题。比如针对一份并未披露海外子公司财务数据的报告，询问其海外具体收入。

理想的系统该如何响应？直接返回证据不存在，触发下游模型拒答。

可在原生 BM25 规则下，引擎采取了单字降级匹配。提问里的“海”、“外”、“收”、“入”四个单字，分别命中了财报里数千个无关段落里的单个汉字。每一次查询，引擎都硬凑并吐出 15 到 3,319 条弱相关分块。大模型的上下文窗口被塞得水泄不通。下游模型在充满噪音的上下文里强行拼凑，最终产生了严重的虚构幻觉。4 道陷阱题全军覆没。没有一道成功拒答。

## 纯标准库客户端查询自愈方案

很多团队遇到上述问题，第一反应是重写底层 Rust 分词插件，或者挂一个显卡消耗极大的 Rerank 模型。但在边缘部署或者低成本私有化场景下，真有必要为了这几个字符错误专门上一张显卡？

我们在客户端接入层写了一个轻量适配器 query_cn。整个组件不引入任何第三方 pip 包依赖，完全依靠 Python 标准库的 re、unicodedata 与字典操作实现。

处理流程清晰划分为三道工序：

```text
原始用户查询
    │
    ▼
[工序一：中英数字双向泛化]
将 "第147条" 同步展开为 "第一百四十七条" 与 "147"
    │
    ▼
[工序二：港交所 CMap 与会计表格文本修复]
消除 "月->尸" 错映，粘合 "39.\n9" 破碎浮点数
    │
    ▼
[工序三：高置信度短语约束与陷阱阻断]
强制最小词长匹配，零相关度时主动清空召回
    │
    ▼
送入 XERJ 检索端点
```

### 核心实现：数字与法条双向转换

我们用简短的代码构建了一个阿拉伯数字与中文小写大写数字的双向映射。重点是在正则识别到法条结构时，将两种表达并列推入 multi_match 候选列表：

```python
import re

CN_NUM_MAP = {
    '零': 0, '一': 1, '二': 2, '三': 3, '四': 4,
    '五': 5, '六': 6, '七': 7, '八': 8, '九': 9
}

def int_to_cn_clause(num_str: str) -> str:
    val = int(num_str)
    if val <= 10:
        return list(CN_NUM_MAP.keys())[val]
    if val < 20:
        return '十' + (list(CN_NUM_MAP.keys())[val - 10] if val > 10 else '')
    if val < 100:
        tens, units = divmod(val, 10)
        return list(CN_NUM_MAP.keys())[tens] + '十' + (list(CN_NUM_MAP.keys())[units] if units > 0 else '')
    if val < 1000:
        hundreds, rem = divmod(val, 100)
        tens, units = divmod(rem, 10)
        res = list(CN_NUM_MAP.keys())[hundreds] + '百'
        if tens > 0:
            res += list(CN_NUM_MAP.keys())[tens] + '十'
        elif units > 0:
            res += '零'
        if units > 0:
            res += list(CN_NUM_MAP.keys())[units]
        return res
    return num_str

def expand_legal_query(query: str) -> str:
    def replacer(match):
        raw_num = match.group(1)
        if raw_num.isdigit():
            cn_ver = int_to_cn_clause(raw_num)
            return f'第{raw_num}条 第{cn_ver}条'
        return match.group(0)

    return re.sub(r'第\s*(\d+)\s*条', replacer, query)
```

这样改动之后，当用户提问“公司法第 147 条”时，送往搜索引擎的关键词同时包含了原始数字和大写中文。XERJ 内部的倒排索引被瞬间击中。相关法条立刻排到首位。

### 核心实现：字体 CMap 错字安全修复

针对港交所 PDF 的“月→尸”乱码，直接全局替换可行吗？显然不行。如果把全文所有的“尸”字粗暴换成“月”，遇到医学或者法医文档里的“尸检”、“验尸”词汇，就会造成不可挽回的语义污染。

我们通过上下文正则回溯，严格把替换范围锁定在日期与月份之间：

```python
def repair_hkex_cmap_safe(text: str) -> str:
    # 严格限定在数字或者大写中文数字之后的日期语境
    pattern = r'([零一二三四五六七八九十百千0-9]{1,4})\s*尸\s*([零一二三四五六七八九十百千0-9]{1,2})\s*[日號号]'
    
    def repl_date(m):
        return f'{m.group(1)}月{m.group(2)}日'

    res = re.sub(pattern, repl_date, text)
    
    # 修复三个月、六个月等财务周期表述
    res = re.sub(r'([三六九十二\d]+)\s*箇\s*尸', r'\1箇月', res)
    res = re.sub(r'([三六九十二\d]+)\s*个\s*尸', r'\1个月', res)
    
    # 修复浮点数跨行被截断导致的破碎
    res = re.sub(r'(\d+)\.\s*\n\s*(\d+)', r'\1.\2', res)
    return res
```

在测试集里，这段代码成功修复了腾讯财报里的 341 处日期错字，且临床试验文本里的专业词汇没有出现哪怕一次误伤。逻辑很轻。非常见效。

## 改造前后对比：60 题基准数据

在同一台 Apple Silicon 机器上，保持完全相同的 XERJ 索引数据不重建。仅通过切换客户端查询适配层，我们对 33,575 个分块执行了三轮严格基准比对。

全部 60 道基准题涵盖：
- 20 道严苛的 SEC 财报与 XBRL 披露数据
- 10 道一级市场硬科技企业招股书数据
- 15 道中国现行法规与资本市场合规问答
- 15 道故意挖坑的不可回答虚构问题

三组分支的实测数据汇总如下：

| 评测分支 | 正确判定数 | 错误判定数 | 拒答命中数 | 净得分值 | 证据块 R@1 | 证据块 R@3 | 检索 p50 延迟 |
| :--- | :--- | :--- | :--- | :--- | :--- | :--- | :--- |
| 基准一：人工标注标准段落直供判定端 | 52 | 7 | 1 | 38 | 100.0% | 100.0% | 0.0 ms |
| 基准二：原生 XERJ 默认 BM25 检索 | 24 | 11 | 25 | 2 | 17.78% | 22.22% | 113.67 ms |
| 基准三：增加 query_cn 适配层检索 | 49 | 6 | 5 | 37 | 77.78% | 91.11% | 102.50 ms |

R@3 从 22.22% 提到 91.11%，拒答相关的错误判定从 25 降到 5。以人工直供标准段落作为满分基准，原生 BM25 的净得分率只有 5.3%，基本不可用；加入轻量适配层后，整体表现达到了基准满分的 97.4%。系统终于能用了。

p50 延迟没涨反而微降，从 113.67 毫秒微降到 102.50 毫秒——主要因为排除了大范围无效过召回。4 道陷阱题全部成功触发拒答，没有再被单字单词噪音带偏。一条虚构幻觉都没有产生。

## 落地建议与技术边界

做中文领域的知识库与 RAG 落地，切忌一出问题就怀疑是向量模型不够大。

别一出问题就急着换 Embedding 或者加重型重排。先查三件事：PDF 字体编码有没有修，法条编号有没有做汉字和阿拉伯数字归一，单字过召回有没有关掉。这三样不修，换多大模型都白搭。

如果你也在基于 XERJ、Elasticsearch 或者其他轻量开源引擎搭建本地知识库，建议优先对照排查以下几点：

- 你的文本预处理流水线是否包含 PDF 特殊字体编码修复？特别是财报类文档。
- 涉及条文与章节编号的字段，是否在入库与查询阶段做了汉字与阿拉伯数字的双向归一化？
- 是否对中文输入启用了过短的单字切分全量召回？遇到低相关度结果，能不能干脆利落地返回空集？

目前关于 XERJ 内核原生支持多语言与 CJK 分词增强的讨论，已经在官方 Issue #3377 中跟进。但在内核彻底更新之前，把精力放在接入层的文本清洗与查询重写上，是用最小成本换取最高确定性的工程解法。
